# G10-T06 — Data Type/Storage | Integer Overflow Risk

## ID
G10-T06

## Group
10 — Data Type/Storage

## Type
Integer Overflow Risk — Numeric Values Approaching or Exceeding the Data Type's Maximum

## Live Scenario
A retail system uses `SMALLINT` (max 32,767) for a product's running order count. After a marketing campaign drives a viral product to 33,000 orders, the INSERT fails with an arithmetic overflow error. The application's error handler doesn't distinguish overflow from a constraint violation, so it logs "Order failed" and displays a generic error page to the customer — no order is captured, no stock is reserved. Orders from 247 customers are lost. The investigation reveals the column was specified as SMALLINT "to save space" in 2019 when the product was new. The fix requires an ALTER TABLE to change to INT — a schema change requiring a maintenance window. A similar issue: a `TINYINT` used for employee count overflows at 256 employees when the company doubles in size.

## The Question
> Integer overflow occurs when a value to be stored exceeds the maximum value of the column's integer type. SQL detects overflow risk by comparing current maximum values to type limits and flagging columns where values are within a threshold of the maximum.
> **"Check the OrderID and TransactionID sequences for proximity to potential integer type limits, identify any numeric columns where the current maximum value is within 10% of a common integer type boundary, and flag potential overflow risks."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Transactions** — `schemas/05_Transactions.csv`
**Products** — `schemas/03_Products.csv`

## Solution Query

```sql
-- Step 1: Integer type limits reference and current maximums
DECLARE @TinyIntMax  INT = 255;
DECLARE @SmallIntMax INT = 32767;
DECLARE @IntMax      BIGINT = 2147483647;
DECLARE @BigIntMax   BIGINT = 9223372036854775807;

SELECT
    'Orders.OrderID' AS Column_Name,
    MAX(OrderID) AS CurrentMax,
    MIN(OrderID) AS CurrentMin,
    COUNT(*) AS RowCount,
    @IntMax AS IntMax,
    ROUND(100.0 * MAX(OrderID) / @IntMax, 4) AS PctOfIntMax,
    CASE
        WHEN MAX(OrderID) > @IntMax * 0.9
             THEN 'CRITICAL: Over 90% of INT max — overflow imminent'
        WHEN MAX(OrderID) > @IntMax * 0.5
             THEN 'WARNING: Over 50% of INT max — plan migration to BIGINT'
        WHEN MAX(OrderID) > @SmallIntMax
             THEN 'OK for INT: Exceeds SMALLINT max — do not use SMALLINT'
        WHEN MAX(OrderID) > @TinyIntMax
             THEN 'OK for INT/SMALLINT: Exceeds TINYINT max'
        ELSE 'Fits in TINYINT range'
    END AS OverflowRisk
FROM Orders
UNION ALL
SELECT
    'Transactions.TransactionID',
    MAX(CAST(TransactionID AS BIGINT)),
    MIN(CAST(TransactionID AS BIGINT)),
    COUNT(*),
    @IntMax,
    ROUND(100.0 * MAX(CAST(TransactionID AS BIGINT)) / @IntMax, 4),
    CASE
        WHEN MAX(CAST(TransactionID AS BIGINT)) > @IntMax * 0.9
             THEN 'CRITICAL: Over 90% of INT max'
        WHEN MAX(CAST(TransactionID AS BIGINT)) > @IntMax * 0.5
             THEN 'WARNING: Over 50% of INT max'
        ELSE 'Comfortably within INT range'
    END
FROM Transactions;

-- Step 2: Products.StockQuantity — check for near-max values
SELECT
    ProductID,
    ProductName,
    StockQuantity,
    CASE
        WHEN StockQuantity > 32767
             THEN 'SMALLINT OVERFLOW: Exceeds SMALLINT max (32,767)'
        WHEN StockQuantity > 32767 * 0.9
             THEN 'APPROACHING SMALLINT MAX: Over 90% of 32,767'
        WHEN StockQuantity < 0
             THEN 'NEGATIVE STOCK: Impossible unless UNSIGNED type expected'
        ELSE 'Within normal range'
    END AS StockOverflowCheck
FROM Products
ORDER BY StockQuantity DESC;

-- Step 3: Growth rate projection — when will the sequence overflow?
WITH SequenceStats AS (
    SELECT
        MIN(CAST(OrderID AS BIGINT))                          AS MinID,
        MAX(CAST(OrderID AS BIGINT))                          AS MaxID,
        MIN(CAST(OrderDate AS DATE))                          AS FirstDate,
        MAX(CAST(OrderDate AS DATE))                          AS LastDate,
        DATEDIFF(DAY, MIN(OrderDate), MAX(OrderDate)) + 1    AS DaysInRange,
        CAST(MAX(OrderID) - MIN(OrderID) AS FLOAT)
            / NULLIF(DATEDIFF(DAY, MIN(OrderDate), MAX(OrderDate)), 0)
            AS AvgIDsPerDay
    FROM Orders
)
SELECT
    MaxID AS CurrentMaxID,
    2147483647 AS IntMaxValue,
    2147483647 - MaxID AS RemainingCapacity,
    AvgIDsPerDay AS EstDailyGrowth,
    CASE
        WHEN AvgIDsPerDay > 0
             THEN CAST(ROUND((2147483647 - MaxID) / AvgIDsPerDay, 0) AS VARCHAR) + ' days until INT overflow'
        ELSE 'Cannot project — insufficient data'
    END AS OverflowProjection
FROM SequenceStats;

-- Step 4: Summary of all numeric columns vs type range
SELECT
    ColName,
    CurrentMax,
    DataTypeMax,
    ROUND(100.0 * CurrentMax / NULLIF(DataTypeMax, 0), 2) AS UtilisationPct,
    CASE
        WHEN 100.0 * CurrentMax / NULLIF(DataTypeMax, 0) > 90
             THEN 'OVERFLOW IMMINENT: Change type immediately'
        WHEN 100.0 * CurrentMax / NULLIF(DataTypeMax, 0) > 50
             THEN 'MONITOR: Plan capacity increase'
        ELSE 'Comfortable headroom'
    END AS CapacityStatus
FROM (
    SELECT 'Orders.OrderID'          AS ColName, MAX(OrderID) AS CurrentMax, 2147483647 AS DataTypeMax FROM Orders
    UNION ALL
    SELECT 'Products.StockQuantity', MAX(StockQuantity), 2147483647 FROM Products
) NumericAudit
ORDER BY UtilisationPct DESC;
```

## Explanation

**Integer type ranges**
- `TINYINT`: 0 to 255 (1 byte)
- `SMALLINT`: -32,768 to 32,767 (2 bytes)
- `INT`: -2,147,483,648 to 2,147,483,647 (4 bytes)
- `BIGINT`: -9,223,372,036,854,775,808 to 9,223,372,036,854,775,807 (8 bytes)

The `OverflowRisk` CASE applies these boundaries. `SMALLINT` is the most common mistake: chosen to "save space" when a column starts small, then overflows after years of growth.

**Growth rate projection**
`(MaxID - MinID) / DaysInRange` estimates IDs consumed per day. `(IntMax - CurrentMax) / DailyRate` projects days until overflow. This is a linear projection that assumes constant growth; in practice, growth accelerates. Monitoring should trigger at 50% capacity to allow enough lead time for a BIGINT migration.

**Sequence overflow vs natural values**
For identity columns (auto-increment sequences), overflow is a capacity planning issue. For natural values (StockQuantity, employee count), overflow indicates the column was sized for a business scale that has since been exceeded. Both require ALTER TABLE — but sequence overflow is often more urgent because inserts fail immediately.

**CAST to BIGINT before comparison**
`MAX(CAST(TransactionID AS BIGINT))` prevents overflow during the aggregation itself. If TransactionID is already INT and its values approach INT max, a `MAX(TransactionID)` comparison to an INT literal could itself overflow. Casting to BIGINT first gives headroom.

## Severity
**Critical** — Integer overflow causes hard failures: INSERT statements throw arithmetic overflow errors, disrupting all write operations to the affected table. Unlike soft errors (wrong data), overflow is an availability failure — the application cannot accept new data. A BIGINT migration on a large production table requires careful planning (online schema change, minimal downtime strategy).
