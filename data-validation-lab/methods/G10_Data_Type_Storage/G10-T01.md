# G10-T01 — Data Type/Storage | Implicit Type Conversion Error

## ID
G10-T01

## Group
10 — Data Type/Storage

## Type
Implicit Type Conversion Error — Comparison or Join Fails Due to Mismatched Column Data Types

## Live Scenario
A data warehouse query joins a fact table (`SalesTransactions.CustomerID` stored as `VARCHAR(20)`) to a dimension table (`Customers.CustomerID` stored as `INT`). SQL Server performs an implicit conversion on every row to make the join work. The query runs correctly but a performance review reveals it is 40× slower than expected: the implicit conversion on the VARCHAR side prevents the index from being used, causing a full table scan of 12 million rows. Additionally, a CustomerID of "0123" in the fact table matches CustomerID 123 in the dimension (leading zeros dropped during conversion), linking transactions to the wrong customer. The fix requires a migration to align data types — a 3-week project that a 5-minute data type review at design time would have prevented.

## The Question
> Implicit type conversion occurs when SQL Server silently converts one data type to another to satisfy a comparison or join. It causes index suppression (poor performance), incorrect matches (leading zeros), and potential runtime errors (string-to-number conversion failures). SQL detects likely implicit conversions by identifying joins and filters where column data types differ.
> **"Identify columns in Orders and Transactions where values stored as VARCHAR can be safely cast to numeric or date types, and flag any values that would fail conversion — indicating the column stores mixed types."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Transactions** — `schemas/05_Transactions.csv`

## Solution Query

```sql
-- Step 1: Test if string columns contain values that look numeric
-- (Detects VARCHAR columns being used to store numeric IDs)
SELECT
    'Orders.OrderID'  AS ColumnReference,
    COUNT(*)          AS TotalRows,
    SUM(CASE WHEN TRY_CAST(CAST(OrderID AS VARCHAR) AS INT) IS NOT NULL THEN 1 ELSE 0 END)
        AS NumericCompatible,
    SUM(CASE WHEN TRY_CAST(CAST(OrderID AS VARCHAR) AS INT) IS NULL THEN 1 ELSE 0 END)
        AS NonNumericOrNull,
    CASE
        WHEN SUM(CASE WHEN TRY_CAST(CAST(OrderID AS VARCHAR) AS INT) IS NULL THEN 1 ELSE 0 END) = 0
             THEN 'All values are numeric — consider INT type'
        ELSE 'Mixed: some non-numeric values present'
    END AS TypeRecommendation
FROM Orders
UNION ALL
SELECT
    'Transactions.TransactionID',
    COUNT(*),
    SUM(CASE WHEN TRY_CAST(CAST(TransactionID AS VARCHAR) AS INT) IS NOT NULL THEN 1 ELSE 0 END),
    SUM(CASE WHEN TRY_CAST(CAST(TransactionID AS VARCHAR) AS INT) IS NULL THEN 1 ELSE 0 END),
    CASE
        WHEN SUM(CASE WHEN TRY_CAST(CAST(TransactionID AS VARCHAR) AS INT) IS NULL THEN 1 ELSE 0 END) = 0
             THEN 'All values are numeric — consider INT type'
        ELSE 'Mixed: some non-numeric values present'
    END
FROM Transactions;

-- Step 2: Detect VARCHAR amount fields that should be DECIMAL
-- TotalAmount stored as VARCHAR would be a type mismatch risk
SELECT
    'Orders.TotalAmount as VARCHAR'  AS TestColumn,
    COUNT(*) AS TotalRows,
    SUM(CASE WHEN TRY_CAST(CAST(TotalAmount AS VARCHAR) AS DECIMAL(18,2)) IS NOT NULL
             THEN 1 ELSE 0 END) AS ValidDecimal,
    SUM(CASE WHEN TRY_CAST(CAST(TotalAmount AS VARCHAR) AS DECIMAL(18,2)) IS NULL
             THEN 1 ELSE 0 END) AS InvalidOrNull,
    MIN(TotalAmount) AS MinValue,
    MAX(TotalAmount) AS MaxValue
FROM Orders;

-- Step 3: Verify that join keys use the same effective value after conversion
-- Detects leading-zero truncation: '0123' (VARCHAR) → 123 (INT) ≠ original intent
WITH OrderIDs AS (
    SELECT DISTINCT OrderID, CAST(OrderID AS VARCHAR(20)) AS OrderIDStr
    FROM Orders
),
TxOrderIDs AS (
    SELECT DISTINCT OrderID, CAST(OrderID AS VARCHAR(20)) AS OrderIDStr
    FROM Transactions
)
SELECT
    o.OrderID,
    o.OrderIDStr AS OrderIDStringForm,
    t.OrderID AS TxOrderID,
    CASE
        WHEN o.OrderIDStr <> t.OrderIDStr
             THEN 'TYPE MISMATCH RISK: String forms differ after conversion'
        WHEN o.OrderID = t.OrderID
             THEN 'Join would succeed correctly'
        ELSE 'No match'
    END AS ConversionRisk
FROM OrderIDs o
FULL OUTER JOIN TxOrderIDs t ON o.OrderID = t.OrderID;

-- Step 4: Implicit conversion impact — counts values that cannot be compared across types
SELECT
    t.TransactionID,
    t.OrderID AS TxOrderID,
    o.OrderID AS OrderTableID,
    CASE
        WHEN o.OrderID IS NULL
             THEN 'NO MATCH: Transaction references non-existent order'
        ELSE 'JOINED: OrderID matched across tables'
    END AS JoinResult,
    CASE
        WHEN TRY_CAST(t.Currency AS INT) IS NOT NULL
             THEN 'TYPE CONCERN: Currency column holds numeric-looking value'
        ELSE 'Currency value type is appropriate'
    END AS CurrencyTypeCheck
FROM Transactions t
LEFT JOIN Orders o ON t.OrderID = o.OrderID
WHERE o.OrderID IS NULL;
```

## Explanation

**TRY_CAST for safe type probing**
`TRY_CAST(expression AS target_type)` returns NULL instead of raising an error when conversion fails. This makes it safe to probe whether a column's values are compatible with a different type — `SUM(CASE WHEN TRY_CAST(...) IS NULL THEN 1 ELSE 0 END)` counts conversion failures. `CAST` would throw a runtime error on the first failure.

**Implicit conversion and index suppression**
When SQL Server implicitly converts the indexed column (e.g., `WHERE VarcharCol = IntegerValue`), it must apply the conversion function to every row in the index, preventing the index seek. The query plan shows a "CONVERT_IMPLICIT" warning. The fix: ensure the compared values are the same data type, putting the conversion on the constant rather than the column.

**Leading zero integrity**
`'0123'` as VARCHAR and `123` as INT are not the same value. If a system uses zero-padded identifiers (common in batch IDs, account numbers, product codes), storing them as INT silently drops the padding. The convention `CAST(OrderID AS VARCHAR(20))` in Step 3 checks whether the string representation matches between the two tables.

**TRY_CAST vs ISNUMERIC**
`ISNUMERIC('1e2')` returns 1 (it evaluates to TRUE for scientific notation), but `TRY_CAST('1e2' AS INT)` returns NULL (it's not a valid INT). TRY_CAST is more precise for type-specific validation; ISNUMERIC should be avoided for data validation.

## Severity
**High** — Implicit type conversions cause silent incorrect results (wrong joins, dropped leading zeros), severe performance degradation (index suppression on large tables), and runtime errors when a conversion that "always worked" encounters an unexpected value. Type alignment is a foundation of correct SQL design.
