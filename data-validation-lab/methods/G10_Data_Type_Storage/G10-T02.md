# G10-T02 — Data Type/Storage | Numeric Precision Loss

## ID
G10-T02

## Group
10 — Data Type/Storage

## Type
Numeric Precision Loss — Rounding or Truncation Caused by Inadequate Column Precision

## Live Scenario
A financial trading system stores trade prices in a `FLOAT` column. Floating-point arithmetic means that 0.1 + 0.2 = 0.30000000000000004 — a rounding error inherent to IEEE 754 binary floating-point representation. Over 10,000 daily trades, the accumulated rounding error causes the end-of-day position calculation to differ from the true value by £847. This exceeds the firm's £500 reconciliation tolerance, triggering a manual investigation that takes 4 hours. The root cause: the column should be `DECIMAL(18,6)`, not `FLOAT`. Similarly, a unit price of £0.0033 stored as `DECIMAL(10,2)` is rounded to £0.00 — every item appears free.

## The Question
> Numeric precision loss occurs when a value cannot be represented exactly in the column's data type, causing rounding or truncation. SQL detects this by comparing stored values to recomputed values, and by identifying columns where precision appears insufficient for the values they contain.
> **"Identify Orders where TotalAmount appears to have been rounded (fewer decimal places than expected), detect any TotalAmount values that are suspiciously round (possible precision loss), and validate that amounts are stored with sufficient decimal precision."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Transactions** — `schemas/05_Transactions.csv`

## Solution Query

```sql
-- Step 1: Check decimal precision of amount values
SELECT
    'Orders.TotalAmount' AS ColumnName,
    COUNT(*) AS TotalRows,
    SUM(CASE WHEN TotalAmount = ROUND(TotalAmount, 0) THEN 1 ELSE 0 END) AS WholeNumbers,
    SUM(CASE WHEN TotalAmount = ROUND(TotalAmount, 1)
              AND TotalAmount <> ROUND(TotalAmount, 0) THEN 1 ELSE 0 END) AS OneDecimalPlace,
    SUM(CASE WHEN TotalAmount = ROUND(TotalAmount, 2)
              AND TotalAmount <> ROUND(TotalAmount, 1) THEN 1 ELSE 0 END) AS TwoDecimalPlaces,
    SUM(CASE WHEN TotalAmount <> ROUND(TotalAmount, 2) THEN 1 ELSE 0 END) AS MoreThanTwoDecimals,
    MIN(TotalAmount) AS MinAmount,
    MAX(TotalAmount) AS MaxAmount,
    AVG(TotalAmount) AS AvgAmount
FROM Orders
UNION ALL
SELECT
    'Transactions.Amount',
    COUNT(*),
    SUM(CASE WHEN Amount = ROUND(Amount, 0) THEN 1 ELSE 0 END),
    SUM(CASE WHEN Amount = ROUND(Amount, 1) AND Amount <> ROUND(Amount, 0) THEN 1 ELSE 0 END),
    SUM(CASE WHEN Amount = ROUND(Amount, 2) AND Amount <> ROUND(Amount, 1) THEN 1 ELSE 0 END),
    SUM(CASE WHEN Amount <> ROUND(TRY_CAST(Amount AS DECIMAL(18,2)), 2) THEN 1 ELSE 0 END),
    MIN(Amount),
    MAX(Amount),
    AVG(Amount)
FROM Transactions;

-- Step 2: Detect suspiciously round amounts — possible precision loss
SELECT
    OrderID,
    TotalAmount,
    CASE
        WHEN TotalAmount = ROUND(TotalAmount, -3) AND TotalAmount > 0
             THEN 'PRECISION CONCERN: Amount is exact multiple of 1000 — truncation possible'
        WHEN TotalAmount = ROUND(TotalAmount, -2) AND TotalAmount > 100
             THEN 'REVIEW: Amount is exact multiple of 100 — verify precision'
        WHEN TotalAmount = ROUND(TotalAmount, 0) AND TotalAmount > 0
             THEN 'Whole number — acceptable if product pricing has no pence'
        WHEN ABS(TotalAmount - ROUND(TotalAmount, 2)) > 0.001
             THEN 'EXCESS PRECISION: Amount has more than 2 decimal places — check storage type'
        ELSE 'Normal precision'
    END AS PrecisionFlag,
    -- Show what the value would be at different precisions
    ROUND(TotalAmount, 0) AS RoundedTo0dp,
    ROUND(TotalAmount, 2) AS RoundedTo2dp
FROM Orders
WHERE TotalAmount = ROUND(TotalAmount, -2)
   OR ABS(TotalAmount - ROUND(TotalAmount, 2)) > 0.001
ORDER BY TotalAmount DESC;

-- Step 3: Floating-point risk — detect values that differ from their DECIMAL equivalent
-- FLOAT columns introduce rounding errors; DECIMAL columns are exact
SELECT
    TransactionID,
    Amount,
    CAST(Amount AS DECIMAL(18,2)) AS AsDecimal,
    ABS(Amount - CAST(Amount AS DECIMAL(18,2))) AS PrecisionError,
    CASE
        WHEN ABS(Amount - CAST(CAST(Amount AS DECIMAL(18,2)) AS FLOAT)) > 0.001
             THEN 'FLOAT PRECISION LOSS: Value differs from DECIMAL representation'
        ELSE 'Acceptable precision'
    END AS FloatRisk
FROM Transactions
WHERE ABS(Amount - CAST(CAST(Amount AS DECIMAL(18,2)) AS FLOAT)) > 0.001;

-- Step 4: Unit price check — Products with prices that lose precision at 2dp
SELECT
    ProductID,
    ProductName,
    Price,
    ROUND(Price, 2) AS PriceAt2dp,
    ABS(Price - ROUND(Price, 2)) AS PrecisionLossAt2dp,
    CASE
        WHEN Price < 0.01 AND Price > 0
             THEN 'SUB-PENNY PRICE: Will round to £0.00 if stored as DECIMAL(10,2)'
        WHEN ABS(Price - ROUND(Price, 2)) > 0.0001
             THEN 'PRECISION REQUIRED: Price needs more than 2dp — use DECIMAL(18,4)'
        ELSE 'Two decimal places sufficient'
    END AS PrecisionRecommendation
FROM Products
WHERE Price < 0.01 OR ABS(Price - ROUND(Price, 2)) > 0.0001;
```

## Explanation

**ROUND(value, -n) for multiple-of-10 detection**
`ROUND(Amount, -2)` rounds to the nearest hundred; if `Amount = ROUND(Amount, -2)`, the amount is an exact multiple of 100. `ROUND(Amount, -3)` detects multiples of 1000. These round-number checks identify values that may have been truncated during storage or import.

**DECIMAL vs FLOAT for financial data**
`DECIMAL(18,2)` stores exact values: 0.10 is 0.10. `FLOAT` stores binary approximations: 0.1 in float is 0.1000000000000000055511151231257827021181583404541015625. For currency, always use DECIMAL. The precision loss `ABS(Amount - CAST(CAST(Amount AS DECIMAL(18,2)) AS FLOAT))` measures how much a value would change if stored as FLOAT.

**Sub-penny pricing**
A `DECIMAL(10,2)` column cannot represent values between 0 and 0.01. If a product costs £0.005, it rounds to £0.01 (standard rounding) or £0.00 (truncation) — a 100% or infinite error respectively. Products with prices below one pence require at least `DECIMAL(10,4)` for accurate representation.

**ABS() for precision symmetry**
`ABS(Price - ROUND(Price, 2)) > 0.0001` catches both positive and negative rounding errors. Without ABS, `1.235 - 1.24 = -0.005` would be negative and fail a `> 0` check. A threshold of 0.0001 (one hundredth of a penny) avoids floating-point noise while catching real precision issues.

## Severity
**High** — Precision loss in financial calculations violates accounting accuracy requirements. In trading systems, accumulated rounding errors can cause position mismatches and failed reconciliations. In retail, sub-penny product pricing stored in 2dp columns causes systematic undercharging or overcharging multiplied across millions of transactions.
