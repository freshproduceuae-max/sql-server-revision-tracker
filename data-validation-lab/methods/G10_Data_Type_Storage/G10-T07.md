# G10-T07 — Data Type/Storage | Date/Time Timezone Inconsistency

## ID
G10-T07

## Group
10 — Data Type/Storage

## Type
Date/Time Timezone Inconsistency — Timestamps Without Timezone Context Mixed With Offset-Aware Values

## Live Scenario
A global logistics platform stores shipment timestamps in a `DATETIME` column without timezone information. The web server in London records "14:30" for a parcel scan. The warehouse in New York records "14:30" for the same parcel's next scan — but it is 09:30 UTC when the New York scan happens (New York is UTC-5). The system calculates transit time as 0 hours (14:30 → 14:30) when the true transit time is 5 hours. A parcel that should be flagged as overdue (transit > 4 hours) is not flagged. Separately, a daylight saving time (DST) transition causes all timestamps from one Sunday to be 1 hour wrong: `DATETIME` has no timezone awareness so the DST shift cannot be applied retroactively.

## The Question
> Timezone inconsistency occurs when timestamps from different timezones are stored in the same column without timezone context, making time differences meaningless. SQL detects timezone issues by checking for timestamp clustering patterns that suggest timezone mixing, and validates that time-difference calculations are consistent.
> **"Identify Transactions and Orders where the time difference between TransactionDate and OrderDate is negative (impossible without timezone errors), check for temporal clustering that suggests timezone offsets, and flag records where timing appears inconsistent."**

## Table Reference
**Transactions** — `schemas/05_Transactions.csv`
**Orders** — `schemas/02_Orders.csv`

## Solution Query

```sql
-- Step 1: Detect impossible negative time differences (timezone offset clue)
SELECT
    t.TransactionID,
    t.OrderID,
    o.OrderDate,
    t.TransactionDate,
    DATEDIFF(HOUR, o.OrderDate, t.TransactionDate) AS HourDiff,
    DATEDIFF(MINUTE, o.OrderDate, t.TransactionDate) AS MinuteDiff,
    CASE
        WHEN DATEDIFF(MINUTE, o.OrderDate, t.TransactionDate) < 0
             THEN 'TIMEZONE CLUE: Transaction before order by '
                  + CAST(ABS(DATEDIFF(MINUTE, o.OrderDate, t.TransactionDate)) AS VARCHAR)
                  + ' minutes — possible timezone offset of '
                  + CAST(ROUND(ABS(DATEDIFF(MINUTE, o.OrderDate, t.TransactionDate)) / 60.0, 1) AS VARCHAR)
                  + 'h'
        WHEN DATEDIFF(HOUR, o.OrderDate, t.TransactionDate) < 0
             THEN 'IMPOSSIBLE: Transaction recorded hours before order — timezone error likely'
        ELSE 'Sequence OK'
    END AS TimezoneFlag
FROM Transactions t
JOIN Orders o ON t.OrderID = o.OrderID
WHERE DATEDIFF(MINUTE, o.OrderDate, t.TransactionDate) < 0;

-- Step 2: Hour-of-day distribution — detect bimodal patterns suggesting timezone mixing
SELECT
    DATEPART(HOUR, TransactionDate) AS HourOfDay,
    COUNT(*) AS TransactionCount,
    ROUND(100.0 * COUNT(*) / SUM(COUNT(*)) OVER (), 1) AS Pct,
    REPLICATE('|', COUNT(*)) AS BarChart
FROM Transactions
WHERE TransactionDate IS NOT NULL
GROUP BY DATEPART(HOUR, TransactionDate)
ORDER BY HourOfDay;

-- Step 3: Check for common UTC offsets — time diff clusters at timezone boundaries
WITH TimeDiffs AS (
    SELECT
        DATEDIFF(MINUTE, o.OrderDate, t.TransactionDate) AS MinuteDiff
    FROM Transactions t
    JOIN Orders o ON t.OrderID = o.OrderID
    WHERE t.TransactionDate >= o.OrderDate
)
SELECT
    CASE
        WHEN MinuteDiff BETWEEN -30  AND 30   THEN 'UTC (or same timezone)'
        WHEN MinuteDiff BETWEEN 60   AND 120  THEN 'UTC+1 to UTC+2 (CET/BST)'
        WHEN MinuteDiff BETWEEN 270  AND 330  THEN 'UTC+5'
        WHEN MinuteDiff BETWEEN 300  AND 360  THEN 'UTC-5 (US Eastern) or UTC+5'
        WHEN MinuteDiff BETWEEN 420  AND 480  THEN 'UTC-7/-8 (US Pacific/Mountain)'
        WHEN MinuteDiff BETWEEN 480  AND 600  THEN 'UTC+8 (China/Singapore)'
        ELSE 'Other offset: ' + CAST(MinuteDiff AS VARCHAR) + ' minutes'
    END AS LikelyTimezone,
    COUNT(*) AS Count,
    AVG(MinuteDiff) AS AvgMinutes,
    MIN(MinuteDiff) AS MinMinutes,
    MAX(MinuteDiff) AS MaxMinutes
FROM TimeDiffs
GROUP BY
    CASE
        WHEN MinuteDiff BETWEEN -30  AND 30   THEN 'UTC (or same timezone)'
        WHEN MinuteDiff BETWEEN 60   AND 120  THEN 'UTC+1 to UTC+2 (CET/BST)'
        WHEN MinuteDiff BETWEEN 270  AND 330  THEN 'UTC+5'
        WHEN MinuteDiff BETWEEN 300  AND 360  THEN 'UTC-5 (US Eastern) or UTC+5'
        WHEN MinuteDiff BETWEEN 420  AND 480  THEN 'UTC-7/-8 (US Pacific/Mountain)'
        WHEN MinuteDiff BETWEEN 480  AND 600  THEN 'UTC+8 (China/Singapore)'
        ELSE 'Other offset: ' + CAST(MinuteDiff AS VARCHAR) + ' minutes'
    END
ORDER BY Count DESC;

-- Step 4: DST boundary check — transactions at exactly :00 or :30 minutes after a DST transition
-- UK DST transitions: last Sunday of March (spring forward) and October (fall back)
-- Look for clustering of transactions around 01:00-02:00 AM UTC which is when DST changes
SELECT
    CAST(TransactionDate AS DATE) AS TxDate,
    DATEPART(HOUR, TransactionDate) AS TxHour,
    COUNT(*) AS TxCount,
    CASE
        WHEN DATEPART(HOUR, TransactionDate) IN (0, 1, 2)
         AND DATEPART(WEEKDAY, TransactionDate) = 1  -- Sunday
             THEN 'DST RISK: Early Sunday morning — check for clock change'
        ELSE 'Normal time'
    END AS DSTRisk
FROM Transactions
GROUP BY CAST(TransactionDate AS DATE), DATEPART(HOUR, TransactionDate)
HAVING DATEPART(WEEKDAY, CAST(TransactionDate AS DATE)) = 1
   AND DATEPART(HOUR, TransactionDate) IN (0, 1, 2)
ORDER BY TxDate, TxHour;
```

## Explanation

**DATETIME has no timezone**
SQL Server's `DATETIME` and `DATETIME2` types store local time with no timezone indicator. `DATETIMEOFFSET` stores UTC offset alongside the timestamp. When systems in different timezones write to a `DATETIME` column, times are compared as if they were the same timezone — producing errors proportional to the timezone difference.

**Bimodal distribution as a timezone signal**
If legitimate business hours are 09:00–17:00 but the data shows two peaks (09:00–11:00 and 14:00–17:00), it may indicate data from two timezones: one in UTC and one in UTC+5. A normal single-timezone dataset shows a single peak. Step 2's hour distribution reveals this pattern visually.

**DST transition vulnerability**
When clocks "spring forward" (e.g., 01:00 → 02:00), there is no 01:30. When clocks "fall back" (02:00 → 01:00), 01:30 occurs twice. `DATETIME` stores the clock time without knowing which occurrence. Step 4 flags Sunday early-morning transactions for DST review — the highest-risk window.

**The correct solution: DATETIMEOFFSET**
`DATETIMEOFFSET` stores the UTC offset with the timestamp: `2024-03-31 14:30:00 +00:00` (London) vs `2024-03-31 14:30:00 -05:00` (New York). Converting both to UTC: London = 14:30, New York = 19:30 — a 5-hour difference, correctly calculated. For new systems, always use DATETIMEOFFSET or store UTC in DATETIME2.

## Severity
**High** — Timezone errors make all time-difference calculations unreliable. Elapsed time, SLA calculations, audit trails, and chronological ordering are all affected. In global systems, the errors are not random but systematic — all events from a particular region are consistently offset by the same number of hours.
