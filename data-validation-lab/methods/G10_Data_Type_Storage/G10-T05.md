# G10-T05 — Data Type/Storage | Unicode and Encoding Issues

## ID
G10-T05

## Group
10 — Data Type/Storage

## Type
Unicode and Encoding Issues — Characters Stored Incorrectly Due to Encoding Mismatches

## Live Scenario
A UK retailer acquires a French subsidiary. Customer records from the French CRM (encoded in UTF-8) are imported into the UK database (using Latin1/ISO-8859-1 collation). French names containing accented characters (é, à, ç, ü) are imported into `VARCHAR` columns instead of `NVARCHAR`. SQL Server stores the accented characters using the column's code page, but characters outside the code page are converted to the nearest ASCII equivalent or replaced with '?'. "Léa Dupont" becomes "Lea Dupont"; "François" becomes "Francois". 847 customer records lose their correct name rendering. Customer letters addressed to "Lea" instead of "Léa" are considered disrespectful and generate complaints. The fix requires an `ALTER TABLE` to change VARCHAR to NVARCHAR — a table rebuild on a 3-million-row customer table.

## The Question
> Unicode encoding issues arise when non-ASCII characters are stored in narrow (VARCHAR) columns or when data from different code pages is mixed. SQL detects encoding issues by checking for non-ASCII characters, Unicode surrogates, and characters that differ between their VARCHAR and NVARCHAR representations.
> **"Identify Customer names and emails that contain non-ASCII characters (which require NVARCHAR storage), detect any characters that have been corrupted by encoding conversion, and flag fields where Unicode characters are present."**

## Table Reference
**Customers** — `schemas/01_Customers.csv`
**Products** — `schemas/03_Products.csv`

## Solution Query

```sql
-- Step 1: Detect non-ASCII characters in string columns
-- ASCII characters have codes 0-127; extended/Unicode are >127
SELECT
    CustomerID,
    FirstName,
    LastName,
    Email,
    LEN(FirstName)       AS FirstNameLen,
    DATALENGTH(FirstName) AS FirstNameBytes,
    -- For NVARCHAR, DATALENGTH = LEN * 2 (2 bytes per char)
    -- For VARCHAR, DATALENGTH ≈ LEN (1 byte per ASCII char, more for extended)
    CASE
        WHEN FirstName LIKE '%[^' + CHAR(0) + '-' + CHAR(127) + ']%'  COLLATE Latin1_General_BIN
             THEN 'CONTAINS NON-ASCII: FirstName has extended/Unicode characters'
        ELSE 'ASCII only'
    END AS FirstNameEncoding,
    CASE
        WHEN LastName LIKE '%[^' + CHAR(0) + '-' + CHAR(127) + ']%'  COLLATE Latin1_General_BIN
             THEN 'CONTAINS NON-ASCII: LastName has extended/Unicode characters'
        ELSE 'ASCII only'
    END AS LastNameEncoding,
    CASE
        WHEN Email LIKE '%[^' + CHAR(0) + '-' + CHAR(127) + ']%'  COLLATE Latin1_General_BIN
             THEN 'NON-ASCII EMAIL: Internationalised email address — verify RFC 6530 support'
        ELSE 'ASCII email'
    END AS EmailEncoding
FROM Customers
WHERE FirstName LIKE '%[^' + CHAR(0) + '-' + CHAR(127) + ']%' COLLATE Latin1_General_BIN
   OR LastName  LIKE '%[^' + CHAR(0) + '-' + CHAR(127) + ']%' COLLATE Latin1_General_BIN
   OR Email     LIKE '%[^' + CHAR(0) + '-' + CHAR(127) + ']%' COLLATE Latin1_General_BIN;

-- Step 2: Detect question-mark substitution (the '?' replacement character)
-- When encoding conversion fails, characters are often replaced with '?'
SELECT
    CustomerID,
    FirstName,
    LastName,
    CHARINDEX('?', FirstName) AS QuestionMarkPosFirst,
    CHARINDEX('?', LastName)  AS QuestionMarkPosLast,
    CASE
        WHEN CHARINDEX('?', FirstName) > 0
             THEN 'ENCODING CORRUPTION: ''?'' in FirstName — likely failed character conversion'
        WHEN CHARINDEX('?', LastName) > 0
             THEN 'ENCODING CORRUPTION: ''?'' in LastName — likely failed character conversion'
        ELSE 'No substitution detected'
    END AS CorruptionFlag
FROM Customers
WHERE CHARINDEX('?', FirstName) > 0
   OR CHARINDEX('?', LastName)  > 0;

-- Step 3: Detect smart quotes and typographic characters (common copy-paste encoding issues)
SELECT
    o.OrderID,
    o.Notes,
    CASE
        WHEN o.Notes LIKE N'%' + NCHAR(8216) + N'%'  -- Left single quotation mark '
          OR o.Notes LIKE N'%' + NCHAR(8217) + N'%'  -- Right single quotation mark '
             THEN 'SMART QUOTE: Single smart quotes present — may corrupt on export'
        ELSE 'No smart quotes'
    END AS SmartQuoteFlag,
    CASE
        WHEN o.Notes LIKE N'%' + NCHAR(8220) + N'%'  -- Left double quotation mark "
          OR o.Notes LIKE N'%' + NCHAR(8221) + N'%'  -- Right double quotation mark "
             THEN 'SMART QUOTE: Double smart quotes present'
        ELSE 'No smart double quotes'
    END AS SmartDoubleQuoteFlag,
    CASE
        WHEN o.Notes LIKE N'%' + NCHAR(8211) + N'%'  -- En dash –
          OR o.Notes LIKE N'%' + NCHAR(8212) + N'%'  -- Em dash —
             THEN 'TYPOGRAPHIC DASH: En/em dash present — may display as ?? in narrow columns'
        ELSE 'No typographic dashes'
    END AS DashFlag
FROM Orders o
WHERE o.Notes IS NOT NULL;

-- Step 4: Column storage type audit — VARCHAR vs NVARCHAR recommendation
SELECT
    ColName,
    MaxLen,
    HasNonASCII,
    CASE
        WHEN HasNonASCII = 1
             THEN 'NVARCHAR REQUIRED: Column contains Unicode characters — VARCHAR will corrupt'
        WHEN MaxLen > 4000
             THEN 'VARCHAR(MAX) or NVARCHAR(MAX): Long text requires MAX type'
        ELSE 'VARCHAR acceptable: all content is ASCII'
    END AS TypeRecommendation
FROM (
    SELECT 'Customers.FirstName' AS ColName, MAX(LEN(FirstName)) AS MaxLen,
           MAX(CASE WHEN FirstName LIKE '%[^' + CHAR(0)+'-'+CHAR(127)+']%'
                         COLLATE Latin1_General_BIN THEN 1 ELSE 0 END) AS HasNonASCII
    FROM Customers
    UNION ALL
    SELECT 'Customers.LastName', MAX(LEN(LastName)),
           MAX(CASE WHEN LastName LIKE '%[^' + CHAR(0)+'-'+CHAR(127)+']%'
                         COLLATE Latin1_General_BIN THEN 1 ELSE 0 END)
    FROM Customers
    UNION ALL
    SELECT 'Orders.Notes', MAX(LEN(Notes)),
           MAX(CASE WHEN Notes LIKE '%[^' + CHAR(0)+'-'+CHAR(127)+']%'
                         COLLATE Latin1_General_BIN THEN 1 ELSE 0 END)
    FROM Orders WHERE Notes IS NOT NULL
) TypeAudit;
```

## Explanation

**ASCII range check with COLLATE BIN**
`FirstName LIKE '%[^CHAR(0)-CHAR(127)]%' COLLATE Latin1_General_BIN` uses a binary collation for the check, ensuring character code comparisons are by byte value rather than linguistic equivalence. Without the binary collation, some case-insensitive collations may not correctly identify extended characters.

**DATALENGTH vs LEN for encoding detection**
For `VARCHAR` columns, `DATALENGTH = LEN` (approximately — excluding trailing spaces). For `NVARCHAR`, `DATALENGTH = LEN × 2`. If `DATALENGTH > LEN × 2`, the column contains multi-byte sequences (possible in UTF-8 contexts). This ratio check can indicate encoding type.

**Question mark as the corruption signature**
When a character cannot be represented in the target code page during a VARCHAR conversion, SQL Server (and many ORMs) substitute `?`. A name containing `?` is almost certainly corrupted — genuine use of `?` in a person's name is exceedingly rare. Step 2 targets this specific pattern.

**NCHAR() for specific Unicode code points**
`NCHAR(8216)` returns the Unicode left single quotation mark (U+2018). This only works if the query uses `N'...'` prefix for the literal. Smart quotes are a common source of encoding issues because they look like ASCII apostrophes but have different code points, causing failures in XML, JSON, and SQL string literals.

## Severity
**Medium** — Encoding errors corrupt personal data (incorrect names), cause search failures (searching for "François" returns nothing if stored as "Francois"), and may violate data accuracy requirements under GDPR. For multilingual systems, encoding failures systematically exclude non-English-speaking users from correct representation.
