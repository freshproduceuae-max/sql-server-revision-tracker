# G10-T10 — Data Type/Storage | Boolean/Flag Field Misuse

## ID
G10-T10

## Group
10 — Data Type/Storage

## Type
Boolean/Flag Field Misuse — Bit or Flag Columns Containing Values Outside the Expected Boolean Range

## Live Scenario
A customer management system stores `IsActive` as a `BIT` column (0 = inactive, 1 = active). A data migration from a legacy Oracle system stores "Y"/"N" strings instead of 1/0. SQL Server accepts 'Y' as a BIT value (it truncates to the bit, and 'Y' has ASCII value 89 which is non-zero, so it stores as 1 — or raises a conversion error, depending on the driver). A second legacy source uses 2 for "pending review" — an undocumented third state in a BIT column that can only store 0 or 1. The ETL silently converts 2 to 1 (non-zero = TRUE), making "pending review" customers appear active. 847 customers under review receive marketing emails, causing GDPR concerns about processing data for customers whose accounts are under investigation.

## The Question
> Boolean/flag fields should contain only the expected set of values (0/1, TRUE/FALSE, Y/N, or a defined set). SQL detects flag field misuse by querying the distinct values and comparing them to the expected value set, and identifying records where flag values have unexpected combinations.
> **"Audit all flag and status fields in Customers and Products: verify that IsActive contains only 0 and 1, that Status contains only expected values, and flag any records where flag field combinations are logically inconsistent."**

## Table Reference
**Customers** — `schemas/01_Customers.csv`
**Products** — `schemas/03_Products.csv`
**Orders** — `schemas/02_Orders.csv`

## Solution Query

```sql
-- Step 1: Distinct value audit for flag/boolean columns
SELECT 'Customers.IsActive' AS FlagColumn, CAST(IsActive AS VARCHAR) AS Value, COUNT(*) AS Count
FROM Customers
GROUP BY IsActive
UNION ALL
SELECT 'Products.IsActive', CAST(IsActive AS VARCHAR), COUNT(*)
FROM Products
GROUP BY IsActive
ORDER BY FlagColumn, Value;

-- Step 2: Validate IsActive contains only expected values (0 and 1)
SELECT
    'Customers.IsActive' AS Column_Name,
    IsActive,
    COUNT(*) AS RowCount,
    CASE
        WHEN IsActive NOT IN (0, 1)
             THEN 'INVALID: Expected 0 or 1 only — found ' + CAST(IsActive AS VARCHAR)
        WHEN IsActive = 1 THEN 'Active (1)'
        WHEN IsActive = 0 THEN 'Inactive (0)'
        ELSE 'NULL: Interpret as inactive or unknown?'
    END AS ValueAssessment
FROM Customers
GROUP BY IsActive
HAVING IsActive IS NULL OR IsActive NOT IN (0, 1)
UNION ALL
SELECT
    'Products.IsActive',
    IsActive,
    COUNT(*),
    CASE
        WHEN IsActive NOT IN (0, 1)
             THEN 'INVALID: Expected 0 or 1 only'
        ELSE 'Valid'
    END
FROM Products
GROUP BY IsActive
HAVING IsActive IS NULL OR IsActive NOT IN (0, 1);

-- Step 3: Status field valid-value check
DECLARE @ValidOrderStatuses TABLE (Status VARCHAR(50));
INSERT INTO @ValidOrderStatuses VALUES
    ('Pending'), ('Processing'), ('Shipped'), ('Delivered'), ('Cancelled'), ('Refunded');

SELECT
    o.OrderID,
    o.Status,
    CASE
        WHEN o.Status IS NULL
             THEN 'NULL STATUS: Order has no status'
        WHEN NOT EXISTS (SELECT 1 FROM @ValidOrderStatuses v WHERE v.Status = o.Status)
             THEN 'INVALID STATUS: ''' + o.Status + ''' not in allowed set'
        ELSE 'Valid status'
    END AS StatusValidation
FROM Orders o
WHERE o.Status IS NULL
   OR NOT EXISTS (SELECT 1 FROM @ValidOrderStatuses v WHERE v.Status = o.Status);

-- Step 4: Logical flag combinations that are impossible
SELECT
    c.CustomerID,
    c.FirstName + ' ' + c.LastName AS CustomerName,
    c.IsActive,
    o.OrderID,
    o.Status,
    CASE
        WHEN c.IsActive = 0 AND o.Status IN ('Processing', 'Shipped')
             THEN 'IMPOSSIBLE: Inactive customer has active order in '
                  + o.Status + ' status'
        WHEN c.IsActive = 0 AND o.Status = 'Pending'
             THEN 'FLAG: Inactive customer has pending order — review'
        ELSE 'Consistent'
    END AS FlagConsistency
FROM Customers c
JOIN Orders o ON c.CustomerID = o.CustomerID
WHERE c.IsActive = 0
  AND o.Status NOT IN ('Delivered', 'Cancelled', 'Refunded')
ORDER BY c.CustomerID;

-- Step 5: Products with inconsistent flag states
SELECT
    p.ProductID,
    p.ProductName,
    p.IsActive,
    p.StockQuantity,
    p.Price,
    CASE
        WHEN p.IsActive = 1 AND p.StockQuantity = 0
             THEN 'REVIEW: Active product with zero stock — set to inactive?'
        WHEN p.IsActive = 0 AND p.StockQuantity > 0
             THEN 'REVIEW: Inactive product still shows ' + CAST(p.StockQuantity AS VARCHAR)
                  + ' units in stock — write off?'
        WHEN p.IsActive = 0 AND p.Price > 0
             THEN 'MINOR: Inactive product has a price — acceptable for record-keeping'
        ELSE 'Consistent flag state'
    END AS FlagStateConsistency
FROM Products p
ORDER BY p.IsActive, p.StockQuantity DESC;
```

## Expected Output

**Step 1 — Distinct values:**
| FlagColumn | Value | Count |
|---|---|---|
| Customers.IsActive | 0 | 3 |
| Customers.IsActive | 1 | 9 |
| Products.IsActive | 0 | 4 |
| Products.IsActive | 1 | 11 |

**Step 4 — Logical flag combinations:**
| CustomerID | CustomerName | IsActive | OrderID | Status | FlagConsistency |
|---|---|---|---|---|---|
| 6 | Eve Jones | 0 | 1016 | Shipped | IMPOSSIBLE: Inactive customer has active order in Shipped status |

**Step 5 — Product flag consistency:**
| ProductID | ProductName | IsActive | StockQuantity | FlagStateConsistency |
|---|---|---|---|---|
| 5 | Widget Pro | 1 | 0 | REVIEW: Active product with zero stock — set to inactive? |
| 9 | Legacy Item | 0 | 45 | REVIEW: Inactive product still shows 45 units in stock — write off? |

## Explanation

**BIT column constraints**
SQL Server's `BIT` type enforces only two values: 0 and 1. A NULL is also allowed unless constrained. Values other than 0/1 cannot be stored in a BIT column — the conversion happens at load time (non-zero → 1). Step 2's check for values outside {0, 1} is therefore a proxy for detecting whether the source data had unexpected values that were silently coerced.

**Distinct value enumeration before analysis**
Step 1 uses GROUP BY to enumerate every distinct value in a flag column. This is the first step in any flag field audit — before validating, know what values exist. A BIT column with values {0, 1, NULL} requires a three-way interpretation; a status column with values including 'CANCELLED' and 'Cancelled' reveals a case inconsistency.

**Impossible flag combinations**
Step 4 validates not just individual columns but combinations: an inactive customer with an in-flight order is a logical contradiction. The rules follow from the business domain: if IsActive = 0 means "account closed," then active orders (Processing, Shipped) cannot exist for that account.

**NULL in flag columns**
`IsActive IS NULL` is ambiguous: does it mean "unknown," "not yet determined," or "default to inactive"? The query in Step 2 surfaces NULLs explicitly. Business rules should define the interpretation of NULL in flag columns; the column should have a DEFAULT constraint (e.g., `DEFAULT 1`) to prevent inadvertent NULLs.

## Severity
**Medium** — Flag field misuse corrupts boolean business logic: active/inactive filtering, status-based workflow routing, and access control all depend on flag columns containing exactly the expected values. In security-critical fields (`IsActive`, `IsAdmin`, `IsVerified`), incorrect values can grant or deny access incorrectly.
