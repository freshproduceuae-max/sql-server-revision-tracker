# G11-T09 — Profiling | Outlier and Anomaly Profile

## ID
G11-T09

## Group
11 — Profiling

## Type
Outlier and Anomaly Profile — Systematically Identifying Values That Deviate From Expected Distributions

## Live Scenario
A procurement analyst is auditing supplier invoices before payment. A standard outlier profile on the `Amount` column flags three invoices as extreme outliers: £0.01, £0.01, and £847,200. The two £0.01 invoices turn out to be test records entered by a developer that were never deleted from the production table — they skew the minimum and drag the mean down. The £847,200 invoice is genuine but exceeds the single-approval threshold of £500,000, meaning it required dual-sign-off that was never obtained. Additionally, the profile shows 47 invoices all for exactly £10,000 — suspiciously round numbers that are characteristic of fictitious invoice schemes. Without a systematic outlier profile, the analyst would have processed all payments without flagging these issues.

## The Question
> An outlier and anomaly profile systematically applies multiple detection methods — Z-score, IQR fences, round-number detection, frequency anomalies, and domain-specific rules — to identify values that deviate from expected distributions and warrant individual review.
> **"Produce a comprehensive outlier profile of TotalAmount in Orders and Amount in Transactions: apply Z-score, IQR fence, and round-number detection methods, and combine results into a multi-method outlier flag showing which records are flagged by one, two, or all three methods."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Transactions** — `schemas/05_Transactions.csv`

## Solution Query

```sql
-- Step 1: Multi-method outlier detection for Orders.TotalAmount
WITH OrderStats AS (
    SELECT
        AVG(TotalAmount)    AS Mean,
        STDEV(TotalAmount)  AS StdDev,
        PERCENTILE_CONT(0.25) WITHIN GROUP (ORDER BY TotalAmount) OVER () AS Q1,
        PERCENTILE_CONT(0.75) WITHIN GROUP (ORDER BY TotalAmount) OVER () AS Q3
    FROM Orders
    WHERE TotalAmount IS NOT NULL
),
UniqueStats AS (
    SELECT DISTINCT Mean, StdDev, Q1, Q3, Q3 - Q1 AS IQR
    FROM OrderStats
),
ScoredOrders AS (
    SELECT
        o.OrderID,
        o.CustomerID,
        o.TotalAmount,
        o.Status,
        s.Mean,
        s.StdDev,
        s.Q1,
        s.Q3,
        s.IQR,
        -- Method 1: Z-score
        ROUND(ABS(o.TotalAmount - s.Mean) / NULLIF(s.StdDev, 0), 2) AS ZScore,
        -- Method 2: IQR fence (Tukey)
        CASE
            WHEN o.TotalAmount < s.Q1 - 1.5 * s.IQR THEN 1
            WHEN o.TotalAmount > s.Q3 + 1.5 * s.IQR THEN 1
            ELSE 0
        END AS IQROutlier,
        -- Method 3: Round number (suspiciously exact values)
        CASE
            WHEN o.TotalAmount % 1000 = 0 THEN 1
            WHEN o.TotalAmount % 500  = 0 THEN 1
            WHEN o.TotalAmount % 100  = 0 AND o.TotalAmount > 1000 THEN 1
            ELSE 0
        END AS RoundNumberFlag
    FROM Orders o
    CROSS JOIN UniqueStats s
    WHERE o.TotalAmount IS NOT NULL
)
SELECT
    OrderID,
    CustomerID,
    TotalAmount,
    Status,
    ZScore,
    IQROutlier,
    RoundNumberFlag,
    -- Count how many methods flag this record
    (CASE WHEN ZScore > 3 THEN 1 ELSE 0 END + IQROutlier + RoundNumberFlag)
        AS MethodsFlagged,
    CASE
        WHEN ZScore > 3 THEN 1 ELSE 0 END AS ZScoreFlag,
    CASE
        WHEN (CASE WHEN ZScore > 3 THEN 1 ELSE 0 END + IQROutlier + RoundNumberFlag) = 3
             THEN 'ALL METHODS: Highest priority review'
        WHEN (CASE WHEN ZScore > 3 THEN 1 ELSE 0 END + IQROutlier + RoundNumberFlag) = 2
             THEN 'TWO METHODS: High priority review'
        WHEN (CASE WHEN ZScore > 3 THEN 1 ELSE 0 END + IQROutlier + RoundNumberFlag) = 1
             THEN 'ONE METHOD: Flag for review'
        ELSE 'No outlier flags'
    END AS OutlierPriority,
    ROUND(Mean, 2) AS DistributionMean,
    ROUND(Q1 - 1.5 * IQR, 2) AS LowerFence,
    ROUND(Q3 + 1.5 * IQR, 2) AS UpperFence
FROM ScoredOrders
ORDER BY MethodsFlagged DESC, ZScore DESC;

-- Step 2: Outlier summary — how many records per method and overlap
SELECT
    SUM(CASE WHEN ZScore > 3 THEN 1 ELSE 0 END) AS ZScoreOutliers,
    SUM(IQROutlier) AS IQROutliers,
    SUM(RoundNumberFlag) AS RoundNumberFlags,
    SUM(CASE WHEN (CASE WHEN ZScore > 3 THEN 1 ELSE 0 END + IQROutlier + RoundNumberFlag) >= 2
             THEN 1 ELSE 0 END) AS MultiMethodOutliers,
    COUNT(*) AS TotalRows,
    ROUND(100.0 * SUM(CASE WHEN ZScore > 3 THEN 1 ELSE 0 END) / COUNT(*), 1)
        AS ZScoreOutlierPct
FROM (
    SELECT
        o.TotalAmount,
        ROUND(ABS(o.TotalAmount - s.Mean) / NULLIF(s.StdDev, 0), 2) AS ZScore,
        CASE WHEN o.TotalAmount < s.Q1 - 1.5 * s.IQR OR
                  o.TotalAmount > s.Q3 + 1.5 * s.IQR THEN 1 ELSE 0 END AS IQROutlier,
        CASE WHEN o.TotalAmount % 1000 = 0
              OR o.TotalAmount % 500  = 0
              OR (o.TotalAmount % 100 = 0 AND o.TotalAmount > 1000) THEN 1 ELSE 0 END AS RoundNumberFlag
    FROM Orders o
    CROSS JOIN (
        SELECT DISTINCT
            AVG(TotalAmount) OVER () AS Mean,
            STDEV(TotalAmount) OVER () AS StdDev,
            PERCENTILE_CONT(0.25) WITHIN GROUP (ORDER BY TotalAmount) OVER () AS Q1,
            PERCENTILE_CONT(0.75) WITHIN GROUP (ORDER BY TotalAmount) OVER () AS Q3,
            PERCENTILE_CONT(0.75) WITHIN GROUP (ORDER BY TotalAmount) OVER ()
            - PERCENTILE_CONT(0.25) WITHIN GROUP (ORDER BY TotalAmount) OVER () AS IQR
        FROM Orders WHERE TotalAmount IS NOT NULL
    ) s
    WHERE o.TotalAmount IS NOT NULL
) Scored;

-- Step 3: Extreme value context — show neighbouring records for perspective
SELECT TOP 5
    OrderID,
    TotalAmount,
    Status,
    OrderDate,
    'HIGHEST' AS ValueContext
FROM Orders
WHERE TotalAmount IS NOT NULL
ORDER BY TotalAmount DESC;

-- Step 4: Frequency anomaly — values appearing suspiciously often
SELECT
    TotalAmount,
    COUNT(*) AS Frequency,
    ROUND(100.0 * COUNT(*) / SUM(COUNT(*)) OVER (), 1) AS Pct,
    CASE
        WHEN COUNT(*) > SUM(COUNT(*)) OVER () * 0.10
             THEN 'FREQUENCY ANOMALY: >10% of orders share this exact value'
        WHEN TotalAmount % 1000 = 0 AND COUNT(*) > 2
             THEN 'ROUND NUMBER CLUSTER: Multiple orders at round thousand'
        ELSE 'Normal'
    END AS FrequencyFlag
FROM Orders
WHERE TotalAmount IS NOT NULL
GROUP BY TotalAmount
HAVING COUNT(*) > 1
ORDER BY Frequency DESC;
```

## Explanation

**Why multiple methods matter**
Each method has blind spots. Z-score assumes normality and is sensitive to the very outliers it tries to detect (they inflate the standard deviation, making themselves look less extreme). IQR fences are robust to skewed distributions but may miss outliers in very dispersed data. Round-number detection catches a completely different class of anomaly (data entry artefacts) that neither statistical method can detect. Combining all three with a `MethodsFlagged` count produces a priority-ranked review list.

**Round-number detection as fraud signal**
When financial amounts cluster at exact round numbers (£1,000, £5,000, £10,000) at far higher frequency than expected from genuine transactions, it may indicate: fictitious invoices below an approval threshold, manual data entry where the operator entered a round estimate, or currency conversion errors where the exchange rate was applied incorrectly. The modulo operator (`TotalAmount % 1000 = 0`) efficiently detects these.

**CROSS JOIN to stats CTE**
`CROSS JOIN UniqueStats` attaches the distribution statistics (mean, IQR bounds) to every row without a correlated subquery. Because `UniqueStats` contains exactly one row (from `SELECT DISTINCT`), the cross join produces the same number of rows as the original table while giving each row access to the global statistics needed for per-row scoring.

**Frequency anomaly detection**
Step 4's `HAVING COUNT(*) > 1` with a `>10% of orders` check catches cases where many rows share the exact same value — a pattern impossible in genuine continuous financial data but common in: test data with hardcoded values, batch loads that default missing amounts to a placeholder, and split invoices where a single contract was artificially divided.

## Severity
**High** — Undetected outliers bias statistical summaries (inflating means, widening confidence intervals), compromise machine learning models (outliers in training data produce incorrect learned boundaries), and in financial contexts represent the primary mechanism for undetected fraud, error, and control failure. Outlier profiling should run before any analysis that uses financial amounts.
