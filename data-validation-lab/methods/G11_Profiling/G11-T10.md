# G11-T10 — Profiling | Schema Change and Drift Detection

## ID
G11-T10

## Group
11 — Profiling

## Type
Schema Change and Drift Detection — Comparing Current Data Profiles Against Baseline Expectations

## Live Scenario
A data engineering team runs a daily pipeline that ingests order data from three regional systems. On a Tuesday morning, the pipeline completes without errors but the dashboard shows a 34% drop in average order value. The team investigates: a schema drift detection query reveals that the `TotalAmount` column's median has shifted from £1,380 to £910 overnight — far outside the ±15% expected variation band. Separately, a new value "ARCHIVED" has appeared in the `Status` column — a value not present in the baseline profile. The source system team confirms: a regional office upgraded their CRM on Monday, which changed how discount codes are applied (reducing amounts) and added a new order status. The schema drift check surfaces both changes as alerts before they corrupt the downstream model's training data.

## The Question
> Schema and data drift detection compares the current data profile against a stored baseline profile to detect: new or missing column values, statistical distribution shifts, cardinality changes, and density changes. This catches upstream system changes before they silently corrupt downstream models and reports.
> **"Compare the current Orders and Customers data profile against expected baseline values — flag any column where cardinality, density, or statistical distribution has shifted beyond acceptable thresholds, and identify any new values in categorical columns not seen in the baseline."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Customers** — `schemas/01_Customers.csv`

## Solution Query

```sql
-- Step 1: Build current profile snapshot (run this regularly and compare to a stored baseline)
SELECT
    'Orders'       AS TableName,
    'TotalAmount'  AS ColName,
    COUNT(*)       AS RowCount,
    COUNT(TotalAmount) AS PopulatedCount,
    ROUND(MIN(TotalAmount), 2) AS MinVal,
    ROUND(MAX(TotalAmount), 2) AS MaxVal,
    ROUND(AVG(TotalAmount), 2) AS MeanVal,
    ROUND(STDEV(TotalAmount), 2) AS StdDevVal,
    ROUND(PERCENTILE_CONT(0.50) WITHIN GROUP (ORDER BY TotalAmount) OVER (), 2) AS MedianVal,
    COUNT(DISTINCT TotalAmount) AS DistinctValues,
    GETDATE() AS ProfileRunDate
FROM Orders
WHERE TotalAmount IS NOT NULL
UNION ALL
SELECT
    'Orders', 'Status',
    COUNT(*), COUNT(Status),
    NULL, NULL,
    NULL, NULL,
    NULL,
    COUNT(DISTINCT Status),
    GETDATE()
FROM Orders
UNION ALL
SELECT
    'Customers', 'Country',
    COUNT(*), COUNT(Country),
    NULL, NULL,
    NULL, NULL,
    NULL,
    COUNT(DISTINCT Country),
    GETDATE()
FROM Customers;

-- Step 2: Compare current cardinality to baseline expectations
-- (Baseline values represent expected state from prior profiling run)
WITH BaselineExpectations AS (
    SELECT 'Orders.Status'   AS ColKey, 5  AS ExpectedDistinct,  20 AS ExpectedRows
    UNION ALL
    SELECT 'Customers.Country', 4, 12
    UNION ALL
    SELECT 'Orders.TotalAmount', 20, 20
),
CurrentCardinality AS (
    SELECT 'Orders.Status'      AS ColKey,
           COUNT(DISTINCT Status) AS CurrentDistinct, COUNT(*) AS CurrentRows FROM Orders
    UNION ALL
    SELECT 'Customers.Country',
           COUNT(DISTINCT Country), COUNT(*) FROM Customers
    UNION ALL
    SELECT 'Orders.TotalAmount',
           COUNT(DISTINCT TotalAmount), COUNT(*) FROM Orders WHERE TotalAmount IS NOT NULL
)
SELECT
    c.ColKey,
    b.ExpectedRows,
    c.CurrentRows,
    b.ExpectedDistinct,
    c.CurrentDistinct,
    c.CurrentDistinct - b.ExpectedDistinct AS CardinalityDrift,
    ROUND(100.0 * (c.CurrentRows - b.ExpectedRows) / NULLIF(b.ExpectedRows, 0), 1) AS RowCountChangePct,
    CASE
        WHEN c.CurrentDistinct > b.ExpectedDistinct
             THEN 'NEW VALUES: Cardinality increased — new category added upstream?'
        WHEN c.CurrentDistinct < b.ExpectedDistinct
             THEN 'MISSING VALUES: Cardinality decreased — category removed or filtered?'
        WHEN ABS(c.CurrentRows - b.ExpectedRows) > b.ExpectedRows * 0.20
             THEN 'ROW COUNT SHIFT: >20% change in row count'
        ELSE 'Within expected range'
    END AS DriftAlert
FROM BaselineExpectations b
JOIN CurrentCardinality c ON b.ColKey = c.ColKey;

-- Step 3: New value detection — values in current data not in known baseline set
WITH BaselineStatusValues AS (
    -- These represent the known-good values from the last validated baseline
    SELECT 'Pending'    AS StatusValue UNION ALL
    SELECT 'Processing' UNION ALL
    SELECT 'Delivered'  UNION ALL
    SELECT 'Cancelled'  UNION ALL
    SELECT 'Returned'
),
BaselineCountryValues AS (
    SELECT 'UK'      AS CountryValue UNION ALL
    SELECT 'US'      UNION ALL
    SELECT 'Germany' UNION ALL
    SELECT 'Internal'
)
-- New order statuses not in baseline
SELECT
    'Orders.Status' AS ColKey,
    Status AS NewValue,
    COUNT(*) AS Occurrences,
    'NEW VALUE: Not in baseline — verify this is expected' AS Alert
FROM Orders
WHERE Status NOT IN (SELECT StatusValue FROM BaselineStatusValues)
  AND Status IS NOT NULL
GROUP BY Status
UNION ALL
-- New country values not in baseline
SELECT
    'Customers.Country',
    Country,
    COUNT(*),
    'NEW VALUE: Not in baseline — verify this is expected'
FROM Customers
WHERE Country NOT IN (SELECT CountryValue FROM BaselineCountryValues)
  AND Country IS NOT NULL
GROUP BY Country;

-- Step 4: Statistical distribution drift for numeric columns
-- Compare current stats to hardcoded baseline (in production, store in a profile table)
WITH CurrentStats AS (
    SELECT
        ROUND(AVG(TotalAmount), 2)   AS CurrentMean,
        ROUND(STDEV(TotalAmount), 2) AS CurrentStdDev,
        ROUND(MIN(TotalAmount), 2)   AS CurrentMin,
        ROUND(MAX(TotalAmount), 2)   AS CurrentMax,
        ROUND(PERCENTILE_CONT(0.50) WITHIN GROUP (ORDER BY TotalAmount) OVER (), 2) AS CurrentMedian
    FROM Orders
    WHERE TotalAmount IS NOT NULL
),
Baseline AS (
    -- Stored baseline values from last known-good profiling run
    SELECT
        1380.50 AS BaselineMean,
        2285.45 AS BaselineStdDev,
        88.00   AS BaselineMin,
        9800.00 AS BaselineMax,
        650.00  AS BaselineMedian
)
SELECT DISTINCT
    b.BaselineMean,
    c.CurrentMean,
    ROUND(100.0 * ABS(c.CurrentMean - b.BaselineMean) / NULLIF(b.BaselineMean, 0), 1)
        AS MeanDriftPct,
    b.BaselineMedian,
    c.CurrentMedian,
    ROUND(100.0 * ABS(c.CurrentMedian - b.BaselineMedian) / NULLIF(b.BaselineMedian, 0), 1)
        AS MedianDriftPct,
    CASE
        WHEN ABS(c.CurrentMean - b.BaselineMean) > b.BaselineMean * 0.15
             THEN 'MEAN DRIFT: >15% change from baseline — investigate upstream'
        WHEN ABS(c.CurrentMedian - b.BaselineMedian) > b.BaselineMedian * 0.15
             THEN 'MEDIAN DRIFT: >15% change from baseline — distribution shifted'
        WHEN c.CurrentMax > b.BaselineMax * 2
             THEN 'MAX SPIKE: New extreme value far above baseline maximum'
        ELSE 'Within 15% drift threshold'
    END AS DistributionAlert
FROM CurrentStats c
CROSS JOIN Baseline b;
```

## Explanation

**Baseline-vs-current comparison pattern**
The core pattern stores known-good profile values (cardinality, mean, median, distinct value lists) and compares the current snapshot against them. In production, the baseline is stored in a dedicated profile tracking table (`dbo.DataProfileHistory`) and queried via a JOIN. In these examples, the baseline is hardcoded as a CTE — sufficient for ad-hoc checks and for illustrating the comparison logic.

**Cardinality as a schema change signal**
When a categorical column's distinct count increases, a new upstream value has been introduced. When it decreases, values have been removed, merged, or filtered out. Both directions are significant: a new "ARCHIVED" status may require a new handling rule in downstream ETL; a disappearing "Processing" status may mean all in-flight orders were batch-resolved, or that the source system renamed the status.

**New value detection as a whitelist check**
Step 3 implements a whitelist approach: define the known-good set of valid values, then find any records NOT IN that set. This is stricter than a referential integrity check (which only validates against a lookup table) because it also catches new values added directly to the lookup table that haven't been reviewed by the data governance team.

**Drift thresholds are domain-specific**
The 15% drift threshold for mean and median is illustrative. Financial amount distributions in B2B contexts may have seasonal variation of 30–40% (Q4 spike), so the threshold should be tuned to the known variation pattern. A tighter 5% threshold is appropriate for tightly controlled inventory counts; a wider 50% threshold may be needed for web traffic data with promotional spikes.

## Severity
**High** — Silent schema and data drift is one of the most damaging data quality failure modes: the pipeline runs without errors, the data loads successfully, and downstream models and reports continue producing output — but the output is wrong because the input distribution changed. Drift detection adds a quality gate that alerts when upstream systems change their data without notifying downstream consumers.
