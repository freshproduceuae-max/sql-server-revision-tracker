# G17-T08 — Security/Compliance | Injection and Sanitisation Audit

## ID
G17-T08

## Group
17 — Security/Compliance

## Type
Injection and Sanitisation Audit — Detecting Unsanitised Input, SQL Injection Payloads, and XSS Strings in Stored Data

## Live Scenario
A penetration tester performing a security audit of an e-commerce company's database discovers that the `Notes` column in the Orders table contains 47 records with values like `'; DROP TABLE Orders; --`, `<script>alert('xss')</script>`, and `admin'--`. These are SQL injection and XSS payloads that were submitted through an unsanitised web form and stored in the database. While the payloads were captured (the database didn't execute them), their presence indicates that the application's input validation layer is not sanitising user-supplied text before storage. Any system that later reads these Notes values and interpolates them into a SQL string (e.g., a reporting tool that builds dynamic SQL) is at risk of executing the injection payload. The sanitisation audit identifies all 47 affected records and flags the input channels that accepted them.

## The Question
> Injection and sanitisation audits scan text columns in the database for stored SQL injection payloads (single quotes followed by SQL keywords, comment sequences `--` and `/**/`, UNION SELECT patterns), XSS payloads (`<script>`, `javascript:`, `onerror=`), and path traversal sequences (`../`, `..\\`). Detecting these patterns in stored data identifies both an active security risk (if the value is re-used in dynamic SQL) and a historical input validation failure that should be investigated and patched at the application layer.
> **"Scan the Orders and Customers tables for stored injection payloads: detect SQL injection patterns in free-text columns (Notes, Metadata, XMLData), identify XSS payload patterns in email and name fields, check for shell injection characters in filename and path fields, and produce a sanitisation risk summary."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Customers** — `schemas/01_Customers.csv`
**Products** — `schemas/03_Products.csv`

## Solution Query

```sql
-- Step 1: SQL injection pattern detection in Orders free-text columns
SELECT
    OrderID,
    LEFT(ISNULL(CAST(Notes AS VARCHAR(500)), ''), 100) AS NotesSample,
    LEFT(ISNULL(CAST(Metadata AS VARCHAR(500)), ''), 100) AS MetadataSample,
    -- SQL injection indicators
    CASE
        WHEN Notes LIKE '%'' OR ''%'
          OR Notes LIKE '%'' OR 1=1%'
          OR Notes LIKE '%''; DROP%'
          OR Notes LIKE '%UNION SELECT%'
          OR Notes LIKE '%UNION ALL SELECT%'
          OR Notes LIKE '%--%'
          OR Notes LIKE '%/*%*/%'
          OR Notes LIKE '%xp_cmdshell%'
          OR Notes LIKE '%EXEC(%'
             THEN 'SQL INJECTION: Notes field contains SQL injection payload'
        WHEN Notes IS NULL
             THEN 'NULL'
        ELSE 'Clean'
    END AS NotesSQLInjectionFlag,
    CASE
        WHEN Metadata LIKE '%<script%'
          OR Metadata LIKE '%javascript:%'
          OR Metadata LIKE '%onerror=%'
          OR Metadata LIKE '%onload=%'
          OR Metadata LIKE '%alert(%'
             THEN 'XSS: Metadata field contains cross-site scripting payload'
        WHEN Metadata IS NULL
             THEN 'NULL'
        ELSE 'Clean'
    END AS MetadataXSSFlag,
    -- Path traversal in attachment paths
    CASE
        WHEN AttachmentPath LIKE '%../%'
          OR AttachmentPath LIKE '%..\%'
          OR AttachmentPath LIKE '%/etc/passwd%'
          OR AttachmentPath LIKE '%C:\Windows%'
             THEN 'PATH TRAVERSAL: AttachmentPath contains directory traversal sequence'
        WHEN AttachmentPath IS NULL
             THEN 'NULL'
        ELSE 'Clean'
    END AS PathTraversalFlag
FROM Orders
WHERE
    Notes LIKE '%''%' OR Notes LIKE '%--%' OR Notes LIKE '%UNION%'
    OR Notes LIKE '%xp_%' OR Notes LIKE '%<script%'
    OR Metadata LIKE '%<script%' OR Metadata LIKE '%javascript:%'
    OR AttachmentPath LIKE '%../%' OR AttachmentPath LIKE '%..\%';

-- Step 2: XSS detection in customer name and email fields
SELECT
    CustomerID,
    FirstName,
    LastName,
    Email,
    CASE
        WHEN FirstName LIKE '%<script%'
          OR FirstName LIKE '%javascript:%'
          OR FirstName LIKE '%onerror=%'
          OR FirstName LIKE '%<img%'
          OR FirstName LIKE '%<svg%'
             THEN 'XSS IN FIRSTNAME: HTML/script tag in name field — input not sanitised'
        ELSE 'Clean'
    END AS FirstNameXSSFlag,
    CASE
        WHEN LastName LIKE '%<script%'
          OR LastName LIKE '%javascript:%'
          OR LastName LIKE '%<img%'
             THEN 'XSS IN LASTNAME: HTML/script tag in name field'
        ELSE 'Clean'
    END AS LastNameXSSFlag,
    CASE
        WHEN Email LIKE '%<script%'
          OR Email LIKE '%javascript:%'
          OR Email LIKE '%" OR "1"="1%'
          OR Email LIKE '%'' OR ''1''=''1%'
             THEN 'INJECTION IN EMAIL: SQL injection or XSS payload in email field'
        ELSE 'Clean'
    END AS EmailInjectionFlag
FROM Customers
WHERE
    FirstName LIKE '%<%' OR FirstName LIKE '%javascript%'
    OR LastName  LIKE '%<%' OR LastName  LIKE '%javascript%'
    OR Email     LIKE '%<%' OR Email     LIKE '%'' OR%';

-- Step 3: Dangerous characters in product free-text fields
SELECT
    ProductID,
    ProductName,
    LEFT(ISNULL(Description, ''), 100) AS DescriptionSample,
    CASE
        WHEN ProductName LIKE '%''%'
             THEN 'UNESCAPED QUOTE: ProductName contains single quote — risk if used in dynamic SQL'
        WHEN ProductName LIKE '%[<>]%'
             THEN 'HTML CHARS: ProductName contains < or > — possible XSS if rendered as HTML'
        ELSE 'Clean'
    END AS ProductNameFlag,
    CASE
        WHEN Description LIKE '%<script%'
          OR Description LIKE '%javascript:%'
             THEN 'XSS IN DESCRIPTION: Script tag in product description'
        WHEN Description LIKE '%''%' AND Description LIKE '%--%'
             THEN 'SQL INJECTION IN DESCRIPTION: Single quote and comment sequence'
        ELSE 'Clean'
    END AS DescriptionInjectionFlag
FROM Products
WHERE
    ProductName LIKE '%''%' OR ProductName LIKE '%[<>]%'
    OR Description LIKE '%<script%' OR Description LIKE '%--%';

-- Step 4: Injection character frequency audit — identify columns with high injection character rates
SELECT
    ColumnRef,
    TotalRecords,
    RecordsWithSingleQuote,
    RecordsWithDash,
    RecordsWithHTMLChars,
    ROUND(100.0 * RecordsWithSingleQuote / NULLIF(TotalRecords, 0), 1) AS QuotePct,
    CASE
        WHEN 100.0 * RecordsWithSingleQuote / NULLIF(TotalRecords, 0) > 5
             THEN 'HIGH: >5% of records have unescaped single quotes — review sanitisation'
        WHEN RecordsWithSingleQuote > 0
             THEN 'PRESENT: Some records have single quotes — verify they are legitimate'
        ELSE 'Clean'
    END AS SanitisationFlag
FROM (
    SELECT
        'Orders.Notes'     AS ColumnRef,
        COUNT(*)           AS TotalRecords,
        SUM(CASE WHEN Notes LIKE '%''%' THEN 1 ELSE 0 END) AS RecordsWithSingleQuote,
        SUM(CASE WHEN Notes LIKE '%--%' THEN 1 ELSE 0 END) AS RecordsWithDash,
        SUM(CASE WHEN Notes LIKE '%<%' OR Notes LIKE '%>%' THEN 1 ELSE 0 END) AS RecordsWithHTMLChars
    FROM Orders
    UNION ALL
    SELECT
        'Customers.Email',
        COUNT(*),
        SUM(CASE WHEN Email LIKE '%''%' THEN 1 ELSE 0 END),
        SUM(CASE WHEN Email LIKE '%--%' THEN 1 ELSE 0 END),
        SUM(CASE WHEN Email LIKE '%<%' THEN 1 ELSE 0 END)
    FROM Customers
    UNION ALL
    SELECT
        'Products.Description',
        COUNT(*),
        SUM(CASE WHEN Description LIKE '%''%' THEN 1 ELSE 0 END),
        SUM(CASE WHEN Description LIKE '%--%' THEN 1 ELSE 0 END),
        SUM(CASE WHEN Description LIKE '%<%' THEN 1 ELSE 0 END)
    FROM Products
) InjectionAudit;

-- Step 5: Remediation priority matrix
SELECT InjectionType, RiskLevel, AffectedColumns, RemediationAction FROM (VALUES
    ('SQL Injection (single quote + keyword)', 'Critical', 'Notes, Metadata, Email',
     'Parameterise all SQL; HTML-encode on output; strip or escape on input'),
    ('XSS (script tag)', 'Critical', 'Notes, Metadata, Description, FirstName',
     'HTML-encode all output; Content-Security-Policy header; validate on input'),
    ('Path Traversal (../)', 'High', 'AttachmentPath',
     'Validate against allowlist of permitted paths; canonicalise before use'),
    ('Comment injection (--)', 'High', 'Notes, Description',
     'Parameterise SQL; strip -- from user input; use ORM'),
    ('Shell metacharacters (; | &&)', 'High', 'Notes, AttachmentPath',
     'Avoid shell execution; validate against allowlist; encode special chars'),
    ('Unescaped single quotes (legitimate)', 'Low', "ProductName (O''Brien)",
     'Use parameterised queries — single quotes in data are safe with parameters')
) Remediation (InjectionType, RiskLevel, AffectedColumns, RemediationAction);
```

## Explanation

**Stored vs reflected injection**
The injection patterns detected here are stored injection payloads — malicious strings that were accepted by the application and written to the database. These are different from reflected injection (where the payload comes in a request and is immediately returned in the response). Stored injection is more dangerous because: (1) the payload persists and can be triggered by any future access; (2) it may be processed by multiple downstream systems (reporting tools, APIs, export scripts) that are not hardened against injection.

**Single quote as a legitimate character**
Not every single quote in a text column is a SQL injection attempt — apostrophes appear legitimately in names (O'Brien), product descriptions, and notes. Step 5 distinguishes between `RecordsWithSingleQuote` (which may be legitimate) and actual injection patterns that combine quotes with SQL keywords. The remediation for legitimate single quotes is parameterised queries (where the quote is always data, never syntax) rather than stripping them.

**Dynamic SQL as the activation vector**
A SQL injection payload sitting in the Notes column is inert until it is read by an application that concatenates it into a SQL string. The risk audit identifies records that contain payloads but does not assess which application components use dynamic SQL. The associated code audit (checking for string concatenation in stored procedures and application code) is the necessary companion to this data audit.

**LIKE with escape characters**
SQL Server LIKE treats `%`, `_`, `[`, and `]` as special pattern characters. To search for these characters literally, they must be escaped with `ESCAPE` clause or wrapped in brackets. For injection detection, this typically means searching for `%''%` to find single quotes, or `%--%` for double-dash sequences. In practice, the patterns shown are effective for the most common injection signatures without requiring complex escaping.

## Severity
**Critical** — Stored XSS and SQL injection payloads represent a two-stage attack: the attacker already succeeded in bypassing input validation (stage 1) and is waiting for the payload to be executed by an authorised user or system (stage 2). Detection and remediation must address both the stored payloads (data scrubbing) and the input validation failure that allowed them to be stored (application security patching).
