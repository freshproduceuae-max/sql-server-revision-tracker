# G17-T04 — Security/Compliance | Audit Trail Completeness Check

## ID
G17-T04

## Group
17 — Security/Compliance

## Type
Audit Trail Completeness Check — Verifying That All Required Audit Events Are Captured and No Gaps Exist in the Audit Log

## Live Scenario
A financial services company is audited by the FCA after a rogue trader submits fraudulent trades. The auditor requests the full audit trail showing who modified which trade records and when. The audit log table is supposed to capture every INSERT, UPDATE, and DELETE on the Transactions table via a trigger. Investigation reveals the trigger was disabled for 11 days during a performance tuning exercise and re-enabled without being documented. All modifications during those 11 days — including the fraudulent ones — have no audit log entries. The audit completeness check, comparing the transaction IDs in the audit log against those in the Transactions table and looking for date gaps in the audit log, would have immediately flagged the 11-day gap.

## The Question
> Audit trail completeness verification confirms that every data modification event has a corresponding audit log entry, that the audit log has no temporal gaps (periods with zero entries when the system was operational), and that the audit log timestamps are consistent with the transaction timestamps they record. SQL detects gaps by joining the transaction table to the audit log and identifying records with no matching audit entry, and by checking for date ranges in the audit log where entries drop to zero during expected operational hours.
> **"Validate audit trail completeness for the Transactions table: identify transactions that have no corresponding audit log entry (simulated by checking for CorrelationID gaps), detect any temporal gaps in the transaction sequence that suggest a period of unlogged activity, verify that the sequence of transaction IDs is continuous, and flag any suspicious patterns in the audit record distribution."**

## Table Reference
**Transactions** — `schemas/05_Transactions.csv`
**Orders** — `schemas/02_Orders.csv`

## Solution Query

```sql
-- Step 1: Transaction ID sequence gap detection
-- Gaps in sequential TransactionIDs suggest deleted records or missing audit entries
WITH ParsedTxnIDs AS (
    SELECT
        TransactionID,
        -- Extract numeric portion of TransactionID (e.g. TXN-001 → 1)
        TRY_CAST(
            SUBSTRING(TransactionID,
                      PATINDEX('%[0-9]%', TransactionID),
                      LEN(TransactionID))
            AS INT) AS TxnSeqNo,
        TransactionDate,
        Amount,
        CorrelationID
    FROM Transactions
    WHERE TransactionID IS NOT NULL
),
SequenceGaps AS (
    SELECT
        TxnSeqNo,
        TransactionID,
        TransactionDate,
        LEAD(TxnSeqNo) OVER (ORDER BY TxnSeqNo) AS NextSeqNo,
        LEAD(TransactionID) OVER (ORDER BY TxnSeqNo) AS NextTxnID
    FROM ParsedTxnIDs
)
SELECT
    TransactionID        AS LastTxnBeforeGap,
    NextTxnID            AS FirstTxnAfterGap,
    TxnSeqNo             AS LastSeqNo,
    NextSeqNo            AS NextSeqNo,
    NextSeqNo - TxnSeqNo - 1 AS MissingCount,
    'SEQUENCE GAP: ' + CAST(NextSeqNo - TxnSeqNo - 1 AS VARCHAR)
    + ' transaction IDs missing between '
    + TransactionID + ' and ' + NextTxnID AS GapDescription
FROM SequenceGaps
WHERE NextSeqNo - TxnSeqNo > 1
ORDER BY TxnSeqNo;

-- Step 2: CorrelationID completeness — every transaction should have a batch reference
SELECT
    TransactionID,
    CorrelationID,
    TransactionDate,
    Amount,
    CASE
        WHEN CorrelationID IS NULL
             THEN 'MISSING CORRELATION: Transaction has no batch/load reference — audit lineage broken'
        WHEN LEN(CorrelationID) < 5
             THEN 'SHORT CORRELATION: CorrelationID is suspiciously short — ' + CAST(CorrelationID AS VARCHAR)
        ELSE 'Has CorrelationID: ' + CAST(CorrelationID AS VARCHAR)
    END AS AuditLineageFlag
FROM Transactions
ORDER BY CorrelationID IS NULL DESC;

-- Step 3: Temporal gap detection in transaction date coverage
-- Identify date ranges where no transactions were recorded
WITH DateRange AS (
    SELECT
        DATEADD(DAY, n.Number, (SELECT MIN(CAST(TransactionDate AS DATE)) FROM Transactions)) AS CalDate
    FROM (
        SELECT ROW_NUMBER() OVER (ORDER BY (SELECT NULL)) - 1 AS Number
        FROM Transactions t1 CROSS JOIN Transactions t2
    ) n
    WHERE DATEADD(DAY, n.Number, (SELECT MIN(CAST(TransactionDate AS DATE)) FROM Transactions))
          <= (SELECT MAX(CAST(TransactionDate AS DATE)) FROM Transactions)
),
DailyTxnCounts AS (
    SELECT CAST(TransactionDate AS DATE) AS TxnDate, COUNT(*) AS TxnCount
    FROM Transactions WHERE TransactionDate IS NOT NULL
    GROUP BY CAST(TransactionDate AS DATE)
)
SELECT
    d.CalDate,
    ISNULL(dtc.TxnCount, 0) AS TxnCount,
    CASE
        WHEN dtc.TxnCount IS NULL
             THEN 'AUDIT GAP: No transactions on this date — verify system was operational'
        WHEN dtc.TxnCount = 1
             THEN 'LOW VOLUME: Only 1 transaction — unusual for an operational system'
        ELSE 'Normal'
    END AS AuditGapFlag
FROM DateRange d
LEFT JOIN DailyTxnCounts dtc ON d.CalDate = dtc.TxnDate
WHERE dtc.TxnCount IS NULL   -- show only gap dates
ORDER BY d.CalDate;

-- Step 4: Batch (CorrelationID) audit trail — all batches should have multiple transactions
-- A batch with only one transaction may indicate a partial audit capture
SELECT
    CorrelationID,
    COUNT(*) AS TxnCount,
    MIN(CAST(TransactionDate AS DATE)) AS EarliestDate,
    MAX(CAST(TransactionDate AS DATE)) AS LatestDate,
    ROUND(SUM(Amount), 2) AS BatchTotal,
    CASE
        WHEN COUNT(*) = 1
             THEN 'SINGLE RECORD BATCH: Only one transaction in this batch — verify completeness'
        ELSE 'Normal batch: ' + CAST(COUNT(*) AS VARCHAR) + ' transactions'
    END AS BatchCompletenessFlag
FROM Transactions
WHERE CorrelationID IS NOT NULL
GROUP BY CorrelationID
ORDER BY TxnCount ASC;

-- Step 5: Audit coverage summary
SELECT
    'Total transactions'                          AS Metric, COUNT(*) AS Value
FROM Transactions
UNION ALL
SELECT 'Transactions with CorrelationID', COUNT(*)
FROM Transactions WHERE CorrelationID IS NOT NULL
UNION ALL
SELECT 'Transactions without CorrelationID', COUNT(*)
FROM Transactions WHERE CorrelationID IS NULL
UNION ALL
SELECT 'Distinct load batches (CorrelationIDs)', COUNT(DISTINCT CorrelationID)
FROM Transactions WHERE CorrelationID IS NOT NULL
UNION ALL
SELECT 'Date span of audit records (days)',
    DATEDIFF(DAY, MIN(CAST(TransactionDate AS DATE)), MAX(CAST(TransactionDate AS DATE)))
FROM Transactions WHERE TransactionDate IS NOT NULL
UNION ALL
SELECT 'Distinct dates with transactions',
    COUNT(DISTINCT CAST(TransactionDate AS DATE))
FROM Transactions WHERE TransactionDate IS NOT NULL;
```

## Explanation

**Sequence gap as a deleted record indicator**
In a system that assigns sequential IDs at insert time, a gap in the sequence (e.g., TXN-003 followed by TXN-006) means either IDs 4 and 5 were never inserted, were inserted and then hard-deleted (bypassing the audit trigger), or were inserted in a different session that the audit log didn't capture. In a compliant financial system, hard deletes should not exist — records should be soft-deleted (flagged as cancelled) so the ID sequence remains continuous and any gap is evidence of a compliance breach.

**CorrelationID as a batch audit key**
The `CorrelationID` (or LoadBatchID) links all transactions from a single ETL load batch together. A complete audit trail means every transaction has a CorrelationID, and every CorrelationID corresponds to a documented batch run in the ETL control table. Transactions with NULL CorrelationID were loaded outside the documented batch process — possibly through direct database access, which should be flagged for investigation.

**Date spine for temporal gap detection**
Step 3's date spine (cross-join row generator producing a continuous calendar) is the most reliable method for detecting temporal gaps in audit logs. A comparison of the generated calendar against the actual transaction dates immediately reveals any dates where the system was silent. For a 24/7 operational system, any date with zero transactions is suspicious; for a Monday–Friday business, weekends are expected gaps that should be excluded from the anomaly detection.

**Single-record batches as capture failures**
A load batch that successfully processed hundreds of records but the audit table only shows one record from that batch indicates the audit trigger was functioning intermittently — it captured the first insert of the batch but then failed (perhaps due to a deadlock or timeout) and all subsequent inserts have no audit record. Step 4 identifies these single-record batches as potential partial-capture failures.

## Severity
**Critical** — An incomplete audit trail is a regulatory compliance failure for financial services (FCA, SOX), healthcare (HIPAA), and any sector subject to GDPR Article 30 (records of processing activities). Beyond compliance, an incomplete audit trail means that in the event of a data breach or fraud investigation, the forensic evidence required to determine what happened, when, and by whom is simply absent.
