# G17-T02 — Security/Compliance | Access Pattern Anomaly Detection

## ID
G17-T02

## Group
17 — Security/Compliance

## Type
Access Pattern Anomaly Detection — Identifying Unusual Query Behaviour That May Indicate Data Exfiltration or Privilege Abuse

## Live Scenario
An e-commerce company's database administrator notices that a junior analyst's account executed 847 SELECT statements on the Customers table between 02:00 and 03:00 on a Sunday morning — outside their normal working hours and 40× their typical daily query volume. Investigation reveals the analyst's credentials had been compromised; an attacker was systematically extracting customer email addresses and phone numbers 500 rows at a time using a scripted crawler. The access pattern anomaly check, running nightly against the SQL Server audit log proxy table (simulated here using SourceIP and timestamp data from Transactions), would have flagged the anomalous query volume within the first 15 minutes.

## The Question
> Access pattern anomaly detection identifies users or IP addresses whose data access behaviour deviates from their established baseline: unusual hours (off-hours access), unusual volume (10× more records than their daily average), unusual patterns (accessing rows in sequential primary key order, suggesting systematic extraction), and unusual scope (accessing tables they have never previously queried). SQL detects these patterns using window functions to compare current activity against rolling historical averages.
> **"Detect access pattern anomalies in the transaction data: identify IP addresses that appear during unusual hours, detect IPs accessing an unusually high transaction volume compared to their historical average, flag sequential record access patterns that suggest systematic extraction, and identify first-time IPs that appear without any prior access history."**

## Table Reference
**Transactions** — `schemas/05_Transactions.csv`
**Orders** — `schemas/02_Orders.csv`

## Solution Query

```sql
-- Step 1: IP access volume by hour — detect off-hours access spikes
WITH HourlyAccess AS (
    SELECT
        SourceIP,
        CAST(TransactionDate AS DATE) AS AccessDate,
        DATEPART(HOUR, TransactionDate) AS AccessHour,
        COUNT(*) AS TxnCount
    FROM Transactions
    WHERE SourceIP IS NOT NULL AND TransactionDate IS NOT NULL
    GROUP BY SourceIP, CAST(TransactionDate AS DATE), DATEPART(HOUR, TransactionDate)
)
SELECT
    SourceIP,
    AccessDate,
    AccessHour,
    TxnCount,
    CASE
        WHEN AccessHour BETWEEN 0 AND 5
             THEN 'OFF-HOURS: Access between midnight and 6am'
        WHEN AccessHour BETWEEN 6 AND 8
             THEN 'EARLY HOURS: Access before 9am'
        WHEN AccessHour BETWEEN 22 AND 23
             THEN 'LATE HOURS: Access after 10pm'
        ELSE 'Business hours'
    END AS HourFlag,
    CASE
        WHEN AccessHour BETWEEN 0 AND 5 AND TxnCount > 5
             THEN 'ALERT: High volume off-hours access — possible automated extraction'
        ELSE 'Normal'
    END AS AlertFlag
FROM HourlyAccess
ORDER BY TxnCount DESC;

-- Step 2: Per-IP daily volume vs rolling average
WITH DailyIPVolume AS (
    SELECT
        SourceIP,
        CAST(TransactionDate AS DATE) AS AccessDate,
        COUNT(*) AS DailyTxnCount
    FROM Transactions
    WHERE SourceIP IS NOT NULL AND TransactionDate IS NOT NULL
    GROUP BY SourceIP, CAST(TransactionDate AS DATE)
),
VolumeWithBaseline AS (
    SELECT
        SourceIP,
        AccessDate,
        DailyTxnCount,
        AVG(DailyTxnCount * 1.0) OVER (
            PARTITION BY SourceIP
            ORDER BY AccessDate
            ROWS BETWEEN 7 PRECEDING AND 1 PRECEDING
        ) AS Rolling7DayAvg,
        COUNT(*) OVER (
            PARTITION BY SourceIP
            ORDER BY AccessDate
            ROWS BETWEEN 7 PRECEDING AND 1 PRECEDING
        ) AS DaysInBaseline
    FROM DailyIPVolume
)
SELECT
    SourceIP,
    AccessDate,
    DailyTxnCount,
    ROUND(Rolling7DayAvg, 1) AS Rolling7DayAvg,
    DaysInBaseline,
    CASE
        WHEN Rolling7DayAvg IS NULL OR DaysInBaseline < 3
             THEN 'NEW IP: Insufficient history for baseline comparison'
        WHEN DailyTxnCount > Rolling7DayAvg * 10
             THEN 'CRITICAL SPIKE: ' + CAST(DailyTxnCount AS VARCHAR)
                  + ' transactions vs 7-day average of ' + CAST(ROUND(Rolling7DayAvg, 0) AS VARCHAR)
                  + ' — possible exfiltration'
        WHEN DailyTxnCount > Rolling7DayAvg * 3
             THEN 'HIGH VOLUME: ' + CAST(ROUND(DailyTxnCount / NULLIF(Rolling7DayAvg, 0), 1) AS VARCHAR)
                  + 'x average — investigate'
        ELSE 'Normal volume'
    END AS VolumeAnomalyFlag
FROM VolumeWithBaseline
ORDER BY DailyTxnCount DESC;

-- Step 3: Sequential access pattern detection
-- Legitimate human queries are not perfectly sequential; automated crawlers often are
WITH TransactionSequence AS (
    SELECT
        TransactionID,
        SourceIP,
        TransactionDate,
        -- Check if TransactionIDs accessed by this IP are consecutive
        LAG(TransactionID) OVER (PARTITION BY SourceIP ORDER BY TransactionDate) AS PriorTxnID,
        LAG(TransactionDate) OVER (PARTITION BY SourceIP ORDER BY TransactionDate) AS PriorDate
    FROM Transactions
    WHERE SourceIP IS NOT NULL
),
SequentialCheck AS (
    SELECT
        SourceIP,
        COUNT(*) AS TotalAccesses,
        SUM(CASE
            WHEN TRY_CAST(TransactionID AS INT) IS NOT NULL
             AND TRY_CAST(PriorTxnID AS INT) IS NOT NULL
             AND ABS(TRY_CAST(TransactionID AS INT) - TRY_CAST(PriorTxnID AS INT)) <= 1
            THEN 1 ELSE 0 END) AS SequentialPairs,
        ROUND(100.0 * SUM(CASE
            WHEN TRY_CAST(TransactionID AS INT) IS NOT NULL
             AND TRY_CAST(PriorTxnID AS INT) IS NOT NULL
             AND ABS(TRY_CAST(TransactionID AS INT) - TRY_CAST(PriorTxnID AS INT)) <= 1
            THEN 1 ELSE 0 END)
        / NULLIF(COUNT(*) - 1, 0), 1) AS SequentialPct
    FROM TransactionSequence
    WHERE PriorTxnID IS NOT NULL
    GROUP BY SourceIP
)
SELECT
    SourceIP,
    TotalAccesses,
    SequentialPairs,
    SequentialPct,
    CASE
        WHEN SequentialPct > 80
             THEN 'SEQUENTIAL CRAWL: ' + CAST(SequentialPct AS VARCHAR)
                  + '% of accesses are to consecutive records — likely automated extraction'
        WHEN SequentialPct > 50
             THEN 'SEMI-SEQUENTIAL: Possible scripted access pattern'
        ELSE 'Random access: Human-like pattern'
    END AS SequentialFlag
FROM SequentialCheck
ORDER BY SequentialPct DESC;

-- Step 4: First-time IP addresses (new IPs with no prior history)
WITH IPFirstSeen AS (
    SELECT
        SourceIP,
        MIN(CAST(TransactionDate AS DATE)) AS FirstSeenDate,
        MAX(CAST(TransactionDate AS DATE)) AS LastSeenDate,
        COUNT(*) AS TotalTxns,
        COUNT(DISTINCT CAST(TransactionDate AS DATE)) AS DaysActive
    FROM Transactions
    WHERE SourceIP IS NOT NULL AND TransactionDate IS NOT NULL
    GROUP BY SourceIP
)
SELECT
    SourceIP,
    FirstSeenDate,
    LastSeenDate,
    TotalTxns,
    DaysActive,
    CASE
        WHEN FirstSeenDate = LastSeenDate AND TotalTxns > 10
             THEN 'ONE-DAY HIGH VOLUME: Appeared for one day with high activity — suspicious'
        WHEN DaysActive = 1
             THEN 'SINGLE-DAY IP: Only active on one day — may be a scan or test'
        ELSE 'Recurring IP: Normal'
    END AS IPHistoryFlag
FROM IPFirstSeen
ORDER BY TotalTxns DESC;

-- Step 5: Access anomaly summary
SELECT
    'Unique source IPs'                   AS Metric, COUNT(DISTINCT SourceIP) AS Value
FROM Transactions WHERE SourceIP IS NOT NULL
UNION ALL
SELECT 'Transactions in off-hours (0-5am)', COUNT(*)
FROM Transactions
WHERE SourceIP IS NOT NULL AND DATEPART(HOUR, TransactionDate) BETWEEN 0 AND 5
UNION ALL
SELECT 'NULL source IP (untracked access)', COUNT(*)
FROM Transactions WHERE SourceIP IS NULL
UNION ALL
SELECT 'Single-day IPs', COUNT(*)
FROM (
    SELECT SourceIP FROM Transactions WHERE SourceIP IS NOT NULL
    GROUP BY SourceIP
    HAVING COUNT(DISTINCT CAST(TransactionDate AS DATE)) = 1
) S;
```

## Explanation

**Rolling average for baseline comparison**
Access pattern anomaly detection requires a baseline — what does "normal" look like for this IP? Using `AVG() OVER (ROWS BETWEEN 7 PRECEDING AND 1 PRECEDING)` computes the 7-day rolling average up to but not including the current day, providing a baseline that reflects recent behaviour without being contaminated by the anomalous day being tested. A 10× spike above this baseline is a strong signal; a 3× spike warrants investigation.

**Sequential access as a crawler fingerprint**
Human users query data based on business context — they look up specific customers, recent orders, or filtered results. Automated crawlers extracting data for exfiltration typically iterate through primary keys sequentially: SELECT * WHERE ID = 1000, then ID = 1001, then ID = 1002. Step 3's consecutive-pair detection identifies this signature: if more than 80% of an IP's TransactionID accesses are to consecutive IDs, the access pattern is almost certainly scripted.

**NULL SourceIP as an audit gap**
Step 5's NULL SourceIP count reveals records where the originating IP was not captured — these represent untracked access that cannot be audited. In a financial system, 100% of transactions should have a logged SourceIP (or session identifier) for regulatory audit trail purposes. A high NULL rate in SourceIP indicates the audit logging is not functioning correctly for some access paths.

**Single-day IPs as scan indicators**
An IP address that appears only once in the access logs — executing multiple transactions in a single session on a single day and never returning — is characteristic of a port scan, credential stuffing probe, or targeted exfiltration attempt. Legitimate business users and systems access the database recurrently across multiple days. Step 4 flags these single-appearance IPs for review.

## Severity
**Critical** — Access pattern anomalies are the primary early warning signal for data breaches in progress. Unlike perimeter security controls that detect intrusion attempts, access pattern monitoring detects successful intrusions where the attacker is already inside the system and actively extracting data. The window between first anomalous access and detection is the critical interval — minimising it requires real-time or near-real-time anomaly detection.
