# G17-T07 — Security/Compliance | Privileged Data Access Validation

## ID
G17-T07

## Group
17 — Security/Compliance

## Type
Privileged Data Access Validation — Detecting Access to Sensitive Columns by Users Who Should Not Have It

## Live Scenario
A healthcare company implements column-level security to prevent junior staff from seeing patient diagnostic codes — a special category under GDPR Article 9. During a penetration test, the tester discovers that a VIEW created for junior staff accidentally includes the diagnostic code column because a developer copied the production view definition without removing the restricted columns. The column-level access validation check, querying the INFORMATION_SCHEMA to compare the columns exposed by each view against the list of restricted columns, immediately flags that the junior staff view exposes three restricted columns.

## The Question
> Privileged data access validation uses SQL Server system catalog views to audit which columns are visible to which roles, verify that sensitive columns are not included in views used by non-privileged roles, check that column-level permissions have been correctly applied, and identify any views or procedures that bypass row-level security by selecting * (which includes all columns regardless of access controls). SQL queries INFORMATION_SCHEMA.COLUMNS, sys.objects, and column permission tables to produce an access control audit.
> **"Validate privileged data access controls: identify which columns in each table contain sensitive data, detect any columns in the Employees and Customers tables that should have restricted access, verify that sensitive numeric columns (HourlyRate, TotalAmount) could be detected via pattern analysis, and produce an access control recommendation matrix."**

## Table Reference
**Employees** — `schemas/04_Employees.csv`
**Customers** — `schemas/01_Customers.csv`
**Transactions** — `schemas/05_Transactions.csv`

## Solution Query

```sql
-- Step 1: Identify sensitive columns by name pattern in current database
-- This simulates querying sys.columns for PII/sensitive column names
SELECT
    TABLE_NAME    AS TableName,
    COLUMN_NAME   AS ColumnName,
    DATA_TYPE     AS DataType,
    IS_NULLABLE   AS Nullable,
    CASE
        -- Financial sensitive
        WHEN COLUMN_NAME IN ('HourlyRate', 'Price', 'TotalAmount', 'Amount',
                             'CommissionRate', 'TargetAmount')
             THEN 'FINANCIAL-SENSITIVE: Compensation or transaction value data'
        -- PII direct
        WHEN COLUMN_NAME IN ('Email', 'Phone', 'DateOfBirth', 'NationalID',
                             'SortCode', 'BankAccountNumber')
             THEN 'PII-DIRECT: Personal identifier — masking and access control required'
        -- PII quasi
        WHEN COLUMN_NAME IN ('PostalCode', 'Latitude', 'Longitude', 'SourceIP')
             THEN 'PII-QUASI: Location/network identifier — restricted in combination'
        -- Credentials / security
        WHEN COLUMN_NAME LIKE '%Password%' OR COLUMN_NAME LIKE '%Secret%'
          OR COLUMN_NAME LIKE '%Token%'   OR COLUMN_NAME LIKE '%Key%'
             THEN 'CREDENTIAL: Authentication material — must never appear in SELECT * results'
        -- Structural identifiers
        WHEN COLUMN_NAME IN ('FullName', 'FirstName', 'LastName')
             THEN 'PII-NAME: Direct personal identifier'
        ELSE 'NON-SENSITIVE'
    END AS DataClassification,
    CASE
        WHEN COLUMN_NAME IN ('NationalID', 'SortCode', 'BankAccountNumber')
             THEN 'DENY to all non-HR/Finance roles; GRANT to HR_Admin, Finance_Admin only'
        WHEN COLUMN_NAME IN ('HourlyRate', 'CommissionRate')
             THEN 'DENY to all non-HR roles; GRANT to HR_Admin, Finance_Analyst'
        WHEN COLUMN_NAME IN ('Email', 'Phone', 'DateOfBirth')
             THEN 'DENY to Analyst role; GRANT to CRM_Operator, HR_Admin'
        WHEN COLUMN_NAME IN ('SourceIP', 'BankAccountNumber')
             THEN 'DENY to all business roles; GRANT to Security_Team, DBA only'
        ELSE 'Standard access: GRANT to all authenticated roles'
    END AS AccessRecommendation
FROM INFORMATION_SCHEMA.COLUMNS
WHERE TABLE_NAME IN ('Customers', 'Employees', 'Transactions', 'Orders', 'Products', 'SalesTargets')
ORDER BY TABLE_NAME,
    CASE
        WHEN COLUMN_NAME IN ('NationalID','SortCode','BankAccountNumber') THEN 1
        WHEN COLUMN_NAME IN ('Email','Phone','DateOfBirth','FullName','FirstName','LastName') THEN 2
        WHEN COLUMN_NAME IN ('HourlyRate','Price','TotalAmount','Amount') THEN 3
        ELSE 4
    END;

-- Step 2: High-value column exposure analysis — which tables expose salary or financial data?
SELECT
    TABLE_NAME,
    COUNT(*) AS TotalColumns,
    SUM(CASE WHEN COLUMN_NAME IN ('HourlyRate','CommissionRate','TargetAmount')
             THEN 1 ELSE 0 END) AS SalaryColumns,
    SUM(CASE WHEN COLUMN_NAME IN ('NationalID','SortCode','BankAccountNumber')
             THEN 1 ELSE 0 END) AS HighSensitivityColumns,
    SUM(CASE WHEN COLUMN_NAME IN ('Email','Phone','DateOfBirth','FullName','FirstName','LastName','SourceIP')
             THEN 1 ELSE 0 END) AS PIIColumns,
    CASE
        WHEN SUM(CASE WHEN COLUMN_NAME IN ('NationalID','SortCode','BankAccountNumber')
                      THEN 1 ELSE 0 END) > 0
             THEN 'HIGH RISK: Contains financial identity data — strict access control required'
        WHEN SUM(CASE WHEN COLUMN_NAME IN ('HourlyRate','CommissionRate')
                      THEN 1 ELSE 0 END) > 0
             THEN 'MEDIUM RISK: Contains salary data — HR role restriction required'
        WHEN SUM(CASE WHEN COLUMN_NAME IN ('Email','Phone','DateOfBirth')
                      THEN 1 ELSE 0 END) > 0
             THEN 'PII PRESENT: Contains personal data — role-based access required'
        ELSE 'LOW RISK: No sensitive columns detected'
    END AS TableRiskLevel
FROM INFORMATION_SCHEMA.COLUMNS
WHERE TABLE_NAME IN ('Customers', 'Employees', 'Transactions', 'Orders', 'Products', 'SalesTargets')
GROUP BY TABLE_NAME
ORDER BY HighSensitivityColumns DESC, SalaryColumns DESC;

-- Step 3: SELECT * risk — identify columns that would be exposed by SELECT *
-- Any SELECT * on these tables exposes all columns including PII and financial data
SELECT
    'If SELECT * is used on Employees:' AS Warning,
    STRING_AGG(COLUMN_NAME, ', ') AS ExposedSensitiveColumns
FROM INFORMATION_SCHEMA.COLUMNS
WHERE TABLE_NAME = 'Employees'
  AND COLUMN_NAME IN ('FullName','NationalID','SortCode','HourlyRate',
                      'HireDate','TerminationDate','Country')
UNION ALL
SELECT
    'If SELECT * is used on Customers:',
    STRING_AGG(COLUMN_NAME, ', ')
FROM INFORMATION_SCHEMA.COLUMNS
WHERE TABLE_NAME = 'Customers'
  AND COLUMN_NAME IN ('Email','Phone','DateOfBirth','PostalCode','Latitude','Longitude')
UNION ALL
SELECT
    'If SELECT * is used on Transactions:',
    STRING_AGG(COLUMN_NAME, ', ')
FROM INFORMATION_SCHEMA.COLUMNS
WHERE TABLE_NAME = 'Transactions'
  AND COLUMN_NAME IN ('BankAccountNumber','SourceIP','Amount');

-- Step 4: Data value range check for financial columns — anomalous values may indicate data breach
SELECT
    'Employees.HourlyRate' AS Column_,
    MIN(HourlyRate)        AS MinValue,
    MAX(HourlyRate)        AS MaxValue,
    AVG(HourlyRate)        AS AvgValue,
    COUNT(*)               AS Records,
    SUM(CASE WHEN HourlyRate > 500 THEN 1 ELSE 0 END) AS SuspiciouslyHigh
FROM Employees WHERE HourlyRate IS NOT NULL
UNION ALL
SELECT
    'Transactions.Amount',
    MIN(Amount),
    MAX(Amount),
    AVG(Amount),
    COUNT(*),
    SUM(CASE WHEN Amount > 50000 THEN 1 ELSE 0 END)
FROM Transactions WHERE Amount IS NOT NULL;

-- Step 5: Access control matrix — recommended roles per sensitive column
SELECT ColumnName, SensitivityLevel, AllowedRoles, DeniedRoles FROM (VALUES
    ('NationalID',      'Critical PII',   'HR_Admin, DBA',         'Analyst, Developer, Support'),
    ('SortCode',        'Financial PII',  'Finance_Admin, DBA',    'Analyst, Developer, Support'),
    ('BankAccountNumber','Financial PII', 'Finance_Admin, DBA',    'Analyst, Developer, Support, HR'),
    ('HourlyRate',      'Salary',         'HR_Admin, Finance_Admin','Analyst, Developer, Support'),
    ('FullName',        'Direct PII',     'CRM_Operator, HR_Admin','Analyst (anonymised view only)'),
    ('Email',           'Direct PII',     'CRM_Operator',          'Analyst (aggregated only)'),
    ('DateOfBirth',     'Direct PII',     'HR_Admin, CRM_Operator','Analyst, Developer'),
    ('SourceIP',        'Quasi-PII',      'Security_Team, DBA',    'All business roles'),
    ('Latitude',        'Quasi-PII',      'All (truncated to 2dp)','Full precision restricted')
) ACL (ColumnName, SensitivityLevel, AllowedRoles, DeniedRoles);
```

## Explanation

**INFORMATION_SCHEMA as an audit surface**
`INFORMATION_SCHEMA.COLUMNS` provides a complete catalog of every column in every table accessible to the current connection. Querying it for column names matching PII patterns produces a comprehensive sensitive-data map without inspecting individual data values — useful for a DBA performing an access audit in an environment where they should not look at actual data values.

**SELECT * as a security anti-pattern**
`SELECT *` in a view or stored procedure is a security anti-pattern because it exposes all columns, including sensitive ones that should be restricted. When a new sensitive column is added to a table (e.g., adding `NationalID` to Employees), any existing `SELECT *` view automatically begins exposing it — without any code change and without triggering any access control review. Step 3 demonstrates which sensitive columns would be exposed by `SELECT *` on each table.

**Column-level vs row-level security**
SQL Server supports both column-level permissions (DENY SELECT ON table(column) TO role) and row-level security (security predicates in security policies). Column-level security prevents specific columns from being returned; row-level security prevents specific rows from being returned. For salary data, column-level security restricts HourlyRate to the HR role; row-level security might further restrict employees to only see their own HourlyRate. Both controls should be validated, not assumed.

**Access control matrix as documentation**
Step 5's access control matrix is both a SQL output and a documentation artefact — the output directly answers "who can access what?" for a compliance audit. In a fully implemented system, this matrix should be stored in a dedicated permissions table and reconciled against actual database role memberships in a nightly job.

## Severity
**High** — Privileged data access failures are the most common vector for insider threats and compliance violations. A developer who has SELECT access to the Employees table including HourlyRate can extract all salary data in a single query. Column-level permissions are often misconfigured at initial setup and then never re-audited as new columns are added — regular catalog-based access audits are the primary control.
