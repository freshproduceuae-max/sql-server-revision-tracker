# G17-T03 — Security/Compliance | Sensitive Value Masking Verification

## ID
G17-T03

## Group
17 — Security/Compliance

## Type
Sensitive Value Masking Verification — Confirming That PII and Financial Data Has Been Correctly Masked in Non-Production Environments

## Live Scenario
A bank's test environment refresh process is supposed to mask all customer account numbers, National Insurance numbers, and sort codes before copying production data to the UAT database. After a refresh, a tester accidentally shares a query result in a team Slack channel containing what appear to be real customer NI numbers. Subsequent investigation reveals that the masking ETL failed silently for all records with NULL values in the masking source column — the masking function was applied conditionally and the fallback was to leave the original value unchanged. 12,000 records were left unmasked. The masking verification check, validating that all values in the masked columns conform to the expected mask pattern rather than a real PII format, would have caught this immediately after the refresh.

## The Question
> Masking verification confirms that values in sensitive columns in non-production environments conform to the expected mask pattern: a masked National Insurance number should look like `XX-999999-X` not `AB123456C`; a masked bank account should be `****1234` not `12345678`; a masked email should be `m***@***.com` not `alice@example.com`. SQL verifies masking by testing that values do NOT match real PII patterns and DO match the expected mask pattern, and by checking that the original-value rate (values that appear unmasked) is zero.
> **"Verify that sensitive fields in the Employees and Customers tables have been correctly masked: check that NationalID values do not match real NI format, verify that SortCode values are masked, confirm that email addresses are in masked format, and quantify the proportion of records where masking appears to have failed (i.e., the original PII format is still detectable)."**

## Table Reference
**Employees** — `schemas/04_Employees.csv`
**Customers** — `schemas/01_Customers.csv`
**Transactions** — `schemas/05_Transactions.csv`

## Solution Query

```sql
-- Step 1: NationalID masking verification
-- Real NI format: AB123456C (2 letters, 6 digits, 1 letter)
-- Expected mask format: should NOT match real NI pattern (e.g., XX-999999-X or *****)
SELECT
    EmployeeID,
    NationalID,
    CASE
        WHEN NationalID IS NULL
             THEN 'NULL: Field is empty — verify if NULL is the expected mask or unloaded'
        WHEN NationalID LIKE '[A-Z][A-Z][0-9][0-9][0-9][0-9][0-9][0-9][A-Z]'
             THEN 'UNMASKED: Value matches real NI format — masking failed for this record'
        WHEN NationalID LIKE 'XX%' OR NationalID LIKE '****%' OR NationalID LIKE '[*]%'
             THEN 'MASKED: Value matches expected mask pattern'
        ELSE 'UNKNOWN MASK FORMAT: Value does not match real NI or expected mask — review masking rule'
    END AS NIMaskStatus
FROM Employees;

-- Step 2: SortCode masking verification
-- Real UK sort code: NN-NN-NN
-- Expected mask: **-**-** or XX-XX-XX or similar
SELECT
    EmployeeID,
    SortCode,
    CASE
        WHEN SortCode IS NULL
             THEN 'NULL'
        WHEN SortCode LIKE '[0-9][0-9]-[0-9][0-9]-[0-9][0-9]'
             THEN 'UNMASKED: Real sort code format — masking ETL failed for this record'
        WHEN SortCode LIKE '[0-9][0-9][0-9][0-9][0-9][0-9]'
             THEN 'UNMASKED (no dashes): Numeric sort code without dashes — masking failed'
        WHEN SortCode LIKE '**%' OR SortCode LIKE 'XX%'
             THEN 'MASKED: Appears to be in masked format'
        ELSE 'REVIEW: Unknown format — ' + LEFT(SortCode, 6)
    END AS SortCodeMaskStatus
FROM Employees;

-- Step 3: Email masking verification
-- Real email: user@domain.com
-- Masked email might be: u***@***.com or ****@***.*** or use a fake domain like @masked.local
SELECT
    CustomerID,
    Email,
    CASE
        WHEN Email IS NULL
             THEN 'NULL'
        WHEN Email LIKE '%@masked.%' OR Email LIKE '%@anonymised.%' OR Email LIKE '%@redacted.%'
             THEN 'MASKED: Uses anonymised domain'
        WHEN Email LIKE '%***%@%' OR Email LIKE '*%@%'
             THEN 'MASKED: Contains asterisk masking pattern'
        WHEN Email LIKE '%@%.%'
             THEN 'POSSIBLY UNMASKED: Matches real email format — verify if this is masked data'
        ELSE 'UNKNOWN FORMAT'
    END AS EmailMaskStatus
FROM Customers;

-- Step 4: Bank account masking in Transactions
SELECT
    TransactionID,
    BankAccountNumber,
    CASE
        WHEN BankAccountNumber IS NULL
             THEN 'NULL'
        WHEN BankAccountNumber LIKE '[0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9]'
             THEN 'UNMASKED: 8-digit account number — real bank account number detected'
        WHEN BankAccountNumber LIKE '****%'
             THEN 'MASKED: Asterisk-masked account number'
        WHEN LEN(CAST(BankAccountNumber AS VARCHAR)) < 4
             THEN 'PARTIAL: Possible last-4-digit masking'
        ELSE 'REVIEW: Unknown format'
    END AS BankAccountMaskStatus
FROM Transactions;

-- Step 5: Masking failure summary — what proportion of records are unmasked?
SELECT
    FieldName,
    TotalRecords,
    UnmaskedCount,
    MaskedOrNullCount,
    ROUND(100.0 * UnmaskedCount / NULLIF(TotalRecords, 0), 2) AS UnmaskedPct,
    CASE
        WHEN UnmaskedCount = 0
             THEN 'PASS: All records masked or NULL'
        WHEN 100.0 * UnmaskedCount / NULLIF(TotalRecords, 0) < 1
             THEN 'WARNING: <1% unmasked — investigate individual records'
        ELSE 'FAIL: ' + CAST(UnmaskedCount AS VARCHAR) + ' records (' +
             CAST(ROUND(100.0 * UnmaskedCount / NULLIF(TotalRecords, 0), 1) AS VARCHAR)
             + '%) have unmasked PII — masking ETL failed'
    END AS MaskingVerdict
FROM (
    SELECT
        'Employees.NationalID'  AS FieldName,
        COUNT(*) AS TotalRecords,
        SUM(CASE WHEN NationalID LIKE '[A-Z][A-Z][0-9][0-9][0-9][0-9][0-9][0-9][A-Z]'
                 THEN 1 ELSE 0 END) AS UnmaskedCount,
        SUM(CASE WHEN NationalID IS NULL
                  OR NOT (NationalID LIKE '[A-Z][A-Z][0-9][0-9][0-9][0-9][0-9][0-9][A-Z]')
                 THEN 1 ELSE 0 END) AS MaskedOrNullCount
    FROM Employees
    UNION ALL
    SELECT
        'Employees.SortCode',
        COUNT(*),
        SUM(CASE WHEN SortCode LIKE '[0-9][0-9]-[0-9][0-9]-[0-9][0-9]'
                  OR SortCode LIKE '[0-9][0-9][0-9][0-9][0-9][0-9]'
                 THEN 1 ELSE 0 END),
        SUM(CASE WHEN SortCode IS NULL
                  OR NOT (SortCode LIKE '[0-9][0-9]-[0-9][0-9]-[0-9][0-9]'
                       OR SortCode LIKE '[0-9][0-9][0-9][0-9][0-9][0-9]')
                 THEN 1 ELSE 0 END)
    FROM Employees
    UNION ALL
    SELECT
        'Transactions.BankAccountNumber',
        COUNT(*),
        SUM(CASE WHEN BankAccountNumber LIKE '[0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9]'
                 THEN 1 ELSE 0 END),
        SUM(CASE WHEN BankAccountNumber IS NULL
                  OR NOT BankAccountNumber LIKE '[0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9]'
                 THEN 1 ELSE 0 END)
    FROM Transactions
) MaskingSummary;
```

## Explanation

**Negative pattern matching for masking verification**
The masking verification logic inverts the usual pattern check: instead of verifying that values match the expected format, it verifies that values do NOT match the real PII format. This correctly handles the situation where multiple mask formats may be in use (asterisks, X-substitution, fake domains) without needing to enumerate all possible mask formats. Any value that matches the real NI number pattern `[A-Z][A-Z][0-9][0-9][0-9][0-9][0-9][0-9][A-Z]` is unmasked regardless of the mask format intended.

**NULL as a valid mask vs NULL as a failure**
In some masking implementations, the entire value is replaced with NULL rather than a substitute pattern. Step 1 flags NULL separately rather than treating it as either masked or unmasked — the distinction matters because a NULL NationalID that was NULL in the source is expected, but a NULL that replaced a real NI number (the masking function set it to NULL) may hide the fact that the original value existed. In high-security environments, replacing PII with NULL should be explicitly documented as an intentional masking strategy.

**Conditional masking failure mode**
The live scenario describes a common failure mode: the masking function is applied conditionally (`IF @value IS NOT NULL THEN mask(@value) ELSE @value`). When the source column is NULL, the ELSE branch returns the original value — which is NULL, so there's no PII exposure. But if the condition check has a bug (e.g., checking the wrong column for NULL), the ELSE branch may return the real value. Step 5's 80% unmasked rate in the sample data reflects the schema reality — this is production data being used for demonstration, not a test environment.

**Environment tagging as a masking prerequisite**
A masking verification query can only work if it knows it's running in a non-production environment. In practice, a stored procedure or job that runs this check should first verify the environment (via a configuration table or database name check) and refuse to execute in production — preventing the verification query itself from inadvertently exposing PII through its output.

## Severity
**Critical** — A masking failure in a test environment that is shared with developers, testers, contractors, and support staff constitutes a personal data breach under GDPR Article 33, requiring notification to the ICO within 72 hours if the risk to individuals is significant. NI numbers and bank sort codes appearing in a test environment accessed by 50+ people without data processing agreements represents a material breach exposure.
