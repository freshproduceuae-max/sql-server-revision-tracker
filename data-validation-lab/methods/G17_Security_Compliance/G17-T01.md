# G17-T01 — Security/Compliance | PII Detection and Data Classification

## ID
G17-T01

## Group
17 — Security/Compliance

## Type
PII Detection and Data Classification — Identifying Columns That Contain Personally Identifiable Information

## Live Scenario
A data engineering team builds a new analytics database by copying tables from the production OLTP system. During a GDPR compliance audit six months later, the auditor discovers that the analytics database — accessible to all 45 analysts — contains the full NationalID (National Insurance number) and SortCode (bank sort code) for all 8,200 employees. These fields were never intended to be in the analytics environment and were copied across because no one ran a PII check on the schema before the migration. The PII detection query, scanning column names and sample values for patterns matching known PII types, would have flagged both columns immediately during schema review.

## The Question
> PII detection scans column names for known PII identifiers (name, email, phone, NationalID, SortCode, passport) and validates sample values against PII format patterns (NI number format: two letters, six digits, one letter; sort code: NN-NN-NN). SQL detects both labelled PII (columns with obvious names) and unlabelled PII (columns whose names don't reveal their content but whose values match PII patterns), enabling data classification before exposure to unauthorised users.
> **"Identify PII fields in the Employees and Customers tables: flag columns whose names indicate PII, validate that PII columns contain expected formats, detect any PII-formatted values in non-PII-named columns, and produce a data classification summary showing which columns require masking, encryption, or access controls."**

## Table Reference
**Employees** — `schemas/04_Employees.csv`
**Customers** — `schemas/01_Customers.csv`
**Transactions** — `schemas/05_Transactions.csv`

## Solution Query

```sql
-- Step 1: Flag Employees columns containing PII by name and value
SELECT
    EmployeeID,
    FullName,
    NationalID,
    SortCode,
    -- NI number format: 2 letters, 6 digits, 1 letter (e.g. AB123456C)
    CASE
        WHEN NationalID IS NULL
             THEN 'NULL'
        WHEN NationalID LIKE '[A-Z][A-Z][0-9][0-9][0-9][0-9][0-9][0-9][A-Z]'
             THEN 'VALID NI FORMAT: PII field with correct format — requires masking'
        ELSE 'NON-STANDARD NI: Verify format — ' + LEFT(NationalID, 4) + '...'
    END AS NationalIDFlag,
    -- Sort code format: NN-NN-NN or NNNNNN
    CASE
        WHEN SortCode IS NULL
             THEN 'NULL'
        WHEN SortCode LIKE '[0-9][0-9]-[0-9][0-9]-[0-9][0-9]'
             THEN 'VALID SORT CODE: PII/financial field — requires masking'
        WHEN SortCode LIKE '[0-9][0-9][0-9][0-9][0-9][0-9]'
             THEN 'VALID SORT CODE (no dashes): PII/financial field'
        ELSE 'NON-STANDARD: ' + LEFT(ISNULL(SortCode, ''), 4)
    END AS SortCodeFlag,
    -- HourlyRate is not PII but is sensitive (salary data)
    CASE
        WHEN HourlyRate IS NOT NULL
             THEN 'SENSITIVE: Salary/compensation data — restrict access'
        ELSE 'NULL'
    END AS HourlyRateFlag
FROM Employees;

-- Step 2: PII in Customers table
SELECT
    CustomerID,
    -- Email
    CASE
        WHEN Email LIKE '%@%.%'
             THEN 'PII: Email address — GDPR Art.4 personal data'
        WHEN Email IS NULL THEN 'NULL'
        ELSE 'Non-email value in Email column'
    END AS EmailClassification,
    -- Phone
    CASE
        WHEN Phone IS NOT NULL
             THEN 'PII: Phone number — personal contact data'
        ELSE 'NULL'
    END AS PhoneClassification,
    -- Date of birth
    CASE
        WHEN DateOfBirth IS NOT NULL
             THEN 'PII: Date of birth — may reveal age category (special category if used for profiling)'
        ELSE 'NULL'
    END AS DOBClassification,
    -- PostalCode
    CASE
        WHEN PostalCode IS NOT NULL
             THEN 'QUASI-PII: Postcode — not PII alone but combined with name enables identification'
        ELSE 'NULL'
    END AS PostcodeClassification
FROM Customers;

-- Step 3: Detect PII-formatted values in non-PII-named columns
-- Check BankAccountNumber in Transactions — obvious PII in a financial column
SELECT
    TransactionID,
    -- Bank account number: typically 8 digits in UK
    CASE
        WHEN BankAccountNumber IS NULL
             THEN 'NULL'
        WHEN BankAccountNumber LIKE '[0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9]'
             THEN 'BANK ACCOUNT: 8-digit UK account number — PII/financial data requiring masking'
        WHEN BankAccountNumber LIKE '[0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9]'
             THEN 'POSSIBLE IBAN PARTIAL: 10+ digit numeric — check if full IBAN'
        ELSE 'NON-STANDARD: ' + LEFT(ISNULL(CAST(BankAccountNumber AS VARCHAR), ''), 4) + '...'
    END AS BankAccountFlag,
    SourceIP,
    CASE
        WHEN SourceIP IS NOT NULL
             THEN 'QUASI-PII: IP address — personal data under GDPR if linked to individual'
        ELSE 'NULL'
    END AS IPFlag
FROM Transactions;

-- Step 4: Data classification summary — all PII columns across all tables
SELECT
    TableName,
    ColumnName,
    PIICategory,
    GDPRBasis,
    RecommendedControl
FROM (VALUES
    ('Employees', 'FullName',      'Direct PII',    'GDPR Art.4 - personal data', 'Mask in non-prod; restrict read access'),
    ('Employees', 'NationalID',    'Sensitive PII', 'GDPR Art.4 - personal data (government identifier; high fraud/identity-theft sensitivity, not an Art.9 special category)', 'Encrypt at rest; mask in all reporting; audit access'),
    ('Employees', 'SortCode',      'Financial PII', 'PCI-DSS - financial account data', 'Encrypt at rest; mask in all reporting'),
    ('Employees', 'HourlyRate',    'Sensitive',     'Not PII — employment contract data', 'Restrict to HR role only'),
    ('Customers', 'Email',         'Direct PII',    'GDPR Art.4 - personal data', 'Mask in non-prod; restrict marketing use to consented'),
    ('Customers', 'Phone',         'Direct PII',    'GDPR Art.4 - personal data', 'Mask in non-prod; consent required for outbound contact'),
    ('Customers', 'DateOfBirth',   'Direct PII',    'GDPR Art.4 - personal data', 'Mask year in reporting; restrict to authorised systems'),
    ('Customers', 'PostalCode',    'Quasi-PII',     'GDPR Art.4 - indirect identifier', 'Safe at postcode level; mask premise-level combination'),
    ('Customers', 'Latitude',      'Quasi-PII',     'GDPR Art.4 - location data', 'Restrict precision to 2dp (~1km) in reporting'),
    ('Customers', 'Longitude',     'Quasi-PII',     'GDPR Art.4 - location data', 'Restrict precision to 2dp (~1km) in reporting'),
    ('Transactions', 'BankAccountNumber', 'Financial PII', 'PCI-DSS - bank account number', 'Encrypt; mask all but last 4 digits in output'),
    ('Transactions', 'SourceIP',   'Quasi-PII',     'GDPR Art.4 - online identifier', 'Pseudonymise for analytics; retain full for security audit')
) PII (TableName, ColumnName, PIICategory, GDPRBasis, RecommendedControl)
ORDER BY TableName, PIICategory;

-- Step 5: PII exposure risk — how many records expose each PII type?
SELECT
    'Employees: NationalID populated'       AS PIIExposure,
    COUNT(*) AS RecordCount,
    ROUND(100.0 * COUNT(*) / NULLIF((SELECT COUNT(*) FROM Employees), 0), 1) AS PopulatedPct
FROM Employees WHERE NationalID IS NOT NULL
UNION ALL
SELECT 'Employees: SortCode populated', COUNT(*),
    ROUND(100.0 * COUNT(*) / NULLIF((SELECT COUNT(*) FROM Employees), 0), 1)
FROM Employees WHERE SortCode IS NOT NULL
UNION ALL
SELECT 'Customers: Email populated', COUNT(*),
    ROUND(100.0 * COUNT(*) / NULLIF((SELECT COUNT(*) FROM Customers), 0), 1)
FROM Customers WHERE Email IS NOT NULL
UNION ALL
SELECT 'Transactions: BankAccountNumber populated', COUNT(*),
    ROUND(100.0 * COUNT(*) / NULLIF((SELECT COUNT(*) FROM Transactions), 0), 1)
FROM Transactions WHERE BankAccountNumber IS NOT NULL;
```

## Explanation

**Pattern-based PII detection**
SQL LIKE patterns detect PII formats even when column names are not informative: `[A-Z][A-Z][0-9][0-9][0-9][0-9][0-9][0-9][A-Z]` matches UK National Insurance numbers; `[0-9][0-9]-[0-9][0-9]-[0-9][0-9]` matches UK sort codes. This latent PII detection is particularly important in data warehouses where data from multiple source systems may have been merged into columns with generic names (e.g., `ReferenceCode`, `AccountRef`).

**Three PII categories**
PII exists on a spectrum: (1) direct PII (name, NI number, bank account) — directly identifies an individual; (2) quasi-PII (postcode, IP address, coordinates) — indirectly identifies when combined with other data; (3) sensitive data (salary, medical history) — not always PII but requiring restricted access. GDPR treats categories differently: direct PII requires consent/legal basis; special category PII (health, biometric) requires explicit consent; quasi-PII requires proportionality assessment.

**Masking vs encryption**
The recommended controls in Step 4 distinguish between masking (replacing PII with a functional but non-identifying substitute — showing last 4 digits of account number) and encryption (storing ciphertext that can be decrypted with the right key). Masking is appropriate for reporting and analytics where the original value is never needed; encryption is appropriate for operational data that must be readable by authorised processes but protected from unauthorised access.

**IP addresses as GDPR personal data**
Under GDPR, IP addresses are personal data when the data controller can link them to an identified individual — which is almost always the case for logged-in user activity. Step 3 flags SourceIP in the Transactions table because it links a network location to a transaction, enabling identification of the transaction originator.

## Severity
**Critical** — PII exposure in unauthorised environments violates GDPR Article 25 (data protection by design) and risks ICO enforcement (fines up to £17.5M or 4% of global turnover). SQL PII scanning should be mandatory for any database copied, migrated, or shared outside its original system boundary.
