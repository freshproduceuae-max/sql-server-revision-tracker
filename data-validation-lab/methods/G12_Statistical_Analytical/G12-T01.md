# G12-T01 — Statistical/Analytical | Moving Average Anomaly Detection

## ID
G12-T01

## Group
12 — Statistical/Analytical

## Type
Moving Average Anomaly Detection — Comparing Each Period's Value to Its Rolling Baseline

## Live Scenario
A revenue operations analyst monitors daily order totals. On the 23rd of the month, the daily total drops from the 7-day rolling average of £14,200 to £2,100 — a 85% drop. Without automated detection, this goes unnoticed until the monthly board review when the CFO asks why March revenue is 12% below forecast. Investigation reveals the payment gateway had a 6-hour outage on the 23rd that silently dropped order submissions. Orders were lost, not delayed — customers abandoned their baskets. The moving average anomaly query, run daily as a monitoring check, would have flagged this on the day it occurred and triggered incident response before the revenue was permanently lost.

## The Question
> A moving average anomaly compares each period's value to the rolling average of the preceding N periods. If the current value deviates from the rolling baseline by more than a threshold (e.g., ±30%), the period is flagged as anomalous. This detects sudden drops, spikes, and trend breaks that simple threshold rules miss.
> **"Calculate a 7-day rolling average of daily order counts and total revenue. Flag any day where the actual value deviates from the rolling average by more than 30%, and show the deviation magnitude."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`

## Solution Query

```sql
-- Step 1: Daily order metrics with 7-day rolling average
WITH DailyOrders AS (
    SELECT
        CAST(OrderDate AS DATE)  AS OrderDay,
        COUNT(*)                 AS DailyCount,
        SUM(TotalAmount)         AS DailyRevenue,
        AVG(TotalAmount)         AS DailyAvgOrder
    FROM Orders
    WHERE OrderDate IS NOT NULL
    GROUP BY CAST(OrderDate AS DATE)
),
RollingMetrics AS (
    SELECT
        OrderDay,
        DailyCount,
        DailyRevenue,
        DailyAvgOrder,
        -- 7-day rolling average of preceding days (excludes today)
        AVG(CAST(DailyCount AS FLOAT))
            OVER (ORDER BY OrderDay
                  ROWS BETWEEN 7 PRECEDING AND 1 PRECEDING)   AS Rolling7DayCount,
        AVG(DailyRevenue)
            OVER (ORDER BY OrderDay
                  ROWS BETWEEN 7 PRECEDING AND 1 PRECEDING)   AS Rolling7DayRevenue,
        -- Count of days contributing to the rolling window
        COUNT(*)
            OVER (ORDER BY OrderDay
                  ROWS BETWEEN 7 PRECEDING AND 1 PRECEDING)   AS WindowDays
    FROM DailyOrders
)
SELECT
    OrderDay,
    DailyCount,
    DailyRevenue,
    ROUND(Rolling7DayCount, 1)    AS Rolling7DayCount,
    ROUND(Rolling7DayRevenue, 2)  AS Rolling7DayRevenue,
    WindowDays,
    -- Deviation from rolling average
    ROUND(DailyCount - Rolling7DayCount, 1) AS CountDeviation,
    ROUND(DailyRevenue - Rolling7DayRevenue, 2) AS RevenueDeviation,
    ROUND(100.0 * (DailyCount - Rolling7DayCount)
          / NULLIF(Rolling7DayCount, 0), 1) AS CountDeviationPct,
    ROUND(100.0 * (DailyRevenue - Rolling7DayRevenue)
          / NULLIF(Rolling7DayRevenue, 0), 1) AS RevenueDeviationPct,
    CASE
        WHEN Rolling7DayCount IS NULL OR WindowDays < 3
             THEN 'INSUFFICIENT HISTORY: Cannot compute baseline'
        WHEN DailyCount = 0
             THEN 'ZERO ORDERS: Complete day gap — outage or holiday?'
        WHEN ABS(100.0 * (DailyCount - Rolling7DayCount) / NULLIF(Rolling7DayCount, 0)) > 50
             THEN 'CRITICAL ANOMALY: >50% deviation from 7-day rolling average'
        WHEN ABS(100.0 * (DailyCount - Rolling7DayCount) / NULLIF(Rolling7DayCount, 0)) > 30
             THEN 'ANOMALY: >30% deviation from 7-day rolling average'
        ELSE 'Normal variation'
    END AS AnomalyFlag
FROM RollingMetrics
ORDER BY OrderDay;

-- Step 2: Weekly aggregation with week-over-week change
WITH WeeklyOrders AS (
    SELECT
        DATEPART(ISO_WEEK, OrderDate) AS WeekNum,
        YEAR(OrderDate)               AS Yr,
        COUNT(*)                      AS WeeklyCount,
        SUM(TotalAmount)              AS WeeklyRevenue
    FROM Orders
    WHERE OrderDate IS NOT NULL
    GROUP BY DATEPART(ISO_WEEK, OrderDate), YEAR(OrderDate)
)
SELECT
    Yr,
    WeekNum,
    WeeklyCount,
    WeeklyRevenue,
    LAG(WeeklyCount)   OVER (ORDER BY Yr, WeekNum) AS PrevWeekCount,
    LAG(WeeklyRevenue) OVER (ORDER BY Yr, WeekNum) AS PrevWeekRevenue,
    ROUND(100.0 * (WeeklyCount - LAG(WeeklyCount) OVER (ORDER BY Yr, WeekNum))
          / NULLIF(LAG(WeeklyCount) OVER (ORDER BY Yr, WeekNum), 0), 1) AS WoWCountChangePct,
    ROUND(100.0 * (WeeklyRevenue - LAG(WeeklyRevenue) OVER (ORDER BY Yr, WeekNum))
          / NULLIF(LAG(WeeklyRevenue) OVER (ORDER BY Yr, WeekNum), 0), 1) AS WoWRevenueChangePct
FROM WeeklyOrders
ORDER BY Yr, WeekNum;

-- Step 3: Detect consecutive anomalous days (a sustained drop is more serious than a spike)
WITH DailyOrders AS (
    SELECT
        CAST(OrderDate AS DATE) AS OrderDay,
        COUNT(*) AS DailyCount,
        SUM(TotalAmount) AS DailyRevenue
    FROM Orders
    WHERE OrderDate IS NOT NULL
    GROUP BY CAST(OrderDate AS DATE)
),
WithRolling AS (
    SELECT
        OrderDay,
        DailyCount,
        AVG(CAST(DailyCount AS FLOAT))
            OVER (ORDER BY OrderDay ROWS BETWEEN 7 PRECEDING AND 1 PRECEDING) AS Baseline,
        CASE WHEN DailyCount < AVG(CAST(DailyCount AS FLOAT))
                  OVER (ORDER BY OrderDay ROWS BETWEEN 7 PRECEDING AND 1 PRECEDING) * 0.7
             THEN 1 ELSE 0 END AS BelowBaseline
    FROM DailyOrders
),
ConsecutiveGroups AS (
    SELECT
        OrderDay,
        DailyCount,
        BelowBaseline,
        ROW_NUMBER() OVER (ORDER BY OrderDay)
        - ROW_NUMBER() OVER (PARTITION BY BelowBaseline ORDER BY OrderDay) AS GroupID
    FROM WithRolling
    WHERE Baseline IS NOT NULL
)
SELECT
    MIN(OrderDay) AS PeriodStart,
    MAX(OrderDay) AS PeriodEnd,
    DATEDIFF(DAY, MIN(OrderDay), MAX(OrderDay)) + 1 AS ConsecutiveDays,
    AVG(DailyCount) AS AvgDailyCount,
    'SUSTAINED DROP: Multiple consecutive below-baseline days' AS Alert
FROM ConsecutiveGroups
WHERE BelowBaseline = 1
GROUP BY GroupID
HAVING COUNT(*) > 1
ORDER BY ConsecutiveDays DESC;
```

## Expected Output

**Step 1 — Rolling average anomaly (sample):**
| OrderDay | DailyCount | DailyRevenue | Rolling7DayCount | CountDeviationPct | AnomalyFlag |
|---|---|---|---|---|---|
| 2024-01-15 | 2 | 2100.00 | 3.2 | -37.5 | ANOMALY: >30% deviation from 7-day rolling average |
| 2024-02-20 | 4 | 6500.00 | 2.8 | 42.9 | ANOMALY: >30% deviation from 7-day rolling average |
| 2024-03-05 | 3 | 3800.00 | 2.9 | 3.4 | Normal variation |

## Explanation

**ROWS BETWEEN 7 PRECEDING AND 1 PRECEDING**
The window excludes the current day (`AND 1 PRECEDING` rather than `AND CURRENT ROW`) so the rolling average is a pure historical baseline — the current day's value is not included in the baseline against which it is compared. Using `CURRENT ROW` would contaminate the baseline with the value being assessed, making the anomaly detection circular.

**WindowDays guard**
`COUNT(*) OVER (... ROWS BETWEEN 7 PRECEDING AND 1 PRECEDING)` counts how many days actually fall in the window. For the first few days of the dataset, the window contains fewer than 7 days. The guard `WHEN WindowDays < 3` skips anomaly detection when fewer than 3 history days are available — a 2-day baseline is too thin to be reliable.

**Consecutive anomaly detection (Step 3)**
A single anomalous day may be noise (a bank holiday, a system restart). Two or more consecutive anomalous days are a sustained pattern requiring investigation. The gaps-and-islands technique using `ROW_NUMBER() - ROW_NUMBER() OVER (PARTITION BY flag)` groups consecutive flagged days into runs, and `HAVING COUNT(*) > 1` isolates multi-day drops.

**Choosing the threshold**
30% and 50% thresholds are illustrative starting points. The appropriate threshold depends on the natural day-to-day volatility of the metric: a metric with a coefficient of variation of 40% should use a wider threshold (e.g., 70%); a tightly controlled metric with CoV of 5% should use a tighter one (e.g., 15%).

## Severity
**High** — Revenue anomalies left undetected for days compound: a payment gateway outage that drops 200 orders on day 1 cannot be recovered if the orders were lost, not queued. Moving average monitoring converts reactive month-end discovery into same-day incident response, enabling intervention while recovery is still possible.
