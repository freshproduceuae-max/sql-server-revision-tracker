# G12-T08 — Statistical/Analytical | Variance and Standard Deviation Validation

## ID
G12-T08

## Group
12 — Statistical/Analytical

## Type
Variance and Standard Deviation Validation — Detecting Unexpected Spread and Homogeneity in Numeric Columns

## Live Scenario
A logistics analyst receives a daily feed of delivery time data from three courier partners. Partner A shows average delivery time of 3.2 days with standard deviation of 0.4 — extremely consistent. Partner B shows average of 3.1 days with standard deviation of 2.8 — massively variable, some deliveries taking 12 days while others take same-day. Partner C shows standard deviation of 0.0 — literally every delivery in the dataset took exactly 3 days. Zero variance is a red flag: no real-world logistics process produces identical times for every delivery. Investigation reveals Partner C is submitting fabricated performance data — they report the contractual target (3 days) for every shipment rather than actual delivery times. The standard deviation check catches data fabrication that average comparison cannot detect.

## The Question
> Standard deviation and variance measure how spread out values are around the mean. Unexpectedly low variance (including zero variance — all values identical) may indicate data fabrication, system defaults, or test data. Unexpectedly high variance may indicate mixed populations, outliers, or data quality issues. SQL validates spread using STDEV(), VAR(), and coefficient of variation.
> **"For each product, compute the standard deviation and coefficient of variation of order amounts. Flag products where the standard deviation is zero (identical pricing in all orders), suspiciously low (tight clustering suggesting non-market pricing), or suspiciously high (extreme spread suggesting data quality issues)."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Products** — `schemas/03_Products.csv`
**Transactions** — `schemas/05_Transactions.csv`

## Solution Query

```sql
-- Step 1: Per-product order amount spread analysis
WITH ProductAmounts AS (
    SELECT
        o.ProductID,
        p.ProductName,
        p.Price AS ListPrice,
        o.TotalAmount,
        o.OrderID
    FROM Orders o
    LEFT JOIN Products p ON o.ProductID = p.ProductID
    WHERE o.TotalAmount IS NOT NULL
),
ProductStats AS (
    SELECT
        ProductID,
        MAX(ProductName) AS ProductName,
        MAX(ListPrice)   AS ListPrice,
        COUNT(*)         AS OrderCount,
        ROUND(AVG(TotalAmount), 2)   AS MeanAmount,
        ROUND(MIN(TotalAmount), 2)   AS MinAmount,
        ROUND(MAX(TotalAmount), 2)   AS MaxAmount,
        ROUND(MAX(TotalAmount) - MIN(TotalAmount), 2) AS Range,
        ROUND(STDEV(TotalAmount), 2) AS StdDev,
        ROUND(VAR(TotalAmount), 2)   AS Variance
    FROM ProductAmounts
    GROUP BY ProductID
    HAVING COUNT(*) >= 2  -- need at least 2 values for meaningful STDEV
)
SELECT
    ProductID,
    ProductName,
    ListPrice,
    OrderCount,
    MeanAmount,
    MinAmount,
    MaxAmount,
    Range,
    StdDev,
    Variance,
    -- Coefficient of Variation: spread relative to mean
    ROUND(100.0 * StdDev / NULLIF(MeanAmount, 0), 1) AS CoVPct,
    -- Compare order amounts to list price
    ROUND(MeanAmount - ListPrice, 2) AS MeanVsListPrice,
    CASE
        WHEN StdDev = 0
             THEN 'ZERO VARIANCE: All orders identical — possible data fabrication or system default'
        WHEN ROUND(100.0 * StdDev / NULLIF(MeanAmount, 0), 1) < 1.0
             THEN 'NEAR-ZERO VARIANCE: CoV <1% — suspiciously uniform pricing'
        WHEN ROUND(100.0 * StdDev / NULLIF(MeanAmount, 0), 1) > 100
             THEN 'EXTREME VARIANCE: CoV >100% — mixed product types or outliers'
        WHEN ROUND(100.0 * StdDev / NULLIF(MeanAmount, 0), 1) > 50
             THEN 'HIGH VARIANCE: CoV >50% — investigate pricing consistency'
        ELSE 'Normal variance'
    END AS VarianceFlag
FROM ProductStats
ORDER BY CoVPct DESC;

-- Step 2: Cross-group variance comparison — is variance consistent across time?
WITH MonthlyStats AS (
    SELECT
        YEAR(OrderDate) AS Yr,
        MONTH(OrderDate) AS Mo,
        COUNT(*) AS OrderCount,
        ROUND(AVG(TotalAmount), 2) AS MonthMean,
        ROUND(STDEV(TotalAmount), 2) AS MonthStdDev,
        ROUND(100.0 * STDEV(TotalAmount) / NULLIF(AVG(TotalAmount), 0), 1) AS MonthCoV
    FROM Orders
    WHERE OrderDate IS NOT NULL AND TotalAmount IS NOT NULL
    GROUP BY YEAR(OrderDate), MONTH(OrderDate)
    HAVING COUNT(*) >= 3
)
SELECT
    Yr,
    Mo,
    OrderCount,
    MonthMean,
    MonthStdDev,
    MonthCoV,
    -- Compare this month's StdDev to the rolling average StdDev
    AVG(MonthStdDev) OVER (ORDER BY Yr, Mo
                            ROWS BETWEEN 2 PRECEDING AND 1 PRECEDING) AS AvgPriorStdDev,
    CASE
        WHEN MonthStdDev = 0
             THEN 'ZERO VARIANCE MONTH: All orders identical this month'
        WHEN MonthStdDev > 3 * AVG(MonthStdDev) OVER (
                ORDER BY Yr, Mo ROWS BETWEEN 2 PRECEDING AND 1 PRECEDING)
             THEN 'VARIANCE SPIKE: StdDev >3× prior average — outlier month'
        WHEN MonthStdDev < AVG(MonthStdDev) OVER (
                ORDER BY Yr, Mo ROWS BETWEEN 2 PRECEDING AND 1 PRECEDING) * 0.1
             THEN 'VARIANCE COLLAPSE: StdDev <10% of prior average — suspiciously uniform'
        ELSE 'Normal'
    END AS MonthVarianceFlag
FROM MonthlyStats
ORDER BY Yr, Mo;

-- Step 3: Detect constant-value columns across the whole table
SELECT
    'TotalAmount'  AS ColName,
    STDEV(TotalAmount)   AS StdDev,
    COUNT(DISTINCT TotalAmount) AS DistinctValues,
    MIN(TotalAmount) AS MinVal, MAX(TotalAmount) AS MaxVal,
    CASE WHEN STDEV(TotalAmount) = 0 OR COUNT(DISTINCT TotalAmount) = 1
         THEN 'CONSTANT: Column has no variation — unusable for analysis'
         ELSE 'Variable' END AS VariationFlag
FROM Orders WHERE TotalAmount IS NOT NULL
UNION ALL
SELECT
    'Amount',
    STDEV(Amount),
    COUNT(DISTINCT Amount),
    MIN(Amount), MAX(Amount),
    CASE WHEN STDEV(Amount) = 0 OR COUNT(DISTINCT Amount) = 1
         THEN 'CONSTANT: Column has no variation'
         ELSE 'Variable' END
FROM Transactions WHERE Amount IS NOT NULL;

-- Step 4: Levene-like homogeneity test — is variance equal across groups?
-- Compare StdDev across Status groups; large differences suggest heteroscedasticity
WITH StatusStats AS (
    SELECT
        Status,
        COUNT(*) AS N,
        ROUND(AVG(TotalAmount), 2) AS Mean,
        ROUND(STDEV(TotalAmount), 2) AS StdDev,
        ROUND(100.0 * STDEV(TotalAmount) / NULLIF(AVG(TotalAmount), 0), 1) AS CoV
    FROM Orders
    WHERE TotalAmount IS NOT NULL
    GROUP BY Status
    HAVING COUNT(*) >= 2
)
SELECT
    Status, N, Mean, StdDev, CoV,
    ROUND(StdDev / NULLIF(MIN(StdDev) OVER (), 0), 1) AS StdDevRatioToMin,
    CASE
        WHEN StdDev / NULLIF(MIN(StdDev) OVER (), 0) > 5
             THEN 'HETEROSCEDASTIC: Variance >5× higher than lowest-variance group'
        ELSE 'Approximately homoscedastic'
    END AS HomogeneityFlag
FROM StatusStats
ORDER BY StdDev DESC;
```

## Explanation

**Coefficient of Variation (CoV) for scale-independent spread**
`STDEV / AVG × 100` expresses spread as a percentage of the mean, enabling comparison across groups with different scales. A product with mean £5,000 and StdDev £2,000 (CoV = 40%) is less variable relative to its scale than a product with mean £100 and StdDev £60 (CoV = 60%). Raw StdDev comparison across differently-scaled groups is misleading; CoV comparison is valid.

**Zero variance as a fabrication signal**
When every value in a group is identical (StdDev = 0, DistinctValues = 1), the data is either: a constant by design (a fixed-fee service), a system default (the application writes a placeholder amount), or fabricated (the supplier reports the contractual target rather than actuals). Distinguishing these requires domain knowledge, but flagging zero-variance groups for investigation is always appropriate.

**Variance across time (Step 2)**
Variance that is stable over time is expected for a mature business process. A sudden variance spike (StdDev 3× higher than the prior two months) indicates the introduction of a new product mix, a pricing change, or an outlier batch in the data. A sudden variance collapse (StdDev 90% lower) is more suspicious: it may indicate a batch load where all amounts were defaulted, or that the current month is incomplete (only same-size orders processed so far).

**Heteroscedasticity detection (Step 4)**
Heteroscedasticity — different groups having different variances — violates the assumptions of standard statistical tests (ANOVA, t-test, linear regression). Detecting it in SQL allows analysts to know before they apply these tests that the assumption of equal variance across groups is violated, avoiding incorrect statistical conclusions.

## Severity
**Medium** — Variance validation catches data quality issues (fabricated data, system defaults, outlier contamination) that mean-based checks miss. A column with the correct mean but wrong variance may still produce incorrect model predictions, incorrect confidence intervals, and incorrect test statistics. Variance checks are particularly important before any statistical modelling or significance testing step.
