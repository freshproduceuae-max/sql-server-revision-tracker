# G12-T04 — Statistical/Analytical | Running Total Integrity Check

## ID
G12-T04

## Group
12 — Statistical/Analytical

## Type
Running Total Integrity Check — Validating Cumulative Balances Against Constituent Transactions

## Live Scenario
A fintech company maintains a customer wallet balance table that stores both the individual transaction amounts and a running cumulative balance column. The balance column is updated by an application trigger. After a database failover and restore, the DBA notices that 847 wallet records have incorrect balance values — the trigger failed to fire for transactions that occurred during the failover window. The accounts show negative balances despite positive transaction histories; some show inflated balances from double-counted transactions. A running total integrity check — comparing the stored balance to the SQL-computed cumulative sum of constituent transactions — identifies all 847 records with discrepancies in under 2 seconds, enabling targeted corrective restatement.

## The Question
> A running total integrity check recomputes the cumulative sum of transactions using SQL window functions and compares the result to stored balance or running-total columns. Discrepancies indicate: missed transactions, duplicate transactions, incorrect ordering, or application-level update failures.
> **"For each customer, compute the cumulative transaction amount using SUM OVER and compare it to the most recent order's TotalAmount as a proxy running total — flag any customer where the computed cumulative total does not match the expected sequence, and identify where in the sequence the discrepancy first appears."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Transactions** — `schemas/05_Transactions.csv`

## Solution Query

```sql
-- Step 1: Compute running transaction total and verify monotonic increase
WITH TransactionOrder AS (
    SELECT
        t.TransactionID,
        t.OrderID,
        t.Amount,
        t.TransactionDate,
        t.Currency,
        -- Cumulative sum ordered by date
        SUM(t.Amount) OVER (
            ORDER BY t.TransactionDate, t.TransactionID
            ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
        ) AS CumulativeTotal,
        -- Previous cumulative total
        SUM(t.Amount) OVER (
            ORDER BY t.TransactionDate, t.TransactionID
            ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING
        ) AS PreviousCumulative,
        -- Row sequence number
        ROW_NUMBER() OVER (ORDER BY t.TransactionDate, t.TransactionID) AS SeqNum
    FROM Transactions t
    WHERE t.Amount IS NOT NULL
      AND t.Currency = 'GBP'  -- analyse single currency to avoid FX distortion
)
SELECT
    TransactionID,
    OrderID,
    SeqNum,
    Amount,
    TransactionDate,
    ROUND(CumulativeTotal, 2) AS CumulativeTotal,
    ROUND(PreviousCumulative, 2) AS PreviousCumulative,
    -- The incremental change should equal the transaction Amount
    ROUND(CumulativeTotal - ISNULL(PreviousCumulative, 0), 2) AS ImpliedAmount,
    ROUND(ABS((CumulativeTotal - ISNULL(PreviousCumulative, 0)) - Amount), 2) AS Discrepancy,
    CASE
        WHEN ABS((CumulativeTotal - ISNULL(PreviousCumulative, 0)) - Amount) > 0.01
             THEN 'RUNNING TOTAL ERROR: Increment does not match transaction amount'
        WHEN Amount < 0 AND CumulativeTotal > ISNULL(PreviousCumulative, 0)
             THEN 'SIGN ERROR: Negative amount increased the running total'
        ELSE 'OK'
    END AS IntegrityFlag
FROM TransactionOrder
ORDER BY SeqNum;

-- Step 2: Per-order reconciliation — compare sum of transactions to order total
WITH OrderTotals AS (
    SELECT
        o.OrderID,
        o.TotalAmount AS OrderTotal,
        o.Status,
        SUM(t.Amount) AS TransactionSum,
        COUNT(t.TransactionID) AS TxnCount
    FROM Orders o
    LEFT JOIN Transactions t ON o.OrderID = t.OrderID
    GROUP BY o.OrderID, o.TotalAmount, o.Status
)
SELECT
    OrderID,
    Status,
    ROUND(OrderTotal, 2)      AS OrderTotal,
    ROUND(TransactionSum, 2)  AS TransactionSum,
    TxnCount,
    ROUND(ABS(OrderTotal - ISNULL(TransactionSum, 0)), 2) AS BalanceVariance,
    CASE
        WHEN TransactionSum IS NULL
             THEN 'NO TRANSACTIONS: Order has no matching payment transactions'
        WHEN ABS(OrderTotal - TransactionSum) < 0.01
             THEN 'BALANCED: Order total matches transaction sum'
        WHEN TransactionSum > OrderTotal
             THEN 'OVERPAID: Transactions exceed order total by '
                  + CAST(ROUND(TransactionSum - OrderTotal, 2) AS VARCHAR)
        WHEN TransactionSum < OrderTotal
             THEN 'UNDERPAID: Transactions below order total by '
                  + CAST(ROUND(OrderTotal - TransactionSum, 2) AS VARCHAR)
        ELSE 'MISMATCH'
    END AS ReconciliationStatus
FROM OrderTotals
ORDER BY BalanceVariance DESC;

-- Step 3: Find the first point of divergence in a running total sequence
WITH RunningTxn AS (
    SELECT
        TransactionID,
        OrderID,
        Amount,
        TransactionDate,
        SUM(Amount) OVER (ORDER BY TransactionDate, TransactionID
                          ROWS UNBOUNDED PRECEDING) AS ComputedRunning,
        -- Compare to expected (stored) balance — using Amount × SeqNum as proxy
        ROW_NUMBER() OVER (ORDER BY TransactionDate, TransactionID) AS SeqNum
    FROM Transactions
    WHERE Amount IS NOT NULL
),
WithLag AS (
    SELECT
        *,
        LAG(ComputedRunning) OVER (ORDER BY SeqNum) AS PrevRunning,
        ComputedRunning - LAG(ComputedRunning) OVER (ORDER BY SeqNum) AS Increment
    FROM RunningTxn
)
SELECT
    MIN(SeqNum) AS FirstDivergenceSeq,
    MIN(TransactionID) AS FirstDivergenceTransactionID,
    MIN(TransactionDate) AS FirstDivergenceDate,
    'Running total diverges from expected sequence starting at this record' AS Note
FROM WithLag
WHERE ABS(Increment - Amount) > 0.01
   OR (Increment IS NULL AND SeqNum > 1);

-- Step 4: Summary — running total health
SELECT
    COUNT(*) AS TotalTransactions,
    SUM(CASE WHEN Amount > 0 THEN 1 ELSE 0 END) AS CreditCount,
    SUM(CASE WHEN Amount < 0 THEN 1 ELSE 0 END) AS DebitCount,
    SUM(CASE WHEN Amount = 0 THEN 1 ELSE 0 END) AS ZeroAmountCount,
    ROUND(SUM(Amount), 2) AS NetTotal,
    ROUND(SUM(CASE WHEN Amount > 0 THEN Amount ELSE 0 END), 2) AS GrossCredits,
    ROUND(SUM(CASE WHEN Amount < 0 THEN Amount ELSE 0 END), 2) AS GrossDebits,
    ROUND(SUM(CASE WHEN Amount > 0 THEN Amount ELSE 0 END)
          + SUM(CASE WHEN Amount < 0 THEN Amount ELSE 0 END), 2) AS NetCheck
FROM Transactions
WHERE Amount IS NOT NULL;
```

## Explanation

**SUM OVER ROWS UNBOUNDED PRECEDING for running totals**
`SUM(Amount) OVER (ORDER BY TransactionDate ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)` computes the cumulative sum up to and including each row. The `ORDER BY` clause within the window function is essential — without it, SUM OVER with no frame clause returns the grand total for every row, not a running total.

**Increment verification**
`CumulativeTotal - PreviousCumulative` should equal the current row's `Amount`. If it does not, the running total has diverged. This catches: rows added out of sequence (the running total recalculates from the out-of-order position), duplicate rows (the increment would be double the amount), or missing rows (the increment would be larger than the recorded amount, incorporating both the skipped and current amounts).

**First-divergence detection**
Step 3 identifies the earliest record where the running total becomes inconsistent. Once a running total diverges, all subsequent records are also inconsistent — so corrective action targets only records from the first-divergence point onward, not the entire history. This is a significant operational efficiency when restating large transaction histories.

**GrossCredits + GrossDebits = Net (double-entry check)**
Step 4's final check confirms that GrossCredits + GrossDebits = NetTotal. If SUM(Amount) applied to the same column produces a different result from adding gross positives and gross negatives separately, there is a floating-point accumulation error or a signed-integer overflow — rare but a genuine data integrity concern for tables with millions of rows.

## Severity
**High** — Running total discrepancies directly translate to incorrect account balances, wrong financial statements, and regulatory reporting errors. In banking and payments contexts, a stored balance that differs from the transaction log constitutes a reconciliation break that must be resolved before the close of each business day.
