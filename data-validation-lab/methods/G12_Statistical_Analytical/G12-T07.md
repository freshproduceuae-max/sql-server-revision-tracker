# G12-T07 — Statistical/Analytical | Regression to Mean Detection

## ID
G12-T07

## Group
12 — Statistical/Analytical

## Type
Regression to Mean Detection — Identifying Entities Whose Performance Is Unusually Far From the Group Average

## Live Scenario
A sales operations analyst is reviewing commission calculations. Sales representatives are ranked each quarter and the top performers receive a 20% bonus commission rate, bottom performers receive 10%. The analyst notices the same reps appear at the top and bottom repeatedly — but when she plots their performance month by month, she sees extreme quarters always followed by a return toward the average. A rep with £180,000 in Q1 (the top) drops to £95,000 in Q2 (near average). A rep with £40,000 in Q1 (the bottom) rises to £85,000 in Q2 (near average). This is regression to the mean — not evidence that the bonus/penalty system is working, but statistical noise reverting. The analyst flags this to the CFO: the commission structure is rewarding and penalising random variance, not real performance differences. SQL-based detection of extreme-then-average sequences makes this pattern visible without a statistical package.

## The Question
> Regression to the mean occurs when an entity that performs extremely well or extremely poorly in one period tends to perform closer to the group average in the next period. SQL detects this pattern by comparing each entity's current-period deviation from the mean to the prior period's deviation — entities that were extreme and are now closer to the mean are candidates for regression-to-mean analysis.
> **"For each salesperson and quarter, compute their deviation from the group average, identify quarters where a salesperson was in the extreme top or bottom 20%, and flag cases where the following quarter shows reversion toward the mean."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Employees** — `schemas/04_Employees.csv`
**SalesTargets** — `schemas/06_SalesTargets.csv`

## Solution Query

```sql
-- Step 1: Quarterly revenue per customer as proxy for salesperson performance
WITH QuarterlyPerformance AS (
    SELECT
        CustomerID AS EntityID,
        YEAR(OrderDate) AS Yr,
        DATEPART(QUARTER, OrderDate) AS Qtr,
        COUNT(*) AS OrderCount,
        SUM(TotalAmount) AS QuarterlyRevenue
    FROM Orders
    WHERE OrderDate IS NOT NULL
      AND TotalAmount IS NOT NULL
    GROUP BY CustomerID, YEAR(OrderDate), DATEPART(QUARTER, OrderDate)
),
WithGroupStats AS (
    SELECT
        EntityID,
        Yr,
        Qtr,
        QuarterlyRevenue,
        -- Group average for this period
        AVG(QuarterlyRevenue) OVER (PARTITION BY Yr, Qtr) AS PeriodAvg,
        STDEV(QuarterlyRevenue) OVER (PARTITION BY Yr, Qtr) AS PeriodStdDev,
        -- Z-score: how many std devs from the period mean?
        (QuarterlyRevenue - AVG(QuarterlyRevenue) OVER (PARTITION BY Yr, Qtr))
            / NULLIF(STDEV(QuarterlyRevenue) OVER (PARTITION BY Yr, Qtr), 0) AS ZScore,
        -- Percentile rank within period
        PERCENT_RANK() OVER (PARTITION BY Yr, Qtr ORDER BY QuarterlyRevenue) AS PctRank
    FROM QuarterlyPerformance
),
WithLag AS (
    SELECT
        *,
        -- Prior period Z-score
        LAG(ZScore) OVER (PARTITION BY EntityID ORDER BY Yr, Qtr) AS PriorZScore,
        LAG(QuarterlyRevenue) OVER (PARTITION BY EntityID ORDER BY Yr, Qtr) AS PriorRevenue,
        LAG(PctRank) OVER (PARTITION BY EntityID ORDER BY Yr, Qtr) AS PriorPctRank
    FROM WithGroupStats
)
SELECT
    EntityID,
    Yr,
    Qtr,
    ROUND(QuarterlyRevenue, 2) AS Revenue,
    ROUND(PeriodAvg, 2) AS PeriodAvg,
    ROUND(ZScore, 2) AS CurrentZScore,
    ROUND(PriorZScore, 2) AS PriorZScore,
    ROUND(PctRank * 100, 1) AS CurrentPctRank,
    ROUND(PriorPctRank * 100, 1) AS PriorPctRank,
    -- Detect regression: was extreme, now closer to mean
    CASE
        WHEN PriorZScore IS NULL
             THEN 'First period — no prior data'
        WHEN PriorZScore > 1.5 AND ZScore < 0.5
             THEN 'REGRESSION FROM HIGH: Was top performer, now near average'
        WHEN PriorZScore < -1.5 AND ZScore > -0.5
             THEN 'REGRESSION FROM LOW: Was bottom performer, now near average'
        WHEN PriorPctRank >= 0.80 AND PctRank < 0.60
             THEN 'REVERSION: Dropped from top 20% to below top 40%'
        WHEN PriorPctRank <= 0.20 AND PctRank > 0.40
             THEN 'REVERSION: Rose from bottom 20% to above bottom 40%'
        ELSE 'No significant reversion'
    END AS RegressionFlag,
    ROUND(ZScore - PriorZScore, 2) AS ZScoreChange
FROM WithLag
WHERE PriorZScore IS NOT NULL
ORDER BY EntityID, Yr, Qtr;

-- Step 2: Count regression events per entity — habitual regressors
WITH QuarterlyPerformance AS (
    SELECT CustomerID AS EntityID,
           YEAR(OrderDate) AS Yr, DATEPART(QUARTER, OrderDate) AS Qtr,
           SUM(TotalAmount) AS QuarterlyRevenue
    FROM Orders WHERE OrderDate IS NOT NULL AND TotalAmount IS NOT NULL
    GROUP BY CustomerID, YEAR(OrderDate), DATEPART(QUARTER, OrderDate)
),
WithStats AS (
    SELECT *, (QuarterlyRevenue - AVG(QuarterlyRevenue) OVER (PARTITION BY Yr, Qtr))
               / NULLIF(STDEV(QuarterlyRevenue) OVER (PARTITION BY Yr, Qtr), 0) AS ZScore
    FROM QuarterlyPerformance
),
WithLag AS (
    SELECT *, LAG(ZScore) OVER (PARTITION BY EntityID ORDER BY Yr, Qtr) AS PriorZScore
    FROM WithStats
)
SELECT
    EntityID,
    COUNT(*) AS TotalPeriods,
    SUM(CASE WHEN PriorZScore > 1.5 AND ZScore < 0.5 THEN 1 ELSE 0 END) AS HighToAvgEvents,
    SUM(CASE WHEN PriorZScore < -1.5 AND ZScore > -0.5 THEN 1 ELSE 0 END) AS LowToAvgEvents,
    ROUND(AVG(ZScore), 2) AS AvgZScore,
    ROUND(MAX(ZScore), 2) AS MaxZScore,
    ROUND(MIN(ZScore), 2) AS MinZScore
FROM WithLag
WHERE PriorZScore IS NOT NULL
GROUP BY EntityID
HAVING SUM(CASE WHEN PriorZScore > 1.5 AND ZScore < 0.5 THEN 1
                WHEN PriorZScore < -1.5 AND ZScore > -0.5 THEN 1
                ELSE 0 END) >= 1
ORDER BY HighToAvgEvents + LowToAvgEvents DESC;

-- Step 3: SalesTargets deviation — actual vs target comparison
SELECT
    st.SalespersonID,
    st.Year,
    st.Quarter,
    st.TargetAmount,
    -- Sum of orders as proxy for actual performance
    ROUND(SUM(o.TotalAmount), 2) AS ActualAmount,
    ROUND(SUM(o.TotalAmount) - st.TargetAmount, 2) AS Variance,
    ROUND(100.0 * (SUM(o.TotalAmount) - st.TargetAmount) / NULLIF(st.TargetAmount, 0), 1)
        AS VariancePct,
    CASE
        WHEN SUM(o.TotalAmount) IS NULL
             THEN 'NO ORDERS: No sales recorded for this target period'
        WHEN SUM(o.TotalAmount) > st.TargetAmount * 1.5
             THEN 'FAR ABOVE TARGET: >50% over — verify this is not a data error'
        WHEN SUM(o.TotalAmount) < st.TargetAmount * 0.5
             THEN 'FAR BELOW TARGET: <50% of target — significant underperformance'
        ELSE 'Near target'
    END AS TargetFlag
FROM SalesTargets st
LEFT JOIN Orders o ON YEAR(o.OrderDate) = st.Year
    AND DATEPART(QUARTER, o.OrderDate) = st.Quarter
    AND o.CustomerID = st.SalespersonID  -- approximation for demo data
GROUP BY st.SalespersonID, st.Year, st.Quarter, st.TargetAmount
ORDER BY st.Year, st.Quarter, st.SalespersonID;
```

## Explanation

**Z-score for cross-period comparability**
Comparing raw revenue across periods is misleading when the overall market grows or shrinks. Z-scores normalise for the period's distribution: a Z-score of +2 means "2 standard deviations above the period average," regardless of whether the period average was £80,000 or £150,000. This makes cross-quarter comparisons meaningful even when absolute revenue levels shift.

**LAG for prior-period comparison**
`LAG(ZScore) OVER (PARTITION BY EntityID ORDER BY Yr, Qtr)` retrieves each entity's Z-score from the previous quarter. The `PARTITION BY EntityID` ensures the lag is within each entity's own time series — it does not compare across entities. The combination of `PriorZScore > 1.5` (was extreme) with `ZScore < 0.5` (now near average) is the regression-to-mean pattern.

**Why regression to mean matters for performance management**
If performance naturally reverts to average after extreme periods, rewarding extreme-high performance and penalising extreme-low performance creates a system that rewards luck (an unusually good quarter) and penalises bad luck (an unusually bad quarter) — not underlying skill differences. Detecting regression events helps separate genuine performance changes from statistical noise before making compensation, staffing, or strategy decisions.

**SalesTargets join approximation**
Step 3 joins SalesTargets to Orders using CustomerID as a proxy for SalespersonID. In a production system, this join would use the actual salesperson assignment. The pattern — comparing actual to target by period — remains valid: far-above-target performance (>150%) is itself a data quality flag, as it may indicate a target was set too low or orders were attributed to the wrong period.

## Severity
**Low** — Regression to mean analysis is an analytical validity check rather than a data integrity check. Its primary value is preventing incorrect causal attribution: businesses that interpret natural regression-to-mean fluctuations as evidence that their interventions are working (or not working) make systematically flawed management decisions. SQL-based detection makes this pattern visible to analysts who do not have access to statistical packages.
