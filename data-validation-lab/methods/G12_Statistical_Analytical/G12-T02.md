# G12-T02 — Statistical/Analytical | Cohort Analysis Validation

## ID
G12-T02

## Group
12 — Statistical/Analytical

## Type
Cohort Analysis Validation — Verifying That Customer Cohorts Are Correctly Defined and Consistently Assigned

## Live Scenario
A product team builds a customer retention model based on cohorts defined by the month of a customer's first order. The model shows January 2024 cohort retention at 94% — suspiciously high. Investigation reveals a data quality issue: customers who were re-activated after a dormant period are being assigned to their re-activation month, not their original first-order month. A February re-activated customer who originally joined in June 2022 appears in the February 2024 cohort, inflating its apparent size. When the correct first-order date is used, January 2024 cohort retention falls to 61% — consistent with industry benchmarks. The cohort definition logic itself is the source of the data quality issue.

## The Question
> Cohort analysis groups customers (or entities) by a defining event (first purchase, registration date, etc.) and tracks their behaviour over subsequent periods. Cohort validation checks that: each entity is assigned to exactly one cohort, the cohort definition is applied consistently, and cohort sizes are plausible given the acquisition history.
> **"Define customer acquisition cohorts by their first order month, validate that each customer belongs to exactly one cohort, show cohort sizes and order activity in subsequent months, and flag any customers whose cohort assignment may be incorrect."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Customers** — `schemas/01_Customers.csv`

## Solution Query

```sql
-- Step 1: Define acquisition cohorts — each customer's first order month
WITH CustomerFirstOrder AS (
    SELECT
        CustomerID,
        MIN(OrderDate)          AS FirstOrderDate,
        YEAR(MIN(OrderDate))    AS CohortYear,
        MONTH(MIN(OrderDate))   AS CohortMonth,
        -- Cohort label for grouping
        CAST(YEAR(MIN(OrderDate)) AS VARCHAR) + '-'
            + RIGHT('0' + CAST(MONTH(MIN(OrderDate)) AS VARCHAR), 2) AS CohortLabel
    FROM Orders
    WHERE OrderDate IS NOT NULL
    GROUP BY CustomerID
),
-- Validate: every customer in Orders should have exactly one cohort
CohortValidation AS (
    SELECT
        CustomerID,
        COUNT(DISTINCT CohortLabel) AS CohortCount
    FROM CustomerFirstOrder
    GROUP BY CustomerID
)
SELECT
    cv.CustomerID,
    cv.CohortCount,
    CASE
        WHEN cv.CohortCount > 1
             THEN 'ERROR: Customer assigned to multiple cohorts'
        ELSE 'OK: Single cohort assignment'
    END AS CohortValidationFlag
FROM CohortValidation cv
WHERE cv.CohortCount <> 1;

-- Step 2: Cohort size and month-0 activity
WITH CustomerFirstOrder AS (
    SELECT
        CustomerID,
        MIN(OrderDate)       AS FirstOrderDate,
        CAST(YEAR(MIN(OrderDate)) AS VARCHAR) + '-'
            + RIGHT('0' + CAST(MONTH(MIN(OrderDate)) AS VARCHAR), 2) AS CohortLabel
    FROM Orders
    WHERE OrderDate IS NOT NULL
    GROUP BY CustomerID
)
SELECT
    CohortLabel,
    COUNT(DISTINCT CustomerID) AS CohortSize,
    SUM(COUNT(DISTINCT CustomerID)) OVER () AS TotalCohortedCustomers,
    ROUND(100.0 * COUNT(DISTINCT CustomerID)
          / SUM(COUNT(DISTINCT CustomerID)) OVER (), 1) AS PctOfTotal,
    MIN(FirstOrderDate) AS EarliestAcquisition,
    MAX(FirstOrderDate) AS LatestAcquisition,
    CASE
        WHEN COUNT(DISTINCT CustomerID) < 2
             THEN 'SMALL COHORT: Too few customers for reliable retention analysis'
        WHEN COUNT(DISTINCT CustomerID) > COUNT(DISTINCT CustomerID) * 3
             THEN 'LARGE COHORT: Unusually large — check for cohort definition error'
        ELSE 'Normal cohort size'
    END AS CohortSizeFlag
FROM CustomerFirstOrder
GROUP BY CohortLabel
ORDER BY CohortLabel;

-- Step 3: Cohort retention — how many customers from each cohort placed orders in subsequent months?
WITH CustomerFirstOrder AS (
    SELECT
        CustomerID,
        MIN(OrderDate) AS FirstOrderDate,
        CAST(YEAR(MIN(OrderDate)) AS VARCHAR) + '-'
            + RIGHT('0' + CAST(MONTH(MIN(OrderDate)) AS VARCHAR), 2) AS CohortLabel,
        YEAR(MIN(OrderDate)) * 12 + MONTH(MIN(OrderDate)) AS CohortPeriodNum
    FROM Orders
    WHERE OrderDate IS NOT NULL
    GROUP BY CustomerID
),
OrderActivity AS (
    SELECT
        o.CustomerID,
        YEAR(o.OrderDate) * 12 + MONTH(o.OrderDate) AS OrderPeriodNum
    FROM Orders o
    WHERE o.OrderDate IS NOT NULL
)
SELECT
    c.CohortLabel,
    COUNT(DISTINCT c.CustomerID) AS CohortSize,
    oa.OrderPeriodNum - c.CohortPeriodNum AS MonthsSinceAcquisition,
    COUNT(DISTINCT oa.CustomerID) AS ActiveCustomers,
    ROUND(100.0 * COUNT(DISTINCT oa.CustomerID)
          / NULLIF(COUNT(DISTINCT c.CustomerID), 0), 1) AS RetentionPct
FROM CustomerFirstOrder c
JOIN OrderActivity oa ON c.CustomerID = oa.CustomerID
WHERE oa.OrderPeriodNum >= c.CohortPeriodNum
GROUP BY c.CohortLabel, c.CohortPeriodNum, oa.OrderPeriodNum - c.CohortPeriodNum
ORDER BY c.CohortLabel, MonthsSinceAcquisition;

-- Step 4: Detect potentially mis-assigned cohort members
-- Customers in the Customers table but never in Orders are not in any cohort
SELECT
    c.CustomerID,
    c.FirstName,
    c.LastName,
    c.IsActive,
    'NO COHORT: Customer exists but has no orders — excluded from all cohorts' AS CohortFlag
FROM Customers c
LEFT JOIN Orders o ON c.CustomerID = o.CustomerID
WHERE o.OrderID IS NULL;
```

## Explanation

**MIN(OrderDate) as the cohort anchor**
Using `MIN(OrderDate) GROUP BY CustomerID` assigns each customer to the period of their very first order. This is robust: even if a customer's records are reloaded or the table is re-sorted, the MIN always returns the same value. Using `ROW_NUMBER()` to find the first record would be fragile — a tie on OrderDate would produce non-deterministic cohort assignments.

**Period arithmetic with Yr×12+Mo**
`YEAR(OrderDate) * 12 + MONTH(OrderDate)` converts year-month pairs into a monotonically increasing integer. Subtracting the cohort period number from the order period number gives "months since acquisition" — a single integer that works correctly across year boundaries (January 2025 = 2025×12+1 = 24301; December 2024 = 2024×12+12 = 24300; difference = 1).

**Cohort validation: exactly one cohort per entity**
Step 1's `COUNT(DISTINCT CohortLabel)` per customer should always be 1. A result greater than 1 indicates a query bug where the same customer appears in multiple cohorts — typically from a JOIN that produces fan-out, assigning the customer to each order's month rather than the first order's month.

**Customers without cohort membership**
Step 4 identifies customers registered in the Customers table who have never placed an order. These customers are invisible to all cohort analyses — they are acquired (registered) but have never converted. Their exclusion from retention analysis may overstate retention rates if non-converting customers are systematically different from converting ones.

## Severity
**Medium** — Cohort definition errors produce fundamentally misleading retention and lifetime value metrics. A 94% retention figure that drops to 61% when the cohort definition is corrected would cause a product team to significantly over-invest in acquisition (believing retention is strong) and under-invest in activation (failing to address the actual 39% churn in month 1).
