# G15-T06 — ETL/Load Process | Load Window and Boundary Condition Check

## ID
G15-T06

## Group
15 — ETL/Load Process

## Type
Load Window and Boundary Condition Check — Validating That Each ETL Run Covers the Correct Date Range Without Gaps or Overlaps

## Live Scenario
An ETL pipeline runs nightly and loads all orders with `OrderDate >= @LastRunDate`. The @LastRunDate is stored in a control table and updated after each successful run. On March 14th, the ETL job runs but the control table update fails (a database timeout). On March 15th, the ETL re-runs with the same @LastRunDate as March 13th — doubling up the March 14th records. Two days later, when an operator manually resets the @LastRunDate to March 15th to skip the failed date, March 14th is loaded a third time from the re-run, and March 15th early-morning orders are never loaded (the manual reset skipped them). The boundary condition check, run after each load, compares the actual date range of loaded records against the expected load window — immediately flagging the gap on March 15th and the duplication on March 14th.

## The Question
> Load window boundary checks verify that each ETL run loaded records from exactly the correct date range: no overlap with prior loads (no re-loading of already-processed records), no gaps (no periods left unloaded), and correct boundary inclusivity (the start date is exclusive of the prior period and the end date is inclusive of the current period). SQL validates this by comparing loaded record timestamps against the expected window boundaries.
> **"Validate the load window for the Orders ETL: verify the date range of loaded records matches the expected extraction window, detect any records that fall outside the expected window, identify duplicate date coverage between consecutive load batches, and flag any date gaps between the current load and the prior load."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Transactions** — `schemas/05_Transactions.csv`

## Solution Query

```sql
-- Step 1: Determine the actual date coverage of each month as a proxy for load batches
WITH MonthlyCoverage AS (
    SELECT
        YEAR(OrderDate)  AS LoadYear,
        MONTH(OrderDate) AS LoadMonth,
        COUNT(*)         AS RecordCount,
        MIN(CAST(OrderDate AS DATE)) AS FirstDate,
        MAX(CAST(OrderDate AS DATE)) AS LastDate,
        DATEDIFF(DAY, MIN(CAST(OrderDate AS DATE)), MAX(CAST(OrderDate AS DATE))) + 1
            AS DaysSpanned,
        COUNT(DISTINCT CAST(OrderDate AS DATE)) AS DaysWithRecords
    FROM Orders
    WHERE OrderDate IS NOT NULL
    GROUP BY YEAR(OrderDate), MONTH(OrderDate)
)
SELECT
    LoadYear,
    LoadMonth,
    RecordCount,
    FirstDate,
    LastDate,
    DaysSpanned,
    DaysWithRecords,
    -- Coverage: fraction of the spanned range that has records
    ROUND(100.0 * DaysWithRecords / NULLIF(DaysSpanned, 0), 1) AS CoveragePct,
    -- Gap from prior month's end to this month's start
    LAG(LastDate) OVER (ORDER BY LoadYear, LoadMonth) AS PriorMonthLastDate,
    DATEDIFF(DAY,
             LAG(LastDate) OVER (ORDER BY LoadYear, LoadMonth),
             FirstDate) AS DaysSincePriorBatch,
    CASE
        WHEN LAG(LastDate) OVER (ORDER BY LoadYear, LoadMonth) IS NULL
             THEN 'First batch'
        WHEN DATEDIFF(DAY,
                      LAG(LastDate) OVER (ORDER BY LoadYear, LoadMonth),
                      FirstDate) > 35
             THEN 'POTENTIAL GAP: ' + CAST(DATEDIFF(DAY,
                                                     LAG(LastDate) OVER (ORDER BY LoadYear, LoadMonth),
                                                     FirstDate) AS VARCHAR)
                  + ' days between last record of prior batch and first record of this batch'
        ELSE 'Contiguous batches'
    END AS BatchContinuityFlag
FROM MonthlyCoverage
ORDER BY LoadYear, LoadMonth;

-- Step 2: Detect records outside the expected load window
-- Define expected window: current month only
DECLARE @WindowStart DATE = DATEFROMPARTS(YEAR(GETDATE()), MONTH(GETDATE()), 1);
DECLARE @WindowEnd   DATE = EOMONTH(GETDATE());

SELECT
    OrderID,
    CAST(OrderDate AS DATE) AS OrderDate,
    TotalAmount,
    Status,
    CASE
        WHEN CAST(OrderDate AS DATE) < @WindowStart
             THEN 'BEFORE WINDOW: Record date ' + CAST(CAST(OrderDate AS DATE) AS VARCHAR)
                  + ' is before load window start ' + CAST(@WindowStart AS VARCHAR)
                  + ' — possible re-load of prior period'
        WHEN CAST(OrderDate AS DATE) > @WindowEnd
             THEN 'AFTER WINDOW: Record date is beyond current window — future-dated or wrong period'
        ELSE 'Within window'
    END AS WindowFlag
FROM Orders
WHERE OrderDate IS NOT NULL
  AND (CAST(OrderDate AS DATE) < @WindowStart OR CAST(OrderDate AS DATE) > @WindowEnd);

-- Step 3: Boundary inclusivity check — are boundary dates inclusive?
SELECT
    'Window start boundary' AS Check_,
    MIN(CAST(OrderDate AS DATE)) AS BoundaryDate,
    COUNT(*) AS RecordsOnBoundary
FROM Orders
WHERE CAST(OrderDate AS DATE) = (SELECT MIN(CAST(OrderDate AS DATE)) FROM Orders)
UNION ALL
SELECT
    'Window end boundary',
    MAX(CAST(OrderDate AS DATE)),
    COUNT(*)
FROM Orders
WHERE CAST(OrderDate AS DATE) = (SELECT MAX(CAST(OrderDate AS DATE)) FROM Orders);

-- Step 4: Day-by-day coverage — are there any days with zero records?
WITH DateRange AS (
    -- Generate all dates in the range using a number sequence
    SELECT
        DATEADD(DAY, n.Number, (SELECT MIN(CAST(OrderDate AS DATE)) FROM Orders)) AS CalendarDate
    FROM (
        SELECT ROW_NUMBER() OVER (ORDER BY (SELECT NULL)) - 1 AS Number
        FROM Orders o1 CROSS JOIN Orders o2
    ) n
    WHERE DATEADD(DAY, n.Number, (SELECT MIN(CAST(OrderDate AS DATE)) FROM Orders))
          <= (SELECT MAX(CAST(OrderDate AS DATE)) FROM Orders)
),
DailyActual AS (
    SELECT CAST(OrderDate AS DATE) AS OrderDay, COUNT(*) AS DailyCount
    FROM Orders WHERE OrderDate IS NOT NULL
    GROUP BY CAST(OrderDate AS DATE)
)
SELECT
    d.CalendarDate,
    ISNULL(a.DailyCount, 0) AS RecordCount,
    CASE
        WHEN a.DailyCount IS NULL
             THEN 'GAP: No records on this date — possible load gap or non-trading day'
        ELSE 'Has records'
    END AS CoverageFlag
FROM DateRange d
LEFT JOIN DailyActual a ON d.CalendarDate = a.OrderDay
WHERE a.DailyCount IS NULL   -- show only gap dates
ORDER BY d.CalendarDate;

-- Step 5: Transaction window validation
SELECT
    'Orders date range'       AS Dataset,
    MIN(CAST(OrderDate AS DATE)) AS MinDate,
    MAX(CAST(OrderDate AS DATE)) AS MaxDate,
    DATEDIFF(DAY, MIN(CAST(OrderDate AS DATE)), MAX(CAST(OrderDate AS DATE))) AS SpanDays
FROM Orders WHERE OrderDate IS NOT NULL
UNION ALL
SELECT
    'Transactions date range',
    MIN(CAST(TransactionDate AS DATE)),
    MAX(CAST(TransactionDate AS DATE)),
    DATEDIFF(DAY, MIN(CAST(TransactionDate AS DATE)), MAX(CAST(TransactionDate AS DATE)))
FROM Transactions WHERE TransactionDate IS NOT NULL;
```

## Explanation

**Watermark boundary conditions**
The two most common boundary errors in watermark-based ETL are: (1) `>=` vs `>` — using `>= LastRunDate` re-loads the record that had exactly the LastRunDate value, creating a duplicate; (2) end boundary exclusivity — using `< NextRunDate` vs `<= CurrentRunDate` affects whether the boundary record is included once or twice in adjacent load windows. The boundary inclusivity check (Step 3) verifies that records on boundary dates are present and not duplicated.

**Gap day detection using date spine**
Step 4 generates a complete calendar of dates between the minimum and maximum OrderDate using a cross-join row generator. Joining this calendar to the actual data and filtering for NULL daily counts identifies specific dates with no records. These may be legitimate (weekends, bank holidays) or indicate a load gap. The analyst should compare the gap dates against a non-trading-day calendar to determine which are expected.

**Cross-dataset window alignment (Step 5)**
The Orders date range should align with the Transactions date range — if transactions cover March 1–20 but orders only cover March 1–15, there are either 5 days of unmatched transactions or the Orders load was incomplete. Step 5 compares the date spans of related tables, flagging misalignments that indicate an incomplete load of one table.

**Prior batch gap detection**
`DATEDIFF(DAY, LAG(LastDate) OVER (...), FirstDate)` measures the gap between the last record of the prior batch and the first record of the current batch. For a daily ETL loading overlapping days, this should be 0–1 days. For a monthly ETL loading non-overlapping periods, it should be 1–5 days (depending on the calendar). A gap of 35+ days between monthly batches suggests a missed month.

## Severity
**High** — Load window boundary errors are the most common cause of duplicate and missing data in incremental ETL systems. They are particularly dangerous because they are systematic — every affected record suffers the same error — and they are invisible in individual record checks. Only range-level validation comparing actual record dates against expected window boundaries can detect these failures reliably.
