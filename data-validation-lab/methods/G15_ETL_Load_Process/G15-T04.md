# G15-T04 — ETL/Load Process | Type Coercion and Implicit Conversion Audit

## ID
G15-T04

## Group
15 — ETL/Load Process

## Type
Type Coercion and Implicit Conversion Audit — Detecting Silent Data Type Mismatches During Load

## Live Scenario
A data migration team migrates a legacy Oracle database to SQL Server. The Oracle source stores order amounts as VARCHAR2(20) (text) because the legacy application pre-dates proper numeric data types. The SQL Server target has `TotalAmount DECIMAL(18,2)`. During migration, the ETL does an implicit conversion: most values convert fine, but 230 records contain commas as thousand separators (`"1,500.00"`) and 45 records contain currency symbols (`"£2,400.00"`). SQL Server silently converts `"£2,400.00"` to an error, TRY_CAST returns NULL, and those 275 records load with NULL amounts — no error is raised. The migration report says "Success: 10,000 records loaded." But 275 records have lost their financial values. The type coercion audit, run post-load, immediately identifies all 275 rows by checking for unexpected NULLs in a column that should be non-NULL.

## The Question
> Type coercion occurs when values are converted from one data type to another during ETL. Silent coercion failures (where TRY_CAST returns NULL instead of raising an error) are particularly dangerous because they produce incomplete data without alerting the ETL operator. A coercion audit identifies fields where conversion may have silently failed, values that don't conform to the target type, and columns where the NULL rate has unexpectedly increased after a load.
> **"Audit type coercion quality on the Orders and Customers tables: identify any columns where values appear to have been silently converted to NULL (failed coercion), test string columns for latent numeric content (values stored as text that should be numbers), and check for values that survived conversion but lost precision."**

## Solution Query

```sql
-- Step 1: Test for latent numeric content in string columns
-- Values that look like numbers but are stored as strings
SELECT
    CustomerID,
    Phone,
    PostalCode,
    -- Is Phone actually a numeric string? (should NOT be numeric — valid phones have +, spaces)
    CASE
        WHEN TRY_CAST(Phone AS BIGINT) IS NOT NULL
             THEN 'NUMERIC STRING: Phone stored as pure digits — may have lost leading zero on conversion'
        WHEN Phone IS NOT NULL AND LEN(Phone) < 6
             THEN 'TOO SHORT: Phone may have been truncated during type conversion'
        ELSE 'OK'
    END AS PhoneCoercionFlag,
    -- PostalCode: should NOT be numeric
    CASE
        WHEN TRY_CAST(PostalCode AS INT) IS NOT NULL
             THEN 'NUMERIC: PostalCode converted to integer — non-numeric characters lost'
        ELSE 'OK'
    END AS PostalCoercionFlag
FROM Customers;

-- Step 2: Decimal precision audit — did conversion lose decimal places?
SELECT
    OrderID,
    TotalAmount,
    -- Check if value is a round integer (possible precision loss from FLOAT conversion)
    CASE
        WHEN TotalAmount = FLOOR(TotalAmount)
             AND TotalAmount IS NOT NULL
             THEN 'ROUND NUMBER: No decimal places — possible precision loss in conversion'
        WHEN TotalAmount IS NULL
             THEN 'NULL: Possible failed conversion from source'
        ELSE 'Has decimal places'
    END AS PrecisionFlag,
    -- Check for excessive decimal places (possible FLOAT contamination)
    CASE
        WHEN TotalAmount <> ROUND(TotalAmount, 2)
             THEN 'EXCESS PRECISION: More than 2 decimal places — possible FLOAT arithmetic error'
        ELSE 'Correct 2dp precision'
    END AS DecimalPlaceFlag
FROM Orders
WHERE TotalAmount IS NOT NULL;

-- Step 3: Date coercion validation — check dates are in valid range and not default sentinel values
SELECT
    OrderID,
    OrderDate,
    DeliveryDate,
    CASE
        WHEN OrderDate IS NULL
             THEN 'NULL: Possible date conversion failure'
        WHEN OrderDate < '1990-01-01'
             THEN 'HISTORIC DATE: OrderDate before 1990 — possible epoch/sentinel value from legacy system'
        WHEN OrderDate > '2099-12-31'
             THEN 'FAR FUTURE: OrderDate beyond 2099 — possible default or max-date sentinel'
        WHEN YEAR(OrderDate) = 1900 AND MONTH(OrderDate) = 1 AND DAY(OrderDate) = 1
             THEN 'EPOCH DEFAULT: 1900-01-01 is the SQL Server DATETIME default — coercion failure'
        ELSE 'Valid date'
    END AS DateCoercionFlag,
    CASE
        WHEN DeliveryDate IS NOT NULL AND YEAR(DeliveryDate) = 9999
             THEN 'SENTINEL DATE: 9999-12-31 is a DW open-ended sentinel — was this intentional?'
        ELSE 'OK'
    END AS DeliveryDateFlag
FROM Orders;

-- Step 4: Integer column coercion check
SELECT
    ProductID,
    ProductName,
    StockQuantity,
    CASE
        WHEN StockQuantity < 0
             THEN 'NEGATIVE STOCK: Possible signed/unsigned conversion error'
        WHEN StockQuantity > 2147483647
             THEN 'INT OVERFLOW: Value exceeds INT max — should be BIGINT'
        WHEN StockQuantity IS NULL
             THEN 'NULL STOCK: Possible failed integer conversion'
        ELSE 'Valid'
    END AS StockCoercionFlag,
    -- DiscountPercent: should be 0-100
    CASE
        WHEN DiscountPercent < 0 OR DiscountPercent > 100
             THEN 'RANGE ERROR: DiscountPercent ' + CAST(DiscountPercent AS VARCHAR)
                  + ' outside 0-100 — possible percentage-to-decimal confusion (0.15 vs 15%)'
        ELSE 'Valid range'
    END AS DiscountCoercionFlag
FROM Products;

-- Step 5: Coercion audit summary — NULL rate by column
SELECT
    ColName,
    TotalRows,
    NullCount,
    ROUND(100.0 * NullCount / NULLIF(TotalRows, 0), 1) AS NullPct,
    CASE
        WHEN ROUND(100.0 * NullCount / NULLIF(TotalRows, 0), 1) > 20
             THEN 'HIGH NULL RATE: >20% NULL — possible systematic coercion failure'
        WHEN NullCount > 0
             THEN 'SOME NULLS: Check if these are expected or coercion failures'
        ELSE 'No nulls'
    END AS NullFlag
FROM (
    SELECT 'TotalAmount'   AS ColName, COUNT(*) TotalRows, COUNT(*) - COUNT(TotalAmount) NullCount FROM Orders UNION ALL
    SELECT 'OrderDate',    COUNT(*), COUNT(*) - COUNT(OrderDate) FROM Orders UNION ALL
    SELECT 'Phone',        COUNT(*), COUNT(*) - COUNT(Phone) FROM Customers UNION ALL
    SELECT 'PostalCode',   COUNT(*), COUNT(*) - COUNT(PostalCode) FROM Customers UNION ALL
    SELECT 'StockQuantity',COUNT(*), COUNT(*) - COUNT(StockQuantity) FROM Products UNION ALL
    SELECT 'Price',        COUNT(*), COUNT(*) - COUNT(Price) FROM Products
) NullAudit
ORDER BY NullPct DESC;
```

## Explanation

**TRY_CAST as the silent failure mechanism**
`TRY_CAST(expr AS type)` returns NULL when the conversion fails instead of raising an error. This is deliberate — it allows ETL pipelines to continue processing without crashing on bad values. But it means failed conversions are invisible unless the NULL rate is monitored. Comparing the pre-load NULL rate to the post-load NULL rate identifies columns where conversion increased the NULL count.

**Round-number detection for precision loss**
After a FLOAT-to-DECIMAL conversion, values that should have decimal places often appear as round integers (e.g., £1,500 instead of £1,499.99). `TotalAmount = FLOOR(TotalAmount)` identifies values with no fractional part. A high proportion of round numbers in a financial amount column may indicate precision was lost during type conversion, or that the source stores integer cents/pence that should have been divided by 100.

**Epoch and sentinel date detection**
Legacy systems use specific date values as sentinels: `1900-01-01` is SQL Server's DATETIME minimum and the default for failed date conversions; `9999-12-31` is commonly used to represent "no end date" in SCD2 records; `0001-01-01` and `2099-12-31` are other common sentinels. These values are technically valid dates and pass NOT NULL checks — only a range check catches them.

**Percentage vs decimal confusion**
A DiscountPercent stored as 0.15 in the source (meaning 15%) and loaded directly into a column that expects 15 (meaning 15%) will be treated as 0.15% — a 99-fold understatement of the discount. This class of coercion error is entirely semantic — both values are valid numbers, both convert without error, but the interpretation is wrong. Domain range checking (0-100 for percentage columns) catches this.

## Severity
**High** — Type coercion failures are particularly insidious because TRY_CAST converts them to NULL silently. A NULL amount in a financial transaction is not "unknown" — it means the amount was present in the source and lost during loading. These NULLs then appear throughout analysis as missing values, understated totals, and division-by-zero errors, with no direct link back to the coercion event that caused them.
