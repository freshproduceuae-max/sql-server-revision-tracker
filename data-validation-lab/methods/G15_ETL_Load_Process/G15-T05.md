# G15-T05 — ETL/Load Process | Lookup and Reference Data Freshness

## ID
G15-T05

## Group
15 — ETL/Load Process

## Type
Lookup and Reference Data Freshness — Validating That Reference Tables Are Current and Complete

## Live Scenario
A bank's ETL pipeline uses a currency exchange rate lookup table to convert all transaction amounts to GBP. The table is updated daily from an FX data feed. On a Bank Holiday, the FX feed fails silently — no alert is raised and no rate update occurs. The ETL continues to run, using the previous day's rates for all transactions processed during the holiday. For most currencies, the difference is negligible (0.1–0.3%). But for a large EUR/GBP transaction of €840,000, using yesterday's rate instead of today's introduces a £2,100 error in the GBP equivalent — material for the bank's daily P&L reporting. The lookup freshness check, querying the maximum `UpdatedDate` of the exchange rate table, would have flagged the stale rates before the ETL used them.

## The Question
> Lookup and reference data freshness validation checks that lookup tables (currency rates, product codes, employee lists, postcode mappings) are: populated (not empty), recently updated (within the expected refresh interval), complete (all expected codes are present), and consistent with the production system. SQL validates these properties using MAX(UpdatedDate), COUNT, and set comparisons against expected value lists.
> **"Validate the freshness and completeness of the reference data used by the ETL: check that all expected Status values are present in the Orders table, all referenced Countries in Customers match the expected set, all ProductIDs in Orders exist in the Products table, and flag any reference gaps that would cause lookup failures."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Customers** — `schemas/01_Customers.csv`
**Products** — `schemas/03_Products.csv`
**Transactions** — `schemas/05_Transactions.csv`

## Solution Query

```sql
-- Step 1: Status lookup completeness — are all expected statuses present?
WITH ExpectedStatuses AS (
    SELECT 'Pending'    AS Status UNION ALL
    SELECT 'Processing' UNION ALL
    SELECT 'Delivered'  UNION ALL
    SELECT 'Cancelled'  UNION ALL
    SELECT 'Returned'
),
ActualStatuses AS (
    SELECT DISTINCT Status FROM Orders WHERE Status IS NOT NULL
)
SELECT
    e.Status AS ExpectedStatus,
    a.Status AS ActualStatus,
    CASE
        WHEN a.Status IS NULL
             THEN 'MISSING: Expected status not found in data — lookup table may be stale or ETL mapped incorrectly'
        ELSE 'Present'
    END AS FreshnessFlag
FROM ExpectedStatuses e
LEFT JOIN ActualStatuses a ON e.Status = a.Status;

-- Step 2: Country reference freshness — are unexpected values appearing?
WITH KnownCountries AS (
    SELECT 'UK'       AS Country UNION ALL
    SELECT 'US'       UNION ALL
    SELECT 'Germany'  UNION ALL
    SELECT 'Internal'
),
ActualCountries AS (
    SELECT DISTINCT Country FROM Customers WHERE Country IS NOT NULL
)
SELECT
    COALESCE(k.Country, a.Country) AS Country,
    CASE WHEN k.Country IS NOT NULL THEN 'In reference list' ELSE 'NOT IN REFERENCE' END AS RefStatus,
    CASE WHEN a.Country IS NOT NULL THEN 'In data' ELSE 'NOT IN DATA' END AS DataStatus,
    CASE
        WHEN k.Country IS NULL
             THEN 'NEW VALUE: "' + a.Country + '" not in reference data — mapping rule missing'
        WHEN a.Country IS NULL
             THEN 'UNUSED REFERENCE: Country in reference but no data — reference table may be over-populated'
        ELSE 'Consistent'
    END AS ConsistencyFlag
FROM KnownCountries k
FULL OUTER JOIN ActualCountries a ON k.Country = a.Country;

-- Step 3: Product reference coverage — all Products used in Orders must be in Products table
SELECT
    'Products referenced in Orders' AS Check_,
    COUNT(DISTINCT o.ProductID) AS OrderProductCount,
    (SELECT COUNT(DISTINCT ProductID) FROM Products) AS ProductTableCount,
    SUM(CASE WHEN p.ProductID IS NULL THEN 1 ELSE 0 END) AS MissingFromProducts,
    CASE
        WHEN SUM(CASE WHEN p.ProductID IS NULL THEN 1 ELSE 0 END) > 0
             THEN 'STALE REFERENCE: Products table missing ProductIDs used in Orders'
        ELSE 'Complete'
    END AS CompletenessFlag
FROM Orders o
LEFT JOIN Products p ON o.ProductID = p.ProductID
WHERE o.ProductID IS NOT NULL;

-- Step 4: Reference data age check — when was the data last updated?
-- Using MAX(OrderDate) as proxy for "most recent record" in each table
SELECT
    TableName,
    MostRecentDate,
    DATEDIFF(DAY, MostRecentDate, GETDATE()) AS DaysSinceUpdate,
    ExpectedMaxAgeDays,
    CASE
        WHEN DATEDIFF(DAY, MostRecentDate, GETDATE()) > ExpectedMaxAgeDays
             THEN 'STALE: Last update was ' + CAST(DATEDIFF(DAY, MostRecentDate, GETDATE()) AS VARCHAR)
                  + ' days ago, expected max ' + CAST(ExpectedMaxAgeDays AS VARCHAR) + ' days'
        ELSE 'Fresh: Within expected refresh interval'
    END AS FreshnessFlag
FROM (
    SELECT 'Orders' AS TableName, MAX(CAST(OrderDate AS DATE)) AS MostRecentDate, 1 AS ExpectedMaxAgeDays
    FROM Orders WHERE OrderDate IS NOT NULL
    UNION ALL
    SELECT 'Transactions', MAX(CAST(TransactionDate AS DATE)), 1
    FROM Transactions WHERE TransactionDate IS NOT NULL
    UNION ALL
    SELECT 'Customers', MAX(CAST(ContractEnd AS DATE)), 365
    FROM Customers WHERE ContractEnd IS NOT NULL
) RefDates;

-- Step 5: Empty reference table guard
SELECT
    'Customers'    AS TableName, COUNT(*) AS RowCount,
    CASE WHEN COUNT(*) = 0 THEN 'EMPTY TABLE: Reference data not loaded' ELSE 'Populated' END AS LoadStatus
FROM Customers
UNION ALL
SELECT 'Products', COUNT(*),
    CASE WHEN COUNT(*) = 0 THEN 'EMPTY TABLE: Reference data not loaded' ELSE 'Populated' END
FROM Products
UNION ALL
SELECT 'Orders', COUNT(*),
    CASE WHEN COUNT(*) = 0 THEN 'EMPTY TABLE: No fact data loaded' ELSE 'Populated' END
FROM Orders;

-- Step 6: Currency reference in Transactions
SELECT
    Currency,
    COUNT(*) AS TxnCount,
    CASE
        WHEN Currency NOT IN ('GBP', 'USD', 'EUR')
             THEN 'UNKNOWN CURRENCY: "' + Currency + '" not in approved currency reference list'
        ELSE 'Known currency'
    END AS CurrencyRefFlag
FROM Transactions
WHERE Currency IS NOT NULL
GROUP BY Currency
ORDER BY TxnCount DESC;
```

## Explanation

**Expected value lists as a freshness check**
Defining an `ExpectedStatuses` CTE and LEFT JOINing it (Expected → Actual) against actual data tests one direction: missing expected values — a status the ETL should have loaded but did not, a reference data gap. Catching the other direction — unexpected values, a status present in the data but not in the reference list, signalling a new value from an upstream system change — needs the actual-vs-reference relationship checked both ways, which is exactly what Step 2 does for Country using a FULL OUTER JOIN. Use LEFT JOIN when you only need "what's missing"; use FULL OUTER JOIN, as Step 2 does, when new unexpected values matter too.

**MAX(date) as a freshness proxy**
When tables lack an explicit `UpdatedDate` column, `MAX(EventDate)` provides a proxy for "when was this last refreshed?" If `MAX(OrderDate)` is 3 days ago and the ETL runs daily, the table is stale. This proxy is imperfect — it cannot detect tables that were loaded but not refreshed — but it provides a lightweight freshness signal that catches the most common staleness scenarios.

**Empty table guard (Step 5)**
A completely empty reference table is the most catastrophic lookup failure: every ETL lookup returns NULL, every record fails validation, and all referential integrity checks fail simultaneously. Checking `COUNT(*) = 0` before running the ETL prevents the pipeline from running against a table that hasn't been loaded yet.

**Currency reference validation**
An unexpected currency code in the Transactions table (e.g., "MXN" from a new international territory) indicates the FX rate lookup table does not have a MXN rate. Without a rate, the ETL either errors, skips the record, or uses a NULL rate — all problematic outcomes. Validating currencies against the FX rate table before running conversion ensures every currency has a corresponding rate.

## Severity
**High** — Stale or incomplete reference data causes ETL lookups to fail silently: a stale exchange rate table produces incorrect GBP equivalents; a missing status mapping produces NULL statuses; a missing product reference produces orphaned fact rows. These failures cascade through every report that uses the affected reference data until the underlying reference table is corrected and the ETL is re-run.
