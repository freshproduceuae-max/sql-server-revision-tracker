# G15-T07 — ETL/Load Process | Incremental vs Full Load Verification

## ID
G15-T07

## Group
15 — ETL/Load Process

## Type
Incremental vs Full Load Verification — Confirming That the Correct Load Mode Was Used and That Records Match the Expected Delta

## Live Scenario
A retail analytics team runs weekly full loads on Sundays and daily incremental loads Monday–Saturday. After a system outage on Wednesday, the ETL team manually re-ran Monday's incremental job on Thursday morning — but they accidentally triggered the full load mode instead, overwriting all changes made Tuesday and Wednesday. The incremental vs full load verification check, comparing the record count of Thursday's load against the 3-week average for a Thursday incremental, immediately flagged that Thursday's load was 47× larger than expected, indicating a full load was mistakenly executed on an incremental day. The check also detected 1,840 records with `OrderDate` values from prior months that should only appear in full loads.

## The Question
> Incremental vs full load verification distinguishes whether a load contained only new/changed records (incremental) or a complete replacement of the target (full), and confirms that the actual load behaviour matches the expected mode for that scheduled run. SQL detects full-load-on-incremental-day errors by comparing actual load volume against a rolling historical baseline, and by checking whether loaded records include historical periods that should never appear in an incremental window.
> **"Verify the load mode used in the Orders ETL: compare the current period's record count against the rolling historical average to detect whether a full load occurred on an incremental day, identify any records outside the expected incremental window, and flag load volume anomalies that suggest the wrong load mode was executed."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Transactions** — `schemas/05_Transactions.csv`

## Solution Query

```sql
-- Step 1: Compute monthly record counts and rolling 3-month average
-- to detect load volume anomalies
WITH MonthlyVolume AS (
    SELECT
        YEAR(OrderDate)  AS LoadYear,
        MONTH(OrderDate) AS LoadMonth,
        COUNT(*)         AS RecordCount
    FROM Orders
    WHERE OrderDate IS NOT NULL
    GROUP BY YEAR(OrderDate), MONTH(OrderDate)
),
VolumeWithRolling AS (
    SELECT
        LoadYear,
        LoadMonth,
        RecordCount,
        AVG(RecordCount * 1.0) OVER (
            ORDER BY LoadYear, LoadMonth
            ROWS BETWEEN 3 PRECEDING AND 1 PRECEDING
        ) AS Rolling3MonthAvg,
        COUNT(*) OVER (
            ORDER BY LoadYear, LoadMonth
            ROWS BETWEEN 3 PRECEDING AND 1 PRECEDING
        ) AS WindowMonths
    FROM MonthlyVolume
)
SELECT
    LoadYear,
    LoadMonth,
    RecordCount,
    ROUND(Rolling3MonthAvg, 1)  AS Rolling3MonthAvg,
    WindowMonths,
    CASE
        WHEN Rolling3MonthAvg IS NULL
             THEN 'Insufficient history for comparison'
        WHEN RecordCount > Rolling3MonthAvg * 5
             THEN 'FULL LOAD SUSPECTED: Record count is '
                  + CAST(ROUND(RecordCount / NULLIF(Rolling3MonthAvg, 0), 1) AS VARCHAR)
                  + 'x the rolling average — possible full load on incremental day'
        WHEN RecordCount > Rolling3MonthAvg * 2
             THEN 'HIGH VOLUME: Record count is '
                  + CAST(ROUND(RecordCount / NULLIF(Rolling3MonthAvg, 0), 1) AS VARCHAR)
                  + 'x average — investigate for load mode error or genuine spike'
        WHEN RecordCount < Rolling3MonthAvg * 0.3
             THEN 'LOW VOLUME: Record count is only '
                  + CAST(ROUND(100.0 * RecordCount / NULLIF(Rolling3MonthAvg, 0), 0) AS VARCHAR)
                  + '% of average — possible incomplete incremental or failed extraction'
        ELSE 'Normal: Within expected incremental range'
    END AS LoadModeFlag
FROM VolumeWithRolling
ORDER BY LoadYear, LoadMonth;

-- Step 2: Detect records outside the expected incremental window
-- An incremental load should only contain records from the current period;
-- older records suggest a full load or a reprocessing of historical data
DECLARE @IncrementalWindowStart DATE = DATEADD(MONTH, -1, CAST(GETDATE() AS DATE));
DECLARE @IncrementalWindowEnd   DATE = CAST(GETDATE() AS DATE);

SELECT
    YEAR(OrderDate)  AS RecordYear,
    MONTH(OrderDate) AS RecordMonth,
    COUNT(*)         AS RecordCount,
    MIN(CAST(OrderDate AS DATE)) AS EarliestDate,
    MAX(CAST(OrderDate AS DATE)) AS LatestDate,
    CASE
        WHEN MAX(CAST(OrderDate AS DATE)) < @IncrementalWindowStart
             THEN 'HISTORICAL RECORDS: Records pre-date the incremental window — full load or reprocessing detected'
        WHEN MIN(CAST(OrderDate AS DATE)) > @IncrementalWindowEnd
             THEN 'FUTURE RECORDS: Records beyond current date — possible clock skew or test data'
        ELSE 'Within incremental window'
    END AS WindowFlag
FROM Orders
WHERE OrderDate IS NOT NULL
GROUP BY YEAR(OrderDate), MONTH(OrderDate)
ORDER BY RecordYear, RecordMonth;

-- Step 3: Load mode classification by period
-- New records only in the most recent period = incremental behaviour
-- Records spread across many historical periods = full load behaviour
SELECT
    'Total months with records'   AS Metric,
    COUNT(DISTINCT YEAR(OrderDate) * 100 + MONTH(OrderDate)) AS Value
FROM Orders WHERE OrderDate IS NOT NULL
UNION ALL
SELECT
    'Months before last 3 months (historical)',
    COUNT(DISTINCT YEAR(OrderDate) * 100 + MONTH(OrderDate))
FROM Orders
WHERE OrderDate IS NOT NULL
  AND OrderDate < DATEADD(MONTH, -3, GETDATE())
UNION ALL
SELECT
    'Records in last 30 days (incremental zone)',
    COUNT(*)
FROM Orders
WHERE OrderDate IS NOT NULL
  AND OrderDate >= DATEADD(DAY, -30, CAST(GETDATE() AS DATE))
UNION ALL
SELECT
    'Records older than 90 days',
    COUNT(*)
FROM Orders
WHERE OrderDate IS NOT NULL
  AND OrderDate < DATEADD(DAY, -90, CAST(GETDATE() AS DATE));

-- Step 4: Verify incremental uniqueness — new records should not already exist in prior periods
-- Simulated by checking for OrderIDs that appear in both the most recent month and earlier months
WITH RecentOrders AS (
    SELECT OrderID, CAST(OrderDate AS DATE) AS OrderDay
    FROM Orders
    WHERE OrderDate >= DATEADD(MONTH, -1, CAST(GETDATE() AS DATE))
      AND OrderDate IS NOT NULL
),
HistoricalOrders AS (
    SELECT OrderID, CAST(OrderDate AS DATE) AS OrderDay
    FROM Orders
    WHERE OrderDate < DATEADD(MONTH, -1, CAST(GETDATE() AS DATE))
      AND OrderDate IS NOT NULL
)
SELECT
    r.OrderID,
    r.OrderDay  AS RecentDate,
    h.OrderDay  AS HistoricalDate,
    'DUPLICATE ACROSS PERIODS: OrderID exists in both recent and historical windows — incremental loaded existing record' AS Flag
FROM RecentOrders r
JOIN HistoricalOrders h ON r.OrderID = h.OrderID;

-- Step 5: Transaction load mode check — corroborate Orders finding with Transactions
SELECT
    'Orders date span (months)'       AS Metric,
    DATEDIFF(MONTH,
             MIN(CAST(OrderDate AS DATE)),
             MAX(CAST(OrderDate AS DATE))) AS Value
FROM Orders WHERE OrderDate IS NOT NULL
UNION ALL
SELECT
    'Transactions date span (months)',
    DATEDIFF(MONTH,
             MIN(CAST(TransactionDate AS DATE)),
             MAX(CAST(TransactionDate AS DATE)))
FROM Transactions WHERE TransactionDate IS NOT NULL
UNION ALL
SELECT
    'Orders total records',
    COUNT(*)
FROM Orders
UNION ALL
SELECT
    'Transactions total records',
    COUNT(*)
FROM Transactions;
```

## Explanation

**Rolling average as load mode baseline**
The rolling 3-month average provides a data-driven threshold for what a "normal" incremental load looks like for a given period. A ratio of 5× or more against this baseline strongly suggests a full load was executed — not because a specific count is inherently wrong, but because it deviates dramatically from the established pattern. The multiplier threshold (5× for full load suspected, 2× for high volume warning) can be tuned to the specific ETL's volatility.

**Historical records as full-load fingerprint**
An incremental load for "this month" should contain only records dated within the incremental window. If the load also contains records from 6 months ago, the ETL clearly loaded more than the incremental delta. Step 2 groups records by year-month and flags any month that falls before the expected incremental window start — a reliable signal that a wider extraction was performed.

**Cross-period duplicate detection (Step 4)**
If an incremental load correctly de-duplicates against the existing target, an OrderID that already exists in a historical month should not re-appear in the new load. The self-join between recent and historical orders detects this — if results appear here, either the incremental filter is missing or the deduplication check before insert is not functioning.

**Corroborating with Transactions (Step 5)**
Comparing the date span and record count of Orders against Transactions provides a second opinion. If Orders shows a 3-month span but Transactions shows a 4-month span for the same load batch, one table received a different extraction scope — indicating the ETL logic for the two tables diverged.

## Severity
**High** — Running a full load on an incremental day causes cascading failures: change history is overwritten (SCD Type 2 records lose intermediate states), aggregates are recalculated using a complete dataset instead of a delta, and any downstream systems that consume the incremental feed receive 10–50× more records than expected, potentially overloading queues and causing processing failures.
