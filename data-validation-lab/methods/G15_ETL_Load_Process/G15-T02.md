# G15-T02 — ETL/Load Process | Transformation Rule Validation

## ID
G15-T02

## Group
15 — ETL/Load Process

## Type
Transformation Rule Validation — Verifying That ETL Business Rules Have Been Applied Correctly

## Live Scenario
An ETL pipeline loads customer data from a legacy CRM into a modern data warehouse. Transformation rules include: phone numbers must be normalised to E.164 format (+447XXXXXXXXX), country codes must be mapped from 2-letter to 3-letter ISO codes, and dates must be converted from DD/MM/YYYY to ISO 8601 (YYYY-MM-DD). Six weeks after go-live, the marketing team reports that SMS campaigns are failing for 23% of customers — the phone numbers are invalid. Investigation reveals three broken rules: (1) phone numbers with international dialling codes other than +44 were passed through without normalisation, (2) the ISO country code mapping table did not include "GB" (only "UK") causing 340 customers to receive NULL country codes, and (3) dates after the 12th of the month were being treated as DD/MM/YYYY by one system and MM/DD/YYYY by another — December 1st was loaded as January 12th. Transformation rule validation would have caught all three failures on the first load.

## The Question
> Transformation rule validation verifies that ETL business rules have been correctly applied to every record: values have been normalised to the expected format, lookups have resolved to valid codes, derived columns contain expected values, and no records were silently dropped when a rule failed. SQL validates by checking post-transformation values against the rule's expected output pattern.
> **"Validate the transformation rules applied to Customers data: verify phone numbers conform to a UK E.164 format, country values are from the expected set, email addresses have been normalised to lowercase, and flag any record where a transformation rule appears to have not been applied."**

## Table Reference
**Customers** — `schemas/01_Customers.csv`
**Products** — `schemas/03_Products.csv`

## Solution Query

```sql
-- Step 1: Phone number transformation validation
SELECT
    CustomerID,
    Phone,
    -- Check E.164 UK format: +447XXXXXXXXX (12 digits with +44 prefix)
    CASE
        WHEN Phone IS NULL
             THEN 'NULL: Phone not present'
        WHEN Phone LIKE '+44[0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9]'
             THEN 'VALID E.164: Correctly normalised'
        WHEN Phone LIKE '07[0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9]'
             THEN 'NOT NORMALISED: UK local format — E.164 transformation not applied'
        WHEN Phone LIKE '+1%'
             THEN 'NOT NORMALISED: US format — transformation rule missing for US numbers'
        WHEN Phone LIKE '00[0-9]%'
             THEN 'NOT NORMALISED: IDD format (00 prefix) — should be + prefix'
        ELSE 'NON-STANDARD: ' + LEFT(Phone, 10)
    END AS PhoneTransformStatus,
    -- Expected normalised value
    CASE
        WHEN Phone LIKE '07[0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9]'
             THEN '+44' + SUBSTRING(Phone, 2, 10)
        ELSE Phone
    END AS ExpectedNormalisedPhone
FROM Customers;

-- Step 2: Country code transformation validation
-- Verify countries are from the expected post-transformation set
WITH ExpectedCountryCodes AS (
    SELECT 'UK'       AS Code UNION ALL
    SELECT 'US'       UNION ALL
    SELECT 'Germany'  UNION ALL
    SELECT 'Internal'
)
SELECT
    c.CustomerID,
    c.Country AS TransformedCountry,
    CASE
        WHEN c.Country IS NULL
             THEN 'NULL: Country not set — lookup failed?'
        WHEN NOT EXISTS (SELECT 1 FROM ExpectedCountryCodes e WHERE e.Code = c.Country)
             THEN 'INVALID CODE: "' + c.Country + '" not in expected country set — mapping failed'
        ELSE 'Valid'
    END AS CountryTransformStatus
FROM Customers c;

-- Step 3: Email normalisation validation — emails should be lowercase
SELECT
    CustomerID,
    Email,
    LOWER(Email) AS ExpectedLowercaseEmail,
    CASE
        WHEN Email IS NULL
             THEN 'NULL'
        WHEN Email <> LOWER(Email)
             THEN 'NOT NORMALISED: Email contains uppercase — lowercase transformation not applied'
        WHEN CHARINDEX(' ', Email) > 0
             THEN 'WHITESPACE: Email contains spaces — trim not applied'
        WHEN Email NOT LIKE '%@%.%'
             THEN 'INVALID FORMAT: Email does not match basic format — validation not applied'
        ELSE 'Valid lowercase'
    END AS EmailTransformStatus
FROM Customers;

-- Step 4: Derived column validation — IsActive should be a BIT (0 or 1 only)
SELECT
    CustomerID,
    IsActive,
    CASE
        WHEN IsActive NOT IN (0, 1)
             THEN 'INVALID VALUE: IsActive must be 0 or 1, got: ' + CAST(IsActive AS VARCHAR)
        WHEN IsActive IS NULL
             THEN 'NULL: IsActive not set — default transformation not applied'
        ELSE 'Valid'
    END AS IsActiveTransformStatus
FROM Customers;

-- Step 5: Product transformation — Price and DiscountPercent rules
SELECT
    ProductID,
    ProductName,
    Price,
    DiscountPercent,
    VATRate,
    -- Business rule: discounted price should be positive
    ROUND(Price * (1 - ISNULL(DiscountPercent, 0) / 100.0), 2) AS DiscountedPrice,
    CASE
        WHEN Price <= 0
             THEN 'INVALID PRICE: Price must be positive after transformation'
        WHEN DiscountPercent < 0 OR DiscountPercent > 100
             THEN 'INVALID DISCOUNT: DiscountPercent must be 0-100, got: '
                  + CAST(DiscountPercent AS VARCHAR)
        WHEN VATRate NOT IN (0, 5, 20) AND VATRate IS NOT NULL
             THEN 'INVALID VAT RATE: Expected 0, 5, or 20, got: ' + CAST(VATRate AS VARCHAR)
        WHEN ROUND(Price * (1 - ISNULL(DiscountPercent, 0) / 100.0), 2) <= 0
             THEN 'INVALID NET PRICE: Discount results in zero or negative price'
        ELSE 'Valid'
    END AS TransformFlag
FROM Products;

-- Step 6: Transformation summary — how many records passed/failed each rule?
SELECT
    'Phone E.164' AS Rule,
    SUM(CASE WHEN Phone LIKE '+44[0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9]' THEN 1 ELSE 0 END) AS Passed,
    SUM(CASE WHEN Phone IS NOT NULL AND Phone NOT LIKE '+44[0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9]' THEN 1 ELSE 0 END) AS Failed,
    SUM(CASE WHEN Phone IS NULL THEN 1 ELSE 0 END) AS Nulls,
    COUNT(*) AS Total
FROM Customers
UNION ALL
SELECT
    'Email Lowercase',
    SUM(CASE WHEN Email = LOWER(Email) AND Email IS NOT NULL THEN 1 ELSE 0 END),
    SUM(CASE WHEN Email <> LOWER(Email) THEN 1 ELSE 0 END),
    SUM(CASE WHEN Email IS NULL THEN 1 ELSE 0 END),
    COUNT(*)
FROM Customers;
```

## Explanation

**Pattern-based validation for format rules**
`LIKE '+44[0-9][0-9]...'` validates that the phone number conforms to the expected post-transformation format. If the ETL applied E.164 normalisation correctly, 100% of non-NULL UK phones should match this pattern. Any that do not reveals a gap in the transformation rule — either a format variant not covered by the normalisation logic or a record that bypassed the transformation step entirely.

**ExpectedNormalisedPhone as a correction preview**
Computing `'+44' + SUBSTRING(Phone, 2, 10)` shows what the correctly transformed value should look like. This serves two purposes: (1) it confirms the transformation logic is correct before applying it at scale, and (2) it produces a correction script — the `UPDATE` statement that would apply the missing transformation to already-loaded records.

**Transformation rule summary (Step 6)**
The summary row per rule — Passed, Failed, Nulls, Total — gives a pass/fail scorecard for each transformation. A 100% pass rate confirms the rule is working; a 58% pass rate (as in the example) flags that 42% of records need the rule applied or the rule logic needs to be extended to cover more format variants.

**VAT rate domain check**
`VATRate NOT IN (0, 5, 20)` validates that the ETL correctly mapped source VAT codes to UK standard rates. A rate of 17.5% (the old UK standard rate before 2011) or 25% (a non-UK rate) indicates a mapping table that was not updated or a record from an overseas source that passed through without country-specific rate conversion.

## Severity
**High** — Transformation rule failures are silent: the ETL completes without error, the records load, and the values appear in reports — but they are wrong. Incorrect phone normalisation causes SMS campaign failures; incorrect country mapping causes wrong geography analysis; incorrect date parsing causes orders to appear in the wrong month. Transformation validation is the quality gate that confirms each business rule was actually applied, not just executed without error.
