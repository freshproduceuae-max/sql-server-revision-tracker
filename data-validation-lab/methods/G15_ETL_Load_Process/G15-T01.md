# G15-T01 — ETL/Load Process | Staging Table Row Count Reconciliation

## ID
G15-T01

## Group
15 — ETL/Load Process

## Type
Staging Table Row Count Reconciliation — Verifying Record Count Through Each ETL Stage

## Live Scenario
A data engineer sets up a new ETL pipeline that extracts from a CRM, transforms in a staging layer, and loads into a data warehouse. On the fourth day of production, the BI team reports that customer counts dropped from 14,200 to 13,850 overnight. The engineer investigates: the extract stage pulled 14,200 rows (matching the source), but the staging transformation step only output 13,850 — 350 rows silently failed during a data type conversion and were dropped by the `TRY_CAST` silently. There is no error logged because `TRY_CAST` returns NULL (not an error) for failed conversions, and the ETL had a `WHERE converted_value IS NOT NULL` filter that removed these rows. The row count reconciliation query, had it been in place, would have flagged the 350 missing rows on the morning of day 1.

## The Question
> Staging table row count reconciliation compares record counts at each stage of the ETL pipeline: extract count → staging count → transform count → load count. A difference at any stage identifies where records are being lost, duplicated, or filtered unexpectedly. SQL implements this by querying row counts from each stage and computing the differential.
> **"Reconcile record counts between the source representation (Transactions), the transformation layer (Orders joined to Transactions), and the final destination layer — identify at which stage any record loss or gain occurs and quantify the discrepancy."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Transactions** — `schemas/05_Transactions.csv`
**Customers** — `schemas/01_Customers.csv`

## Solution Query

```sql
-- Step 1: Count at each ETL stage
SELECT
    'Stage 1: Source (Transactions)' AS Stage,
    COUNT(*) AS RecordCount,
    MIN(CAST(TransactionDate AS DATE)) AS EarliestDate,
    MAX(CAST(TransactionDate AS DATE)) AS LatestDate,
    ROUND(SUM(Amount), 2) AS TotalAmount
FROM Transactions
WHERE Amount IS NOT NULL
UNION ALL
SELECT
    'Stage 2: Source with OrderID (joinable)',
    COUNT(*),
    MIN(CAST(TransactionDate AS DATE)),
    MAX(CAST(TransactionDate AS DATE)),
    ROUND(SUM(Amount), 2)
FROM Transactions
WHERE Amount IS NOT NULL AND OrderID IS NOT NULL
UNION ALL
SELECT
    'Stage 3: After JOIN to Orders',
    COUNT(*),
    MIN(CAST(o.OrderDate AS DATE)),
    MAX(CAST(o.OrderDate AS DATE)),
    ROUND(SUM(t.Amount), 2)
FROM Transactions t
INNER JOIN Orders o ON t.OrderID = o.OrderID
WHERE t.Amount IS NOT NULL
UNION ALL
SELECT
    'Stage 4: After filter (Delivered only)',
    COUNT(*),
    MIN(CAST(o.OrderDate AS DATE)),
    MAX(CAST(o.OrderDate AS DATE)),
    ROUND(SUM(t.Amount), 2)
FROM Transactions t
INNER JOIN Orders o ON t.OrderID = o.OrderID
WHERE t.Amount IS NOT NULL
  AND o.Status = 'Delivered';

-- Step 2: Stage-by-stage differential
WITH StageCounts AS (
    SELECT 1 AS StageNum, 'Source Transactions'    AS Stage, COUNT(*) AS Cnt FROM Transactions WHERE Amount IS NOT NULL
    UNION ALL
    SELECT 2, 'Has OrderID', COUNT(*) FROM Transactions WHERE Amount IS NOT NULL AND OrderID IS NOT NULL
    UNION ALL
    SELECT 3, 'Joined to Orders', COUNT(*)
    FROM Transactions t INNER JOIN Orders o ON t.OrderID = o.OrderID WHERE t.Amount IS NOT NULL
    UNION ALL
    SELECT 4, 'Delivered Only', COUNT(*)
    FROM Transactions t INNER JOIN Orders o ON t.OrderID = o.OrderID
    WHERE t.Amount IS NOT NULL AND o.Status = 'Delivered'
)
SELECT
    s.StageNum,
    s.Stage,
    s.Cnt,
    s.Cnt - LAG(s.Cnt) OVER (ORDER BY s.StageNum) AS RecordDelta,
    ROUND(100.0 * (s.Cnt - LAG(s.Cnt) OVER (ORDER BY s.StageNum))
          / NULLIF(LAG(s.Cnt) OVER (ORDER BY s.StageNum), 0), 1) AS DeltaPct,
    CASE
        WHEN LAG(s.Cnt) OVER (ORDER BY s.StageNum) IS NULL
             THEN 'Baseline stage'
        WHEN s.Cnt < LAG(s.Cnt) OVER (ORDER BY s.StageNum)
             THEN 'RECORD LOSS: '
                  + CAST(ABS(s.Cnt - LAG(s.Cnt) OVER (ORDER BY s.StageNum)) AS VARCHAR)
                  + ' records dropped at this stage'
        WHEN s.Cnt > LAG(s.Cnt) OVER (ORDER BY s.StageNum)
             THEN 'RECORD GAIN: '
                  + CAST(s.Cnt - LAG(s.Cnt) OVER (ORDER BY s.StageNum) AS VARCHAR)
                  + ' records added — possible fan-out from JOIN'
        ELSE 'No change'
    END AS StageFlag
FROM StageCounts s
ORDER BY s.StageNum;

-- Step 3: Identify records lost at the JOIN stage
-- Records in Transactions that do not join to Orders
SELECT
    t.TransactionID,
    t.OrderID,
    t.Amount,
    t.TransactionDate,
    'UNJOINED: Transaction has no matching Order' AS DropReason
FROM Transactions t
WHERE t.OrderID IS NOT NULL
  AND NOT EXISTS (SELECT 1 FROM Orders o WHERE o.OrderID = t.OrderID)
UNION ALL
SELECT
    t.TransactionID,
    t.OrderID,
    t.Amount,
    t.TransactionDate,
    'NULL ORDER ID: Transaction cannot be joined — no OrderID'
FROM Transactions t
WHERE t.OrderID IS NULL;

-- Step 4: Count reconciliation summary
DECLARE @SourceCount INT = (SELECT COUNT(*) FROM Transactions WHERE Amount IS NOT NULL);
DECLARE @DestCount   INT = (SELECT COUNT(*) FROM Orders);
DECLARE @Variance    INT = @SourceCount - @DestCount;

SELECT
    @SourceCount AS SourceRecords,
    @DestCount   AS DestinationRecords,
    @Variance    AS Variance,
    CASE
        WHEN @Variance = 0 THEN 'BALANCED: Source and destination counts match'
        WHEN @Variance > 0 THEN 'SOURCE EXCESS: ' + CAST(@Variance AS VARCHAR) + ' records not loaded'
        ELSE 'DEST EXCESS: ' + CAST(ABS(@Variance) AS VARCHAR) + ' extra records in destination — duplicates?'
    END AS ReconciliationStatus;
```

## Expected Output

**Step 1 — Stage counts:**
| Stage | RecordCount | TotalAmount |
|---|---|---|
| Stage 1: Source (Transactions) | 25 | 26800.00 |
| Stage 2: Source with OrderID (joinable) | 22 | 24500.00 |
| Stage 3: After JOIN to Orders | 22 | 24500.00 |
| Stage 4: After filter (Delivered only) | 14 | 17200.00 |

**Step 2 — Stage differentials:**
| Stage | Cnt | RecordDelta | DeltaPct | StageFlag |
|---|---|---|---|---|
| Source Transactions | 25 | NULL | NULL | Baseline stage |
| Has OrderID | 22 | -3 | -12.0 | RECORD LOSS: 3 records dropped at this stage |
| Joined to Orders | 22 | 0 | 0.0 | No change |
| Delivered Only | 14 | -8 | -36.4 | RECORD LOSS: 8 records dropped at this stage |

## Explanation

**Stage count waterfall**
The waterfall pattern — counting records at each ETL stage and computing the delta — immediately identifies where records are lost. Each stage's delta tells you what happened there: -3 at the "Has OrderID" stage means 3 transactions have NULL OrderID; -8 at the "Delivered Only" filter means 8 transactions belong to non-Delivered orders. Both are expected drops — the validation confirms the drop magnitude matches the known filter criteria.

**Expected vs unexpected record loss**
Record loss at a filter stage is expected (the filter is the business rule). Record loss at a JOIN stage is unexpected (the JOIN should find a match for every record, unless referential integrity is broken). The validation query distinguishes between these cases: if the JOIN-stage delta matches the count of NULL OrderIDs, the loss is explained; if there is additional unexplained loss, there are records that have valid OrderIDs but no matching Order — an orphan condition.

**Record gain as a fan-out warning**
If a stage shows MORE records than the prior stage, a fan-out has occurred — one record joined to multiple rows in another table, replicating the original record. This is the signal to investigate the JOIN cardinality and add a GROUP BY or deduplication step.

**DECLARE and compare for final reconciliation**
Step 4's DECLARE pattern stores the source and destination counts in variables for direct arithmetic comparison. This is the simplest form of control total verification: if `@Variance <> 0`, the ETL has not transferred the expected number of records and the reason must be identified before the load is accepted as complete.

## Severity
**High** — Undetected record loss in ETL pipelines accumulates silently. A 3-record loss per day becomes 90 records per month. For financial data, this means understated revenue, missing customer records, and incorrect audit trails. Row count reconciliation at every ETL stage converts silent loss into a visible, quantified alert that triggers investigation before the missing data becomes a reporting problem.
