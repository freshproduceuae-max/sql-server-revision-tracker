# G15-T09 — ETL/Load Process | Reject and Exception Record Audit

## ID
G15-T09

## Group
15 — ETL/Load Process

## Type
Reject and Exception Record Audit — Validating That Rejected Records Are Captured, Quantified, and Resolved

## Live Scenario
An e-commerce company's nightly ETL loads orders from three regional systems into a central warehouse. The ETL has a reject table that captures records failing validation. For six months, the ETL team watches the nightly success email ("Loaded: 450 orders, Rejected: 12") without investigating the rejects — assuming they are benign test records. A quarterly audit reveals that 2,160 rejected records accumulated in the reject table, including 340 orders from the UK system with a currency field of "GBP " (trailing space) that the ETL's exact-match currency lookup rejected. These 340 orders, totalling £187,000 of revenue, were never loaded into the warehouse and never appeared in any sales report. The reject audit, examining reject volume, reject reasons, and age of oldest unresolved reject, would have flagged the growing reject backlog after the first week.

## The Question
> Reject and exception record audits quantify the volume, age, and financial impact of records that failed ETL validation and were routed to a reject or error table rather than the target. SQL analyses the reject pattern by failure reason, identifies whether rejects are accumulating (growing backlog) or being resolved, and measures the financial materiality of unloaded data. Where no dedicated reject table exists, proxy measures — NULL rate spikes, count mismatches between source and target, and orphan transaction counts — serve as reject indicators.
> **"Audit ETL reject patterns using the available data: identify records that may have been rejected based on data quality failures (NULL required fields, invalid values, FK violations), estimate the volume and financial impact of potential rejects, and flag whether the reject rate is within acceptable limits or indicates a systemic extraction failure."**

## Solution Query

```sql
-- Step 1: Identify records that would have been rejected under common ETL rules
-- (simulating a reject table using quality failure detection)
WITH OrderRejectReasons AS (
    SELECT
        OrderID,
        CustomerID,
        ProductID,
        OrderDate,
        TotalAmount,
        Status,
        CASE WHEN CustomerID IS NULL   THEN 1 ELSE 0 END AS RejectNullCustomer,
        CASE WHEN ProductID IS NULL    THEN 1 ELSE 0 END AS RejectNullProduct,
        CASE WHEN TotalAmount IS NULL  THEN 1 ELSE 0 END AS RejectNullAmount,
        CASE WHEN TotalAmount <= 0     THEN 1 ELSE 0 END AS RejectInvalidAmount,
        CASE WHEN OrderDate IS NULL    THEN 1 ELSE 0 END AS RejectNullDate,
        CASE WHEN Status IS NULL OR Status NOT IN
             ('Pending','Processing','Delivered','Cancelled','Returned')
             THEN 1 ELSE 0 END AS RejectInvalidStatus
    FROM Orders
)
SELECT
    OrderID,
    CustomerID,
    TotalAmount,
    CAST(OrderDate AS DATE) AS OrderDate,
    Status,
    RejectNullCustomer + RejectNullProduct + RejectNullAmount
        + RejectInvalidAmount + RejectNullDate + RejectInvalidStatus AS RuleFailureCount,
    CASE WHEN RejectNullCustomer  = 1 THEN 'NULL_CUSTOMER; '  ELSE '' END +
    CASE WHEN RejectNullProduct   = 1 THEN 'NULL_PRODUCT; '   ELSE '' END +
    CASE WHEN RejectNullAmount    = 1 THEN 'NULL_AMOUNT; '    ELSE '' END +
    CASE WHEN RejectInvalidAmount = 1 THEN 'INVALID_AMOUNT; ' ELSE '' END +
    CASE WHEN RejectNullDate      = 1 THEN 'NULL_DATE; '      ELSE '' END +
    CASE WHEN RejectInvalidStatus = 1 THEN 'INVALID_STATUS; ' ELSE '' END
        AS RejectReasonList
FROM OrderRejectReasons
WHERE RejectNullCustomer + RejectNullProduct + RejectNullAmount
      + RejectInvalidAmount + RejectNullDate + RejectInvalidStatus > 0
ORDER BY RuleFailureCount DESC;

-- Step 2: Reject rate by reason — volume and financial impact
SELECT
    RejectReason,
    RecordCount,
    ROUND(100.0 * RecordCount / NULLIF(TotalOrders, 0), 2) AS RejectRatePct,
    ROUND(FinancialImpact, 2) AS FinancialImpact,
    CASE
        WHEN 100.0 * RecordCount / NULLIF(TotalOrders, 0) > 5
             THEN 'CRITICAL: >5% reject rate — systemic extraction failure'
        WHEN 100.0 * RecordCount / NULLIF(TotalOrders, 0) > 1
             THEN 'HIGH: >1% reject rate — investigate reject pattern'
        WHEN RecordCount > 0
             THEN 'MONITOR: Rejects present but below 1% threshold'
        ELSE 'OK: No rejects for this rule'
    END AS SeverityFlag
FROM (
    SELECT
        'NULL CustomerID'     AS RejectReason,
        SUM(CASE WHEN CustomerID IS NULL THEN 1 ELSE 0 END) AS RecordCount,
        SUM(CASE WHEN CustomerID IS NULL THEN ISNULL(TotalAmount, 0) ELSE 0 END) AS FinancialImpact,
        COUNT(*) AS TotalOrders
    FROM Orders
    UNION ALL
    SELECT
        'NULL/Invalid Amount',
        SUM(CASE WHEN TotalAmount IS NULL OR TotalAmount <= 0 THEN 1 ELSE 0 END),
        SUM(CASE WHEN TotalAmount IS NULL OR TotalAmount <= 0 THEN ISNULL(TotalAmount, 0) ELSE 0 END),
        COUNT(*)
    FROM Orders
    UNION ALL
    SELECT
        'Invalid Status',
        SUM(CASE WHEN Status IS NULL OR Status NOT IN
            ('Pending','Processing','Delivered','Cancelled','Returned') THEN 1 ELSE 0 END),
        SUM(CASE WHEN Status IS NULL OR Status NOT IN
            ('Pending','Processing','Delivered','Cancelled','Returned')
            THEN ISNULL(TotalAmount, 0) ELSE 0 END),
        COUNT(*)
    FROM Orders
    UNION ALL
    SELECT
        'Orphan ProductID',
        SUM(CASE WHEN p.ProductID IS NULL AND o.ProductID IS NOT NULL THEN 1 ELSE 0 END),
        SUM(CASE WHEN p.ProductID IS NULL AND o.ProductID IS NOT NULL
            THEN ISNULL(o.TotalAmount, 0) ELSE 0 END),
        COUNT(*)
    FROM Orders o LEFT JOIN Products p ON o.ProductID = p.ProductID
) RejectSummary;

-- Step 3: Monthly reject trend — is the reject rate stable or growing?
SELECT
    YEAR(OrderDate)  AS Yr,
    MONTH(OrderDate) AS Mo,
    COUNT(*) AS TotalRecords,
    SUM(CASE WHEN CustomerID IS NULL OR TotalAmount IS NULL OR TotalAmount <= 0
             OR Status NOT IN ('Pending','Processing','Delivered','Cancelled','Returned')
             THEN 1 ELSE 0 END) AS PotentialRejects,
    ROUND(100.0 *
        SUM(CASE WHEN CustomerID IS NULL OR TotalAmount IS NULL OR TotalAmount <= 0
                 OR Status NOT IN ('Pending','Processing','Delivered','Cancelled','Returned')
                 THEN 1 ELSE 0 END)
        / NULLIF(COUNT(*), 0), 2) AS RejectRatePct
FROM Orders
WHERE OrderDate IS NOT NULL
GROUP BY YEAR(OrderDate), MONTH(OrderDate)
ORDER BY Yr, Mo;

-- Step 4: Transaction reject proxy — transactions with no valid Order reference
-- These represent records that either were rejected or were never linked
SELECT
    t.TransactionID,
    t.OrderID,
    t.Amount,
    t.Currency,
    CAST(t.TransactionDate AS DATE) AS TransactionDate,
    CASE
        WHEN t.OrderID IS NULL
             THEN 'NULL_FK: Transaction has no OrderID — likely a reject that loaded without reference'
        WHEN o.OrderID IS NULL
             THEN 'ORPHAN_FK: OrderID ' + CAST(t.OrderID AS VARCHAR)
                  + ' not found — referenced order may have been rejected'
        ELSE 'Valid'
    END AS RejectProxyFlag
FROM Transactions t
LEFT JOIN Orders o ON t.OrderID = o.OrderID
WHERE t.OrderID IS NULL OR o.OrderID IS NULL;

-- Step 5: Overall ETL health scorecard
SELECT
    'Total Orders loaded'               AS Metric,
    CAST(COUNT(*) AS VARCHAR)           AS Value
FROM Orders
UNION ALL
SELECT
    'Orders with any quality failure',
    CAST(SUM(CASE
        WHEN CustomerID IS NULL OR ProductID IS NULL OR TotalAmount IS NULL
          OR TotalAmount <= 0 OR OrderDate IS NULL
          OR Status NOT IN ('Pending','Processing','Delivered','Cancelled','Returned')
        THEN 1 ELSE 0 END) AS VARCHAR)
FROM Orders
UNION ALL
SELECT
    'Overall reject-eligible rate',
    CAST(ROUND(100.0 *
        SUM(CASE
            WHEN CustomerID IS NULL OR ProductID IS NULL OR TotalAmount IS NULL
              OR TotalAmount <= 0 OR OrderDate IS NULL
              OR Status NOT IN ('Pending','Processing','Delivered','Cancelled','Returned')
            THEN 1 ELSE 0 END)
        / NULLIF(COUNT(*), 0), 2) AS VARCHAR) + '%'
FROM Orders
UNION ALL
SELECT
    'Total Transactions loaded',
    CAST(COUNT(*) AS VARCHAR)
FROM Transactions
UNION ALL
SELECT
    'Transactions with no Order match',
    CAST(SUM(CASE WHEN o.OrderID IS NULL AND t.OrderID IS NOT NULL THEN 1 ELSE 0 END) AS VARCHAR)
FROM Transactions t LEFT JOIN Orders o ON t.OrderID = o.OrderID;
```

## Explanation

**Simulating a reject table without one**
Production ETL systems should write rejected records to a dedicated reject or quarantine table with the failure reason. When that infrastructure doesn't exist, SQL can simulate it by applying the same validation rules to the loaded data and counting records that would have failed. This is a compensating check, not a replacement — it only catches quality failures in records that made it to the target, not records that were dropped before load.

**Reject rate thresholds**
Industry practice typically treats 0% rejects as the target, with alert thresholds of 0.1% (monitor), 1% (investigate), and 5% (halt load). These thresholds must be calibrated per pipeline — a feed with known source quality issues may have a baseline reject rate of 0.5% that is normal, while any reject above zero is a defect for a tightly controlled financial feed.

**Growing vs stable reject rate (Step 3)**
A stable 0.5% monthly reject rate is manageable; a rate growing from 0.5% to 1.2% to 2.8% over three months indicates a deteriorating source system or a mapping rule that is no longer covering all input variants. Step 3's monthly trend detects this trajectory before the reject backlog becomes material.

**Transaction orphans as reject proxy**
Transactions referencing OrderIDs that don't exist in the Orders table are a proxy signal for rejected orders — if an order was rejected before load, its associated transaction arrives in the Transactions load without a matching parent, becoming an orphan. The orphan count in Transactions therefore provides an indirect measure of the Orders reject volume even when no reject table exists.

## Severity
**High** — Unmonitored reject tables are a silent revenue black hole: every rejected record represents real business activity (an order placed, a payment made) that disappears from all reporting without any visible error. Reject records are often valid business transactions that encountered fixable validation failures — trailing spaces, mismatched codes, format variants — that could be corrected and reloaded. Without a reject audit, these records remain invisible indefinitely.
