# G15-T08 — ETL/Load Process | Orphan Record and Broken FK Detection Post-Load

## ID
G15-T08

## Group
15 — ETL/Load Process

## Type
Orphan Record and Broken FK Detection Post-Load — Identifying Foreign Key Violations Introduced by Partial or Out-of-Order Loads

## Live Scenario
A multi-source ETL pipeline loads Customers, Products, and Orders from three separate source systems on a nightly schedule. On a Tuesday night, the Customers extract fails at 02:14 but the Orders extract completes successfully at 02:47. Wednesday morning, 318 Orders have been loaded referencing CustomerIDs that do not exist in the Customers table — because the new customers placed their first orders during the same day the customer extract failed. The orphan record check, comparing Orders.CustomerID against Customers.CustomerID, immediately identifies all 318 orphaned orders before any analyst queries the data, enabling the ETL team to re-run the Customers extract and complete the load before business hours.

## The Question
> Post-load FK validation verifies that all foreign key references introduced by an ETL run resolve to valid parent records in the target schema. SQL detects orphans using LEFT JOIN + IS NULL, quantifies the financial exposure of orphaned records, and identifies whether the breakage is concentrated in newly-loaded records (partial load failure) or spread across the full dataset (historic integrity drift).
> **"Detect orphan records introduced by the ETL load: identify Orders with no matching CustomerID in Customers, Orders with no matching ProductID in Products, and Transactions with no matching OrderID in Orders. Quantify the financial impact of each orphan type and flag whether the breakage is recent (likely the current load) or historic."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Customers** — `schemas/01_Customers.csv`
**Products** — `schemas/03_Products.csv`
**Transactions** — `schemas/05_Transactions.csv`

## Solution Query

```sql
-- Step 1: Orders with no matching CustomerID (orphaned orders)
SELECT
    o.OrderID,
    o.CustomerID,
    CAST(o.OrderDate AS DATE) AS OrderDate,
    o.TotalAmount,
    o.Status,
    'ORPHAN: CustomerID ' + CAST(o.CustomerID AS VARCHAR) + ' not found in Customers table'
        AS OrphanFlag,
    CASE
        WHEN o.OrderDate >= DATEADD(DAY, -1, CAST(GETDATE() AS DATE))
             THEN 'RECENT: Likely from current load — parent record may be missing'
        ELSE 'HISTORIC: Pre-existing FK violation — may indicate historic load error'
    END AS RecencyFlag
FROM Orders o
LEFT JOIN Customers c ON o.CustomerID = c.CustomerID
WHERE c.CustomerID IS NULL
  AND o.CustomerID IS NOT NULL
ORDER BY o.OrderDate DESC;

-- Step 2: Orders with no matching ProductID (orphaned product references)
SELECT
    o.OrderID,
    o.ProductID,
    CAST(o.OrderDate AS DATE) AS OrderDate,
    o.TotalAmount,
    'ORPHAN: ProductID ' + CAST(o.ProductID AS VARCHAR) + ' not found in Products table'
        AS OrphanFlag
FROM Orders o
LEFT JOIN Products p ON o.ProductID = p.ProductID
WHERE p.ProductID IS NULL
  AND o.ProductID IS NOT NULL
ORDER BY o.OrderDate DESC;

-- Step 3: Transactions with no matching OrderID (orphaned transactions)
SELECT
    t.TransactionID,
    t.OrderID,
    CAST(t.TransactionDate AS DATE) AS TransactionDate,
    t.Amount,
    t.Currency,
    'ORPHAN: OrderID ' + CAST(t.OrderID AS VARCHAR) + ' not found in Orders table'
        AS OrphanFlag
FROM Transactions t
LEFT JOIN Orders o ON t.OrderID = o.OrderID
WHERE o.OrderID IS NULL
  AND t.OrderID IS NOT NULL
ORDER BY t.TransactionDate DESC;

-- Step 4: Orphan financial impact summary
SELECT
    'Orders: orphaned CustomerID'   AS OrphanType,
    COUNT(*)                         AS OrphanCount,
    ROUND(SUM(o.TotalAmount), 2)     AS OrphanRevenue,
    ROUND(100.0 * COUNT(*) / NULLIF((SELECT COUNT(*) FROM Orders), 0), 1) AS OrphanPct
FROM Orders o
LEFT JOIN Customers c ON o.CustomerID = c.CustomerID
WHERE c.CustomerID IS NULL AND o.CustomerID IS NOT NULL
UNION ALL
SELECT
    'Orders: orphaned ProductID',
    COUNT(*),
    ROUND(SUM(o.TotalAmount), 2),
    ROUND(100.0 * COUNT(*) / NULLIF((SELECT COUNT(*) FROM Orders), 0), 1)
FROM Orders o
LEFT JOIN Products p ON o.ProductID = p.ProductID
WHERE p.ProductID IS NULL AND o.ProductID IS NOT NULL
UNION ALL
SELECT
    'Transactions: orphaned OrderID',
    COUNT(*),
    ROUND(SUM(t.Amount), 2),
    ROUND(100.0 * COUNT(*) / NULLIF((SELECT COUNT(*) FROM Transactions), 0), 1)
FROM Transactions t
LEFT JOIN Orders o ON t.OrderID = o.OrderID
WHERE o.OrderID IS NULL AND t.OrderID IS NOT NULL;

-- Step 5: NULL FK vs orphan FK distinction
-- NULL FK = record was loaded without a parent reference (source data issue)
-- Orphan FK = record was loaded with a reference that doesn't resolve (partial load issue)
SELECT
    'Orders: NULL CustomerID (source data)'   AS IssueType,
    COUNT(*) AS RecordCount
FROM Orders WHERE CustomerID IS NULL
UNION ALL
SELECT
    'Orders: Orphan CustomerID (broken FK)',
    COUNT(*)
FROM Orders o
LEFT JOIN Customers c ON o.CustomerID = c.CustomerID
WHERE c.CustomerID IS NULL AND o.CustomerID IS NOT NULL
UNION ALL
SELECT
    'Orders: NULL ProductID (source data)',
    COUNT(*)
FROM Orders WHERE ProductID IS NULL
UNION ALL
SELECT
    'Orders: Orphan ProductID (broken FK)',
    COUNT(*)
FROM Orders o
LEFT JOIN Products p ON o.ProductID = p.ProductID
WHERE p.ProductID IS NULL AND o.ProductID IS NOT NULL
UNION ALL
SELECT
    'Transactions: NULL OrderID (source data)',
    COUNT(*)
FROM Transactions WHERE OrderID IS NULL
UNION ALL
SELECT
    'Transactions: Orphan OrderID (broken FK)',
    COUNT(*)
FROM Transactions t
LEFT JOIN Orders o ON t.OrderID = o.OrderID
WHERE o.OrderID IS NULL AND t.OrderID IS NOT NULL;
```

## Explanation

**LEFT JOIN + IS NULL as the orphan detection pattern**
`LEFT JOIN parent ON child.FK = parent.PK WHERE parent.PK IS NULL` is the canonical SQL orphan detection pattern. It selects all child rows and then filters to those where the LEFT JOIN found no match — i.e., the FK value exists in the child but not in the parent. This is equivalent to `NOT EXISTS (SELECT 1 FROM parent WHERE parent.PK = child.FK)` but often performs better on large tables with appropriate indexing.

**NULL FK vs orphan FK**
A NULL foreign key and an orphan foreign key are different failure modes requiring different remediation. A NULL FK means the source record never had a parent reference — this is a source data quality issue (the order was placed without a customer, or the customer association was lost upstream). An orphan FK means the reference exists but the parent row is absent — this is an ETL sequencing issue (the child was loaded before or without the parent). Step 5 counts both types separately so the ETL team knows whether to fix the source or re-run a failed parent load.

**Recency flag for load triage**
Step 1's recency flag distinguishes whether orphans are from the current load (yesterday's records) or are historic. Recent orphans indicate the parent table extract failed during last night's run; historic orphans suggest a pre-existing integrity problem that was never caught. The remediation differs: recent orphans require re-running the parent extract; historic orphans require a data audit and possible correction script.

**Financial exposure quantification**
Step 4 computes the total `TotalAmount` of orphaned orders and the total `Amount` of orphaned transactions. This converts the technical defect into a business metric — "£8,400 of transaction revenue is unmatched to orders" is actionable for finance teams in a way that "8 orphan rows" is not. The orphan percentage contextualises severity: 32% of transactions being orphaned is critical; 0.1% may be acceptable background noise.

## Severity
**High** — Orphan records are invisible in normal reporting: an ORDER BY or GROUP BY on CustomerID will include the orphaned orders, but any join to Customers to add customer attributes will silently drop them. Revenue reports will appear complete but customer-level analysis will undercount, creating inconsistent totals between summary and detail levels that are very difficult to diagnose without a dedicated FK integrity check.
