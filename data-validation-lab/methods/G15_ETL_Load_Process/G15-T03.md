# G15-T03 — ETL/Load Process | Duplicate Detection During Load

## ID
G15-T03

## Group
15 — ETL/Load Process

## Type
Duplicate Detection During Load — Identifying and Preventing Duplicate Records from Entering the Target Table

## Live Scenario
A payment processing company receives a nightly file of transaction records from three payment gateways. On a Friday, Gateway B's file is delayed and sent Saturday with Friday's transactions — but Gateway B also sends a corrected version on Monday that includes both the original Friday records and Saturday's records. The ETL processes Monday's file without deduplication, loading 4,200 duplicate Friday transaction records alongside the legitimate Saturday records. By Tuesday, the finance team notices total transaction volume for the week is £2.1M higher than the payment gateway reconciliation shows. The duplicate detection query, run before every load, would have identified the 4,200 duplicates before they entered the target table and routed them to a quarantine table for review.

## The Question
> Duplicate detection during load identifies records in the incoming data that already exist in the target table, or that appear multiple times within the incoming batch itself. SQL detects both types using NOT EXISTS (for cross-table duplicates) and GROUP BY/HAVING (for within-batch duplicates), enabling selective loading of only new, unique records.
> **"Identify duplicate Orders in the dataset: detect orders where the same OrderID appears more than once, find orders that appear to be business-key duplicates (same CustomerID, ProductID, and date within a tolerance), and quantify the financial impact of loading duplicates without deduplication."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Transactions** — `schemas/05_Transactions.csv`

## Solution Query

```sql
-- Step 1: Exact key duplicates — same OrderID more than once
WITH OrderIDDupes AS (
    SELECT
        OrderID,
        COUNT(*) AS OccurrenceCount,
        MIN(CAST(OrderDate AS DATE)) AS FirstDate,
        MAX(CAST(OrderDate AS DATE)) AS LastDate,
        SUM(TotalAmount) AS TotalIfDuplicated
    FROM Orders
    GROUP BY OrderID
    HAVING COUNT(*) > 1
)
SELECT
    o.OrderID,
    o.CustomerID,
    o.ProductID,
    o.TotalAmount,
    o.OrderDate,
    o.Status,
    d.OccurrenceCount,
    d.TotalIfDuplicated,
    'EXACT DUPLICATE: OrderID appears ' + CAST(d.OccurrenceCount AS VARCHAR) + ' times' AS DuplicateType
FROM Orders o
JOIN OrderIDDupes d ON o.OrderID = d.OrderID
ORDER BY o.OrderID;

-- Step 2: Business-key duplicates — same customer + product + date (different OrderID)
WITH BusinessKeyGroups AS (
    SELECT
        CustomerID,
        ProductID,
        CAST(OrderDate AS DATE) AS OrderDay,
        COUNT(*) AS OrderCount,
        SUM(TotalAmount) AS TotalAmount,
        STRING_AGG(CAST(OrderID AS VARCHAR), ', ') AS OrderIDs,
        MIN(TotalAmount) AS MinAmount,
        MAX(TotalAmount) AS MaxAmount
    FROM Orders
    WHERE CustomerID IS NOT NULL
      AND ProductID IS NOT NULL
      AND OrderDate IS NOT NULL
    GROUP BY CustomerID, ProductID, CAST(OrderDate AS DATE)
    HAVING COUNT(*) > 1
)
SELECT
    CustomerID,
    ProductID,
    OrderDay,
    OrderCount,
    ROUND(TotalAmount, 2) AS TotalAmount,
    ROUND(MinAmount, 2) AS MinAmount,
    ROUND(MaxAmount, 2) AS MaxAmount,
    OrderIDs,
    CASE
        WHEN ABS(MaxAmount - MinAmount) < 0.01
             THEN 'LIKELY DUPLICATE: Same amount — possible double load'
        ELSE 'POSSIBLE DUPLICATE: Same customer+product+date but different amounts — review'
    END AS DuplicateType
FROM BusinessKeyGroups
ORDER BY OrderCount DESC;

-- Step 3: Near-duplicate detection — same amount, same customer, within 3 days
SELECT
    a.OrderID AS OrderID_A,
    b.OrderID AS OrderID_B,
    a.CustomerID,
    a.TotalAmount,
    CAST(a.OrderDate AS DATE) AS Date_A,
    CAST(b.OrderDate AS DATE) AS Date_B,
    DATEDIFF(DAY, a.OrderDate, b.OrderDate) AS DaysBetween,
    'NEAR-DUPLICATE: Same customer + amount within 3 days — possible retry or resubmission' AS Flag
FROM Orders a
JOIN Orders b
    ON a.CustomerID = b.CustomerID
    AND a.OrderID < b.OrderID   -- avoid self-join and symmetric pairs
    AND ABS(a.TotalAmount - b.TotalAmount) < 0.01
    AND ABS(DATEDIFF(DAY, a.OrderDate, b.OrderDate)) <= 3
ORDER BY a.CustomerID, a.TotalAmount;

-- Step 4: Within-batch duplicate summary
SELECT
    'Total Transactions in batch' AS Metric, COUNT(*) AS Value
FROM Transactions
UNION ALL
SELECT 'Unique OrderIDs in Transactions', COUNT(DISTINCT OrderID)
FROM Transactions WHERE OrderID IS NOT NULL
UNION ALL
SELECT 'Duplicate Transactions (same OrderID + Amount)',
    COUNT(*) - COUNT(DISTINCT CAST(OrderID AS VARCHAR) + '|' + CAST(Amount AS VARCHAR))
FROM Transactions WHERE OrderID IS NOT NULL AND Amount IS NOT NULL
UNION ALL
SELECT 'Revenue if loaded without dedup', ROUND(SUM(Amount), 0)
FROM Transactions WHERE Amount IS NOT NULL
UNION ALL
SELECT 'Revenue of unique transactions', ROUND(SUM(Amount), 0)
FROM (
    SELECT DISTINCT OrderID, Amount FROM Transactions
    WHERE OrderID IS NOT NULL AND Amount IS NOT NULL
) Unique_;

-- Step 5: Deduplication preview — show which record to keep
WITH Ranked AS (
    SELECT
        *,
        ROW_NUMBER() OVER (
            PARTITION BY CustomerID, ProductID, CAST(OrderDate AS DATE)
            ORDER BY OrderID  -- keep the first OrderID
        ) AS Rn
    FROM Orders
    WHERE CustomerID IS NOT NULL AND ProductID IS NOT NULL AND OrderDate IS NOT NULL
)
SELECT
    OrderID,
    CustomerID,
    ProductID,
    CAST(OrderDate AS DATE) AS OrderDay,
    TotalAmount,
    Rn,
    CASE WHEN Rn = 1 THEN 'KEEP' ELSE 'DISCARD (duplicate)' END AS LoadDecision
FROM Ranked
ORDER BY CustomerID, ProductID, OrderDay, Rn;
```

## Explanation

**Exact key vs business key vs near-duplicate**
Three different duplicate types require different detection strategies: (1) exact key duplicates (same OrderID) are definitively wrong — the primary key constraint should prevent them; (2) business key duplicates (same CustomerID+ProductID+date) may be legitimate (two genuine same-day orders) or erroneous (retry loads) — amounts help distinguish; (3) near-duplicates (same customer+amount within N days) are probabilistic — they require business context to confirm.

**ROW_NUMBER for deduplication**
Step 5's `ROW_NUMBER() OVER (PARTITION BY business_key ORDER BY OrderID)` assigns rank 1 to the record to keep (the first by OrderID) and higher ranks to duplicates. `WHERE Rn = 1` in an INSERT statement loads only the deduplicated set. The `ORDER BY OrderID` keeps the earliest-assigned ID — often the correct choice when the first occurrence is the canonical record.

**The financial impact of skipping deduplication**
Step 4 computes what would happen if the batch is loaded without deduplication: £26,800 loaded vs £21,400 for unique records — a £5,400 overstatement (25%). For a payment processing company, this means reporting 25% more revenue than was actually received, a material misstatement in any financial report.

**Preventing vs detecting duplicates**
SQL deduplication is a compensating control — it detects duplicates that already exist. The primary control should be upstream: unique constraints on the target table, idempotent ETL design (re-running the same load produces the same result), and source-system deduplication before extraction. The SQL detection provides a safety net when upstream controls fail.

## Severity
**High** — Duplicate records in financial transaction tables cause overstated revenue, double-counted inventory movements, and incorrect account balances. Unlike some data quality failures that are visible in individual records, duplicates can be indistinguishable from legitimate repeat transactions — they look like real data and pass all field-level validation checks. Count and amount reconciliation is the primary detection mechanism.
