# G09-T01 — Timeliness | Stale Data Detection

## ID
G09-T01

## Group
9 — Timeliness

## Type
Stale Data Detection — Records Not Updated Within the Expected Refresh Window

## Live Scenario
A logistics dashboard displays real-time delivery status for 4,200 active shipments. The dashboard pulls from a status table that is refreshed every 15 minutes by an API call to the courier's tracking system. An API rate limit change by the courier reduces the allowed call frequency from 4 per minute to 1 per minute. The refresh job does not detect the throttling — it receives HTTP 429 responses but continues silently. After 2 hours, 847 shipments show status data from 2 hours ago. A customer service agent marks a delivery "completed" based on the stale status; the customer is told their parcel has arrived when it is still in a depot 40 miles away.

## The Question
> Stale data occurs when records have not been updated within the expected refresh window. SQL detects staleness by comparing the last update timestamp to GETDATE() and flagging records whose age exceeds the defined threshold.
> **"Identify Orders whose status has not progressed and whose OrderDate is significantly older than the DeliveryDate expectation, treating any order in a non-terminal state for more than 30 days as potentially stale."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Customers** — `schemas/01_Customers.csv`

## Solution Query

```sql
-- Step 1: Stale non-terminal orders — open orders older than expected processing time
DECLARE @StalenessThresholdDays INT = 30;

SELECT
    o.OrderID,
    o.CustomerID,
    c.FirstName + ' ' + c.LastName AS CustomerName,
    o.OrderDate,
    o.Status,
    o.DeliveryDate,
    DATEDIFF(DAY, o.OrderDate, GETDATE()) AS AgeDays,
    DATEDIFF(DAY, o.OrderDate, GETDATE()) - @StalenessThresholdDays AS DaysOverThreshold,
    CASE
        WHEN o.Status IN ('Delivered', 'Cancelled', 'Refunded')
             THEN 'Terminal — no action needed'
        WHEN DATEDIFF(DAY, o.OrderDate, GETDATE()) > @StalenessThresholdDays * 3
             THEN 'CRITICAL STALE: Order over 90 days old in non-terminal state'
        WHEN DATEDIFF(DAY, o.OrderDate, GETDATE()) > @StalenessThresholdDays
             THEN 'STALE: Order older than ' + CAST(@StalenessThresholdDays AS VARCHAR)
                  + ' days without terminal status'
        ELSE 'Within expected processing window'
    END AS StalenessFlag
FROM Orders o
JOIN Customers c ON o.CustomerID = c.CustomerID
WHERE o.Status NOT IN ('Delivered', 'Cancelled', 'Refunded')
  AND DATEDIFF(DAY, o.OrderDate, GETDATE()) > @StalenessThresholdDays
ORDER BY AgeDays DESC;

-- Step 2: Status distribution by age — identify where orders are getting stuck
SELECT
    o.Status,
    COUNT(*) AS OrderCount,
    AVG(DATEDIFF(DAY, o.OrderDate, GETDATE())) AS AvgAgeDays,
    MIN(DATEDIFF(DAY, o.OrderDate, GETDATE())) AS MinAgeDays,
    MAX(DATEDIFF(DAY, o.OrderDate, GETDATE())) AS MaxAgeDays,
    SUM(o.TotalAmount) AS TotalValueAtRisk
FROM Orders o
WHERE o.Status NOT IN ('Delivered', 'Cancelled')
GROUP BY o.Status
ORDER BY AvgAgeDays DESC;

-- Step 3: Orders where delivery date has passed but status is not Delivered
SELECT
    o.OrderID,
    o.CustomerID,
    o.OrderDate,
    o.DeliveryDate,
    o.Status,
    o.TotalAmount,
    DATEDIFF(DAY, o.DeliveryDate, GETDATE()) AS DaysOverdue,
    CASE
        WHEN DATEDIFF(DAY, o.DeliveryDate, GETDATE()) > 14
             THEN 'SIGNIFICANTLY OVERDUE: ' + CAST(DATEDIFF(DAY, o.DeliveryDate, GETDATE()) AS VARCHAR) + ' days past delivery date'
        ELSE 'OVERDUE: ' + CAST(DATEDIFF(DAY, o.DeliveryDate, GETDATE()) AS VARCHAR) + ' days past delivery date'
    END AS OverdueFlag
FROM Orders o
WHERE o.DeliveryDate IS NOT NULL
  AND o.DeliveryDate < CAST(GETDATE() AS DATE)
  AND o.Status NOT IN ('Delivered', 'Cancelled', 'Refunded')
ORDER BY DaysOverdue DESC;

-- Step 4: Summary — freshness scorecard
SELECT
    COUNT(*) AS TotalOrders,
    SUM(CASE WHEN Status IN ('Delivered','Cancelled','Refunded') THEN 1 ELSE 0 END) AS TerminalOrders,
    SUM(CASE WHEN Status NOT IN ('Delivered','Cancelled','Refunded')
              AND DATEDIFF(DAY, OrderDate, GETDATE()) <= 30 THEN 1 ELSE 0 END) AS FreshOpenOrders,
    SUM(CASE WHEN Status NOT IN ('Delivered','Cancelled','Refunded')
              AND DATEDIFF(DAY, OrderDate, GETDATE()) > 30 THEN 1 ELSE 0 END) AS StaleOpenOrders,
    ROUND(100.0 * SUM(CASE WHEN Status NOT IN ('Delivered','Cancelled','Refunded')
              AND DATEDIFF(DAY, OrderDate, GETDATE()) > 30 THEN 1 ELSE 0 END)
          / NULLIF(COUNT(*),0), 1) AS StalePct
FROM Orders;
```

## Expected Output

**Step 1 — Stale orders:**
| OrderID | CustomerName | OrderDate | Status | AgeDays | StalenessFlag |
|---|---|---|---|---|---|
| 1003 | Bob Smith | 2024-01-10 | Processing | 172 | CRITICAL STALE: Order over 90 days old in non-terminal state |

**Step 3 — Overdue deliveries:**
| OrderID | OrderDate | DeliveryDate | Status | DaysOverdue | OverdueFlag |
|---|---|---|---|---|---|
| 1009 | 2024-02-14 | 2024-02-21 | Shipped | 130 | SIGNIFICANTLY OVERDUE: 130 days past delivery date |

## Explanation

**GETDATE() as the freshness reference**
`DATEDIFF(DAY, OrderDate, GETDATE())` computes age relative to today. In production, replace `GETDATE()` with a parameter if the check needs to be run against a specific reference date (e.g., the close date for a period review). Using `GETDATE()` means the query returns different results each day — appropriate for operational monitoring.

**Terminal vs non-terminal states**
The staleness check only applies to non-terminal records. Records in terminal states (Delivered, Cancelled, Refunded) are definitionally complete — they should not be updated. Filtering `WHERE Status NOT IN ('Delivered','Cancelled','Refunded')` limits the check to orders where further processing is expected.

**Delivery date overdue check**
Step 3 catches a specific staleness pattern: the promised delivery date has passed but the status hasn't been updated to Delivered. This is the most customer-visible form of stale data — the system shows the order is "on its way" when it should have arrived days ago.

**Staleness thresholds by workflow**
The 30-day threshold is appropriate for order processing. Different domains require different thresholds: a patient record not updated in 24 hours (clinical), a price feed not updated in 1 minute (financial trading), a fraud score not updated in 6 hours (payments). Always parameterise the threshold.

## Severity
**Medium** — Stale operational data causes wrong decisions (customer service, inventory, logistics). The severity escalates to High when stale data drives automated actions (automated order cancellation, credit decisions) or when it affects regulated disclosures (clinical records, financial positions).
