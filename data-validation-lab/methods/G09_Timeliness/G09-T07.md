# G09-T07 — Timeliness | Event Sequence Out of Order

## ID
G09-T07

## Group
9 — Timeliness

## Type
Event Sequence Out of Order — Records Arrive or Are Processed in the Wrong Chronological Order

## Live Scenario
A streaming platform processes user events in real time. Events are emitted from mobile devices and may arrive at the server out of order due to network delays or device clock drift. A "video started" event arrives 3 seconds after a "video completed" event for the same session. The recommendation engine that triggers "watch next" suggestions uses the latest-received event to determine state, so it sees "completed" and suggests the next video — then receives "started" and incorrectly marks the session as active again. A second scenario: a database replication process applies update logs out of sequence, causing a customer record to revert to an older state after a newer update was already applied.

## The Question
> Out-of-order events create impossible sequences: a payment before an order, a delivery confirmation before dispatch, or a cancel after a completion. SQL detects these using LAG/LEAD to compare consecutive events in a sequence and flagging pairs where the timestamp ordering contradicts the logical ordering.
> **"For each Order, validate that the OrderDate precedes the DeliveryDate, and identify Transactions where the TransactionDate sequence is inconsistent with the expected order of events."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Transactions** — `schemas/05_Transactions.csv`

## Solution Query

```sql
-- Step 1: Orders where logical sequence is violated (delivery before order)
SELECT
    o.OrderID,
    o.CustomerID,
    o.OrderDate,
    o.DeliveryDate,
    o.Status,
    DATEDIFF(DAY, o.DeliveryDate, o.OrderDate) AS DaysDeliveredBeforeOrdered,
    CASE
        WHEN o.DeliveryDate IS NULL
             THEN 'No delivery date — cannot check sequence'
        WHEN o.DeliveryDate < o.OrderDate
             THEN 'SEQUENCE ERROR: Delivered (' + CAST(o.DeliveryDate AS VARCHAR)
                  + ') before ordered (' + CAST(o.OrderDate AS VARCHAR) + ')'
        WHEN o.DeliveryDate = o.OrderDate AND o.Status = 'Delivered'
             THEN 'SAME-DAY DELIVERY: Valid but unusual — verify'
        ELSE 'Sequence OK: ordered before delivered'
    END AS SequenceFlag
FROM Orders o
WHERE o.DeliveryDate IS NOT NULL
  AND o.DeliveryDate < o.OrderDate
ORDER BY DaysDeliveredBeforeOrdered DESC;

-- Step 2: For each order, check that transactions are in chronological order and payments follow orders
WITH OrderTransactionSeq AS (
    SELECT
        o.OrderID,
        o.OrderDate,
        t.TransactionID,
        t.TransactionDate,
        t.Amount,
        ROW_NUMBER() OVER (PARTITION BY o.OrderID ORDER BY t.TransactionDate, t.TransactionID) AS SeqNum,
        LAG(t.TransactionDate) OVER (PARTITION BY o.OrderID ORDER BY t.TransactionDate, t.TransactionID) AS PrevTxDate,
        LAG(t.Amount)          OVER (PARTITION BY o.OrderID ORDER BY t.TransactionDate, t.TransactionID) AS PrevAmount
    FROM Orders o
    JOIN Transactions t ON o.OrderID = t.OrderID
)
SELECT
    OrderID,
    OrderDate,
    TransactionID,
    TransactionDate,
    Amount,
    SeqNum,
    PrevTxDate,
    DATEDIFF(DAY, PrevTxDate, TransactionDate) AS DaysBetweenTx,
    CASE
        WHEN PrevTxDate IS NULL
             THEN 'First transaction for this order'
        WHEN TransactionDate < PrevTxDate
             THEN 'OUT OF ORDER: Transaction at ' + CAST(TransactionDate AS VARCHAR)
                  + ' is before previous at ' + CAST(PrevTxDate AS VARCHAR)
        WHEN PrevAmount < 0 AND Amount > 0 AND TransactionDate <= PrevTxDate
             THEN 'REFUND BEFORE PAYMENT: Credit recorded before original charge'
        ELSE 'Sequence OK'
    END AS SequenceCheck
FROM OrderTransactionSeq
WHERE PrevTxDate IS NOT NULL
  AND TransactionDate < PrevTxDate
ORDER BY OrderID, SeqNum;

-- Step 3: Customer-level event sequence — first order after a transaction (no order exists yet)
SELECT
    t.TransactionID,
    t.OrderID,
    t.TransactionDate,
    o.OrderDate,
    t.Amount,
    'PAYMENT BEFORE ORDER: Transaction recorded before parent order date' AS SequenceViolation
FROM Transactions t
JOIN Orders o ON t.OrderID = o.OrderID
WHERE t.TransactionDate < o.OrderDate
ORDER BY DATEDIFF(DAY, t.TransactionDate, o.OrderDate) DESC;

-- Step 4: Detect same-second duplicate events (event storm / replay attack)
SELECT
    OrderID,
    CAST(TransactionDate AS DATE)        AS TxDate,
    DATEPART(HOUR, TransactionDate)      AS TxHour,
    DATEPART(MINUTE, TransactionDate)    AS TxMinute,
    COUNT(*)                             AS TxInSameMinute,
    SUM(Amount)                          AS TotalAmount,
    CASE
        WHEN COUNT(*) > 1
             THEN 'DUPLICATE EVENTS: ' + CAST(COUNT(*) AS VARCHAR)
                  + ' transactions in same minute for OrderID ' + CAST(OrderID AS VARCHAR)
        ELSE 'Normal'
    END AS EventStormFlag
FROM Transactions
GROUP BY OrderID,
         CAST(TransactionDate AS DATE),
         DATEPART(HOUR, TransactionDate),
         DATEPART(MINUTE, TransactionDate)
HAVING COUNT(*) > 1
ORDER BY TxInSameMinute DESC;
```

## Explanation

**LAG for within-order sequence checking**
`LAG(TransactionDate) OVER (PARTITION BY OrderID ORDER BY TransactionDate, TransactionID)` returns the previous transaction date within the same order. If `TransactionDate < LAG(TransactionDate)`, the current record is out of chronological order — an impossibility in a correctly functioning system.

**ROW_NUMBER for event ordering**
`ROW_NUMBER() OVER (PARTITION BY OrderID ORDER BY TransactionDate, TransactionID)` assigns a sequence number to each event within an order. This makes it easy to reference "the first event" (SeqNum = 1), "the second event" (SeqNum = 2), and to check specific sequence requirements like "payment must precede refund."

**Same-minute clustering as event storm**
Step 4 detects multiple transactions for the same order within the same minute. This can indicate a retry storm (the same API call was retried multiple times due to a timeout), a replay attack (re-sending captured transactions), or a race condition in the payment processing system.

**Delivery before order as the canonical impossibility**
Step 1's `DeliveryDate < OrderDate` is the clearest form of sequence violation: something was delivered before it was ordered. This only happens due to date entry errors, timezone handling bugs, or deliberate backdating.

## Severity
**High** — Out-of-order events corrupt event-driven systems, state machines, and time-series analytics. In financial systems, incorrect event ordering can cause double payments, missed settlements, or incorrect balance calculations. In clinical systems, a medication administered event before a prescription event violates clinical workflow requirements.
