# G09-T11 — Timeliness | Temporal Completeness Check

## ID
G09-T11

## Group
9 — Timeliness

## Type
Temporal Completeness Check — Verifying Data Exists for All Expected Time Periods

## Live Scenario
A financial regulator requires a bank to submit daily transaction data for all business days. The submission covers 252 business days per year. An automated submission system has a public holiday calendar that is out of date — it marks Good Friday as a working day and submits an empty file (0 records) rather than omitting the day entirely. The regulator's system expects no submission on bank holidays; receiving an empty submission triggers a "zero-transaction anomaly" investigation. Separately, the bank misses the submission for August 14 (a Tuesday) because the automated job failed and no retry was configured. This missing day is not detected for 3 weeks because monitoring only checked for job completion, not for data coverage.

## The Question
> Temporal completeness verifies that data exists for every period in the expected range — no days, months, or hours are missing. SQL checks this by generating the expected set of periods and left-joining to the actual data, flagging any expected period with no records.
> **"Verify that the Transactions table has data for every month in the range covered by the Orders table, identify any months with unexpectedly low transaction counts, and flag gaps in the daily transaction sequence."**

## Table Reference
**Transactions** — `schemas/05_Transactions.csv`
**Orders** — `schemas/02_Orders.csv`

## Solution Query

```sql
-- Step 1: Generate expected months and check transaction presence
WITH OrderDateRange AS (
    SELECT
        MIN(CAST(YEAR(OrderDate) AS VARCHAR(4)) + '-'
            + RIGHT('0' + CAST(MONTH(OrderDate) AS VARCHAR(2)), 2)) AS MinPeriod,
        MAX(CAST(YEAR(OrderDate) AS VARCHAR(4)) + '-'
            + RIGHT('0' + CAST(MONTH(OrderDate) AS VARCHAR(2)), 2)) AS MaxPeriod,
        MIN(DATEFROMPARTS(YEAR(OrderDate), MONTH(OrderDate), 1)) AS MinDate,
        MAX(DATEFROMPARTS(YEAR(OrderDate), MONTH(OrderDate), 1)) AS MaxDate,
        DATEDIFF(MONTH,
                 MIN(DATEFROMPARTS(YEAR(OrderDate), MONTH(OrderDate), 1)),
                 MAX(DATEFROMPARTS(YEAR(OrderDate), MONTH(OrderDate), 1))) + 1 AS ExpectedMonths
    FROM Orders
),
-- Generate sequence of months using a numbers trick
MonthSequence AS (
    SELECT TOP 120  -- Max 10 years of months
        ROW_NUMBER() OVER (ORDER BY (SELECT NULL)) - 1 AS MonthOffset
    FROM Transactions t1
    CROSS JOIN Transactions t2
),
ExpectedMonths AS (
    SELECT
        DATEADD(MONTH, ms.MonthOffset, odr.MinDate) AS PeriodStart,
        YEAR(DATEADD(MONTH, ms.MonthOffset, odr.MinDate)) AS ExpYr,
        MONTH(DATEADD(MONTH, ms.MonthOffset, odr.MinDate)) AS ExpMo
    FROM OrderDateRange odr
    CROSS JOIN MonthSequence ms
    WHERE DATEADD(MONTH, ms.MonthOffset, odr.MinDate) <= odr.MaxDate
),
ActualMonths AS (
    SELECT
        YEAR(TransactionDate)  AS ActYr,
        MONTH(TransactionDate) AS ActMo,
        COUNT(*) AS TxCount
    FROM Transactions
    GROUP BY YEAR(TransactionDate), MONTH(TransactionDate)
)
SELECT
    em.ExpYr AS Year,
    em.ExpMo AS Month,
    ISNULL(am.TxCount, 0) AS TransactionCount,
    CASE
        WHEN am.ActYr IS NULL
             THEN 'MISSING PERIOD: No transactions for ' + CAST(em.ExpMo AS VARCHAR)
                  + '/' + CAST(em.ExpYr AS VARCHAR)
        WHEN am.TxCount < 2
             THEN 'LOW VOLUME: Only ' + CAST(am.TxCount AS VARCHAR)
                  + ' transaction(s) — verify completeness'
        ELSE 'Present: ' + CAST(am.TxCount AS VARCHAR) + ' transactions'
    END AS TemporalStatus
FROM ExpectedMonths em
LEFT JOIN ActualMonths am ON em.ExpYr = am.ActYr AND em.ExpMo = am.ActMo
ORDER BY em.ExpYr, em.ExpMo;

-- Step 2: Day-level gap detection within the transaction sequence
WITH TxDays AS (
    SELECT DISTINCT CAST(TransactionDate AS DATE) AS TxDay
    FROM Transactions
    WHERE TransactionDate IS NOT NULL
),
TxDaysWithLag AS (
    SELECT
        TxDay,
        LAG(TxDay) OVER (ORDER BY TxDay) AS PrevDay,
        DATEDIFF(DAY, LAG(TxDay) OVER (ORDER BY TxDay), TxDay) AS DayGap
    FROM TxDays
)
SELECT
    PrevDay AS LastDayWithData,
    TxDay AS NextDayWithData,
    DayGap - 1 AS MissingDays,
    DATEADD(DAY, 1, PrevDay) AS GapStart,
    DATEADD(DAY, -1, TxDay)  AS GapEnd,
    CASE
        WHEN DayGap = 2 THEN 'One day gap — weekend or holiday?'
        WHEN DayGap = 3 THEN 'Two day gap — weekend?'
        WHEN DayGap > 3 THEN 'SIGNIFICANT GAP: '
             + CAST(DayGap - 1 AS VARCHAR) + ' days without data from '
             + CAST(DATEADD(DAY, 1, PrevDay) AS VARCHAR)
             + ' to ' + CAST(DATEADD(DAY, -1, TxDay) AS VARCHAR)
        ELSE NULL
    END AS GapAssessment
FROM TxDaysWithLag
WHERE DayGap > 1 AND PrevDay IS NOT NULL
ORDER BY MissingDays DESC;

-- Step 3: Expected transaction volume per day — flag low-volume days
WITH DailyStats AS (
    SELECT
        CAST(TransactionDate AS DATE) AS TxDay,
        COUNT(*) AS DailyCount,
        SUM(Amount) AS DailyTotal
    FROM Transactions
    GROUP BY CAST(TransactionDate AS DATE)
)
SELECT
    TxDay,
    DailyCount,
    DailyTotal,
    AVG(DailyCount) OVER () AS OverallAvgCount,
    CASE
        WHEN DailyCount < AVG(DailyCount) OVER () * 0.3
             THEN 'VERY LOW: Less than 30% of average — partial load?'
        WHEN DailyCount < AVG(DailyCount) OVER () * 0.7
             THEN 'LOW: Less than 70% of average — investigate'
        ELSE 'Normal volume'
    END AS VolumeFlag
FROM DailyStats
ORDER BY DailyCount;

-- Step 4: Summary completeness scorecard
SELECT
    DATEDIFF(MONTH,
             MIN(DATEFROMPARTS(YEAR(TransactionDate), MONTH(TransactionDate), 1)),
             MAX(DATEFROMPARTS(YEAR(TransactionDate), MONTH(TransactionDate), 1))) + 1
        AS MonthsInRange,
    COUNT(DISTINCT YEAR(TransactionDate) * 100 + MONTH(TransactionDate))
        AS MonthsWithData,
    COUNT(DISTINCT CAST(TransactionDate AS DATE)) AS DaysWithData,
    DATEDIFF(DAY, MIN(TransactionDate), MAX(TransactionDate)) + 1 AS TotalDaysInRange,
    ROUND(100.0 * COUNT(DISTINCT CAST(TransactionDate AS DATE))
          / NULLIF(DATEDIFF(DAY, MIN(TransactionDate), MAX(TransactionDate)) + 1, 0), 1)
        AS DayCoveragePct
FROM Transactions
WHERE TransactionDate IS NOT NULL;
```

|---|---|---|---|
| 2024 | 1 | 8 | Present: 8 transactions |
| 2024 | 2 | 11 | Present: 11 transactions |
| 2024 | 3 | 5 | Present: 5 transactions |

**Step 2 — Day gaps:**
| LastDayWithData | NextDayWithData | MissingDays | GapAssessment |
|---|---|---|---|
| 2024-01-15 | 2024-01-19 | 3 | SIGNIFICANT GAP: 3 days without data from 2024-01-16 to 2024-01-18 |

**Step 4 — Coverage scorecard:**
| MonthsInRange | MonthsWithData | DaysWithData | TotalDaysInRange | DayCoveragePct |
|---|---|---|---|---|
| 3 | 3 | 19 | 79 | 24.1 |

## Explanation

**Generating expected periods without a calendar table**
The `MonthSequence` CTE uses `ROW_NUMBER() OVER (ORDER BY (SELECT NULL))` with a CROSS JOIN to generate a sequence of integers (0, 1, 2, …). `DATEADD(MONTH, offset, MinDate)` converts each offset to an actual month. This is a standard SQL Server technique for generating a date sequence without a dedicated calendar table.

**LEFT JOIN for gap detection**
`LEFT JOIN ActualMonths am ON em.ExpYr = am.ActYr AND em.ExpMo = am.ActMo` returns all expected months; where no actual data exists, `am.ActYr IS NULL` — the gap. This is the fundamental pattern for completeness checking: generate what should exist, left-join to what does exist, flag NULLs.

**Day coverage percentage**
Step 4's `DayCoveragePct` of 24.1% looks alarming but is expected for sparse data — the sample data only has transactions on 19 of 79 days in the range. In production, if transactions occur every business day, this percentage should be ~70% (5/7 days are business days). A sudden drop below the historical average is the alert signal.

**LAG for adjacent-day gap detection**
Step 2's LAG approach is simpler than generating a calendar — it only finds the specific gaps without knowing all expected dates in advance. The tradeoff: it cannot distinguish weekends (expected gaps) from missed batches (unexpected gaps) without a business-day calendar.

## Severity
**High** — Temporal incompleteness means reports cover a period that is silently incomplete. Unlike a total absence of data (which is obvious), a missing day or month within an otherwise populated range is invisible to users who assume continuity. Time-series analysis, trend detection, and SLA reporting are all invalidated by temporal gaps.
