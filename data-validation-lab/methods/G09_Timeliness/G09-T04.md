# G09-T04 — Timeliness | Future-Dated Records

## ID
G09-T04

## Group
9 — Timeliness

## Type
Future-Dated Records — Timestamps That Exceed the Current Date Without Authorisation

## Live Scenario
A payroll system processes salary increases. An HR administrator configuring a backdated promotion accidentally enters "2025-03-15" instead of "2024-03-15" for a HireDate override. The employee's anniversary-based benefits calculation uses HireDate, so the system calculates that the employee has been employed for negative months — and refuses to process their annual leave entitlement. A second issue: a batch data migration from a legacy system fails to convert 2-digit years correctly, writing "2099" for records that should be "1999." These 347 records are treated as current employees whose contract end dates are in 2099, so their contracts appear perpetual and are never flagged for renewal review.

## The Question
> Future-dated records contain timestamps beyond the current date in fields that should only record past events (hire dates, order dates, transaction dates). SQL detects these by comparing date fields to GETDATE() and flagging values that exceed a reasonable near-future tolerance.
> **"Identify any Orders where OrderDate is in the future, any Transactions where TransactionDate is in the future, and any Customers where ContractEnd is more than 5 years away (suggesting a data entry error)."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Transactions** — `schemas/05_Transactions.csv`
**Customers** — `schemas/01_Customers.csv`

## Solution Query

```sql
-- Step 1: Future-dated orders — OrderDate should not exceed today
SELECT
    o.OrderID,
    o.CustomerID,
    o.OrderDate,
    o.Status,
    o.TotalAmount,
    DATEDIFF(DAY, GETDATE(), o.OrderDate) AS DaysInFuture,
    CASE
        WHEN DATEDIFF(DAY, GETDATE(), o.OrderDate) > 365
             THEN 'CRITICAL: Order date over 1 year in future — likely year entry error'
        WHEN DATEDIFF(DAY, GETDATE(), o.OrderDate) > 30
             THEN 'SUSPICIOUS: Order date more than 30 days in future'
        ELSE 'MINOR: Order date within 30 days future — possible scheduled order'
    END AS FutureDateFlag
FROM Orders o
WHERE o.OrderDate > CAST(GETDATE() AS DATE)
ORDER BY o.OrderDate DESC;

-- Step 2: Future-dated transactions — TransactionDate should not exceed today
SELECT
    t.TransactionID,
    t.OrderID,
    t.Amount,
    t.Currency,
    t.TransactionDate,
    DATEDIFF(DAY, GETDATE(), t.TransactionDate) AS DaysInFuture,
    'TRANSACTION IN FUTURE: Cannot have processed a future payment' AS IssueType
FROM Transactions t
WHERE t.TransactionDate > CAST(GETDATE() AS DATE)
ORDER BY t.TransactionDate DESC;

-- Step 3: Customer ContractEnd anomalies — excessively far-future dates
SELECT
    c.CustomerID,
    c.FirstName + ' ' + c.LastName AS CustomerName,
    c.ContractEnd,
    DATEDIFF(YEAR, GETDATE(), c.ContractEnd) AS YearsUntilExpiry,
    CASE
        WHEN YEAR(c.ContractEnd) > 2090
             THEN 'YEAR ERROR: Year 2090+ suggests 2-digit year migration error (e.g. 99 → 2099)'
        WHEN DATEDIFF(YEAR, GETDATE(), c.ContractEnd) > 10
             THEN 'FAR FUTURE: Contract end over 10 years away — verify'
        WHEN DATEDIFF(YEAR, GETDATE(), c.ContractEnd) > 5
             THEN 'REVIEW: Contract end over 5 years — may be intentional perpetual contract'
        ELSE 'Reasonable contract end date'
    END AS ContractEndFlag
FROM Customers c
WHERE c.ContractEnd IS NOT NULL
  AND c.ContractEnd > DATEADD(YEAR, 5, GETDATE())
ORDER BY c.ContractEnd DESC;

-- Step 4: All date fields across tables — summary of future-dated records
SELECT 'Orders.OrderDate'          AS DateField,
       COUNT(*) AS FutureDatedCount,
       MAX(OrderDate) AS MostFutureDate
FROM Orders WHERE OrderDate > CAST(GETDATE() AS DATE)
UNION ALL
SELECT 'Orders.DeliveryDate',
       COUNT(*), MAX(DeliveryDate)
FROM Orders WHERE DeliveryDate > DATEADD(DAY, 30, GETDATE())  -- >30 days future is suspicious
UNION ALL
SELECT 'Transactions.TransactionDate',
       COUNT(*), MAX(TransactionDate)
FROM Transactions WHERE TransactionDate > CAST(GETDATE() AS DATE)
UNION ALL
SELECT 'Customers.ContractEnd',
       COUNT(*), MAX(ContractEnd)
FROM Customers WHERE ContractEnd > DATEADD(YEAR, 10, GETDATE())
ORDER BY FutureDatedCount DESC;
```

## Explanation

**GETDATE() as the upper bound**
For event timestamps (order dates, transaction dates, hire dates), the current date is the maximum valid value — events cannot have happened in the future. `OrderDate > CAST(GETDATE() AS DATE)` catches genuine future dates. `CAST(GETDATE() AS DATE)` strips the time component to avoid a clock-tick edge case where a record created earlier today might appear to be future-dated if the time portion is later than GETDATE().

**Year 2099/2090+ as migration error signature**
Two-digit year migration errors produce a characteristic pattern: years 1990–1999 become 2090–2099 when added to 2000 instead of being kept as 19XX. `YEAR(ContractEnd) > 2090` targets this specific class of error without affecting legitimate far-future dates like perpetual licences.

**Tolerance for scheduled/future events**
Not all future dates are errors — some systems schedule orders or contracts in advance. The tolerance logic uses days (30 days future = possibly scheduled) and years (5+ years = review, 10+ years = error) to distinguish likely errors from legitimate forward-planning.

**Multi-table date audit**
Step 4 produces a single-pass audit across all date fields, useful as a nightly data quality check. The result is one row per date field with count and maximum, making it easy to add to a monitoring dashboard.

## Severity
**Medium** — Future-dated records corrupt date-based calculations (age, tenure, SLA, interest accrual) and distort time-series analytics. They also affect period-boundary filters: a 2099 transaction will appear in every "future period" report indefinitely. The severity rises to High when future dates drive financial calculations (loan maturity, insurance coverage end).
