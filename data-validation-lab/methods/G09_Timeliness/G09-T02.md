# G09-T02 — Timeliness | Data Arrival Latency

## ID
G09-T02

## Group
9 — Timeliness

## Type
Data Arrival Latency — Records Arrive Later Than the SLA Requires

## Live Scenario
A financial services firm has an SLA with its data vendor: trade data for each business day must be delivered by 07:00 the following morning. An ETL monitoring table records when each file arrives. In March, the vendor's feed arrives at 09:47 on three separate occasions, breaching the SLA. The firm's risk team uses the morning data to run overnight position calculations starting at 07:30. On the three late days, stale position data is used for the first 2 hours of trading, potentially missing intraday risk limit breaches. The SLA breach triggers a contractual penalty clause. The firm's own monitoring system did not alert because the SLA check threshold was set to 10:00 — misconfigured at go-live.

## The Question
> Data arrival latency measures the gap between when data should arrive and when it actually arrives. SQL computes this lag by comparing TransactionDate (the data timestamp) to OrderDate (when the triggering event occurred), and identifies records that exceeded the latency SLA.
> **"Measure the lag between OrderDate (when an event occurs) and TransactionDate (when the corresponding transaction is recorded), identify records exceeding a 48-hour SLA, and produce a latency distribution report."**

## Table Reference
**Transactions** — `schemas/05_Transactions.csv`
**Orders** — `schemas/02_Orders.csv`

## Solution Query

```sql
-- Step 1: Compute arrival lag for each order-transaction pair
DECLARE @SLAHours INT = 48;

SELECT
    o.OrderID,
    o.OrderDate,
    t.TransactionDate,
    t.TransactionID,
    DATEDIFF(HOUR, o.OrderDate, t.TransactionDate)   AS LagHours,
    DATEDIFF(DAY,  o.OrderDate, t.TransactionDate)   AS LagDays,
    CASE
        WHEN t.TransactionID IS NULL
             THEN 'NO TRANSACTION: Order has no corresponding record'
        WHEN DATEDIFF(HOUR, o.OrderDate, t.TransactionDate) < 0
             THEN 'EARLY: Transaction predates order — data integrity error'
        WHEN DATEDIFF(HOUR, o.OrderDate, t.TransactionDate) <= @SLAHours
             THEN 'WITHIN SLA: ' + CAST(DATEDIFF(HOUR, o.OrderDate, t.TransactionDate) AS VARCHAR) + 'h'
        ELSE 'SLA BREACH: ' + CAST(DATEDIFF(HOUR, o.OrderDate, t.TransactionDate) AS VARCHAR)
             + 'h (SLA is ' + CAST(@SLAHours AS VARCHAR) + 'h)'
    END AS LatencyStatus
FROM Orders o
LEFT JOIN Transactions t ON o.OrderID = t.OrderID
WHERE o.Status NOT IN ('Cancelled', 'Pending')
ORDER BY LagHours DESC;

-- Step 2: Latency distribution — how many records fall in each lag band?
WITH OrderLag AS (
    SELECT
        o.OrderID,
        DATEDIFF(HOUR, o.OrderDate, t.TransactionDate) AS LagHours
    FROM Orders o
    JOIN Transactions t ON o.OrderID = t.OrderID
    WHERE o.Status NOT IN ('Cancelled')
)
SELECT
    CASE
        WHEN LagHours < 0    THEN 'Negative (error)'
        WHEN LagHours < 24   THEN '0-23 hours'
        WHEN LagHours < 48   THEN '24-47 hours'
        WHEN LagHours < 72   THEN '48-71 hours (SLA breach)'
        WHEN LagHours < 168  THEN '3-7 days (significant breach)'
        ELSE '7+ days (critical breach)'
    END AS LatencyBand,
    COUNT(*) AS OrderCount,
    ROUND(100.0 * COUNT(*) / SUM(COUNT(*)) OVER (), 1) AS Pct,
    MIN(LagHours) AS MinHours,
    MAX(LagHours) AS MaxHours,
    AVG(LagHours) AS AvgHours
FROM OrderLag
GROUP BY
    CASE
        WHEN LagHours < 0    THEN 'Negative (error)'
        WHEN LagHours < 24   THEN '0-23 hours'
        WHEN LagHours < 48   THEN '24-47 hours'
        WHEN LagHours < 72   THEN '48-71 hours (SLA breach)'
        WHEN LagHours < 168  THEN '3-7 days (significant breach)'
        ELSE '7+ days (critical breach)'
    END
ORDER BY MIN(LagHours);

-- Step 3: SLA breach summary by month
SELECT
    YEAR(o.OrderDate)  AS Yr,
    MONTH(o.OrderDate) AS Mo,
    COUNT(t.TransactionID) AS TotalTransactions,
    SUM(CASE WHEN DATEDIFF(HOUR, o.OrderDate, t.TransactionDate) > @SLAHours THEN 1 ELSE 0 END)
        AS SLABreaches,
    ROUND(100.0 * SUM(CASE WHEN DATEDIFF(HOUR, o.OrderDate, t.TransactionDate) > @SLAHours THEN 1 ELSE 0 END)
          / NULLIF(COUNT(t.TransactionID), 0), 1) AS BreachPct,
    MAX(DATEDIFF(HOUR, o.OrderDate, t.TransactionDate)) AS MaxLagHours,
    AVG(DATEDIFF(HOUR, o.OrderDate, t.TransactionDate)) AS AvgLagHours
FROM Orders o
JOIN Transactions t ON o.OrderID = t.OrderID
WHERE o.Status NOT IN ('Cancelled')
GROUP BY YEAR(o.OrderDate), MONTH(o.OrderDate)
ORDER BY Yr, Mo;

-- Step 4: Orders with no transaction at all — maximum possible latency (never arrived)
SELECT
    o.OrderID,
    o.OrderDate,
    o.Status,
    o.TotalAmount,
    DATEDIFF(HOUR, o.OrderDate, GETDATE()) AS HoursSinceOrder,
    'MISSING: No transaction recorded — data may never have arrived' AS LatencyFlag
FROM Orders o
WHERE NOT EXISTS (SELECT 1 FROM Transactions t WHERE t.OrderID = o.OrderID)
  AND o.Status NOT IN ('Cancelled', 'Pending')
ORDER BY HoursSinceOrder DESC;
```

## Explanation

**DATEDIFF(HOUR) for hour-precision latency**
`DATEDIFF(HOUR, OrderDate, TransactionDate)` returns the whole number of hours between the two timestamps. For sub-hour precision, use `DATEDIFF(MINUTE)`. Choose the unit that matches the SLA definition — a "next-day by 07:00" SLA is easier to express in minutes than hours.

**Negative lag as a data integrity error**
`LagHours < 0` means the transaction was recorded before the order was created — an impossible sequence unless timestamps are from different time zones or were manually backdated. This is both a timeliness and a consistency error requiring investigation.

**Latency distribution for SLA design**
Step 2 shows the distribution across latency bands. If 95% of records arrive within 24 hours but 5% take 7+ days, the SLA should be based on the 95th percentile, not the maximum. The distribution also reveals whether breaches are clustered (systematic issue) or scattered (random).

**Missing records as infinite latency**
Step 4 treats orders with no transaction as a latency problem: if a record never arrives, the latency is effectively infinite. `DATEDIFF(HOUR, OrderDate, GETDATE())` shows how long since the order was placed — the minimum time the corresponding transaction has been absent.

## Severity
**High** — Latency breaches mean data consumers are working with outdated information. In trading, clinical, and fraud systems, the cost of acting on stale data (missed risk, wrong diagnosis, undetected fraud) far exceeds the cost of the breach penalty. SLA monitoring with automated alerting is essential.
