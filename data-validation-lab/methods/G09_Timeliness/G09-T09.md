# G09-T09 — Timeliness | Reporting Lag Detection

## ID
G09-T09

## Group
9 — Timeliness

## Type
Reporting Lag Detection — Reports Cover a Period That Is More Stale Than Expected

## Live Scenario
A retail chain publishes daily sales reports for store managers. The report is supposed to reflect sales up to 23:59 the previous day. A report-generation job runs at 05:00 but uses a hardcoded date filter of `WHERE SaleDate < '2024-01-01'` — a developer copied a year-end test query into production and never updated the date parameter. Store managers receive a report that is perpetually stale: it always shows data up to 31 December 2023 regardless of the actual date. Because the sales figures are plausible and managers don't know the report's coverage period, the error goes undetected for 6 weeks. During this period, 87,000 transactions are missing from all management reports.

## The Question
> Reporting lag is the gap between the latest data available in the database and the latest data included in a report or view. SQL measures lag by comparing MAX(timestamp) in the source data to the expected coverage date and flagging when the gap exceeds the acceptable threshold.
> **"Measure the reporting lag in the Transactions table by comparing MAX(TransactionDate) to today's date, and identify whether the most recent data for each Order is within the expected freshness window."**

## Table Reference
**Transactions** — `schemas/05_Transactions.csv`
**Orders** — `schemas/02_Orders.csv`

## Solution Query

```sql
-- Step 1: Overall reporting lag — how far behind is the most recent data?
DECLARE @MaxExpectedLagDays INT = 1;  -- Data should be at most 1 day old

SELECT
    MAX(CAST(TransactionDate AS DATE)) AS LatestTransactionDate,
    CAST(GETDATE() AS DATE)            AS Today,
    DATEDIFF(DAY,
             MAX(CAST(TransactionDate AS DATE)),
             CAST(GETDATE() AS DATE))  AS LagDays,
    COUNT(*)                           AS TotalTransactions,
    SUM(CASE WHEN CAST(TransactionDate AS DATE) = MAX(CAST(TransactionDate AS DATE))
             THEN 1 ELSE 0 END)       AS TxOnLatestDay,
    CASE
        WHEN DATEDIFF(DAY, MAX(CAST(TransactionDate AS DATE)), CAST(GETDATE() AS DATE))
             <= @MaxExpectedLagDays
             THEN 'FRESH: Data is within ' + CAST(@MaxExpectedLagDays AS VARCHAR) + '-day threshold'
        WHEN DATEDIFF(DAY, MAX(CAST(TransactionDate AS DATE)), CAST(GETDATE() AS DATE))
             <= @MaxExpectedLagDays * 7
             THEN 'STALE: Data is '
                  + CAST(DATEDIFF(DAY, MAX(CAST(TransactionDate AS DATE)), CAST(GETDATE() AS DATE)) AS VARCHAR)
                  + ' days old — exceeds threshold'
        ELSE 'CRITICAL LAG: Data is '
             + CAST(DATEDIFF(DAY, MAX(CAST(TransactionDate AS DATE)), CAST(GETDATE() AS DATE)) AS VARCHAR)
             + ' days old — reporting is severely stale'
    END AS FreshnessStatus
FROM Transactions;

-- Step 2: Per-order freshness — when was the last event recorded for each order?
SELECT
    o.OrderID,
    o.CustomerID,
    o.OrderDate,
    o.Status,
    MAX(t.TransactionDate) AS LastTransactionDate,
    DATEDIFF(DAY, MAX(t.TransactionDate), GETDATE()) AS DaysSinceLastEvent,
    CASE
        WHEN MAX(t.TransactionDate) IS NULL
             THEN 'NO EVENTS: Order has no transaction history'
        WHEN o.Status IN ('Delivered', 'Cancelled', 'Refunded')
             THEN 'Terminal — no further events expected. Last event '
                  + CAST(DATEDIFF(DAY, MAX(t.TransactionDate), GETDATE()) AS VARCHAR) + ' days ago'
        WHEN DATEDIFF(DAY, MAX(t.TransactionDate), GETDATE()) > 30
             THEN 'STALE ACTIVE: Non-terminal order with no events for '
                  + CAST(DATEDIFF(DAY, MAX(t.TransactionDate), GETDATE()) AS VARCHAR) + ' days'
        ELSE 'Recent activity: last event '
             + CAST(DATEDIFF(DAY, MAX(t.TransactionDate), GETDATE()) AS VARCHAR) + ' days ago'
    END AS EventFreshness
FROM Orders o
LEFT JOIN Transactions t ON o.OrderID = t.OrderID
GROUP BY o.OrderID, o.CustomerID, o.OrderDate, o.Status
ORDER BY CASE WHEN DaysSinceLastEvent IS NULL THEN 1 ELSE 0 END, DaysSinceLastEvent DESC;

-- Step 3: Data freshness by month — is the most recent month fully populated?
SELECT
    YEAR(TransactionDate)  AS Yr,
    MONTH(TransactionDate) AS Mo,
    COUNT(*) AS RecordCount,
    MAX(CAST(TransactionDate AS DATE)) AS LastDayInMonth,
    DAY(EOMONTH(MAX(TransactionDate))) AS DaysInMonth,
    MAX(DAY(TransactionDate)) AS LastDayWithData,
    CASE
        WHEN YEAR(MAX(TransactionDate)) < YEAR(GETDATE())
          OR MONTH(MAX(TransactionDate)) < MONTH(GETDATE())
             THEN 'Historical month'
        WHEN MAX(DAY(TransactionDate)) < DAY(GETDATE()) - 1
             THEN 'CURRENT MONTH INCOMPLETE: Data only through day '
                  + CAST(MAX(DAY(TransactionDate)) AS VARCHAR)
                  + ' of ' + CAST(DAY(GETDATE()) AS VARCHAR)
        ELSE 'Current month — data appears current'
    END AS MonthCompleteness
FROM Transactions
GROUP BY YEAR(TransactionDate), MONTH(TransactionDate)
ORDER BY Yr DESC, Mo DESC;

-- Step 4: Reporting coverage audit — what is the effective date range?
SELECT
    MIN(CAST(TransactionDate AS DATE)) AS EarliestData,
    MAX(CAST(TransactionDate AS DATE)) AS LatestData,
    DATEDIFF(DAY, MIN(CAST(TransactionDate AS DATE)),
                  MAX(CAST(TransactionDate AS DATE))) AS CoverageDays,
    COUNT(DISTINCT CAST(TransactionDate AS DATE)) AS DaysWithData,
    DATEDIFF(DAY,
             MIN(CAST(TransactionDate AS DATE)),
             MAX(CAST(TransactionDate AS DATE))) + 1 AS ExpectedDays,
    DATEDIFF(DAY, MAX(CAST(TransactionDate AS DATE)), CAST(GETDATE() AS DATE)) AS LagFromToday,
    'Report should cover through ' + CAST(DATEADD(DAY, -1, CAST(GETDATE() AS DATE)) AS VARCHAR) AS ExpectedCoverage
FROM Transactions;
```

## Explanation

**MAX(TransactionDate) as the freshness indicator**
The most recent timestamp in the data tells you how far behind the data is. `DATEDIFF(DAY, MAX(TransactionDate), GETDATE())` is the lag in days. If a report is supposed to be "as of yesterday" and the lag is 40 days, the report is 40 days stale regardless of what date it displays in its header.

**Expected lag threshold**
`@MaxExpectedLagDays = 1` captures the most common real-time-ish requirement: data should be at most one day old. Real-time dashboards might use minutes; weekly reports might tolerate 7 days. The threshold is a business requirement, not a technical constant.

**Month completeness check**
Step 3 identifies whether the current month's data is complete: if today is the 25th but the latest data is from the 18th, the month is incomplete. `MAX(DAY(TransactionDate))` extracts the latest day-of-month with data; compared to `DAY(GETDATE()) - 1` (yesterday), this reveals the lag within the current month.

**The hardcoded date bug pattern**
The scenario describes a classic production bug: a hardcoded date in a WHERE clause. The SQL equivalent of this check is Step 4's `Expected coverage` output — if a report shows `LatestData = 2023-12-31` but today is July 2024, the report's WHERE clause is likely hardcoded.

## Severity
**High** — Reporting lag means decisions are made on outdated information. For operational reports (inventory, orders, fraud alerts), even a few hours of lag can have material consequences. For management information, a lag that is not disclosed is a governance failure — report consumers assume data is current unless told otherwise.
