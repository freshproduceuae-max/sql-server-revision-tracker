# G05-T09 — Range/Boundary | Coordinates Out of Range

## ID
G05-T09

## Group
5 — Range/Boundary

## Type
Coordinates Out of Range — Latitude/Longitude Beyond Physical Bounds

## Live Scenario
A food delivery platform stores restaurant and customer coordinates in `Latitude` and `Longitude` columns. A mobile app bug swaps latitude and longitude values for 340 addresses in one postcode district (`SE1`). Latitude `51.5` (London) is stored as longitude, and longitude `-0.09` is stored as latitude. The routing engine now routes to `-0.09` latitude (near the equator in the Indian Ocean) and `51.5` longitude (somewhere in Kazakhstan) for those customers. Deliveries fail and the coordinates look plausible individually — both values are within valid ranges — but are in the wrong columns.

## The Question
> Geographic coordinates have strict physical bounds: latitude must be between -90 and 90, longitude between -180 and 180. Additionally, coordinates should match the expected geographic region for the business context (e.g., UK-based deliveries should have latitude 49–61, longitude -8 to 2).
> **"Find all Customers where Latitude is outside the range -90 to 90, Longitude is outside -180 to 180, or where coordinates place the customer outside the expected UK region (latitude 49–61, longitude -8 to 2)."**

## Table Reference
**Customers** — `schemas/01_Customers.csv`

## Solution Query

```sql
-- Step 1: Physical coordinate bounds check
SELECT
    CustomerID,
    FirstName,
    LastName,
    Latitude,
    Longitude,
    CASE
        WHEN Latitude IS NULL OR Longitude IS NULL       THEN 'NULL coordinates'
        WHEN Latitude NOT BETWEEN -90 AND 90             THEN 'Latitude out of range (-90 to 90)'
        WHEN Longitude NOT BETWEEN -180 AND 180          THEN 'Longitude out of range (-180 to 180)'
        ELSE 'Within physical bounds'
    END AS PhysicalBoundsCheck
FROM Customers
WHERE Latitude IS NULL
   OR Longitude IS NULL
   OR Latitude NOT BETWEEN -90 AND 90
   OR Longitude NOT BETWEEN -180 AND 180;

-- Step 2: UK region plausibility check
SELECT
    CustomerID,
    FirstName,
    LastName,
    Latitude,
    Longitude,
    CASE
        WHEN Latitude BETWEEN 49 AND 61
             AND Longitude BETWEEN -8 AND 2         THEN 'UK region — plausible'
        WHEN Latitude BETWEEN 51 AND 52
             AND Longitude BETWEEN -0.5 AND 0.3     THEN 'Greater London — plausible'
        WHEN Latitude BETWEEN 47 AND 72
             AND Longitude BETWEEN -10 AND 30       THEN 'Western Europe — verify'
        ELSE 'Outside UK and Western Europe region'
    END AS RegionCheck
FROM Customers
WHERE Latitude IS NOT NULL AND Longitude IS NOT NULL
  AND (Latitude NOT BETWEEN 49 AND 61 OR Longitude NOT BETWEEN -8 AND 2);

-- Step 3: Detect lat/lon swap
-- If latitude looks like a longitude value and vice versa
SELECT
    CustomerID,
    Latitude,
    Longitude,
    'Possible lat/lon swap — latitude appears to be in longitude range' AS Issue
FROM Customers
WHERE Latitude IS NOT NULL
  AND Longitude IS NOT NULL
  AND Latitude BETWEEN -180 AND -90  -- outside latitude range but valid longitude range
  AND Longitude BETWEEN 49 AND 61;  -- outside typical London longitude but valid UK latitude

-- Step 4: Zero coordinate detection (0,0 is in the Gulf of Guinea — usually a sentinel)
SELECT
    CustomerID,
    FirstName,
    Latitude,
    Longitude,
    '(0, 0) — Null Island sentinel coordinate' AS Issue
FROM Customers
WHERE Latitude = 0 AND Longitude = 0;

-- Step 5: Coordinate precision check (suspiciously round numbers)
SELECT
    CustomerID,
    Latitude,
    Longitude,
    CASE
        WHEN Latitude = FLOOR(Latitude) AND Longitude = FLOOR(Longitude)
             THEN 'Integer coordinates — no decimal precision (approximate at best)'
        WHEN ABS(Latitude - ROUND(Latitude, 1)) < 0.00001
             AND ABS(Longitude - ROUND(Longitude, 1)) < 0.00001
             THEN 'Only 1 decimal place — very low precision (~11km accuracy)'
        ELSE 'Precision appears adequate'
    END AS PrecisionCheck
FROM Customers
WHERE Latitude IS NOT NULL AND Longitude IS NOT NULL;

-- Step 6: Summary
SELECT
    SUM(CASE WHEN Latitude NOT BETWEEN -90 AND 90 OR Longitude NOT BETWEEN -180 AND 180 THEN 1 ELSE 0 END) AS OutOfPhysicalBounds,
    SUM(CASE WHEN Latitude = 0 AND Longitude = 0 THEN 1 ELSE 0 END) AS NullIslandSentinel,
    SUM(CASE WHEN Latitude NOT BETWEEN 49 AND 61 OR Longitude NOT BETWEEN -8 AND 2 THEN 1 ELSE 0 END) AS OutsideUKRegion,
    COUNT(*) AS TotalCustomersWithCoords
FROM Customers
WHERE Latitude IS NOT NULL AND Longitude IS NOT NULL;
```

## Explanation

**Physical coordinate ranges**
Latitude: -90 (South Pole) to +90 (North Pole). Longitude: -180 to +180 (International Date Line). These are hard physical limits — there is no point on Earth outside these bounds. Any violation is a definitive error.

**"Null Island" (0°, 0°) as a sentinel value**
The coordinate (0, 0) is a point in the Gulf of Guinea, west of Gabon. No delivery or customer address should be located there. When a geocoding system fails to find a match, some return (0, 0) as a default. This is the geospatial equivalent of `1900-01-01` — a sentinel that means "geocoding failed."

**Lat/lon swap detection**
Swapped coordinates are insidious because both individual values remain within valid ranges. Detection requires domain knowledge: if a UK business expects latitude ≈ 51 and longitude ≈ -0.1, a value of latitude = -0.1 and longitude = 51 is likely a swap. Step 3 exploits this asymmetry.

**Coordinate precision and accuracy**
1 decimal place (e.g., `51.5`) has ~11km accuracy — fine for city-level routing but useless for street-level delivery. 4–6 decimal places (e.g., `51.5074`) have 1–100m accuracy. Step 5 flags suspiciously imprecise coordinates that suggest a manual entry or approximate geocoding.

## Severity
**High** — Invalid coordinates cause delivery failures, routing errors, and geofence misidentification. In logistics and emergency services, wrong coordinates mean personnel arrive at the wrong location. Out-of-bounds coordinates crash GIS systems that don't validate input.
