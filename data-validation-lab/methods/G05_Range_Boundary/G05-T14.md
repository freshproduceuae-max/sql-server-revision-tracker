# G05-T14 — Range/Boundary | Boundary Condition — Off-by-One Error

## ID
G05-T14

## Group
5 — Range/Boundary

## Type
Boundary Condition — Off-by-One Error in Range Application

## Live Scenario
A loyalty programme awards bonus points when a customer's total spend reaches exactly £500. The business rule is: "customers who spend £500 or more in a calendar month receive 2× points." A developer implements this as `WHERE TotalSpend > 500` (strict greater-than) instead of `>= 500` (greater-than-or-equal). Customers who spend exactly £500.00 receive only 1× points. The error affects 34 customers per month on average. A customer who monitors their points closely notices they received 3,000 points instead of 6,000 after a £500 purchase and raises a complaint. The loyalty system team spends three days investigating before identifying the off-by-one error.

## The Question
> Boundary conditions require careful attention to whether the boundary value itself is included or excluded. `>` vs `>=` and `<` vs `<=` determine whether the threshold value itself is in or out. Off-by-one errors are especially common at exactly-N thresholds.
> **"Find all SalesTargets where the commission tier logic uses strict greater-than when the business rule specifies 'at or above' — demonstrate the difference between BETWEEN (inclusive), > (exclusive), and >= (inclusive of boundary)."**

## Table Reference
**SalesTargets** — `schemas/06_SalesTargets.csv`
**Transactions** — `schemas/05_Transactions.csv`

## Solution Query

```sql
-- Step 1: Demonstrate BETWEEN vs > vs >= at exact boundary values
-- Business rule: commission of 10% for targets >= 100,000 and < 200,000
DECLARE @LowerBound DECIMAL(18,2) = 100000;
DECLARE @UpperBound DECIMAL(18,2) = 200000;

SELECT
    TargetID,
    TargetAmount,
    -- BETWEEN: inclusive on both ends
    CASE WHEN TargetAmount BETWEEN @LowerBound AND @UpperBound
         THEN '10% commission (BETWEEN — inclusive)' ELSE 'Not in tier' END AS BETWEENResult,
    -- Strict greater-than: excludes exactly 100000
    CASE WHEN TargetAmount > @LowerBound AND TargetAmount <= @UpperBound
         THEN '10% commission (> strict — EXCLUDES boundary)' ELSE 'Not in tier' END AS StrictGTResult,
    -- Greater-than-or-equal: includes exactly 100000
    CASE WHEN TargetAmount >= @LowerBound AND TargetAmount < @UpperBound
         THEN '10% commission (>= — INCLUDES lower, excludes upper)' ELSE 'Not in tier' END AS GTEResult
FROM SalesTargets
WHERE ABS(TargetAmount - @LowerBound) < 1000  -- show only records near the boundary
ORDER BY TargetAmount;

-- Step 2: Find records that fall exactly on the boundary
SELECT
    TargetID,
    SalespersonID,
    TargetAmount,
    'Exactly at boundary — tier assignment depends on > vs >= choice' AS BoundaryAlert
FROM SalesTargets
WHERE TargetAmount IN (100000, 200000, 300000);  -- tier boundary values

-- Step 3: Commission tier assignment with explicit boundary inclusion rules
SELECT
    TargetID,
    SalespersonID,
    TargetAmount,
    CASE
        -- Tier 1: below 100k (exclusive of 100k = < 100k)
        WHEN TargetAmount < 100000  THEN '5% — Tier 1 (< 100k)'
        -- Tier 2: 100k to 200k (inclusive of 100k, exclusive of 200k)
        WHEN TargetAmount >= 100000 AND TargetAmount < 200000 THEN '10% — Tier 2 (100k–200k)'
        -- Tier 3: 200k and above (inclusive of 200k)
        WHEN TargetAmount >= 200000 THEN '15% — Tier 3 (>= 200k)'
        ELSE 'Uncategorised'
    END AS CommissionTier,
    CASE
        -- Verify no record falls into multiple tiers (overlap check)
        WHEN (TargetAmount < 100000) +
             (TargetAmount >= 100000 AND TargetAmount < 200000) +
             (TargetAmount >= 200000) > 1
             THEN 'ERROR: in multiple tiers'
        ELSE 'Single tier — correct'
    END AS TierConsistency
FROM SalesTargets;

-- Step 4: Find gaps — values that fall into NO tier (should be impossible with correct logic)
SELECT
    TargetID,
    TargetAmount,
    'Falls into no commission tier — logic gap' AS Issue
FROM SalesTargets
WHERE TargetAmount NOT IN (
    SELECT TargetAmount FROM SalesTargets WHERE TargetAmount < 100000          -- Tier 1
    UNION ALL
    SELECT TargetAmount FROM SalesTargets WHERE TargetAmount >= 100000 AND TargetAmount < 200000 -- Tier 2
    UNION ALL
    SELECT TargetAmount FROM SalesTargets WHERE TargetAmount >= 200000         -- Tier 3
);

-- Step 5: Boundary transition count (how many records are in each tier)
SELECT
    CASE
        WHEN TargetAmount < 100000                          THEN 'Tier 1 (< 100k)'
        WHEN TargetAmount >= 100000 AND TargetAmount < 200000 THEN 'Tier 2 (100k–200k)'
        WHEN TargetAmount >= 200000                         THEN 'Tier 3 (>= 200k)'
    END AS Tier,
    COUNT(*) AS TargetCount,
    MIN(TargetAmount) AS MinInTier,
    MAX(TargetAmount) AS MaxInTier,
    AVG(TargetAmount) AS AvgInTier
FROM SalesTargets
WHERE TargetAmount IS NOT NULL
GROUP BY
    CASE
        WHEN TargetAmount < 100000                          THEN 'Tier 1 (< 100k)'
        WHEN TargetAmount >= 100000 AND TargetAmount < 200000 THEN 'Tier 2 (100k–200k)'
        WHEN TargetAmount >= 200000                         THEN 'Tier 3 (>= 200k)'
    END
ORDER BY MIN(TargetAmount);
```

## Explanation

**BETWEEN is inclusive on both ends**
`value BETWEEN 100000 AND 200000` is equivalent to `value >= 100000 AND value <= 200000`. Both boundary values (100000 and 200000) are included. If the business rule is "Tier 2 includes £100k but excludes £200k," `BETWEEN` is wrong — use `>= 100000 AND < 200000` instead.

**The three boundary choices**
For a threshold T:
- `value > T` — T itself is excluded (Tier 1 only below T)
- `value >= T` — T itself is included (Tier 2 includes T)
- `value BETWEEN T AND U` — both T and U are included (problematic for adjacent tiers)

Always use `>=` for the lower bound and `<` for the upper bound of each tier to create non-overlapping, gap-free coverage.

**Gap-free tier design**
A correct multi-tier structure uses `< T1`, `>= T1 AND < T2`, `>= T2 AND < T3`, `>= T3`. Each boundary appears exactly once — as the exclusive upper bound of one tier and the inclusive lower bound of the next. Step 4 verifies no value falls through the gaps.

**Testing at exact boundary values**
The most important test cases for any range/tier logic are: exactly at each boundary value, 1 unit below each boundary, and 1 unit above each boundary. If a record at exactly £100,000 is classified correctly, the boundary condition is right.

## Severity
**Medium** — Off-by-one boundary errors cause incorrect tier assignments, wrong commission calculations, and loyalty programme errors for customers exactly at thresholds. In financial systems with regulatory tier thresholds (e.g., tax brackets, credit limits), off-by-one errors have direct financial and compliance consequences.
