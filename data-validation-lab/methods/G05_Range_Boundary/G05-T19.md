# G05-T19 — Range/Boundary | Business Hours Range

## ID
G05-T19

## Group
5 — Range/Boundary

## Type
Business Hours Range — Activity Outside Expected Operating Window

## Live Scenario
A financial services firm operates from 08:00 to 18:00 Monday–Friday. All customer-facing transactions must be timestamped within this window for compliance reasons (trades outside business hours require special authorisation). A data quality check reveals 23 transactions with timestamps between 22:00 and 06:00 on weekdays, and 14 transactions on weekends. Investigation reveals a timezone conversion bug: a US-based integration is sending timestamps in Eastern Time (UTC-5), and the system stores them without conversion. What appears to be 22:00 GMT is actually 17:00 EST — a valid business-hours transaction that looks like an after-hours violation.

## The Question
> Records created or processed outside business hours may indicate automated processing, system errors, timezone issues, or genuine unauthorised activity. SQL can flag timestamps that fall outside the expected operating window using DATEPART to extract hour and day-of-week.
> **"Find all Transactions where the TransactionDate falls outside business hours (08:00–18:00, Monday–Friday), and classify them as weekend, after-hours weekday, or early-morning weekday."**

## Table Reference
**Transactions** — `schemas/05_Transactions.csv`
**Orders** — `schemas/02_Orders.csv`

## Solution Query

```sql
-- Step 1: Flag transactions outside business hours
SELECT
    TransactionID,
    OrderID,
    TransactionDate,
    DATEPART(WEEKDAY, TransactionDate) AS DayOfWeek,  -- 1=Sun, 2=Mon, ..., 7=Sat
    DATEPART(HOUR, TransactionDate) AS TxHour,
    DATENAME(WEEKDAY, TransactionDate) AS DayName,
    CASE
        WHEN DATEPART(WEEKDAY, TransactionDate) IN (1, 7)
             THEN 'Weekend transaction'
        WHEN DATEPART(HOUR, TransactionDate) < 8
             THEN 'Early morning (before 08:00)'
        WHEN DATEPART(HOUR, TransactionDate) >= 18
             THEN 'After hours (18:00 or later)'
        ELSE 'Within business hours'
    END AS BusinessHoursFlag
FROM Transactions
WHERE TransactionDate IS NOT NULL
  AND (
    DATEPART(WEEKDAY, TransactionDate) IN (1, 7)   -- weekend
    OR DATEPART(HOUR, TransactionDate) < 8          -- before 08:00
    OR DATEPART(HOUR, TransactionDate) >= 18        -- 18:00 or later
  )
ORDER BY TransactionDate;

-- Step 2: Breakdown by category
SELECT
    CASE
        WHEN DATEPART(WEEKDAY, TransactionDate) IN (1, 7) THEN 'Weekend'
        WHEN DATEPART(HOUR, TransactionDate) < 8          THEN 'Before 08:00'
        WHEN DATEPART(HOUR, TransactionDate) >= 18        THEN 'After 18:00'
    END AS Category,
    COUNT(*) AS TxCount,
    SUM(Amount) AS TotalAmount,
    ROUND(100.0 * COUNT(*) / SUM(COUNT(*)) OVER (), 1) AS PctOfOutOfHours
FROM Transactions
WHERE TransactionDate IS NOT NULL
  AND (
    DATEPART(WEEKDAY, TransactionDate) IN (1, 7)
    OR DATEPART(HOUR, TransactionDate) < 8
    OR DATEPART(HOUR, TransactionDate) >= 18
  )
GROUP BY
    CASE
        WHEN DATEPART(WEEKDAY, TransactionDate) IN (1, 7) THEN 'Weekend'
        WHEN DATEPART(HOUR, TransactionDate) < 8          THEN 'Before 08:00'
        WHEN DATEPART(HOUR, TransactionDate) >= 18        THEN 'After 18:00'
    END;

-- Step 3: Hour-of-day distribution (heatmap data for all transactions)
SELECT
    DATEPART(HOUR, TransactionDate) AS HourOfDay,
    COUNT(*) AS TxCount,
    SUM(CASE WHEN DATEPART(WEEKDAY, TransactionDate) IN (1,7) THEN 1 ELSE 0 END) AS WeekendCount,
    SUM(CASE WHEN DATEPART(WEEKDAY, TransactionDate) NOT IN (1,7) THEN 1 ELSE 0 END) AS WeekdayCount
FROM Transactions
WHERE TransactionDate IS NOT NULL
GROUP BY DATEPART(HOUR, TransactionDate)
ORDER BY HourOfDay;

-- Step 4: Orders placed outside business hours (unusual for a B2B platform)
SELECT
    OrderID,
    CustomerID,
    OrderDate,
    DATENAME(WEEKDAY, OrderDate) AS DayName,
    FORMAT(OrderDate, 'HH:mm') AS OrderTime,
    'Order placed outside business hours' AS Alert
FROM Orders
WHERE DATEPART(WEEKDAY, OrderDate) IN (1, 7)
   OR DATEPART(HOUR, OrderDate) < 8
   OR DATEPART(HOUR, OrderDate) >= 18
ORDER BY OrderDate;

-- Step 5: Salesperson activity outside working hours (possible data entry backdating)
SELECT
    SalespersonID,
    COUNT(*) AS OutOfHoursTxCount,
    MIN(TransactionDate) AS EarliestOOH,
    MAX(TransactionDate) AS LatestOOH
FROM Transactions t
JOIN Orders o ON t.OrderID = o.OrderID
WHERE DATEPART(WEEKDAY, t.TransactionDate) IN (1,7)
   OR DATEPART(HOUR, t.TransactionDate) < 8
   OR DATEPART(HOUR, t.TransactionDate) >= 18
GROUP BY SalespersonID
ORDER BY OutOfHoursTxCount DESC;
```

## Explanation

**DATEPART(WEEKDAY, ...) SQL Server convention**
In SQL Server, `DATEPART(WEEKDAY, date)` returns 1–7 where 1 = Sunday and 7 = Saturday (following the US week convention with `@@DATEFIRST = 7`). To detect weekends: `IN (1, 7)`. If `SET DATEFIRST` has been changed, adjust accordingly: `DATEPART(WEEKDAY, date) % 7 IN (0, 6)` is more portable.

**DATEPART(HOUR, ...) for time-of-day**
`DATEPART(HOUR, datetime)` extracts the integer hour (0–23). Business hours 08:00–18:00 means `HOUR >= 8 AND HOUR < 18`. Using `< 18` (not `<= 18`) means 18:00:00 itself is after hours — align with business definition.

**Legitimate out-of-hours activity**
Not all out-of-hours transactions are errors. Automated batch processes, scheduled jobs, and international time zones generate valid out-of-hours records. The business context determines what is flagged as a violation vs. a known exception. A classification column (`BatchProcess`, `ManualEntry`) helps distinguish them.

**`SET DATEFIRST` awareness**
SQL Server's `@@DATEFIRST` setting (default 7 = Sunday) affects `DATEPART(WEEKDAY, ...)`. Code that relies on specific weekday numbers is fragile in environments where `SET DATEFIRST 1` (Monday start) is used. Always test with the actual `@@DATEFIRST` value of the target database.

## Severity
**Medium** — Out-of-hours activity may indicate genuine violations (unauthorised system access, compliance breach) or data quality issues (timezone errors, batch processing misclassification). The severity depends on whether the system has compliance requirements around operating hours (financial trading, healthcare record access).
