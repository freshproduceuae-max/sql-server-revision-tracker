# G05-T03 — Range/Boundary | Date in the Future (Should Be Past)

## ID
G05-T03

## Group
5 — Range/Boundary

## Type
Date in the Future — Value Should Not Be Later Than Today

## Live Scenario
A customer onboarding system records `DateOfBirth` for age verification. A batch import from a partner system uses a 2-digit year format. The import script interprets `24` (meaning 1924) as 2024, making a 100-year-old customer appear to be unborn. A separate issue: the `OrderDate` column has 17 rows with dates in 2025 and 2026 because a data entry operator's system clock was set incorrectly for two weeks. Both categories — future birth dates and future order dates — represent impossible or implausible dates given the context.

## The Question
> Some date fields must never contain future dates. A `DateOfBirth` after today is impossible. An `OrderDate` after today suggests a system clock error or data entry error. `GETDATE()` provides the current date/time for the comparison.
> **"Find all Customers whose DateOfBirth is after today (impossible — person not yet born), and all Orders where OrderDate is in the future (system clock or entry error)."**

## Table Reference
**Customers** — `schemas/01_Customers.csv`
**Orders** — `schemas/02_Orders.csv`

## Solution Query

```sql
-- Step 1: Future DateOfBirth (impossible)
SELECT
    CustomerID,
    FirstName,
    LastName,
    DateOfBirth,
    CAST(GETDATE() AS DATE) AS Today,
    DATEDIFF(DAY, CAST(GETDATE() AS DATE), DateOfBirth) AS DaysInFuture
FROM Customers
WHERE DateOfBirth > CAST(GETDATE() AS DATE)
ORDER BY DateOfBirth DESC;

-- Step 2: Future OrderDate (implausible)
SELECT
    OrderID,
    CustomerID,
    OrderDate,
    CAST(GETDATE() AS DATE) AS Today,
    DATEDIFF(DAY, CAST(GETDATE() AS DATE), OrderDate) AS DaysAhead
FROM Orders
WHERE OrderDate > CAST(GETDATE() AS DATE)
ORDER BY OrderDate DESC;

-- Step 3: Near-future dates (within 7 days) — plausible pre-booking vs error
SELECT
    OrderID,
    OrderDate,
    DATEDIFF(DAY, CAST(GETDATE() AS DATE), OrderDate) AS DaysAhead,
    CASE
        WHEN DATEDIFF(DAY, CAST(GETDATE() AS DATE), OrderDate) > 30  THEN 'Far future (> 30 days) — likely error'
        WHEN DATEDIFF(DAY, CAST(GETDATE() AS DATE), OrderDate) > 7   THEN 'Near future (8-30 days) — flag for review'
        WHEN DATEDIFF(DAY, CAST(GETDATE() AS DATE), OrderDate) > 0   THEN 'Within 7 days — possible pre-booking'
        ELSE 'Not future'
    END AS FutureCategory
FROM Orders
WHERE OrderDate > CAST(GETDATE() AS DATE);

-- Step 4: Multi-date column future check in one query
SELECT 'DateOfBirth in future'   AS Check, COUNT(*) AS ViolationCount
FROM Customers WHERE DateOfBirth > CAST(GETDATE() AS DATE)
UNION ALL
SELECT 'OrderDate in future',     COUNT(*)
FROM Orders WHERE OrderDate > CAST(GETDATE() AS DATE)
UNION ALL
SELECT 'TransactionDate in future', COUNT(*)
FROM Transactions WHERE TransactionDate > CAST(GETDATE() AS DATE);

-- Step 5: Date anomaly context — is the future date a 2-digit year issue?
SELECT
    CustomerID,
    DateOfBirth,
    CASE
        WHEN YEAR(DateOfBirth) > YEAR(GETDATE())
             AND YEAR(DateOfBirth) - 100 BETWEEN 1900 AND YEAR(GETDATE())
             THEN 'Possible century flip: ' + CAST(YEAR(DateOfBirth) - 100 AS VARCHAR) +
                  ' interpreted as ' + CAST(YEAR(DateOfBirth) AS VARCHAR)
        ELSE 'Future date — no obvious century flip pattern'
    END AS CenturyFlipCheck
FROM Customers
WHERE DateOfBirth > CAST(GETDATE() AS DATE);
```

## Explanation

**`GETDATE()` vs `CAST(GETDATE() AS DATE)`**
`GETDATE()` returns current datetime including time component. Comparing `OrderDate DATE` to `GETDATE() DATETIME` may produce unexpected results near midnight due to implicit conversion. `CAST(GETDATE() AS DATE)` strips the time component, giving a clean "today" date for date-to-date comparison.

**`> GETDATE()` as a future date test**
The condition `DateOfBirth > CAST(GETDATE() AS DATE)` is simple and reliable. It runs against an indexed date column efficiently. The `DATEDIFF(DAY, today, date)` calculation adds context — how far in the future?

**The century flip problem**
A 2-digit year `24` can be interpreted as 1924 or 2024 depending on the import script's pivot year. Step 5 checks whether subtracting 100 years from the future date produces a plausible birth year — a strong diagnostic for this common import error.

**Context matters: some future dates are valid**
`DeliveryDate` (planned future delivery) should be in the future. `OrderDate` should not. The same data type (DATE) requires different range rules depending on which column it's in. Always specify the column's business meaning before applying a future-date check.

## Severity
**High** — Future dates in historical fields (DateOfBirth, OrderDate, TransactionDate) indicate import errors, system clock problems, or data entry errors. They corrupt age calculations, SLA measurements, and time-series analysis. A future DateOfBirth breaks age verification, which may have legal implications for age-restricted products.
