# G05-T15 — Range/Boundary | Invalid Enumerated Value

## ID
G05-T15

## Group
5 — Range/Boundary

## Type
Invalid Enumerated Value — Value Outside Permitted Set

## Live Scenario
An order management system stores order status as a VARCHAR column with permitted values: 'Pending', 'Processing', 'Shipped', 'Delivered', 'Cancelled', 'Refunded'. A third-party integration writes 'DISPATCHED' (uppercase variant of 'Shipped') and 'Returned' (an unmapped status) into the column. Downstream reporting groups orders by status — 'DISPATCHED' and 'Returned' appear as separate buckets, understating 'Shipped' counts and creating phantom categories on executive dashboards. A fulfilment SLA report shows 94% on-time delivery when the true figure, including 'DISPATCHED' orders, is 87%.

## The Question
> Columns with a fixed permitted set of values must be validated against that set. Any value not in the list is invalid regardless of whether it looks plausible. A CHECK constraint enforces this at write time; SQL validation queries detect violations in existing data.
> **"Find all Orders where Status is not in the permitted set ('Pending', 'Processing', 'Shipped', 'Delivered', 'Cancelled', 'Refunded'), and find all Employees where EmploymentType is not in ('Full-Time', 'Part-Time', 'Contract', 'Intern')."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Employees** — `schemas/04_Employees.csv`

## Solution Query

```sql
-- Step 1: Invalid order status values
DECLARE @ValidStatuses TABLE (StatusValue VARCHAR(50));
INSERT INTO @ValidStatuses VALUES
    ('Pending'), ('Processing'), ('Shipped'),
    ('Delivered'), ('Cancelled'), ('Refunded');

SELECT
    OrderID,
    CustomerID,
    OrderDate,
    Status,
    'Status not in permitted set' AS Issue
FROM Orders
WHERE Status NOT IN (
    SELECT StatusValue FROM @ValidStatuses
)
   OR Status IS NULL;

-- Step 2: Case-sensitive variant detection (catches 'SHIPPED', 'shipped', etc.)
SELECT
    OrderID,
    Status AS ActualValue,
    -- Find the closest permitted value (case-insensitive match)
    CASE
        WHEN UPPER(Status) = 'PENDING'    THEN 'Pending'
        WHEN UPPER(Status) = 'PROCESSING' THEN 'Processing'
        WHEN UPPER(Status) = 'SHIPPED'    THEN 'Shipped'
        WHEN UPPER(Status) = 'DELIVERED'  THEN 'Delivered'
        WHEN UPPER(Status) = 'CANCELLED'  THEN 'Cancelled'
        WHEN UPPER(Status) = 'REFUNDED'   THEN 'Refunded'
        ELSE NULL
    END AS SuggestedCorrection,
    CASE
        WHEN UPPER(Status) IN ('PENDING','PROCESSING','SHIPPED','DELIVERED','CANCELLED','REFUNDED')
             THEN 'Case mismatch — value is valid with correction'
        ELSE 'Unknown value — no match found'
    END AS DiagnosticNote
FROM Orders
WHERE Status NOT IN ('Pending','Processing','Shipped','Delivered','Cancelled','Refunded');

-- Step 3: Invalid employment type values
SELECT
    EmployeeID,
    FullName,
    EmploymentType,
    'EmploymentType not in permitted set' AS Issue
FROM Employees
WHERE EmploymentType NOT IN ('Full-Time', 'Part-Time', 'Contract', 'Intern')
   OR EmploymentType IS NULL;

-- Step 4: Summary of all invalid enum values across both tables
SELECT 'Orders.Status' AS Column_Name, Status AS InvalidValue, COUNT(*) AS RecordCount
FROM Orders
WHERE Status NOT IN ('Pending','Processing','Shipped','Delivered','Cancelled','Refunded')
GROUP BY Status

UNION ALL

SELECT 'Employees.EmploymentType', EmploymentType, COUNT(*)
FROM Employees
WHERE EmploymentType NOT IN ('Full-Time','Part-Time','Contract','Intern')
GROUP BY EmploymentType

ORDER BY Column_Name, RecordCount DESC;

-- Step 5: Distinct value audit — shows all values present including valid ones
SELECT
    Status AS PresentValue,
    COUNT(*) AS Occurrences,
    CASE WHEN Status IN ('Pending','Processing','Shipped','Delivered','Cancelled','Refunded')
         THEN 'Valid' ELSE 'INVALID' END AS Validity
FROM Orders
GROUP BY Status
ORDER BY Validity DESC, Occurrences DESC;
```

## Explanation

**NOT IN vs NOT EXISTS for set membership**
`WHERE Status NOT IN ('a','b','c')` is clean and readable for small fixed sets. For large dynamic reference sets, `NOT EXISTS (SELECT 1 FROM RefTable WHERE RefTable.Value = t.Status)` is preferred. Caution: `NOT IN` returns no rows if the list contains a NULL — always ensure the reference set excludes NULLs.

**Case sensitivity in SQL Server**
SQL Server collation determines whether `'Shipped' = 'SHIPPED'`. On case-insensitive collations (CI, the default), `NOT IN ('Shipped')` also excludes 'SHIPPED'. On case-sensitive collations (CS), they differ. Step 2 uses `UPPER()` to perform an explicit case-insensitive check that works regardless of collation.

**CHECK constraint as the preventive fix**
```sql
ALTER TABLE Orders ADD CONSTRAINT chk_OrderStatus
CHECK (Status IN ('Pending','Processing','Shipped','Delivered','Cancelled','Refunded'));
```
The SQL validation query detects existing violations; the CHECK constraint prevents new ones. Both are needed: historical data may have violations that pre-date the constraint.

**Domain table vs inline list**
For enum sets that change over time (e.g., new statuses added), a reference table (`StatusCodes`) with a FK constraint is more maintainable than a hardcoded list in a CHECK constraint. The inline list must be updated every time a new value is added; a FK reference auto-validates against the current reference table.

## Severity
**Medium** — Invalid enum values corrupt categorical analysis and reporting. A phantom category in a status field causes reporting errors proportional to the volume of affected records. In regulated systems (e.g., trade status, GDPR consent categories), invalid values may constitute a compliance violation.
