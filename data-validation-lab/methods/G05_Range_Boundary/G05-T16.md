# G05-T16 — Range/Boundary | Fiscal Year / Period Boundary

## ID
G05-T16

## Group
5 — Range/Boundary

## Type
Fiscal Year / Period Boundary — Date Outside Reported Period

## Live Scenario
A retail company's fiscal year runs April 1 to March 31. A finance analyst exports "FY2024 transactions" (April 2023 – March 2024) but the reporting query uses `WHERE YEAR(TransactionDate) = 2024` — a calendar year filter, not a fiscal year filter. This includes January–March 2024 (correct) but excludes April–December 2023 (FY2024 Q1–Q3). The revenue figure is understated by £4.1M. The error is only caught during external audit when the analyst's figures don't reconcile with the auditor's independently produced FY2024 total.

## The Question
> Fiscal periods don't align with calendar years. Queries filtering on `YEAR()` silently use the wrong boundary when the fiscal year doesn't start on January 1. Date range filters must be explicit about the fiscal calendar being used.
> **"Find all Transactions where TransactionDate falls outside the fiscal year April 2023 – March 2024, and demonstrate why YEAR(TransactionDate) = 2024 is wrong for a non-calendar fiscal year."**

## Table Reference
**Transactions** — `schemas/05_Transactions.csv`
**Orders** — `schemas/02_Orders.csv`

## Solution Query

```sql
-- Step 1: Fiscal year boundary definition (April–March)
DECLARE @FYStart DATE = '2023-04-01';
DECLARE @FYEnd   DATE = '2024-03-31';

-- Correct fiscal year filter
SELECT
    TransactionID,
    TransactionDate,
    Amount,
    'In FY2024 (Apr 2023 – Mar 2024)' AS FiscalPeriod
FROM Transactions
WHERE TransactionDate >= @FYStart
  AND TransactionDate <= @FYEnd;

-- Step 2: Show the error — calendar year vs fiscal year
SELECT
    TransactionID,
    TransactionDate,
    Amount,
    CASE
        WHEN YEAR(TransactionDate) = 2024                              THEN 'Captured by YEAR()=2024'
        WHEN TransactionDate >= '2023-04-01' AND TransactionDate <= '2024-03-31'
                                                                       THEN 'Captured by FY filter'
        ELSE 'Not in either'
    END AS FilterCaptures,
    CASE
        WHEN YEAR(TransactionDate) = 2024
         AND NOT (TransactionDate >= '2023-04-01' AND TransactionDate <= '2024-03-31')
                                                                       THEN 'Wrongly included by YEAR()=2024'
        WHEN (TransactionDate >= '2023-04-01' AND TransactionDate <= '2024-03-31')
         AND YEAR(TransactionDate) != 2024
                                                                       THEN 'Wrongly excluded by YEAR()=2024'
        ELSE 'Consistent'
    END AS DiscrepancyFlag
FROM Transactions
WHERE YEAR(TransactionDate) = 2024
   OR (TransactionDate >= '2023-04-01' AND TransactionDate <= '2024-03-31');

-- Step 3: Assign fiscal year and quarter to every transaction
SELECT
    TransactionID,
    TransactionDate,
    Amount,
    -- Fiscal year: if month >= April, fiscal year = calendar year + 1
    CASE WHEN MONTH(TransactionDate) >= 4
         THEN YEAR(TransactionDate) + 1
         ELSE YEAR(TransactionDate)
    END AS FiscalYear,
    -- Fiscal quarter
    CASE
        WHEN MONTH(TransactionDate) IN (4,5,6)   THEN 'FQ1'
        WHEN MONTH(TransactionDate) IN (7,8,9)   THEN 'FQ2'
        WHEN MONTH(TransactionDate) IN (10,11,12) THEN 'FQ3'
        WHEN MONTH(TransactionDate) IN (1,2,3)   THEN 'FQ4'
    END AS FiscalQuarter
FROM Transactions
WHERE TransactionDate IS NOT NULL
ORDER BY TransactionDate;

-- Step 4: Revenue summary by fiscal year (correct) vs calendar year (potentially wrong)
SELECT
    CASE WHEN MONTH(TransactionDate) >= 4
         THEN YEAR(TransactionDate) + 1
         ELSE YEAR(TransactionDate)
    END AS FiscalYear,
    COUNT(*) AS TxCount,
    SUM(Amount) AS FiscalRevenue
FROM Transactions
WHERE TransactionDate IS NOT NULL
GROUP BY
    CASE WHEN MONTH(TransactionDate) >= 4
         THEN YEAR(TransactionDate) + 1
         ELSE YEAR(TransactionDate)
    END
ORDER BY FiscalYear;

-- Step 5: Flag records that span a fiscal year boundary (e.g., subscriptions)
SELECT
    o.OrderID,
    o.OrderDate,
    o.DeliveryDate,
    CASE
        WHEN (MONTH(o.OrderDate) >= 4) != (MONTH(o.DeliveryDate) >= 4)
          OR YEAR(o.OrderDate) != YEAR(o.DeliveryDate)
             THEN 'Spans fiscal year boundary — may need period split'
        ELSE 'Within same fiscal year'
    END AS FiscalBoundaryFlag
FROM Orders o
WHERE o.DeliveryDate IS NOT NULL
  AND (
    (CASE WHEN MONTH(o.OrderDate) >= 4 THEN YEAR(o.OrderDate)+1 ELSE YEAR(o.OrderDate) END) !=
    (CASE WHEN MONTH(o.DeliveryDate) >= 4 THEN YEAR(o.DeliveryDate)+1 ELSE YEAR(o.DeliveryDate) END)
  );
```

## Explanation

**The April-start fiscal year formula**
`CASE WHEN MONTH(date) >= 4 THEN YEAR(date) + 1 ELSE YEAR(date) END` maps any date to its fiscal year number (where FY2024 = Apr 2023 – Mar 2024). The fiscal year is named for the calendar year in which it ends — a convention common in UK accounting, government finance, and many retail chains.

**Why `YEAR() = 2024` is wrong**
`YEAR(TransactionDate) = 2024` returns dates from 2024-01-01 to 2024-12-31. For a fiscal year ending 31 March 2024, this includes April–December 2024 (FY2025 territory) and excludes April–December 2023 (FY2024 Q1–Q3). The error is systematic, not random — always wrong by exactly 9 months of data.

**Explicit date range filters are unambiguous**
`WHERE TransactionDate >= '2023-04-01' AND TransactionDate <= '2024-03-31'` is explicit and correct regardless of fiscal calendar. Wrapping it in a scalar `@FYStart`/`@FYEnd` variable makes it parameterised and documentable.

**Spanning records need period allocation**
Transactions that start in one fiscal period and end in another (subscriptions, long-term orders) may need to be split across periods for accrual accounting. Step 5 identifies such records so that revenue recognition logic can be applied.

## Severity
**High** — Fiscal boundary errors systematically misstate periodic revenue, cost, and KPI figures. Unlike random errors, they affect entire reporting periods and are reproducible — every query using the wrong boundary produces the same wrong answer. In regulated financial reporting (audit, Companies House, tax filings), these errors have legal and compliance consequences.
