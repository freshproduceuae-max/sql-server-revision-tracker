# G05-T18 — Range/Boundary | Timestamp Clock Drift

## ID
G05-T18

## Group
5 — Range/Boundary

## Type
Timestamp Clock Drift — System Timestamps Inconsistent or Impossible

## Live Scenario
A distributed transaction processing system runs across three application servers in different time zones. Server A is configured for UTC, Server B is on UTC+1, and Server C — after a botched NTP synchronisation — has its clock running 47 minutes fast. Transactions processed on Server C have timestamps 47 minutes in the future. An audit log joining Server A and Server C transactions to reconstruct event sequences shows Server C events appearing to occur *after* their downstream effects — a payment confirmation timestamped at 14:23 appears in the log after the inventory deduction timestamped at 13:36, when the correct sequence is reversed. Fraud detection rules that rely on event ordering flag false positives.

## The Question
> Timestamps should be internally consistent: a record created at time T cannot be modified before T, a parent event cannot occur after its child events, and no system timestamp should be in the future relative to the current time. Clock drift in distributed systems breaks these assumptions.
> **"Find all Transactions where TransactionDate is in the future (after GETDATE()), and find all Orders where the OrderDate is after the DeliveryDate or after the current date."**

## Table Reference
**Transactions** — `schemas/05_Transactions.csv`
**Orders** — `schemas/02_Orders.csv`

## Solution Query

```sql
-- Step 1: Future-dated transactions (timestamps ahead of now)
SELECT
    TransactionID,
    OrderID,
    TransactionDate,
    GETDATE() AS CurrentTimestamp,
    DATEDIFF(MINUTE, GETDATE(), TransactionDate) AS MinutesAhead,
    CASE
        WHEN TransactionDate > DATEADD(MINUTE, 5, GETDATE())  THEN 'CLOCK DRIFT: >5 min in future'
        WHEN TransactionDate > GETDATE()                       THEN 'Minor drift: within 5 minutes'
        ELSE 'Timestamp OK'
    END AS ClockDriftFlag
FROM Transactions
WHERE TransactionDate > GETDATE()
ORDER BY MinutesAhead DESC;

-- Step 2: Orders with delivery before order date (temporal impossibility)
SELECT
    OrderID,
    CustomerID,
    OrderDate,
    DeliveryDate,
    DATEDIFF(DAY, DeliveryDate, OrderDate) AS DaysInverted,
    'DeliveryDate precedes OrderDate — impossible sequence' AS Issue
FROM Orders
WHERE DeliveryDate IS NOT NULL
  AND DeliveryDate < OrderDate;

-- Step 3: Transactions after their parent order date
-- A transaction should not pre-date its associated order
SELECT
    t.TransactionID,
    t.OrderID,
    o.OrderDate,
    t.TransactionDate,
    DATEDIFF(DAY, t.TransactionDate, o.OrderDate) AS DaysBeforeOrder,
    'Transaction precedes its order — clock drift or data error' AS Issue
FROM Transactions t
JOIN Orders o ON t.OrderID = o.OrderID
WHERE t.TransactionDate < o.OrderDate;

-- Step 4: Cluster analysis — identify drift by time window
-- Transactions clustered far ahead of the median may originate from a drifted clock
WITH Stats AS (
    SELECT
        AVG(CAST(TransactionDate AS FLOAT)) AS AvgDateFloat,
        STDEV(CAST(TransactionDate AS FLOAT)) AS StdDevDateFloat
    FROM Transactions
    WHERE TransactionDate IS NOT NULL
)
SELECT
    t.TransactionID,
    t.TransactionDate,
    DATEDIFF(HOUR,
        CAST(AVG(CAST(t2.TransactionDate AS FLOAT)) OVER () AS DATETIME),
        t.TransactionDate
    ) AS HoursFromMean,
    'Significant time deviation from batch median' AS Flag
FROM Transactions t
CROSS JOIN Stats s
WHERE ABS(CAST(t.TransactionDate AS FLOAT) - s.AvgDateFloat)
      > 3 * s.StdDevDateFloat
ORDER BY t.TransactionDate DESC;

-- Step 5: Summary drift report by date
SELECT
    CAST(TransactionDate AS DATE) AS TxDate,
    COUNT(*) AS TxCount,
    MIN(TransactionDate) AS EarliestTx,
    MAX(TransactionDate) AS LatestTx,
    SUM(CASE WHEN TransactionDate > GETDATE() THEN 1 ELSE 0 END) AS FutureDatedCount
FROM Transactions
WHERE TransactionDate IS NOT NULL
GROUP BY CAST(TransactionDate AS DATE)
HAVING SUM(CASE WHEN TransactionDate > GETDATE() THEN 1 ELSE 0 END) > 0
ORDER BY TxDate DESC;
```

## Explanation

**GETDATE() as the reference point**
`GETDATE()` returns the current server time. In a distributed system, the "current time" differs by server. Centralising all timestamp validation on a single server's `GETDATE()` exposes drift from other servers. The 5-minute tolerance in Step 1 accounts for legitimate sub-second network latency without masking real drift.

**Temporal ordering constraints**
Parent-child event ordering is a logical constraint: a transaction cannot precede the order it settles. Step 3 detects this using a JOIN and comparing timestamps across tables — a cross-table temporal consistency check that a single-table constraint cannot enforce.

**FLOAT casting for STDEV on dates**
SQL Server cannot compute `STDEV()` directly on DATETIME columns. `CAST(... AS FLOAT)` converts the internal DATETIME representation (a floating-point number of days since 1 January 1900) to a numeric type, enabling standard deviation calculation for outlier detection.

**Prevention: UTC everywhere**
The root fix for multi-server clock drift is standardising all timestamps to UTC at the application layer. `GETUTCDATE()` or `SYSUTCDATETIME()` in SQL Server returns the UTC equivalent. Storing local-time timestamps in a multi-timezone system creates irreversible ambiguity.

## Severity
**High** — Timestamp errors break audit trails, corrupt event sequencing, and cause false positives in fraud detection and anomaly detection systems. In financial systems, incorrect timestamps may constitute regulatory reporting failures (MiFID II requires sub-second trade timestamps accurate to within 1ms).
