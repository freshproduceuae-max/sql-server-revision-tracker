# G05-T11 — Range/Boundary | Overlapping Date Ranges

## ID
G05-T11

## Group
5 — Range/Boundary

## Type
Overlapping Date Ranges — Two Intervals for the Same Entity Overlap in Time

## Live Scenario
An HR system tracks employee salary history. Each row has `EffectiveFrom` and `EffectiveTo` dates for a given salary band. A system bug during a contract renewal creates two salary rows for employee E0042 where the new row starts before the old row expires: Row 1 covers 2024-01-01 to 2024-06-30, Row 2 covers 2024-06-01 to 2024-12-31. The 30-day overlap (June 1–30) means that any salary lookup for June returns two rows. The payroll system picks the first match, silently applying the old (lower) salary for the entire month of June. The employee is underpaid and only notices three months later when reviewing payslips.

## The Question
> Temporal records that should be non-overlapping (salary periods, contract periods, price tiers, SCD Type 2 records) must have a gap of at least one day between the end of one period and the start of the next. An overlap means two records are simultaneously valid for the same entity, which breaks point-in-time lookups.
> **"Find all Employees who have two or more salary history rows where the date ranges overlap — where one period's EffectiveFrom is before another period's EffectiveTo for the same employee."**

## Table Reference
**Employees** — `schemas/04_Employees.csv`

## Solution Query

```sql
-- Step 1: Find overlapping salary history rows using a self-join
SELECT
    a.EmployeeID,
    a.SalaryHistoryID AS Record1ID,
    a.EffectiveFrom AS Record1From,
    a.EffectiveTo AS Record1To,
    b.SalaryHistoryID AS Record2ID,
    b.EffectiveFrom AS Record2From,
    b.EffectiveTo AS Record2To,
    DATEDIFF(DAY,
             CASE WHEN a.EffectiveFrom > b.EffectiveFrom THEN a.EffectiveFrom ELSE b.EffectiveFrom END,
             CASE WHEN a.EffectiveTo < b.EffectiveTo THEN a.EffectiveTo ELSE b.EffectiveTo END
    ) AS OverlapDays,
    'Overlapping salary periods' AS Issue
FROM SalaryHistory a
JOIN SalaryHistory b
    ON  a.EmployeeID  = b.EmployeeID
    AND a.SalaryHistoryID < b.SalaryHistoryID   -- avoid duplicate pairs
    AND a.EffectiveFrom < b.EffectiveTo         -- a starts before b ends
    AND a.EffectiveTo   > b.EffectiveFrom       -- a ends after b starts
ORDER BY a.EmployeeID, OverlapDays DESC;

-- Step 2: Detect overlaps using LAG window function (more efficient for ordered data)
WITH OrderedHistory AS (
    SELECT
        EmployeeID,
        SalaryHistoryID,
        EffectiveFrom,
        EffectiveTo,
        LAG(EffectiveTo) OVER (PARTITION BY EmployeeID ORDER BY EffectiveFrom) AS PrevEffectiveTo
    FROM SalaryHistory
)
SELECT
    EmployeeID,
    SalaryHistoryID,
    EffectiveFrom,
    EffectiveTo,
    PrevEffectiveTo,
    DATEDIFF(DAY, EffectiveFrom, PrevEffectiveTo) AS OverlapDays,
    CASE
        WHEN PrevEffectiveTo IS NULL                THEN 'First record — no predecessor'
        WHEN EffectiveFrom > PrevEffectiveTo        THEN 'Gap between periods — OK'
        WHEN EffectiveFrom = PrevEffectiveTo        THEN 'Contiguous (starts same day as prev ends) — OK'
        WHEN EffectiveFrom < PrevEffectiveTo        THEN 'OVERLAP: starts before previous period ends'
        ELSE 'Unknown'
    END AS PeriodStatus
FROM OrderedHistory
WHERE EffectiveFrom <= PrevEffectiveTo
  AND PrevEffectiveTo IS NOT NULL;

-- Step 3: Overlaps in Order validity periods (promotional pricing)
SELECT
    a.ProductID,
    a.PriceHistoryID AS Price1ID,
    a.ValidFrom AS Price1From, a.ValidTo AS Price1To, a.UnitPrice AS Price1,
    b.PriceHistoryID AS Price2ID,
    b.ValidFrom AS Price2From, b.ValidTo AS Price2To, b.UnitPrice AS Price2,
    'Two valid prices for same product overlap in time' AS Issue
FROM PriceHistory a
JOIN PriceHistory b
    ON  a.ProductID = b.ProductID
    AND a.PriceHistoryID < b.PriceHistoryID
    AND a.ValidFrom < b.ValidTo
    AND a.ValidTo   > b.ValidFrom;

-- Step 4: Summary of employees with overlapping records
SELECT
    EmployeeID,
    COUNT(*) AS OverlapCount,
    MIN(DATEDIFF(DAY,
        CASE WHEN a.EffectiveFrom > b.EffectiveFrom THEN a.EffectiveFrom ELSE b.EffectiveFrom END,
        CASE WHEN a.EffectiveTo < b.EffectiveTo THEN a.EffectiveTo ELSE b.EffectiveTo END
    )) AS MinOverlapDays,
    MAX(DATEDIFF(DAY,
        CASE WHEN a.EffectiveFrom > b.EffectiveFrom THEN a.EffectiveFrom ELSE b.EffectiveFrom END,
        CASE WHEN a.EffectiveTo < b.EffectiveTo THEN a.EffectiveTo ELSE b.EffectiveTo END
    )) AS MaxOverlapDays
FROM SalaryHistory a
JOIN SalaryHistory b
    ON a.EmployeeID = b.EmployeeID
    AND a.SalaryHistoryID < b.SalaryHistoryID
    AND a.EffectiveFrom < b.EffectiveTo
    AND a.EffectiveTo > b.EffectiveFrom
GROUP BY a.EmployeeID
ORDER BY OverlapCount DESC;
```

## Explanation

**The overlap condition: A overlaps B if A.start < B.end AND A.end > B.start**
Two date ranges `[A.from, A.to]` and `[B.from, B.to]` overlap if and only if `A.from < B.to AND A.to > B.from`. This is Allen's Interval Algebra overlap condition. It covers all overlap cases: partial overlap, one contained within the other, and identical ranges. Using `<` (not `<=`) for both conditions means touching ranges (A.to = B.from) are NOT considered overlapping.

**Self-join vs LAG for overlap detection**
The self-join (Step 1) finds all overlapping pairs regardless of ordering — it handles cases where non-consecutive records overlap. The LAG approach (Step 2) only compares each record to its immediate predecessor, which is faster and catches the most common case (consecutive records overlapping). For paranoid validation, use the self-join; for routine checking, use LAG.

**Overlap vs gap**
The complement of this check is detecting gaps — periods where no record is valid (see the related consistency check in G06). Together, overlap and gap checks validate the completeness and non-redundancy of a temporal coverage.

**The BETWEEN overlap formula simplified**
An alternative phrasing: "A and B overlap if A.from is BETWEEN B.from and B.to, OR B.from is BETWEEN A.from and A.to." This is equivalent to the Allen condition but sometimes easier to reason about.

## Severity
**Critical** — Overlapping date ranges in temporal records (salary, pricing, contracts, SCD Type 2) cause non-deterministic lookups. A point-in-time query returns multiple rows, and whichever is returned first is used — producing inconsistent results depending on execution order. In payroll, this means salary errors; in pricing, it means wrong prices; in reporting, it means non-reproducible results.
