# G05-T20 — Range/Boundary | Invalid Week or Month Number

## ID
G05-T20

## Group
5 — Range/Boundary

## Type
Invalid Week or Month Number — Numeric Period Value Outside Valid Range

## Live Scenario
A sales planning system stores target periods as separate Year, Quarter, and Month columns (integers) rather than a DATE column. A bulk import from a legacy system maps month numbers incorrectly: months 10, 11, 12 from the source map to 0, 1, 2 in the target (a zero-based month system converted to one-based without adjustment). The import creates 847 records with Month = 0, 1, or 2 that should be 10, 11, or 12. A seasonal analysis of Q4 performance shows near-zero data because October, November, and December records were inserted with invalid month numbers and are excluded from any query using `WHERE Month BETWEEN 1 AND 12`.

## The Question
> Numeric representations of date parts (week 1–53, month 1–12, quarter 1–4, day 1–31) have fixed valid ranges. Values outside those ranges cannot represent a real date and indicate an encoding error, off-by-one import bug, or data entry mistake.
> **"Find all SalesTargets where Quarter is not between 1 and 4, where Year is outside a sensible range, and demonstrate validation of all numeric period components."**

## Table Reference
**SalesTargets** — `schemas/06_SalesTargets.csv`

## Solution Query

```sql
-- Step 1: Validate all period columns in SalesTargets
SELECT
    TargetID,
    SalespersonID,
    Year,
    Quarter,
    -- Check each period column
    CASE WHEN Quarter NOT BETWEEN 1 AND 4 OR Quarter IS NULL
         THEN 'INVALID Quarter: ' + ISNULL(CAST(Quarter AS VARCHAR), 'NULL')
         ELSE 'Quarter OK' END AS QuarterCheck,
    CASE WHEN Year NOT BETWEEN 2000 AND 2099 OR Year IS NULL
         THEN 'INVALID Year: ' + ISNULL(CAST(Year AS VARCHAR), 'NULL')
         ELSE 'Year OK' END AS YearCheck,
    CASE WHEN CommissionRate NOT BETWEEN 0 AND 100 OR CommissionRate IS NULL
         THEN 'INVALID CommissionRate: ' + ISNULL(CAST(CommissionRate AS VARCHAR), 'NULL')
         ELSE 'CommissionRate OK' END AS CommRateCheck
FROM SalesTargets
WHERE Quarter NOT BETWEEN 1 AND 4
   OR Year NOT BETWEEN 2000 AND 2099
   OR CommissionRate NOT BETWEEN 0 AND 100
   OR Quarter IS NULL
   OR Year IS NULL;

-- Step 2: Month validation (1–12) — in a hypothetical monthly targets table
-- Demonstrated with a derived check on existing data
SELECT
    TargetID,
    Year,
    Quarter,
    -- Derive the valid months for the given quarter
    CASE Quarter
        WHEN 1 THEN '1, 2, 3'
        WHEN 2 THEN '4, 5, 6'
        WHEN 3 THEN '7, 8, 9'
        WHEN 4 THEN '10, 11, 12'
        ELSE 'Unknown (invalid Quarter)'
    END AS ValidMonthsForQuarter
FROM SalesTargets
WHERE Quarter BETWEEN 1 AND 4;

-- Step 3: Week number validation (1–53)
-- ISO week numbers: 1–52 (most years) or 1–53 (years with 53 weeks)
SELECT
    TransactionID,
    TransactionDate,
    DATEPART(WEEK, TransactionDate) AS WeekNumber,
    DATEPART(ISO_WEEK, TransactionDate) AS ISOWeekNumber,
    CASE
        WHEN DATEPART(ISO_WEEK, TransactionDate) NOT BETWEEN 1 AND 53
             THEN 'INVALID ISO week number'
        ELSE 'Week OK'
    END AS WeekCheck
FROM Transactions
WHERE TransactionDate IS NOT NULL
  AND DATEPART(ISO_WEEK, TransactionDate) NOT BETWEEN 1 AND 53;

-- Step 4: Summary of invalid period values
SELECT 'SalesTargets.Quarter' AS ColumnName,
       CAST(Quarter AS VARCHAR) AS InvalidValue,
       COUNT(*) AS RecordCount
FROM SalesTargets
WHERE Quarter NOT BETWEEN 1 AND 4
GROUP BY Quarter

UNION ALL

SELECT 'SalesTargets.Year',
       CAST(Year AS VARCHAR),
       COUNT(*)
FROM SalesTargets
WHERE Year NOT BETWEEN 2000 AND 2099
GROUP BY Year

ORDER BY RecordCount DESC;

-- Step 5: Attempt to reconstruct valid periods from invalid ones
-- Example: zero-based month import (0=Jan, 11=Dec) → fix by adding 1
SELECT
    TargetID,
    Year,
    Quarter AS InvalidQuarter,
    -- If quarter = 0 or 5+, suggest the correction
    CASE
        WHEN Quarter = 0 THEN 'Likely Q4 (zero-based off-by-one)'
        WHEN Quarter = 5 THEN 'Likely Q1 (one-off upper bound)'
        ELSE 'No obvious correction'
    END AS SuggestedCorrection
FROM SalesTargets
WHERE Quarter NOT BETWEEN 1 AND 4;
```

## Explanation

**Fixed valid ranges for date parts**
- Month: 1–12 (never 0, never 13+)
- Quarter: 1–4 (never 0, never 5+)
- Week (ISO): 1–52 in most years, 1–53 in long years (e.g., 2015, 2020)
- Day of month: 1–28/29/30/31 depending on month and year
- Hour: 0–23 (never 24)
- Minute/Second: 0–59 (never 60, unless leap second — not used in SQL Server)

**Zero-based vs one-based encoding**
Many programming languages use zero-based month numbering (January = 0, December = 11). SQL Server uses one-based (January = 1, December = 12). Import errors frequently arise from this mismatch — the off-by-one converts valid source data into invalid SQL dates. `WHERE Month = 0` or `WHERE Month = 13` catches both directions of the error.

**Year range validation**
There is no universal valid year range, but a business-appropriate range (e.g., 2000–2099 for a modern system) catches likely errors: year 0, year 9999, year 202 (missing a digit), year 20241 (extra digit). The range should match the business domain — a historical records system might validate 1800–2100.

**DATEPART(ISO_WEEK, ...) vs DATEPART(WEEK, ...)**
SQL Server's `DATEPART(WEEK, ...)` depends on `@@DATEFIRST` and can return up to 54. `DATEPART(ISO_WEEK, ...)` returns the ISO 8601 week number (1–53) consistently. For international systems, ISO week is preferable.

## Severity
**Medium** — Invalid period numbers cause records to be silently excluded from period-based queries, producing understated totals and missing categories in reports. Off-by-one import errors affecting an entire import batch can distort quarterly or annual summaries by the full volume of affected records.
