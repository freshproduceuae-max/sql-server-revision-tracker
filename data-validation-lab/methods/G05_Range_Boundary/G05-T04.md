# G05-T04 — Range/Boundary | Date Too Far in the Past

## ID
G05-T04

## Group
5 — Range/Boundary

## Type
Date Too Far in the Past — Value Predates Plausible Business Range

## Live Scenario
A financial services platform has been in operation since 2010. Transaction records should all have dates from 2010 onwards. A data migration from an acquired company introduces records with dates back to 1985. More concerning: 43 records have dates in `1900-01-01` — the sentinel default value for "unknown date" from the legacy system. A risk model trained on historical transaction data is distorted because the pre-2010 records (which belong to a different business under different regulatory conditions) are mixed with the current company's data.

## The Question
> Some date fields should not predate the system's go-live date, the business's founding date, or a defined historical cutoff. A date of `1900-01-01` almost always indicates a sentinel default, not a real date.
> **"Find all Transactions where TransactionDate is before the system go-live date of 2010-01-01, and find all records in any table where a date column contains the sentinel default 1900-01-01."**

## Table Reference
**Transactions** — `schemas/05_Transactions.csv`
**Orders** — `schemas/02_Orders.csv`
**Customers** — `schemas/01_Customers.csv`

## Solution Query

```sql
-- Step 1: Transactions before system go-live
DECLARE @GoLiveDate DATE = '2010-01-01';

SELECT
    TransactionID,
    OrderID,
    TransactionDate,
    Amount,
    DATEDIFF(YEAR, TransactionDate, @GoLiveDate) AS YearsBeforeGoLive,
    CASE
        WHEN TransactionDate = '1900-01-01'  THEN 'Sentinel default (1900-01-01)'
        WHEN TransactionDate < '2000-01-01'  THEN 'Pre-2000 — century flip suspected'
        ELSE 'Before go-live — migration artifact?'
    END AS DateIssueCategory
FROM Transactions
WHERE TransactionDate < @GoLiveDate
ORDER BY TransactionDate;

-- Step 2: Sentinel default date detection across all tables
SELECT 'Customers.DateOfBirth'     AS ColumnRef, COUNT(*) AS SentinelCount
FROM Customers WHERE DateOfBirth = '1900-01-01'
UNION ALL
SELECT 'Orders.OrderDate',          COUNT(*) FROM Orders WHERE OrderDate = '1900-01-01'
UNION ALL
SELECT 'Transactions.TransactionDate', COUNT(*) FROM Transactions WHERE TransactionDate = '1900-01-01'
UNION ALL
-- Also check for other common sentinel dates
SELECT 'Orders — 1753-01-01 (SQL min date)', COUNT(*) FROM Orders WHERE OrderDate = '1753-01-01'
UNION ALL
SELECT 'Transactions — 9999-12-31 (far future)', COUNT(*) FROM Transactions WHERE TransactionDate = '9999-12-31';

-- Step 3: Plausibility by year — volume of records per year
SELECT
    YEAR(TransactionDate) AS TxYear,
    COUNT(*) AS TxCount,
    SUM(Amount) AS TotalAmount,
    CASE
        WHEN YEAR(TransactionDate) < 2010 THEN 'Before go-live — investigate'
        WHEN YEAR(TransactionDate) > YEAR(GETDATE()) THEN 'Future — data entry error'
        ELSE 'Within operational range'
    END AS YearStatus
FROM Transactions
GROUP BY YEAR(TransactionDate)
ORDER BY TxYear;

-- Step 4: Age-based implausibility for DateOfBirth
SELECT
    CustomerID,
    FirstName,
    LastName,
    DateOfBirth,
    DATEDIFF(YEAR, DateOfBirth, GETDATE()) AS ApparentAge,
    CASE
        WHEN DATEDIFF(YEAR, DateOfBirth, GETDATE()) > 130 THEN 'Age > 130 — implausible (sentinel or century error)'
        WHEN DATEDIFF(YEAR, DateOfBirth, GETDATE()) > 110 THEN 'Age > 110 — very unlikely (verify)'
        WHEN DATEDIFF(YEAR, DateOfBirth, GETDATE()) < 0   THEN 'Future date — impossible'
        ELSE 'Age within plausible range'
    END AS AgeCheck
FROM Customers
WHERE DateOfBirth IS NOT NULL
  AND (DATEDIFF(YEAR, DateOfBirth, GETDATE()) > 110
    OR DateOfBirth < '1900-01-02');  -- 1900-01-01 is almost always a sentinel
```

## Explanation

**`1900-01-01` as a sentinel default**
Many legacy systems and SQL Server datetime defaults use `1900-01-01` (which is `CAST(0 AS DATETIME)` in SQL Server) as a placeholder for "unknown date." These are not real dates — they should be NULL or carry a separate "date unknown" flag. Always check for this value explicitly in addition to range checks.

**`1753-01-01` as another SQL Server date artifact**
SQL Server's SMALLDATETIME minimum is `1900-01-01` and DATETIME minimum is `1753-01-01` (when the Gregorian calendar was adopted in Britain). Records with exactly this date are almost always a sentinel from a DATETIME column's minimum value.

**Year-by-year volume as a plausibility check**
Step 3 groups records by year and flags years outside the operational range. A sudden spike of records in 1985 or 1900 (years outside the operational range) is immediately visible in the year distribution and doesn't require row-by-row inspection.

**Age-based validation for DateOfBirth**
A customer with an apparent age > 130 years has an invalid date of birth. The world's oldest verified person ever was 122 years old. Step 4 flags anyone over 110 as needing verification and anyone over 130 as definitely wrong.

## Severity
**High** — Pre-go-live dates contaminate time-series analysis, distort trend reports, and corrupt ML training data. Sentinel dates (1900-01-01) that are treated as real dates break age calculations, duration calculations, and SLA measurements. In financial services, pre-go-live transaction dates can create false regulatory reporting obligations.
