# G04-T04 — Format/Pattern | Date Format in VARCHAR Column

## ID
G04-T04

## Group
4 — Format/Pattern

## Type
Date Format in VARCHAR Column — Inconsistent or Unparseable Date Strings

## Live Scenario
A legacy ERP system exports a `DeliveryDate` column as VARCHAR(20). Over 8 years of use, three different regional teams have entered dates in their local formats: the UK team uses `DD/MM/YYYY`, the US team uses `MM/DD/YYYY`, and an automated feed uses `YYYY-MM-DD`. All three formats produce valid-looking strings — `"01/02/2024"` is either 1 February or 2 January depending on which convention is active. When the data warehouse tries to CAST all values to DATE, 23% fail outright and the rest are silently misinterpreted by region.

## The Question
> Dates stored as strings are one of the most common sources of silent data corruption. A string that looks like a date may be in the wrong format, contain impossible values, or be unparseable entirely.
> **"Find all rows in the Orders table where OrderDate (stored as VARCHAR) cannot be safely converted to a DATE, or where the string is ambiguous between DD/MM/YYYY and MM/DD/YYYY formats."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`

## Solution Query

```sql
-- Step 1: Find values that cannot be cast to DATE at all
SELECT
    OrderID,
    OrderDate,
    'Cannot convert to DATE' AS Issue
FROM Orders
WHERE TRY_CAST(OrderDate AS DATE) IS NULL
  AND OrderDate IS NOT NULL;

-- Step 2: Detect the date format used in each row
SELECT
    OrderID,
    OrderDate,
    CASE
        -- ISO 8601: YYYY-MM-DD (unambiguous)
        WHEN OrderDate LIKE '[0-9][0-9][0-9][0-9]-[0-1][0-9]-[0-3][0-9]'
             THEN 'ISO 8601 (YYYY-MM-DD)'
        -- Slash-delimited with 4-digit year last
        WHEN OrderDate LIKE '[0-3][0-9]/[0-1][0-9]/[0-9][0-9][0-9][0-9]'
             THEN 'DD/MM/YYYY or MM/DD/YYYY — ambiguous'
        -- Dot-delimited (European)
        WHEN OrderDate LIKE '[0-3][0-9].[0-1][0-9].[0-9][0-9][0-9][0-9]'
             THEN 'DD.MM.YYYY (European dot format)'
        -- 2-digit year
        WHEN OrderDate LIKE '[0-9][0-9]/[0-9][0-9]/[0-9][0-9]'
             THEN '2-digit year — century ambiguous'
        -- Text month (e.g. 01-Jan-2024)
        WHEN OrderDate LIKE '[0-9][0-9]-[A-Za-z][A-Za-z][A-Za-z]-[0-9][0-9][0-9][0-9]'
             THEN 'DD-Mon-YYYY (Oracle export format)'
        ELSE 'Unknown or invalid format'
    END AS DetectedFormat,
    TRY_CAST(OrderDate AS DATE) AS ParsedAsDate
FROM Orders
WHERE OrderDate IS NOT NULL;

-- Step 3: Flag impossible date values (day > 31, month > 12, etc.)
SELECT
    OrderID,
    OrderDate,
    CASE
        WHEN TRY_CAST(OrderDate AS DATE) IS NULL        THEN 'Unparseable'
        WHEN MONTH(TRY_CAST(OrderDate AS DATE)) > 12   THEN 'Invalid month > 12'
        WHEN DAY(TRY_CAST(OrderDate AS DATE)) > 31     THEN 'Invalid day > 31'
        WHEN YEAR(TRY_CAST(OrderDate AS DATE)) < 1900  THEN 'Year before 1900'
        WHEN YEAR(TRY_CAST(OrderDate AS DATE)) > 2100  THEN 'Year after 2100'
        ELSE 'OK'
    END AS DateIssue
FROM Orders
WHERE OrderDate IS NOT NULL
  AND (TRY_CAST(OrderDate AS DATE) IS NULL
       OR YEAR(TRY_CAST(OrderDate AS DATE)) NOT BETWEEN 1900 AND 2100);

-- Step 4: Safe conversion with fallback — attempt multiple formats
SELECT
    OrderID,
    OrderDate,
    COALESCE(
        TRY_CONVERT(DATE, OrderDate, 120),   -- YYYY-MM-DD (ISO)
        TRY_CONVERT(DATE, OrderDate, 103),   -- DD/MM/YYYY (British)
        TRY_CONVERT(DATE, OrderDate, 101),   -- MM/DD/YYYY (US)
        TRY_CONVERT(DATE, OrderDate, 105)    -- DD-MM-YYYY
    ) AS BestGuessDate,
    CASE
        WHEN TRY_CONVERT(DATE, OrderDate, 120) IS NOT NULL THEN 'Converted as ISO'
        WHEN TRY_CONVERT(DATE, OrderDate, 103) IS NOT NULL THEN 'Converted as DD/MM/YYYY'
        WHEN TRY_CONVERT(DATE, OrderDate, 101) IS NOT NULL THEN 'Converted as MM/DD/YYYY'
        ELSE 'Failed all conversions'
    END AS ConversionMethod
FROM Orders
WHERE OrderDate IS NOT NULL;
```

|---|---|---|

| 1019 | delivery pending | Cannot convert to DATE |

**Step 2 — Format detection:**
| OrderID | OrderDate | DetectedFormat |
|---|---|---|
| 1001 | 2024-01-15 | ISO 8601 (YYYY-MM-DD) |
| 1003 | 15/01/2024 | DD/MM/YYYY or MM/DD/YYYY — ambiguous |
| 1009 | 15.01.2024 | DD.MM.YYYY (European dot format) |

## Explanation

**TRY_CAST vs CAST for format validation**
`CAST(value AS DATE)` throws an error if conversion fails, halting the entire query. `TRY_CAST(value AS DATE)` returns NULL on failure, allowing the rest of the rows to be processed. Always use TRY_CAST or TRY_CONVERT when validating strings as dates.

**TRY_CONVERT format codes (style parameter)**
SQL Server's CONVERT function accepts a style code that specifies the expected date string format:
- `120` — `YYYY-MM-DD HH:MM:SS` (ISO 8601, unambiguous)
- `103` — `DD/MM/YYYY` (British/French)
- `101` — `MM/DD/YYYY` (US)
- `105` — `DD-MM-YYYY`
- `106` — `DD Mon YYYY`

**The ambiguity problem with `DD/MM/YYYY` vs `MM/DD/YYYY`**
`01/02/2024` is a valid date in both conventions. SQL Server cannot determine which is intended without a style code or external context. The only safe fix is to standardise all dates to ISO 8601 (`YYYY-MM-DD`) at the point of entry.

**Step 4 as a migration tool**
The COALESCE over multiple TRY_CONVERT attempts is a practical migration pattern: try the most likely format first, fall back to alternates. Document which format code succeeded so the source of ambiguity is visible in the output.

## Severity
**High** — Date format errors cause silent data corruption (wrong dates that look correct) and conversion failures (rows dropped from aggregations). In financial reporting, a misinterpreted date can move a transaction into the wrong fiscal period.
