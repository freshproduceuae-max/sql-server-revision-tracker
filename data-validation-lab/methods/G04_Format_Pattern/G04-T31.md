# G04-T31 — Format/Pattern | Numeric Precision / Scale Mismatch

## ID
G04-T31

## Group
4 — Format/Pattern

## Type
Numeric Precision / Scale Mismatch — Wrong Decimal Scale for the Domain

## Live Scenario
A financial data warehouse receives trade data from three exchanges. Exchange A sends prices with 4 decimal places (`123.4567`), Exchange B sends with 2 (`123.45`), and Exchange C sends with 8 (`123.45670000`). The warehouse schema expects `DECIMAL(18,4)`. During ETL, Exchange B data is stored without issue. Exchange C data loses the last 4 decimal places silently (the values are the same but the precision difference in the source is undocumented). A quant analyst calculates a spread incorrectly because the sub-cent precision they expected from Exchange C is gone. Similarly, some records have values stored as integers (`123`) with no decimal component — these turn out to be prices in minor units (pence/cents) that were never converted.

## The Question
> When a numeric column has a defined scale (number of decimal places), values stored with fewer decimal places may indicate a unit error, and values that were provided with more decimal places may have been silently rounded. Checking the actual vs expected scale reveals these mismatches.
> **"Find all Transactions where the Amount column has more than 4 decimal places (indicating an import from a system with higher precision that may have been silently rounded), or has 0 decimal places on a column that should always have 2 (possible minor-unit import)."**

## Table Reference
**Transactions** — `schemas/05_Transactions.csv`

## Solution Query

```sql
-- Step 1: Count actual decimal places for each Amount value
SELECT
    TransactionID,
    Amount,
    CASE
        WHEN CHARINDEX('.', CAST(Amount AS VARCHAR(30))) = 0
             THEN 0
        ELSE LEN(CAST(Amount AS VARCHAR(30))) - CHARINDEX('.', CAST(Amount AS VARCHAR(30)))
    END AS ActualDecimalPlaces,
    CASE
        WHEN CHARINDEX('.', CAST(Amount AS VARCHAR(30))) = 0   THEN 'Integer — no decimal places (minor unit?)'
        WHEN LEN(CAST(Amount AS VARCHAR(30))) - CHARINDEX('.', CAST(Amount AS VARCHAR(30))) < 2
             THEN 'Fewer than 2dp — missing trailing zero?'
        WHEN LEN(CAST(Amount AS VARCHAR(30))) - CHARINDEX('.', CAST(Amount AS VARCHAR(30))) = 2
             THEN 'Exactly 2dp — standard'
        WHEN LEN(CAST(Amount AS VARCHAR(30))) - CHARINDEX('.', CAST(Amount AS VARCHAR(30))) BETWEEN 3 AND 4
             THEN '3-4dp — acceptable for high-precision pricing'
        WHEN LEN(CAST(Amount AS VARCHAR(30))) - CHARINDEX('.', CAST(Amount AS VARCHAR(30))) > 4
             THEN 'More than 4dp — possible precision loss on storage'
        ELSE 'Other'
    END AS PrecisionCategory
FROM Transactions
WHERE Amount IS NOT NULL;

-- Step 2: Identify amounts that are suspiciously round integers (possible minor-unit error)
SELECT
    TransactionID,
    Amount,
    Currency,
    CASE
        WHEN Amount = FLOOR(Amount)
             AND Amount > 100
             AND Currency IN ('GBP','USD','EUR')
             THEN 'Round integer > 100 in major-unit currency — possible pence/cents import'
        WHEN Amount = FLOOR(Amount)
             AND Currency = 'JPY'
             THEN 'Integer amount for JPY — correct (JPY has no minor unit)'
        WHEN Amount = FLOOR(Amount)
             AND Amount <= 100
             THEN 'Round integer <= 100 — plausible but verify'
        ELSE 'Has decimal component — not a round integer'
    END AS IntegerAmountCheck
FROM Transactions
WHERE Amount IS NOT NULL;

-- Step 3: Verify DECIMAL(18,4) column for rounding impact
SELECT
    TransactionID,
    Amount AS StoredAmount,
    -- Simulate what would happen with higher precision storage
    ROUND(Amount, 4) AS RoundedTo4dp,
    CASE
        WHEN Amount <> ROUND(Amount, 4) THEN 'Rounding occurred — precision loss'
        ELSE 'No rounding at 4dp'
    END AS RoundingCheck
FROM Transactions
WHERE Amount IS NOT NULL
  AND Amount <> ROUND(Amount, 4);

-- Step 4: Scale distribution across the dataset
SELECT
    CASE
        WHEN CHARINDEX('.', CAST(Amount AS VARCHAR(30))) = 0 THEN 0
        ELSE LEN(CAST(Amount AS VARCHAR(30))) - CHARINDEX('.', CAST(Amount AS VARCHAR(30)))
    END AS DecimalPlaces,
    COUNT(*) AS TransactionCount,
    MIN(Amount) AS MinAmount,
    MAX(Amount) AS MaxAmount
FROM Transactions
WHERE Amount IS NOT NULL
GROUP BY
    CASE
        WHEN CHARINDEX('.', CAST(Amount AS VARCHAR(30))) = 0 THEN 0
        ELSE LEN(CAST(Amount AS VARCHAR(30))) - CHARINDEX('.', CAST(Amount AS VARCHAR(30)))
    END
ORDER BY DecimalPlaces;

-- Step 5: Detect inconsistent precision per currency
SELECT
    Currency,
    MIN(CASE WHEN CHARINDEX('.', CAST(Amount AS VARCHAR(30))) = 0 THEN 0
             ELSE LEN(CAST(Amount AS VARCHAR(30))) - CHARINDEX('.', CAST(Amount AS VARCHAR(30))) END) AS MinDecimalPlaces,
    MAX(CASE WHEN CHARINDEX('.', CAST(Amount AS VARCHAR(30))) = 0 THEN 0
             ELSE LEN(CAST(Amount AS VARCHAR(30))) - CHARINDEX('.', CAST(Amount AS VARCHAR(30))) END) AS MaxDecimalPlaces,
    COUNT(*) AS TxCount
FROM Transactions
WHERE Amount IS NOT NULL
GROUP BY Currency
HAVING MIN(CASE WHEN CHARINDEX('.', CAST(Amount AS VARCHAR(30))) = 0 THEN 0
               ELSE LEN(CAST(Amount AS VARCHAR(30))) - CHARINDEX('.', CAST(Amount AS VARCHAR(30))) END)
     <> MAX(CASE WHEN CHARINDEX('.', CAST(Amount AS VARCHAR(30))) = 0 THEN 0
                 ELSE LEN(CAST(Amount AS VARCHAR(30))) - CHARINDEX('.', CAST(Amount AS VARCHAR(30))) END);
```

## Expected Output

**Step 1 — Precision categories:**
| TransactionID | Amount | ActualDecimalPlaces | PrecisionCategory |
|---|---|---|---|
| T001 | 123.45 | 2 | Exactly 2dp — standard |
| T004 | 12345 | 0 | Integer — no decimal places (minor unit?) |
| T007 | 123.45670000 | 8 | More than 4dp — possible precision loss on storage |

**Step 4 — Scale distribution:**
| DecimalPlaces | TransactionCount | MinAmount | MaxAmount |
|---|---|---|---|
| 0 | 3 | 100 | 9999 |
| 2 | 14 | 0.01 | 9999.99 |
| 4 | 2 | 12.3456 | 567.8901 |

## Explanation

**Decimal place count via string inspection**
`LEN(CAST(Amount AS VARCHAR)) - CHARINDEX('.', CAST(Amount AS VARCHAR))` gives the number of digits after the decimal point. When CHARINDEX returns 0 (no decimal point), the value is an integer with 0 decimal places. This approach works for any numeric type after converting to string.

**The DECIMAL(18,4) precision trap**
Storing `123.456789` in a `DECIMAL(18,4)` column silently rounds it to `123.4568`. No error is raised. The only way to detect this was precision loss is to compare the source value to the stored value — which requires either keeping the source or using a higher-precision staging column.

**Currency-specific expected precision**
JPY and some other currencies have no minor units — integer amounts are correct. GBP, USD, and EUR expect 2 decimal places. Some financial instruments trade in fractions of a cent (4-6 decimal places). The correct precision is a business rule, not a SQL rule.

**Step 5: inconsistent precision per currency**
If the same currency appears with both 0 and 2 decimal places, there's likely a mixed minor/major unit import. HAVING with MIN ≠ MAX decimal places detects this multi-precision situation.

## Severity
**High** — Numeric precision mismatches cause incorrect financial calculations, reconciliation failures, and regulatory reporting errors. A 100× magnitude error (minor vs major units) is a critical financial data quality failure.
