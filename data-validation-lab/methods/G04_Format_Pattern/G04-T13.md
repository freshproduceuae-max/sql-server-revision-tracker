# G04-T13 — Format/Pattern | Leading/Trailing Whitespace

## ID
G04-T13

## Group
4 — Format/Pattern

## Type
Leading / Trailing Whitespace — Hidden Padding Characters

## Live Scenario
A customer loyalty platform uses `Email` as the natural key for account lookups. Users register with `"john@example.com"` via the mobile app, but the web portal trims input fields while the mobile app does not. The database ends up with `"john@example.com"` and `" john@example.com"` (leading space) as two separate rows. The customer has two accounts, split loyalty points, and two copies of every marketing email. Support tickets spike after each campaign.

## The Question
> Leading and trailing whitespace is invisible in most query result displays but is detected by string comparison. A value with a leading space does not equal the same value without it, breaking lookups, deduplication, and FK joins.
> **"Find all Customers where Email, FirstName, or LastName has leading or trailing whitespace — where the stored value differs from its trimmed version."**

## Table Reference
**Customers** — `schemas/01_Customers.csv`

## Solution Query

```sql
-- Step 1: Detect leading or trailing whitespace by comparing to trimmed version
SELECT
    CustomerID,
    FirstName,
    LastName,
    Email,
    CASE WHEN FirstName <> LTRIM(RTRIM(FirstName)) THEN 'Y' ELSE 'N' END AS FirstNameHasWhitespace,
    CASE WHEN LastName  <> LTRIM(RTRIM(LastName))  THEN 'Y' ELSE 'N' END AS LastNameHasWhitespace,
    CASE WHEN Email     <> LTRIM(RTRIM(Email))     THEN 'Y' ELSE 'N' END AS EmailHasWhitespace
FROM Customers
WHERE FirstName <> LTRIM(RTRIM(FirstName))
   OR LastName  <> LTRIM(RTRIM(LastName))
   OR Email     <> LTRIM(RTRIM(Email));

-- Step 2: Distinguish leading vs trailing whitespace
SELECT
    CustomerID,
    Email,
    LEN(Email)                          AS StoredLength,
    LEN(LTRIM(RTRIM(Email)))            AS TrimmedLength,
    LEN(Email) - LEN(LTRIM(Email))      AS LeadingSpaces,
    LEN(Email) - LEN(RTRIM(Email))      AS TrailingSpaces,
    CASE
        WHEN LEN(Email) - LEN(LTRIM(Email)) > 0
             AND LEN(Email) - LEN(RTRIM(Email)) > 0 THEN 'Both leading and trailing spaces'
        WHEN LEN(Email) - LEN(LTRIM(Email)) > 0     THEN 'Leading spaces only'
        WHEN LEN(Email) - LEN(RTRIM(Email)) > 0     THEN 'Trailing spaces only'
        ELSE 'No whitespace padding'
    END AS WhitespaceLocation
FROM Customers
WHERE Email IS NOT NULL
  AND Email <> LTRIM(RTRIM(Email));

-- Step 3: Detect non-breaking spaces and tab characters (not caught by LTRIM/RTRIM)
SELECT
    CustomerID,
    Email,
    CASE
        WHEN Email LIKE '%' + CHAR(160) + '%'   THEN 'Contains non-breaking space (CHAR 160)'
        WHEN Email LIKE '%' + CHAR(9) + '%'     THEN 'Contains tab character (CHAR 9)'
        WHEN Email LIKE '%' + CHAR(13) + '%'    THEN 'Contains carriage return (CHAR 13)'
        WHEN Email LIKE '%' + CHAR(10) + '%'    THEN 'Contains line feed (CHAR 10)'
        ELSE 'No hidden control characters'
    END AS HiddenCharCheck
FROM Customers
WHERE Email IS NOT NULL
  AND (Email LIKE '%' + CHAR(160) + '%'
    OR Email LIKE '%' + CHAR(9)   + '%'
    OR Email LIKE '%' + CHAR(13)  + '%'
    OR Email LIKE '%' + CHAR(10)  + '%');

-- Step 4: Find pairs that are duplicates only when trimmed
SELECT
    a.CustomerID AS Customer1,
    b.CustomerID AS Customer2,
    a.Email AS Email1,
    b.Email AS Email2,
    'Duplicate after trimming' AS Issue
FROM Customers a
JOIN Customers b
    ON a.CustomerID < b.CustomerID
    AND LTRIM(RTRIM(LOWER(a.Email))) = LTRIM(RTRIM(LOWER(b.Email)))
WHERE a.Email <> b.Email;  -- they differ as stored but match when trimmed

-- Step 5: Fix preview — show corrected values
SELECT
    CustomerID,
    Email AS CurrentEmail,
    LTRIM(RTRIM(Email)) AS CorrectedEmail,
    FirstName AS CurrentFirstName,
    LTRIM(RTRIM(FirstName)) AS CorrectedFirstName
FROM Customers
WHERE Email <> LTRIM(RTRIM(Email))
   OR FirstName <> LTRIM(RTRIM(FirstName));
```

## Expected Output

**Step 2 — Whitespace details:**
| CustomerID | Email | StoredLength | TrimmedLength | LeadingSpaces | TrailingSpaces | WhitespaceLocation |
|---|---|---|---|---|---|---|
| 5 | " john@example.com" | 18 | 17 | 1 | 0 | Leading spaces only |
| 11 | "sarah@example.com " | 19 | 18 | 0 | 1 | Trailing spaces only |

**Step 4 — Trimmed duplicates:**
| Customer1 | Customer2 | Email1 | Email2 | Issue |
|---|---|---|---|---|
| 1 | 5 | john@example.com | " john@example.com" | Duplicate after trimming |

## Explanation

**`value <> LTRIM(RTRIM(value))` as the whitespace test**
If a string has leading or trailing spaces, removing them changes its length. The comparison `Email <> LTRIM(RTRIM(Email))` is NULL-safe in this direction (a NULL Email won't match) and is the standard SQL Server pattern for whitespace detection.

**LEN vs DATALENGTH for whitespace counting**
`LEN()` ignores trailing spaces — `LEN('abc ')` returns 3. `DATALENGTH()` returns the byte count including trailing spaces. Use `DATALENGTH(Email)/2 - LEN(Email)` (for NVARCHAR, divide by 2 for byte-to-char) to count trailing spaces precisely.

**Non-breaking spaces (CHAR 160) are invisible to LTRIM/RTRIM**
`LTRIM` and `RTRIM` only remove ASCII space (CHAR 32). The non-breaking space (CHAR 160, `&nbsp;` in HTML) is not trimmed by these functions. It is visually identical to a regular space but causes string comparison failures. Step 3 detects these hidden characters.

**The trimmed-duplicate problem**
Step 4 finds records that are effectively duplicates once whitespace is removed. This is the root cause of the split-account scenario: two records with different stored values that represent the same entity. The fix is to trim first and then deduplicate, not the other way around.

## Severity
**High** — Whitespace padding causes silent identity mismatches in case-sensitive string comparisons, breaks deduplication, splits loyalty accounts, and causes FK join failures when the FK column has a space that the parent row doesn't. Trailing spaces are particularly dangerous because they are invisible in most query tools.
