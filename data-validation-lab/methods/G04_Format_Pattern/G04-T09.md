# G04-T09 — Format/Pattern | Currency Amount Format

## ID
G04-T09

## Group
4 — Format/Pattern

## Type
Currency Amount Format — Decimal Places, Sign, and Precision

## Live Scenario
A multi-currency accounting system receives transaction feeds from three payment processors. Processor A sends amounts as `19.99`, Processor B sends them as `1999` (in minor units — pence/cents), and Processor C sends them as `19.990000` (6 decimal places). All three are loaded into the same `Amount` column. The accounting reconciliation totals for Processor B are 100× too high because the minor-unit amounts were never converted. The 6-decimal-place amounts create precision noise in financial reports that should show 2 decimal places.

## The Question
> Currency amounts must conform to the currency's decimal precision (GBP and USD use 2 decimal places; JPY uses 0; some crypto currencies use 8+). Values with the wrong precision, wrong sign, or suspiciously large magnitudes indicate format or unit errors.
> **"Find all Transactions where the Amount does not have exactly 2 decimal places (as expected for GBP/USD transactions), where the Amount is negative when it should be positive, or where the Amount has more than 6 digits before the decimal point (suggesting a minor-unit import error)."**

## Table Reference
**Transactions** — `schemas/05_Transactions.csv`

## Solution Query

```sql
-- Step 1: Check decimal places in Amount
SELECT
    TransactionID,
    Amount,
    CASE
        WHEN Amount IS NULL                                             THEN 'NULL'
        WHEN CHARINDEX('.', CAST(Amount AS VARCHAR(30))) = 0           THEN 'No decimal point — whole number'
        WHEN LEN(CAST(Amount AS VARCHAR(30)))
             - CHARINDEX('.', CAST(Amount AS VARCHAR(30))) > 2         THEN 'More than 2 decimal places'
        WHEN LEN(CAST(Amount AS VARCHAR(30)))
             - CHARINDEX('.', CAST(Amount AS VARCHAR(30))) < 2         THEN 'Fewer than 2 decimal places'
        ELSE 'Correct 2 decimal places'
    END AS DecimalCheck
FROM Transactions
WHERE Amount IS NOT NULL;

-- Step 2: Flag suspected minor-unit amounts (value >= 100x expected range)
SELECT
    TransactionID,
    Amount,
    Currency,
    CASE
        WHEN Amount > 100000 AND Currency IN ('GBP', 'USD', 'EUR')
             THEN 'Amount exceeds £/$/€100,000 — possible minor-unit import (pence/cents)?'
        WHEN Amount < 0
             THEN 'Negative amount — refund or data entry error?'
        WHEN Amount = 0
             THEN 'Zero amount — intentional or missing value?'
        ELSE 'Amount within plausible range'
    END AS AmountPlausibility
FROM Transactions
WHERE Amount <= 0 OR Amount > 100000;

-- Step 3: Precision audit — how many decimal places does each amount actually have?
SELECT
    TransactionID,
    Amount,
    CASE
        WHEN CHARINDEX('.', CAST(Amount AS VARCHAR(30))) = 0
             THEN 0
        ELSE LEN(CAST(Amount AS VARCHAR(30))) - CHARINDEX('.', CAST(Amount AS VARCHAR(30)))
    END AS ActualDecimalPlaces,
    Currency
FROM Transactions
WHERE Amount IS NOT NULL
ORDER BY ActualDecimalPlaces DESC;

-- Step 4: Rounding check — does the amount round to itself at 2dp?
SELECT
    TransactionID,
    Amount,
    ROUND(Amount, 2) AS RoundedAmount,
    CASE
        WHEN Amount <> ROUND(Amount, 2) THEN 'Precision beyond 2dp — rounding will change value'
        ELSE 'OK — 2dp or fewer'
    END AS RoundingImpact
FROM Transactions
WHERE Amount IS NOT NULL
  AND Amount <> ROUND(Amount, 2);

-- Step 5: Currency-specific precision rules
SELECT
    Currency,
    COUNT(*) AS TransactionCount,
    SUM(CASE
        WHEN Currency = 'JPY' AND Amount <> FLOOR(Amount) THEN 1
        WHEN Currency IN ('GBP','USD','EUR')
             AND Amount <> ROUND(Amount, 2)               THEN 1
        ELSE 0
    END) AS PrecisionViolations
FROM Transactions
WHERE Amount IS NOT NULL
GROUP BY Currency;
```

## Explanation

**Minor-unit vs major-unit amounts**
Many payment APIs return amounts in minor units (pence, cents) — `£19.99` becomes `1999`. SQL has no way to know which convention was used. Detecting suspiciously large amounts relative to the expected range (Step 2) flags potential minor-unit imports. The fix requires knowing which processor used which convention and dividing by 100 for currency with 2 decimal places.

**CHARINDEX('.', CAST(Amount AS VARCHAR)) for decimal place count**
`LEN(string) - CHARINDEX('.', string)` gives the number of characters after the decimal point. If CHARINDEX returns 0 (no dot), the number is a whole number with 0 decimal places.

**ROUND(Amount, 2) as a precision test**
`Amount <> ROUND(Amount, 2)` identifies any value that would be changed by rounding to 2 decimal places. This catches amounts stored with more precision than the currency supports, which may indicate a unit conversion error or a precision mismatch between source and target systems.

**Currency-specific rules**
JPY has 0 decimal places — any non-integer JPY amount is wrong. BHD (Bahraini Dinar) uses 3 decimal places. Cryptocurrency uses up to 8. Apply the correct precision rule per currency from a reference table.

## Severity
**High** — Currency precision errors cause reconciliation failures, incorrect financial statements, and payment processing rejections. A 100× magnitude error (minor vs major units) is a critical financial reporting error that can trigger regulatory investigation.
