# G04-T14 — Format/Pattern | Special Character / Control Character in Text Field

## ID
G04-T14

## Group
4 — Format/Pattern

## Type
Special Character / Control Character in Text Field

## Live Scenario
A product description feed from an e-commerce platform is imported via CSV. Descriptions are HTML-stripped before storage. Some descriptions were originally rich text and the stripping process failed partially — the `Description` column ends up containing HTML entities (`&amp;`, `&lt;`), raw HTML tags (`<b>`, `</div>`), control characters from a Word document paste (CHAR 1–31), emoji (when the column is VARCHAR not NVARCHAR), and BOM characters (Byte Order Mark, CHAR 65279) at the start of some rows. The mobile app renders these as garbled text.

## The Question
> Text fields that are displayed to end users should contain only printable characters in the expected encoding. Control characters, HTML remnants, and invisible special characters cause rendering failures and data quality issues.
> **"Find all Products where the Description column contains HTML tags (< or > characters), HTML entities (&amp;), control characters (ASCII 0–31), or starts with a BOM character."**

## Table Reference
**Products** — `schemas/03_Products.csv`

## Solution Query

```sql
-- Step 1: Detect HTML remnants in description fields
SELECT
    ProductID,
    ProductName,
    LEFT(Description, 100) AS DescriptionPreview,
    CASE
        WHEN Description LIKE '%<%' AND Description LIKE '%>%'   THEN 'Contains HTML tags (< >)'
        WHEN Description LIKE '%&amp;%'
          OR Description LIKE '%&lt;%'
          OR Description LIKE '%&gt;%'
          OR Description LIKE '%&nbsp;%'
          OR Description LIKE '%&#%'                             THEN 'Contains HTML entities'
        ELSE 'No HTML detected'
    END AS HTMLCheck
FROM Products
WHERE Description IS NOT NULL
  AND (Description LIKE '%<%'
    OR Description LIKE '%&amp;%'
    OR Description LIKE '%&lt;%'
    OR Description LIKE '%&#%');

-- Step 2: Detect control characters (CHAR 0 through CHAR 31, excluding CHAR 9, 10, 13)
-- CHAR 9 = tab, CHAR 10 = LF, CHAR 13 = CR — sometimes intentional in multiline text
SELECT
    ProductID,
    Description,
    CASE
        WHEN PATINDEX('%[' + CHAR(1) + '-' + CHAR(8)  + ']%', Description) > 0 THEN 'CHAR 1-8 (control)'
        WHEN Description LIKE '%' + CHAR(11) + '%'                              THEN 'CHAR 11 (vertical tab)'
        WHEN Description LIKE '%' + CHAR(12) + '%'                              THEN 'CHAR 12 (form feed)'
        WHEN PATINDEX('%[' + CHAR(14) + '-' + CHAR(31) + ']%', Description) > 0 THEN 'CHAR 14-31 (control)'
        WHEN Description LIKE '%' + CHAR(0) + '%'                               THEN 'CHAR 0 (null byte)'
        ELSE 'No control characters'
    END AS ControlCharCheck
FROM Products
WHERE Description IS NOT NULL
  AND (Description LIKE '%' + CHAR(0)  + '%'
    OR Description LIKE '%' + CHAR(11) + '%'
    OR Description LIKE '%' + CHAR(12) + '%'
    OR PATINDEX('%[' + CHAR(1) + '-' + CHAR(8) + ']%', Description) > 0);

-- Step 3: Detect BOM (Byte Order Mark) at start of field
-- UTF-8 BOM = EF BB BF; in NVARCHAR it appears as NCHAR(65279)
SELECT
    ProductID,
    Description,
    ASCII(LEFT(Description, 1)) AS FirstCharASCII,
    CASE
        WHEN LEFT(Description, 1) = NCHAR(65279)   THEN 'Starts with BOM character'
        WHEN ASCII(LEFT(Description, 1)) < 32       THEN 'Starts with control character'
        ELSE 'OK'
    END AS BOMLead
FROM Products
WHERE Description IS NOT NULL
  AND (LEFT(Description, 1) = NCHAR(65279)
    OR ASCII(LEFT(Description, 1)) < 32);

-- Step 4: Detect double-encoded HTML entities (entity encoded twice)
SELECT
    ProductID,
    Description,
    'Double-encoded HTML entity detected' AS Issue
FROM Products
WHERE Description LIKE '%&amp;amp;%'   -- &amp; encoded again
   OR Description LIKE '%&amp;lt;%'
   OR Description LIKE '%&amp;gt;%';

-- Step 5: Summary of contamination types
SELECT
    CASE
        WHEN Description LIKE '%<%' AND Description LIKE '%>%'  THEN 'HTML tags'
        WHEN Description LIKE '%&amp;%' OR Description LIKE '%&#%' THEN 'HTML entities'
        WHEN LEFT(Description,1) = NCHAR(65279)                 THEN 'BOM'
        WHEN PATINDEX('%[' + CHAR(1) + '-' + CHAR(31) + ']%', Description) > 0 THEN 'Control chars'
        ELSE 'Clean'
    END AS ContaminationType,
    COUNT(*) AS ProductCount
FROM Products
WHERE Description IS NOT NULL
GROUP BY
    CASE
        WHEN Description LIKE '%<%' AND Description LIKE '%>%'  THEN 'HTML tags'
        WHEN Description LIKE '%&amp;%' OR Description LIKE '%&#%' THEN 'HTML entities'
        WHEN LEFT(Description,1) = NCHAR(65279)                 THEN 'BOM'
        WHEN PATINDEX('%[' + CHAR(1) + '-' + CHAR(31) + ']%', Description) > 0 THEN 'Control chars'
        ELSE 'Clean'
    END
ORDER BY ProductCount DESC;
```

## Explanation

**Why PATINDEX with CHAR() is needed for control character detection**
SQL Server's LIKE operator cannot use `[CHAR(1)-CHAR(8)]` range syntax directly with character literals — the CHAR function must be used to build the pattern string. `PATINDEX('%[' + CHAR(1) + '-' + CHAR(8) + ']%', col)` constructs a pattern at runtime that matches any character in that ASCII range.

**BOM (Byte Order Mark) causes invisible prefix issues**
The BOM (U+FEFF) is a zero-width character that appears at the start of some Unicode files to declare encoding. When imported into SQL Server, it becomes the first character of the first field in the first row. It is invisible in most query tools but breaks exact string matching: `'Widget A'` ≠ `'﻿Widget A'`.

**Double-encoded entities indicate two-pass HTML encoding**
`&amp;amp;` means `&amp;` was HTML-encoded a second time. This happens when an HTML-encoding function is applied to already-encoded text. The symptom in the rendered UI is the entity text appearing literally (the page shows `&amp;` instead of `&`).

**Control characters (CHAR 0–31) come from multiple sources**
Null bytes (CHAR 0) come from binary field exports. Vertical tabs and form feeds (CHAR 11, 12) come from Word/PDF copy-paste. Control chars 1–8 come from legacy system exports. All must be stripped or rejected before storage in user-facing text fields.

## Severity
**Medium** — Special characters cause rendering failures in web and mobile UIs, break XML/JSON exports, and introduce security risks (stored XSS if HTML tags are not properly escaped in downstream rendering). Control characters cause CSV/TSV parsing failures and may corrupt binary protocols.
