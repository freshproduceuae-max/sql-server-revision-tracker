# G04-T16 — Format/Pattern | Gender / Enumerated Field Format

## ID
G04-T16

## Group
4 — Format/Pattern

## Type
Enumerated Field Format — Values Outside Permitted Set

## Live Scenario
An HR system stores employee gender in a VARCHAR(10) column with an expected set of `'M'`, `'F'`, `'NB'` (non-binary), and `'U'` (undisclosed). Data arrives from three source systems: the legacy HR tool uses `'Male'`/`'Female'`, the new self-service portal uses `'M'`/`'F'`/`'NB'`, and an imported spreadsheet uses `'1'`/`'2'`/`'3'`. The diversity reporting tool queries `WHERE Gender IN ('M','F','NB','U')` and miscounts by 40% because `'Male'` and `'Female'` are excluded.

## The Question
> Enumerated (categorical) columns should contain only values from a defined permitted set. Any value outside that set is a format violation, regardless of whether it is semantically similar to a valid value.
> **"Find all Employees where the Department column contains a value not in the approved list, and classify each violation by what value was used."**

## Table Reference
**Employees** — `schemas/04_Employees.csv`

## Solution Query

```sql
-- Step 1: Validate Department against approved list
DECLARE @ApprovedDepts TABLE (DeptName VARCHAR(50));
INSERT INTO @ApprovedDepts VALUES
    ('Sales'), ('Marketing'), ('Engineering'),
    ('Finance'), ('HR'), ('Operations'), ('Legal');

SELECT
    e.EmployeeID,
    e.FullName,
    e.Department,
    CASE
        WHEN e.Department IS NULL                           THEN 'NULL — no department assigned'
        WHEN e.Department NOT IN (SELECT DeptName FROM @ApprovedDepts)
                                                            THEN 'Invalid: "' + e.Department + '" not in approved list'
        ELSE 'Valid'
    END AS DeptValidation
FROM Employees e
WHERE e.Department IS NULL
   OR e.Department NOT IN (SELECT DeptName FROM @ApprovedDepts);

-- Step 2: Profile all distinct Department values (find the full contamination picture)
SELECT
    Department,
    COUNT(*) AS EmployeeCount,
    CASE
        WHEN Department IN ('Sales','Marketing','Engineering','Finance','HR','Operations','Legal')
             THEN 'Approved'
        WHEN Department IS NULL
             THEN 'NULL'
        ELSE 'Not in approved list'
    END AS ApprovalStatus
FROM Employees
GROUP BY Department
ORDER BY ApprovalStatus, Department;

-- Step 3: Nearest-match suggestion (which approved value does the invalid one most resemble?)
SELECT
    e.EmployeeID,
    e.Department AS EnteredValue,
    a.DeptName AS SuggestedCorrection,
    DIFFERENCE(e.Department, a.DeptName) AS SoundexSimilarity   -- 4 = highest
FROM Employees e
CROSS JOIN @ApprovedDepts a
WHERE e.Department NOT IN (SELECT DeptName FROM @ApprovedDepts)
  AND e.Department IS NOT NULL
  AND DIFFERENCE(e.Department, a.DeptName) >= 3   -- show plausible matches only
ORDER BY e.EmployeeID, SoundexSimilarity DESC;

-- Step 4: Case-insensitive version of the check (catches 'sales', 'SALES')
SELECT
    EmployeeID,
    Department,
    'Department is valid but wrong case — normalise to Title Case' AS Issue
FROM Employees
WHERE LOWER(Department) IN ('sales','marketing','engineering','finance','hr','operations','legal')
  AND Department NOT IN ('Sales','Marketing','Engineering','Finance','HR','Operations','Legal');

-- Step 5: Full enumeration health check across multiple flag columns
SELECT
    'Department'   AS ColumnName,
    Department     AS Value,
    COUNT(*)       AS Count
FROM Employees
WHERE Department NOT IN ('Sales','Marketing','Engineering','Finance','HR','Operations','Legal')
   OR Department IS NULL
GROUP BY Department

UNION ALL

SELECT
    'EmploymentType',
    EmploymentType,
    COUNT(*)
FROM Employees
WHERE EmploymentType NOT IN ('Full-Time','Part-Time','Contract','Intern')
   OR EmploymentType IS NULL
GROUP BY EmploymentType

ORDER BY ColumnName, Count DESC;
```

## Expected Output

**Step 1 — Department violations:**
| EmployeeID | FullName | Department | DeptValidation |
|---|---|---|---|
| E003 | Tom Baker | IT | Invalid: "IT" not in approved list |
| E009 | Sarah Park | engineering | Invalid: "engineering" not in approved list |
| E014 | Mike Ross | NULL | NULL — no department assigned |

**Step 2 — Profile:**
| Department | EmployeeCount | ApprovalStatus |
|---|---|---|
| Sales | 8 | Approved |
| Engineering | 5 | Approved |
| IT | 2 | Not in approved list |
| engineering | 1 | Not in approved list |

## Explanation

**Approved list as a table variable vs hard-coded IN list**
Using a table variable (`@ApprovedDepts`) separates the approved values from the validation logic. This makes the query easier to maintain — add or remove approved values in one place without touching the WHERE clause. In production, move the approved list to a permanent reference table.

**Profile first, then validate**
Step 2 shows all distinct values before filtering. This reveals the full picture: how many records use each value, and which exact strings are invalid. Without profiling, you might fix `'IT'` but miss `'Information Technology'`.

**SOUNDEX/DIFFERENCE for nearest-match suggestions**
Step 3 uses `DIFFERENCE()` to find which approved department name sounds most like each invalid entry. `DIFFERENCE('engineering', 'Engineering')` = 4 (maximum — same phonetic code) because SOUNDEX is case-insensitive. This helps data stewards map invalid values to corrections without guessing.

**Case as a separate violation**
`'sales'` and `'Sales'` are not in the approved list if the database is case-sensitive. Step 4 separates wrong-case from semantically wrong values — these need different fixes (UPDATE with correct case vs manual review).

**Enumerated columns should use a CHECK constraint**
The long-term fix is `ALTER TABLE Employees ADD CONSTRAINT chk_Department CHECK (Department IN ('Sales','Marketing','Engineering','Finance','HR','Operations','Legal'))`. This prevents future invalid values at the database level.

## Severity
**High** — Invalid enumerated values cause incorrect aggregations and filtering. A report counting headcount by department silently undercounts departments where the name is spelled differently. In HR and compliance reporting, this can misrepresent workforce composition data.
