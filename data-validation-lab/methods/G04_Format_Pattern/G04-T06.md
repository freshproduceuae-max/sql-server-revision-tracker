# G04-T06 — Format/Pattern | IBAN / Bank Account Number Format

## ID
G04-T06

## Group
4 — Format/Pattern

## Type
IBAN / Bank Account Number Format Validation

## Live Scenario
A fintech platform processes international bank transfers. The BankAccountNumber column stores IBANs from customers across 30 countries. Data entry staff copy IBANs from paper forms. The column contains: correctly formatted IBANs (`GB29NWBK60161331926819`), IBANs with spaces (`GB29 NWBK 6016 1331 9268 19`), IBANs with wrong country prefix length (`GB2NWBK60161331926819`), non-IBAN account numbers (`12345678`), and placeholder text (`"TO BE CONFIRMED"`). The payment processor rejects 12% of transfers with "invalid account format."

## The Question
> IBANs have a country-specific structure: 2-letter country code + 2 check digits + BBAN (Basic Bank Account Number). The total length and character pattern vary by country (GB = 22 chars, DE = 22, FR = 27, etc.).
> **"Find all Transactions where the BankAccountNumber does not match a valid IBAN structural pattern — check for the 2-letter country prefix, 2 numeric check digits, and expected character length for common country codes."**

## Table Reference
**Transactions** — `schemas/05_Transactions.csv`

## Solution Query

```sql
-- Step 1: Remove spaces and uppercase (normalise before validation)
-- Then check structural rules for common IBAN country codes

SELECT
    TransactionID,
    BankAccountNumber,
    REPLACE(UPPER(BankAccountNumber), ' ', '') AS NormalisedIBAN,
    CASE
        WHEN BankAccountNumber IS NULL                                          THEN 'NULL'
        WHEN LEN(REPLACE(UPPER(BankAccountNumber), ' ', '')) < 15              THEN 'Too short for any IBAN'
        WHEN LEN(REPLACE(UPPER(BankAccountNumber), ' ', '')) > 34              THEN 'Too long for any IBAN'
        WHEN REPLACE(UPPER(BankAccountNumber), ' ', '') NOT LIKE '[A-Z][A-Z][0-9][0-9]%'
                                                                                THEN 'Missing 2-letter country code + 2 digits'
        -- UK IBAN: GB + 2 digits + 4 letters + 14 digits = 22 chars
        WHEN LEFT(REPLACE(UPPER(BankAccountNumber), ' ', ''), 2) = 'GB'
             AND LEN(REPLACE(UPPER(BankAccountNumber), ' ', '')) <> 22         THEN 'UK IBAN must be 22 chars'
        -- German IBAN: DE + 2 digits + 18 digits = 22 chars
        WHEN LEFT(REPLACE(UPPER(BankAccountNumber), ' ', ''), 2) = 'DE'
             AND LEN(REPLACE(UPPER(BankAccountNumber), ' ', '')) <> 22         THEN 'DE IBAN must be 22 chars'
        -- French IBAN: FR + 2 digits + 23 alphanumeric = 27 chars
        WHEN LEFT(REPLACE(UPPER(BankAccountNumber), ' ', ''), 2) = 'FR'
             AND LEN(REPLACE(UPPER(BankAccountNumber), ' ', '')) <> 27         THEN 'FR IBAN must be 27 chars'
        WHEN REPLACE(UPPER(BankAccountNumber), ' ', '') LIKE '%[^A-Z0-9]%'    THEN 'Contains invalid characters'
        ELSE 'Structural check passed'
    END AS IBANCheck
FROM Transactions
WHERE BankAccountNumber IS NOT NULL;

-- Step 2: Check digits validation approximation (mod-97 rule)
-- Rearrange: move first 4 chars to end, convert letters to numbers (A=10, B=11 ... Z=35)
-- Then check if result MOD 97 = 1
-- SQL Server cannot natively compute MOD on a 34-digit integer, so we use a simplified structural flag

SELECT
    TransactionID,
    BankAccountNumber,
    LEFT(REPLACE(UPPER(BankAccountNumber), ' ', ''), 2) AS CountryCode,
    SUBSTRING(REPLACE(UPPER(BankAccountNumber), ' ', ''), 3, 2) AS CheckDigits,
    LEN(REPLACE(UPPER(BankAccountNumber), ' ', ''))             AS IBANLength
FROM Transactions
WHERE BankAccountNumber IS NOT NULL
  AND REPLACE(UPPER(BankAccountNumber), ' ', '') LIKE '[A-Z][A-Z][0-9][0-9]%';

-- Step 3: Flag non-IBAN account numbers (only digits, no country prefix)
SELECT
    TransactionID,
    BankAccountNumber,
    CASE
        WHEN BankAccountNumber LIKE '[0-9]%'
             AND BankAccountNumber NOT LIKE '%[A-Z]%'           THEN 'Looks like domestic account number, not IBAN'
        WHEN BankAccountNumber LIKE '%[A-Za-z]%'
             AND BankAccountNumber NOT LIKE '[A-Z][A-Z][0-9][0-9]%' THEN 'Letters present but no country-code prefix'
        ELSE 'Pattern consistent with IBAN structure'
    END AS AccountFormatType
FROM Transactions
WHERE BankAccountNumber IS NOT NULL;

-- Step 4: Summary of IBAN validation results
SELECT
    LEFT(REPLACE(UPPER(BankAccountNumber), ' ', ''), 2) AS CountryCode,
    COUNT(*) AS TotalTransactions,
    SUM(CASE WHEN LEN(REPLACE(UPPER(BankAccountNumber),' ','')) < 15
                  OR LEN(REPLACE(UPPER(BankAccountNumber),' ','')) > 34 THEN 1 ELSE 0 END) AS LengthViolations
FROM Transactions
WHERE BankAccountNumber IS NOT NULL
GROUP BY LEFT(REPLACE(UPPER(BankAccountNumber), ' ', ''), 2)
ORDER BY TotalTransactions DESC;
```

## Explanation

**IBAN structure: country code + check digits + BBAN**
Every IBAN starts with a 2-letter ISO country code and 2 numeric check digits. The BBAN (Basic Bank Account Number) length and format varies by country. The full IBAN length ranges from 15 chars (Norway) to 34 chars (Malta).

**Why the mod-97 check isn't directly implementable in SQL**
The IBAN check digit algorithm (ISO 7064, MOD 97-10) requires converting letters to 2-digit numbers (A=10, Z=35), rearranging the string, and computing the 34-digit result modulo 97. SQL Server integers overflow at 19 digits, so this requires a CLR function, a multi-step string conversion, or an application-layer validator. SQL handles structural checks; the mod-97 validation belongs in application code.

**Normalisation before validation**
IBANs are sometimes written with spaces for readability (`GB29 NWBK 6016 1331 9268 19`). Remove spaces and uppercase the string before any structural check. Always validate the normalised form, not the raw input.

**Country-specific length as the primary structural check**
The most reliable structural test is: does the normalised IBAN length match the expected length for its declared country code? Maintain a reference table of country codes and expected IBAN lengths for complete validation.

## Severity
**High** — Invalid IBANs cause payment rejections, delayed transfers, and manual investigation costs. In high-volume payment processing, even a 1% invalid rate means thousands of failed transactions per day.
