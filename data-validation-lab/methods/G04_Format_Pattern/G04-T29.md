# G04-T29 — Format/Pattern | Mixed Language / Encoding Artifact

## ID

## Group

## Type
Mixed Language / Encoding Artifact — Mojibake and Character Substitution

## Live Scenario
A global retail platform serves customers in 35 countries. Customer names and addresses are stored in NVARCHAR columns. A regional ETL job incorrectly converts data from UTF-8 to Latin-1 before loading. The result is that `"Müller"` becomes `"MÃ¼ller"` (UTF-8 bytes interpreted as Latin-1) — a classic mojibake encoding corruption. Similarly, `"Søren"` becomes `"SÃ¸ren"` and `"Ångström"` becomes `"Ã…ngstrÃ¶m"`. Customer communications addressed to `"MÃ¼ller"` trigger spam filter blocks and customer complaints. Name matching across systems fails because the same customer has different representations.

## The Question
> Encoding artifacts (mojibake) occur when a string encoded in one character set is decoded using a different one. In SQL Server, common signs are multi-byte UTF-8 sequences appearing as `Ã` + a second character, replacement characters (NCHAR(65533), shown as `?`), or `?` substitutions for non-ASCII characters.
> **"Find all Customers where FirstName or LastName contains encoding artifact patterns — specifically the UTF-8-as-Latin-1 sequence `Ã` followed by another character, or the replacement character (U+FFFD)."**

## Explanation

**Mojibake: how UTF-8 bytes look when read as Latin-1**
UTF-8 encodes non-ASCII characters as 2–4 bytes. When those bytes are read as Latin-1 (ISO-8859-1), each byte is treated as a separate character. The German `ü` (UTF-8: `0xC3 0xBC`) becomes `Ã¼` in Latin-1 (`0xC3` = `Ã`, `0xBC` = `¼`). The pattern `Ã` appearing in names is a strong indicator of this exact encoding error.

**Unicode replacement character NCHAR(65533)**
`U+FFFD` (`NCHAR(65533)`) is the Unicode standard replacement character — it appears when a byte sequence cannot be decoded. SQL Server may substitute it when converting VARCHAR → NVARCHAR if the source encoding is misspecified. A `?` character in a name usually indicates the same issue in older codepage-based systems.

**Fix: re-encode at the source, not in SQL**
Fixing mojibake in SQL requires knowing the exact original encoding, which is difficult to infer reliably. The correct fix is to re-extract the data from the source system using the correct encoding (UTF-8) and re-import. SQL string functions cannot reliably un-mojibake text because the original byte sequence information is lost.

**Detection vs remediation**
These queries detect encoding artifacts. Remediation in SQL is limited to known patterns (e.g., a `REPLACE(FirstName, 'Ã¼', 'ü')` for German ü). For systemic encoding errors across many languages, fix at the ETL layer — add `WITH (CODEPAGE = '65001')` to the BULK INSERT or `FORMAT = 'CSV', CODEPAGE = 'UTF-8'` to the import configuration.

## Severity
**High** — Encoding artifacts corrupt customer names and addresses, breaking communication, legal document generation, and identity verification. In GDPR contexts, storing data in a corrupted form that misrepresents the subject's name is a data quality compliance issue.
