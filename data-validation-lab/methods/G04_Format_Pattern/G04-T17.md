# G04-T17 — Format/Pattern | Time Format Validation

## ID
G04-T17

## Group
4 — Format/Pattern

## Type
Time Format Validation — Invalid or Inconsistent Time Strings

## Live Scenario
A scheduling platform stores appointment times as VARCHAR(10) in a `StartTime` column. Input comes from three sources: the web app (24-hour format `14:30`), the iOS app (`2:30 PM`), and a legacy desktop client (`14.30`). A fourth source — a CSV import from a third-party clinic — uses `1430` (no separators). When the system tries to build the schedule, `TRY_CAST` converts some formats and silently returns NULL for others. Appointments with NULL parsed times are placed at midnight and double-booked with overnight cleaning slots.

## The Question
> Time strings must follow a consistent format (HH:MM, HH:MM:SS, or HH:MM AM/PM) and contain valid hour and minute values. A value like `25:61` or `14.30` cannot be converted to TIME.
> **"Find all Orders where the DeliveryTime column (stored as VARCHAR) cannot be converted to a TIME value, or contains a format that is ambiguous between 12-hour and 24-hour representation."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`

## Solution Query

```sql
-- Step 1: Attempt TIME conversion and flag failures
SELECT
    OrderID,
    DeliveryTime,
    TRY_CAST(DeliveryTime AS TIME) AS ParsedTime,
    CASE
        WHEN DeliveryTime IS NULL                           THEN 'NULL'
        WHEN TRY_CAST(DeliveryTime AS TIME) IS NULL         THEN 'Cannot convert to TIME'
        ELSE 'Converts OK'
    END AS ConversionCheck
FROM Orders
WHERE DeliveryTime IS NOT NULL
  AND TRY_CAST(DeliveryTime AS TIME) IS NULL;

-- Step 2: Detect format patterns in time strings
SELECT
    OrderID,
    DeliveryTime,
    CASE
        -- Standard 24-hour HH:MM or HH:MM:SS
        WHEN DeliveryTime LIKE '[0-2][0-9]:[0-5][0-9]'         THEN '24h HH:MM'
        WHEN DeliveryTime LIKE '[0-2][0-9]:[0-5][0-9]:[0-5][0-9]' THEN '24h HH:MM:SS'
        -- 12-hour with AM/PM
        WHEN DeliveryTime LIKE '[0-9]:[0-5][0-9] [AP]M'        THEN '12h H:MM AM/PM'
        WHEN DeliveryTime LIKE '[0-1][0-9]:[0-5][0-9] [AP]M'   THEN '12h HH:MM AM/PM'
        -- Dot separator
        WHEN DeliveryTime LIKE '[0-2][0-9].[0-5][0-9]'         THEN 'Dot separator (non-standard)'
        -- No separator (HHMM)
        WHEN DeliveryTime LIKE '[0-2][0-9][0-5][0-9]'          THEN 'No separator HHMM (non-standard)'
        ELSE 'Unknown/invalid format'
    END AS DetectedFormat
FROM Orders
WHERE DeliveryTime IS NOT NULL;

-- Step 3: Validate hour and minute ranges
SELECT
    OrderID,
    DeliveryTime,
    CASE
        WHEN DeliveryTime LIKE '[0-9][0-9]:[0-9][0-9]%'
             THEN CAST(LEFT(DeliveryTime, 2) AS INT)
        ELSE NULL
    END AS ParsedHour,
    CASE
        WHEN DeliveryTime LIKE '[0-9][0-9]:[0-9][0-9]%'
             THEN CAST(SUBSTRING(DeliveryTime, 4, 2) AS INT)
        ELSE NULL
    END AS ParsedMinute,
    CASE
        WHEN DeliveryTime LIKE '[0-9][0-9]:[0-9][0-9]%'
             AND CAST(LEFT(DeliveryTime, 2) AS INT) > 23    THEN 'Hour > 23'
        WHEN DeliveryTime LIKE '[0-9][0-9]:[0-9][0-9]%'
             AND CAST(SUBSTRING(DeliveryTime, 4, 2) AS INT) > 59 THEN 'Minute > 59'
        WHEN TRY_CAST(DeliveryTime AS TIME) IS NOT NULL     THEN 'Valid'
        ELSE 'Cannot parse'
    END AS RangeCheck
FROM Orders
WHERE DeliveryTime IS NOT NULL;

-- Step 4: Normalise all valid formats to HH:MM (24-hour)
SELECT
    OrderID,
    DeliveryTime AS OriginalTime,
    CASE
        -- Already valid HH:MM
        WHEN TRY_CAST(DeliveryTime AS TIME) IS NOT NULL
             AND DeliveryTime LIKE '[0-9][0-9]:[0-9][0-9]'
             THEN DeliveryTime
        -- Dot separator → colon
        WHEN DeliveryTime LIKE '[0-2][0-9].[0-5][0-9]'
             THEN REPLACE(DeliveryTime, '.', ':')
        -- HHMM → HH:MM
        WHEN DeliveryTime LIKE '[0-2][0-9][0-5][0-9]'
             THEN LEFT(DeliveryTime,2) + ':' + RIGHT(DeliveryTime,2)
        ELSE 'Cannot normalise'
    END AS NormalisedTime
FROM Orders
WHERE DeliveryTime IS NOT NULL;
```

## Expected Output

**Step 1 — Conversion failures:**
| OrderID | DeliveryTime | ConversionCheck |
|---|---|---|
| 1003 | 14.30 | Cannot convert to TIME |
| 1007 | 25:00 | Cannot convert to TIME |
| 1011 | 1430 | Cannot convert to TIME |

**Step 2 — Format detection:**
| OrderID | DeliveryTime | DetectedFormat |
|---|---|---|
| 1001 | 14:30 | 24h HH:MM |
| 1004 | 2:30 PM | 12h H:MM AM/PM |
| 1003 | 14.30 | Dot separator (non-standard) |
| 1011 | 1430 | No separator HHMM (non-standard) |

## Explanation

**`TRY_CAST(value AS TIME)` handles most standard formats**
SQL Server's TIME type parser accepts `HH:MM`, `HH:MM:SS`, `HH:MM:SS.nnn`, and 12-hour AM/PM formats. It rejects dot separators, no-separator HHMM format, and values with hours > 23 or minutes > 59. TRY_CAST is the primary filter; format detection (Step 2) explains WHY conversion failed.

**Hour 24 vs hour 0**
`24:00` is valid in some time standards (midnight at end of day) but SQL Server's TIME type does not accept it. If source systems use `24:00` as a valid end-of-day marker, it must be normalised to `00:00` before conversion.

**12-hour vs 24-hour ambiguity**
`12:30` in 12-hour format with no AM/PM could be noon or midnight. Always require AM/PM when accepting 12-hour time input. In 24-hour format, `12:30` is noon with no ambiguity.

**Normalisation approach in Step 4**
A CASE expression maps each detected format to a standardised HH:MM output. This produces a cleansing preview. The actual UPDATE should be run after verifying the mapping is correct for each format variant.

## Severity
**Medium** — Invalid time values cause scheduling failures, audit log corruption, and SLA calculation errors. In healthcare and transportation, incorrect appointment or departure times have direct safety and compliance implications.
