# G04-T10 — Format/Pattern | IP Address Format

## ID
G04-T10

## Group
4 — Format/Pattern

## Type
IP Address Format Validation (IPv4 and IPv6)

## Live Scenario
A security operations platform logs all authentication attempts with the source IP address. The `SourceIP` column is VARCHAR(45) — large enough for IPv6. Over two years it has accumulated: valid IPv4 (`192.168.1.1`), valid IPv6 (`2001:0db8:85a3::8a2e:0370:7334`), malformed IPv4 (`999.168.1.1`, `192.168.1`), IPv4 with a port appended (`192.168.1.1:8080`), IPv4 mapped to IPv6 (`::ffff:192.168.1.1`), and placeholder text (`"unknown"`, `"internal"`). The IP-to-country geolocation lookup fails for all malformed entries, producing NULL country codes in the threat intelligence report.

## The Question
> IPv4 addresses have exactly 4 octets (0–255) separated by dots. IPv6 addresses have up to 8 groups of 4 hex digits separated by colons. SQL LIKE can validate the structural pattern of IPv4; IPv6 validation is more complex due to the `::` shorthand.
> **"Find all log records where SourceIP is not a valid IPv4 address — specifically: wrong number of octets, octet values > 255, leading zeros in octets, or non-numeric characters in octets."**

## Table Reference
**Transactions** — `schemas/05_Transactions.csv` *(proxy — SourceIP field used for illustration)*

## Solution Query

```sql
-- Step 1: IPv4 format validation using LIKE pattern
-- Pattern: between 1-3 digits, dot, repeated 4 times (no dot at end)
SELECT
    TransactionID,
    SourceIP,
    CASE
        WHEN SourceIP IS NULL                                           THEN 'NULL'
        WHEN SourceIP LIKE '%[^0-9.]%'                                 THEN 'Contains non-numeric/non-dot chars'
        WHEN SourceIP NOT LIKE '%.%.%.%'                               THEN 'Not enough octets (need 3 dots)'
        WHEN SourceIP LIKE '%.%.%.%.%'                                 THEN 'Too many octets (> 3 dots)'
        WHEN SourceIP LIKE '.%' OR SourceIP LIKE '%.'                  THEN 'Leading or trailing dot'
        ELSE 'Structural pattern OK'
    END AS IPv4StructureCheck
FROM Transactions
WHERE SourceIP IS NOT NULL;

-- Step 2: Extract and validate each octet value (0-255)
-- Use PARSENAME which is designed for 4-part dotted strings
SELECT
    TransactionID,
    SourceIP,
    TRY_CAST(PARSENAME(SourceIP, 4) AS INT) AS Octet1,
    TRY_CAST(PARSENAME(SourceIP, 3) AS INT) AS Octet2,
    TRY_CAST(PARSENAME(SourceIP, 2) AS INT) AS Octet3,
    TRY_CAST(PARSENAME(SourceIP, 1) AS INT) AS Octet4,
    CASE
        WHEN PARSENAME(SourceIP, 4) IS NULL OR PARSENAME(SourceIP, 1) IS NULL
             THEN 'PARSENAME failed — not a 4-part IP'
        WHEN TRY_CAST(PARSENAME(SourceIP, 4) AS INT) NOT BETWEEN 0 AND 255
          OR TRY_CAST(PARSENAME(SourceIP, 3) AS INT) NOT BETWEEN 0 AND 255
          OR TRY_CAST(PARSENAME(SourceIP, 2) AS INT) NOT BETWEEN 0 AND 255
          OR TRY_CAST(PARSENAME(SourceIP, 1) AS INT) NOT BETWEEN 0 AND 255
             THEN 'Octet out of range (0-255)'
        ELSE 'Valid IPv4'
    END AS OctetRangeCheck
FROM Transactions
WHERE SourceIP IS NOT NULL
  AND SourceIP NOT LIKE '%:%';  -- exclude IPv6

-- Step 3: Flag private/reserved IP ranges that shouldn't appear in public traffic
SELECT
    TransactionID,
    SourceIP,
    CASE
        WHEN PARSENAME(SourceIP, 4) = '10'                             THEN 'Private: 10.x.x.x'
        WHEN PARSENAME(SourceIP, 4) = '172'
             AND TRY_CAST(PARSENAME(SourceIP, 3) AS INT) BETWEEN 16 AND 31
                                                                        THEN 'Private: 172.16-31.x.x'
        WHEN PARSENAME(SourceIP, 4) = '192'
             AND PARSENAME(SourceIP, 3) = '168'                        THEN 'Private: 192.168.x.x'
        WHEN PARSENAME(SourceIP, 4) = '127'                            THEN 'Loopback: 127.x.x.x'
        WHEN PARSENAME(SourceIP, 4) = '0'                              THEN 'Reserved: 0.x.x.x'
        WHEN PARSENAME(SourceIP, 4) = '255'                            THEN 'Broadcast: 255.x.x.x'
        ELSE 'Public IP'
    END AS IPClassification
FROM Transactions
WHERE SourceIP IS NOT NULL
  AND SourceIP NOT LIKE '%:%'
  AND SourceIP LIKE '%.%.%.%';

-- Step 4: IPv6 basic structural check
SELECT
    TransactionID,
    SourceIP,
    CASE
        WHEN SourceIP LIKE '%:%'                            -- contains colons = likely IPv6
             AND SourceIP NOT LIKE '%[^0-9A-Fa-f:.]%'     -- only hex, colons, dots (for mapped)
             THEN 'Possible IPv6 — validate separately'
        WHEN SourceIP LIKE '%:%'
             AND SourceIP LIKE '%[^0-9A-Fa-f:.]%'
             THEN 'IPv6 with invalid characters'
        ELSE 'Not IPv6'
    END AS IPv6Check
FROM Transactions
WHERE SourceIP LIKE '%:%';
```

## Explanation

**PARSENAME as an IPv4 parser**
`PARSENAME` is designed for four-part object names (`server.database.schema.table`) but works identically on dotted IP addresses. `PARSENAME('192.168.1.1', 4)` returns `'192'`; `PARSENAME(..., 1)` returns `'1'`. It returns NULL if there are not exactly 4 parts, making it a natural structural check.

**Why LIKE alone is not enough for IPv4**
`LIKE '%.%.%.%'` confirms four parts but doesn't check octet values. `192.168.999.1` passes the LIKE check but has an invalid octet. The combination of LIKE (structure) + PARSENAME + TRY_CAST (range) covers both.

**IPv6 validation complexity**
IPv6 has 8 groups of 4 hex digits but the `::` shorthand collapses consecutive zero groups. `2001:db8::1` is valid. Full IPv6 validation in pure SQL requires a multi-step CTE or a CLR function. Step 4 provides a minimal structural flag; complete validation belongs in application code.

**Private IP ranges in authentication logs**
Private IPs (`10.x`, `172.16–31.x`, `192.168.x`) should not appear as source IPs for internet-facing systems. If they do, it may indicate: a reverse proxy not forwarding the real IP, internal testing traffic, or a misconfigured logging pipeline.

## Severity
**Medium** — Invalid IPs cause geolocation failures and gaps in security audit trails. In regulated environments (PCI-DSS, SOC 2) where all access must be traceable to a source IP, missing or invalid IPs are an audit finding.
