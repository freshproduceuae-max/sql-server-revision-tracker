# G04-T32 — Format/Pattern | Free-Text Field with Embedded Structured Data

## ID
G04-T32

## Group
4 — Format/Pattern

## Type
Free-Text Field with Embedded Structured Data — Data Stored in Wrong Column

## Live Scenario
A helpdesk ticketing system has a `Notes` VARCHAR(MAX) column for free-form agent comments. Over three years, agents have started pasting structured data into this column because there was no dedicated field: `"Order #12345"`, `"Customer email: jane@example.com"`, `"Refund amount: £49.99"`, `"Tracking: 1Z999AA10123456784"`, `"DOB: 1985-03-15"`. A data analyst notices that 40% of Notes contain extractable order IDs and starts using CHARINDEX to mine them out. But the format is inconsistent — some say `"Order #"`, some say `"OrderID:"`, some just include the number inline. The data that belongs in structured columns has been buried in free text.

## The Question
> Free-text fields often accumulate structured data that should have been stored in dedicated columns. Detecting these patterns helps identify schema gaps and enables data extraction for migration.
> **"Find all Orders where the Notes column contains values that appear to be: order IDs (# followed by digits), email addresses (@ pattern), monetary amounts (£ or $ with digits), or dates (YYYY-MM-DD pattern) — data that should live in structured columns."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`

## Solution Query

```sql
-- Step 1: Detect structured data patterns embedded in free-text Notes
SELECT
    OrderID,
    LEFT(Notes, 200) AS NotesPreview,
    CASE WHEN Notes LIKE '%#[0-9][0-9][0-9][0-9]%'             THEN 'Y' ELSE 'N' END AS ContainsOrderID,
    CASE WHEN Notes LIKE '%@%.__%'                              THEN 'Y' ELSE 'N' END AS ContainsEmail,
    CASE WHEN Notes LIKE '%[£$€][0-9]%' OR Notes LIKE '%[0-9].[0-9][0-9]%'
                                                                THEN 'Y' ELSE 'N' END AS ContainsCurrency,
    CASE WHEN Notes LIKE '%[0-9][0-9][0-9][0-9]-[0-1][0-9]-[0-3][0-9]%'
                                                                THEN 'Y' ELSE 'N' END AS ContainsDate,
    CASE WHEN Notes LIKE '%DOB:%' OR Notes LIKE '%Date of Birth:%'
                                                                THEN 'Y' ELSE 'N' END AS ContainsPII
FROM Orders
WHERE Notes IS NOT NULL
  AND (Notes LIKE '%#[0-9][0-9][0-9][0-9]%'
    OR Notes LIKE '%@%.__%'
    OR Notes LIKE '%[£$€][0-9]%'
    OR Notes LIKE '%[0-9][0-9][0-9][0-9]-[0-1][0-9]-[0-3][0-9]%'
    OR Notes LIKE '%DOB:%');

-- Step 2: Extract embedded values where pattern is identifiable
SELECT
    OrderID,
    Notes,
    -- Extract order ID (assumes format "#NNNNN" with 4-8 digits)
    CASE
        WHEN PATINDEX('%#[0-9]%', Notes) > 0
             THEN SUBSTRING(Notes,
                            PATINDEX('%#[0-9]%', Notes) + 1,
                            PATINDEX('%[^0-9]%',
                                     SUBSTRING(Notes, PATINDEX('%#[0-9]%', Notes) + 1, 20) + 'X') - 1)
        ELSE NULL
    END AS ExtractedOrderRef,
    -- Extract email address
    CASE
        WHEN PATINDEX('%[^ @]+@[^ @]+\.[^ @]%', Notes) > 0
             THEN 'Email pattern found at position ' + CAST(PATINDEX('%[^ ]%@%', Notes) AS VARCHAR)
        ELSE NULL
    END AS EmailFound
FROM Orders
WHERE Notes IS NOT NULL
  AND (Notes LIKE '%#[0-9]%' OR Notes LIKE '%@%.%');

-- Step 3: Classify the type of misuse
SELECT
    OrderID,
    CASE
        WHEN Notes LIKE '%DOB%' OR Notes LIKE '%NI:%' OR Notes LIKE '%SSN:%'
             THEN 'PII data in notes — compliance risk'
        WHEN Notes LIKE '%#[0-9]%' AND Notes LIKE '%Order%'
             THEN 'Order reference in notes — should be in OrderRef column'
        WHEN Notes LIKE '%@%.__%'
             THEN 'Email address in notes — should be in Email column'
        WHEN Notes LIKE '%[£$][0-9]%'
             THEN 'Currency amount in notes — should be in Amount column'
        WHEN Notes LIKE '%[0-9][0-9][0-9][0-9]-[0-1][0-9]-[0-3][0-9]%'
             THEN 'Date in notes — should be in a date column'
        ELSE 'No structured data pattern detected'
    END AS MisuseCategory
FROM Orders
WHERE Notes IS NOT NULL;

-- Step 4: Volume by misuse category
SELECT
    CASE
        WHEN Notes LIKE '%DOB%' OR Notes LIKE '%NI:%' OR Notes LIKE '%SSN:%'
             THEN 'PII data'
        WHEN Notes LIKE '%#[0-9]%'
             THEN 'Reference numbers'
        WHEN Notes LIKE '%@%.__%'
             THEN 'Email addresses'
        WHEN Notes LIKE '%[£$][0-9]%'
             THEN 'Currency amounts'
        ELSE 'Free text (no pattern)'
    END AS Category,
    COUNT(*) AS NoteCount
FROM Orders
WHERE Notes IS NOT NULL
GROUP BY
    CASE
        WHEN Notes LIKE '%DOB%' OR Notes LIKE '%NI:%' OR Notes LIKE '%SSN:%'
             THEN 'PII data'
        WHEN Notes LIKE '%#[0-9]%'
             THEN 'Reference numbers'
        WHEN Notes LIKE '%@%.__%'
             THEN 'Email addresses'
        WHEN Notes LIKE '%[£$][0-9]%'
             THEN 'Currency amounts'
        ELSE 'Free text (no pattern)'
    END
ORDER BY NoteCount DESC;
```

## Explanation

**Why structured data ends up in free-text fields**
Schema gaps: when users need to record information but no dedicated column exists, they use the nearest available free-text field. Over time, a convention develops (`"Order #NNNN"`) that becomes informal structured data — queryable only with PATINDEX/LIKE, not with a simple column reference.

**Detection as schema gap evidence**
Step 4's volume output is evidence for a schema improvement request: if 5 of 20 orders have reference numbers in Notes, a dedicated `OrderReference` column should be added. The embedded data can then be migrated using the extraction query in Step 2.

**PII in free-text fields is a compliance risk**
Date of birth, NI numbers, SSNs, and other PII in an uncontrolled free-text column bypass data access controls, retention policies, and audit trails applied to dedicated PII columns. Step 3 flags these specifically as compliance risks rather than just data quality issues.

**PATINDEX for extraction (Step 2)**
Extracting a substring of unknown length requires finding the start position (PATINDEX of the pattern start) and end position (PATINDEX of the first non-matching character after the start). This nested PATINDEX approach is fragile and format-dependent — it works for known patterns but breaks on minor variations.

## Severity
**Medium** — Free-text structural data is unreliable (format varies, incomplete, unparseable) and causes reporting gaps. Severity rises to **High** when PII data is involved (compliance risk) or when the embedded data is being used for operational decisions (e.g., agents reading order IDs from notes instead of a proper order lookup).
