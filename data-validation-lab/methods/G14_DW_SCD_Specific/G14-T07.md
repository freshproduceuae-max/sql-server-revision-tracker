# G14-T07 — DW/SCD Specific | Slowly Changing Dimension Type 1 Override Audit

## ID
G14-T07

## Group
14 — DW/SCD Specific

## Type
Slowly Changing Dimension Type 1 Override Audit — Tracking What Changed When History Is Overwritten

## Live Scenario
A data warehouse team uses SCD Type 1 (overwrite-in-place) for the customer dimension: when a customer's email changes, the old email is simply replaced. Six months later, a compliance officer asks: "Which customers changed their email address in the last 90 days?" The answer is "we don't know" — SCD1 destroyed the history by overwriting it. A finance team then discovers that 340 customer segment changes in Q3 were overwritten in the dimension, meaning Q3 historical analysis now uses Q4 customer segments — producing wrong cohort analysis. The audit reveals what the team needed was not SCD1 but SCD2 or SCD1 with a change-log table. Going forward, a change-detection query compares the current dimension to a nightly snapshot, producing a change log that captures what changed and when.

## The Question
> SCD Type 1 overwrites historical values, making it impossible to recover the previous state from the dimension table alone. An SCD1 audit detects changes by comparing two snapshots of the dimension table and reporting what attributes changed between them. SQL implements this using EXCEPT or self-joins comparing current state to a prior snapshot.
> **"Detect which Customers have changed their Country, IsActive flag, or ContractEnd date compared to an expected baseline — simulate an SCD1 change audit that identifies the changed attribute, the old value, and the new value."**

## Table Reference
**Customers** — `schemas/01_Customers.csv`

## Solution Query

```sql
-- Step 1: Simulate a prior snapshot (baseline)
-- In production, this would be a separate snapshot table loaded yesterday
-- Here we use a hardcoded CTE to represent the "yesterday" state
WITH Baseline AS (
    -- Simulated prior snapshot: same customers with slightly different values
    SELECT 'CUST-001' AS CustomerID, 'UK'       AS Country, 1 AS IsActive, CAST('2025-12-31' AS DATE) AS ContractEnd
    UNION ALL SELECT 'CUST-002', 'US',       1, CAST('2026-06-30' AS DATE)
    UNION ALL SELECT 'CUST-003', 'Germany',  1, NULL
    UNION ALL SELECT 'CUST-004', 'UK',       1, CAST('2024-09-30' AS DATE)
    UNION ALL SELECT 'CUST-005', 'US',       0, NULL
    UNION ALL SELECT 'CUST-006', 'UK',       1, CAST('2025-03-31' AS DATE)
    UNION ALL SELECT 'CUST-007', 'Internal', 1, NULL
    UNION ALL SELECT 'CUST-008', 'UK',       1, CAST('2026-12-31' AS DATE)
    -- CUST-009 onwards: new customers not in yesterday's snapshot
),
CurrentState AS (
    SELECT
        CustomerID,
        Country,
        IsActive,
        CAST(ContractEnd AS DATE) AS ContractEnd
    FROM Customers
),

-- Step 2: Detect attribute changes by comparing current to baseline
Changes AS (
    SELECT
        c.CustomerID,
        -- Country change
        CASE WHEN ISNULL(c.Country, '') <> ISNULL(b.Country, '') THEN 1 ELSE 0 END AS CountryChanged,
        b.Country AS OldCountry, c.Country AS NewCountry,
        -- IsActive change
        CASE WHEN ISNULL(c.IsActive, -1) <> ISNULL(b.IsActive, -1) THEN 1 ELSE 0 END AS ActiveChanged,
        b.IsActive AS OldActive, c.IsActive AS NewActive,
        -- ContractEnd change
        CASE WHEN ISNULL(CAST(c.ContractEnd AS VARCHAR), '') <> ISNULL(CAST(b.ContractEnd AS VARCHAR), '')
             THEN 1 ELSE 0 END AS ContractChanged,
        b.ContractEnd AS OldContractEnd, c.ContractEnd AS NewContractEnd,
        -- New customer (not in baseline)
        CASE WHEN b.CustomerID IS NULL THEN 1 ELSE 0 END AS IsNew,
        -- Deleted customer (in baseline but not current)
        CASE WHEN c.CustomerID IS NULL THEN 1 ELSE 0 END AS IsDeleted
    FROM CurrentState c
    FULL OUTER JOIN Baseline b ON c.CustomerID = b.CustomerID
)
SELECT
    CustomerID,
    IsNew,
    IsDeleted,
    CountryChanged,
    OldCountry,
    NewCountry,
    ActiveChanged,
    OldActive,
    NewActive,
    ContractChanged,
    OldContractEnd,
    NewContractEnd,
    CountryChanged + ActiveChanged + ContractChanged AS TotalAttributesChanged,
    CASE
        WHEN IsNew = 1
             THEN 'NEW RECORD: Customer not in prior snapshot'
        WHEN IsDeleted = 1
             THEN 'DELETED: Customer present in baseline but removed from current'
        WHEN CountryChanged + ActiveChanged + ContractChanged = 0
             THEN 'UNCHANGED'
        ELSE CAST(CountryChanged + ActiveChanged + ContractChanged AS VARCHAR)
             + ' attribute(s) changed'
    END AS ChangeType,
    GETDATE() AS DetectedAt
FROM Changes
WHERE IsNew = 1 OR IsDeleted = 1
   OR CountryChanged + ActiveChanged + ContractChanged > 0
ORDER BY TotalAttributesChanged DESC, CustomerID;

-- Step 3: Change summary by attribute
WITH Baseline AS (
    SELECT 'CUST-001' AS CustomerID, 'UK' AS Country, 1 AS IsActive UNION ALL
    SELECT 'CUST-002', 'US', 1 UNION ALL SELECT 'CUST-003', 'Germany', 1 UNION ALL
    SELECT 'CUST-004', 'UK', 1 UNION ALL SELECT 'CUST-005', 'US', 0 UNION ALL
    SELECT 'CUST-006', 'UK', 1 UNION ALL SELECT 'CUST-007', 'Internal', 1 UNION ALL
    SELECT 'CUST-008', 'UK', 1
)
SELECT
    'Country' AS Attribute,
    SUM(CASE WHEN ISNULL(c.Country,'') <> ISNULL(b.Country,'') THEN 1 ELSE 0 END) AS ChangedCount,
    (SELECT COUNT(*) FROM Customers) AS TotalCustomers
FROM Customers c LEFT JOIN Baseline b ON c.CustomerID = b.CustomerID
UNION ALL
SELECT
    'IsActive',
    SUM(CASE WHEN ISNULL(c.IsActive,-1) <> ISNULL(b.IsActive,-1) THEN 1 ELSE 0 END),
    (SELECT COUNT(*) FROM Customers)
FROM Customers c LEFT JOIN Baseline b ON c.CustomerID = b.CustomerID;

-- Step 4: Identify customers added or removed since baseline
WITH Baseline AS (
    SELECT 'CUST-001' AS CustomerID UNION ALL SELECT 'CUST-002' UNION ALL
    SELECT 'CUST-003' UNION ALL SELECT 'CUST-004' UNION ALL SELECT 'CUST-005' UNION ALL
    SELECT 'CUST-006' UNION ALL SELECT 'CUST-007' UNION ALL SELECT 'CUST-008'
)
SELECT
    'NEW' AS ChangeKind, c.CustomerID, c.FirstName + ' ' + c.LastName AS Name
FROM Customers c
WHERE NOT EXISTS (SELECT 1 FROM Baseline b WHERE b.CustomerID = c.CustomerID)
UNION ALL
SELECT
    'REMOVED', b.CustomerID, 'Was in baseline, no longer in current'
FROM Baseline b
WHERE NOT EXISTS (SELECT 1 FROM Customers c WHERE c.CustomerID = b.CustomerID);
```

## Explanation

**SCD1 vs SCD2 vs change log**
SCD1 overwrites history — no historical record survives. SCD2 preserves history by adding new rows with new date ranges — but queries must always filter on the effective date. A change log table is a third approach: every time SCD1 overwrites a value, a trigger or ETL writes the old value to a change log. Step 2 simulates what a nightly change detection job would produce — the missing intermediate between pure SCD1 (no history) and SCD2 (full history in the dimension).

**FULL OUTER JOIN for insertion and deletion detection**
`FULL OUTER JOIN Baseline ON CustomerID` produces: rows present in both (changed or unchanged customers), rows only in CurrentState (new customers), and rows only in Baseline (deleted customers). The `IS NULL` checks on each side identify additions and deletions. A plain INNER JOIN would miss both.

**Attribute-level change detection**
`ISNULL(c.Country, '') <> ISNULL(b.Country, '')` handles the case where both old and new values are NULL — `NULL <> NULL` evaluates to unknown in SQL (neither true nor false), which would incorrectly flag unchanged NULL values as changed. Wrapping both sides in ISNULL ensures NULL-to-NULL transitions are correctly identified as "no change."

**The SCD1 trap for analytics**
When a dimension attribute changes under SCD1, all historical fact rows for that entity now have the new attribute value retroactively applied. A customer who changed from "UK" to "Germany" in July will now appear as a German customer for all their January–June orders. This is correct for some use cases (current state analysis) but wrong for historical analysis (what was this customer's country when they placed this order?). The SCD1 audit makes this trade-off visible and documentable.

## Severity
**Medium** — SCD1 overwrite decisions are often made for simplicity, with the data quality implications not fully understood. When analysts later need historical state (which segment was this customer in last quarter?), they discover the answer has been irretrievably destroyed. The SCD1 audit at minimum creates a documented record of what changed, enabling analysts to assess the impact of each overwrite on historical analyses.
