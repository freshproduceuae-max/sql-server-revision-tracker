# G14-T06 — DW/SCD Specific | Incremental Load Completeness Check

## ID
G14-T06

## Group
14 — DW/SCD Specific

## Type
Incremental Load Completeness Check — Verifying That Each ETL Load Transferred All Expected Records

## Live Scenario
A data pipeline loads new orders from the source system every hour using a watermark pattern: it loads all orders where `ModifiedDate > last_watermark`. After a source system database maintenance window, the `ModifiedDate` column's index was rebuilt and the statistics were updated — this caused a 2-hour window where `ModifiedDate` values were slightly off-clock due to a timezone misconfiguration during the rebuild. 1,847 orders from that 2-hour window have `ModifiedDate` values that fall before the last watermark used for the load — they are perpetually invisible to the incremental loader. Without an incremental load completeness check, these orders remain unloaded indefinitely. The completeness check compares the source count for the expected period against the destination count and flags the 1,847 missing records within 30 minutes of the failed load.

## The Question
> Incremental load completeness validates that every record in a source system that should have been included in an ETL load batch actually arrived in the destination. SQL checks completeness by: comparing record counts by load period between source and destination, detecting sequence gaps in loaded IDs, identifying periods with counts below the expected minimum, and spotting missing batches entirely.
> **"Verify incremental load completeness for Orders: compare the count of orders by month between what exists in the fact table and what the source (Transactions) indicates should exist, detect any gaps in the OrderID sequence that might indicate missing records, and flag months where the load count is suspiciously low compared to the rolling average."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Transactions** — `schemas/05_Transactions.csv`

## Solution Query

```sql
-- Step 1: Monthly load count comparison (source: Transactions, destination: Orders)
WITH SourceCounts AS (
    SELECT
        YEAR(TransactionDate)  AS Yr,
        MONTH(TransactionDate) AS Mo,
        COUNT(DISTINCT OrderID) AS SourceOrderCount
    FROM Transactions
    WHERE TransactionDate IS NOT NULL
    GROUP BY YEAR(TransactionDate), MONTH(TransactionDate)
),
DestCounts AS (
    SELECT
        YEAR(OrderDate)  AS Yr,
        MONTH(OrderDate) AS Mo,
        COUNT(*) AS DestOrderCount
    FROM Orders
    WHERE OrderDate IS NOT NULL
    GROUP BY YEAR(OrderDate), MONTH(OrderDate)
)
SELECT
    COALESCE(s.Yr, d.Yr)   AS Yr,
    COALESCE(s.Mo, d.Mo)   AS Mo,
    ISNULL(s.SourceOrderCount, 0) AS SourceCount,
    ISNULL(d.DestOrderCount, 0)   AS DestCount,
    ISNULL(s.SourceOrderCount, 0) - ISNULL(d.DestOrderCount, 0) AS MissingCount,
    ROUND(100.0 * (ISNULL(s.SourceOrderCount, 0) - ISNULL(d.DestOrderCount, 0))
          / NULLIF(s.SourceOrderCount, 0), 1) AS MissingPct,
    CASE
        WHEN s.Yr IS NULL
             THEN 'DEST ONLY: Month present in destination but not source'
        WHEN d.Yr IS NULL
             THEN 'SOURCE ONLY: Month present in source but not destination — batch may not have loaded'
        WHEN s.SourceOrderCount > d.DestOrderCount
             THEN 'INCOMPLETE LOAD: '
                  + CAST(s.SourceOrderCount - d.DestOrderCount AS VARCHAR)
                  + ' records missing from destination'
        WHEN d.DestOrderCount > s.SourceOrderCount
             THEN 'OVER-LOAD: Destination has more records than source — possible duplicates'
        ELSE 'Complete: Source and destination counts match'
    END AS LoadStatus
FROM SourceCounts s
FULL OUTER JOIN DestCounts d ON s.Yr = d.Yr AND s.Mo = d.Mo
ORDER BY Yr, Mo;

-- Step 2: OrderID sequence gap detection
-- If OrderIDs are sequential integers, missing values indicate missing records
WITH OrderSequence AS (
    SELECT
        OrderID,
        -- Compute expected next ID
        LEAD(OrderID) OVER (ORDER BY OrderID) AS NextID,
        -- Gap size = next - current - 1
        LEAD(OrderID) OVER (ORDER BY OrderID) - OrderID - 1 AS GapSize
    FROM Orders
    WHERE OrderID IS NOT NULL
)
SELECT
    OrderID AS LastBeforeGap,
    NextID AS FirstAfterGap,
    GapSize AS MissingIDCount,
    'GAP: ' + CAST(GapSize AS VARCHAR) + ' OrderIDs missing between '
        + CAST(OrderID AS VARCHAR) + ' and ' + CAST(NextID AS VARCHAR) AS GapDescription
FROM OrderSequence
WHERE GapSize > 0
ORDER BY GapSize DESC;

-- Step 3: Rolling average load count — flag suspiciously low periods
WITH MonthlyCounts AS (
    SELECT
        YEAR(OrderDate) AS Yr,
        MONTH(OrderDate) AS Mo,
        COUNT(*) AS MonthlyCount
    FROM Orders
    WHERE OrderDate IS NOT NULL
    GROUP BY YEAR(OrderDate), MONTH(OrderDate)
),
WithRolling AS (
    SELECT
        *,
        AVG(CAST(MonthlyCount AS FLOAT))
            OVER (ORDER BY Yr, Mo ROWS BETWEEN 3 PRECEDING AND 1 PRECEDING) AS Avg3MonthPrior,
        COUNT(*) OVER (ORDER BY Yr, Mo ROWS BETWEEN 3 PRECEDING AND 1 PRECEDING)
            AS HistoryMonths
    FROM MonthlyCounts
)
SELECT
    Yr,
    Mo,
    MonthlyCount,
    ROUND(Avg3MonthPrior, 0) AS Avg3MonthBaseline,
    HistoryMonths,
    ROUND(100.0 * (MonthlyCount - Avg3MonthPrior) / NULLIF(Avg3MonthPrior, 0), 1)
        AS DeviationFromBaselinePct,
    CASE
        WHEN HistoryMonths < 2
             THEN 'INSUFFICIENT HISTORY: Cannot establish baseline'
        WHEN MonthlyCount < Avg3MonthPrior * 0.5
             THEN 'LOAD ALERT: Count <50% of 3-month average — possible incomplete load'
        WHEN MonthlyCount < Avg3MonthPrior * 0.7
             THEN 'LOW COUNT: Count <70% of 3-month average — investigate'
        ELSE 'Normal load volume'
    END AS LoadVolumeFlag
FROM WithRolling
ORDER BY Yr, Mo;

-- Step 4: Load watermark check — most recent loaded record
SELECT
    'Orders' AS TableName,
    MAX(CAST(OrderDate AS DATE)) AS MostRecentEventDate,
    MIN(CAST(OrderDate AS DATE)) AS EarliestEventDate,
    DATEDIFF(DAY, MAX(CAST(OrderDate AS DATE)), GETDATE()) AS DaysSinceLatestRecord,
    CASE
        WHEN DATEDIFF(DAY, MAX(CAST(OrderDate AS DATE)), GETDATE()) > 2
             THEN 'STALE: Latest order is more than 2 days old — check if load is running'
        ELSE 'Current'
    END AS FreshnessFlag
FROM Orders WHERE OrderDate IS NOT NULL
UNION ALL
SELECT
    'Transactions',
    MAX(CAST(TransactionDate AS DATE)),
    MIN(CAST(TransactionDate AS DATE)),
    DATEDIFF(DAY, MAX(CAST(TransactionDate AS DATE)), GETDATE()),
    CASE
        WHEN DATEDIFF(DAY, MAX(CAST(TransactionDate AS DATE)), GETDATE()) > 2
             THEN 'STALE: Latest transaction is more than 2 days old'
        ELSE 'Current'
    END
FROM Transactions WHERE TransactionDate IS NOT NULL;
```

## Explanation

**Watermark-based incremental loading**
The most common incremental load pattern uses a watermark column (typically `ModifiedDate` or `CreatedDate`): each run loads records where `ModifiedDate > last_run_watermark`. The completeness check verifies the load by comparing counts between source and destination for the same period. A missing count > 0 means records that should have been loaded were not.

**OrderID sequence gap detection**
When the source system assigns sequential integer IDs, gaps in the loaded ID sequence identify missing records with precision. `LEAD(OrderID) - OrderID - 1` gives the exact number of IDs missing between each consecutive pair of loaded records. This is more precise than count comparison because it identifies exactly which IDs are missing, not just how many.

**Rolling average as a completeness baseline**
The 3-month rolling average load count establishes what a "normal" load volume looks like. A month with <50% of the average count is a strong signal of an incomplete load — either the batch failed mid-run, the watermark was misconfigured, or the source system had a data quality event. This check catches failures that count-comparison cannot: if the source count is also low (the source itself has fewer records), a missing-record scenario and a genuine business decline look identical from count comparison alone.

**Over-load detection**
Destination count > source count indicates duplicate records in the destination. This can occur when: the ETL runs twice for the same window without deduplication, the watermark is reset to a prior value, or a full load is accidentally combined with an incremental load. Over-loads are often harder to detect than under-loads because the totals increase, which looks like business growth.

## Severity
**High** — Incremental load failures silently exclude records from all downstream reports and models. Unlike a failed load (which raises an error), a partial load completes successfully and passes monitoring checks that only verify job completion, not record completeness. The only reliable detection is count-based validation comparing what was loaded against what was expected.
