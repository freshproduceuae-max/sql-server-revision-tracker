# G14-T01 — DW/SCD Specific | SCD Type 2 Gap and Overlap Detection

## ID
G14-T01

## Group
14 — DW/SCD Specific

## Type
SCD Type 2 Gap and Overlap Detection — Validating That Effective Date Ranges Are Complete and Non-Overlapping

## Live Scenario
A data warehouse team loads a customer dimension with Slowly Changing Dimension Type 2 (SCD2) history: each change to a customer's address, status, or segment creates a new row with `EffectiveFrom` and `EffectiveTo` date columns. After 18 months of daily loads, a query that joins fact table order dates to the customer dimension using the effective date range starts returning incorrect customer segments for 3,400 orders. Investigation reveals two categories of error: (1) gaps — for 120 customers, a period of 3–47 days exists where the `EffectiveTo` of one record and the `EffectiveFrom` of the next record do not meet, leaving a gap where no dimension row is valid; (2) overlaps — for 85 customers, two dimension rows are simultaneously active for the same date range. Both are caused by the ETL loading a correction row without properly closing the prior row's `EffectiveTo`. Orders falling in the gap period return no customer dimension match; orders in the overlap period return two rows, causing fan-out double-counting.

## The Question
> SCD Type 2 date range validation checks that for each entity in the dimension: (1) effective date ranges do not overlap (only one row is valid on any given date), (2) there are no gaps between consecutive records (the history is contiguous), (3) exactly one current row exists (EffectiveTo = '9999-12-31' or NULL), and (4) the EffectiveFrom of each record immediately follows the EffectiveTo of the prior record.
> **"Validate the SCD Type 2 history in the Customers table (using ContractEnd as a proxy EffectiveTo column): for each customer, detect gaps and overlaps in their effective date history, identify customers with multiple or no active records, and verify that the current record flag is set correctly."**

## Table Reference
**Customers** — `schemas/01_Customers.csv`
**Orders** — `schemas/02_Orders.csv`

## Solution Query

```sql
-- Step 1: Simulate SCD2 structure using Customers + Orders history
-- In real DW, this would be a dimension table with EffectiveFrom, EffectiveTo
-- Here we construct a proxy: customer's first order date as EffectiveFrom,
-- and ContractEnd as a proxy for the version boundary

WITH CustomerVersions AS (
    SELECT
        c.CustomerID,
        c.FirstName + ' ' + c.LastName AS CustomerName,
        c.Country,
        c.IsActive,
        -- Use DateOfBirth as "version start" proxy
        CAST(c.DateOfBirth AS DATE)  AS EffectiveFrom,
        -- Use ContractEnd as "version end" proxy
        CAST(c.ContractEnd AS DATE)  AS EffectiveTo,
        -- Current row = no ContractEnd or ContractEnd in the future
        CASE
            WHEN c.ContractEnd IS NULL OR c.ContractEnd > GETDATE()
                 THEN 1 ELSE 0
        END AS IsCurrent
    FROM Customers c
    WHERE c.DateOfBirth IS NOT NULL
),

-- Step 2: Within-customer version ordering
OrderedVersions AS (
    SELECT
        *,
        ROW_NUMBER() OVER (PARTITION BY CustomerID ORDER BY EffectiveFrom) AS VersionSeq,
        LAG(EffectiveTo) OVER (PARTITION BY CustomerID ORDER BY EffectiveFrom) AS PriorEffectiveTo,
        LEAD(EffectiveFrom) OVER (PARTITION BY CustomerID ORDER BY EffectiveFrom) AS NextEffectiveFrom
    FROM CustomerVersions
)
SELECT
    CustomerID,
    CustomerName,
    VersionSeq,
    EffectiveFrom,
    EffectiveTo,
    IsCurrent,
    PriorEffectiveTo,
    NextEffectiveFrom,
    -- Gap detection: gap exists if prior row's EffectiveTo != this row's EffectiveFrom
    CASE
        WHEN PriorEffectiveTo IS NULL
             THEN 'First version'
        WHEN DATEDIFF(DAY, PriorEffectiveTo, EffectiveFrom) > 1
             THEN 'GAP DETECTED: ' + CAST(DATEDIFF(DAY, PriorEffectiveTo, EffectiveFrom) - 1 AS VARCHAR)
                  + ' day gap between versions'
        WHEN EffectiveFrom < PriorEffectiveTo
             THEN 'OVERLAP DETECTED: This version starts before prior version ends'
        WHEN EffectiveFrom = PriorEffectiveTo
             THEN 'ADJACENT: Versions meet exactly (valid)'
        ELSE 'Contiguous: No gap or overlap'
    END AS GapOverlapFlag
FROM OrderedVersions
ORDER BY CustomerID, VersionSeq;

-- Step 3: Summary — how many customers have gaps or overlaps?
WITH CustomerVersions AS (
    SELECT
        CustomerID,
        CAST(DateOfBirth AS DATE) AS EffectiveFrom,
        CAST(ContractEnd AS DATE) AS EffectiveTo,
        CASE WHEN ContractEnd IS NULL OR ContractEnd > GETDATE() THEN 1 ELSE 0 END AS IsCurrent
    FROM Customers WHERE DateOfBirth IS NOT NULL
),
OrderedVersions AS (
    SELECT *,
           LAG(EffectiveTo) OVER (PARTITION BY CustomerID ORDER BY EffectiveFrom) AS PriorEffectiveTo
    FROM CustomerVersions
)
SELECT
    COUNT(DISTINCT CustomerID) AS TotalCustomers,
    COUNT(DISTINCT CASE WHEN PriorEffectiveTo IS NOT NULL
                         AND DATEDIFF(DAY, PriorEffectiveTo, EffectiveFrom) > 1
                        THEN CustomerID END) AS CustomersWithGaps,
    COUNT(DISTINCT CASE WHEN PriorEffectiveTo IS NOT NULL
                         AND EffectiveFrom < PriorEffectiveTo
                        THEN CustomerID END) AS CustomersWithOverlaps,
    SUM(IsCurrent) AS CurrentVersionCount,
    (SELECT COUNT(*) FROM Customers) AS TotalRows,
    CASE
        WHEN SUM(IsCurrent) > COUNT(DISTINCT CustomerID)
             THEN 'ALERT: More current rows than customers — multiple active versions exist'
        WHEN SUM(IsCurrent) < COUNT(DISTINCT CustomerID)
             THEN 'ALERT: Fewer current rows than customers — some customers have no active version'
        ELSE 'OK: One current version per customer'
    END AS CurrentVersionFlag
FROM OrderedVersions;

-- Step 4: Point-in-time join test — can orders be resolved to exactly one dimension row?
-- For each order, find the matching customer version
SELECT
    o.OrderID,
    o.CustomerID,
    CAST(o.OrderDate AS DATE) AS OrderDate,
    o.TotalAmount,
    c.Country AS CustomerCountry,
    c.IsActive,
    CASE
        WHEN c.CustomerID IS NULL
             THEN 'NO MATCH: No dimension row covers this order date'
        ELSE 'Matched'
    END AS DimensionJoinFlag
FROM Orders o
LEFT JOIN Customers c
    ON o.CustomerID = c.CustomerID
    AND CAST(o.OrderDate AS DATE) >= ISNULL(CAST(c.DateOfBirth AS DATE), '1900-01-01')
    AND CAST(o.OrderDate AS DATE) <= ISNULL(CAST(c.ContractEnd AS DATE), '9999-12-31')
WHERE o.OrderDate IS NOT NULL;
```

## Explanation

**SCD2 date range invariants**
A correctly loaded SCD2 dimension must satisfy three invariants per entity: (1) non-overlapping — for any date D, at most one row has `EffectiveFrom ≤ D ≤ EffectiveTo`; (2) gapless — for any date D between the first and last version, exactly one row covers D; (3) current-only — exactly one row has `EffectiveTo = '9999-12-31'` (or NULL) representing the current state. Violation of any invariant causes incorrect point-in-time join results.

**GAP detection with LAG**
`LAG(EffectiveTo) OVER (PARTITION BY CustomerID ORDER BY EffectiveFrom)` retrieves the previous version's end date. A gap exists when `EffectiveFrom > PriorEffectiveTo + 1 day` — the new version starts more than one day after the previous version ended. The gap size is `DATEDIFF(DAY, PriorEffectiveTo, EffectiveFrom) - 1`.

**OVERLAP detection**
An overlap exists when `EffectiveFrom < PriorEffectiveTo` — the new version starts before the previous version has ended. This means two rows simultaneously claim to be the valid version for dates in the intersection period. A point-in-time join on an overlap date returns two rows, causing fan-out and double-counting in any aggregate query.

**The multiple-current-row problem**
More current rows than customers means at least one customer has two active versions simultaneously — the worst case of an overlap, where the ETL created a new current row without closing the old current row. Queries that filter on `IsCurrent = 1` will return both rows for that customer, doubling that customer's fact table contributions.

## Severity
**High** — SCD2 integrity failures directly corrupt time-series analysis. An analyst running "customer segment distribution in Q3 2023" against a dimension with gaps will silently exclude orders from the gap periods; with overlaps, the same orders will be counted twice. Neither failure raises an error — the query completes and returns a plausible-looking but incorrect result.
