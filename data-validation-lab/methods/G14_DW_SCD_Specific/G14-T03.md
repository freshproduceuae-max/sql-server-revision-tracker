# G14-T03 — DW/SCD Specific | Dimension Key Integrity in Star Schema

## ID
G14-T03

## Group
14 — DW/SCD Specific

## Type
Dimension Key Integrity in Star Schema — Validating Foreign Key Links Between Fact and Dimension Tables

## Live Scenario
A BI team discovers that their sales dashboard has been understating revenue by £340,000 over the past quarter. Investigation reveals the source: 1,200 fact table rows reference a ProductID of -1 (the "unknown product" placeholder that was loaded into the product dimension three years ago to handle unresolvable product references). These rows were excluded from all product-level aggregations because the BI tool's dimension filter does not include the -1 placeholder. Nobody knew the -1 rows existed because the ETL loaded them silently — when a product lookup failed, instead of rejecting the row, it defaulted to -1. A dimension key integrity check identifies all fact rows pointing to placeholder or missing dimension keys, quantifying the hidden revenue being systematically excluded from every report.

## The Question
> Dimension key integrity validates that: every foreign key in the fact table points to a valid, active row in the corresponding dimension, no fact rows reference placeholder or "unknown" dimension members that are systematically excluded from analysis, and every dimension member that should be reachable from the fact table is actually referenced. SQL validates this using NOT EXISTS, anti-JOINs, and range checks.
> **"Validate dimension key integrity in Orders as a fact table: verify all CustomerID and ProductID values exist in their respective dimension tables, identify any fact rows referencing inactive dimension members (IsActive=0), and find dimension members that have never been referenced by any fact row."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Customers** — `schemas/01_Customers.csv`
**Products** — `schemas/03_Products.csv`

## Solution Query

```sql
-- Step 1: Fact-to-dimension key validation — all dimension keys must exist
SELECT
    o.OrderID,
    o.CustomerID,
    o.ProductID,
    -- Dimension key validity
    CASE WHEN c.CustomerID IS NULL THEN 'MISSING' ELSE 'EXISTS' END AS CustomerDimStatus,
    CASE WHEN p.ProductID IS NULL  THEN 'MISSING' ELSE 'EXISTS' END AS ProductDimStatus,
    -- Inactive dimension member references
    CASE WHEN c.IsActive = 0 THEN 'INACTIVE CUSTOMER' ELSE 'OK' END AS CustomerActiveFlag,
    CASE WHEN p.IsActive = 0 THEN 'INACTIVE PRODUCT' ELSE 'OK' END AS ProductActiveFlag
FROM Orders o
LEFT JOIN Customers c ON o.CustomerID = c.CustomerID
LEFT JOIN Products p  ON o.ProductID  = p.ProductID
WHERE c.CustomerID IS NULL   -- missing customer dimension row
   OR p.ProductID IS NULL    -- missing product dimension row
   OR c.IsActive = 0         -- order on inactive customer
   OR p.IsActive = 0         -- order on inactive product
ORDER BY o.OrderID;

-- Step 2: Summary of dimension key integrity
SELECT
    'CustomerID' AS DimensionKey,
    COUNT(*) AS TotalFactRows,
    SUM(CASE WHEN c.CustomerID IS NULL THEN 1 ELSE 0 END) AS MissingDimRows,
    SUM(CASE WHEN c.IsActive = 0 THEN 1 ELSE 0 END) AS InactiveDimRows,
    SUM(CASE WHEN c.CustomerID IS NOT NULL AND c.IsActive = 1 THEN 1 ELSE 0 END) AS ValidActiveRows,
    ROUND(100.0 * SUM(CASE WHEN c.CustomerID IS NOT NULL THEN 1 ELSE 0 END)
          / NULLIF(COUNT(*), 0), 1) AS DimCoveragePct
FROM Orders o
LEFT JOIN Customers c ON o.CustomerID = c.CustomerID
UNION ALL
SELECT
    'ProductID',
    COUNT(*),
    SUM(CASE WHEN p.ProductID IS NULL THEN 1 ELSE 0 END),
    SUM(CASE WHEN p.IsActive = 0 THEN 1 ELSE 0 END),
    SUM(CASE WHEN p.ProductID IS NOT NULL AND p.IsActive = 1 THEN 1 ELSE 0 END),
    ROUND(100.0 * SUM(CASE WHEN p.ProductID IS NOT NULL THEN 1 ELSE 0 END)
          / NULLIF(COUNT(*), 0), 1)
FROM Orders o
LEFT JOIN Products p ON o.ProductID = p.ProductID;

-- Step 3: Dimension coverage — which dimension members are never referenced in facts?
-- Customers with no orders (unreferenced dimension members)
SELECT
    c.CustomerID,
    c.FirstName + ' ' + c.LastName AS CustomerName,
    c.Country,
    c.IsActive,
    'UNREFERENCED: Customer exists in dimension but has no orders in fact table' AS Note
FROM Customers c
WHERE NOT EXISTS (SELECT 1 FROM Orders o WHERE o.CustomerID = c.CustomerID)
UNION ALL
-- Products with no orders
SELECT
    p.ProductID,
    p.ProductName,
    NULL,
    p.IsActive,
    'UNREFERENCED: Product exists in dimension but has no orders in fact table'
FROM Products p
WHERE NOT EXISTS (SELECT 1 FROM Orders o WHERE o.ProductID = p.ProductID);

-- Step 4: Conformed dimension check — CustomerIDs used in Orders also in Transactions
SELECT
    o.CustomerID,
    COUNT(DISTINCT o.OrderID) AS OrderCount,
    COUNT(DISTINCT t.TransactionID) AS TxnCount,
    CASE
        WHEN COUNT(DISTINCT t.TransactionID) = 0
             THEN 'ORDERS WITHOUT TRANSACTIONS: Orders exist but no matching payments'
        ELSE 'Customer has both orders and transactions'
    END AS ConformanceFlag
FROM Orders o
LEFT JOIN Transactions t ON o.OrderID = t.OrderID
GROUP BY o.CustomerID
HAVING COUNT(DISTINCT t.TransactionID) = 0
ORDER BY OrderCount DESC;

-- Step 5: Role-playing dimension check — CustomerID used correctly
-- In star schemas, the same dimension can serve multiple roles (e.g., ship-to vs bill-to customer)
-- Verify no CustomerID appears in a role it should not
SELECT
    CustomerID,
    COUNT(*) AS OrderCount,
    MIN(CAST(OrderDate AS DATE)) AS FirstOrder,
    MAX(CAST(OrderDate AS DATE)) AS LastOrder,
    COUNT(DISTINCT Status) AS StatusVariety,
    COUNT(DISTINCT ProductID) AS ProductVariety
FROM Orders
GROUP BY CustomerID
HAVING COUNT(*) > 0
ORDER BY OrderCount DESC;
```

## Explanation

**LEFT JOIN for dimension key validation**
`LEFT JOIN Customers ON Orders.CustomerID = Customers.CustomerID` returns NULL for Customers columns when no matching CustomerID exists in the dimension. `WHERE c.CustomerID IS NULL` isolates rows where the join found no match — these are the orphaned fact rows. This is more efficient than NOT EXISTS for returning the full row context of the failing records.

**Active dimension members vs inactive**
A fact table row referencing an inactive dimension member (IsActive = 0) is technically valid from a referential integrity standpoint — the key exists. But it represents a business logic concern: should inactive products or inactive customers appear in current sales reports? Some BI tools filter on `IsActive = 1` by default, which would cause these fact rows to be silently excluded from all aggregations.

**Unreferenced dimension members**
Step 3 finds dimension members never referenced by any fact row. These represent: customers who registered but never ordered (legitimate), products added to the catalogue but never sold (legitimate), or placeholder/test dimension rows that should be excluded from user-facing reports. Unreferenced dimension members inflate dimension sizes and appear as empty rows in cross-tab reports.

**Conformed dimensions**
In a star schema, the same CustomerID dimension should work across all fact tables (Orders, Transactions, Support tickets). Step 4 checks that CustomerIDs appearing in Orders also have corresponding Transactions — a basic conformance check. A CustomerID with orders but zero transactions is either a legitimate cash-on-delivery customer or an ETL gap where payment records were not loaded.

## Severity
**High** — Dimension key failures cause invisible revenue exclusion from BI reports. A missing dimension key causes the fact row to be excluded from any inner-join or filter-based aggregation; an inactive dimension key causes exclusion from any active-member filter. Both scenarios produce understated totals without any error — the report appears complete but is systematically omitting revenue.
