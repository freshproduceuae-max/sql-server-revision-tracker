# G14-T02 — DW/SCD Specific | Fact Table Grain Validation

## ID
G14-T02

## Group
14 — DW/SCD Specific

## Type
Fact Table Grain Validation — Verifying That Every Row in a Fact Table Represents the Correct Level of Detail

## Live Scenario
A BI team builds a sales fact table at the order-line-item grain: one row per product per order. Six months later, a developer adds a new ETL path for a regional system that loads at the order-header grain (one row per order, not per product). The fact table now contains two grains mixed together. Queries that SUM(Quantity) by Product now double-count because order-header rows do not have a ProductID — they are joined to a "dummy" product dimension row. Revenue totals are overstated by 18% because the order-header rows contain the full order total while the line-item rows also contain their portion. The grain validation query detects this immediately: it shows that 340 rows have NULL ProductID (indicating a different grain from the intended one-row-per-product design).

## The Question
> A fact table's grain defines the lowest level of detail represented by each row. Grain validation checks that: every row represents the correct grain (e.g., one row per order-product combination), no rows violate the grain by being aggregated to a higher level, and no grain duplicates exist (the same combination of dimension keys appears more than once at the intended grain).
> **"Validate the grain of the Orders table as a fact table at the CustomerID-ProductID-OrderDate grain: detect any duplicate grain combinations, any rows with NULL dimension keys that would represent a different grain, and verify that the key combination uniquely identifies each row."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Transactions** — `schemas/05_Transactions.csv`

## Solution Query

```sql
-- Step 1: Grain duplicate detection — same dimension key combination more than once
WITH GrainCheck AS (
    SELECT
        CustomerID,
        ProductID,
        CAST(OrderDate AS DATE) AS OrderDay,
        COUNT(*) AS RowCount,
        SUM(TotalAmount) AS TotalForGrain,
        STRING_AGG(CAST(OrderID AS VARCHAR), ', ') AS OrderIDs
    FROM Orders
    WHERE OrderDate IS NOT NULL
    GROUP BY CustomerID, ProductID, CAST(OrderDate AS DATE)
)
SELECT
    CustomerID,
    ProductID,
    OrderDay,
    RowCount,
    TotalForGrain,
    OrderIDs,
    CASE
        WHEN RowCount > 1
             THEN 'GRAIN VIOLATION: ' + CAST(RowCount AS VARCHAR)
                  + ' rows share the same CustomerID-ProductID-Date — duplicate grain'
        ELSE 'Unique grain'
    END AS GrainFlag
FROM GrainCheck
ORDER BY RowCount DESC;

-- Step 2: NULL dimension keys — rows with incomplete grain
SELECT
    'NULL CustomerID' AS Issue,
    COUNT(*) AS Count,
    ROUND(100.0 * COUNT(*) / (SELECT COUNT(*) FROM Orders), 1) AS Pct
FROM Orders WHERE CustomerID IS NULL
UNION ALL
SELECT 'NULL ProductID', COUNT(*),
       ROUND(100.0 * COUNT(*) / (SELECT COUNT(*) FROM Orders), 1)
FROM Orders WHERE ProductID IS NULL
UNION ALL
SELECT 'NULL OrderDate', COUNT(*),
       ROUND(100.0 * COUNT(*) / (SELECT COUNT(*) FROM Orders), 1)
FROM Orders WHERE OrderDate IS NULL
UNION ALL
SELECT 'All grain keys populated', COUNT(*),
       ROUND(100.0 * COUNT(*) / (SELECT COUNT(*) FROM Orders), 1)
FROM Orders
WHERE CustomerID IS NOT NULL AND ProductID IS NOT NULL AND OrderDate IS NOT NULL;

-- Step 3: Additive measure validation — amounts should sum correctly
SELECT
    COUNT(*) AS TotalFactRows,
    ROUND(SUM(TotalAmount), 2) AS TotalRevenue,
    ROUND(AVG(TotalAmount), 2) AS AvgPerRow,
    -- Check for negative amounts (should be separate return/credit rows)
    SUM(CASE WHEN TotalAmount < 0 THEN 1 ELSE 0 END) AS NegativeAmountRows,
    SUM(CASE WHEN TotalAmount = 0 THEN 1 ELSE 0 END) AS ZeroAmountRows,
    -- Additive measure range sanity
    MIN(TotalAmount) AS MinAmount,
    MAX(TotalAmount) AS MaxAmount,
    CASE
        WHEN MAX(TotalAmount) > MIN(TotalAmount) * 1000
             THEN 'WIDE RANGE: Max is >1000× min — possible grain mixing (header + line)'
        ELSE 'Plausible range'
    END AS RangeFlag
FROM Orders
WHERE TotalAmount IS NOT NULL;

-- Step 4: Surrogate key density — does OrderID uniquely identify each fact row?
SELECT
    COUNT(*) AS TotalRows,
    COUNT(DISTINCT OrderID) AS DistinctOrderIDs,
    COUNT(*) - COUNT(DISTINCT OrderID) AS DuplicateKeyCount,
    CASE
        WHEN COUNT(*) = COUNT(DISTINCT OrderID)
             THEN 'UNIQUE: OrderID is a valid surrogate key for this fact table'
        ELSE 'DUPLICATE KEYS: OrderID not unique — cannot be used as row identifier'
    END AS SurrogateKeyFlag
FROM Orders;

-- Step 5: Degenerate dimension validation — OrderID as a degenerate dimension
-- In fact tables, the source transaction key (OrderID) is stored as a degenerate dimension
-- It must be present and unique within the fact grain
SELECT
    CASE
        WHEN OrderID IS NULL THEN 'NULL ORDER ID'
        WHEN LEN(LTRIM(RTRIM(CAST(OrderID AS VARCHAR)))) = 0 THEN 'EMPTY ORDER ID'
        ELSE LEFT(CAST(OrderID AS VARCHAR), 5) + '...'
    END AS OrderIDPattern,
    COUNT(*) AS Count
FROM Orders
GROUP BY
    CASE
        WHEN OrderID IS NULL THEN 'NULL ORDER ID'
        WHEN LEN(LTRIM(RTRIM(CAST(OrderID AS VARCHAR)))) = 0 THEN 'EMPTY ORDER ID'
        ELSE LEFT(CAST(OrderID AS VARCHAR), 5) + '...'
    END
ORDER BY Count DESC;
```

## Explanation

**Grain definition and the COUNT DISTINCT test**
The fact table grain is the combination of dimension foreign keys that uniquely identifies each row. Testing the grain means: GROUP BY the expected grain key columns and confirm COUNT(*) = 1 for every group. Any group with COUNT(*) > 1 contains duplicate rows at that grain — either the grain was incorrectly specified or the ETL is producing duplicates.

**NULL grain keys as a grain indicator**
A NULL in a dimension key column means the fact row cannot be assigned to a dimension member at the intended grain level. This is the hallmark of a mixed-grain fact table: some rows have all keys (line-item grain) while others have only some keys (header grain). The "All grain keys populated" count in Step 2 tells you what percentage of rows conform to the intended grain.

**Negative amounts in fact tables**
Negative TotalAmount values represent reversals, refunds, or credit notes. In a well-designed fact table, these are legitimate signed measures that can be summed to produce net revenue. However, if the original design assumed all amounts are positive (unit price × quantity), a negative amount may indicate a grain error (a credit note loaded as an order row) or a data entry error (sign reversed accidentally).

**Degenerate dimensions**
A degenerate dimension is a fact table attribute that is not a foreign key to a separate dimension table — typically the source transaction ID (OrderID, InvoiceNumber). It is stored in the fact table itself rather than in a dimension. Degenerate dimensions must be non-NULL (otherwise the fact cannot be traced to its source) and typically near-unique (though the same source order may generate multiple fact rows at line-item grain).

## Severity
**High** — Grain violations in a fact table cause silent aggregation errors: mixed-grain rows (header + line) produce inflated totals; duplicate grain rows double-count. Both failures look like correct query results to any analyst who does not know the grain is corrupted. Because fact tables aggregate millions of rows, a 5% grain violation rate can translate to tens of millions of pounds of incorrect reported revenue.
