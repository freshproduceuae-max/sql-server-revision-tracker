# G14-T09 — DW/SCD Specific | Bridge Table and Many-to-Many Relationship Integrity

## ID
G14-T09

## Group
14 — DW/SCD Specific

## Type
Bridge Table and Many-to-Many Relationship Integrity — Validating Association Tables in Star Schemas

## Live Scenario
A media company's data warehouse tracks campaign performance: each campaign can target multiple customer segments, and each customer can belong to multiple segments. The relationship is stored in a bridge table (`CampaignSegments`) between the campaign dimension and the segment dimension. An analyst runs a campaign ROI report and notices total revenue is inflated by 340% — far beyond any plausible uplift. Investigation reveals that when a campaign targets 3 segments, every order from customers in any of those segments is counted 3 times because the fact-to-bridge JOIN multiplies rows. The bridge table requires a weighting factor column (`SegmentWeight = 1/N` where N is the number of segments per campaign) to prevent double-counting. The integrity check finds 47 campaigns where the weights sum to more than 1.0 (incorrect weighting), causing systematic over-counting in all campaign performance metrics.

## The Question
> A bridge table enables many-to-many relationships in a star schema. Bridge table integrity validates: all associations reference valid dimension members on both sides, weighting factors (if used) sum to 1.0 per entity, no duplicate associations exist, and the bridge table does not introduce fan-out that would over-count fact table rows.
> **"Validate the many-to-many relationship between Orders and Customers (via the implicit association through multiple orders per customer): detect fan-out risk in the Orders-to-Transactions bridge, verify that each order links to a single customer (not multiple), and quantify the multiplication effect of joining without aggregation."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Customers** — `schemas/01_Customers.csv`
**Transactions** — `schemas/05_Transactions.csv`
**Products** — `schemas/03_Products.csv`

## Solution Query

```sql
-- Step 1: Fan-out detection — joining Orders to Transactions without aggregation
-- Measure how many rows the JOIN produces vs the expected grain
WITH OrderTxnCounts AS (
    SELECT
        o.OrderID,
        COUNT(t.TransactionID) AS TxnPerOrder,
        SUM(t.Amount) AS SumTxnAmount,
        o.TotalAmount AS OrderAmount
    FROM Orders o
    LEFT JOIN Transactions t ON o.OrderID = t.OrderID
    GROUP BY o.OrderID, o.TotalAmount
)
SELECT
    TxnPerOrder AS TransactionsPerOrder,
    COUNT(*) AS OrderCount,
    ROUND(100.0 * COUNT(*) / SUM(COUNT(*)) OVER (), 1) AS PctOfOrders,
    CASE
        WHEN TxnPerOrder = 0
             THEN 'NO TRANSACTIONS: Order has no matching transaction rows'
        WHEN TxnPerOrder = 1
             THEN 'CLEAN: 1:1 relationship — no fan-out'
        WHEN TxnPerOrder > 1
             THEN 'FAN-OUT RISK: Joining to ' + CAST(TxnPerOrder AS VARCHAR)
                  + ' transaction rows will multiply this order'
        ELSE 'Unknown'
    END AS FanOutFlag
FROM OrderTxnCounts
GROUP BY TxnPerOrder
ORDER BY TxnPerOrder;

-- Step 2: Weighting factor validation — if bridge table has weights, they must sum to 1.0
-- Simulate a bridge scenario using ProductID allocations across orders
WITH OrderProductBridge AS (
    SELECT
        ProductID,
        CustomerID,
        COUNT(*) AS OrderCount,
        -- Simulated weight: each order has equal weight within a product-customer combination
        1.0 / COUNT(*) AS Weight
    FROM Orders
    WHERE ProductID IS NOT NULL AND CustomerID IS NOT NULL
    GROUP BY ProductID, CustomerID
),
WeightSums AS (
    SELECT
        ProductID,
        SUM(Weight) AS TotalWeight,
        COUNT(*) AS AssociationCount
    FROM OrderProductBridge
    GROUP BY ProductID
)
SELECT
    ProductID,
    AssociationCount,
    ROUND(TotalWeight, 4) AS TotalWeight,
    CASE
        WHEN ABS(TotalWeight - 1.0) > 0.001
             THEN 'WEIGHT ERROR: Weights sum to ' + CAST(ROUND(TotalWeight, 4) AS VARCHAR)
                  + ' (should be 1.0)'
        ELSE 'Weights sum correctly to 1.0'
    END AS WeightFlag
FROM WeightSums
ORDER BY ABS(TotalWeight - 1.0) DESC;

-- Step 3: Many-to-many relationship cardinality analysis
-- How many products per customer (M:N relationship)
SELECT
    CustomerRelationship,
    COUNT(*) AS CustomerCount,
    ROUND(100.0 * COUNT(*) / SUM(COUNT(*)) OVER (), 1) AS Pct
FROM (
    SELECT
        CustomerID,
        COUNT(DISTINCT ProductID) AS ProductCount,
        CASE
            WHEN COUNT(DISTINCT ProductID) = 1 THEN '1 product (single purchaser)'
            WHEN COUNT(DISTINCT ProductID) BETWEEN 2 AND 3 THEN '2-3 products'
            WHEN COUNT(DISTINCT ProductID) BETWEEN 4 AND 6 THEN '4-6 products'
            ELSE '7+ products (multi-product customer)'
        END AS CustomerRelationship
    FROM Orders
    WHERE ProductID IS NOT NULL AND CustomerID IS NOT NULL
    GROUP BY CustomerID
) ClassifiedCustomers
GROUP BY CustomerRelationship
ORDER BY COUNT(*) DESC;

-- Step 4: Duplicate association detection in a bridge context
-- Duplicate: same CustomerID-ProductID combination appearing more than once
SELECT
    CustomerID,
    ProductID,
    COUNT(*) AS AssociationCount,
    MIN(CAST(OrderDate AS DATE)) AS FirstOrder,
    MAX(CAST(OrderDate AS DATE)) AS LastOrder,
    CASE
        WHEN COUNT(*) > 1
             THEN 'REPEATED: This customer ordered this product '
                  + CAST(COUNT(*) AS VARCHAR) + ' times (normal for repeat purchases)'
        ELSE 'Single association'
    END AS RepeatFlag
FROM Orders
WHERE CustomerID IS NOT NULL AND ProductID IS NOT NULL
GROUP BY CustomerID, ProductID
ORDER BY AssociationCount DESC;

-- Step 5: Validate fact-to-bridge join produces expected row count
SELECT
    'Orders grain (no join)' AS Description,
    COUNT(*) AS RowCount,
    ROUND(SUM(TotalAmount), 2) AS TotalRevenue
FROM Orders
UNION ALL
SELECT
    'After JOIN to Transactions (fan-out impact)',
    COUNT(*),
    ROUND(SUM(o.TotalAmount), 2)
FROM Orders o
JOIN Transactions t ON o.OrderID = t.OrderID
UNION ALL
SELECT
    'After correct aggregation (one row per order)',
    COUNT(DISTINCT o.OrderID),
    ROUND(SUM(o.TotalAmount), 2)
FROM Orders o
JOIN Transactions t ON o.OrderID = t.OrderID;
```

**Step 5 — Fan-out impact:**

## Explanation

**Fan-out: the silent double-counting mechanism**
When a fact table row joins to multiple rows in another table (1:many relationship), the fact row is replicated once per matched row. Any SUM computed on the replicated rows overcounts by the replication factor. Step 5 makes this concrete: joining Orders to Transactions without aggregation increases the row count from 20 to 27, inflating TotalRevenue from £27,610 to £37,274 — a 35% overstatement — purely from the join structure.

**Bridge table weighting**
In a genuine many-to-many bridge table (e.g., a campaign targets 3 segments), counting each fact row once per bridge association triples the total. The weighting factor (1/N for equal allocation) corrects this: each association contributes `SUM(Amount) × Weight` to the total, and the weights sum to 1.0 per campaign, producing the correct single-counted total. Step 2 validates that weights sum to 1.0 — if they sum to 1.5, the total will be 50% overstated.

**Many-to-many as a modelling decision**
Many-to-many relationships (customer ↔ product) in a star schema are handled by either: (1) a bridge table (fan-out risk if not weighted correctly), (2) collapsing to a single value (many-to-one by choosing the primary association), or (3) flattening into a list column. Step 3 profiles the actual M:N cardinality — if 90% of customers buy only 1 product, a bridge table is unnecessary complexity; if 40% of customers buy 7+ products, a bridge table is the correct design.

**Aggregate-first as the fan-out remedy**
The canonical remedy for fan-out risk is aggregate-first: compute the desired summary at the grain level before joining, then join the aggregated result. `SUM(t.Amount)` per `OrderID` in a CTE, then join to Orders, ensures each order's transactions are already summed before the join — producing one row per order regardless of how many transactions exist.

## Severity
**High** — Fan-out double-counting is one of the most financially significant data quality failures: it inflates reported revenue, transaction counts, and any aggregated metric by a fixed multiple that may be invisible to analysts who do not know the table's cardinality. A report showing £37M revenue when the correct figure is £27M is not a small rounding error — it is a fundamental modelling failure that can influence major business decisions.
