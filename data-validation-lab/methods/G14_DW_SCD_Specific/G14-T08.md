# G14-T08 — DW/SCD Specific | Data Lineage and Source Traceability

## ID
G14-T08

## Group
14 — DW/SCD Specific

## Type
Data Lineage and Source Traceability — Validating That Every Record Can Be Traced Back to Its Source

## Live Scenario
A data governance audit requires the BI team to answer: "For the £340,000 revenue figure on the Q2 board report, which source system records does it derive from?" Without data lineage, this question cannot be answered: the warehouse contains transformed, aggregated data with no direct link to the source records. When auditors find a £12,000 discrepancy, the team cannot identify which specific orders it relates to without re-running all transformations. Going forward, the team adds a `SourceSystemID`, `SourceRecordID`, and `LoadBatchID` column to every fact table. A lineage validation query verifies that these columns are populated, that the `SourceRecordID` values match valid source records, and that no two destination records claim the same source record (preventing duplicate loads).

## The Question
> Data lineage validation checks that every record in the data warehouse can be traced to its source: the originating system, the source record identifier, and the load batch that brought it in. SQL validates lineage by checking that lineage columns are populated, that source IDs are unique or follow the expected duplication pattern, and that all records from an expected source batch are present.
> **"Validate data lineage on Orders: verify that each order has a traceable source (using TransactionID as a proxy lineage key), detect any orders that cannot be traced to a transaction, identify any transaction that has been loaded more than once (duplicate lineage), and flag any orders with inconsistent lineage attributes."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Transactions** — `schemas/05_Transactions.csv`

## Solution Query

```sql
-- Step 1: Lineage coverage — which orders have traceable source records?
SELECT
    o.OrderID,
    o.CustomerID,
    o.TotalAmount,
    o.Status,
    -- Proxy lineage: does a matching transaction exist?
    t.TransactionID AS SourceTransactionID,
    t.TransactionDate AS SourceLoadDate,
    t.CorrelationID AS SourceCorrelationID,
    CASE
        WHEN t.TransactionID IS NULL
             THEN 'NO LINEAGE: Order cannot be traced to any transaction'
        WHEN t.CorrelationID IS NULL
             THEN 'PARTIAL LINEAGE: Transaction found but CorrelationID missing'
        ELSE 'Full lineage'
    END AS LineageFlag
FROM Orders o
LEFT JOIN Transactions t ON o.OrderID = t.OrderID
ORDER BY LineageFlag DESC;

-- Step 2: Duplicate lineage detection — same source record loaded more than once
WITH TransactionLinked AS (
    SELECT
        t.OrderID,
        t.TransactionID,
        t.CorrelationID,
        COUNT(*) OVER (PARTITION BY t.OrderID) AS TimesLoaded
    FROM Transactions t
    WHERE t.OrderID IS NOT NULL
)
SELECT
    OrderID,
    COUNT(DISTINCT TransactionID) AS TransactionCount,
    STRING_AGG(CAST(TransactionID AS VARCHAR), ', ') AS TransactionIDs,
    CASE
        WHEN COUNT(DISTINCT TransactionID) > 1
             THEN 'DUPLICATE LOAD: Order ID matched to multiple transactions — possible double-load'
        ELSE 'Single source transaction'
    END AS DuplicateLingeFlag
FROM TransactionLinked
GROUP BY OrderID
HAVING COUNT(DISTINCT TransactionID) > 1;

-- Step 3: CorrelationID as a batch identifier — which load batch brought each record?
SELECT
    t.CorrelationID AS LoadBatchID,
    COUNT(*) AS RecordsInBatch,
    MIN(CAST(t.TransactionDate AS DATE)) AS EarliestTxnDate,
    MAX(CAST(t.TransactionDate AS DATE)) AS LatestTxnDate,
    ROUND(SUM(t.Amount), 2) AS BatchTotal,
    COUNT(DISTINCT t.OrderID) AS UniqueOrders,
    CASE
        WHEN t.CorrelationID IS NULL
             THEN 'NULL BATCH: Records with no load batch identifier — lineage incomplete'
        WHEN COUNT(*) = 1
             THEN 'SINGLETON BATCH: Only one record in batch — verify this is expected'
        ELSE 'Normal batch'
    END AS BatchFlag
FROM Transactions t
GROUP BY t.CorrelationID
ORDER BY RecordsInBatch DESC;

-- Step 4: Source record integrity — SourceIP as a provenance attribute
SELECT
    SourceIP,
    COUNT(*) AS TxnCount,
    ROUND(100.0 * COUNT(*) / SUM(COUNT(*)) OVER (), 1) AS Pct,
    MIN(CAST(TransactionDate AS DATE)) AS FirstSeen,
    MAX(CAST(TransactionDate AS DATE)) AS LastSeen,
    ROUND(SUM(Amount), 2) AS TotalAmount,
    CASE
        WHEN SourceIP IS NULL
             THEN 'NO SOURCE IP: Provenance unknown'
        WHEN SourceIP LIKE '192.168.%' OR SourceIP LIKE '10.%'
             THEN 'INTERNAL IP: Record originated from internal system'
        WHEN SourceIP LIKE '127.%'
             THEN 'LOOPBACK: Record originated from localhost — test or ETL agent'
        ELSE 'EXTERNAL IP: Record from external source — verify'
    END AS SourceIPFlag
FROM Transactions
GROUP BY SourceIP
ORDER BY TxnCount DESC;

-- Step 5: End-to-end lineage audit — can we trace an order to a transaction to a source?
SELECT
    o.OrderID,
    o.TotalAmount AS OrderAmount,
    t.TransactionID,
    t.Amount AS TransactionAmount,
    t.Currency,
    t.SourceIP,
    t.CorrelationID,
    ROUND(ABS(o.TotalAmount - t.Amount), 2) AS AmountDiscrepancy,
    CASE
        WHEN t.TransactionID IS NULL
             THEN 'UNTRACED: No source transaction'
        WHEN ABS(o.TotalAmount - t.Amount) > 0.01
             THEN 'AMOUNT MISMATCH: Order amount differs from transaction — transformation error?'
        WHEN t.CorrelationID IS NULL
             THEN 'MISSING BATCH REF: Transaction has no batch correlation ID'
        WHEN t.SourceIP IS NULL
             THEN 'MISSING SOURCE: Transaction has no source IP — provenance unknown'
        ELSE 'TRACEABLE: Full lineage available'
    END AS LineageCompleteness
FROM Orders o
LEFT JOIN Transactions t ON o.OrderID = t.OrderID
ORDER BY LineageCompleteness DESC;
```

## Explanation

**Three-component lineage: source system, record ID, batch ID**
Complete data lineage requires knowing: (1) which source system the record came from (`SourceSystemID`); (2) the unique identifier of the record in that source system (`SourceRecordID`); and (3) which ETL load batch brought the record into the warehouse (`LoadBatchID`/`CorrelationID`). With all three, any record in the warehouse can be traced back to the exact source row and the exact time it was loaded.

**Duplicate lineage as a duplicate load indicator**
When the same `SourceRecordID` appears more than once in the destination, the source record was loaded multiple times. This happens when: the ETL watermark was reset and re-ran a completed period, a full reload was combined with an incremental load, or a retry mechanism loaded a batch twice after a partial failure. Unlike application-layer duplicates (same business event twice), these are ETL duplicates — the business event happened once but it was loaded twice.

**CorrelationID as load batch traceability**
A `CorrelationID` (or `BatchID`, `LoadID`) ties all records from the same ETL batch together. If a batch is found to contain errors, the CorrelationID enables targeted removal and re-load of exactly those records, without touching records from other batches. Without a batch ID, the only option is a full reload of the affected period.

**Amount discrepancy in lineage audit**
The order amount should match the transaction amount exactly (within rounding tolerance). A discrepancy indicates a transformation was applied during ETL — currency conversion, tax addition, discount application — that changed the amount without being documented. The lineage audit surfaces these transformations so they can be reviewed and verified against business rules.

## Severity
**Medium** — Data lineage is a governance and auditability requirement, not typically a day-to-day operational failure. However, in regulated industries (banking, insurance, pharmaceutical), the inability to trace a reported figure back to its source record is a compliance failure. Lineage validation ensures that every number in a report can be supported with a source-level audit trail when required by auditors or regulators.
