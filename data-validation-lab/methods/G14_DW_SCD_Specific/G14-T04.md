# G14-T04 — DW/SCD Specific | Late-Arriving Facts Detection

## ID
G14-T04

## Group
14 — DW/SCD Specific

## Type
Late-Arriving Facts Detection — Identifying Transactions That Arrive After Their Reporting Period Has Closed

## Live Scenario
A financial controller closes the books for Q1 on April 5th. The reporting system shows Q1 revenue of £4.2M. On April 19th, a batch of 340 orders from March arrives in the data warehouse — they were delayed in transit from an overseas subsidiary's system. These late-arriving facts post to the April load date (April 19th) but carry March order dates. The Q1 revenue report, already distributed to the board, now needs an amendment: the correct Q1 figure is £4.54M. More problematically, the Q1 SCD2 customer dimension has already been frozen — the late-arriving March orders must be joined to the April customer dimension state, not the March state they should have used. The late-arriving fact detector flags these 340 orders for special handling: either reopen Q1, post to April with a note, or create adjustment entries.

## The Question
> A late-arriving fact is a transaction that enters the data warehouse significantly after its event date — after the period it belongs to has been reported, closed, or audited. SQL detects late-arriving facts by comparing the transaction's business event date to the date the record was loaded into the warehouse, flagging records where the gap exceeds a threshold.
> **"Identify Orders where the OrderDate falls in a reporting period that is more than 30 days before the record appears in the system, compare late-arriving orders to on-time orders by period, and quantify the financial impact of late arrivals on closed reporting periods."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Transactions** — `schemas/05_Transactions.csv`

## Solution Query

```sql
-- Step 1: Detect late-arriving orders
-- Proxy: use TransactionDate from Transactions as the "load date"
-- Orders with TransactionDate significantly later than OrderDate are "late"
WITH OrderWithLoad AS (
    SELECT
        o.OrderID,
        o.CustomerID,
        o.ProductID,
        CAST(o.OrderDate AS DATE)     AS EventDate,
        o.TotalAmount,
        o.Status,
        YEAR(o.OrderDate)             AS EventYear,
        MONTH(o.OrderDate)            AS EventMonth,
        -- Use first matching transaction date as "load date" proxy
        MIN(CAST(t.TransactionDate AS DATE)) AS LoadDate
    FROM Orders o
    LEFT JOIN Transactions t ON o.OrderID = t.OrderID
    WHERE o.OrderDate IS NOT NULL
    GROUP BY o.OrderID, o.CustomerID, o.ProductID, o.OrderDate, o.TotalAmount, o.Status
),
WithLateness AS (
    SELECT
        *,
        DATEDIFF(DAY, EventDate, ISNULL(LoadDate, CAST(GETDATE() AS DATE))) AS DaysLate,
        -- Reporting period: YYYY-MM
        CAST(EventYear AS VARCHAR) + '-' + RIGHT('0' + CAST(EventMonth AS VARCHAR), 2)
            AS ReportingPeriod,
        -- Load period
        CAST(YEAR(ISNULL(LoadDate, GETDATE())) AS VARCHAR) + '-'
            + RIGHT('0' + CAST(MONTH(ISNULL(LoadDate, GETDATE())) AS VARCHAR), 2)
            AS LoadPeriod
    FROM OrderWithLoad
)
SELECT
    OrderID,
    EventDate,
    LoadDate,
    ReportingPeriod,
    LoadPeriod,
    DaysLate,
    TotalAmount,
    Status,
    CASE
        WHEN LoadDate IS NULL
             THEN 'UNLOADED: No transaction found — order not yet processed'
        WHEN DaysLate <= 0
             THEN 'ON-TIME: Loaded same day or before event date'
        WHEN DaysLate <= 7
             THEN 'MINOR DELAY: 1-7 days late'
        WHEN DaysLate <= 30
             THEN 'MODERATE DELAY: 8-30 days late'
        WHEN DaysLate <= 90
             THEN 'LATE-ARRIVING: 31-90 days late — period may be already closed'
        ELSE 'VERY LATE: >90 days — period definitely closed'
    END AS LatenessFlag
FROM WithLateness
ORDER BY DaysLate DESC;

-- Step 2: Late-arriving impact by reporting period
WITH OrderWithLoad AS (
    SELECT
        o.OrderID,
        CAST(o.OrderDate AS DATE) AS EventDate,
        o.TotalAmount,
        CAST(YEAR(o.OrderDate) AS VARCHAR) + '-'
            + RIGHT('0' + CAST(MONTH(o.OrderDate) AS VARCHAR), 2) AS ReportingPeriod,
        MIN(CAST(t.TransactionDate AS DATE)) AS LoadDate
    FROM Orders o
    LEFT JOIN Transactions t ON o.OrderID = t.OrderID
    WHERE o.OrderDate IS NOT NULL
    GROUP BY o.OrderID, o.OrderDate, o.TotalAmount
)
SELECT
    ReportingPeriod,
    COUNT(*) AS TotalOrders,
    COUNT(CASE WHEN DATEDIFF(DAY, EventDate, ISNULL(LoadDate, GETDATE())) > 30 THEN 1 END)
        AS LateArrivingOrders,
    ROUND(SUM(TotalAmount), 2) AS TotalRevenue,
    ROUND(SUM(CASE WHEN DATEDIFF(DAY, EventDate, ISNULL(LoadDate, GETDATE())) > 30
                   THEN TotalAmount ELSE 0 END), 2) AS LateRevenue,
    ROUND(100.0 * SUM(CASE WHEN DATEDIFF(DAY, EventDate, ISNULL(LoadDate, GETDATE())) > 30
                            THEN TotalAmount ELSE 0 END)
          / NULLIF(SUM(TotalAmount), 0), 1) AS LateRevenuePct
FROM OrderWithLoad
GROUP BY ReportingPeriod
ORDER BY ReportingPeriod;

-- Step 3: Compare on-time vs late volume by month
WITH OrderWithLoad AS (
    SELECT
        o.OrderID,
        CAST(o.OrderDate AS DATE) AS EventDate,
        o.TotalAmount,
        MIN(CAST(t.TransactionDate AS DATE)) AS LoadDate
    FROM Orders o
    LEFT JOIN Transactions t ON o.OrderID = t.OrderID
    WHERE o.OrderDate IS NOT NULL
    GROUP BY o.OrderID, o.OrderDate, o.TotalAmount
)
SELECT
    YEAR(EventDate) AS Yr,
    MONTH(EventDate) AS Mo,
    COUNT(*) AS TotalOrders,
    SUM(CASE WHEN DATEDIFF(DAY, EventDate, ISNULL(LoadDate, GETDATE())) <= 30 THEN 1 ELSE 0 END)
        AS OnTimeOrders,
    SUM(CASE WHEN DATEDIFF(DAY, EventDate, ISNULL(LoadDate, GETDATE())) > 30 THEN 1 ELSE 0 END)
        AS LateOrders,
    ROUND(SUM(CASE WHEN DATEDIFF(DAY, EventDate, ISNULL(LoadDate, GETDATE())) <= 30
                   THEN TotalAmount ELSE 0 END), 2) AS OnTimeRevenue,
    ROUND(SUM(CASE WHEN DATEDIFF(DAY, EventDate, ISNULL(LoadDate, GETDATE())) > 30
                   THEN TotalAmount ELSE 0 END), 2) AS LateRevenue
FROM OrderWithLoad
GROUP BY YEAR(EventDate), MONTH(EventDate)
ORDER BY Yr, Mo;
```

## Explanation

**Event date vs load date**
The event date (OrderDate) is when the business event occurred — this determines which reporting period the revenue belongs to. The load date is when the record entered the data warehouse — this determines which nightly load batch included the record. The gap between them is the lateness. In this example, TransactionDate is used as a proxy for load date; in production DW systems, a dedicated `LoadDate` or `InsertedDate` audit column captures the exact load timestamp.

**The closed period problem**
When a period is closed (financial close, audit sign-off, regulatory filing), late-arriving facts for that period must be handled explicitly: either reopen the period (rare, expensive), post to the current period with a restatement note, or accumulate in a late-arriving fact table. The query identifies which periods have already received late arrivals, enabling the finance team to assess whether restatement is required.

**SCD2 dimension mismatch for late arrivals**
Late-arriving facts cause a specific DW integrity problem with SCD2 dimensions: the correct dimension version for a March transaction is the March customer segment, but by the time the transaction arrives in April, the customer may have changed segment. The ETL must look up the effective dimension row as of the event date (not the load date) for late arrivals — a special handling path that most standard ETL tools do not apply by default.

**Lateness threshold as a business decision**
The 30-day threshold for "period closed" is illustrative. In practice: a 7-day threshold catches transactions that missed the weekly reconciliation; a 45-day threshold catches transactions that missed the month-end close; a 90-day threshold catches transactions that missed the quarter-end. The appropriate threshold should align with the organisation's financial reporting cadence.

## Severity
**High** — Late-arriving facts cause financial reporting errors and control failures. Revenue restated after the board pack is distributed undermines confidence in the reporting function. For regulated businesses (public companies, banks), late-arriving facts in closed periods may constitute a material misstatement requiring formal correction and disclosure.
