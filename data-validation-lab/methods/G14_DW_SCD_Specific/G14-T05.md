# G14-T05 — DW/SCD Specific | Aggregate Consistency Between Fact Layers

## ID
G14-T05

## Group
14 — DW/SCD Specific

## Type
Aggregate Consistency Between Fact Layers — Verifying That Summary Tables Match Their Underlying Detailed Facts

## Live Scenario
A retail data warehouse has three fact layers: a granular order-line fact table, a daily aggregate table (pre-computed sums by day and product), and a monthly aggregate table (pre-computed sums by month and category). After a data pipeline failure and restart, a data engineer notices that the January monthly total on the dashboard is £4.2M but the sum of January daily aggregates is £4.19M — a £10,000 discrepancy. Drilling to the granular layer shows the correct total is £4.23M. The daily aggregates miss a batch that was loaded after the daily aggregation job ran; the monthly aggregates picked up the corrected total but were not reloaded after the daily aggregation was corrected. The aggregate consistency check, run after every load, catches both discrepancies immediately rather than having them surface in a board presentation.

## The Question
> Aggregate consistency validation compares totals computed from detailed fact rows to totals stored in pre-computed summary tables. A consistent data warehouse ensures that `SUM(grain-level facts)` = `SUM(daily aggregates)` = `SUM(monthly aggregates)` for every reporting dimension and period combination.
> **"Validate aggregate consistency across the Orders data at three levels: individual orders, daily totals, and monthly totals — verify that summing upward from orders produces the same result as the pre-computed aggregates, and flag any period where the totals diverge."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Transactions** — `schemas/05_Transactions.csv`

## Solution Query

```sql
-- Step 1: Compute daily totals from the grain-level fact table
WITH DailyFromOrders AS (
    SELECT
        CAST(OrderDate AS DATE) AS Day,
        YEAR(OrderDate)         AS Yr,
        MONTH(OrderDate)        AS Mo,
        COUNT(*)                AS OrderCount,
        ROUND(SUM(TotalAmount), 2) AS DailyRevenue
    FROM Orders
    WHERE OrderDate IS NOT NULL AND TotalAmount IS NOT NULL
    GROUP BY CAST(OrderDate AS DATE), YEAR(OrderDate), MONTH(OrderDate)
),
-- Simulate pre-aggregated daily table (in production, this would be a separate table)
-- Here we use Transactions as the "daily summary" layer
DailyFromTransactions AS (
    SELECT
        CAST(TransactionDate AS DATE) AS Day,
        YEAR(TransactionDate)         AS Yr,
        MONTH(TransactionDate)        AS Mo,
        COUNT(*)                      AS TxnCount,
        ROUND(SUM(Amount), 2)         AS DailyAmount
    FROM Transactions
    WHERE TransactionDate IS NOT NULL AND Amount IS NOT NULL
    GROUP BY CAST(TransactionDate AS DATE), YEAR(TransactionDate), MONTH(TransactionDate)
)
SELECT
    COALESCE(o.Day, t.Day)  AS Day,
    o.OrderCount,
    o.DailyRevenue          AS OrderLayerRevenue,
    t.TxnCount,
    t.DailyAmount           AS TxnLayerAmount,
    ROUND(ISNULL(o.DailyRevenue, 0) - ISNULL(t.DailyAmount, 0), 2) AS DailyVariance,
    CASE
        WHEN o.Day IS NULL
             THEN 'TRANSACTION ONLY: Day has transactions but no orders'
        WHEN t.Day IS NULL
             THEN 'ORDER ONLY: Day has orders but no transactions'
        WHEN ABS(ISNULL(o.DailyRevenue, 0) - ISNULL(t.DailyAmount, 0)) > 1.00
             THEN 'DAILY VARIANCE: Order revenue and transaction amount differ by >'
                  + CAST(ROUND(ABS(o.DailyRevenue - t.DailyAmount), 2) AS VARCHAR)
        ELSE 'Balanced'
    END AS DayConsistencyFlag
FROM DailyFromOrders o
FULL OUTER JOIN DailyFromTransactions t ON o.Day = t.Day
ORDER BY COALESCE(o.Day, t.Day);

-- Step 2: Monthly roll-up consistency
WITH MonthlyFromOrders AS (
    SELECT
        YEAR(OrderDate) AS Yr, MONTH(OrderDate) AS Mo,
        COUNT(*) AS OrderCount,
        ROUND(SUM(TotalAmount), 2) AS MonthlyRevenue
    FROM Orders
    WHERE OrderDate IS NOT NULL AND TotalAmount IS NOT NULL
    GROUP BY YEAR(OrderDate), MONTH(OrderDate)
),
MonthlyFromTransactions AS (
    SELECT
        YEAR(TransactionDate) AS Yr, MONTH(TransactionDate) AS Mo,
        COUNT(*) AS TxnCount,
        ROUND(SUM(Amount), 2) AS MonthlyAmount
    FROM Transactions
    WHERE TransactionDate IS NOT NULL AND Amount IS NOT NULL
    GROUP BY YEAR(TransactionDate), MONTH(TransactionDate)
)
SELECT
    COALESCE(o.Yr, t.Yr)  AS Yr,
    COALESCE(o.Mo, t.Mo)  AS Mo,
    ISNULL(o.OrderCount, 0)     AS OrderCount,
    ISNULL(o.MonthlyRevenue, 0) AS OrderRevenue,
    ISNULL(t.TxnCount, 0)       AS TxnCount,
    ISNULL(t.MonthlyAmount, 0)  AS TxnAmount,
    ROUND(ISNULL(o.MonthlyRevenue, 0) - ISNULL(t.MonthlyAmount, 0), 2) AS MonthlyVariance,
    ROUND(100.0 * ABS(ISNULL(o.MonthlyRevenue, 0) - ISNULL(t.MonthlyAmount, 0))
          / NULLIF(ISNULL(o.MonthlyRevenue, 0), 0), 1) AS VariancePct,
    CASE
        WHEN ABS(ISNULL(o.MonthlyRevenue, 0) - ISNULL(t.MonthlyAmount, 0)) > 100
             THEN 'MONTHLY VARIANCE ALERT: >£100 difference between order and transaction layers'
        WHEN ABS(ISNULL(o.MonthlyRevenue, 0) - ISNULL(t.MonthlyAmount, 0)) > 0.01
             THEN 'MINOR VARIANCE: <£100 difference — rounding or timing'
        ELSE 'Consistent'
    END AS MonthFlag
FROM MonthlyFromOrders o
FULL OUTER JOIN MonthlyFromTransactions t ON o.Yr = t.Yr AND o.Mo = t.Mo
ORDER BY Yr, Mo;

-- Step 3: Grand total cross-check
SELECT
    'Orders.TotalAmount'          AS Source,
    COUNT(*) AS RowCount,
    ROUND(SUM(TotalAmount), 2)    AS GrandTotal
FROM Orders WHERE TotalAmount IS NOT NULL
UNION ALL
SELECT
    'Transactions.Amount',
    COUNT(*),
    ROUND(SUM(Amount), 2)
FROM Transactions WHERE Amount IS NOT NULL;

-- Step 4: Count consistency check — orders vs transactions
WITH OrderCounts AS (
    SELECT
        YEAR(OrderDate) AS Yr,
        MONTH(OrderDate) AS Mo,
        COUNT(*) AS Orders
    FROM Orders WHERE OrderDate IS NOT NULL
    GROUP BY YEAR(OrderDate), MONTH(OrderDate)
),
TxnCounts AS (
    SELECT
        YEAR(TransactionDate) AS Yr,
        MONTH(TransactionDate) AS Mo,
        COUNT(*) AS Transactions
    FROM Transactions WHERE TransactionDate IS NOT NULL
    GROUP BY YEAR(TransactionDate), MONTH(TransactionDate)
)
SELECT
    COALESCE(o.Yr, t.Yr) AS Yr,
    COALESCE(o.Mo, t.Mo) AS Mo,
    ISNULL(o.Orders, 0)       AS OrderCount,
    ISNULL(t.Transactions, 0) AS TxnCount,
    ISNULL(t.Transactions, 0) - ISNULL(o.Orders, 0) AS CountDiff,
    CASE
        WHEN ISNULL(t.Transactions, 0) > ISNULL(o.Orders, 0)
             THEN 'MORE TRANSACTIONS THAN ORDERS: Possible duplicate payments or split transactions'
        WHEN ISNULL(t.Transactions, 0) < ISNULL(o.Orders, 0)
             THEN 'FEWER TRANSACTIONS THAN ORDERS: Some orders have no payment record'
        ELSE 'Counts match'
    END AS CountFlag
FROM OrderCounts o
FULL OUTER JOIN TxnCounts t ON o.Yr = t.Yr AND o.Mo = t.Mo
ORDER BY Yr, Mo;
```

## Explanation

**The three-layer consistency invariant**
In a layered DW architecture, totals must agree across all layers: `grain-level SUM = daily aggregate SUM = monthly aggregate SUM = quarterly aggregate SUM`. A discrepancy between any two layers indicates a loading failure, a process ordering error (aggregates computed before the grain load was complete), or a filter difference (the aggregate excludes records the grain includes).

**FULL OUTER JOIN for completeness**
Using `FULL OUTER JOIN` between the two fact layers ensures that periods present in one but absent from the other are detected. A LEFT JOIN would miss cases where Transaction periods exist without corresponding Order periods (unmatched transactions); a RIGHT JOIN would miss the reverse. Only FULL OUTER JOIN catches both simultaneously.

**Variance percentage for relative materialit**
A £100 variance on a £100,000 period total (0.1%) is immaterial; the same £100 variance on a £1,000 period total (10%) is material. `ABS(variance) / total × 100` normalises for scale. The threshold should align with the organisation's materiality policy — typically 0.1%–1% for financial reporting, tighter for regulatory submissions.

**Count vs amount consistency**
Step 4 checks count consistency (number of orders vs number of transactions) separately from amount consistency. A count match with an amount mismatch indicates individual amounts differ; an amount match with a count mismatch indicates duplicate or split records that net out. These two failure modes have different root causes and different remediation paths.

## Severity
**High** — Aggregate inconsistency is the most common DW data quality failure in production environments. It arises from partial loads, process ordering failures, and incremental refresh gaps. Undetected inconsistency means analysts at different layers of the data warehouse see different numbers for the same metric, destroying confidence in the data platform and forcing manual reconciliation work before every board meeting.
