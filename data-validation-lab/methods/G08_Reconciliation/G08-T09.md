# G08-T09 — Reconciliation | Duplicate Payment Detection

## ID
G08-T09

## Group
8 — Reconciliation

## Type
Duplicate Payment Detection — The Same Invoice Paid More Than Once

## Live Scenario
A manufacturing company processes supplier invoices through an accounts payable system. A supplier resubmits invoice INV-2847 after not receiving payment within 30 days. The AP team, unable to find the original in the system (it was filed under a slightly different supplier name), processes the second submission as a new invoice. Both are paid via BACS. The duplicate is discovered three months later when the supplier's account is reconciled: the supplier's statement shows two credits of £24,600 each, but only one invoice. Recovering the overpayment takes four weeks of supplier negotiation. In the same period, six similar duplicates totalling £87,400 are found across other suppliers.

## The Question
> Duplicate payments arise when the same invoice is paid multiple times — exactly or with minor variations (different supplier name spelling, different invoice date entry). SQL detects duplicates by grouping on identifying keys and finding groups with count > 1, as well as near-duplicates using amount + date proximity.
> **"Find all duplicate and near-duplicate Transactions — exact duplicates sharing OrderID and Amount, and near-duplicates with the same Amount within a short time window — and calculate the total overpayment exposure."**

## Table Reference
**Transactions** — `schemas/05_Transactions.csv`
**Orders** — `schemas/02_Orders.csv`

## Solution Query

```sql
-- Step 1: Exact duplicates — same OrderID and Amount paid more than once
WITH ExactDuplicates AS (
    SELECT
        OrderID,
        Amount,
        Currency,
        COUNT(*)                                                AS PaymentCount,
        MIN(TransactionDate)                                    AS FirstPayment,
        MAX(TransactionDate)                                    AS LastPayment,
        DATEDIFF(DAY, MIN(TransactionDate), MAX(TransactionDate)) AS DaysBetweenPayments,
        SUM(Amount)                                             AS TotalPaid,
        SUM(Amount) - Amount                                    AS OverpaymentAmount,
        STRING_AGG(CAST(TransactionID AS VARCHAR), ', ')        AS TransactionIDs
    FROM Transactions
    WHERE Amount > 0
    GROUP BY OrderID, Amount, Currency
    HAVING COUNT(*) > 1
)
SELECT
    ed.OrderID,
    o.TotalAmount AS InvoiceAmount,
    ed.Amount AS EachPayment,
    ed.PaymentCount,
    ed.TotalPaid,
    ed.OverpaymentAmount,
    ed.FirstPayment,
    ed.LastPayment,
    ed.DaysBetweenPayments,
    ed.TransactionIDs,
    CASE
        WHEN ed.DaysBetweenPayments = 0
             THEN 'SAME-DAY DUPLICATE: Possible system double-submit'
        WHEN ed.DaysBetweenPayments <= 7
             THEN 'WEEKLY DUPLICATE: Likely re-submission of unpaid invoice'
        ELSE 'OLD DUPLICATE: Supplier resubmission or manual re-entry'
    END AS DuplicateType
FROM ExactDuplicates ed
LEFT JOIN Orders o ON ed.OrderID = o.OrderID
ORDER BY ed.OverpaymentAmount DESC;

-- Step 2: Near-duplicate payments — same amount within 5 days (different OrderID)
SELECT
    t1.TransactionID AS FirstTxID,
    t1.OrderID       AS FirstOrderID,
    t1.Amount,
    t1.TransactionDate AS FirstDate,
    t2.TransactionID AS SecondTxID,
    t2.OrderID       AS SecondOrderID,
    t2.TransactionDate AS SecondDate,
    DATEDIFF(DAY, t1.TransactionDate, t2.TransactionDate) AS DaysBetween,
    'NEAR-DUPLICATE: Same amount, different order, within 5 days — investigate' AS Flag
FROM Transactions t1
JOIN Transactions t2
    ON  t1.Amount = t2.Amount
    AND t1.Currency = t2.Currency
    AND t1.TransactionID < t2.TransactionID  -- avoid self-join and mirror rows
    AND t2.OrderID <> t1.OrderID
    AND DATEDIFF(DAY, t1.TransactionDate, t2.TransactionDate) BETWEEN 0 AND 5
WHERE t1.Amount > 0
ORDER BY t1.Amount DESC, DaysBetween;

-- Step 3: Orders with more transactions than expected (ratio > 1)
SELECT
    o.OrderID,
    o.TotalAmount,
    o.Status,
    COUNT(t.TransactionID) AS TransactionCount,
    SUM(t.Amount)          AS TotalPaid,
    SUM(t.Amount) - o.TotalAmount AS ExcessPaid,
    CASE
        WHEN COUNT(t.TransactionID) = 1 THEN 'Normal: one transaction per order'
        WHEN COUNT(t.TransactionID) = 2 AND SUM(t.Amount) = o.TotalAmount
             THEN 'Split payment: two transactions summing to order total'
        WHEN SUM(t.Amount) > o.TotalAmount
             THEN 'OVERPAID: ' + CAST(ROUND(SUM(t.Amount) - o.TotalAmount, 2) AS VARCHAR) + ' excess'
        ELSE 'Multiple transactions — verify split payment intent'
    END AS PaymentStatus
FROM Orders o
LEFT JOIN Transactions t ON o.OrderID = t.OrderID
WHERE o.Status NOT IN ('Cancelled')
GROUP BY o.OrderID, o.TotalAmount, o.Status
HAVING COUNT(t.TransactionID) > 1
ORDER BY ExcessPaid DESC;

-- Step 4: Total duplicate payment exposure
SELECT
    COUNT(*)                         AS DuplicateOrderCount,
    SUM(OverpaymentAmount)           AS TotalOverpaymentExposure,
    AVG(OverpaymentAmount)           AS AvgOverpayment,
    MAX(OverpaymentAmount)           AS LargestDuplicate
FROM (
    SELECT
        OrderID,
        Amount,
        Currency,
        COUNT(*) AS PaymentCount,
        SUM(Amount) - Amount AS OverpaymentAmount
    FROM Transactions
    WHERE Amount > 0
    GROUP BY OrderID, Amount, Currency
    HAVING COUNT(*) > 1
) Duplicates;
```

## Expected Output

|---|---|---|---|---|---|
| 1005 | 450.00 | 425.00 | 2 | 425.00 | WEEKLY DUPLICATE: Likely re-submission of unpaid invoice |

**Step 3 — Orders with multiple transactions:**
| OrderID | TotalAmount | TransactionCount | TotalPaid | ExcessPaid | PaymentStatus |
|---|---|---|---|---|---|
| 1005 | 450.00 | 2 | 850.00 | 400.00 | OVERPAID: 400.00 excess |
| 1007 | 2400.00 | 2 | 2400.00 | 0.00 | Split payment: two transactions summing to order total |

## Explanation

**Exact duplicate detection: GROUP BY + HAVING COUNT > 1**
The core pattern: group on the identifying key set (OrderID + Amount + Currency) and filter for count > 1. `SUM(Amount) - Amount` gives the overpayment (total paid minus what should have been paid once). `STRING_AGG` collects all TransactionIDs for the duplicate group so they can be reviewed.

**Near-duplicate self-join**
Step 2 uses a self-join with `t1.TransactionID < t2.TransactionID` to find pairs. This eliminates duplicate pairs (A,B and B,A) appearing twice. The `BETWEEN 0 AND 5` window catches the common pattern of a supplier resubmitting an invoice within a week of non-payment.

**Split payment vs duplicate payment**
Not all multi-transaction orders are duplicates — split payments are legitimate (e.g., deposit plus balance). Step 3 distinguishes: if two transactions sum exactly to the order total, it's a split payment; if they sum to more than the order total, it's an overpayment. The `CASE` statement surfaces this distinction clearly.

## Severity
**High** — Duplicate payments are a direct financial loss. Unlike data errors, they represent actual cash transferred to the counterparty, which must be recovered through supplier credit notes or refund requests. At scale, duplicate payment rates of 0.1–0.3% of AP spend are common without controls, representing millions of pounds in recoverable cash.
