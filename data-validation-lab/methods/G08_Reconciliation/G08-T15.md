# G08-T15 — Reconciliation | Control Total Verification

## ID
G08-T15

## Group
8 — Reconciliation

## Type
Control Total Verification — Batch or File Total Does Not Match Sum of Detail Records

## Live Scenario
A payroll bureau processes 1,200 employee salary payments via BACS. The payment file contains a control record at the end: total record count = 1,200 and total payment amount = £3,847,200. The bureau's finance system imports the file and posts 1,198 payments totalling £3,842,600 — two records were rejected due to invalid sort codes but the rejection was not surfaced in the UI. The bureau submits the file to the bank with the original control totals (1,200 records, £3,847,200). The bank receives all 1,200 entries. Two employees with invalid sort codes are allocated to a default sort code and paid to the wrong account. When the employees do not receive their salary, they contact HR — two weeks after payday.

## The Question
> Control total verification checks that the number of records and the sum of key values in a batch or file match a pre-agreed header/trailer record. SQL implements this by comparing COUNT(*) and SUM(Amount) against declared control totals and flagging any difference.
> **"Verify that the total count and total value of Transactions for each month matches expected control totals, and produce a batch verification report showing any discrepancies between the declared totals and the actual data."**

## Table Reference
**Transactions** — `schemas/05_Transactions.csv`
**Orders** — `schemas/02_Orders.csv`

## Solution Query

```sql
-- Step 1: Compute actual batch totals and compare to expected control values
-- (In practice, expected totals come from a ControlTotals reference table or file header)
DECLARE @ExpectedCount  INT           = 25;     -- Declared record count
DECLARE @ExpectedAmount DECIMAL(18,2) = 28590.00; -- Declared total amount
DECLARE @Tolerance      DECIMAL(10,2) = 0.00;  -- Zero tolerance for batch files

WITH ActualTotals AS (
    SELECT
        COUNT(*)    AS ActualCount,
        SUM(Amount) AS ActualAmount,
        MIN(TransactionDate) AS EarliestDate,
        MAX(TransactionDate) AS LatestDate
    FROM Transactions
    WHERE Amount > 0
)
SELECT
    @ExpectedCount              AS DeclaredCount,
    @ExpectedAmount             AS DeclaredAmount,
    ActualCount,
    ActualAmount,
    @ExpectedCount - ActualCount            AS CountDiscrepancy,
    @ExpectedAmount - ActualAmount          AS AmountDiscrepancy,
    CASE
        WHEN @ExpectedCount = ActualCount AND ABS(@ExpectedAmount - ActualAmount) <= @Tolerance
             THEN 'VERIFIED: Batch control totals match'
        WHEN @ExpectedCount <> ActualCount
             THEN 'RECORD COUNT MISMATCH: Expected '
                  + CAST(@ExpectedCount AS VARCHAR) + ', found '
                  + CAST(ActualCount AS VARCHAR)
                  + ' (' + CAST(@ExpectedCount - ActualCount AS VARCHAR) + ' difference)'
        ELSE 'AMOUNT MISMATCH: Declared '
             + CAST(@ExpectedAmount AS VARCHAR)
             + ', actual ' + CAST(ActualAmount AS VARCHAR)
    END AS VerificationResult
FROM ActualTotals;

-- Step 2: Monthly batch control totals (treat each month as a batch)
SELECT
    YEAR(TransactionDate)  AS BatchYear,
    MONTH(TransactionDate) AS BatchMonth,
    COUNT(*)               AS RecordCount,
    SUM(Amount)            AS BatchTotal,
    SUM(CASE WHEN Amount > 0 THEN Amount ELSE 0 END) AS PositiveTotal,
    SUM(CASE WHEN Amount < 0 THEN Amount ELSE 0 END) AS NegativeTotal,
    COUNT(CASE WHEN Amount IS NULL THEN 1 END)        AS NullAmounts,
    COUNT(CASE WHEN OrderID IS NULL THEN 1 END)       AS OrphanCount,
    -- Hash-like checksum for change detection
    CHECKSUM_AGG(CHECKSUM(TransactionID, Amount, Currency)) AS BatchChecksum
FROM Transactions
GROUP BY YEAR(TransactionDate), MONTH(TransactionDate)
ORDER BY BatchYear, BatchMonth;

-- Step 3: Detect gaps in sequential TransactionID (missing records)
WITH SequenceCheck AS (
    SELECT
        TransactionID,
        LAG(TransactionID) OVER (ORDER BY TransactionID) AS PrevID,
        TransactionID - LAG(TransactionID) OVER (ORDER BY TransactionID) AS Gap
    FROM Transactions
)
SELECT
    PrevID + 1 AS GapStartsAt,
    TransactionID - 1 AS GapEndsAt,
    Gap - 1 AS MissingRecords,
    'SEQUENCE GAP: ' + CAST(Gap - 1 AS VARCHAR) + ' TransactionID(s) missing between '
        + CAST(PrevID AS VARCHAR) + ' and ' + CAST(TransactionID AS VARCHAR) AS GapDescription
FROM SequenceCheck
WHERE Gap > 1
ORDER BY PrevID;

-- Step 4: Hash-based integrity check — verify a set of records has not been altered
-- Store BINARY_CHECKSUM results for audit trail comparison
SELECT
    COUNT(*)                          AS RecordCount,
    SUM(Amount)                       AS TotalAmount,
    CHECKSUM_AGG(
        BINARY_CHECKSUM(TransactionID, OrderID, Amount, Currency, TransactionDate)
    )                                 AS IntegrityHash,
    CAST(GETDATE() AS DATE)           AS VerificationDate,
    'Run this query after each batch load to verify data integrity' AS Note
FROM Transactions;

-- Step 5: Cross-reference — orders vs transaction counts should stay within expected ratio
SELECT
    YEAR(o.OrderDate)  AS Yr,
    MONTH(o.OrderDate) AS Mo,
    COUNT(DISTINCT o.OrderID)   AS OrderCount,
    COUNT(t.TransactionID)      AS TxCount,
    ROUND(CAST(COUNT(t.TransactionID) AS FLOAT)
          / NULLIF(COUNT(DISTINCT o.OrderID), 0), 2) AS TxToOrderRatio,
    SUM(o.TotalAmount)          AS ExpectedValue,
    SUM(t.Amount)               AS ActualValue,
    ROUND(SUM(o.TotalAmount) - ISNULL(SUM(t.Amount),0), 2) AS Variance,
    CASE
        WHEN ABS(SUM(o.TotalAmount) - ISNULL(SUM(t.Amount),0)) < 1.00
             THEN 'Batch balanced'
        ELSE 'BATCH VARIANCE: ' + CAST(ROUND(SUM(o.TotalAmount) - ISNULL(SUM(t.Amount),0),2) AS VARCHAR)
    END AS BatchStatus
FROM Orders o
LEFT JOIN Transactions t ON o.OrderID = t.OrderID
WHERE o.Status NOT IN ('Cancelled')
GROUP BY YEAR(o.OrderDate), MONTH(o.OrderDate)
ORDER BY Yr, Mo;
```

## Explanation

**Control total as a hash equivalent**
A control total (record count + sum of amounts) is a simple form of data integrity check. Any record lost in transit, truncated, or reordered causes either the count or the sum to differ from the declared control values. Unlike cryptographic hashes, control totals are easily human-readable and manually verifiable.

**CHECKSUM_AGG for change detection**
`CHECKSUM_AGG(BINARY_CHECKSUM(...))` produces a single integer representing the aggregate state of all specified columns. If any record is altered after the initial hash is computed, the checksum changes. Step 4 produces a batch hash that can be stored and re-run to verify no post-load alterations occurred — an audit trail mechanism.

**Sequence gap detection**
Sequential IDs with gaps indicate missing records (deleted, rejected, or never loaded). `LAG(TransactionID) OVER (ORDER BY TransactionID)` returns the previous ID; `Gap = CurrentID - PrevID - 1` counts missing IDs between them. A gap of 0 means consecutive; a gap of 2 means one missing record; etc.

**Zero tolerance for batch files**
Unlike business data (where ±£0.01 rounding tolerance is acceptable), batch file control totals must match exactly. `@Tolerance = 0.00` enforces this. A BACS payment file with a £5 discrepancy between declared and actual total will be rejected by the clearing house; a payroll file with one missing record means one employee goes unpaid.

## Severity
**Critical** — Batch control total failures indicate data loss in transit or rejected records. In payment processing, a mismatch means employees or suppliers may not receive payment. In financial reporting, a batch count mismatch invalidates the completeness assertion — the most important assertion in financial statement audits.
