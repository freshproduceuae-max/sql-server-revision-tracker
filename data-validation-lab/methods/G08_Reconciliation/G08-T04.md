# G08-T04 — Reconciliation | Period Closing Balance

## ID
G08-T04

## Group
8 — Reconciliation

## Type
Period Closing Balance — End-of-Period Aggregate Does Not Match Expected Running Total

## Live Scenario
A stock management system tracks inventory movements daily. Each day's closing stock balance should equal: previous day's closing balance + receipts received − units sold. A batch process computes daily closing balances and stores them in a `DailyInventory` snapshot table. A database backup restore — needed to fix an unrelated issue — restores the snapshot table to a state from 3 days prior without also restoring the transactions for those 3 days. The closing balance from 3 days ago is now the "current" balance, but 3 days of movements (47 receipts, 129 sales) are not reflected. Stock reports show 82 more units than physically exist, causing overselling of a critical component.

## The Question
> Period closing balances must satisfy the accounting identity: `closing = opening + movements`. SQL validates this by recomputing the expected closing balance from its components and comparing it to the stored value.
> **"For each period, validate that the closing balance equals the opening balance plus net movements (credits minus debits), and flag any period where the stored balance differs from the recomputed balance."**

## Table Reference
**Transactions** — `schemas/05_Transactions.csv`
**Orders** — `schemas/02_Orders.csv`

## Solution Query

```sql
-- Step 1: Compute running total of transactions by month and compare to expected progression
WITH MonthlyMovements AS (
    SELECT
        YEAR(TransactionDate)  AS Yr,
        MONTH(TransactionDate) AS Mo,
        SUM(CASE WHEN Amount > 0 THEN Amount ELSE 0 END) AS Credits,
        SUM(CASE WHEN Amount < 0 THEN Amount ELSE 0 END) AS Debits,
        SUM(Amount) AS NetMovement,
        COUNT(*) AS TxCount
    FROM Transactions
    WHERE TransactionDate IS NOT NULL
    GROUP BY YEAR(TransactionDate), MONTH(TransactionDate)
),
CumulativeBalance AS (
    SELECT
        Yr,
        Mo,
        Credits,
        Debits,
        NetMovement,
        TxCount,
        SUM(NetMovement) OVER (ORDER BY Yr, Mo
                               ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)
            AS RunningClosingBalance,
        LAG(SUM(NetMovement) OVER (ORDER BY Yr, Mo
                                   ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW))
            OVER (ORDER BY Yr, Mo) AS PrevClosingBalance
    FROM MonthlyMovements
)
SELECT
    Yr AS Year,
    Mo AS Month,
    Credits AS PeriodCredits,
    Debits AS PeriodDebits,
    NetMovement,
    ISNULL(PrevClosingBalance, 0) AS OpeningBalance,
    ISNULL(PrevClosingBalance, 0) + NetMovement AS RecomputedClosing,
    RunningClosingBalance AS RunningTotal,
    -- If stored closing balance existed, compare here:
    -- ABS(StoredClosing - RecomputedClosing) AS Variance
    CASE
        WHEN ABS(RunningClosingBalance -
                 (ISNULL(PrevClosingBalance, 0) + NetMovement)) < 0.01
             THEN 'Balances correctly'
        ELSE 'PERIOD BALANCE ERROR'
    END AS BalanceCheck
FROM CumulativeBalance
ORDER BY Year, Month;

-- Step 2: Period-over-period movement analysis
WITH PeriodTotals AS (
    SELECT
        YEAR(TransactionDate) AS Yr,
        MONTH(TransactionDate) AS Mo,
        SUM(Amount) AS PeriodNet,
        SUM(SUM(Amount)) OVER (ORDER BY YEAR(TransactionDate), MONTH(TransactionDate)
                               ROWS UNBOUNDED PRECEDING) AS CumulativeNet
    FROM Transactions
    WHERE TransactionDate IS NOT NULL
    GROUP BY YEAR(TransactionDate), MONTH(TransactionDate)
)
SELECT
    Yr,
    Mo,
    PeriodNet,
    CumulativeNet,
    LAG(CumulativeNet) OVER (ORDER BY Yr, Mo) AS PrevCumulative,
    CumulativeNet - LAG(CumulativeNet) OVER (ORDER BY Yr, Mo) AS MovementThisPeriod,
    CASE
        WHEN ABS((CumulativeNet - LAG(CumulativeNet) OVER (ORDER BY Yr, Mo)) - PeriodNet) < 0.01
             THEN 'Consistent: cumulative movement matches period total'
        ELSE 'INCONSISTENCY: Cumulative jump ≠ period total'
    END AS CumulativeConsistency
FROM PeriodTotals
ORDER BY Yr, Mo;

-- Step 3: Day-level closing balance for Transactions
WITH DailyMovements AS (
    SELECT
        CAST(TransactionDate AS DATE) AS TxDay,
        SUM(CASE WHEN Amount > 0 THEN Amount ELSE 0 END) AS DailyCredits,
        SUM(CASE WHEN Amount < 0 THEN ABS(Amount) ELSE 0 END) AS DailyDebits,
        SUM(Amount) AS DailyNet
    FROM Transactions
    WHERE TransactionDate IS NOT NULL
    GROUP BY CAST(TransactionDate AS DATE)
)
SELECT
    TxDay,
    DailyCredits,
    DailyDebits,
    DailyNet,
    SUM(DailyNet) OVER (ORDER BY TxDay ROWS UNBOUNDED PRECEDING) AS RunningBalance
FROM DailyMovements
ORDER BY TxDay;

-- Step 4: Detect missing periods in the balance sequence
WITH PeriodList AS (
    SELECT DISTINCT
        YEAR(TransactionDate) AS Yr,
        MONTH(TransactionDate) AS Mo
    FROM Transactions
),
PeriodWithLag AS (
    SELECT
        Yr, Mo,
        LAG(Yr) OVER (ORDER BY Yr, Mo) AS PrevYr,
        LAG(Mo) OVER (ORDER BY Yr, Mo) AS PrevMo
    FROM PeriodList
)
SELECT
    Yr, Mo, PrevYr, PrevMo,
    CASE
        WHEN PrevYr IS NULL THEN 'First period'
        WHEN (Yr * 12 + Mo) - (PrevYr * 12 + PrevMo) = 1 THEN 'Consecutive — OK'
        ELSE 'GAP: Missing period between ' + CAST(PrevMo AS VARCHAR) + '/'
             + CAST(PrevYr AS VARCHAR) + ' and ' + CAST(Mo AS VARCHAR) + '/'
             + CAST(Yr AS VARCHAR)
    END AS PeriodContinuity
FROM PeriodWithLag
WHERE (Yr * 12 + Mo) - (PrevYr * 12 + PrevMo) > 1
   OR PrevYr IS NULL;
```

## Explanation

**The accounting identity: closing = opening + net movements**
This identity is the foundation of double-entry bookkeeping and inventory accounting. Any stored closing balance must satisfy it. If `stored_closing ≠ prev_closing + net_movements`, either the stored balance is wrong or the movement records are incomplete.

**Cumulative SUM window function**
`SUM(NetMovement) OVER (ORDER BY Yr, Mo ROWS UNBOUNDED PRECEDING)` computes a running total — the cumulative balance at the end of each period. `ROWS UNBOUNDED PRECEDING` specifies that the window covers all prior rows plus the current row in the ORDER BY sequence.

**LAG for period-over-period checks**
`LAG(CumulativeNet) OVER (ORDER BY Yr, Mo)` returns the previous period's cumulative balance. The current period's net movement should equal `CurrentCumulative - PrevCumulative`. Step 2 validates this identity — if the movement for period N plus the previous cumulative doesn't equal the new cumulative, the running total has an error.

**Missing period detection**
Step 4 detects gaps in the period sequence. `(Yr * 12 + Mo)` converts year-month to a single comparable integer; the difference between consecutive periods should be exactly 1. A gap of 2 or more means at least one period has no transactions — which may be valid (no activity) or indicate missing data.

## Severity
**High** — Period closing balance errors in accounting systems cause trial balance failures, audit qualifications, and incorrect financial statements. In inventory systems, an incorrect closing balance drives all subsequent procurement, production planning, and stock reporting.
