# G08-T10 — Reconciliation | Aggregation Level Mismatch

## ID
G08-T10

## Group
8 — Reconciliation

## Type
Aggregation Level Mismatch — Summary Totals Computed at Wrong Granularity Causing Double-Counting

## Live Scenario
A sales dashboard query joins the Orders table (one row per order) to the Transactions table (multiple rows per order) to show monthly revenue. The developer writes `SUM(o.TotalAmount)` after the join, not realising the join fans out each order row to match multiple transaction rows. An order worth £1,200 with three transactions appears three times in the join result; its contribution to the SUM is £3,600 instead of £1,200. The dashboard shows monthly revenue of £47,800 against a true figure of £31,200 — a 53% overstatement. The error persists for four months before a finance analyst cross-checks the dashboard against the trial balance.

## The Question
> Aggregation level mismatch (fan-out double-counting) occurs when a join multiplies header rows by the number of detail rows, then aggregates the header value. The fix is to aggregate the detail table first, then join to the header — or to aggregate the header independently. SQL detects fan-out by comparing COUNT(DISTINCT) to COUNT(*) in the join result.
> **"Demonstrate the fan-out double-counting error when joining Orders to Transactions, quantify the overstatement, and produce the correct aggregation using the aggregate-first pattern."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Transactions** — `schemas/05_Transactions.csv`

## Solution Query

```sql
-- Step 1: Demonstrate the FAN-OUT error — wrong approach (illustrative)
-- This query OVER-COUNTS order totals when orders have multiple transactions
SELECT
    YEAR(o.OrderDate)   AS OrderYear,
    MONTH(o.OrderDate)  AS OrderMonth,
    COUNT(*)            AS RowCount,               -- Inflated by fan-out
    COUNT(DISTINCT o.OrderID) AS DistinctOrders,  -- True order count
    SUM(o.TotalAmount)  AS FanOutTotal,            -- WRONG: double-counted
    SUM(t.Amount)       AS TxSum,                  -- Correct: one row per transaction
    SUM(o.TotalAmount) - SUM(DISTINCT o.TotalAmount) * COUNT(DISTINCT o.OrderID)
        / NULLIF(COUNT(DISTINCT o.OrderID), 0)     AS ApproxOverstatement
FROM Orders o
JOIN Transactions t ON o.OrderID = t.OrderID
GROUP BY YEAR(o.OrderDate), MONTH(o.OrderDate)
ORDER BY OrderYear, OrderMonth;

-- Step 2: Detect fan-out — compare COUNT(*) to COUNT(DISTINCT OrderID) in the join
SELECT
    COUNT(*)                  AS TotalJoinRows,
    COUNT(DISTINCT o.OrderID) AS DistinctOrders,
    COUNT(*) - COUNT(DISTINCT o.OrderID) AS ExtraRowsFromFanOut,
    ROUND(CAST(COUNT(*) AS FLOAT) / NULLIF(COUNT(DISTINCT o.OrderID), 0), 2)
        AS FanOutMultiplier,
    SUM(o.TotalAmount)        AS FanOutSum,
    -- Corrected: aggregate detail first, then join
    SUM(tx_agg.TxTotal)       AS CorrectOrderTotal
FROM Orders o
JOIN Transactions t ON o.OrderID = t.OrderID
JOIN (
    SELECT OrderID, SUM(Amount) AS TxTotal
    FROM Transactions
    GROUP BY OrderID
) tx_agg ON o.OrderID = tx_agg.OrderID
WHERE o.Status NOT IN ('Cancelled');

-- Step 3: CORRECT approach — aggregate-first pattern (subquery/CTE)
WITH TransactionTotals AS (
    SELECT
        OrderID,
        SUM(Amount)  AS TxTotal,
        COUNT(*)     AS TxCount
    FROM Transactions
    GROUP BY OrderID
)
SELECT
    YEAR(o.OrderDate)   AS OrderYear,
    MONTH(o.OrderDate)  AS OrderMonth,
    COUNT(DISTINCT o.OrderID)   AS OrderCount,
    SUM(o.TotalAmount)          AS HeaderTotal,   -- Safe: one row per order
    SUM(tt.TxTotal)             AS TransactionTotal,
    ROUND(SUM(o.TotalAmount) - SUM(ISNULL(tt.TxTotal, 0)), 2) AS HeaderTxVariance
FROM Orders o
LEFT JOIN TransactionTotals tt ON o.OrderID = tt.OrderID
WHERE o.Status NOT IN ('Cancelled')
GROUP BY YEAR(o.OrderDate), MONTH(o.OrderDate)
ORDER BY OrderYear, OrderMonth;

-- Step 4: Show which specific orders cause the worst fan-out
SELECT
    o.OrderID,
    o.TotalAmount,
    COUNT(t.TransactionID)  AS TxCount,
    o.TotalAmount * COUNT(t.TransactionID) AS FanOutContribution,
    o.TotalAmount           AS CorrectContribution,
    o.TotalAmount * (COUNT(t.TransactionID) - 1) AS Overstatement
FROM Orders o
JOIN Transactions t ON o.OrderID = t.OrderID
GROUP BY o.OrderID, o.TotalAmount
HAVING COUNT(t.TransactionID) > 1
ORDER BY Overstatement DESC;

-- Step 5: Safe aggregation using DISTINCT — alternate pattern
SELECT
    YEAR(o.OrderDate)  AS OrderYear,
    MONTH(o.OrderDate) AS OrderMonth,
    COUNT(DISTINCT o.OrderID)              AS OrderCount,
    -- SUM(DISTINCT ...) is unreliable if two orders have the same TotalAmount
    -- The aggregate-first CTE in Step 3 is the preferred safe approach
    SUM(o.TotalAmount)                     AS HeaderTotal,
    AVG(o.TotalAmount)                     AS AvgOrderValue
FROM Orders o
WHERE o.Status NOT IN ('Cancelled')
GROUP BY YEAR(o.OrderDate), MONTH(o.OrderDate)
ORDER BY OrderYear, OrderMonth;
```

## Explanation

**Fan-out: the join multiplication problem**
When a one-to-many join is followed by an aggregate on the "one" side column, each header value is summed once per detail row. An order with 3 transactions is summed 3 times. `COUNT(*) / COUNT(DISTINCT OrderID)` measures the average fan-out multiplier — a value above 1.0 confirms the problem.

**The aggregate-first CTE pattern**
The fix: aggregate the many-side first (`GROUP BY OrderID` in a CTE or subquery), reducing it to one row per order, then join to the one-side. Now each header row still has exactly one detail row to join, and `SUM(o.TotalAmount)` is safe.

**SUM(DISTINCT) is not a reliable fix**
`SUM(DISTINCT TotalAmount)` would eliminate duplicate header amounts, but it also eliminates legitimate orders that happen to have the same value (two orders of £450.00 would be treated as one). The aggregate-first pattern is always the safe solution.

**COUNT(*) vs COUNT(DISTINCT)**
The diagnostic signal: `COUNT(*) = 22` but `COUNT(DISTINCT OrderID) = 17` means 5 extra rows exist from fan-out. The fan-out multiplier of 1.29 means the sum is overstated by 29% on average.

## Severity
**High** — Fan-out double-counting produces KPI and revenue figures that are materially wrong. Because the query runs without errors and returns plausible-looking numbers, the error often propagates into BI dashboards and board reports for months. It is one of the most common SQL mistakes in analytics and reporting code.
