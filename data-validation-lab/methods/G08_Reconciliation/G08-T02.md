# G08-T02 — Reconciliation | Count Mismatch Between Systems

## ID
G08-T02

## Group
8 — Reconciliation

## Type
Count Mismatch Between Systems — Record Count in Source Does Not Match Count in Target

## Live Scenario
An ETL pipeline loads 45,230 customer records from a CRM system into a data warehouse nightly. A monitoring dashboard shows successful completion — all batches processed with exit code 0. A data analyst counting records directly in the warehouse finds 45,187 customers — 43 fewer than the source. The ETL framework's "success" indicator only checks for batch completion, not for row count equality. Investigation reveals that 43 records had special characters (smart quotes, em dashes) in the customer name field that caused the file parsing to fail silently — the ETL framework logged warnings but did not set the exit code to failure. The 43 records are missing from all downstream reports.

## The Question
> Row count equality between source and target is the most fundamental ETL validation. A count mismatch — even of 1 record — indicates that data was either lost in transit, rejected during loading, or duplicated. SQL implements count reconciliation by querying both systems and comparing.
> **"Compare the count of Orders to the count of related Transactions, identifying any Orders with no transactions and any Transactions with no parent Order, and produce a reconciliation summary."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Transactions** — `schemas/05_Transactions.csv`
**Customers** — `schemas/01_Customers.csv`
**Products** — `schemas/03_Products.csv`

## Solution Query

```sql
-- Step 1: Basic count reconciliation across related tables
SELECT
    'Orders'       AS TableName, COUNT(*) AS RowCount FROM Orders
UNION ALL
SELECT 'Transactions', COUNT(*) FROM Transactions
UNION ALL
SELECT 'Customers',    COUNT(*) FROM Customers
UNION ALL
SELECT 'Products',     COUNT(*) FROM Products
UNION ALL
SELECT 'SalesTargets', COUNT(*) FROM SalesTargets
UNION ALL
SELECT 'Employees',    COUNT(*) FROM Employees
ORDER BY RowCount DESC;

-- Step 2: Orders with no transactions (count mismatch at relationship level)
SELECT
    'Orders without any transactions' AS ReconciliationCheck,
    COUNT(*) AS Count
FROM Orders o
WHERE NOT EXISTS (SELECT 1 FROM Transactions t WHERE t.OrderID = o.OrderID)

UNION ALL

SELECT
    'Transactions without a parent Order',
    COUNT(*)
FROM Transactions t
WHERE NOT EXISTS (SELECT 1 FROM Orders o WHERE o.OrderID = t.OrderID)

UNION ALL

SELECT
    'Orders referencing a non-existent Customer',
    COUNT(*)
FROM Orders o
WHERE NOT EXISTS (SELECT 1 FROM Customers c WHERE c.CustomerID = o.CustomerID)

UNION ALL

SELECT
    'Orders referencing a non-existent Product',
    COUNT(*)
FROM Orders o
WHERE NOT EXISTS (SELECT 1 FROM Products p WHERE p.ProductID = o.ProductID)

ORDER BY Count DESC;

-- Step 3: Ratio analysis — expected relationships
-- Business expectation: on average, each order has 1 transaction
SELECT
    COUNT(DISTINCT o.OrderID) AS TotalOrders,
    COUNT(t.TransactionID) AS TotalTransactions,
    ROUND(CAST(COUNT(t.TransactionID) AS FLOAT) / NULLIF(COUNT(DISTINCT o.OrderID), 0), 2)
        AS TxPerOrderRatio,
    CASE
        WHEN ROUND(CAST(COUNT(t.TransactionID) AS FLOAT) / NULLIF(COUNT(DISTINCT o.OrderID), 0), 2)
             BETWEEN 0.9 AND 2.0 THEN 'Ratio within expected range (0.9–2.0)'
        WHEN COUNT(t.TransactionID) < COUNT(DISTINCT o.OrderID)
             THEN 'WARNING: Fewer transactions than orders — missing payments?'
        ELSE 'REVIEW: Unusually high transaction-to-order ratio'
    END AS RatioStatus
FROM Orders o
LEFT JOIN Transactions t ON o.OrderID = t.OrderID;

-- Step 4: Status-based count — orders in each state
SELECT
    Status,
    COUNT(*) AS OrderCount,
    ROUND(100.0 * COUNT(*) / SUM(COUNT(*)) OVER (), 1) AS Pct,
    SUM(TotalAmount) AS TotalValue
FROM Orders
GROUP BY Status
ORDER BY OrderCount DESC;

-- Step 5: Customer coverage — how many customers have at least one order?
SELECT
    COUNT(DISTINCT c.CustomerID) AS TotalCustomers,
    COUNT(DISTINCT o.CustomerID) AS CustomersWithOrders,
    COUNT(DISTINCT c.CustomerID) - COUNT(DISTINCT o.CustomerID) AS CustomersWithoutOrders,
    ROUND(100.0 * COUNT(DISTINCT o.CustomerID) / NULLIF(COUNT(DISTINCT c.CustomerID), 0), 1)
        AS CustomerCoveragePct
FROM Customers c
LEFT JOIN Orders o ON c.CustomerID = o.CustomerID;
```

## Explanation

**Count reconciliation as the first validation step**
Before validating data quality, confirm that the expected number of records arrived. `SELECT COUNT(*)` on both source and target (or on related tables within the same database) is the most basic check. A count mismatch is the primary indicator that something failed in loading or transformation.

**UNION ALL for multi-table count report**
`UNION ALL` combines multiple COUNT queries into a single result set for easy comparison. Each row represents one entity type; ordering by RowCount descending shows the largest tables first. This is the standard "database inventory" query.

**NOT EXISTS for relationship-level count checks**
`NOT EXISTS (SELECT 1 FROM Transactions WHERE OrderID = o.OrderID)` is efficient — it stops scanning as soon as one matching row is found (or confirms none exists). More efficient than `LEFT JOIN … WHERE t.OrderID IS NULL` for large tables because it doesn't need to produce a join row for every match.

**Ratio thresholds**
The ratio of child records to parent records has an expected range based on the business model. One transaction per order is the expected baseline for a simple payment system. A ratio < 1 suggests missing transactions (payment not recorded); a ratio > 3 suggests duplicate transactions or a refund pattern that creates multiple records per order.

## Severity
**High** — Count mismatches in ETL pipelines are the most common cause of data warehouse inaccuracy. Missing records are invisible in downstream analytics — they affect every KPI, trend, and report. A 43-record shortfall in 45,230 represents 0.095% error — small enough to pass casual review but large enough to matter in regulatory filings or financial close.
