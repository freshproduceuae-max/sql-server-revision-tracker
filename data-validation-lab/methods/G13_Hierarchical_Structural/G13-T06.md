# G13-T06 — Hierarchical/Structural | Nested Set and Adjacency List Consistency

## ID
G13-T06

## Group
13 — Hierarchical/Structural

## Type
Nested Set and Adjacency List Consistency — Validating That Two Representations of the Same Hierarchy Agree

## Live Scenario
A content management system stores its category hierarchy in two formats simultaneously: an adjacency list (ParentID column) for easy editing, and a nested set (lft/rgt integer columns) for efficient subtree queries. The dual-format approach is common in CMSs because it gives fast reads (nested set) and easy writes (adjacency list) — but it requires the two representations to be kept in sync. After 6 months of maintenance, a data audit reveals 43 categories where the adjacency list and nested set disagree: a category's parent in the adjacency list is different from what the nested set implies. The desync was caused by a developer who updated only the ParentID column without regenerating the nested set values. In this scenario, the Employees table stores only an adjacency list, so this file teaches validation of the adjacency list itself and how to detect when a second representation would be needed.

## The Question
> An adjacency list stores each node's direct parent reference. A nested set stores each node's subtree boundaries (lft/rgt integers). Both represent the same hierarchy. Consistency validation checks: (1) the adjacency list is self-consistent (correct depth, no cycles), (2) if nested set values exist, they encode the same parent-child relationships as the adjacency list, and (3) all depth values agree between the two representations.
> **"Validate the Employees adjacency list: check that computed depths are consistent, that every non-root employee has a reachable root ancestor, that the depth distribution matches expected organisational structure bounds, and simulate nested set lft/rgt values to verify they would encode the same hierarchy."**

## Table Reference
**Employees** — `schemas/04_Employees.csv`

## Solution Query

```sql
-- Step 1: Compute depths and validate consistency
WITH Depths AS (
    -- Anchor: root nodes
    SELECT
        EmployeeID,
        FullName,
        ManagerID,
        0 AS Depth,
        CAST(EmployeeID AS VARCHAR(MAX)) AS AncestorPath
    FROM Employees
    WHERE ManagerID IS NULL

    UNION ALL

    SELECT
        e.EmployeeID,
        e.FullName,
        e.ManagerID,
        d.Depth + 1,
        d.AncestorPath + '/' + CAST(e.EmployeeID AS VARCHAR(10))
    FROM Employees e
    JOIN Depths d ON d.EmployeeID = e.ManagerID
    WHERE e.ManagerID <> e.EmployeeID
)
SELECT
    d.EmployeeID,
    d.FullName,
    d.ManagerID,
    d.Depth,
    d.AncestorPath,
    -- Verify depth consistency: count slashes in AncestorPath as proxy for depth
    LEN(d.AncestorPath) - LEN(REPLACE(d.AncestorPath, '/', '')) AS PathDepth,
    CASE
        WHEN d.Depth <> LEN(d.AncestorPath) - LEN(REPLACE(d.AncestorPath, '/', ''))
             THEN 'DEPTH INCONSISTENCY: Computed depth does not match path depth'
        ELSE 'Consistent'
    END AS DepthConsistencyFlag
FROM Depths d
ORDER BY d.Depth, d.FullName
OPTION (MAXRECURSION 50);

-- Step 2: Validate that every employee has exactly one root ancestor
WITH Depths AS (
    SELECT EmployeeID, FullName, ManagerID, 0 AS Depth,
           CAST(EmployeeID AS VARCHAR(10)) AS RootAncestor
    FROM Employees WHERE ManagerID IS NULL
    UNION ALL
    SELECT e.EmployeeID, e.FullName, e.ManagerID, d.Depth + 1, d.RootAncestor
    FROM Employees e JOIN Depths d ON d.EmployeeID = e.ManagerID
    WHERE e.ManagerID <> e.EmployeeID
)
SELECT
    d.EmployeeID,
    d.FullName,
    COUNT(DISTINCT d.RootAncestor) AS RootCount,
    STRING_AGG(CAST(d.RootAncestor AS VARCHAR), ', ') AS RootAncestors,
    CASE
        WHEN COUNT(DISTINCT d.RootAncestor) > 1
             THEN 'MULTIPLE ROOTS: Employee reachable from more than one root — hierarchy error'
        WHEN COUNT(DISTINCT d.RootAncestor) = 0
             THEN 'NO ROOT: Employee not reachable from any root — disconnected'
        ELSE 'Single root'
    END AS RootFlag
FROM Depths d
GROUP BY d.EmployeeID, d.FullName
HAVING COUNT(DISTINCT d.RootAncestor) <> 1
OPTION (MAXRECURSION 50);

-- Step 3: Derive genuine nested set lft/rgt values from the adjacency list,
-- then validate real parent-child containment against them.
--
-- Consecutive integers per row (lft = 2n-1, rgt = 2n) cannot demonstrate
-- containment: every node's own rgt is always exactly lft+1 by
-- construction, so a per-row "rgt > lft" check can never fail regardless
-- of data. A genuine nested set numbering must instead reflect real DFS
-- pre-order structure, where a parent's [lft, rgt] range fully encloses
-- every descendant's range.
--
-- Closed-form derivation used below (provable from nested-set pre-order
-- semantics, verified by hand-trace against a 3-level chain plus a
-- sibling root before use):
--   lft(N)  = 1 + depth(N) + 2 x (count of nodes M that finish, in
--             pre-order, strictly before N opens, where M is not an
--             ancestor of N)
--   rgt(N)  = lft(N) + 2 x subtree_size(N) - 1
-- "M finishes before N opens and is not N's ancestor" is exactly
-- "M.AncestorPath < N.AncestorPath AND N.AncestorPath NOT LIKE
-- M.AncestorPath + '/%'" -- both are derivable directly from the
-- materialized path already built while walking the adjacency list.
WITH Depths AS (
    SELECT
        EmployeeID, FullName, ManagerID, 0 AS Depth,
        CAST(EmployeeID AS VARCHAR(MAX)) AS AncestorPath
    FROM Employees WHERE ManagerID IS NULL
    UNION ALL
    SELECT
        e.EmployeeID, e.FullName, e.ManagerID, d.Depth + 1,
        d.AncestorPath + '/' + CAST(e.EmployeeID AS VARCHAR(10))
    FROM Employees e JOIN Depths d ON d.EmployeeID = e.ManagerID
    WHERE e.ManagerID <> e.EmployeeID
),
SubtreeSizes AS (
    SELECT
        d.EmployeeID,
        -- Count self + every node whose path descends from this node's path
        (SELECT COUNT(*) FROM Depths d2
         WHERE d2.AncestorPath = d.AncestorPath
            OR d2.AncestorPath LIKE d.AncestorPath + '/%') AS SubtreeSize
    FROM Depths d
),
NestedSet AS (
    SELECT
        d.EmployeeID,
        d.FullName,
        d.ManagerID,
        d.Depth,
        ss.SubtreeSize,
        1 + d.Depth + 2 * (
            SELECT COUNT(*) FROM Depths m
            WHERE m.AncestorPath < d.AncestorPath
              AND d.AncestorPath NOT LIKE m.AncestorPath + '/%'
        ) AS DerivedLft
    FROM Depths d
    JOIN SubtreeSizes ss ON ss.EmployeeID = d.EmployeeID
),
NestedSetFull AS (
    SELECT
        EmployeeID, FullName, ManagerID, Depth, DerivedLft,
        DerivedLft + 2 * SubtreeSize - 1 AS DerivedRgt
    FROM NestedSet
)
SELECT
    child.EmployeeID,
    child.FullName,
    child.ManagerID,
    child.Depth,
    child.DerivedLft,
    child.DerivedRgt,
    parent.DerivedLft AS ParentLft,
    parent.DerivedRgt AS ParentRgt,
    CASE
        WHEN child.ManagerID IS NULL
             THEN 'ROOT: No parent to validate containment against'
        WHEN parent.DerivedLft < child.DerivedLft
             AND child.DerivedRgt < parent.DerivedRgt
             THEN 'VALID: Child range is fully contained within parent range'
        ELSE 'INVALID: Child lft/rgt range is not contained within parent range'
    END AS ContainmentFlag
FROM NestedSetFull child
LEFT JOIN NestedSetFull parent ON parent.EmployeeID = child.ManagerID
ORDER BY child.DerivedLft
OPTION (MAXRECURSION 50);

-- Step 4: Adjacency list completeness — every parent referenced must exist
SELECT
    e.EmployeeID,
    e.FullName,
    e.ManagerID,
    CASE
        WHEN e.ManagerID IS NULL THEN 'ROOT: No parent (valid)'
        WHEN e.ManagerID = e.EmployeeID THEN 'SELF-LOOP: Invalid'
        WHEN NOT EXISTS (SELECT 1 FROM Employees m WHERE m.EmployeeID = e.ManagerID)
             THEN 'DANGLING: Parent ManagerID does not exist in Employees'
        ELSE 'Valid parent reference'
    END AS ParentStatus,
    -- Level 2 ancestor
    (SELECT m.ManagerID FROM Employees m WHERE m.EmployeeID = e.ManagerID) AS GrandManagerID
FROM Employees e
ORDER BY ParentStatus DESC;
```

## Explanation

**Adjacency list vs nested set trade-offs**
The adjacency list stores only the direct parent reference — one row per node, simple to insert and update. The nested set stores two integers (lft, rgt) per node such that a node's entire subtree is the set of nodes with lft/rgt values within the parent's lft/rgt range. Subtree queries require a range scan (`WHERE child.lft BETWEEN parent.lft AND parent.rgt`) instead of a recursive CTE, making reads faster at the cost of expensive writes (every insert/move resequences all lft/rgt values).

**AncestorPath as a consistency check**
Building a path string (`'EMP-001/EMP-002/EMP-005'`) during recursive traversal creates a verifiable audit trail. The number of separators (slashes) in the path should equal the computed depth. If they disagree, the recursive CTE encountered a join condition error or the depth initialisation in the anchor was wrong.

**Deriving genuine nested set values from an adjacency list**
This table has no stored lft/rgt columns to validate — only an adjacency list. Assigning lft/rgt as consecutive integers per row (`lft = 2n-1, rgt = 2n`, ordered by depth) cannot demonstrate containment: every node's own rgt is always exactly lft+1 by construction, so no containment check against those values can ever fail, on any data. Step 3 instead derives real nested set values: `lft(N) = 1 + depth(N) + 2 × (count of nodes that finish, in pre-order, strictly before N opens and are not N's ancestors)`, and `rgt(N) = lft(N) + 2 × subtree_size(N) - 1`. Both pieces — "finishes before N in pre-order" and "is not N's ancestor" — are derivable directly from the `AncestorPath` string already built while walking the hierarchy: a node M finishes before N opens and isn't its ancestor exactly when `M.AncestorPath < N.AncestorPath AND N.AncestorPath NOT LIKE M.AncestorPath + '/%'`. Step 3 then validates the real invariant — `parent.lft < child.lft AND child.rgt < parent.rgt` — against these genuinely derived values, not simulated ones.

**The consistency invariant**
For a valid nested set encoding of the adjacency list: (1) every parent's lft < every child's lft, and every child's rgt < parent's rgt; (2) no two nodes share any lft or rgt value; (3) rgt - lft + 1 = 2 × (number of nodes in subtree including self); (4) the root has lft = 1 and rgt = 2 × (total node count). Checking these four invariants fully validates a nested set representation.

## Severity
**Medium** — Adjacency list inconsistencies (dangling parents, multiple roots, cycles) cause hierarchy queries to silently return incorrect results. Nested set desync is particularly dangerous because the fast read path (nested set range query) returns different data from the source-of-truth path (adjacency list recursive traversal). Users see correct results in the edit interface but wrong results in the read/report interface — a split-brain data quality failure.
