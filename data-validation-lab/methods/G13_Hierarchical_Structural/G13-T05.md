# G13-T05 — Hierarchical/Structural | Graph Connectivity and Orphan Node Detection

## ID
G13-T05

## Group
13 — Hierarchical/Structural

## Type
Graph Connectivity and Orphan Node Detection — Finding Disconnected Nodes in Network Relationships

## Live Scenario
A supply chain analyst is modelling the supplier network as a graph: each supplier has relationships to sub-suppliers, and those sub-suppliers may have their own sub-suppliers. The company needs to assess supply chain risk — if a tier-1 supplier fails, which tier-2 and tier-3 suppliers are also affected? The graph analysis reveals three supplier clusters that are completely disconnected from the main supply chain: seven suppliers exist in the database but have no relationship edges connecting them to any other supplier. These turn out to be legacy suppliers from an acquired business whose relationships were never entered. Additionally, one supplier has edges pointing to itself (a self-loop) and two supplier pairs point to each other with no connection to the main graph (a two-node isolated island). The supply chain risk model would have completely omitted these isolated nodes — underestimating the supplier base by 12%.

## The Question
> Graph connectivity validation checks that: nodes have at least one edge (non-isolated), all nodes are reachable from a defined starting point (the graph is connected), self-loops do not exist where they are structurally invalid, and edge tables do not reference non-existent nodes. SQL detects these patterns using recursive CTEs, anti-joins, and SELF JOINs.
> **"Using the Employees table as a directed graph (EmployeeID → ManagerID edges), identify: isolated nodes with no edges, nodes not reachable from the root, self-loop edges, and the total number of connected components in the graph."**

## Table Reference
**Employees** — `schemas/04_Employees.csv`
**Orders** — `schemas/02_Orders.csv`
**Customers** — `schemas/01_Customers.csv`

## Solution Query

```sql
-- Step 1: Find isolated nodes — employees with no outgoing (manager) edge
--         and no incoming (direct report) edges
SELECT
    e.EmployeeID,
    e.FullName,
    e.Department,
    e.ManagerID,
    CASE
        WHEN e.ManagerID IS NULL
             AND NOT EXISTS (SELECT 1 FROM Employees sub WHERE sub.ManagerID = e.EmployeeID)
             THEN 'ISOLATED ROOT: No manager and no direct reports'
        WHEN e.ManagerID IS NOT NULL
             AND NOT EXISTS (SELECT 1 FROM Employees sub WHERE sub.ManagerID = e.EmployeeID)
             THEN 'LEAF NODE: Has manager, no direct reports (normal for staff)'
        WHEN e.ManagerID IS NULL
             AND EXISTS (SELECT 1 FROM Employees sub WHERE sub.ManagerID = e.EmployeeID)
             THEN 'ROOT NODE: No manager, has direct reports (normal for CEO)'
        ELSE 'INTERNAL NODE: Has both manager and direct reports'
    END AS NodeRole,
    (SELECT COUNT(*) FROM Employees sub WHERE sub.ManagerID = e.EmployeeID) AS OutDegree,
    CASE WHEN e.ManagerID IS NOT NULL THEN 1 ELSE 0 END AS InDegree
FROM Employees e;

-- Step 2: Self-loop detection
SELECT
    EmployeeID,
    FullName,
    ManagerID,
    'SELF-LOOP: Employee references themselves as manager' AS Issue
FROM Employees
WHERE ManagerID = EmployeeID;

-- Step 3: Connected components — traverse from root to find reachable nodes
WITH Reachable AS (
    -- Seed: start from root(s)
    SELECT EmployeeID, FullName, 0 AS ComponentID
    FROM Employees
    WHERE ManagerID IS NULL

    UNION ALL

    SELECT e.EmployeeID, e.FullName, r.ComponentID
    FROM Employees e
    JOIN Reachable r ON r.EmployeeID = e.ManagerID
    WHERE e.ManagerID <> e.EmployeeID
)
SELECT
    r.EmployeeID,
    r.FullName,
    r.ComponentID,
    'Reachable from root' AS Connectivity
FROM Reachable r

UNION ALL

-- Nodes NOT reachable from any root
SELECT
    e.EmployeeID,
    e.FullName,
    -1 AS ComponentID,
    'DISCONNECTED: Not reachable from any root' AS Connectivity
FROM Employees e
WHERE NOT EXISTS (SELECT 1 FROM Reachable r WHERE r.EmployeeID = e.EmployeeID)
OPTION (MAXRECURSION 50);

-- Step 4: Bipartite relationship validation — Orders ↔ Customers ↔ Products
-- Each order should connect exactly one customer to one product
SELECT
    o.OrderID,
    COUNT(DISTINCT o.CustomerID) AS CustomerLinks,
    COUNT(DISTINCT o.ProductID) AS ProductLinks,
    CASE
        WHEN COUNT(DISTINCT o.CustomerID) > 1
             THEN 'MULTI-CUSTOMER: Order linked to multiple customers'
        WHEN COUNT(DISTINCT o.ProductID) > 1
             THEN 'MULTI-PRODUCT: Order linked to multiple products (check if intended)'
        WHEN o.CustomerID IS NULL
             THEN 'NO CUSTOMER: Order has no customer link'
        WHEN o.ProductID IS NULL
             THEN 'NO PRODUCT: Order has no product link'
        ELSE 'Valid single-customer single-product link'
    END AS GraphStructureFlag
FROM Orders o
GROUP BY o.OrderID, o.CustomerID, o.ProductID
HAVING COUNT(DISTINCT o.CustomerID) > 1
    OR COUNT(DISTINCT o.ProductID) > 1
    OR o.CustomerID IS NULL
    OR o.ProductID IS NULL;

-- Step 5: Degree distribution — how many edges per node?
SELECT
    TotalEdges AS Degree,
    COUNT(*) AS NodeCount,
    ROUND(100.0 * COUNT(*) / SUM(COUNT(*)) OVER (), 1) AS Pct,
    CASE
        WHEN TotalEdges = 0 THEN 'ISOLATED: No connections'
        WHEN TotalEdges = 1 THEN 'TERMINAL: One connection (leaf or root)'
        ELSE 'CONNECTED: Multiple edges'
    END AS DegreeCategory
FROM (
    SELECT
        e.EmployeeID,
        (CASE WHEN e.ManagerID IS NOT NULL AND e.ManagerID <> e.EmployeeID THEN 1 ELSE 0 END)
        + (SELECT COUNT(*) FROM Employees sub WHERE sub.ManagerID = e.EmployeeID
           AND sub.EmployeeID <> sub.ManagerID) AS TotalEdges
    FROM Employees e
) NodeDegrees
GROUP BY TotalEdges
ORDER BY TotalEdges;
```

## Explanation

**Graph vs tree vs hierarchy**
An adjacency-list hierarchy (parent-child with single parent per node) is a special case of a directed graph (DAG when acyclic, tree when each node has exactly one parent). The SQL patterns in this section apply to any directed graph stored as an edge table or adjacency list. Graph connectivity validation is more general than hierarchy validation: a graph can have multiple roots, no root, or cycles — all valid in a general graph context but invalid in a strict organisational hierarchy.

**In-degree and out-degree**
In a directed graph, in-degree is the number of edges pointing INTO a node; out-degree is the number pointing OUT. In the management hierarchy, in-degree for each employee equals 1 (they have exactly one manager) except for the root (in-degree = 0) and self-loops. Out-degree equals the number of direct reports. An isolated node has both in-degree = 0 and out-degree = 0.

**Connected components**
A connected component is a set of nodes where every node is reachable from every other node (ignoring edge direction in an undirected sense). A tree has exactly one component; a disconnected graph has multiple. Step 3 finds nodes reachable from root nodes — nodes NOT in the reachable set are either in separate components or are genuinely isolated.

**Bipartite validation (Step 4)**
Step 4 validates a different structural property: that the relationship between Customers and Products through Orders maintains a valid bipartite structure (each order links exactly one customer to one product). Violations — an order with NULL CustomerID, or fan-out producing multiple CustomerID values for one OrderID — indicate ETL errors or JOIN multiplicities in the source data.

## Severity
**Medium** — Graph connectivity failures cause silent analytical exclusions: disconnected nodes are invisible to any traversal-based query, roll-up, or network analysis. In supply chain, HR, and network analysis contexts, disconnected nodes represent real-world entities that the analysis model treats as non-existent — producing incorrect risk assessments, coverage reports, and organisational analyses.
