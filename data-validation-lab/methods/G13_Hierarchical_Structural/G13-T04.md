# G13-T04 — Hierarchical/Structural | JSON Structure Validation

## ID
G13-T04

## Group
13 — Hierarchical/Structural

## Type
JSON Structure Validation — Verifying That JSON Fields Contain Expected Keys and Valid Values

## Live Scenario
An e-commerce platform stores order metadata as a JSON column. A new microservice begins writing to the Metadata column using a slightly different schema — it uses `"customer_ref"` instead of `"customerRef"` and omits the `"source"` key entirely. For three weeks, the discrepancy goes unnoticed because the column accepts any valid JSON. The analytics pipeline that reads `$.customerRef` via `JSON_VALUE` silently returns NULL for all orders from the new microservice — 12,000 orders in three weeks show no customer reference in the analytics layer. The JSON structure validation query, run daily, would have flagged on day 1 that a new key naming convention had appeared in the Metadata column, triggering an investigation before 12,000 records accumulated with the wrong schema.

## The Question
> JSON structure validation checks that: JSON fields contain valid JSON (syntactically parseable), expected top-level keys are present, key values are of the expected type and format, and the distribution of keys matches what is expected. SQL Server provides ISJSON(), JSON_VALUE(), and JSON_QUERY() for these checks.
> **"Validate the Metadata JSON column in Orders: verify all values are valid JSON, check that expected keys (source, amount, currency) are present in each document, validate that the currency value is one of the permitted codes, and flag any documents with unexpected schema."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`

## Solution Query

```sql
-- Step 1: Basic JSON validity check
SELECT
    OrderID,
    Metadata,
    ISJSON(Metadata) AS IsValidJSON,
    CASE
        WHEN Metadata IS NULL
             THEN 'NULL: No metadata stored'
        WHEN ISJSON(Metadata) = 0
             THEN 'INVALID JSON: Syntax error — cannot parse'
        WHEN ISJSON(Metadata) = 1
             THEN 'Valid JSON'
        ELSE 'UNKNOWN'
    END AS JSONValidityFlag
FROM Orders
WHERE Metadata IS NOT NULL;

-- Step 2: Expected key presence check
SELECT
    OrderID,
    Metadata,
    -- Extract expected keys
    JSON_VALUE(Metadata, '$.source')         AS Source,
    JSON_VALUE(Metadata, '$.amount')         AS Amount,
    JSON_VALUE(Metadata, '$.currency')       AS Currency,
    JSON_VALUE(Metadata, '$.customerRef')    AS CustomerRef,
    -- Check presence (NULL means key absent OR value is null)
    CASE WHEN JSON_VALUE(Metadata, '$.source') IS NULL
         THEN 'MISSING' ELSE 'PRESENT' END AS SourcePresence,
    CASE WHEN JSON_VALUE(Metadata, '$.amount') IS NULL
         THEN 'MISSING' ELSE 'PRESENT' END AS AmountPresence,
    CASE WHEN JSON_VALUE(Metadata, '$.currency') IS NULL
         THEN 'MISSING' ELSE 'PRESENT' END AS CurrencyPresence,
    -- Valid currency check
    CASE
        WHEN JSON_VALUE(Metadata, '$.currency') NOT IN ('GBP', 'USD', 'EUR')
             AND JSON_VALUE(Metadata, '$.currency') IS NOT NULL
             THEN 'INVALID CURRENCY: ' + JSON_VALUE(Metadata, '$.currency')
        ELSE 'OK'
    END AS CurrencyFlag,
    -- Amount consistency: JSON amount vs column TotalAmount
    CASE
        WHEN TRY_CAST(JSON_VALUE(Metadata, '$.amount') AS DECIMAL(18,2)) IS NOT NULL
             AND ABS(TRY_CAST(JSON_VALUE(Metadata, '$.amount') AS DECIMAL(18,2)) - TotalAmount) > 0.01
             THEN 'AMOUNT MISMATCH: JSON amount differs from TotalAmount column'
        ELSE 'OK'
    END AS AmountConsistencyFlag
FROM Orders
WHERE ISJSON(Metadata) = 1;

-- Step 3: Key distribution profile — which keys appear most often?
WITH KeyCounts AS (
    SELECT
        OrderID,
        CASE WHEN JSON_VALUE(Metadata, '$.source')      IS NOT NULL THEN 1 ELSE 0 END AS HasSource,
        CASE WHEN JSON_VALUE(Metadata, '$.amount')      IS NOT NULL THEN 1 ELSE 0 END AS HasAmount,
        CASE WHEN JSON_VALUE(Metadata, '$.currency')    IS NOT NULL THEN 1 ELSE 0 END AS HasCurrency,
        CASE WHEN JSON_VALUE(Metadata, '$.customerRef') IS NOT NULL THEN 1 ELSE 0 END AS HasCustomerRef
    FROM Orders
    WHERE ISJSON(Metadata) = 1
)
SELECT
    COUNT(*) AS ValidJSONDocs,
    SUM(HasSource)      AS DocsWithSource,
    SUM(HasAmount)      AS DocsWithAmount,
    SUM(HasCurrency)    AS DocsWithCurrency,
    SUM(HasCustomerRef) AS DocsWithCustomerRef,
    ROUND(100.0 * SUM(HasSource)      / NULLIF(COUNT(*), 0), 1) AS SourcePct,
    ROUND(100.0 * SUM(HasAmount)      / NULLIF(COUNT(*), 0), 1) AS AmountPct,
    ROUND(100.0 * SUM(HasCurrency)    / NULLIF(COUNT(*), 0), 1) AS CurrencyPct,
    ROUND(100.0 * SUM(HasCustomerRef) / NULLIF(COUNT(*), 0), 1) AS CustomerRefPct,
    -- Flag if any expected key is missing from more than 5% of documents
    CASE WHEN ROUND(100.0 * SUM(HasSource) / NULLIF(COUNT(*), 0), 1) < 95
         THEN 'SOURCE KEY MISSING from >' + CAST(100 - ROUND(100.0 * SUM(HasSource) / NULLIF(COUNT(*),0),0) AS VARCHAR) + '% of docs'
         ELSE 'Source key well-populated' END AS SourceCoverageFlag
FROM KeyCounts;

-- Step 4: JSON document summary — valid, invalid, null breakdown
SELECT
    COUNT(*) AS TotalOrders,
    SUM(CASE WHEN Metadata IS NULL THEN 1 ELSE 0 END) AS NullMetadata,
    SUM(CASE WHEN Metadata IS NOT NULL AND ISJSON(Metadata) = 0 THEN 1 ELSE 0 END) AS InvalidJSON,
    SUM(CASE WHEN ISJSON(Metadata) = 1 THEN 1 ELSE 0 END) AS ValidJSON,
    ROUND(100.0 * SUM(CASE WHEN ISJSON(Metadata) = 1 THEN 1 ELSE 0 END)
          / NULLIF(COUNT(*), 0), 1) AS ValidJSONPct
FROM Orders;
```

## Explanation

**ISJSON() for syntax validation**
`ISJSON(col)` returns 1 for syntactically valid JSON, 0 for invalid JSON, and NULL for NULL input. It validates only that the string is parseable as JSON — it does not check schema, key names, or value types. It is the first-pass filter before any `JSON_VALUE` extraction is attempted. Calling `JSON_VALUE` on an invalid JSON string returns NULL rather than raising an error, so `ISJSON` must be used to distinguish "key absent" from "invalid JSON returning NULL."

**JSON_VALUE vs JSON_QUERY**
`JSON_VALUE(col, '$.key')` extracts a scalar value (string, number, boolean) as NVARCHAR. `JSON_QUERY(col, '$.key')` extracts a nested object or array as a JSON fragment. Use `JSON_VALUE` for individual field values and `JSON_QUERY` when the target value is itself a JSON object (e.g., an embedded address object within the order metadata).

**NULL from JSON_VALUE — key absent vs null value**
`JSON_VALUE` returns NULL both when the key is absent and when the key's value is explicitly `null`. To distinguish: use `JSON_QUERY` and check whether the resulting fragment is the string `"null"`, or check the raw string with `CHARINDEX('"source"', Metadata) > 0`. For most validation purposes, treating both as "missing" is appropriate.

**Amount cross-validation (JSON vs column)**
Step 2's `AmountConsistencyFlag` compares the amount embedded in the JSON document against the `TotalAmount` column. These should agree. If they diverge, it indicates: the JSON was written by a different system than the column, a currency conversion was applied to one but not the other, or the JSON represents a sub-total while the column represents the gross total.

## Severity
**High** — JSON schema drift is one of the most insidious data quality failures: the column remains valid JSON, ISJSON returns 1, no errors are raised, but the expected keys are absent or renamed — and every downstream pipeline that reads those keys silently returns NULL. The failure propagates invisibly until an analyst notices that a dimension is returning blank values, often weeks or months later.
