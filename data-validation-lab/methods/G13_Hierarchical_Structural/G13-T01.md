# G13-T01 — Hierarchical/Structural | Parent-Child Referential Integrity

## ID
G13-T01

## Group
13 — Hierarchical/Structural

## Type
Parent-Child Referential Integrity — Detecting Orphaned Records and Missing Parent References

## Live Scenario
A data migration team is importing a 15-year-old ERP system into a new cloud database. The source system's foreign key constraints were disabled 8 years ago to "improve performance." Running a parent-child integrity check before migration reveals: 4,200 orders reference CustomerIDs that do not exist in the Customers table — these customers were deleted without cascading the deletion to their orders. 890 orders reference ProductIDs that have been removed from the Products table. The migration team cannot simply ignore these orphans: orders without customers will fail downstream BI joins and produce invisible rows in customer-level reports. Before migrating, the team must decide: restore the deleted parent records from backup, reassign orphan orders to a placeholder "DELETED CUSTOMER" entity, or exclude orphans from the migration with a documented data loss assessment.

## The Question
> Parent-child referential integrity validates that every foreign key value in a child table matches a primary key value in its parent table. Orphaned records (child rows with no matching parent) and dangling references (foreign key values that point to nothing) are the two classes of referential integrity failure.
> **"Find all Orders that reference a CustomerID not present in the Customers table, all Orders that reference a ProductID not present in the Products table, and all Transactions that reference an OrderID not present in the Orders table — quantify orphan count and percentage for each relationship."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Customers** — `schemas/01_Customers.csv`
**Products** — `schemas/03_Products.csv`
**Transactions** — `schemas/05_Transactions.csv`

## Solution Query

```sql
-- Step 1: Orphaned orders — CustomerID not in Customers
SELECT
    'Orders.CustomerID → Customers.CustomerID' AS Relationship,
    COUNT(*) AS OrphanCount,
    (SELECT COUNT(*) FROM Orders) AS TotalChildRows,
    ROUND(100.0 * COUNT(*) / NULLIF((SELECT COUNT(*) FROM Orders), 0), 1) AS OrphanPct
FROM Orders o
WHERE NOT EXISTS (
    SELECT 1 FROM Customers c WHERE c.CustomerID = o.CustomerID
)
AND o.CustomerID IS NOT NULL;

-- Step 2: All FK relationships — unified orphan summary
SELECT Relationship, OrphanCount, TotalChildRows,
       ROUND(100.0 * OrphanCount / NULLIF(TotalChildRows, 0), 1) AS OrphanPct,
       CASE
           WHEN OrphanCount = 0 THEN 'OK: No orphans'
           WHEN 100.0 * OrphanCount / NULLIF(TotalChildRows, 0) < 1
                THEN 'LOW: <1% orphans — likely isolated data errors'
           WHEN 100.0 * OrphanCount / NULLIF(TotalChildRows, 0) < 10
                THEN 'MEDIUM: 1-10% orphans — systematic issue'
           ELSE 'HIGH: >10% orphans — major referential integrity failure'
       END AS Severity
FROM (
    -- Orders → Customers
    SELECT
        'Orders.CustomerID → Customers' AS Relationship,
        SUM(CASE WHEN NOT EXISTS (SELECT 1 FROM Customers c WHERE c.CustomerID = o.CustomerID)
                  AND o.CustomerID IS NOT NULL THEN 1 ELSE 0 END) AS OrphanCount,
        COUNT(*) AS TotalChildRows
    FROM Orders o
    UNION ALL
    -- Orders → Products
    SELECT
        'Orders.ProductID → Products',
        SUM(CASE WHEN NOT EXISTS (SELECT 1 FROM Products p WHERE p.ProductID = o.ProductID)
                  AND o.ProductID IS NOT NULL THEN 1 ELSE 0 END),
        COUNT(*)
    FROM Orders o
    UNION ALL
    -- Transactions → Orders
    SELECT
        'Transactions.OrderID → Orders',
        SUM(CASE WHEN NOT EXISTS (SELECT 1 FROM Orders o WHERE o.OrderID = t.OrderID)
                  AND t.OrderID IS NOT NULL THEN 1 ELSE 0 END),
        COUNT(*)
    FROM Transactions t
) Summary
ORDER BY OrphanPct DESC;

-- Step 3: Detail — show the actual orphaned records
SELECT
    o.OrderID,
    o.CustomerID,
    o.ProductID,
    o.TotalAmount,
    o.Status,
    o.OrderDate,
    CASE
        WHEN NOT EXISTS (SELECT 1 FROM Customers c WHERE c.CustomerID = o.CustomerID)
             AND o.CustomerID IS NOT NULL
             THEN 'ORPHAN: CustomerID ' + CAST(o.CustomerID AS VARCHAR) + ' not in Customers'
        ELSE NULL
    END AS CustomerOrphanFlag,
    CASE
        WHEN NOT EXISTS (SELECT 1 FROM Products p WHERE p.ProductID = o.ProductID)
             AND o.ProductID IS NOT NULL
             THEN 'ORPHAN: ProductID ' + CAST(o.ProductID AS VARCHAR) + ' not in Products'
        ELSE NULL
    END AS ProductOrphanFlag
FROM Orders o
WHERE
    (NOT EXISTS (SELECT 1 FROM Customers c WHERE c.CustomerID = o.CustomerID)
     AND o.CustomerID IS NOT NULL)
    OR
    (NOT EXISTS (SELECT 1 FROM Products p WHERE p.ProductID = o.ProductID)
     AND o.ProductID IS NOT NULL);

-- Step 4: NULL foreign keys — missing references
SELECT
    'Orders.CustomerID IS NULL' AS Issue,
    COUNT(*) AS Count,
    ROUND(100.0 * COUNT(*) / (SELECT COUNT(*) FROM Orders), 1) AS Pct
FROM Orders WHERE CustomerID IS NULL
UNION ALL
SELECT 'Orders.ProductID IS NULL', COUNT(*),
       ROUND(100.0 * COUNT(*) / (SELECT COUNT(*) FROM Orders), 1)
FROM Orders WHERE ProductID IS NULL
UNION ALL
SELECT 'Transactions.OrderID IS NULL', COUNT(*),
       ROUND(100.0 * COUNT(*) / (SELECT COUNT(*) FROM Transactions), 1)
FROM Transactions WHERE OrderID IS NULL;
```

## Expected Output

**Step 2 — FK relationship summary:**
| Relationship | OrphanCount | TotalChildRows | OrphanPct | Severity |
|---|---|---|---|---|
| Orders.CustomerID → Customers | 0 | 20 | 0.0 | OK: No orphans |
| Orders.ProductID → Products | 0 | 20 | 0.0 | OK: No orphans |
| Transactions.OrderID → Orders | 0 | 25 | 0.0 | OK: No orphans |

**Step 4 — NULL foreign keys:**
| Issue | Count | Pct |
|---|---|---|
| Orders.ProductID IS NULL | 0 | 0.0 |
| Transactions.OrderID IS NULL | 3 | 12.0 |

## Explanation

**NOT EXISTS vs LEFT JOIN / IS NULL**
Both `NOT EXISTS (SELECT 1 FROM Parent WHERE Parent.PK = Child.FK)` and `LEFT JOIN Parent ON ... WHERE Parent.PK IS NULL` detect orphans. NOT EXISTS is often preferred because: it short-circuits on the first match (faster for large parent tables), it reads as a natural English statement ("where no parent exists"), and it handles NULL FK values more intuitively. LEFT JOIN / IS NULL is preferred when you also want to return columns from the parent for comparison.

**NULL FK vs orphan FK — two distinct failure modes**
Step 4 separates NULL foreign keys (the reference is absent) from orphan foreign keys (the reference exists but points nowhere). A NULL FK may be valid (an optional relationship) or a data entry gap; an orphan FK is always a data integrity failure — the reference points to a record that does not exist. Both require investigation but for different reasons.

**Cascaded deletion as the root cause**
The most common cause of orphaned records is deletion of parent records without cascading the deletion to children. When the database lacks a foreign key constraint with `ON DELETE CASCADE` or `ON DELETE RESTRICT`, application-layer deletion can leave children behind. Orphan detection is the audit step that discovers this has happened.

**Severity classification**
A 0% orphan rate means referential integrity is intact. Above 1% suggests isolated incidents (developer test records, migration artefacts). Above 10% suggests systematic failure: a foreign key constraint was dropped, an ETL loaded child records without the parent step, or a large-scale delete was applied to only one table.

## Severity
**High** — Orphaned records cause invisible data loss: a JOIN between Orders and Customers on a system with orphaned Orders will silently exclude those orphan orders from every customer-level report. Analysts see customer totals that are understated without any error being raised. In financial reporting, this constitutes a misstatement of revenue.
