# G13-T02 — Hierarchical/Structural | Circular Reference Detection

## ID
G13-T02

## Group
13 — Hierarchical/Structural

## Type
Circular Reference Detection — Finding Loops in Self-Referencing Hierarchies

## Live Scenario
A company's HR system stores the management hierarchy as a self-referencing table: each employee record has a ManagerID pointing to another employee's EmployeeID. A database administrator runs a recursive CTE to generate the org chart for a board presentation. The CTE runs for 4 minutes, consuming all available CPU, and then fails with "maximum recursion depth exceeded." Investigation reveals two circular references: Employee A reports to Employee B, who reports to Employee C, who reports back to Employee A — a three-node cycle. Additionally, the CEO record has been set to report to themselves (ManagerID = their own EmployeeID), creating a self-loop. These cycles were created by a poorly written HR application that did not validate the hierarchy before saving. Without circular reference detection, the recursive CTE would loop infinitely.

## The Question
> A circular reference occurs when following the parent-child chain in a self-referencing hierarchy eventually leads back to a previously visited node. Circular references cause infinite loops in recursive queries, incorrect depth calculations, and invalid tree traversal results. SQL detects cycles using recursive CTEs with a path-tracking or depth-limit guard.
> **"In the Employees table where each employee has a ManagerID referencing another EmployeeID, detect any circular references in the management hierarchy: find employees who appear in their own management chain, and identify the full cycle path."**

## Table Reference
**Employees** — `schemas/04_Employees.csv`

## Solution Query

```sql
-- Step 1: Detect self-referencing employees (immediate cycle)
SELECT
    EmployeeID,
    FullName,
    ManagerID,
    'SELF-LOOP: Employee is their own manager' AS CycleType
FROM Employees
WHERE ManagerID = EmployeeID;

-- Step 2: Cycle detection using recursive CTE with path tracking
-- MAXRECURSION 0 would loop forever on cycles; use MAXRECURSION 100 as safety
WITH HierarchyCTE AS (
    -- Anchor: start from each employee
    SELECT
        EmployeeID AS StartNode,
        EmployeeID AS CurrentNode,
        ManagerID AS NextNode,
        CAST(EmployeeID AS VARCHAR(MAX)) AS PathStr,
        1 AS Depth
    FROM Employees
    WHERE ManagerID IS NOT NULL
      AND ManagerID <> EmployeeID   -- exclude immediate self-loops

    UNION ALL

    -- Recursive: follow the manager chain
    SELECT
        h.StartNode,
        e.EmployeeID AS CurrentNode,
        e.ManagerID AS NextNode,
        h.PathStr + ' → ' + CAST(e.EmployeeID AS VARCHAR(10)),
        h.Depth + 1
    FROM HierarchyCTE h
    JOIN Employees e ON e.EmployeeID = h.NextNode
    WHERE e.ManagerID IS NOT NULL
      AND e.ManagerID <> e.EmployeeID          -- avoid self-loops in recursion
      AND CHARINDEX(CAST(e.EmployeeID AS VARCHAR(10)), h.PathStr) = 0  -- cycle guard
      AND h.Depth < 20   -- absolute depth limit
)
-- Step 3: Identify nodes that appear in their own descendant chain
SELECT DISTINCT
    StartNode AS EmployeeInCycle,
    PathStr AS CyclePath,
    Depth AS CycleLength,
    'CYCLE DETECTED: Employee appears in own management chain' AS Alert
FROM HierarchyCTE
WHERE CurrentNode = StartNode  -- the path has looped back to the start
ORDER BY Depth;

-- Step 4: Full hierarchy depth and structure (for cycle-free trees only)
-- Use OPTION (MAXRECURSION 50) to safely limit in production
WITH HierarchyCTE AS (
    -- Root employees: no manager, or manager not in table
    SELECT
        EmployeeID,
        FullName,
        ManagerID,
        0 AS Depth,
        CAST(FullName AS VARCHAR(MAX)) AS OrgPath
    FROM Employees
    WHERE ManagerID IS NULL
       OR NOT EXISTS (SELECT 1 FROM Employees m WHERE m.EmployeeID = Employees.ManagerID)

    UNION ALL

    SELECT
        e.EmployeeID,
        e.FullName,
        e.ManagerID,
        h.Depth + 1,
        h.OrgPath + ' > ' + e.FullName
    FROM Employees e
    JOIN HierarchyCTE h ON h.EmployeeID = e.ManagerID
    WHERE e.ManagerID <> e.EmployeeID   -- guard against self-loop
)
SELECT
    EmployeeID,
    FullName,
    ManagerID,
    Depth AS HierarchyLevel,
    OrgPath,
    CASE
        WHEN Depth = 0 THEN 'ROOT: Top of hierarchy'
        WHEN Depth = 1 THEN 'LEVEL 1: Reports directly to root'
        WHEN Depth > 5 THEN 'DEEP: Hierarchy depth >5 — may indicate flattening opportunity'
        ELSE 'LEVEL ' + CAST(Depth AS VARCHAR)
    END AS LevelLabel
FROM HierarchyCTE
ORDER BY OrgPath
OPTION (MAXRECURSION 50);

-- Step 5: Employees who reference a manager that does not exist
SELECT
    e.EmployeeID,
    e.FullName,
    e.ManagerID,
    'DANGLING MANAGER: ManagerID not in Employees table' AS Issue
FROM Employees e
WHERE e.ManagerID IS NOT NULL
  AND e.ManagerID <> e.EmployeeID
  AND NOT EXISTS (SELECT 1 FROM Employees m WHERE m.EmployeeID = e.ManagerID);
```

| EMP-004 | Carol Davis | 2 | Alice Johnson > Bob Smith > Carol Davis | LEVEL 2 |

|---|---|---|---|
| EMP-010 | Frank White | EMP-099 | DANGLING MANAGER: ManagerID not in Employees table |

## Explanation

**Path-string cycle guard**
`CHARINDEX(CAST(e.EmployeeID AS VARCHAR(10)), h.PathStr) = 0` checks whether the current node's ID already appears anywhere in the accumulated path string. If it does, adding it again would create a loop. The path string serves as a visited-nodes record, preventing the recursion from following cycles. This is more robust than using a depth counter alone, which would incorrectly truncate valid deep hierarchies rather than detecting true cycles.

**MAXRECURSION safety limit**
SQL Server's default maximum recursion depth is 100. For a genuine circular reference without the path guard, the query would hit this limit and throw an error rather than looping forever. During development, `OPTION (MAXRECURSION 0)` removes the limit (dangerous on circular data); `OPTION (MAXRECURSION 50)` provides a safe practical limit for most org charts (it's rare for genuine reporting hierarchies to exceed 10–15 levels).

**Root identification for anchor**
The anchor of the hierarchy CTE must be the root nodes: employees who either have no ManagerID (NULL) or whose ManagerID references an employee not in the table (the top-level root may reference an external system ID). Using `WHERE ManagerID IS NULL` alone misses cases where the root's ManagerID is a non-NULL sentinel value.

**Three cycle types**
Step 5 classifies three structural problems: (1) self-loops (ManagerID = EmployeeID), caught in Step 1; (2) multi-node cycles (A→B→C→A), caught in Step 3; (3) dangling references (ManagerID points to a non-existent record), caught in Step 5. All three must be resolved before a recursive hierarchy CTE can safely traverse the entire tree.

## Severity
**High** — Circular references in self-referencing hierarchies cause recursive queries to fail, BI tools to crash when rendering org charts or drill-down hierarchies, and ETL processes to loop indefinitely. They are particularly dangerous because they are silent until a query actually traverses the cycle — a simple SELECT on the flat table returns without error, masking the structural problem.
