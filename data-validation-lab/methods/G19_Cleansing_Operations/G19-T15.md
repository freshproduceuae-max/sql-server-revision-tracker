# G19-T15 — Cleansing Operations | Flag and Status Field Standardisation

## ID
G19-T15

## Group
19 — Cleansing Operations

## Type
Flag and Status Field Standardisation — Ensuring Boolean and Status Fields Contain Only Values From Their Defined Domain

## Live Scenario
A customer database accumulated IsActive values of 1, 0, 'Y', 'N', 'Yes', 'No', 'TRUE', 'FALSE', NULL, and 2 over five years of integrations with different source systems. A GDPR compliance tool queries `WHERE IsActive = 0` to identify inactive customers for data erasure, but finds only 30% of the customers it should because the other inactive customers have IsActive = 'N', 'No', or 'FALSE'. The 70% of inactive customers not identified by the query continue to receive marketing emails, violating GDPR lawful processing requirements. Standardising IsActive to a BIT column (1/0 only) and NULLs to a known default ensures the compliance query works correctly.

## The Question
> Flag and status field standardisation ensures that fields with a defined value domain (BIT: 0/1, Status: predefined set, IsActive: TRUE/FALSE) contain only permitted values. SQL detects out-of-domain values with a NOT IN check against the permitted set, validates BIT equivalence using TRY_CAST, and produces a remediation script that maps each non-standard value to its canonical equivalent. NULL handling is documented separately (NULL = unknown vs NULL = default false) because NULLs affect IS NULL queries differently from 0 or 'N'.
> **"Audit and standardise boolean and status flag fields across the Customers, Orders, and Products tables: verify IsActive contains only 0/1/NULL, verify Orders.Status contains only the permitted vocabulary, verify Products.IsActive is consistent, and produce a domain constraint violation report with remediation recommendations."**

## Table Reference
**Customers** — `schemas/01_Customers.csv`
**Orders** — `schemas/02_Orders.csv`
**Products** — `schemas/03_Products.csv`
**Employees** — `schemas/04_Employees.csv`

## Solution Query

```sql
-- Step 1: IsActive domain audit — Customers
SELECT
    CustomerID,
    IsActive,
    CASE
        WHEN IsActive IS NULL
             THEN 'NULL: Unknown active status — business must decide if NULL = inactive or unknown'
        WHEN IsActive = 1 OR IsActive = 0
             THEN 'VALID BIT: ' + CAST(IsActive AS VARCHAR)
        WHEN TRY_CAST(IsActive AS BIT) IS NOT NULL
             THEN 'CASTABLE: "' + CAST(IsActive AS VARCHAR)
                  + '" maps to BIT ' + CAST(TRY_CAST(IsActive AS BIT) AS VARCHAR)
        ELSE 'DOMAIN VIOLATION: IsActive = "' + CAST(IsActive AS VARCHAR)
             + '" is not a valid boolean value'
    END AS IsActiveFlag,
    -- Proposed canonical value
    CASE
        WHEN IsActive IS NULL THEN NULL
        WHEN IsActive = 1 THEN 1
        WHEN IsActive = 0 THEN 0
        WHEN TRY_CAST(IsActive AS BIT) IS NOT NULL THEN TRY_CAST(IsActive AS BIT)
        ELSE NULL  -- cannot determine — manual review
    END AS ProposedCanonicalValue
FROM Customers;

-- Step 2: Orders Status domain audit — validate against permitted vocabulary
WITH PermittedStatuses AS (
    SELECT 'Pending'    AS Status UNION ALL
    SELECT 'Processing'           UNION ALL
    SELECT 'Delivered'            UNION ALL
    SELECT 'Returned'             UNION ALL
    SELECT 'Cancelled'
)
SELECT
    o.OrderID,
    o.Status AS StoredStatus,
    ps.Status AS InPermittedSet,
    CASE
        WHEN o.Status IS NULL
             THEN 'NULL STATUS: Orders must have a status — default to Pending?'
        WHEN ps.Status IS NOT NULL
             THEN 'VALID: "' + o.Status + '" is in the permitted Status vocabulary'
        ELSE 'DOMAIN VIOLATION: "' + o.Status
             + '" is not in {Pending, Processing, Delivered, Returned, Cancelled}'
    END AS StatusDomainFlag
FROM Orders o
LEFT JOIN PermittedStatuses ps ON o.Status = ps.Status
ORDER BY StatusDomainFlag DESC, o.OrderID;

-- Step 3: EmploymentType domain audit — Employees
WITH PermittedEmploymentTypes AS (
    SELECT 'Full-Time'  AS EmpType UNION ALL
    SELECT 'Part-Time'             UNION ALL
    SELECT 'Contractor'            UNION ALL
    SELECT 'Intern'
)
SELECT
    e.EmployeeID,
    e.FullName,
    e.EmploymentType,
    CASE
        WHEN e.EmploymentType IS NULL
             THEN 'NULL: Employment type missing'
        WHEN pet.EmpType IS NOT NULL
             THEN 'VALID'
        ELSE 'DOMAIN VIOLATION: "' + e.EmploymentType
             + '" is not in {Full-Time, Part-Time, Contractor, Intern}'
    END AS EmploymentTypeFlag
FROM Employees e
LEFT JOIN PermittedEmploymentTypes pet ON e.EmploymentType = pet.EmpType;

-- Step 4: Products IsActive cross-consistency check
-- An inactive product (IsActive=0) should not have a Price > 0 shown as available
-- A product with StockQuantity > 0 but IsActive = 0 is a stock management inconsistency
SELECT
    ProductID,
    ProductName,
    IsActive,
    Price,
    StockQuantity,
    CASE
        WHEN IsActive IS NULL
             THEN 'NULL IsActive: Product active status unknown'
        WHEN IsActive = 0 AND StockQuantity > 0
             THEN 'INACTIVE WITH STOCK: Product is inactive but has '
                  + CAST(StockQuantity AS VARCHAR)
                  + ' units in stock — verify whether stock should be returned/written off'
        WHEN IsActive = 0 AND Price > 0
             THEN 'INACTIVE WITH PRICE: Product is inactive but Price = '
                  + CAST(Price AS VARCHAR)
                  + ' — price should be zeroed for inactive products'
        WHEN IsActive = 1 AND (Price IS NULL OR Price = 0)
             THEN 'ACTIVE WITHOUT PRICE: Product is active but has no price — '
                  + 'cannot be sold'
        WHEN IsActive = 1 AND StockQuantity = 0
             THEN 'OUT OF STOCK: Active product with zero stock — will create orders that cannot fulfil'
        ELSE 'CONSISTENT: IsActive and related fields are aligned'
    END AS ConsistencyFlag
FROM Products;

-- Step 5: Domain constraint violation scorecard
WITH OrderStatusStats AS (
    SELECT
        COUNT(*) AS Total,
        SUM(CASE WHEN Status IN ('Pending','Processing','Delivered','Returned','Cancelled')
                 THEN 1 ELSE 0 END) AS ValidCount,
        SUM(CASE WHEN Status IS NULL THEN 1 ELSE 0 END) AS NullCount,
        SUM(CASE WHEN Status NOT IN ('Pending','Processing','Delivered','Returned','Cancelled')
                 AND Status IS NOT NULL THEN 1 ELSE 0 END) AS ViolationCount
    FROM Orders
),
CustomerIsActiveStats AS (
    SELECT
        COUNT(*) AS Total,
        SUM(CASE WHEN IsActive IN (0, 1) THEN 1 ELSE 0 END) AS ValidCount,
        SUM(CASE WHEN IsActive IS NULL THEN 1 ELSE 0 END) AS NullCount,
        SUM(CASE WHEN IsActive NOT IN (0, 1) AND IsActive IS NOT NULL THEN 1 ELSE 0 END) AS ViolationCount
    FROM Customers
),
ProductIsActiveStats AS (
    SELECT
        COUNT(*) AS Total,
        SUM(CASE WHEN IsActive IN (0, 1) THEN 1 ELSE 0 END) AS ValidCount,
        SUM(CASE WHEN IsActive IS NULL THEN 1 ELSE 0 END) AS NullCount,
        SUM(CASE WHEN IsActive NOT IN (0, 1) AND IsActive IS NOT NULL THEN 1 ELSE 0 END) AS ViolationCount
    FROM Products
)
SELECT 'Orders.Status' AS FieldName, Total, ValidCount, NullCount, ViolationCount,
    ROUND(100.0 * ValidCount / NULLIF(Total - NullCount, 0), 1) AS ConformancePct
FROM OrderStatusStats
UNION ALL
SELECT 'Customers.IsActive', Total, ValidCount, NullCount, ViolationCount,
    ROUND(100.0 * ValidCount / NULLIF(Total - NullCount, 0), 1)
FROM CustomerIsActiveStats
UNION ALL
SELECT 'Products.IsActive', Total, ValidCount, NullCount, ViolationCount,
    ROUND(100.0 * ValidCount / NULLIF(Total - NullCount, 0), 1)
FROM ProductIsActiveStats;
```

## Explanation

**NULL as a distinct state from FALSE**
`IsActive IS NULL` and `IsActive = 0` are semantically different: NULL means the active status is unknown, while 0 means the record is definitively inactive. A compliance query `WHERE IsActive = 0` does not return NULLs. If NULLs mean "unknown, treat as inactive for compliance purposes", the query must be `WHERE ISNULL(IsActive, 0) = 0`. Documenting the business meaning of NULL for each boolean field is as important as standardising the non-NULL values.

**NOT IN with NULL produces unexpected results**
`WHERE Status NOT IN ('Pending', 'Processing', 'Delivered', 'Returned', 'Cancelled')` does NOT return rows where Status IS NULL, because `NULL NOT IN (...)` evaluates to UNKNOWN rather than TRUE. To include NULLs in a domain violation check, the WHERE clause must be: `WHERE Status IS NULL OR Status NOT IN (...)`. This is a common source of missed domain violations in validation queries.

**BIT column enforcement as the definitive fix**
A BIT column in SQL Server only allows 0, 1, and NULL — any other value is rejected at the database level. Changing IsActive from NVARCHAR or INT to BIT enforces domain conformance permanently without ongoing validation checks. The schema change requires: (1) audit that all existing values can be cast to BIT, (2) ALTER TABLE to change the column type, (3) update application code that may compare `IsActive = 'Y'` to `IsActive = 1`.

**Cross-field consistency for flags**
Step 4 illustrates that boolean flag validity is not only about the field's own value but also about consistency with related fields. An IsActive = 0 product with StockQuantity > 0 is internally inconsistent — the flag and the related fact contradict each other. Cross-field consistency checks surface these contradictions that single-field domain checks miss.

## Severity
**High for compliance-critical fields** — A misclassified IsActive field in a GDPR or suppression context has direct regulatory consequences. For operational flags (product active/inactive), the severity is medium — an incorrectly flagged product appears in or disappears from listings incorrectly. In both cases, the remediation is straightforward: standardise the domain and add a CHECK constraint.
