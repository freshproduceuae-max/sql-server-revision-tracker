# G19-T12 — Cleansing Operations | Derived Field Recalculation

## ID
G19-T12

## Group
19 — Cleansing Operations

## Type
Derived Field Recalculation — Detecting and Correcting Fields Whose Values Should Be Derived from Other Fields but Have Drifted Out of Sync

## Live Scenario
An e-commerce platform stores TotalAmount at the order level as a denormalised convenience field. When a returns processing bug credits the wrong amount, TotalAmount is updated directly in the Orders table without recalculating it from the individual order lines. Over three months, 890 orders accumulate where TotalAmount does not equal Price × Quantity (the correct derivation). Finance notices the discrepancy when the sum of TotalAmounts differs from the sum of Price × Quantity by £14,700. A derived field audit identifies each mismatched order, quantifies the delta, and generates the corrected TotalAmount based on the authoritative source fields.

## The Question
> Derived field validation checks whether a stored derived value still matches the result of the formula used to compute it, using the current values of the source fields. SQL detects drift with a computed comparison column (StoredValue vs ROUND(DerivedFormula, 2)) and a tolerance threshold (ROUND(ABS(stored - derived), 2) > 0.01 to account for floating-point rounding). The recalculation produces the correct derived value alongside the original for review, and an impact summary shows the financial magnitude of the drift.
> **"Audit derived fields in the Orders and Products tables: verify that TotalAmount in Orders is consistent with Price × implied quantity (TotalAmount / Price), check that discounted price (Price × (1 - DiscountPercent/100)) in Products matches expected margins, and produce a recalculation impact summary showing the total value at risk from derived field drift."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Products** — `schemas/03_Products.csv`

## Solution Query

```sql
-- Step 1: Verify TotalAmount is consistent with product price (implied quantity check)
WITH OrderWithPrice AS (
    SELECT
        o.OrderID,
        o.CustomerID,
        o.ProductID,
        o.TotalAmount,
        p.Price AS UnitPrice,
        -- Implied quantity: how many units does the total amount suggest?
        CASE
            WHEN p.Price > 0
                 THEN ROUND(o.TotalAmount / p.Price, 2)
            ELSE NULL
        END AS ImpliedQuantity,
        -- Expected amount if quantity is a whole number
        CASE
            WHEN p.Price > 0
                 THEN ROUND(p.Price * ROUND(o.TotalAmount / p.Price, 0), 2)
            ELSE NULL
        END AS ExpectedAmount
    FROM Orders o
    LEFT JOIN Products p ON o.ProductID = p.ProductID
    WHERE o.TotalAmount IS NOT NULL AND p.Price IS NOT NULL
)
SELECT
    OrderID,
    CustomerID,
    ProductID,
    ROUND(TotalAmount, 2) AS StoredTotalAmount,
    ROUND(UnitPrice, 2) AS UnitPrice,
    ROUND(ImpliedQuantity, 2) AS ImpliedQuantity,
    ROUND(ExpectedAmount, 2) AS ExpectedWholeUnitAmount,
    ROUND(ABS(TotalAmount - ExpectedAmount), 2) AS AmountDelta,
    CASE
        WHEN ImpliedQuantity = ROUND(ImpliedQuantity, 0)
             THEN 'CONSISTENT: TotalAmount = '
                  + CAST(ROUND(ImpliedQuantity, 0) AS VARCHAR)
                  + ' × ' + CAST(ROUND(UnitPrice, 2) AS VARCHAR)
        WHEN ABS(TotalAmount - ExpectedAmount) <= 0.02
             THEN 'ROUNDING DIFF: Delta of '
                  + CAST(ROUND(ABS(TotalAmount - ExpectedAmount), 2) AS VARCHAR)
                  + ' — likely rounding at line level'
        ELSE 'DRIFT DETECTED: TotalAmount ' + CAST(ROUND(TotalAmount,2) AS VARCHAR)
             + ' ≠ expected ' + CAST(ROUND(ExpectedAmount,2) AS VARCHAR)
             + ' (Δ = ' + CAST(ROUND(ABS(TotalAmount-ExpectedAmount),2) AS VARCHAR) + ')'
    END AS ConsistencyFlag
FROM OrderWithPrice
ORDER BY AmountDelta DESC;

-- Step 2: Product discounted price derivation check
SELECT
    ProductID,
    ProductName,
    Price,
    DiscountPercent,
    VATRate,
    -- Derived fields that should exist but are not stored separately
    ROUND(Price * (1 - ISNULL(DiscountPercent, 0) / 100.0), 2) AS DiscountedPrice,
    ROUND(Price * (1 - ISNULL(DiscountPercent, 0) / 100.0)
               * (1 + ISNULL(VATRate, 0) / 100.0), 2) AS PriceIncVAT,
    -- Check internal consistency: DiscountPercent should not push price negative
    CASE
        WHEN DiscountPercent IS NULL
             THEN 'NO DISCOUNT: Price = ' + CAST(Price AS VARCHAR)
        WHEN DiscountPercent < 0
             THEN 'NEGATIVE DISCOUNT: Invalid'
        WHEN DiscountPercent > 100
             THEN 'DISCOUNT > 100%: Results in negative price'
        WHEN Price * (1 - DiscountPercent/100.0) < 0
             THEN 'DERIVED PRICE NEGATIVE: ' + CAST(ROUND(Price*(1-DiscountPercent/100.0),2) AS VARCHAR)
        WHEN DiscountPercent > 50
             THEN 'HIGH DISCOUNT: Discounted price = £'
                  + CAST(ROUND(Price*(1-DiscountPercent/100.0),2) AS VARCHAR)
                  + ' — verify margin is acceptable'
        ELSE 'Derivation consistent: Discounted = £'
             + CAST(ROUND(Price*(1-DiscountPercent/100.0),2) AS VARCHAR)
             + ', Inc VAT = £' + CAST(ROUND(Price*(1-ISNULL(DiscountPercent,0)/100.0)*(1+ISNULL(VATRate,0)/100.0),2) AS VARCHAR)
    END AS DerivationFlag
FROM Products
ORDER BY DiscountPercent DESC;

-- Step 3: Employee salary derivation — Annual vs Hourly rate consistency
-- Annual salary should equal HourlyRate × 52 (weeks) × 40 (hours/week) = HourlyRate × 2080
SELECT
    EmployeeID,
    FullName,
    EmploymentType,
    HourlyRate,
    ROUND(HourlyRate * 2080, 2) AS DerivedAnnualSalary,
    ROUND(HourlyRate * 260 * 8, 2) AS DerivedSalaryAlt,  -- 260 working days × 8 hours
    CASE
        WHEN HourlyRate IS NULL
             THEN 'NULL RATE: Cannot derive annual salary'
        WHEN HourlyRate <= 0
             THEN 'INVALID RATE: HourlyRate must be > 0'
        WHEN EmploymentType = 'Full-Time'
             AND ROUND(HourlyRate * 2080, 2) < 20800
             THEN 'BELOW MINIMUM WAGE: Annual equivalent £'
                  + CAST(ROUND(HourlyRate * 2080, 2) AS VARCHAR)
                  + ' (hourly £' + CAST(ROUND(HourlyRate, 2) AS VARCHAR) + ')'
        WHEN EmploymentType = 'Full-Time'
             AND ROUND(HourlyRate * 2080, 2) > 500000
             THEN 'VERY HIGH: Annual equivalent £'
                  + CAST(ROUND(HourlyRate * 2080, 2) AS VARCHAR)
                  + ' — verify no pence/pounds error'
        ELSE 'Rate consistent: Annual equivalent = £'
             + CAST(ROUND(HourlyRate * 2080, 2) AS VARCHAR)
    END AS RateConsistencyFlag
FROM Employees
WHERE HireDate IS NOT NULL
ORDER BY HourlyRate DESC;

-- Step 4: Total revenue reconciliation — sum of order amounts vs sum by product
WITH OrderRevenue AS (
    SELECT
        ProductID,
        COUNT(*) AS OrderCount,
        ROUND(SUM(TotalAmount), 2) AS StoredRevenue
    FROM Orders
    WHERE TotalAmount IS NOT NULL
    GROUP BY ProductID
),
DerivedRevenue AS (
    SELECT
        o.ProductID,
        COUNT(*) AS OrderCount,
        ROUND(SUM(p.Price), 2) AS DerivedRevenue  -- assuming qty=1 for simplicity
    FROM Orders o
    LEFT JOIN Products p ON o.ProductID = p.ProductID
    WHERE o.TotalAmount IS NOT NULL
    GROUP BY o.ProductID
)
SELECT
    COALESCE(or_.ProductID, dr.ProductID) AS ProductID,
    or_.StoredRevenue,
    dr.DerivedRevenue,
    ROUND(or_.StoredRevenue - dr.DerivedRevenue, 2) AS RevenueDelta,
    CASE
        WHEN ABS(or_.StoredRevenue - dr.DerivedRevenue) <= 1.00
             THEN 'RECONCILES: Delta within £1.00 tolerance'
        WHEN or_.StoredRevenue > dr.DerivedRevenue
             THEN 'STORED > DERIVED: £' + CAST(ROUND(or_.StoredRevenue - dr.DerivedRevenue,2) AS VARCHAR)
                  + ' excess in stored TotalAmount — may reflect discounts in stored but not unit price'
        ELSE 'STORED < DERIVED: £' + CAST(ROUND(dr.DerivedRevenue - or_.StoredRevenue,2) AS VARCHAR)
             + ' shortfall — possible data corruption'
    END AS ReconciliationFlag
FROM OrderRevenue or_
FULL OUTER JOIN DerivedRevenue dr ON or_.ProductID = dr.ProductID;

-- Step 5: Derived field drift impact summary
SELECT
    'TotalAmount vs Price × Implied Qty' AS DerivedCheck,
    COUNT(*) AS TotalOrders,
    SUM(CASE WHEN ABS(o.TotalAmount - ROUND(p.Price * ROUND(o.TotalAmount/NULLIF(p.Price,0),0),2)) <= 0.02
             THEN 1 ELSE 0 END) AS Consistent,
    SUM(CASE WHEN ABS(o.TotalAmount - ROUND(p.Price * ROUND(o.TotalAmount/NULLIF(p.Price,0),0),2)) > 0.02
             AND p.Price IS NOT NULL
             THEN 1 ELSE 0 END) AS Drifted,
    ROUND(SUM(CASE WHEN ABS(o.TotalAmount - ROUND(p.Price * ROUND(o.TotalAmount/NULLIF(p.Price,0),0),2)) > 0.02
                   AND p.Price IS NOT NULL
                   THEN ABS(o.TotalAmount - ROUND(p.Price * ROUND(o.TotalAmount/NULLIF(p.Price,0),0),2))
                   ELSE 0 END), 2) AS TotalDriftValue
FROM Orders o
LEFT JOIN Products p ON o.ProductID = p.ProductID
WHERE o.TotalAmount IS NOT NULL;
```

## Explanation

**Denormalised derived fields are always at risk of drift**
Any time a value that could be computed from other fields is also stored separately, those two values can diverge. Common causes: (1) an UPDATE to a source field (Price changed) without recalculating the derived field (TotalAmount); (2) a discount or adjustment applied directly to the derived field without tracking the components; (3) a bug in the calculation formula that is later fixed, leaving old records with the wrong value. The only way to prevent drift is either to not store the derived value at all (calculate it at query time) or to enforce it via a trigger or computed column.

**Tolerance threshold for floating-point comparison**
`ABS(stored - derived) > 0.01` rather than `stored <> derived` accounts for floating-point arithmetic differences and rounding at different stages. Price × Quantity may produce 19.9999999 due to floating-point representation, which rounds to 20.00 — a 0.00000001 difference that is not a real discrepancy. Set the tolerance based on the field's precision (2 decimal places for currency → 0.01 tolerance).

**SQL Server computed columns as a prevention strategy**
SQL Server supports computed columns (`Price * Qty AS TotalAmount`) which guarantee the derived value always equals the formula result. Persisted computed columns (`WITH PERSISTED`) are stored on disk and can be indexed. The trade-off: schema changes to the formula require an ALTER TABLE, which can be expensive on large tables.

**Recalculation before correction**
Before running an UPDATE to correct drifted derived fields, verify the source fields (Price, Quantity) are themselves correct. If Price was incorrectly updated and the derived TotalAmount was correctly maintained from the wrong Price, "correcting" TotalAmount to match the wrong Price propagates the source error into the derived field. Always trace the drift to the root cause field before correcting.

## Severity
**High for financial fields** — Derived field drift in TotalAmount directly affects revenue reporting, commission calculations, and financial reconciliation. A £14,700 discrepancy between the sum of TotalAmount and the sum of Price × Quantity is material for financial reporting. Medium severity for non-financial derived fields (e.g., a display name that doesn't match FirstName + LastName).
