# G19-T02 — Cleansing Operations | Case Normalisation

## ID
G19-T02

## Group
19 — Cleansing Operations

## Type
Case Normalisation — Standardising Text Fields to Consistent Case for Reliable Matching and Display

## Live Scenario
A marketing team queries customer emails for a campaign suppression check. The suppression list contains emails in lowercase ("alice@example.com"), but the CRM stores emails in mixed case ("Alice@Example.COM") because the registration form preserves user input. The suppression join fails for 2,800 customers because `'Alice@Example.COM' = 'alice@example.com'` evaluates to FALSE under a case-sensitive collation. These customers receive a marketing email they had asked to be suppressed from. A case normalisation script applied at load time — `LOWER(Email)` — would have prevented the mismatch.

## The Question
> Case normalisation standardises text fields to a target case: LOWER for emails, usernames, and codes where case is not semantically meaningful; UPPER for country codes, currency codes, and product codes where uppercase is the standard; proper case (UPPER on first character, LOWER on rest) for names and addresses. SQL implements these conversions with LOWER(), UPPER(), and a proper-case expression, then checks which records deviate from the target case.
> **"Normalise case across the Customers and Products tables: verify that Email fields are lowercase, that Country codes are in the expected case, that ProductCode values are uppercase, and produce a case normalisation scorecard showing the proportion of records that already conform vs those requiring correction."**

## Table Reference
**Customers** — `schemas/01_Customers.csv`
**Products** — `schemas/03_Products.csv`

## Solution Query

```sql
-- Step 1: Email lowercase validation
SELECT
    CustomerID,
    Email,
    LOWER(Email) AS NormalisedEmail,
    CASE
        WHEN Email IS NULL
             THEN 'NULL'
        WHEN Email = LOWER(Email)
             THEN 'CORRECT: Email is already lowercase'
        ELSE 'NEEDS NORMALISING: Email contains uppercase characters — '
             + CAST(LEN(Email) - LEN(LOWER(Email)) AS VARCHAR) + ' case differences'
    END AS EmailCaseFlag
FROM Customers;

-- Step 2: Country case validation
-- Country values: expected format 'UK', 'US', 'Germany' — check consistency
SELECT
    CustomerID,
    Country,
    UPPER(Country) AS UpperCountry,
    CASE
        WHEN Country IS NULL
             THEN 'NULL'
        WHEN Country = 'uk' OR Country = 'UK' OR Country = 'Uk'
             THEN CASE WHEN Country = 'UK' THEN 'CORRECT' ELSE 'WRONG CASE: "' + Country + '" should be "UK"' END
        WHEN Country = 'us' OR Country = 'US' OR Country = 'Us'
             THEN CASE WHEN Country = 'US' THEN 'CORRECT' ELSE 'WRONG CASE: "' + Country + '" should be "US"' END
        -- Country names: first letter of each word should be capitalised
        WHEN Country = LOWER(Country)
             THEN 'ALL LOWERCASE: Country "' + Country + '" should have initial capitals'
        WHEN Country = UPPER(Country) AND LEN(Country) > 3
             THEN 'ALL UPPERCASE: Country "' + Country
                  + '" is entirely uppercase (acceptable for codes, not for names)'
        ELSE 'REVIEW: "' + Country + '" — verify expected case format'
    END AS CountryCaseFlag
FROM Customers;

-- Step 3: ProductCode uppercase validation
SELECT
    ProductID,
    ProductCode,
    UPPER(ProductCode) AS NormalisedProductCode,
    CASE
        WHEN ProductCode IS NULL
             THEN 'NULL'
        WHEN ProductCode = UPPER(ProductCode)
             THEN 'CORRECT: ProductCode is uppercase'
        ELSE 'NEEDS NORMALISING: ProductCode "' + ProductCode
             + '" contains lowercase — should be "' + UPPER(ProductCode) + '"'
    END AS ProductCodeCaseFlag
FROM Products
WHERE ProductCode IS NOT NULL;

-- Step 4: Proper case for customer names
-- Name fields should be "First Letter Uppercase, Rest Lowercase"
-- e.g. "ALICE" → "Alice", "alice" → "Alice", "ALICE SMITH" → "Alice Smith"
SELECT
    CustomerID,
    FirstName,
    LastName,
    -- Simple proper case: first char upper, rest lower
    UPPER(LEFT(ISNULL(FirstName,''), 1)) + LOWER(SUBSTRING(ISNULL(FirstName,''), 2, LEN(ISNULL(FirstName,'')))) AS ProperFirstName,
    UPPER(LEFT(ISNULL(LastName,''),  1)) + LOWER(SUBSTRING(ISNULL(LastName,''),  2, LEN(ISNULL(LastName,''))))  AS ProperLastName,
    CASE
        WHEN FirstName IS NULL THEN 'NULL'
        WHEN FirstName = UPPER(FirstName) AND LEN(FirstName) > 1
             THEN 'ALL CAPS: "' + FirstName + '" — possible mainframe import'
        WHEN FirstName = LOWER(FirstName)
             THEN 'ALL LOWERCASE: "' + FirstName + '" — case not applied at data entry'
        WHEN FirstName <> UPPER(LEFT(FirstName,1)) + LOWER(SUBSTRING(FirstName,2,LEN(FirstName)))
         AND CHARINDEX(' ', FirstName) = 0
             THEN 'MID-CAPS: "' + FirstName + '" — unusual capitalisation'
        ELSE 'OK: First name case looks correct'
    END AS FirstNameCaseFlag
FROM Customers;

-- Step 5: Case normalisation scorecard
SELECT
    FieldName,
    TotalRows,
    AlreadyCorrect,
    NeedsNormalising,
    NullCount,
    ROUND(100.0 * AlreadyCorrect / NULLIF(TotalRows - NullCount, 0), 1) AS ConformancePct
FROM (
    SELECT
        'Customers.Email (lowercase)'    AS FieldName,
        COUNT(*)                          AS TotalRows,
        SUM(CASE WHEN Email = LOWER(Email) AND Email IS NOT NULL THEN 1 ELSE 0 END) AS AlreadyCorrect,
        SUM(CASE WHEN Email <> LOWER(Email) THEN 1 ELSE 0 END) AS NeedsNormalising,
        SUM(CASE WHEN Email IS NULL THEN 1 ELSE 0 END) AS NullCount
    FROM Customers
    UNION ALL
    SELECT
        'Products.ProductCode (uppercase)',
        COUNT(*),
        SUM(CASE WHEN ProductCode = UPPER(ProductCode) AND ProductCode IS NOT NULL THEN 1 ELSE 0 END),
        SUM(CASE WHEN ProductCode <> UPPER(ProductCode) THEN 1 ELSE 0 END),
        SUM(CASE WHEN ProductCode IS NULL THEN 1 ELSE 0 END)
    FROM Products
    UNION ALL
    SELECT
        'Customers.Country (expected case)',
        COUNT(*),
        SUM(CASE WHEN Country IN ('UK','US','Germany','Internal') THEN 1 ELSE 0 END),
        SUM(CASE WHEN Country NOT IN ('UK','US','Germany','Internal') AND Country IS NOT NULL THEN 1 ELSE 0 END),
        SUM(CASE WHEN Country IS NULL THEN 1 ELSE 0 END)
    FROM Customers
) CaseScorecard;

-- UPDATE script (comment out to run)
/*

UPDATE Customers SET Email = LOWER(Email)
WHERE Email <> LOWER(Email) AND Email IS NOT NULL;

-- Normalise ProductCode to uppercase
UPDATE Products SET ProductCode = UPPER(ProductCode)
WHERE ProductCode <> UPPER(ProductCode) AND ProductCode IS NOT NULL;
*/
```

## Explanation

**Collation and case sensitivity**
SQL Server's default collation (`SQL_Latin1_General_CP1_CI_AS`) is case-insensitive (CI), meaning `'Alice' = 'alice'` evaluates to TRUE. This makes case mismatches invisible to most queries — the WHERE clause matches regardless of case. But when data is exported to a case-sensitive system (Linux file system, PostgreSQL with CS collation, Python string comparison), mismatches re-appear. Normalising case at load time prevents cross-system matching failures.

**Simple proper case limitation**
The proper case expression `UPPER(LEFT(col,1)) + LOWER(SUBSTRING(col,2,LEN(col)))` correctly capitalises single-word names ("alice" → "Alice") but fails for multi-word names ("alice smith" → "Alice smith", not "Alice Smith"). A full proper-case implementation requires splitting on spaces and applying the capitalisation to each word. For the purposes of validation detection, the simple expression identifies names that are entirely uppercase or lowercase, which are the most common cases.

**Email case normalisation safety**
Email addresses are technically case-sensitive in the local part (before @) per RFC 5321, but in practice virtually all email providers treat the local part case-insensitively. Normalising to lowercase is safe for all major providers (Gmail, Outlook, Yahoo) and prevents matching failures without losing any functional meaning. The domain part (after @) is always case-insensitive per DNS specification.

**Country code format standards**
ISO 3166-1 alpha-2 (UK = "GB" officially, though "UK" is commonly used) defines country codes in uppercase. ISO 3166-1 alpha-3 uses uppercase 3-letter codes. Full country names (Germany, France) use standard title case. The validation in Step 2 checks for consistency within the expected format for this dataset — not necessarily strict ISO compliance.

## Severity
**Low to Medium** — Case mismatches are usually invisible within a single system (case-insensitive collation handles them), but cause failures at system boundaries. The impact escalates from cosmetic (names displayed in ALL CAPS in customer-facing UIs) to operational (suppression list matching failures that cause regulatory non-compliance) depending on how the data is used.
