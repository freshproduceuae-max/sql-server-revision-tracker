# G19-T18 — Cleansing Operations | Temporal Sequence and Chronological Consistency

## ID
G19-T18

## Group
19 — Cleansing Operations

## Type
Temporal Sequence and Chronological Consistency — Detecting and Correcting Date Fields That Violate Expected Chronological Ordering

## Live Scenario
A fulfilment system records five dates per order: OrderDate → ConfirmedDate → DispatchDate → DeliveryDate → ReturnDate. The sequence must be strictly non-decreasing: an order cannot be dispatched before it is confirmed, delivered before dispatched, or returned before delivered. After a timezone configuration error in the warehouse management system, 680 orders have DispatchDate recorded in UTC while the other dates are in local time (UTC+1 in summer). This makes DispatchDate appear one hour earlier than ConfirmedDate for orders confirmed just after midnight, creating a sequence violation. The temporal consistency audit detects all violations, quantifies the timezone offset as the root cause, and generates the corrected dates.

## The Question
> Temporal sequence validation checks that a set of related date/datetime fields follows the expected chronological order. SQL detects violations using comparison predicates (Date1 <= Date2 for non-strict, Date1 < Date2 for strict ordering) and CASE expressions to identify which specific pair in the sequence is out of order. DATEDIFF measures the gap between consecutive dates to detect implausible durations (delivery in 0 minutes, return 3 years after order). The violation report includes the specific sequence position that broke, the magnitude of the violation, and a suggested fix where the root cause is identifiable (timezone offset, data entry transposition).
> **"Validate temporal sequence consistency across the Orders table: verify that OrderDate precedes DeliveryDate, detect orders where DeliveryDate is before OrderDate (impossible sequence), identify orders where the gap between OrderDate and DeliveryDate is implausibly short (same day) or implausibly long (over 365 days), and produce a timeline consistency report."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Employees** — `schemas/04_Employees.csv`

## Solution Query

```sql
-- Step 1: Basic temporal sequence check — OrderDate must precede DeliveryDate
SELECT
    OrderID,
    CustomerID,
    CAST(OrderDate AS DATE) AS OrderDate,
    CAST(DeliveryDate AS DATE) AS DeliveryDate,
    DATEDIFF(DAY, OrderDate, DeliveryDate) AS LeadTimeDays,
    Status,
    CASE
        WHEN OrderDate IS NULL
             THEN 'NULL ORDER DATE: Cannot validate sequence'
        WHEN DeliveryDate IS NULL
             THEN CASE WHEN Status IN ('Delivered','Returned')
                       THEN 'MISSING DELIVERY DATE: Status is "' + Status
                            + '" but DeliveryDate is NULL — data capture failure'
                       ELSE 'NO DELIVERY DATE: Order not yet delivered (Status: '
                            + ISNULL(Status,'NULL') + ')'
                  END
        WHEN DeliveryDate < OrderDate
             THEN 'SEQUENCE VIOLATION: DeliveryDate '
                  + CAST(CAST(DeliveryDate AS DATE) AS VARCHAR)
                  + ' is BEFORE OrderDate '
                  + CAST(CAST(OrderDate AS DATE) AS VARCHAR)
                  + ' by ' + CAST(ABS(DATEDIFF(DAY, DeliveryDate, OrderDate)) AS VARCHAR)
                  + ' days — impossible sequence'
        WHEN DeliveryDate = OrderDate
             THEN 'SAME DAY DELIVERY: OrderDate = DeliveryDate ('
                  + CAST(CAST(OrderDate AS DATE) AS VARCHAR)
                  + ') — verify this is physically possible for the product'
        WHEN DATEDIFF(DAY, OrderDate, DeliveryDate) > 365
             THEN 'VERY LONG LEAD TIME: ' + CAST(DATEDIFF(DAY, OrderDate, DeliveryDate) AS VARCHAR)
                  + ' days — check for year entry error (2023 vs 2024?)'
        ELSE 'SEQUENCE VALID: ' + CAST(DATEDIFF(DAY, OrderDate, DeliveryDate) AS VARCHAR)
             + ' day lead time'
    END AS SequenceFlag
FROM Orders
ORDER BY
    CASE WHEN DeliveryDate < OrderDate THEN 0
         WHEN DeliveryDate = OrderDate THEN 1
         ELSE 2 END,
    DATEDIFF(DAY, OrderDate, DeliveryDate) DESC;

-- Step 2: Employee tenure sequence — HireDate must precede TerminationDate
SELECT
    EmployeeID,
    FullName,
    CAST(HireDate AS DATE) AS HireDate,
    CAST(TerminationDate AS DATE) AS TerminationDate,
    DATEDIFF(YEAR, HireDate, ISNULL(TerminationDate, GETDATE())) AS TenureYears,
    DATEDIFF(DAY, HireDate, ISNULL(TerminationDate, GETDATE())) AS TenureDays,
    CASE
        WHEN HireDate IS NULL
             THEN 'NULL HIRE DATE: Cannot validate tenure'
        WHEN TerminationDate IS NULL
             THEN 'CURRENTLY ACTIVE: No termination date (assumed still employed)'
        WHEN TerminationDate < HireDate
             THEN 'SEQUENCE VIOLATION: TerminationDate '
                  + CAST(CAST(TerminationDate AS DATE) AS VARCHAR)
                  + ' is before HireDate '
                  + CAST(CAST(HireDate AS DATE) AS VARCHAR)
                  + ' by ' + CAST(ABS(DATEDIFF(DAY, TerminationDate, HireDate)) AS VARCHAR)
                  + ' days'
        WHEN TerminationDate = HireDate
             THEN 'ZERO TENURE: Hired and terminated on same day ('
                  + CAST(CAST(HireDate AS DATE) AS VARCHAR) + ')'
        WHEN DATEDIFF(YEAR, HireDate, TerminationDate) > 50
             THEN 'IMPLAUSIBLE TENURE: ' + CAST(DATEDIFF(YEAR, HireDate, TerminationDate) AS VARCHAR)
                  + ' years — check for date entry error'
        WHEN DATEDIFF(DAY, HireDate, TerminationDate) < 30
             THEN 'SHORT TENURE: ' + CAST(DATEDIFF(DAY, HireDate, TerminationDate) AS VARCHAR)
                  + ' days — probationary termination or data entry transposition?'
        ELSE 'SEQUENCE VALID: ' + CAST(DATEDIFF(YEAR, HireDate, TerminationDate) AS VARCHAR)
             + ' year tenure'
    END AS TenureFlag
FROM Employees
ORDER BY TenureFlag;

-- Step 3: Transaction date vs Order date — transactions should not predate their order
SELECT
    t.TransactionID,
    t.OrderID,
    CAST(t.TransactionDate AS DATE) AS TransactionDate,
    CAST(o.OrderDate AS DATE) AS OrderDate,
    DATEDIFF(DAY, o.OrderDate, t.TransactionDate) AS DaysAfterOrder,
    CASE
        WHEN o.OrderID IS NULL
             THEN 'ORPHAN TRANSACTION: No matching order'
        WHEN t.TransactionDate < o.OrderDate
             THEN 'SEQUENCE VIOLATION: Transaction '
                  + CAST(CAST(t.TransactionDate AS DATE) AS VARCHAR)
                  + ' predates Order '
                  + CAST(CAST(o.OrderDate AS DATE) AS VARCHAR)
                  + ' by ' + CAST(ABS(DATEDIFF(DAY, t.TransactionDate, o.OrderDate)) AS VARCHAR)
                  + ' days'
        WHEN DATEDIFF(DAY, o.OrderDate, t.TransactionDate) > 90
             THEN 'LATE TRANSACTION: Payment captured '
                  + CAST(DATEDIFF(DAY, o.OrderDate, t.TransactionDate) AS VARCHAR)
                  + ' days after order — verify not a duplicate or adjustment entry'
        ELSE 'SEQUENCE VALID: Transaction ' + CAST(DATEDIFF(DAY, o.OrderDate, t.TransactionDate) AS VARCHAR)
             + ' days after order'
    END AS TemporalFlag
FROM Transactions t
LEFT JOIN Orders o ON t.OrderID = o.OrderID
WHERE t.TransactionDate IS NOT NULL
ORDER BY DaysAfterOrder ASC;

-- Step 4: Lead time statistical analysis — detect implausible outliers
WITH LeadTimeStats AS (
    SELECT
        DATEDIFF(DAY, OrderDate, DeliveryDate) AS LeadTime,
        PERCENTILE_CONT(0.25) WITHIN GROUP (ORDER BY DATEDIFF(DAY, OrderDate, DeliveryDate)) OVER () AS Q1,
        PERCENTILE_CONT(0.75) WITHIN GROUP (ORDER BY DATEDIFF(DAY, OrderDate, DeliveryDate)) OVER () AS Q3
    FROM Orders
    WHERE OrderDate IS NOT NULL AND DeliveryDate IS NOT NULL
      AND DeliveryDate > OrderDate
)
SELECT
    CASE
        WHEN LeadTime < 0              THEN 'NEGATIVE (impossible)'
        WHEN LeadTime = 0              THEN 'SAME DAY'
        WHEN LeadTime <= 3             THEN '1-3 days (express)'
        WHEN LeadTime <= 7             THEN '4-7 days (standard)'
        WHEN LeadTime <= 14            THEN '8-14 days (slow)'
        WHEN LeadTime <= Q3 + 1.5*(Q3-Q1) THEN '15+ days (within IQR fence)'
        ELSE 'OUTLIER (' + CAST(LeadTime AS VARCHAR) + ' days)'
    END AS LeadTimeBand,
    COUNT(*) AS OrderCount,
    ROUND(MIN(CAST(LeadTime AS FLOAT)), 0) AS MinDays,
    ROUND(MAX(CAST(LeadTime AS FLOAT)), 0) AS MaxDays
FROM LeadTimeStats
GROUP BY
    CASE
        WHEN LeadTime < 0                      THEN 'NEGATIVE (impossible)'
        WHEN LeadTime = 0                      THEN 'SAME DAY'
        WHEN LeadTime <= 3                     THEN '1-3 days (express)'
        WHEN LeadTime <= 7                     THEN '4-7 days (standard)'
        WHEN LeadTime <= 14                    THEN '8-14 days (slow)'
        WHEN LeadTime <= Q3 + 1.5*(Q3-Q1)     THEN '15+ days (within IQR fence)'
        ELSE 'OUTLIER (' + CAST(LeadTime AS VARCHAR) + ' days)'
    END
ORDER BY MinDays;

-- Step 5: Temporal consistency scorecard
SELECT
    CheckName,
    TotalRows,
    PassCount,
    FailCount,
    NullRelated,
    ROUND(100.0 * PassCount / NULLIF(TotalRows - NullRelated, 0), 1) AS PassPct
FROM (
    SELECT
        'Orders: DeliveryDate > OrderDate' AS CheckName,
        COUNT(*) AS TotalRows,
        SUM(CASE WHEN DeliveryDate > OrderDate THEN 1 ELSE 0 END) AS PassCount,
        SUM(CASE WHEN DeliveryDate IS NOT NULL
                 AND OrderDate IS NOT NULL
                 AND DeliveryDate <= OrderDate THEN 1 ELSE 0 END) AS FailCount,
        SUM(CASE WHEN DeliveryDate IS NULL OR OrderDate IS NULL THEN 1 ELSE 0 END) AS NullRelated
    FROM Orders
    UNION ALL
    SELECT
        'Employees: TerminationDate > HireDate',
        COUNT(*),
        SUM(CASE WHEN TerminationDate IS NULL OR TerminationDate > HireDate THEN 1 ELSE 0 END),
        SUM(CASE WHEN TerminationDate IS NOT NULL AND TerminationDate <= HireDate THEN 1 ELSE 0 END),
        SUM(CASE WHEN HireDate IS NULL THEN 1 ELSE 0 END)
    FROM Employees
    UNION ALL
    SELECT
        'Transactions: TransactionDate >= OrderDate',
        COUNT(*),
        SUM(CASE WHEN o.OrderDate IS NULL OR t.TransactionDate >= o.OrderDate THEN 1 ELSE 0 END),
        SUM(CASE WHEN o.OrderDate IS NOT NULL
                 AND t.TransactionDate < o.OrderDate THEN 1 ELSE 0 END),
        SUM(CASE WHEN t.TransactionDate IS NULL THEN 1 ELSE 0 END)
    FROM Transactions t
    LEFT JOIN Orders o ON t.OrderID = o.OrderID
) TemporalChecks;
```

## Explanation

**Strict vs non-strict ordering**
`DeliveryDate > OrderDate` (strict: delivery must be after order, same-day delivery is a violation) vs `DeliveryDate >= OrderDate` (non-strict: same-day delivery is acceptable). The choice depends on the business model — a digital goods retailer may legitimately deliver in seconds of the order. Always confirm the correct ordering constraint with the business before writing the validation.

**NULL handling in sequence checks**
`WHERE DeliveryDate <= OrderDate` does not catch rows where DeliveryDate IS NULL. NULL <= any value evaluates to UNKNOWN in SQL, which fails the WHERE clause. The sequence validation must handle NULLs explicitly: a NULL DeliveryDate for a "Delivered" status is a data capture failure (not a sequence violation), while a NULL DeliveryDate for a "Pending" order is expected.

**Timezone offset as a systematic sequence violation**
When dates from two sources with different timezones are compared, the offset can create sequence violations for records near timezone boundaries. A UTC date of "2024-06-15 23:30:00" appears as "2024-06-16 00:30:00" BST — a different day. Step 1's DATEDIFF(DAY,...) hides sub-day violations. For datetime-precision sequence checks, use DATEDIFF(SECOND,...) and flag violations of more than -3600 seconds (one-hour timezone offset) separately.

**Day transposition as a common entry error**
The sequence violation "DeliveryDate = 2024-01-05, OrderDate = 2024-05-01" (delivery before order by 116 days) is a classic day/month transposition: "05/01" was entered as delivery date when "01/05" was intended. Step 1's `DATEDIFF` magnitude helps diagnose the root cause: a ~1 month violation suggests a month/day transposition; a ~365 day violation suggests a year error.

## Severity
**Medium to High** — Temporal sequence violations produce incorrect lead time metrics, SLA breach calculations, and cohort analysis. A delivery recorded before the order date corrupts the lead time average to a negative value. More critically, the violation indicates a systemic data capture problem (timezone misconfiguration, system clock error) that will continue producing bad data until the root cause is resolved.
