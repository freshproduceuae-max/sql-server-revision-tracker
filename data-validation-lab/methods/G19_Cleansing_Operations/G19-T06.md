# G19-T06 — Cleansing Operations | Date Format Normalisation and Parsing

## ID
G19-T06

## Group
19 — Cleansing Operations

## Type
Date Format Normalisation and Parsing — Detecting and Correcting Inconsistent Date Formats Stored as Strings

## Live Scenario
A retailer imports order data from three legacy systems: a UK system that stores dates as "DD/MM/YYYY", a US system that uses "MM/DD/YYYY", and an ERP that exports ISO 8601 "YYYY-MM-DD". All three are loaded into the same NVARCHAR column in a staging table. When the ETL job calls `CONVERT(DATE, OrderDate)`, it silently swaps day and month for UK dates — "15/01/2024" becomes January 15th but "01/15/2024" throws a conversion error and is rejected. The date normalisation script detects all three formats, parses them correctly using format-specific CONVERT style codes, and flags any values that cannot be parsed into a valid date.

## The Question
> Date format normalisation parses date strings stored in inconsistent formats into a single canonical DATE or DATETIME type. SQL Server's CONVERT(DATE, value, style) accepts style codes (103 = DD/MM/YYYY, 101 = MM/DD/YYYY, 120 = YYYY-MM-DD HH:MM:SS, 23 = YYYY-MM-DD) to handle specific formats. TRY_CONVERT returns NULL instead of throwing an error on unparseable values. Format detection uses PATINDEX with format-specific patterns. After normalisation, a date range validation confirms the parsed dates fall within the expected business range.
> **"Detect and normalise date formats in the Orders table: identify the format of each date string in OrderDate and DeliveryDate, convert them to a canonical DATE using the appropriate style code, flag values that cannot be parsed, and produce a date format distribution report showing how many records use each format."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`

## Solution Query

```sql
-- Step 1: Detect date format patterns in OrderDate (treated as string for format analysis)
-- Orders.OrderDate is stored as DATE but we simulate format detection for string fields
SELECT
    OrderID,
    CAST(OrderDate AS VARCHAR(20)) AS RawOrderDate,
    CAST(DeliveryDate AS VARCHAR(20)) AS RawDeliveryDate,
    -- Classify the format based on the string representation
    CASE
        WHEN CAST(OrderDate AS VARCHAR(20)) LIKE '[0-9][0-9]/[0-9][0-9]/[0-9][0-9][0-9][0-9]'
             AND CAST(LEFT(CAST(OrderDate AS VARCHAR(20)), 2) AS INT) <= 12
             THEN 'MM/DD/YYYY (US format — ambiguous if day ≤ 12)'
        WHEN CAST(OrderDate AS VARCHAR(20)) LIKE '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]'
             THEN 'YYYY-MM-DD (ISO 8601 — unambiguous)'
        WHEN CAST(OrderDate AS VARCHAR(20)) LIKE '[0-9][0-9]/[0-9][0-9]/[0-9][0-9][0-9][0-9]'
             THEN 'DD/MM/YYYY or MM/DD/YYYY — ambiguous, source system check needed'
        ELSE 'UNRECOGNISED FORMAT: "' + CAST(OrderDate AS VARCHAR(20)) + '"'
    END AS FormatClassification
FROM Orders
WHERE OrderDate IS NOT NULL;

-- Step 2: Simulate mixed-format scenario using string parsing
-- Demonstrates how TRY_CONVERT handles each format style code
WITH SampleDates AS (
    -- Simulated staging data with mixed formats
    SELECT 'ORD-SIM-01' AS OrderRef, '15/01/2024' AS RawDate, 'UK' AS SourceSystem UNION ALL
    SELECT 'ORD-SIM-02',             '01/15/2024',             'US'                 UNION ALL
    SELECT 'ORD-SIM-03',             '2024-01-15',             'ERP'                UNION ALL
    SELECT 'ORD-SIM-04',             '2024-01-15 09:30:00',    'ERP-datetime'       UNION ALL
    SELECT 'ORD-SIM-05',             '15-Jan-2024',            'Legacy'             UNION ALL
    SELECT 'ORD-SIM-06',             '20240115',               'Compact'            UNION ALL
    SELECT 'ORD-SIM-07',             '32/01/2024',             'Corrupt'            UNION ALL
    SELECT 'ORD-SIM-08',             NULL,                     'Missing'
)
SELECT
    OrderRef,
    SourceSystem,
    RawDate,
    -- Try each style code; first non-NULL result wins
    COALESCE(
        TRY_CONVERT(DATE, RawDate, 103),   -- DD/MM/YYYY
        TRY_CONVERT(DATE, RawDate, 101),   -- MM/DD/YYYY
        TRY_CONVERT(DATE, RawDate, 23),    -- YYYY-MM-DD
        TRY_CONVERT(DATE, RawDate, 120),   -- YYYY-MM-DD HH:MM:SS (datetime)
        TRY_CONVERT(DATE, RawDate, 106),   -- DD Mon YYYY (15 Jan 2024)
        TRY_CONVERT(DATE, RawDate, 112)    -- YYYYMMDD (compact)
    ) AS ParsedDate,
    CASE
        WHEN RawDate IS NULL
             THEN 'NULL'
        WHEN TRY_CONVERT(DATE, RawDate, 103) IS NOT NULL
             THEN 'PARSED AS DD/MM/YYYY (style 103)'
        WHEN TRY_CONVERT(DATE, RawDate, 101) IS NOT NULL
             THEN 'PARSED AS MM/DD/YYYY (style 101)'
        WHEN TRY_CONVERT(DATE, RawDate, 23) IS NOT NULL
             THEN 'PARSED AS YYYY-MM-DD (style 23)'
        WHEN TRY_CONVERT(DATE, RawDate, 120) IS NOT NULL
             THEN 'PARSED AS YYYY-MM-DD HH:MM:SS (style 120)'
        WHEN TRY_CONVERT(DATE, RawDate, 106) IS NOT NULL
             THEN 'PARSED AS DD Mon YYYY (style 106)'
        WHEN TRY_CONVERT(DATE, RawDate, 112) IS NOT NULL
             THEN 'PARSED AS YYYYMMDD (style 112)'
        ELSE 'UNPARSEABLE: Cannot convert "' + ISNULL(RawDate,'NULL') + '" to a valid date'
    END AS ParseResult
FROM SampleDates;

-- Step 3: Validate parsed dates fall within expected business range
WITH DateBounds AS (
    SELECT
        CAST('2020-01-01' AS DATE) AS EarliestExpected,
        CAST('2026-12-31' AS DATE) AS LatestExpected
)
SELECT
    o.OrderID,
    CAST(o.OrderDate AS DATE) AS OrderDate,
    CAST(o.DeliveryDate AS DATE) AS DeliveryDate,
    db.EarliestExpected,
    db.LatestExpected,
    CASE
        WHEN o.OrderDate < db.EarliestExpected
             THEN 'ORDER DATE TOO EARLY: ' + CAST(CAST(o.OrderDate AS DATE) AS VARCHAR)
                  + ' is before system launch date ' + CAST(db.EarliestExpected AS VARCHAR)
        WHEN o.OrderDate > db.LatestExpected
             THEN 'ORDER DATE IN FUTURE: ' + CAST(CAST(o.OrderDate AS DATE) AS VARCHAR)
                  + ' exceeds expected range — likely entry error'
        WHEN o.DeliveryDate IS NOT NULL AND o.DeliveryDate < o.OrderDate
             THEN 'DELIVERY BEFORE ORDER: Delivery '
                  + CAST(CAST(o.DeliveryDate AS DATE) AS VARCHAR)
                  + ' precedes order ' + CAST(CAST(o.OrderDate AS DATE) AS VARCHAR)
        WHEN o.DeliveryDate IS NOT NULL
             AND DATEDIFF(DAY, o.OrderDate, o.DeliveryDate) > 365
             THEN 'DELIVERY VERY LATE: ' + CAST(DATEDIFF(DAY, o.OrderDate, o.DeliveryDate) AS VARCHAR)
                  + ' days between order and delivery — likely year format error'
        ELSE 'DATE RANGE VALID'
    END AS DateRangeFlag
FROM Orders o
CROSS JOIN DateBounds db
WHERE o.OrderDate IS NOT NULL;

-- Step 4: Date format distribution report for the full Orders table
SELECT
    'OrderDate' AS ColumnName,
    COUNT(*) AS TotalRows,
    SUM(CASE WHEN OrderDate IS NULL THEN 1 ELSE 0 END) AS NullCount,
    SUM(CASE WHEN OrderDate IS NOT NULL
             AND YEAR(OrderDate) BETWEEN 2020 AND 2026 THEN 1 ELSE 0 END) AS ValidRange,
    SUM(CASE WHEN OrderDate IS NOT NULL
             AND YEAR(OrderDate) NOT BETWEEN 2020 AND 2026 THEN 1 ELSE 0 END) AS OutOfRange,
    MIN(CAST(OrderDate AS DATE)) AS EarliestDate,
    MAX(CAST(OrderDate AS DATE)) AS LatestDate
FROM Orders
UNION ALL
SELECT
    'DeliveryDate',
    COUNT(*),
    SUM(CASE WHEN DeliveryDate IS NULL THEN 1 ELSE 0 END),
    SUM(CASE WHEN DeliveryDate IS NOT NULL
             AND YEAR(DeliveryDate) BETWEEN 2020 AND 2026 THEN 1 ELSE 0 END),
    SUM(CASE WHEN DeliveryDate IS NOT NULL
             AND YEAR(DeliveryDate) NOT BETWEEN 2020 AND 2026 THEN 1 ELSE 0 END),
    MIN(CAST(DeliveryDate AS DATE)),
    MAX(CAST(DeliveryDate AS DATE))
FROM Orders;

-- Step 5: Century pivot problem — 2-digit year ambiguity check
-- SQL Server interprets 2-digit years using the 'two digit year cutoff' setting (default: 2049)
-- '50' → 1950, '49' → 2049
WITH TwoDigitYearRisk AS (
    SELECT
        OrderID,
        OrderDate,
        YEAR(OrderDate) AS OrderYear,
        CASE
            WHEN YEAR(OrderDate) < 1990
                 THEN 'CENTURY ERROR: Year ' + CAST(YEAR(OrderDate) AS VARCHAR)
                      + ' likely a 2-digit year mis-parsed as 1900s'
            WHEN YEAR(OrderDate) > YEAR(GETDATE()) + 1
                 THEN 'FUTURE DATE: Year ' + CAST(YEAR(OrderDate) AS VARCHAR)
                      + ' is in the future'
            ELSE 'Year OK: ' + CAST(YEAR(OrderDate) AS VARCHAR)
        END AS YearValidation
    FROM Orders
    WHERE OrderDate IS NOT NULL
)
SELECT
    YearValidation,
    COUNT(*) AS RecordCount
FROM TwoDigitYearRisk
GROUP BY YearValidation
ORDER BY RecordCount DESC;
```

## Explanation

**TRY_CONVERT vs CONVERT for safe parsing**
`CONVERT(DATE, value, style)` throws an error and aborts the query if any single value cannot be parsed. `TRY_CONVERT(DATE, value, style)` returns NULL for unparseable values and continues — essential when the input contains mixed formats or corrupt data. Always use TRY_CONVERT in data validation and cleansing queries; use CONVERT only when the format is guaranteed by the source system.

**The ambiguity of MM/DD vs DD/MM**
For dates where both day and month are ≤ 12 (e.g., "04/06/2024"), DD/MM and MM/DD formats produce different dates (4 June vs 6 April) and neither TRY_CONVERT call will fail. The only way to resolve ambiguity is to know the source system's locale. A common heuristic: if any date in the file has a day > 12, the format must be MM/DD; if any has a month > 12, the format must be DD/MM. Apply the detected format consistently to the entire file, not row by row.

**SQL Server CONVERT style codes**
Key style codes: 23 = YYYY-MM-DD (ISO 8601, recommended), 103 = DD/MM/YYYY (British/French), 101 = MM/DD/YYYY (US), 112 = YYYYMMDD (compact), 106 = DD Mon YYYY (15 Jan 2024), 120 = YYYY-MM-DD HH:MM:SS (ODBC canonical). The full list is in SQL Server Books Online under `CAST and CONVERT`.

**Two-digit year pivot**
SQL Server's `two digit year cutoff` server option (default 2049) controls how 2-digit years are interpreted: years 00–49 are treated as 2000–2049; years 50–99 as 1950–1999. A date "01/01/50" is parsed as 1950-01-01, not 2050-01-01. Step 5 detects any dates before 1990 as potential century pivot errors.

## Severity
**High** — Date format errors cause silent data corruption: a UK date "15/01/2024" (15 January) parsed as US "01/15/2024" (January 15th) gives the same result, but "15/06/2024" (15 June) parsed as US format fails entirely. The silently converted dates produce incorrect lead time calculations, SLA measurements, and trend reports with no visible error in the output.
