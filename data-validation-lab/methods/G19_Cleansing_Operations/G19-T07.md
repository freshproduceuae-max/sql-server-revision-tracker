# G19-T07 — Cleansing Operations | Phone Number Standardisation

## ID
G19-T07

## Group
19 — Cleansing Operations

## Type
Phone Number Standardisation — Normalising Inconsistent Phone Number Formats to a Canonical Representation

## Live Scenario
A UK telecoms company's customer database contains phone numbers entered over 15 years from multiple channels: web forms, call centre agents, and CSV imports. The Phone field contains "07700 900123", "+44 7700 900123", "07700900123", "0044 7700 900123", "(07700) 900-123", and "7700900123" — all representing the same mobile number. A marketing campaign that deduplicates by phone number treats all six as unique customers, resulting in the same person receiving six copies of a promotion. The phone normalisation script strips all non-numeric characters, applies UK country code logic, and produces a canonical E.164 format (+447700900123) that collapses all six representations to one.

## The Question
> Phone number standardisation removes formatting characters (spaces, dashes, parentheses, dots), normalises country code prefixes (0044 → +44, leading 0 → +44 for UK numbers), and validates the result against expected length and prefix rules. SQL implements this with nested REPLACE() calls to strip characters, CASE logic for prefix normalisation, and LIKE/LEN checks for format validation. The canonical output uses E.164 format (+[country code][number]) which is unambiguous, internationally consistent, and suitable for deduplication keys.
> **"Standardise phone numbers in the Customers table: strip all formatting characters, normalise UK country code prefixes to +44 E.164 format, validate the resulting number against UK mobile and landline length rules, and produce a phone number quality scorecard."**

## Table Reference
**Customers** — `schemas/01_Customers.csv`

## Solution Query

```sql
-- Step 1: Inspect raw phone number formats
SELECT
    CustomerID,
    Phone,
    LEN(Phone) AS RawLength,
    LEN(REPLACE(REPLACE(REPLACE(REPLACE(REPLACE(REPLACE(REPLACE(
        ISNULL(Phone,''),
        ' ',''), '-',''), '(',''), ')',''), '+',''), '.',''), '/','')) AS NumericLength,
    CASE
        WHEN Phone IS NULL
             THEN 'NULL'
        WHEN Phone LIKE '+44%'
             THEN 'E.164 FORMAT: already has +44 prefix'
        WHEN Phone LIKE '0044%'
             THEN 'INTERNATIONAL: 0044 prefix — needs +44 conversion'
        WHEN Phone LIKE '07%'
             THEN 'UK MOBILE: starts with 07 — needs +44 prefix'
        WHEN Phone LIKE '01%' OR Phone LIKE '02%' OR Phone LIKE '03%'
             THEN 'UK LANDLINE: starts with 01/02/03 — needs +44 prefix'
        WHEN Phone LIKE '08%' OR Phone LIKE '09%'
             THEN 'UK SPECIAL: 08xx/09xx service number — needs +44 prefix'
        ELSE 'UNRECOGNISED FORMAT: "' + Phone + '"'
    END AS PhoneFormatFlag
FROM Customers
WHERE Phone IS NOT NULL;

-- Step 2: Strip formatting and normalise to E.164
WITH StrippedPhone AS (
    SELECT
        CustomerID,
        Phone AS OriginalPhone,
        -- Step 1: Remove all non-numeric and non-plus characters
        REPLACE(REPLACE(REPLACE(REPLACE(REPLACE(REPLACE(REPLACE(
            ISNULL(Phone,''),
            ' ',''), '-',''), '(',''), ')',''), '.',''), '/',''), CHAR(160),'')
        AS PartiallyStripped
    FROM Customers
    WHERE Phone IS NOT NULL
),
PrefixNormalised AS (
    SELECT
        CustomerID,
        OriginalPhone,
        PartiallyStripped,
        -- Convert various UK prefixes to +44 E.164
        CASE
            WHEN PartiallyStripped LIKE '+44%'
                 THEN PartiallyStripped                             -- already E.164
            WHEN PartiallyStripped LIKE '0044%'
                 THEN '+44' + SUBSTRING(PartiallyStripped, 5, 20)  -- 0044 → +44
            WHEN PartiallyStripped LIKE '44%' AND LEN(PartiallyStripped) = 12
                 THEN '+' + PartiallyStripped                       -- 44 without + → +44
            WHEN PartiallyStripped LIKE '0%' AND LEN(PartiallyStripped) = 11
                 THEN '+44' + SUBSTRING(PartiallyStripped, 2, 20)  -- 07xxx → +447xxx
            ELSE PartiallyStripped                                  -- leave for validation
        END AS NormalisedE164
    FROM StrippedPhone
)
SELECT
    CustomerID,
    OriginalPhone,
    NormalisedE164,
    LEN(NormalisedE164) AS NormalisedLength,
    CASE
        WHEN NormalisedE164 LIKE '+447[0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9]'
             THEN 'VALID UK MOBILE: +44 7xx xxxxxxx'
        WHEN NormalisedE164 LIKE '+441[0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9]'
          OR NormalisedE164 LIKE '+442[0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9]'
          OR NormalisedE164 LIKE '+443[0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9]'
             THEN 'VALID UK LANDLINE: +44 1xx/2xx/3xx xxxxxxx'
        WHEN NormalisedE164 LIKE '+448[0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9]'
          OR NormalisedE164 LIKE '+449[0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9]'
             THEN 'UK SPECIAL: +44 8xx/9xx service number'
        WHEN LEN(NormalisedE164) <> 13
             THEN 'LENGTH ERROR: Expected 13 chars for +44 format, got '
                  + CAST(LEN(NormalisedE164) AS VARCHAR)
        ELSE 'FORMAT REVIEW: Does not match known UK number patterns'
    END AS ValidationFlag
FROM PrefixNormalised;

-- Step 3: Detect test/placeholder/fictional numbers
-- Ofcom reserves 07700 900000-07700 900999 for fictional use in TV/film
SELECT
    CustomerID,
    Phone,
    CASE
        WHEN REPLACE(REPLACE(REPLACE(Phone,' ',''),'-',''),'(','') LIKE '%07700900%'
             THEN 'OFCOM RESERVED: 07700 900xxx numbers are reserved for fictional use'
        WHEN Phone LIKE '%000000%'
             THEN 'PLACEHOLDER: Repeated zeros suggest test data'
        WHEN Phone LIKE '%111111%' OR Phone LIKE '%999999%'
             THEN 'PLACEHOLDER: Repeated digits suggest test data'
        WHEN Phone IN ('00000000000', '11111111111', '99999999999')
             THEN 'OBVIOUS TEST NUMBER: All same digit'
        ELSE 'No placeholder pattern detected'
    END AS PlaceholderFlag
FROM Customers
WHERE Phone IS NOT NULL;

-- Step 4: Duplicate phone number detection (after normalisation)
WITH StrippedPhone AS (
    SELECT CustomerID,
           CASE
               WHEN REPLACE(Phone,' ','') LIKE '+44%'    THEN REPLACE(Phone,' ','')
               WHEN REPLACE(Phone,' ','') LIKE '0044%'   THEN '+44' + SUBSTRING(REPLACE(Phone,' ',''),5,20)
               WHEN REPLACE(Phone,' ','') LIKE '0%'      THEN '+44' + SUBSTRING(REPLACE(Phone,' ',''),2,20)
               ELSE Phone
           END AS NormPhone
    FROM Customers WHERE Phone IS NOT NULL
)
SELECT
    NormPhone,
    COUNT(*) AS CustomerCount,
    STRING_AGG(CustomerID, ', ') WITHIN GROUP (ORDER BY CustomerID) AS CustomerIDs,
    CASE
        WHEN COUNT(*) > 1
             THEN 'DUPLICATE PHONE: ' + CAST(COUNT(*) AS VARCHAR)
                  + ' customers share this number — potential duplicate records'
        ELSE 'UNIQUE'
    END AS DuplicateFlag
FROM StrippedPhone
GROUP BY NormPhone
HAVING COUNT(*) > 1;

-- Step 5: Phone number quality scorecard
WITH PhoneStats AS (
    SELECT
        COUNT(*) AS Total,
        SUM(CASE WHEN Phone IS NULL THEN 1 ELSE 0 END) AS NullCount,
        SUM(CASE WHEN Phone IS NOT NULL
                 AND REPLACE(REPLACE(Phone,' ',''),'-','') LIKE '+447[0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9]'
                 THEN 1 ELSE 0 END) AS AlreadyE164Mobile,
        SUM(CASE WHEN Phone IS NOT NULL
                 AND LEN(REPLACE(REPLACE(REPLACE(Phone,' ',''),'-',''),'(','')) BETWEEN 10 AND 13
                 THEN 1 ELSE 0 END) AS NormalisableLength,
        SUM(CASE WHEN Phone IS NOT NULL
                 AND LEN(REPLACE(REPLACE(REPLACE(Phone,' ',''),'-',''),'(','')) < 10
                 THEN 1 ELSE 0 END) AS TooShort,
        SUM(CASE WHEN Phone IS NOT NULL
                 AND LEN(REPLACE(REPLACE(REPLACE(Phone,' ',''),'-',''),'(','')) > 15
                 THEN 1 ELSE 0 END) AS TooLong
    FROM Customers
)
SELECT
    Total,
    NullCount,
    AlreadyE164Mobile,
    NormalisableLength,
    TooShort,
    TooLong,
    ROUND(100.0 * AlreadyE164Mobile / NULLIF(Total - NullCount, 0), 1) AS E164ConformancePct,
    ROUND(100.0 * NormalisableLength / NULLIF(Total - NullCount, 0), 1) AS NormalisablePct
FROM PhoneStats;
```

## Explanation

**E.164 as the canonical format**
ITU-T E.164 format (+[country_code][subscriber_number], max 15 digits, no spaces or separators) is the international standard for phone numbers. It is unambiguous, suitable for deduplication keys, and compatible with telecoms APIs and SMS gateways. Once normalised to E.164, two numbers can be compared with a simple string equality check — no format-specific parsing required.

**Nested REPLACE for character stripping**
SQL Server has no single function to strip all non-numeric characters from a string. The nested REPLACE approach handles specific known characters (space, dash, parenthesis, dot). For a more complete solution, a scalar UDF or CLR function with a regex pattern `[^0-9+]` is more maintainable. The nested REPLACE is limited to the characters explicitly listed — a new separator character in incoming data would be missed.

**Country code ambiguity for numbers without prefix**
A 10-digit number starting with "7" could be a UK mobile without the leading zero, a US number, or a number from another country. Without context (source system locale, customer address country), the correct country code cannot be inferred. The normalisation in Step 2 only applies +44 prefix logic when the number pattern matches known UK formats (starts with 0 and has 11 digits).

**Ofcom reserved test numbers**
Ofcom (the UK telecoms regulator) reserves the range 07700 900000–07700 900999 for use in TV, film, and fictional contexts to prevent real people receiving unwanted calls. These numbers appear in test data, demo scripts, and documentation. Step 3 flags them as reserved numbers that should not appear in production customer records.

## Severity
**Medium** — Phone number format inconsistency causes deduplication failures (the same customer treated as multiple records), SMS delivery failures (the gateway rejects non-E.164 numbers), and outbound calling failures. The fix is purely transformational — the underlying number is not wrong, only its representation — making it safe to normalise in bulk.
