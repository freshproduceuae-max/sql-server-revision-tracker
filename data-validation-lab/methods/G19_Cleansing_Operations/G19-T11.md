# G19-T11 — Cleansing Operations | Pattern-Based Data Correction

## ID
G19-T11

## Group
19 — Cleansing Operations

## Type
Pattern-Based Data Correction — Using Pattern Matching to Detect and Fix Systematic Data Entry Errors

## Live Scenario
A financial services firm's onboarding form accepts National Insurance numbers in any format — users enter "AB123456C", "AB 12 34 56 C", "ab123456c", and "AB-123456-C". All represent the same NI number but in different formats. The downstream compliance system rejects any NI number that does not exactly match the format `AA######A` (two uppercase letters, six digits, one uppercase letter). A pattern-based correction script strips all non-alphanumeric characters, converts to uppercase, and validates the result against the canonical 9-character pattern — converting all valid variants to a single standard form and flagging the ones that cannot be corrected because the underlying value is malformed.

## The Question
> Pattern-based correction uses PATINDEX, LIKE, and regular expression-style character class patterns to detect values that match a known-good pattern but in the wrong format, then applies a sequence of transformations to produce the canonical form. The correction is only applied when the cleaned value still matches the expected pattern — values that remain invalid after cleaning are flagged for manual review rather than silently passed through. A before/after correction report shows the transformation applied to each record.
> **"Apply pattern-based corrections to key fields in the Customers and Employees tables: standardise National Insurance numbers to the format AA######A (no spaces, uppercase), standardise sort codes to the format ##-##-## (with hyphens), and standardise PostalCode to the standard UK format with a space before the inward code. Report which corrections were applied and which values remain invalid after correction."**

## Table Reference
**Customers** — `schemas/01_Customers.csv`
**Employees** — `schemas/04_Employees.csv`

## Solution Query

```sql
-- Step 1: National Insurance number standardisation (Employees.NationalID)
-- Target format: AA######A (2 uppercase letters, 6 digits, 1 uppercase letter) — 9 chars, no spaces
WITH NationalIDCleaned AS (
    SELECT
        EmployeeID,
        FullName,
        NationalID AS OriginalNI,
        -- Strip spaces, hyphens, and dots; convert to uppercase
        UPPER(REPLACE(REPLACE(REPLACE(REPLACE(
            ISNULL(NationalID, ''),
            ' ', ''), '-', ''), '.', ''), '/', ''))
        AS CleanedNI
    FROM Employees
    WHERE NationalID IS NOT NULL
)
SELECT
    EmployeeID,
    FullName,
    OriginalNI,
    CleanedNI,
    LEN(CleanedNI) AS CleanedLength,
    CASE
        WHEN CleanedNI LIKE '[A-Z][A-Z][0-9][0-9][0-9][0-9][0-9][0-9][A-Z]'
             AND CleanedNI NOT LIKE 'D[FIQUVS]%'    -- prefix D + invalid second letter
             AND CleanedNI NOT LIKE '[^A-Z]%'        -- valid first letter check
             THEN CASE WHEN OriginalNI = CleanedNI
                       THEN 'ALREADY CANONICAL: No change needed'
                       ELSE 'CORRECTED: "' + OriginalNI + '" → "' + CleanedNI + '"'
                  END
        WHEN LEN(CleanedNI) = 9
             THEN 'PATTERN INVALID after cleaning: "' + CleanedNI
                  + '" — does not match [A-Z][A-Z][0-9][0-9][0-9][0-9][0-9][0-9][A-Z]'
        WHEN LEN(CleanedNI) <> 9
             THEN 'LENGTH ERROR after cleaning: ' + CAST(LEN(CleanedNI) AS VARCHAR)
                  + ' chars (expected 9) for "' + CleanedNI + '"'
        ELSE 'MANUAL REVIEW REQUIRED'
    END AS CorrectionResult
FROM NationalIDCleaned;

-- Step 2: Sort code standardisation (Employees.SortCode) — target: ##-##-##
WITH SortCodeCleaned AS (
    SELECT
        EmployeeID,
        SortCode AS OriginalSortCode,
        -- Strip all non-numeric characters then reformat with hyphens
        REPLACE(REPLACE(REPLACE(REPLACE(REPLACE(
            ISNULL(SortCode,''),
            '-',''), ' ',''), '/',''), '.',''), CHAR(160),'')
        AS NumericOnly
    FROM Employees
    WHERE SortCode IS NOT NULL
)
SELECT
    EmployeeID,
    OriginalSortCode,
    NumericOnly,
    CASE
        WHEN LEN(NumericOnly) = 6 AND NumericOnly NOT LIKE '%[^0-9]%'
             THEN LEFT(NumericOnly,2) + '-' + SUBSTRING(NumericOnly,3,2) + '-' + RIGHT(NumericOnly,2)
        ELSE NULL
    END AS CanonicalSortCode,
    CASE
        WHEN SortCode LIKE '[0-9][0-9]-[0-9][0-9]-[0-9][0-9]'
             THEN 'ALREADY CANONICAL'
        WHEN LEN(NumericOnly) = 6 AND NumericOnly NOT LIKE '%[^0-9]%'
             THEN 'CORRECTED: Reformatted to ##-##-## with hyphens'
        WHEN LEN(NumericOnly) <> 6
             THEN 'LENGTH ERROR: Sort code must have exactly 6 digits, found '
                  + CAST(LEN(NumericOnly) AS VARCHAR)
        ELSE 'INVALID: Non-numeric characters remain after cleaning'
    END AS SortCodeCorrectionFlag
FROM SortCodeCleaned;

-- Step 3: UK postcode standardisation — target format: outward_code SPACE inward_code
-- UK inward code is always 3 characters (number + two letters): e.g. "1AA"
WITH PostcodeCleaned AS (
    SELECT
        CustomerID,
        PostalCode AS OriginalPostcode,
        -- Strip all spaces and convert to uppercase
        UPPER(REPLACE(ISNULL(PostalCode,''), ' ', '')) AS NoSpacePC
    FROM Customers
    WHERE PostalCode IS NOT NULL
),
PostcodeFormatted AS (
    SELECT
        CustomerID,
        OriginalPostcode,
        NoSpacePC,
        LEN(NoSpacePC) AS PCLength,
        -- Insert space before the last 3 characters (standard UK inward code)
        CASE
            WHEN LEN(NoSpacePC) BETWEEN 5 AND 7
                 THEN LEFT(NoSpacePC, LEN(NoSpacePC) - 3)
                      + ' ' + RIGHT(NoSpacePC, 3)
            ELSE NoSpacePC
        END AS FormattedPostcode
    FROM PostcodeCleaned
)
SELECT
    CustomerID,
    OriginalPostcode,
    FormattedPostcode,
    CASE
        -- Valid UK postcode patterns (covers most common formats)
        WHEN FormattedPostcode LIKE '[A-Z][0-9] [0-9][A-Z][A-Z]'
          OR FormattedPostcode LIKE '[A-Z][0-9][0-9] [0-9][A-Z][A-Z]'
          OR FormattedPostcode LIKE '[A-Z][A-Z][0-9] [0-9][A-Z][A-Z]'
          OR FormattedPostcode LIKE '[A-Z][A-Z][0-9][0-9] [0-9][A-Z][A-Z]'
          OR FormattedPostcode LIKE '[A-Z][0-9][A-Z] [0-9][A-Z][A-Z]'
          OR FormattedPostcode LIKE '[A-Z][A-Z][0-9][A-Z] [0-9][A-Z][A-Z]'
             THEN CASE WHEN OriginalPostcode = FormattedPostcode
                       THEN 'ALREADY CANONICAL'
                       ELSE 'CORRECTED: "' + OriginalPostcode
                            + '" → "' + FormattedPostcode + '"'
                  END
        ELSE 'INVALID POSTCODE: "' + FormattedPostcode
             + '" does not match any UK postcode pattern'
    END AS PostcodeCorrectionFlag
FROM PostcodeFormatted;

-- Step 4: Barcode check digit validation (Products.Barcode) — EAN-13 format
-- EAN-13: 13 digits; check digit = 10 - ((sum of odd-position digits + 3 * sum of even-position digits) mod 10)
WITH BarcodeDigits AS (
    SELECT
        ProductID,
        Barcode,
        LEN(REPLACE(ISNULL(Barcode,''), '-', '')) AS DigitCount,
        CASE WHEN Barcode NOT LIKE '%[^0-9]%' AND LEN(Barcode) = 13
             THEN
                -- EAN-13 check digit calculation
                (10 - (
                    (CAST(SUBSTRING(Barcode,1,1) AS INT) +
                     CAST(SUBSTRING(Barcode,3,1) AS INT) +
                     CAST(SUBSTRING(Barcode,5,1) AS INT) +
                     CAST(SUBSTRING(Barcode,7,1) AS INT) +
                     CAST(SUBSTRING(Barcode,9,1) AS INT) +
                     CAST(SUBSTRING(Barcode,11,1) AS INT) +
                     3 * (CAST(SUBSTRING(Barcode,2,1) AS INT) +
                          CAST(SUBSTRING(Barcode,4,1) AS INT) +
                          CAST(SUBSTRING(Barcode,6,1) AS INT) +
                          CAST(SUBSTRING(Barcode,8,1) AS INT) +
                          CAST(SUBSTRING(Barcode,10,1) AS INT) +
                          CAST(SUBSTRING(Barcode,12,1) AS INT))
                    ) % 10
                ) % 10
             ELSE NULL
        END AS ExpectedCheckDigit
    FROM Products WHERE Barcode IS NOT NULL
)
SELECT
    ProductID,
    Barcode,
    DigitCount,
    ExpectedCheckDigit,
    CASE WHEN Barcode IS NULL THEN 'NULL'
         WHEN LEN(Barcode) <> 13 THEN 'LENGTH ERROR: Expected 13 digits'
         WHEN Barcode LIKE '%[^0-9]%' THEN 'NON-NUMERIC: Barcode contains non-digit characters'
         WHEN CAST(RIGHT(Barcode,1) AS INT) = ExpectedCheckDigit THEN 'VALID EAN-13'
         ELSE 'CHECK DIGIT FAIL: Expected ' + CAST(ExpectedCheckDigit AS VARCHAR)
              + ' but got ' + RIGHT(Barcode,1)
    END AS BarcodeValidationFlag
FROM BarcodeDigits;

-- Step 5: Pattern correction summary
SELECT
    FieldName, TotalRows, AlreadyCanonical, Corrected, Invalid, NullCount,
    ROUND(100.0 * (AlreadyCanonical + Corrected) / NULLIF(TotalRows - NullCount, 0), 1) AS CorrectablePct
FROM (
    SELECT 'Employees.NationalID' AS FieldName,
           COUNT(*) AS TotalRows,
           SUM(CASE WHEN NationalID LIKE '[A-Z][A-Z][0-9][0-9][0-9][0-9][0-9][0-9][A-Z]' THEN 1 ELSE 0 END) AS AlreadyCanonical,
           SUM(CASE WHEN NationalID IS NOT NULL
                    AND NationalID NOT LIKE '[A-Z][A-Z][0-9][0-9][0-9][0-9][0-9][0-9][A-Z]'
                    AND UPPER(REPLACE(REPLACE(NationalID,' ',''),'-',''))
                        LIKE '[A-Z][A-Z][0-9][0-9][0-9][0-9][0-9][0-9][A-Z]'
                    THEN 1 ELSE 0 END) AS Corrected,
           SUM(CASE WHEN NationalID IS NOT NULL
                    AND UPPER(REPLACE(REPLACE(NationalID,' ',''),'-',''))
                        NOT LIKE '[A-Z][A-Z][0-9][0-9][0-9][0-9][0-9][0-9][A-Z]'
                    THEN 1 ELSE 0 END) AS Invalid,
           SUM(CASE WHEN NationalID IS NULL THEN 1 ELSE 0 END) AS NullCount
    FROM Employees
    UNION ALL
    SELECT 'Customers.PostalCode',
           COUNT(*),
           SUM(CASE WHEN PostalCode LIKE '[A-Z][A-Z][0-9][0-9] [0-9][A-Z][A-Z]'
                      OR PostalCode LIKE '[A-Z][0-9][0-9] [0-9][A-Z][A-Z]'
                      OR PostalCode LIKE '[A-Z][0-9] [0-9][A-Z][A-Z]'
                    THEN 1 ELSE 0 END),
           0, 0,
           SUM(CASE WHEN PostalCode IS NULL THEN 1 ELSE 0 END)
    FROM Customers
) Summary;
```

## Explanation

**Correctable vs invalid distinction**
Pattern-based correction has two outcomes: a value that matches the target pattern after cleaning (correctable) and a value that still fails validation after cleaning (invalid). Correctable values are safe to update automatically. Invalid values require manual review because the underlying data is wrong — not just formatted incorrectly. The correction script must never silently pass an invalid value through as if it were corrected.

**EAN-13 check digit validation**
EAN-13 barcodes include a check digit (the 13th digit) computed from the first 12 digits using a weighted sum algorithm. Verifying the check digit catches single-character transpositions and entry errors that the pattern match (`[0-9]{13}`) would pass. A barcode with correct length and all numeric characters is not necessarily a valid barcode — the check digit must be independently verified.

**PATINDEX character class limitations in SQL Server**
SQL Server's LIKE pattern supports character classes `[a-z]`, `[0-9]`, and ranges, but does not support quantifiers like `[0-9]{6}` (regex-style). Each character position must be spelled out individually: `[0-9][0-9][0-9][0-9][0-9][0-9]`. For complex patterns (email, URL, IPv4), a CLR scalar function with .NET regex is more maintainable than long LIKE expressions.

**Idempotency of the correction**
A well-designed pattern correction is idempotent: applying it twice produces the same result as applying it once. `UPPER(REPLACE(NI, ' ', ''))` is idempotent — running it on already-canonical data leaves it unchanged. This allows the correction to be re-run safely on data that has already been partially cleansed without risk of double-transformation.

## Severity
**Medium** — Pattern-based errors (sort codes without hyphens, NI numbers with spaces) cause validation failures in downstream systems that enforce strict format requirements. The correction is typically low-risk because the semantic content of the field is unchanged — only its representation is corrected. The main risk is incorrectly correcting a value that is actually invalid (e.g., completing a truncated sort code by assuming missing digits).
