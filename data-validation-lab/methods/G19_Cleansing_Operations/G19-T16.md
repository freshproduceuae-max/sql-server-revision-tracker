# G19-T16 — Cleansing Operations | Currency and Decimal Normalisation

## ID
G19-T16

## Group
19 — Cleansing Operations

## Type
Currency and Decimal Normalisation — Standardising Monetary Values Across Currencies, Precision Levels, and Unit Representations

## Live Scenario
A multinational retailer consolidates transaction data from four countries: the UK (GBP, 2 decimal places), Japan (JPY, 0 decimal places — yen is not subdivided), Kuwait (KWD, 3 decimal places — fils), and the US (USD, 2 decimal places). The ETL job loads all amounts into a DECIMAL(10,2) column. The Japanese transactions lose no data (yen has no fractional part), but the Kuwaiti transactions lose precision (1.225 KWD becomes 1.23, a rounding of 0.005 KWD = ~0.013 USD per transaction). Additionally, some USD amounts arrive as cents (integer: 1299 = $12.99) while others are in dollars (12.99). The normalisation script detects each precision anomaly and applies currency-specific rounding rules before storing.

## The Question
> Currency and decimal normalisation standardises monetary amounts to a target precision and unit (pounds vs pence, dollars vs cents, yen vs sen) and applies currency-specific decimal place rules (ISO 4217: GBP=2, JPY=0, KWD=3). SQL implements this with a currency-to-precision mapping CTE, ROUND() with the correct decimal places for each currency, and a unit detection heuristic (amounts divisible by 100 with no fractional part may be in the minor unit). The normalisation produces both the original and normalised amounts for review.
> **"Normalise monetary amounts in the Transactions table: apply ISO 4217 decimal place rules by currency, detect possible minor-unit errors (cents vs dollars), calculate the financial impact of rounding differences, and produce a currency normalisation scorecard showing the total value in each currency before and after normalisation."**

## Table Reference
**Transactions** — `schemas/05_Transactions.csv`
**Orders** — `schemas/02_Orders.csv`

## Solution Query

```sql
-- Step 1: Currency-to-precision mapping (ISO 4217)
WITH CurrencyPrecision AS (
    SELECT 'GBP' AS Currency, 2 AS DecimalPlaces, 'Pound Sterling'      AS CurrencyName,
           'minor unit = penny (1/100)'  AS MinorUnit UNION ALL
    SELECT 'USD', 2, 'US Dollar',          'minor unit = cent (1/100)'   UNION ALL
    SELECT 'EUR', 2, 'Euro',               'minor unit = cent (1/100)'   UNION ALL
    SELECT 'JPY', 0, 'Japanese Yen',       'no minor unit (yen)'         UNION ALL
    SELECT 'KWD', 3, 'Kuwaiti Dinar',      'minor unit = fils (1/1000)'  UNION ALL
    SELECT 'BHD', 3, 'Bahraini Dinar',     'minor unit = fils (1/1000)'  UNION ALL
    SELECT 'CHF', 2, 'Swiss Franc',        'minor unit = centime (1/100)'
)
SELECT
    t.TransactionID,
    t.Amount AS OriginalAmount,
    t.Currency,
    cp.DecimalPlaces,
    cp.CurrencyName,
    -- Apply ISO 4217 rounding
    ROUND(t.Amount, cp.DecimalPlaces) AS ISO4217Amount,
    ABS(t.Amount - ROUND(t.Amount, cp.DecimalPlaces)) AS RoundingDifference,
    CASE
        WHEN cp.Currency IS NULL
             THEN 'UNKNOWN CURRENCY: "' + ISNULL(t.Currency,'NULL')
                  + '" — add to CurrencyPrecision mapping'
        WHEN cp.DecimalPlaces = 0 AND t.Amount <> FLOOR(t.Amount)
             THEN 'PRECISION ERROR: ' + t.Currency
                  + ' has no decimal places but Amount = '
                  + CAST(t.Amount AS VARCHAR) + ' has fractional part'
        WHEN ABS(t.Amount - ROUND(t.Amount, cp.DecimalPlaces)) > 0.005
             THEN 'ROUNDING REQUIRED: ' + CAST(t.Amount AS VARCHAR)
                  + ' → ' + CAST(ROUND(t.Amount, cp.DecimalPlaces) AS VARCHAR)
                  + ' (Δ = ' + CAST(ABS(t.Amount - ROUND(t.Amount, cp.DecimalPlaces)) AS VARCHAR) + ')'
        ELSE 'PRECISION OK: Amount has correct decimal places for ' + t.Currency
    END AS PrecisionFlag
FROM Transactions t
LEFT JOIN CurrencyPrecision cp ON t.Currency = cp.Currency
WHERE t.Amount IS NOT NULL;

-- Step 2: Minor unit detection — pence vs pounds / cents vs dollars
WITH CurrencyStats AS (
    SELECT
        Currency,
        COUNT(*) AS TxnCount,
        ROUND(AVG(Amount), 2) AS AvgAmount,
        ROUND(MIN(Amount), 2) AS MinAmount,
        ROUND(MAX(Amount), 2) AS MaxAmount
    FROM Transactions
    WHERE Amount IS NOT NULL AND Currency IS NOT NULL
    GROUP BY Currency
)
SELECT
    t.TransactionID,
    t.Currency,
    ROUND(t.Amount, 2) AS Amount,
    cs.AvgAmount AS CurrencyAvg,
    -- Heuristic: if amount is > 100× the average for that currency,
    -- it may be in the minor unit (cents instead of dollars)
    CASE
        WHEN t.Amount > cs.AvgAmount * 100
             THEN 'POSSIBLE MINOR UNIT: Amount ' + CAST(ROUND(t.Amount,2) AS VARCHAR)
                  + ' is >100× the currency average (' + CAST(cs.AvgAmount AS VARCHAR) + ')'
                  + ' — may be in pence/cents rather than ' + t.Currency
        WHEN t.Amount < cs.AvgAmount / 100 AND t.Amount > 0
             THEN 'POSSIBLE MAJOR UNIT FRACTION: Amount seems too small for ' + t.Currency
        ELSE 'Amount scale plausible for ' + t.Currency
    END AS UnitScaleFlag,
    -- Proposed major-unit value if minor unit suspected
    CASE
        WHEN t.Amount > cs.AvgAmount * 100
             THEN ROUND(t.Amount / 100.0, 2)
        ELSE t.Amount
    END AS SuggestedMajorUnitAmount
FROM Transactions t
JOIN CurrencyStats cs ON t.Currency = cs.Currency
WHERE t.Amount IS NOT NULL;

-- Step 3: Cross-currency amount comparison — Orders vs Transactions
-- Check that transaction amounts match order amounts, accounting for currency
WITH OrderTransactionMatch AS (
    SELECT
        o.OrderID,
        o.TotalAmount AS OrderAmount,
        'GBP' AS OrderCurrency,  -- assume Orders are in GBP
        t.TransactionID,
        t.Amount AS TxnAmount,
        t.Currency AS TxnCurrency
    FROM Orders o
    LEFT JOIN Transactions t ON o.OrderID = t.OrderID
    WHERE o.TotalAmount IS NOT NULL
)
SELECT
    OrderID,
    OrderAmount,
    TxnAmount,
    TxnCurrency,
    ROUND(ABS(OrderAmount - TxnAmount), 2) AS AmountDelta,
    CASE
        WHEN TxnAmount IS NULL
             THEN 'NO TRANSACTION: Order has no matching transaction'
        WHEN TxnCurrency = 'GBP' AND ABS(OrderAmount - TxnAmount) <= 0.01
             THEN 'MATCHED: Same currency, amount within 1p tolerance'
        WHEN TxnCurrency = 'GBP' AND ABS(OrderAmount - TxnAmount) > 0.01
             THEN 'MISMATCH: Order £' + CAST(ROUND(OrderAmount,2) AS VARCHAR)
                  + ' vs Transaction £' + CAST(ROUND(TxnAmount,2) AS VARCHAR)
                  + ' (Δ = £' + CAST(ROUND(ABS(OrderAmount - TxnAmount),2) AS VARCHAR) + ')'
        WHEN TxnCurrency <> 'GBP'
             THEN 'CROSS-CURRENCY: Transaction in ' + TxnCurrency
                  + ' — FX conversion required for comparison'
        ELSE 'REVIEW'
    END AS ReconciliationFlag
FROM OrderTransactionMatch
ORDER BY AmountDelta DESC;

-- Step 4: Rounding impact summary by currency
WITH CurrencyPrecision AS (
    SELECT 'GBP' AS Currency, 2 AS DP UNION ALL
    SELECT 'USD', 2 UNION ALL
    SELECT 'EUR', 2 UNION ALL
    SELECT 'JPY', 0
)
SELECT
    t.Currency,
    cp.DP AS ISO4217DecimalPlaces,
    COUNT(*) AS TransactionCount,
    ROUND(SUM(t.Amount), 2) AS TotalAmountStored,
    ROUND(SUM(ROUND(t.Amount, cp.DP)), 2) AS TotalAmountISO4217,
    ROUND(SUM(t.Amount) - SUM(ROUND(t.Amount, cp.DP)), 4) AS TotalRoundingImpact,
    SUM(CASE WHEN ABS(t.Amount - ROUND(t.Amount, cp.DP)) > 0.005 THEN 1 ELSE 0 END)
        AS TransactionsNeedingRounding
FROM Transactions t
LEFT JOIN CurrencyPrecision cp ON t.Currency = cp.Currency
WHERE t.Amount IS NOT NULL AND t.Currency IS NOT NULL
GROUP BY t.Currency, cp.DP
ORDER BY TransactionsNeedingRounding DESC;

-- Step 5: Currency distribution and normalisation scorecard
SELECT
    ISNULL(Currency, 'NULL') AS Currency,
    COUNT(*) AS TransactionCount,
    ROUND(SUM(Amount), 2) AS TotalAmount,
    ROUND(MIN(Amount), 2) AS MinAmount,
    ROUND(MAX(Amount), 2) AS MaxAmount,
    ROUND(AVG(Amount), 2) AS AvgAmount,
    ROUND(100.0 * COUNT(*) / SUM(COUNT(*)) OVER (), 1) AS PctOfTransactions,
    ROUND(100.0 * SUM(Amount) / SUM(SUM(Amount)) OVER (), 1) AS PctOfTotalValue
FROM Transactions
WHERE Amount IS NOT NULL
GROUP BY Currency
ORDER BY TotalAmount DESC;
```

## Explanation

**ISO 4217 decimal place rules**
ISO 4217 specifies the number of decimal places (exponent) for each currency. Most currencies use 2 (GBP, USD, EUR), some use 0 (JPY, KRW), and a few use 3 (KWD, BHD, OMR). Storing a KWD amount in a DECIMAL(10,2) column silently drops the third decimal place — a fils precision loss that accumulates across millions of transactions. The correct column type for multi-currency applications is DECIMAL(15,4) with ISO 4217 rounding applied at the application layer.

**Minor unit heuristic limitations**
The "amount is 100× the average" heuristic for minor unit detection produces false positives for genuinely large transactions (a single corporate order of £10,000 when the average is £100 is not a pence error). The heuristic is a screening tool only — all flagged records require manual review before any correction is applied. A more reliable signal is the transaction source system's documented currency unit convention.

**Rounding in financial calculations**
`ROUND(12.225, 2)` in SQL Server uses "round half away from zero" by default, producing 12.23. Excel and some databases use "round half to even" (banker's rounding), producing 12.22. Consistency in rounding method is critical when reconciling amounts across systems — a 0.01 difference per transaction accumulates to material amounts at scale.

**FX conversion for cross-currency reconciliation**
Step 3 flags cross-currency transaction-to-order matches as requiring FX conversion before comparison. The FX rate at the time of the transaction (not today's rate) must be used. A common pattern is to store a `FXRateToBase` field with each transaction at the time of capture, allowing historical reconciliation without dependency on current market rates.

## Severity
**High for financial reporting** — Currency precision errors in aggregate financial reports are auditable findings. A DECIMAL(10,2) column silently rounding KWD amounts at the third decimal place produces a reconciliation difference between the database and the bank statement for every Kuwaiti transaction. Minor-unit errors (cents vs dollars) overstate revenue by 100× for the affected transactions, immediately corrupting any revenue report that includes them.
