# G19-T13 — Cleansing Operations | Referential Integrity Repair

## ID
G19-T13

## Group
19 — Cleansing Operations

## Type
Referential Integrity Repair — Detecting and Correcting Foreign Key Violations to Restore Consistent Relationships Between Tables

## Live Scenario
A legacy migration loads 50,000 orders from a decommissioned system. The migration script does not enforce foreign key constraints during the load (to improve performance). After the load, the data team discovers 1,200 orders reference CustomerIDs that do not exist in the Customers table, and 340 orders reference ProductIDs not in the Products table. Some of the missing customers exist in a second migration batch not yet loaded. Others are genuine orphans — customers deleted from the source before the extract. The referential integrity repair script categorises each orphan: resolvable (the customer will arrive in the next batch) vs unresolvable (customer permanently absent), and generates a repair plan for each category.

## The Question
> Referential integrity repair identifies records with foreign key values that do not match any primary key in the referenced table, then categorises and resolves each violation. SQL detects orphans with LEFT JOIN + IS NULL. Resolution options are: (1) re-key to an existing parent (when a duplicate/renamed parent exists); (2) create a placeholder parent record (when the transaction must be preserved but the parent is absent); (3) NULL the FK column (when the reference is optional); (4) delete the orphan (when the transaction is meaningless without the parent). Each option must be approved by the business before execution.
> **"Identify all referential integrity violations in the Orders table: find orders with CustomerIDs not in Customers and ProductIDs not in Products, categorise each orphan by likely cause (deleted parent, wrong ID, out-of-sequence load), and produce a repair recommendation with the count and financial impact for each resolution category."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Customers** — `schemas/01_Customers.csv`
**Products** — `schemas/03_Products.csv`
**Transactions** — `schemas/05_Transactions.csv`

## Solution Query

```sql
-- Step 1: Detect orders with orphan CustomerIDs
SELECT
    o.OrderID,
    o.CustomerID,
    o.ProductID,
    o.TotalAmount,
    o.Status,
    CAST(o.OrderDate AS DATE) AS OrderDate,
    'ORPHAN CUSTOMER: CustomerID "' + o.CustomerID
    + '" does not exist in Customers table' AS IntegrityViolation
FROM Orders o
LEFT JOIN Customers c ON o.CustomerID = c.CustomerID
WHERE c.CustomerID IS NULL
  AND o.CustomerID IS NOT NULL
ORDER BY o.OrderDate DESC;

-- Step 2: Detect orders with orphan ProductIDs
SELECT
    o.OrderID,
    o.CustomerID,
    o.ProductID,
    o.TotalAmount,
    o.Status,
    CAST(o.OrderDate AS DATE) AS OrderDate,
    'ORPHAN PRODUCT: ProductID "' + o.ProductID
    + '" does not exist in Products table' AS IntegrityViolation
FROM Orders o
LEFT JOIN Products p ON o.ProductID = p.ProductID
WHERE p.ProductID IS NULL
  AND o.ProductID IS NOT NULL
ORDER BY o.OrderDate DESC;

-- Step 3: Classify orphans by likely cause
WITH OrphanOrders AS (
    SELECT
        o.OrderID,
        o.CustomerID,
        o.ProductID,
        o.TotalAmount,
        o.OrderDate,
        o.Status,
        CASE WHEN c.CustomerID IS NULL AND o.CustomerID IS NOT NULL
             THEN 'ORPHAN_CUSTOMER' ELSE NULL END AS CustomerOrphan,
        CASE WHEN p.ProductID IS NULL AND o.ProductID IS NOT NULL
             THEN 'ORPHAN_PRODUCT' ELSE NULL END AS ProductOrphan
    FROM Orders o
    LEFT JOIN Customers c ON o.CustomerID = c.CustomerID
    LEFT JOIN Products p ON o.ProductID = p.ProductID
    WHERE (c.CustomerID IS NULL AND o.CustomerID IS NOT NULL)
       OR (p.ProductID IS NULL AND o.ProductID IS NOT NULL)
)
SELECT
    OrderID,
    CustomerID,
    ProductID,
    ROUND(TotalAmount, 2) AS TotalAmount,
    CAST(OrderDate AS DATE) AS OrderDate,
    Status,
    CustomerOrphan,
    ProductOrphan,
    -- Classify by likely cause based on ID format and order characteristics
    CASE
        -- ID format looks valid but entity is absent — likely out-of-sequence load
        WHEN CustomerOrphan = 'ORPHAN_CUSTOMER'
             AND CustomerID LIKE 'CUST-%'
             THEN 'LIKELY_PENDING_LOAD: CustomerID matches expected format — may arrive in next batch'
        -- ID does not match expected format — likely a data entry or mapping error
        WHEN CustomerOrphan = 'ORPHAN_CUSTOMER'
             AND CustomerID NOT LIKE 'CUST-%'
             THEN 'LIKELY_MAPPING_ERROR: CustomerID "' + CustomerID
                  + '" does not match CUST-### format'
        WHEN ProductOrphan = 'ORPHAN_PRODUCT'
             AND ProductID LIKE 'PROD-%'
             THEN 'LIKELY_DELETED_PRODUCT: ProductID format valid but product absent — may have been discontinued'
        WHEN ProductOrphan = 'ORPHAN_PRODUCT'
             THEN 'LIKELY_WRONG_ID: ProductID "' + ProductID + '" format unexpected'
        ELSE 'BOTH_PARENTS_MISSING: Order has neither valid customer nor valid product'
    END AS OrphanCategory
FROM OrphanOrders;

-- Step 4: Repair impact assessment
WITH AllOrphans AS (
    SELECT o.OrderID, o.TotalAmount,
           CASE WHEN c.CustomerID IS NULL AND o.CustomerID IS NOT NULL THEN 1 ELSE 0 END AS CustomerOrphan,
           CASE WHEN p.ProductID IS NULL AND o.ProductID IS NOT NULL THEN 1 ELSE 0 END AS ProductOrphan
    FROM Orders o
    LEFT JOIN Customers c ON o.CustomerID = c.CustomerID
    LEFT JOIN Products p ON o.ProductID = p.ProductID
    WHERE o.TotalAmount IS NOT NULL
)
SELECT
    'Total Orders' AS Category,
    COUNT(*) AS OrderCount,
    ROUND(SUM(TotalAmount), 2) AS TotalRevenue,
    100.0 AS PctOfTotal
FROM Orders WHERE TotalAmount IS NOT NULL
UNION ALL
SELECT
    'Orphan Customer Orders',
    SUM(CustomerOrphan),
    ROUND(SUM(CASE WHEN CustomerOrphan = 1 THEN TotalAmount ELSE 0 END), 2),
    ROUND(100.0 * SUM(CustomerOrphan) / NULLIF(COUNT(*), 0), 1)
FROM AllOrphans
UNION ALL
SELECT
    'Orphan Product Orders',
    SUM(ProductOrphan),
    ROUND(SUM(CASE WHEN ProductOrphan = 1 THEN TotalAmount ELSE 0 END), 2),
    ROUND(100.0 * SUM(ProductOrphan) / NULLIF(COUNT(*), 0), 1)
FROM AllOrphans
UNION ALL
SELECT
    'Both Parents Orphaned',
    SUM(CASE WHEN CustomerOrphan = 1 AND ProductOrphan = 1 THEN 1 ELSE 0 END),
    ROUND(SUM(CASE WHEN CustomerOrphan = 1 AND ProductOrphan = 1 THEN TotalAmount ELSE 0 END), 2),
    ROUND(100.0 * SUM(CASE WHEN CustomerOrphan = 1 AND ProductOrphan = 1 THEN 1 ELSE 0 END)
          / NULLIF(COUNT(*), 0), 1)
FROM AllOrphans;

-- Step 5: Transactions referencing non-existent Orders (orphan transactions)
SELECT
    t.TransactionID,
    t.OrderID,
    ROUND(t.Amount, 2) AS Amount,
    CAST(t.TransactionDate AS DATE) AS TransactionDate,
    t.Currency,
    CASE
        WHEN t.OrderID IS NULL
             THEN 'NULL ORDER REF: Transaction has no associated order'
        ELSE 'ORPHAN TRANSACTION: OrderID "' + t.OrderID
             + '" not found in Orders table — transaction cannot be attributed'
    END AS OrphanFlag
FROM Transactions t
LEFT JOIN Orders o ON t.OrderID = o.OrderID
WHERE (o.OrderID IS NULL AND t.OrderID IS NOT NULL)
   OR t.OrderID IS NULL
ORDER BY t.TransactionDate DESC;
```

## Explanation

**Four resolution options for orphan records**
Each orphan has a different appropriate resolution: (1) **Re-key**: the customer exists under a different ID (duplicate record, renamed entity) — update the FK to point to the correct parent; (2) **Placeholder parent**: the transaction must be preserved for financial reporting, but the parent no longer exists — insert a synthetic "Unknown Customer" or "Deleted Product" parent record; (3) **NULL the FK**: the FK is optional by business rules (an order that pre-dates the customer database) — set the FK to NULL and accept the loss of linkage; (4) **Delete**: the orphan record is meaningless without its parent and has no downstream references — delete it. The business must approve which resolution applies to each category before execution.

**Out-of-sequence load as a common cause**
In multi-batch migrations, a "load orders before customers" sequence creates temporary orphans that resolve themselves when the customer batch loads. Detecting these early prevents them being treated as permanent data quality issues. The classification heuristic in Step 3 uses ID format conformance as a signal: an OrderID that matches the expected pattern (CUST-xxx) is more likely to be a pending load than a mapping error.

**Constraint deferral vs post-load repair**
SQL Server supports `NOCHECK` on FK constraints during bulk loads (`ALTER TABLE Orders WITH NOCHECK ADD CONSTRAINT FK_Orders_Customers...`) to allow loading without FK validation, then enables checking after the load completes. This is more maintainable than disabling the constraint entirely because the constraint definition stays in place and `DBCC CHECKCONSTRAINTS` can verify existing data after re-enabling.

**Cascading repair**
Transactions that reference Orders which reference non-existent Customers form a chain of orphans. Repairing the Customer FK in Orders does not automatically repair Transactions — each level of the FK hierarchy must be independently verified. Step 5 checks the Transactions → Orders relationship separately.

## Severity
**High** — Foreign key violations undermine the relational model's fundamental guarantee: a transaction cannot be attributed to a customer or product that does not exist. Orphan orders cause revenue to appear in financial reports without an associated customer (can't send receipts, can't compute customer LTV) and without an associated product (can't compute per-product margin). The financial impact of orphan records is directly quantified in Step 4.
