# G19-T04 — Cleansing Operations | Duplicate Record Deduplication Strategy

## ID
G19-T04

## Group
19 — Cleansing Operations

## Type
Duplicate Record Deduplication Strategy — Identifying, Ranking, and Eliminating Duplicate Records While Preserving the Canonical Version

## Live Scenario
A CRM migration project consolidates customer data from three regional systems into a single database. After the load, the data team discovers 1,200 customers appear more than once — some because they registered in multiple regions, some because the same person was entered with slight name variations ("John Smith" vs "J. Smith"). The deduplication strategy uses ROW_NUMBER() with a canonical ranking rule (most recent order date = preferred record) to mark each duplicate cluster and flag all non-canonical records for suppression. Before deletion, the non-canonical records are reviewed and their orphaned orders are re-keyed to the canonical CustomerID so no transactional history is lost.

## The Question
> Deduplication identifies records that represent the same real-world entity appearing more than once in the dataset. SQL implements deduplication using ROW_NUMBER() OVER (PARTITION BY [natural key fields] ORDER BY [canonical ranking]) to rank each duplicate group, then marks all rows with RANK > 1 as duplicates. The natural key (Email, Phone, or composite) defines what "same entity" means; the canonical ranking rule (most recent activity, most complete record, lowest ID) determines which copy to keep. A duplicate audit report shows the cluster size distribution and the proportion of duplicate records.
> **"Detect and prepare a deduplication plan for the Customers table: identify duplicate Email addresses, rank each duplicate cluster by registration completeness (non-NULL field count), produce a deduplication report showing which records are canonical vs duplicates, and estimate the impact of removing duplicate rows on the Orders table."**

## Table Reference
**Customers** — `schemas/01_Customers.csv`
**Orders** — `schemas/02_Orders.csv`

## Solution Query

```sql
-- Step 1: Detect duplicate Email addresses
WITH EmailGroups AS (
    SELECT
        Email,
        COUNT(*) AS DuplicateCount,
        MIN(CustomerID) AS EarliestID,
        MAX(CustomerID) AS LatestID,
        STRING_AGG(CustomerID, ', ') WITHIN GROUP (ORDER BY CustomerID) AS AllCustomerIDs
    FROM Customers
    WHERE Email IS NOT NULL
    GROUP BY Email
    HAVING COUNT(*) > 1
)
SELECT
    eg.Email,
    eg.DuplicateCount,
    eg.EarliestID,
    eg.LatestID,
    eg.AllCustomerIDs,
    'DUPLICATE GROUP: ' + CAST(eg.DuplicateCount AS VARCHAR)
    + ' records share email "' + eg.Email + '"' AS DuplicateFlag
FROM EmailGroups eg
ORDER BY eg.DuplicateCount DESC, eg.Email;

-- Step 2: Rank each duplicate cluster — canonical record = most complete (most non-NULL fields)
WITH CompletenessScore AS (
    SELECT
        CustomerID,
        Email,
        -- Count non-NULL, non-empty fields to measure record completeness
        (CASE WHEN FirstName  IS NOT NULL AND FirstName  <> '' THEN 1 ELSE 0 END +
         CASE WHEN LastName   IS NOT NULL AND LastName   <> '' THEN 1 ELSE 0 END +
         CASE WHEN Phone      IS NOT NULL AND Phone      <> '' THEN 1 ELSE 0 END +
         CASE WHEN PostalCode IS NOT NULL AND PostalCode <> '' THEN 1 ELSE 0 END +
         CASE WHEN Country    IS NOT NULL AND Country    <> '' THEN 1 ELSE 0 END +
         CASE WHEN DateOfBirth IS NOT NULL THEN 1 ELSE 0 END +
         CASE WHEN Latitude   IS NOT NULL THEN 1 ELSE 0 END) AS FieldCompleteness
    FROM Customers
    WHERE Email IS NOT NULL
),
DuplicateEmails AS (
    SELECT Email FROM Customers
    WHERE Email IS NOT NULL
    GROUP BY Email HAVING COUNT(*) > 1
),
RankedDuplicates AS (
    SELECT
        c.CustomerID,
        c.FirstName,
        c.LastName,
        c.Email,
        c.Phone,
        c.PostalCode,
        cs.FieldCompleteness,
        ROW_NUMBER() OVER (
            PARTITION BY c.Email
            ORDER BY cs.FieldCompleteness DESC, c.CustomerID ASC
        ) AS DuplicateRank
    FROM Customers c
    JOIN CompletenessScore cs ON c.CustomerID = cs.CustomerID
    WHERE c.Email IN (SELECT Email FROM DuplicateEmails)
)
SELECT
    CustomerID,
    FirstName,
    LastName,
    Email,
    Phone,
    PostalCode,
    FieldCompleteness,
    DuplicateRank,
    CASE
        WHEN DuplicateRank = 1
             THEN 'CANONICAL: Keep this record (highest completeness)'
        ELSE 'DUPLICATE: Suppress after re-keying orders to canonical CustomerID'
    END AS DeduplicationAction
FROM RankedDuplicates
ORDER BY Email, DuplicateRank;

-- Step 3: Impact on Orders — how many orders reference duplicate (non-canonical) customers?
WITH DuplicateEmails AS (
    SELECT Email FROM Customers
    WHERE Email IS NOT NULL
    GROUP BY Email HAVING COUNT(*) > 1
),
CompletenessScore AS (
    SELECT CustomerID, Email,
        (CASE WHEN FirstName  IS NOT NULL THEN 1 ELSE 0 END +
         CASE WHEN LastName   IS NOT NULL THEN 1 ELSE 0 END +
         CASE WHEN Phone      IS NOT NULL THEN 1 ELSE 0 END +
         CASE WHEN PostalCode IS NOT NULL THEN 1 ELSE 0 END +
         CASE WHEN Country    IS NOT NULL THEN 1 ELSE 0 END) AS Score
    FROM Customers WHERE Email IS NOT NULL
),
CanonicalMap AS (
    SELECT
        c.CustomerID,
        c.Email,
        ROW_NUMBER() OVER (PARTITION BY c.Email ORDER BY cs.Score DESC, c.CustomerID ASC) AS Rnk
    FROM Customers c
    JOIN CompletenessScore cs ON c.CustomerID = cs.CustomerID
    WHERE c.Email IN (SELECT Email FROM DuplicateEmails)
)
SELECT
    o.OrderID,
    o.CustomerID AS CurrentCustomerID,
    cm.Email,
    (SELECT TOP 1 CustomerID FROM CanonicalMap
     WHERE Email = cm.Email AND Rnk = 1) AS CanonicalCustomerID,
    ROUND(o.TotalAmount, 2) AS TotalAmount,
    o.Status,
    CASE
        WHEN cm.Rnk = 1
             THEN 'ORDER ON CANONICAL: No re-keying required'
        ELSE 'ORDER ON DUPLICATE: Re-key to canonical CustomerID '
             + (SELECT TOP 1 CAST(CustomerID AS VARCHAR)
                FROM CanonicalMap WHERE Email = cm.Email AND Rnk = 1)
    END AS ReKeyAction
FROM Orders o
JOIN CanonicalMap cm ON o.CustomerID = cm.CustomerID
ORDER BY cm.Email, o.OrderID;

-- Step 4: Deduplication summary report
WITH DuplicateEmails AS (
    SELECT Email, COUNT(*) AS GrpSize
    FROM Customers WHERE Email IS NOT NULL
    GROUP BY Email HAVING COUNT(*) > 1
)
SELECT
    COUNT(DISTINCT de.Email)   AS DuplicateEmailGroups,
    SUM(de.GrpSize)            AS TotalDuplicateRecords,
    SUM(de.GrpSize) - COUNT(DISTINCT de.Email) AS RecordsToRemove,
    (SELECT COUNT(*) FROM Customers) AS TotalCustomers,
    ROUND(100.0 * (SUM(de.GrpSize) - COUNT(DISTINCT de.Email))
          / NULLIF((SELECT COUNT(*) FROM Customers), 0), 1) AS DuplicatePct,
    MAX(de.GrpSize)            AS LargestCluster,
    SUM(CASE WHEN de.GrpSize = 2 THEN 1 ELSE 0 END) AS PairsCount,
    SUM(CASE WHEN de.GrpSize >= 3 THEN 1 ELSE 0 END) AS LargerClustersCount
FROM DuplicateEmails de;

-- Step 5: Cluster size distribution
WITH DuplicateEmails AS (
    SELECT Email, COUNT(*) AS GrpSize
    FROM Customers WHERE Email IS NOT NULL
    GROUP BY Email HAVING COUNT(*) > 1
)
SELECT
    GrpSize AS ClusterSize,
    COUNT(*) AS NumberOfClusters,
    COUNT(*) * GrpSize AS TotalRecords,
    COUNT(*) * (GrpSize - 1) AS RecordsToDelete,
    REPLICATE('|', COUNT(*)) AS FrequencyBar
FROM DuplicateEmails
GROUP BY GrpSize
ORDER BY GrpSize;
```

## Explanation

**Natural key selection determines deduplication scope**
The natural key defines what "duplicate" means. For customers, Email is the most reliable natural key because it is unique per person and is validated by the application. Phone number is less reliable (shared landlines, number recycled). Composite keys (FirstName + LastName + DateOfBirth) catch near-duplicates but generate false positives for people with identical names and birthdays. The choice of natural key must be validated with the business before running any DELETE or suppression.

**ROW_NUMBER vs RANK for canonical selection**
ROW_NUMBER() assigns a unique rank even when the ordering columns have ties — exactly what is needed for deduplication, because each duplicate group needs exactly one record labelled RANK = 1. RANK() would assign the same rank to tied records, potentially retaining multiple records from the same group if the completeness score is equal. Tie-breaking with `CustomerID ASC` ensures deterministic selection of the canonical record.

**Re-keying before deletion prevents orphan transactions**
Deleting a duplicate customer record without re-keying its orders creates orphan orders that reference a non-existent CustomerID. Step 3 identifies every order that belongs to a duplicate (non-canonical) customer and generates the re-key target. The correct deduplication sequence is: (1) identify canonical records, (2) re-key all transactional references to the canonical ID, (3) validate the re-key (order count per canonical ID = sum of all duplicate group order counts), (4) delete non-canonical records.

**Completeness scoring as a canonical ranking strategy**
A completeness score — the count of non-NULL, non-empty fields — favours the record with the most information. This works well when duplicates arise from partial re-registration (new account with only email, original account with full profile). An alternative strategy is "most recently active" (latest OrderDate), which favours the record with the most up-to-date contact details.

## Severity
**High** — Duplicate customer records inflate CRM customer counts, distort cohort analysis, and cause double-targeting in marketing campaigns (the same customer receives two emails). They also inflate customer lifetime value calculations if orders are split across duplicate records. The re-keying risk is also high: a DELETE without re-keying orphans historical orders and breaks revenue attribution.
