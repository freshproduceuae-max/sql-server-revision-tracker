# G03-T06 — Referential Integrity | Cross-Database FK Violation

## ID
G03-T06

## Group
3 — Referential Integrity

## Type
Cross-Database FK Violation

## Live Scenario
A manufacturing company has two SQL Server databases on the same instance: `Operations` (stores work orders) and `HR` (stores employees). Every work order has an AssignedEmployeeID that references the HR database. SQL Server cannot enforce a foreign key constraint across databases. A round of redundancies in HR deletes 15 employee records, but the Operations work orders still reference those IDs. Nobody notices until the production scheduling system crashes trying to display the assigned employee's name.

## The Question
> SQL Server FK constraints cannot span databases. Referential integrity across databases must be validated manually.
> **"Find all Orders rows where the CustomerID exists in our main database but does NOT exist in a linked/secondary database — simulated here by treating one subset of Customers as the 'external reference table'."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Customers** — `schemas/01_Customers.csv`
**Employees** — `schemas/04_Employees.csv` (proxy for a second database's employee table)

## Solution Query

```sql
-- Simulate cross-database check using a three-part reference
-- In production: replace DatabaseName.dbo.TableName with the actual cross-DB path

-- Pattern 1: Cross-database NOT EXISTS (most common pattern)
SELECT
    o.OrderID,
    o.CustomerID,
    o.OrderDate,
    o.TotalAmount,
    'CustomerID not found in external CRM database' AS Issue
FROM Orders o
WHERE NOT EXISTS (
    -- In production: SELECT 1 FROM ExternalCRM.dbo.Customers c WHERE c.CustomerID = o.CustomerID
    -- Simulated here with a subset:
    SELECT 1 FROM Customers c
    WHERE c.CustomerID = o.CustomerID
      AND c.Country = 'UK'    -- pretend only UK customers are in the external system
);

-- Pattern 2: Using a linked server (four-part naming)
-- SELECT o.OrderID, o.CustomerID
-- FROM LocalDB.dbo.Orders o
-- WHERE NOT EXISTS (
--     SELECT 1 FROM [LinkedServerName].[RemoteDB].[dbo].[Customers] c
--     WHERE c.CustomerID = o.CustomerID
-- );

-- Pattern 3: Snapshot validation — copy remote IDs to a temp table first (faster than live cross-DB JOIN)
-- Step 1: populate temp table from the remote database
CREATE TABLE #RemoteCustomerIDs (CustomerID INT);
INSERT INTO #RemoteCustomerIDs (CustomerID)
SELECT CustomerID FROM Customers WHERE IsActive = 1;  -- simulates pulling from remote DB

-- Step 2: validate local table against the snapshot
SELECT
    o.OrderID,
    o.CustomerID,
    o.OrderDate,
    'CustomerID missing from remote system snapshot' AS Issue
FROM Orders o
WHERE o.CustomerID NOT IN (SELECT CustomerID FROM #RemoteCustomerIDs);

DROP TABLE #RemoteCustomerIDs;

-- Summary: count cross-DB violations by source table
SELECT
    'Orders.CustomerID vs RemoteDB.Customers' AS FKRelationship,
    COUNT(*) AS ViolationCount,
    GETDATE() AS CheckRunAt
FROM Orders o
WHERE NOT EXISTS (
    SELECT 1 FROM Customers c WHERE c.CustomerID = o.CustomerID AND c.IsActive = 1
);
```

## Explanation

**Why SQL Server cannot enforce cross-database FKs**
Foreign key constraints in SQL Server are limited to tables within the same database. Even on the same server instance, you cannot write `FOREIGN KEY REFERENCES OtherDatabase.dbo.TableName`. Cross-database referential integrity is entirely the responsibility of the application layer and validation scripts.

**Three options for cross-database validation**
1. **Live cross-DB query** using three-part or four-part naming (`LinkedServer.Database.Schema.Table`): simplest but slowest and blocks if the remote system is down
2. **Snapshot into a temp table**: pull the remote IDs into `#TempTable` first, then validate locally — faster and more resilient
3. **Scheduled reconciliation**: run the check nightly, write results to a DQ log table, alert on non-zero counts

**The temp table pattern is preferred for production**
Populating `#RemoteCustomerIDs` from the remote system first, then validating locally, avoids repeated cross-database round-trips for every row in the local table. The cross-DB query runs once; the local validation runs at local speed.

**Document the cross-DB dependencies**
Because SQL Server cannot enforce these FKs, the relationships exist only in application code and documentation. Maintain a data dictionary that explicitly lists every cross-database reference, the validation schedule, and the alert owner.

## Severity
**High** — Cross-database FK violations are among the hardest to detect because no system enforces them automatically. They accumulate silently until a downstream process tries to JOIN across the boundary and fails or returns wrong results.
