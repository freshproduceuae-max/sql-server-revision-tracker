# G03-T09 — Referential Integrity | Missing Mandatory Relationship

## ID
G03-T09

## Group
3 — Referential Integrity

## Type
Missing Mandatory Relationship — Record Must Have a Parent, Doesn't

## Live Scenario
An invoicing system requires every Invoice to be linked to a Contract — the Contract sets the billing terms, VAT rate, and payment schedule. The schema has a `ContractID` column on the Invoices table but it was made nullable during a migration "temporarily" to allow legacy data import. Six months later, 312 invoices have NULL ContractID. The finance system cannot calculate the correct VAT for those invoices and is applying the default rate. The error is discovered during a tax audit.

## The Question
> Some relationships are business-mandatory even when the schema doesn't enforce them with a NOT NULL constraint. A nullable FK column allows records to exist without a parent, but the business rule says every record must have one.
> **"Find all Orders that have no associated Customer — either the CustomerID is NULL (the FK was left empty) or the CustomerID value doesn't match any row in the Customers table (an orphan). Every order must have a valid, non-null customer."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Customers** — `schemas/01_Customers.csv`
**Transactions** — `schemas/05_Transactions.csv`

## Solution Query

```sql
-- Case 1: CustomerID is NULL (FK column left empty)
SELECT
    o.OrderID,
    o.CustomerID,
    o.OrderDate,
    o.TotalAmount,
    o.Status,
    'CustomerID is NULL — mandatory relationship missing' AS Issue
FROM Orders o
WHERE o.CustomerID IS NULL;

-- Case 2: CustomerID is populated but points to no valid Customer (orphan)
SELECT
    o.OrderID,
    o.CustomerID,
    o.OrderDate,
    o.TotalAmount,
    o.Status,
    'CustomerID has no matching Customer row — orphan FK' AS Issue
FROM Orders o
WHERE o.CustomerID IS NOT NULL
  AND NOT EXISTS (
      SELECT 1 FROM Customers c WHERE c.CustomerID = o.CustomerID
  );

-- Case 3: Combined mandatory relationship check — both failure modes in one query
SELECT
    o.OrderID,
    o.CustomerID,
    o.OrderDate,
    o.TotalAmount,
    o.Status,
    CASE
        WHEN o.CustomerID IS NULL                          THEN 'NULL — relationship not set'
        WHEN NOT EXISTS (
            SELECT 1 FROM Customers c
            WHERE c.CustomerID = o.CustomerID)             THEN 'Orphan — parent row missing'
        ELSE 'OK'
    END AS RelationshipStatus
FROM Orders o
WHERE o.CustomerID IS NULL
   OR NOT EXISTS (
       SELECT 1 FROM Customers c WHERE c.CustomerID = o.CustomerID
   )
ORDER BY RelationshipStatus, o.OrderID;

-- Case 4: Mandatory relationship completeness rate
SELECT
    COUNT(*)                                                        AS TotalOrders,
    SUM(CASE WHEN o.CustomerID IS NULL THEN 1 ELSE 0 END)          AS NullFK,
    SUM(CASE WHEN o.CustomerID IS NOT NULL
              AND NOT EXISTS (
                  SELECT 1 FROM Customers c WHERE c.CustomerID = o.CustomerID
              ) THEN 1 ELSE 0 END)                                  AS OrphanFK,
    SUM(CASE WHEN o.CustomerID IS NOT NULL
              AND EXISTS (
                  SELECT 1 FROM Customers c WHERE c.CustomerID = o.CustomerID
              ) THEN 1 ELSE 0 END)                                  AS ValidFK,
    CAST(
        100.0 * SUM(CASE WHEN o.CustomerID IS NOT NULL
                          AND EXISTS (
                              SELECT 1 FROM Customers c WHERE c.CustomerID = o.CustomerID
                          ) THEN 1 ELSE 0 END)
        / NULLIF(COUNT(*), 0)
    AS DECIMAL(5,2))                                                AS ValidFKPct
FROM Orders o;

-- Case 5: Check all mandatory FK columns across the key tables
SELECT 'Orders missing CustomerID'   AS Check, COUNT(*) AS FailCount FROM Orders WHERE CustomerID IS NULL
UNION ALL
SELECT 'Transactions missing OrderID', COUNT(*) FROM Transactions WHERE OrderID IS NULL
UNION ALL
SELECT 'Orders with orphan CustomerID', COUNT(*)
FROM Orders o WHERE CustomerID IS NOT NULL
  AND NOT EXISTS (SELECT 1 FROM Customers c WHERE c.CustomerID = o.CustomerID)
UNION ALL
SELECT 'Transactions with orphan OrderID', COUNT(*)
FROM Transactions t WHERE OrderID IS NOT NULL
  AND NOT EXISTS (SELECT 1 FROM Orders o WHERE o.OrderID = t.OrderID);
```

## Explanation

**Two distinct failure modes for a mandatory relationship**
A mandatory FK can fail in two ways: the FK column is NULL (the relationship was never set), or the FK column has a value that doesn't match any parent row (an orphan). Both are violations of the mandatory relationship rule. Case 3 catches both in a single pass using a CASE expression.

**Why nullable FK columns are a schema smell**
If the business rule is "every Order must have a Customer," the FK column should be NOT NULL. A nullable FK column advertises the relationship as optional at the schema level while the business rule says mandatory — the schema and the business rule are in conflict. This mismatch almost always accumulates violations over time because the database does not enforce what the business requires.

**Completeness rate as a quality metric**
Case 4 calculates the percentage of orders with a valid, non-null FK. A mandatory relationship should show 100%. Anything below that is a data quality score that can be tracked over time. If the rate is dropping, it means new violations are being introduced and the root cause (missing application validation, nullable column) needs to be addressed.

**The multi-table summary as a data quality dashboard entry**
Case 5 is structured to run as a scheduled check. Each row is one mandatory relationship across the dataset; the FailCount should be 0 for all rows in a healthy system. Add GETDATE() and write results to a DQ log table to build a historical trend.

**Difference from G03-T02 (Dangling Reference)**
G03-T02 covers the case where a parent was deleted *after* the relationship was created — the child had a valid parent that was subsequently removed. G03-T09 covers the case where the relationship was *never set* or was never valid to begin with. The SQL patterns overlap (both use NOT EXISTS) but the root cause and remediation are different.

## Severity
**High** — A missing mandatory relationship means downstream processes that depend on joining to the parent table will either drop the record entirely (INNER JOIN) or return NULL values for parent attributes (LEFT JOIN), both of which produce incorrect results silently. In regulated contexts (finance, healthcare, legal), a record with no mandatory parent may fail audit requirements independently of any functional impact.
