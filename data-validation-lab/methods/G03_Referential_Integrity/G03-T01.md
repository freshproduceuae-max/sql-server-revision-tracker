# G03-T01 — Referential Integrity | Orphan Record

## ID
G03-T01

## Group
3 — Referential Integrity

## Type
Orphan Record — FK Points to Non-Existent Parent

## Live Scenario
A retail company migrates orders from a legacy system. CustomerID and ProductID constraints were disabled for the bulk load. After the load, 23 orders reference CustomerID 99 — a customer that was deleted from the Customers table six months ago. These orphan orders cannot be invoiced, cannot be tracked to a customer, and cause every report that joins Orders to Customers to silently drop those rows.

## The Question
> Foreign key constraints may be disabled, bypassed, or simply not enforced. Orphan records — rows whose FK value points to a parent that doesn't exist — break every JOIN.
> **"Find all orders that reference a CustomerID or ProductID that does not exist in the parent table. Report which FK is broken and how many orphans exist per broken key value."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Customers** — `schemas/01_Customers.csv`
**Products** — `schemas/03_Products.csv`

## Solution Query

```sql
-- Method A: LEFT JOIN anti-join — gold standard for FK orphan detection
SELECT
    o.OrderID,
    o.CustomerID,
    o.ProductID,
    o.OrderDate,
    o.TotalAmount,
    CASE
        WHEN c.CustomerID IS NULL AND p.ProductID IS NULL THEN 'Both FK missing'
        WHEN c.CustomerID IS NULL                         THEN 'CustomerID not in Customers'
        WHEN p.ProductID  IS NULL                         THEN 'ProductID not in Products'
    END AS OrphanType
FROM Orders o
LEFT JOIN Customers c ON o.CustomerID = c.CustomerID
LEFT JOIN Products  p ON o.ProductID  = p.ProductID
WHERE c.CustomerID IS NULL
   OR p.ProductID  IS NULL
ORDER BY OrphanType, o.OrderID;

-- Method B: NOT EXISTS — readable and often faster on large indexed tables
SELECT
    OrderID,
    CustomerID,
    'CustomerID orphan — parent not in Customers' AS ViolationType
FROM Orders o
WHERE NOT EXISTS (
    SELECT 1 FROM Customers c WHERE c.CustomerID = o.CustomerID
)
UNION ALL
SELECT
    OrderID,
    ProductID,
    'ProductID orphan — parent not in Products'
FROM Orders o
WHERE NOT EXISTS (
    SELECT 1 FROM Products p WHERE p.ProductID = o.ProductID
)
ORDER BY ViolationType, OrderID;

-- Method C: Summary count for a data quality dashboard
SELECT
    'Orders → Customers (CustomerID)' AS FKCheck,
    COUNT(*)                          AS OrphanCount
FROM Orders o
WHERE NOT EXISTS (SELECT 1 FROM Customers c WHERE c.CustomerID = o.CustomerID)
UNION ALL
SELECT
    'Orders → Products (ProductID)',
    COUNT(*)
FROM Orders o
WHERE NOT EXISTS (SELECT 1 FROM Products p WHERE p.ProductID = o.ProductID);
```

## Expected Output

**Method A:**
| OrderID | CustomerID | ProductID | OrphanType |
|---|---|---|---|
| 1004 | 99 | P003 | CustomerID not in Customers |

**Method C:**
| FKCheck | OrphanCount |
|---|---|
| Orders → Customers (CustomerID) | 1 |
| Orders → Products (ProductID) | 0 |

## Explanation

**The LEFT JOIN trick**
LEFT JOIN returns every row from the left table plus matched columns from the right. Where no match exists, the right-side columns are NULL. Filtering `WHERE c.CustomerID IS NULL` isolates exactly the unmatched rows — the orphans. This is one of the most important patterns in data validation.

**NOT EXISTS vs LEFT JOIN IS NULL**
Both return identical rows. NOT EXISTS short-circuits on the first match — potentially faster when the parent table is large and the FK column is indexed. LEFT JOIN materialises the full join first. Use NOT EXISTS when readability and performance both matter; use LEFT JOIN when you need to check multiple parent tables in a single query (as in Method A above).

**Method C for monitoring dashboards**
A count of zero means the FK relationship is clean. Any non-zero count triggers investigation. This summary format belongs on a data quality dashboard alongside row counts and NULL rates — a single number per FK check that turns red when something breaks.

## Severity
**Critical** — Orphan records cause INNER JOIN reports to silently drop rows, leading to understated counts and revenue figures. They are invisible in aggregations and only reveal themselves when someone notices totals don't add up.
