# G03-T04 — Referential Integrity | Circular Reference in Hierarchy

## ID
G03-T04

## Group
3 — Referential Integrity

## Type
Circular Reference in Hierarchy — A → B → C → A

## Live Scenario
A product category tree has 500 nodes. During a bulk category restructure, a drag-and-drop UI bug allows a parent category to be placed inside one of its own descendants. Category "Electronics" (ID 5) is set as the parent of "Phones" (ID 12). "Phones" is set as the parent of "Smartphones" (ID 34). "Smartphones" is then — incorrectly — set as the parent of "Electronics". The loop 5→12→34→5 is now in the database. The category navigation renders as a loading spinner forever.

## The Question
> A hierarchy has a chain of parent-child relationships that eventually loops back to an earlier node — a multi-hop circular reference.
> **"Find all circular references in the Employees reporting hierarchy — not just direct self-loops (A → A) or two-way loops (A → B → A), but chains of any length that eventually return to their starting point."**

## Table Reference
**Employees** — `schemas/04_Employees.csv`

## Solution Query

```sql
-- Detect circular references of any depth using a Recursive CTE with path tracking
WITH HierarchyWalk AS (
    -- Anchor: start from every employee
    SELECT
        EmployeeID                              AS StartNode,
        EmployeeID                              AS CurrentNode,
        ManagerID                               AS NextNode,
        CAST(EmployeeID AS VARCHAR(MAX))        AS VisitedPath,
        0                                       AS Depth,
        0                                       AS IsCircular
    FROM Employees
    WHERE ManagerID IS NOT NULL

    UNION ALL

    -- Recursive: follow the chain upward
    SELECT
        hw.StartNode,
        e.EmployeeID,
        e.ManagerID,
        hw.VisitedPath + ' > ' + CAST(e.EmployeeID AS VARCHAR(20)),
        hw.Depth + 1,
        -- Circular if we've returned to the start node
        CASE WHEN e.ManagerID = hw.StartNode THEN 1 ELSE 0 END
    FROM Employees e
    JOIN HierarchyWalk hw
        ON  e.EmployeeID = hw.NextNode
        AND hw.IsCircular = 0          -- stop once circular is detected
        AND hw.Depth < 20              -- safety: stop after 20 hops
        AND hw.VisitedPath NOT LIKE '%' + CAST(e.EmployeeID AS VARCHAR(20)) + '%'  -- stop if node revisited
)
SELECT DISTINCT
    StartNode   AS CircularMember,
    VisitedPath AS CircularChain
FROM HierarchyWalk
WHERE IsCircular = 1
ORDER BY CircularMember;

-- Simpler approach: detect nodes that cannot be reached from a root (ManagerID IS NULL)
-- Any employee not in the hierarchy walk from roots is either isolated or in a loop
WITH ReachableFromRoot AS (
    SELECT EmployeeID
    FROM Employees WHERE ManagerID IS NULL  -- roots

    UNION ALL

    SELECT e.EmployeeID
    FROM Employees e
    JOIN ReachableFromRoot r ON e.ManagerID = r.EmployeeID
)
SELECT
    e.EmployeeID,
    e.FullName,
    e.ManagerID,
    'Not reachable from any root — likely in a circular chain' AS Issue
FROM Employees e
WHERE e.EmployeeID NOT IN (SELECT EmployeeID FROM ReachableFromRoot)
OPTION (MAXRECURSION 200);
```

## Explanation

**Path tracking as a circular reference detector**
The recursive CTE builds a path string (e.g., `E005 > E008 > E012`) as it walks up the hierarchy. If the next node to visit is already in the path, the walk has found a cycle. The condition `hw.VisitedPath NOT LIKE '%' + node + '%'` stops the recursion before it loops.

**The "not reachable from root" shortcut**
Any node in a circular chain cannot be reached by walking downward from the root (a node with ManagerID IS NULL), because the chain never connects to the root. The second query uses this property: walk the tree from all roots, then flag anything not visited. It is simpler and works for any cycle depth, though it also catches genuinely disconnected nodes (employees whose entire chain has an invalid ManagerID at the top).

**Why MAXRECURSION is critical here**
Without `OPTION (MAXRECURSION n)`, SQL Server's default limit of 100 will cause a "maximum recursion exceeded" error the moment the recursive CTE enters a circular chain. MAXRECURSION is both a safety cap and the reason Checks 1–3 in G03-T03 must be run before attempting any deep recursive hierarchy walk.

**Depth < 20 as a second safety net**
Most real org charts are fewer than 10 levels deep. A depth limit of 20 stops runaway recursion even if MAXRECURSION is set high. Adjust based on the known maximum depth of the hierarchy being validated.

## Severity
**Critical** — Circular references cause infinite loops in any system that traverses the hierarchy: org chart rendering, category navigation, access control inheritance, and recursive SQL queries. They must be fixed before any hierarchy-dependent feature can work reliably.
