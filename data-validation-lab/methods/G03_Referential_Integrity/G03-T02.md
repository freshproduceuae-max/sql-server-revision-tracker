# G03-T02 — Referential Integrity | Dangling Reference

## ID
G03-T02

## Group
3 — Referential Integrity

## Type
Dangling Reference — Parent Deleted, Child Remains

## Live Scenario
A content platform allows users to be deleted for GDPR compliance. The deletion script removes the User row but forgets to cascade to Comments, Posts, and Reviews. Six months later, the platform has 4,200 comments referencing deleted users. The comment display page crashes trying to JOIN to a user that no longer exists. The analytics team's author attribution query silently drops those 4,200 comments from content metrics.

## The Question
> A parent record was physically deleted but its children were not. The child rows' FK values now point to nothing.
> **"Find all orders where the CustomerID no longer exists in the Customers table — indicating the customer was deleted after the order was placed. These are dangling references created by a missing cascade delete."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Customers** — `schemas/01_Customers.csv`

## Solution Query

```sql
-- Find orders whose customer has been deleted (dangling FK)
SELECT
    o.OrderID,
    o.CustomerID,
    o.OrderDate,
    o.TotalAmount,
    o.Status,
    'Customer deleted — dangling reference' AS Issue
FROM Orders o
WHERE NOT EXISTS (
    SELECT 1 FROM Customers c WHERE c.CustomerID = o.CustomerID
)
ORDER BY o.CustomerID, o.OrderDate;

-- How much revenue is stranded in dangling-reference orders?
SELECT
    o.CustomerID                                AS DeletedCustomerID,
    COUNT(o.OrderID)                            AS StrандedOrders,
    SUM(o.TotalAmount)                          AS StrandedRevenue,
    MIN(o.OrderDate)                            AS EarliestOrder,
    MAX(o.OrderDate)                            AS LatestOrder,
    'Customer deleted — orders orphaned'        AS Issue
FROM Orders o
WHERE NOT EXISTS (
    SELECT 1 FROM Customers c WHERE c.CustomerID = o.CustomerID
)
GROUP BY o.CustomerID
ORDER BY StrandedRevenue DESC;

-- Compare: orphan from G03-T01 (parent never existed) vs dangling ref (parent existed then deleted)
-- If you have a DeletedCustomers archive table, you can distinguish the two:
SELECT
    o.OrderID,
    o.CustomerID,
    o.OrderDate,
    CASE
        WHEN dc.CustomerID IS NOT NULL THEN 'Dangling — customer was deleted (found in archive)'
        ELSE                               'Orphan — CustomerID never existed'
    END AS ReferenceType
FROM Orders o
LEFT JOIN Customers  c  ON o.CustomerID = c.CustomerID
LEFT JOIN DeletedCustomers dc ON o.CustomerID = dc.CustomerID  -- archive table if it exists
WHERE c.CustomerID IS NULL;
```

## Expected Output

**Revenue stranded in dangling-reference orders:**
| DeletedCustomerID | StrandedOrders | StrandedRevenue | EarliestOrder | Issue |
|---|---|---|---|---|
| 99 | 3 | 847.50 | 2023-11-01 | Customer deleted — orders orphaned |

## Explanation

**Dangling reference vs orphan**
These look identical in SQL — both are child rows with no matching parent. The difference is causal: an orphan was created with an invalid FK from the start (bad data); a dangling reference was valid when created but became invalid later because the parent was deleted. The distinction matters for root cause analysis and the correct fix. Detecting which is which requires an archive table or audit log.

**Why cascade deletes are not always the answer**
`ON DELETE CASCADE` automatically deletes child rows when the parent is deleted. But in many business scenarios, you don't want to delete orders when a customer is deleted — you need to retain them for audit, revenue reporting, and legal compliance. The correct pattern is often to soft-delete the customer (set IsActive = 0) rather than physically delete, keeping the FK relationship intact.

**Quantifying the business impact**
The second query groups dangling references by deleted CustomerID and sums the stranded revenue. This transforms a data quality flag into a business metric — the finance team needs to know £847.50 of revenue is attached to records that can no longer be attributed to a customer for reporting purposes.

## Severity
**Critical** — Dangling references cause JOIN failures, silent row drops in reports, and revenue attribution errors. In GDPR contexts they also represent a compliance risk if the deletion was intended to be complete but child data remains visible.
