# G03-T05 — Referential Integrity | Many-to-Many Junction Table Violation

## ID
G03-T05

## Group
3 — Referential Integrity

## Type
Many-to-Many Junction Table with Invalid FK on Either Side

## Live Scenario
An e-learning platform has Students, Courses, and an Enrollments table (StudentID, CourseID, EnrollmentDate). A data migration imports historical enrollments but the Students and Courses tables are populated in separate batches. Due to ordering issues, some enrollments are loaded before the students or courses they reference. The enrollment records are in the table but their FK values point to nothing. The platform shows 0 students enrolled in some courses, and some students appear to have no courses — both caused by the broken junction table.

## The Question
> A junction (bridge) table in a many-to-many relationship must have both FK columns pointing to valid parent records. An invalid FK on either side breaks the relationship entirely.
> **"Validate the SalesTargets table — it links Salespeople (Employees) to Quarters. Find any row where either the SalespersonID doesn't exist in Employees, or where the Year/Quarter combination is outside valid ranges."**

## Table Reference
**SalesTargets** — `schemas/06_SalesTargets.csv`
**Employees** — `schemas/04_Employees.csv`

## Solution Query

```sql
-- Check FK on the left side: SalespersonID must exist in Employees
SELECT
    st.TargetID,
    st.SalespersonID,
    st.Year,
    st.Quarter,
    st.TargetAmount,
    'SalespersonID does not exist in Employees' AS Issue
FROM SalesTargets st
WHERE NOT EXISTS (
    SELECT 1 FROM Employees e WHERE e.EmployeeID = st.SalespersonID
);

-- Check FK on the right side: Year and Quarter must be in valid range
SELECT
    st.TargetID,
    st.SalespersonID,
    st.Year,
    st.Quarter,
    st.TargetAmount,
    CASE
        WHEN st.Year < 2000 OR st.Year > 2100        THEN 'Year out of valid range'
        WHEN st.Quarter NOT IN (1, 2, 3, 4)           THEN 'Quarter must be 1, 2, 3, or 4'
        ELSE 'OK'
    END AS Issue
FROM SalesTargets st
WHERE st.Year < 2000 OR st.Year > 2100
   OR st.Quarter NOT IN (1, 2, 3, 4);

-- Check composite uniqueness: each salesperson should have one target per (Year, Quarter)
SELECT
    SalespersonID,
    Year,
    Quarter,
    COUNT(*) AS TargetCount,
    SUM(TargetAmount) AS CombinedTarget
FROM SalesTargets
GROUP BY SalespersonID, Year, Quarter
HAVING COUNT(*) > 1
ORDER BY TargetCount DESC;

-- Full junction table health check in one query
SELECT
    st.TargetID,
    st.SalespersonID,
    e.FullName          AS SalespersonName,
    st.Year,
    st.Quarter,
    st.TargetAmount,
    CASE
        WHEN e.EmployeeID IS NULL              THEN 'Invalid SalespersonID — orphan'
        WHEN st.Quarter NOT IN (1,2,3,4)       THEN 'Invalid Quarter value'
        WHEN st.Year < 2000 OR st.Year > 2100  THEN 'Invalid Year value'
        WHEN st.TargetAmount <= 0              THEN 'TargetAmount must be positive'
        ELSE 'OK'
    END AS ValidationStatus
FROM SalesTargets st
LEFT JOIN Employees e ON st.SalespersonID = e.EmployeeID
WHERE e.EmployeeID IS NULL
   OR st.Quarter NOT IN (1,2,3,4)
   OR st.Year < 2000 OR st.Year > 2100
   OR st.TargetAmount <= 0
ORDER BY ValidationStatus, st.TargetID;
```

## Expected Output

**Left FK violation:**
| TargetID | SalespersonID | Year | Quarter | Issue |
|---|---|---|---|---|
| T088 | E099 | 2024 | 2 | SalespersonID does not exist in Employees |

**Right side violation:**
| TargetID | SalespersonID | Year | Quarter | Issue |
|---|---|---|---|---|
| T091 | E003 | 2024 | 5 | Quarter must be 1, 2, 3, or 4 |

## Explanation

**Junction tables have two FK directions — both must be validated**
A junction table's integrity depends on BOTH foreign keys being valid. Checking only one side leaves the other side exposed. The LEFT JOIN in the full health check joins to the left parent table; a second LEFT JOIN (or NOT EXISTS) would check the right parent. Always validate both directions.

**Referential integrity is different from domain integrity here**
The Quarter check is not a FK check — it's a range check (domain integrity). But in a junction table these validations are often combined because the junction table's meaning depends on both the FK validity AND the domain validity of its columns. A valid SalespersonID with an invalid Quarter produces a record that looks referentially intact but is semantically meaningless.

**The composite uniqueness check matters too**
A junction table typically enforces a unique combination of its FK columns (e.g., one target per salesperson per quarter). Step 3 checks for duplicate (SalespersonID, Year, Quarter) combinations — which would indicate a data entry error or a reload bug.

## Severity
**Critical** — A broken junction table breaks the many-to-many relationship entirely. Queries joining through the junction return wrong results: missing relationships on one side, phantom relationships on the other.
