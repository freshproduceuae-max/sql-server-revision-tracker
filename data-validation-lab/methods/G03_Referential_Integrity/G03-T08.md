# G03-T08 — Referential Integrity | Cascade Delete Orphan Check

## ID
G03-T08

## Group
3 — Referential Integrity

## Type
Cascade Delete Orphan Check — Verify Cascade Worked Correctly

## Live Scenario
A GDPR deletion request comes in for Customer C0042. The deletion script removes the customer row and relies on `ON DELETE CASCADE` to automatically remove orders and transactions. The DBA runs the deletion, gets no errors, and closes the ticket. Six weeks later an audit discovers that the OrderItems table — which has a FK to Orders but with `ON DELETE NO ACTION` — still has 47 line items referencing deleted orders. The cascade stopped at Orders and left OrderItems as orphans.

## The Question
> A cascade delete was supposed to remove all child records when the parent was deleted. You need to verify the cascade worked completely — that no orphan records were left behind at any level of the hierarchy.
> **"After deleting a customer, verify that all their orders and all order-level children were also removed. Find any remaining records that reference the deleted CustomerID or its child order IDs."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Customers** — `schemas/01_Customers.csv`
**Transactions** — `schemas/05_Transactions.csv`

## Solution Query

```sql
-- Step 1: Find all orphan orders (their customer was deleted)
SELECT
    o.OrderID,
    o.CustomerID,
    o.OrderDate,
    o.TotalAmount,
    'Order references deleted CustomerID' AS OrphanType
FROM Orders o
WHERE NOT EXISTS (
    SELECT 1 FROM Customers c WHERE c.CustomerID = o.CustomerID
);

-- Step 2: Find all orphan transactions (their order was deleted)
SELECT
    t.TransactionID,
    t.OrderID,
    t.Amount,
    t.TransactionDate,
    'Transaction references deleted OrderID' AS OrphanType
FROM Transactions t
WHERE NOT EXISTS (
    SELECT 1 FROM Orders o WHERE o.OrderID = t.OrderID
);

-- Step 3: Cascade integrity check — are there orphans at ANY level?
-- Run this after any parent deletion to verify the cascade completed
SELECT
    'Level 1: Orders with deleted Customers'    AS Level,
    COUNT(*)                                    AS OrphanCount
FROM Orders o
WHERE NOT EXISTS (SELECT 1 FROM Customers c WHERE c.CustomerID = o.CustomerID)
UNION ALL
SELECT
    'Level 2: Transactions with deleted Orders',
    COUNT(*)
FROM Transactions t
WHERE NOT EXISTS (SELECT 1 FROM Orders o WHERE o.OrderID = t.OrderID)
ORDER BY Level;

-- Step 4: Pre-deletion check — show what WILL be deleted before running cascade
-- Run this BEFORE the DELETE to verify scope
DECLARE @CustomerToDelete INT = 5;  -- replace with the target CustomerID

SELECT 'Customer' AS EntityType, @CustomerToDelete AS EntityID, 1 AS RowCount
UNION ALL
SELECT 'Orders', COUNT(*), COUNT(*)
FROM Orders WHERE CustomerID = @CustomerToDelete
UNION ALL
SELECT 'Transactions', COUNT(*), COUNT(*)
FROM Transactions
WHERE OrderID IN (SELECT OrderID FROM Orders WHERE CustomerID = @CustomerToDelete);
```

## Expected Output

**Step 3 — Post-deletion cascade integrity:**
| Level | OrphanCount |
|---|---|
| Level 1: Orders with deleted Customers | 0 |
| Level 2: Transactions with deleted Orders | 0 |

*(Zero across all levels = cascade was complete. Any non-zero = orphans remain.)*

**Step 4 — Pre-deletion scope (CustomerID 5):**
| EntityType | RowCount |
|---|---|
| Customer | 1 |
| Orders | 3 |
| Transactions | 7 |

## Explanation

**Cascade delete is not always enabled — and it doesn't always chain**
`ON DELETE CASCADE` must be set on every FK in the hierarchy that should cascade. A cascade on Customer→Orders does NOT automatically cascade Orders→Transactions unless that FK also has `ON DELETE CASCADE`. A multi-level hierarchy requires explicit cascade configuration at every level.

**Check cascade settings in sys.foreign_keys**
```sql
SELECT
    fk.name AS FK_Name,
    tp.name AS ParentTable,
    tr.name AS ReferencedTable,
    fk.delete_referential_action_desc AS OnDeleteAction
FROM sys.foreign_keys fk
JOIN sys.tables tp ON fk.parent_object_id = tp.object_id
JOIN sys.tables tr ON fk.referenced_object_id = tr.object_id
ORDER BY tp.name, tr.name;
```
`ON DELETE CASCADE` shows as `CASCADE`; `ON DELETE NO ACTION` shows as `NO_ACTION`.

**Pre-deletion scope check prevents surprises**
Step 4 shows exactly how many rows at each level will be affected before the DELETE runs. This prevents accidental large-scale deletions and documents the expected cascade scope for the audit trail.

**When to use this check**
Run Step 3 as a post-deletion integrity test after every GDPR erasure, test data cleanup, or bulk deletion operation. If any level shows a non-zero orphan count, the cascade was incomplete and remediation is needed before the deletion ticket can be closed.

## Severity
**High** — Incomplete cascade deletes leave orphan records that violate referential integrity silently. In GDPR contexts, a partially completed erasure request is a compliance failure — the data that should be deleted still exists.
