# G03-T07 — Referential Integrity | Soft-Delete FK Violation

## ID
G03-T07

## Group
3 — Referential Integrity

## Type
Soft-Delete FK Violation — FK Points to a Deleted/Inactive Parent

## Live Scenario
A subscription platform uses soft deletes on the Products table: `IsActive = 0` marks a discontinued product. A customer places an order for ProductID P009, which was soft-deleted yesterday. The FK constraint is satisfied — P009 still exists in the Products table. But the product's details, pricing, and inventory are all flagged as inactive. The order confirmation email shows the product name correctly, but the fulfilment system skips it because IsActive = 0. The order is confirmed but never fulfilled.

## The Question
> A FK constraint only checks that the parent row EXISTS — it does not check whether that parent is active. An FK pointing to a soft-deleted parent row is technically valid but functionally broken.
> **"Find all orders that reference a Product which has been soft-deleted (IsActive = 0). The FK is intact but the relationship is broken from a business perspective."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Products** — `schemas/03_Products.csv`
**Customers** — `schemas/01_Customers.csv`

## Solution Query

```sql
-- Orders referencing a soft-deleted (inactive) product
SELECT
    o.OrderID,
    o.CustomerID,
    o.ProductID,
    o.OrderDate,
    o.TotalAmount,
    o.Status,
    p.ProductName,
    p.IsActive,
    'Order references INACTIVE product' AS Issue
FROM Orders o
JOIN Products p ON o.ProductID = p.ProductID
WHERE p.IsActive = 0                     -- product exists but is soft-deleted
  AND o.Status NOT IN ('Cancelled', 'Returned');   -- only flag open/active orders

-- Orders referencing a soft-deleted (inactive) customer
SELECT
    o.OrderID,
    o.CustomerID,
    o.OrderDate,
    o.Status,
    c.FirstName + ' ' + c.LastName AS CustomerName,
    c.IsActive,
    'Order references INACTIVE customer' AS Issue
FROM Orders o
JOIN Customers c ON o.CustomerID = c.CustomerID
WHERE c.IsActive = 0
  AND o.Status NOT IN ('Cancelled', 'Returned', 'Delivered');

-- Summary: how many active orders reference inactive parents?
SELECT
    'Active orders on inactive products' AS Check,
    COUNT(*) AS ViolationCount
FROM Orders o
JOIN Products p ON o.ProductID = p.ProductID
WHERE p.IsActive = 0
  AND o.Status NOT IN ('Cancelled', 'Returned')
UNION ALL
SELECT
    'Active orders on inactive customers',
    COUNT(*)
FROM Orders o
JOIN Customers c ON o.CustomerID = c.CustomerID
WHERE c.IsActive = 0
  AND o.Status NOT IN ('Cancelled', 'Returned', 'Delivered');
```

## Expected Output

| OrderID | CustomerID | ProductID | ProductName | IsActive | Issue |
|---|---|---|---|---|---|
| 1015 | 7 | P009 | Headset Pro | 0 | Order references INACTIVE product |

## Explanation

**Why the FK constraint doesn't catch this**
SQL Server's FK constraint checks: does the referenced row exist? It does — P009 is in the Products table. The constraint is satisfied. Whether `IsActive = 0` makes that reference functionally meaningless is a business rule, not a schema constraint. Only an application-level or validation-script check can catch this.

**JOIN vs LEFT JOIN for this check**
Because we know the FK is valid (the row exists), this check uses an INNER JOIN (`JOIN Products p ON ...`) and then filters on `p.IsActive = 0`. We don't need a LEFT JOIN here — we're not looking for missing parents, we're looking for parents that exist but are inactive. Using INNER JOIN is more efficient and more intentional.

**The status exclusion — not all combinations are errors**
A Returned or Cancelled order referencing an inactive product is not a problem — the order was already resolved before or around the same time the product was deactivated. The check uses `WHERE o.Status NOT IN ('Cancelled', 'Returned')` to focus only on orders that are still open and would actually try to fulfil against the inactive product.

**The business rule behind the check**
The rule is: an active order should not reference an inactive (soft-deleted) parent entity. The exact definition of "active" on each side is a business decision — it might be based on IsActive, EndDate < GETDATE(), Status = 'Discontinued', or another flag. Adjust the WHERE clause to match the soft-delete convention in each table.

## Severity
**High** — Soft-delete FK violations are invisible to schema-level constraint checks. They cause fulfilment failures, pricing errors, and access control issues when the inactive parent drives downstream logic that now silently behaves as if the relationship doesn't exist.
