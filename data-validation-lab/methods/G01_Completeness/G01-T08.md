# G01-T08 — Completeness | Missing Expected Row

## ID
G01-T08

## Group
1 — Completeness

## Type
Missing Expected Row — A Record That Should Exist, Doesn't

## Live Scenario
A finance team runs a month-end close. Every cost centre in the company must submit a monthly budget entry. The controller asks: "Which cost centres have NOT submitted their October budget?" The problem isn't a bad value in a row — it's the absence of a row entirely. Standard NULL checks will not find this because there is no row to check.

## The Question
> You have a reference list of all expected entities — 12 months, 50 branches, 30 cost centres.
> **"Which cost centres have not submitted a budget entry for October 2024? Return a list of the missing ones so the finance team can chase the responsible managers."**

## Table Reference
**Transactions** — `schemas/05_Transactions.csv`
**Employees** (as cost centre proxy) — `schemas/04_Employees.csv`

## Solution Query

```sql
-- Pattern 1: LEFT JOIN to find what's missing
-- Every expected month × branch combination vs what actually loaded
WITH ExpectedMonths AS (
    SELECT DISTINCT DATEFROMPARTS(YEAR(TransactionDate), MONTH(TransactionDate), 1) AS MonthStart
    FROM Transactions
    WHERE TransactionDate >= '2024-01-01'
),
ExpectedBranches AS (
    SELECT DISTINCT Department AS Branch FROM Employees
),
Expected AS (
    SELECT m.MonthStart, b.Branch
    FROM ExpectedMonths m
    CROSS JOIN ExpectedBranches b
),
Actual AS (
    SELECT
        DATEFROMPARTS(YEAR(TransactionDate), MONTH(TransactionDate), 1) AS MonthStart,
        Branch
    FROM Transactions
    WHERE TransactionDate >= '2024-01-01'
    GROUP BY DATEFROMPARTS(YEAR(TransactionDate), MONTH(TransactionDate), 1), Branch
)
SELECT
    e.MonthStart,
    e.Branch,
    'Missing — no transactions submitted' AS Issue
FROM Expected e
LEFT JOIN Actual a
    ON  e.MonthStart = a.MonthStart
    AND e.Branch     = a.Branch
WHERE a.MonthStart IS NULL
ORDER BY e.Branch, e.MonthStart;

-- Pattern 2: Check a sequence — are all CustomerIDs from 1 to MAX present?
WITH ExpectedIDs AS (
    SELECT TOP (SELECT MAX(CustomerID) FROM Customers)
           ROW_NUMBER() OVER (ORDER BY (SELECT NULL)) AS ExpectedID
    FROM sys.all_objects a CROSS JOIN sys.all_objects b
)
SELECT ExpectedID AS MissingCustomerID
FROM ExpectedIDs
WHERE ExpectedID NOT IN (SELECT CustomerID FROM Customers)
ORDER BY ExpectedID;
```

## Expected Output

| MonthStart | Branch | Issue |
|---|---|---|
| 2024-10-01 | Finance | Missing — no transactions submitted |
| 2024-10-01 | Operations | Missing — no transactions submitted |

## Explanation

**This is NOT a NULL check — the row doesn't exist**
Every other completeness check in G01 looks at rows that ARE present but have bad values. This check looks for rows that should exist but DON'T. The mechanism is always the same: build an expected set, build an actual set, and LEFT JOIN to find what's in expected but not in actual (the IS NULL on the right side reveals the gap).

**CROSS JOIN to build the expected set**
`CROSS JOIN` produces every combination of two sets — every month with every branch, for example. This is the standard way to generate an expected grid when you have two dimensions. The result is every row that SHOULD exist; the LEFT JOIN then reveals which ones DON'T.

**Sequence gap via ROW_NUMBER**
The second pattern generates a sequence of integers (1 to MAX CustomerID) using ROW_NUMBER on a system table cross join, then uses NOT IN to find which IDs from the sequence are absent from the actual table. This is the standard pattern for detecting gaps in an ID sequence.

## Severity
**Critical** — Missing rows are invisible to row-level validation. In financial reporting, a missing budget submission, a missing daily load, or a missing reconciliation entry can cause understated figures that pass audit checks because there is simply no row to flag.
