# G01-T10 — Completeness | Sentinel Default Value

## ID
G01-T10

## Group
1 — Completeness

## Type
Sentinel Default Used Instead of Real Value (01/01/1900, -1, 0, 9999)

## Live Scenario
A pension fund's legacy system cannot store NULL dates — the database was built before the team understood nullable columns. When a member's retirement date is unknown, the system writes `01/01/1900` as a placeholder. Thirty years of data now contains thousands of members apparently retiring on the same date in 1900. An actuarial model consuming this data calculates negative pension durations and crashes.

## The Question
> Your data contains fields that look populated but hold a magic value the system wrote when the real value was unknown.
> **"Find all records where date or numeric fields contain known sentinel/default values that represent 'unknown' rather than a real value. Classify each by sentinel type."**

## Table Reference
**Customers** — `schemas/01_Customers.csv`
**Orders** — `schemas/02_Orders.csv`
**Employees** — `schemas/04_Employees.csv`

## Solution Query

```sql
-- Date sentinel detection
SELECT
    CustomerID,
    FirstName + ' ' + LastName AS CustomerName,
    DOB,
    CASE
        WHEN DOB = '19000101' THEN 'Sentinel: 01/01/1900 (legacy unknown)'
        WHEN DOB = '19010101' THEN 'Sentinel: 01/01/1901 (legacy unknown variant)'
        WHEN DOB = '99991231' THEN 'Sentinel: 31/12/9999 (far-future unknown end date)'
        WHEN DOB = '20000101' THEN 'Sentinel: 01/01/2000 (system default)'
        WHEN YEAR(DOB) < 1900 THEN 'Impossible year — before 1900'
        WHEN DOB > GETDATE()  THEN 'Future DOB — impossible'
        ELSE 'OK'
    END AS DOB_SentinelFlag
FROM Customers
WHERE DOB IN ('19000101','19010101','99991231','20000101')
   OR YEAR(DOB) < 1900
   OR DOB > GETDATE();

-- Numeric sentinel detection
SELECT
    OrderID,
    CustomerID,
    TotalAmount,
    DiscountPct,
    CASE
        WHEN TotalAmount = -1    THEN 'Sentinel: -1 (unknown amount)'
        WHEN TotalAmount = 0     THEN 'Zero amount — check if intentional'
        WHEN TotalAmount = 9999  THEN 'Sentinel: 9999 (legacy placeholder)'
        WHEN TotalAmount = 99999 THEN 'Sentinel: 99999 (legacy placeholder)'
        ELSE 'OK'
    END AS Amount_SentinelFlag,
    CASE
        WHEN DiscountPct = -1  THEN 'Sentinel: -1 (discount not set)'
        WHEN DiscountPct = 999 THEN 'Sentinel: 999 (overflow placeholder)'
        ELSE 'OK'
    END AS Discount_SentinelFlag
FROM Orders
WHERE TotalAmount IN (-1, 0, 9999, 99999)
   OR DiscountPct IN (-1, 999);

-- Summary: how many sentinel dates exist?
SELECT
    CAST(DOB AS VARCHAR(10)) AS SentinelValue,
    COUNT(*) AS Occurrences,
    'DOB' AS AffectedField
FROM Customers
WHERE DOB IN ('19000101','19010101','99991231','20000101')
GROUP BY CAST(DOB AS VARCHAR(10))
ORDER BY Occurrences DESC;
```

## Explanation

**What a sentinel value is**
A sentinel (or magic value) is a specific value chosen to mean "unknown" or "not applicable" in a system that cannot store NULL. The value is technically valid (it is a real date, a real number) but semantically meaningless. Common sentinels: `01/01/1900`, `31/12/9999`, `-1`, `0`, `9999`, `99999`, `000-00-0000`.

**Sentinel dates are system archaeology**
Different systems have different sentinels. SQL Server's minimum DATETIME is `01/01/1753`; Access uses `30/12/1899`; Excel's epoch starts at `01/01/1900`. When these systems talk to each other, their respective "empty date" sentinels collide with real data. Documenting the sentinels from each source system is an essential step in any data migration.

**Converting sentinels to NULL on ingestion**
The correct fix is to replace sentinel values with NULL at the point of ingestion using NULLIF or a CASE WHEN:
```sql
NULLIF(DOB, '19000101')          -- returns NULL if DOB = 01/01/1900
CASE WHEN DOB = '19000101' THEN NULL ELSE DOB END
```
This converts the problem value to a proper NULL so all downstream NULL-handling logic applies.

## Severity
**Critical** — Sentinel values are the most dangerous type of completeness failure because they look real. They pass NULL checks, range checks, and format checks. They only reveal themselves when their specific value is recognised as a placeholder — which requires documented knowledge of the source system.
