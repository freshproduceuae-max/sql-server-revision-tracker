# G01-T09 — Completeness | Truncated Value

## ID
G01-T09

## Group
1 — Completeness

## Type
Truncated Value — Data Cut Off Mid-String

## Live Scenario
A retailer imports product descriptions from a supplier's API. The target column is VARCHAR(100) but some descriptions are 250 characters long. SQL Server silently truncates them to 100 characters on insert — no error is raised unless SET ANSI_WARNINGS is ON. Six months later, the product team notices that all long product names end mid-word. The data has been quietly incomplete since day one.

## The Question
> After a data migration, product descriptions look short. You suspect the source data was longer than the column allowed.
> **"Find all records where the description or name field appears to be cut off — either hitting exactly the column's maximum length, or ending mid-word without punctuation."**

## Table Reference
**Products** — `schemas/03_Products.csv`

## Solution Query

```sql
-- Check 1: Values that are exactly at the column length limit (suspicious)
-- Assumes ProductName is VARCHAR(50) — adjust MAX_LENGTH to match actual column definition
SELECT
    ProductID,
    ProductName,
    LEN(ProductName)        AS CurrentLength,
    50                      AS ColumnMaxLength,
    CASE
        WHEN LEN(ProductName) = 50 THEN 'At column limit — possibly truncated'
        ELSE 'OK'
    END AS TruncationFlag
FROM Products
WHERE LEN(ProductName) = 50;   -- Replace 50 with actual column max

-- Check 2: Values that end with an incomplete word (no punctuation, no space at end, ends mid-token)
SELECT
    ProductID,
    ProductName,
    LEN(ProductName) AS Length,
    RIGHT(ProductName, 1) AS LastChar,
    CASE
        WHEN RIGHT(ProductName, 1) NOT IN ('.', '!', '?', ')', ']', '"', '''')
         AND RIGHT(ProductName, 1) <> ' '
         AND LEN(ProductName) >= 45   -- close to but not necessarily at the limit
        THEN 'Ends mid-token — possible truncation'
        ELSE 'OK'
    END AS TruncationHint
FROM Products
WHERE LEN(ProductName) >= 45;

-- Check 3: Detect actual column max from metadata and flag rows at that length
SELECT
    t.name AS TableName,
    c.name AS ColumnName,
    c.max_length AS MaxBytes,
    c.max_length AS MaxChars,   -- for VARCHAR; for NVARCHAR divide by 2
    COUNT(*) AS RowsAtMaxLength
FROM sys.columns c
JOIN sys.tables  t ON c.object_id = t.object_id
WHERE t.name = 'Products'
  AND c.name = 'ProductName'
GROUP BY t.name, c.name, c.max_length;
```

## Expected Output

| ProductID | ProductName | CurrentLength | ColumnMaxLength | TruncationFlag |
|---|---|---|---|---|
| P003 | Wireless Ergonomic Keyboard with Bac | 50 | 50 | At column limit — possibly truncated |

## Explanation

**Silent truncation — SQL Server's dangerous default**
By default SQL Server (pre-2019) silently truncates strings that exceed column length. The insert succeeds, no error is raised, and the data is permanently incomplete. Since SQL Server 2019, `SET ANSI_WARNINGS ON` is the default in most configurations and raises an error instead of truncating — but legacy systems and bulk inserts often bypass this.

**Why "exactly at max length" is suspicious**
A value that is exactly as long as the column allows is a signal — not proof — that the original value may have been longer. Legitimate data can naturally hit the limit, but in practice a cluster of values all landing exactly at the boundary is a strong indicator of truncation.

**sys.columns for metadata-driven checks**
Querying `sys.columns` lets you build dynamic validation that adapts to the actual column definition rather than hard-coding the length. This is important in pipelines that move across environments where column sizes may differ.

**RIGHT() to check for mid-word endings**
If the last character of a string is a letter or digit with no terminal punctuation, and the string is close to the column limit, that combination is a strong hint the text was cut off. This heuristic has false positives (short product names are fine ending on a letter) so pair it with the length threshold.

## Severity
**Medium** — Truncated values look complete but carry less information than intended. Impact ranges from cosmetic (cut-off product names) to serious (truncated IBAN numbers or legal clauses in contract text).
