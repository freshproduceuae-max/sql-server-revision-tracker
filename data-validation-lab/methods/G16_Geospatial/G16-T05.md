# G16-T05 — Geospatial | Coordinate-to-Region Consistency Check

## ID
G16-T05

## Group
16 — Geospatial

## Type
Coordinate-to-Region Consistency Check — Verifying That Coordinates Match Declared Region, Country, or Postal District

## Live Scenario
A European insurance company's CRM stores customer addresses with both a `Country` field (populated from account creation) and coordinates (populated by a geocoding service). After a system migration, 890 customers have their coordinates updated by a geocoding batch job that inadvertently uses a German address database for all records — including UK customers. A British customer in Sheffield now has coordinates pointing to Stuttgart. The coordinate-to-country consistency check, comparing each customer's coordinates against the expected latitude/longitude bounds for their declared Country, flags all 890 mismatches: UK customers with German coordinates, whose latitudes (48–51°N) fall below the UK minimum of 49.8°N.

## The Question
> Coordinate-to-region consistency checks cross-validate two independently-sourced pieces of geographic information: the declared country or region (from the form the customer filled in) and the geocoded coordinates (from the geocoding API). If both sources are correct, the coordinates should fall within the geographic bounds of the declared country. A mismatch indicates either a wrong country label, a wrong geocode, or a geocoding pipeline that used the wrong region's address database.
> **"Validate coordinate-to-country consistency in the Customers table: for each customer with a declared Country and valid coordinates, check whether the coordinates fall within the expected geographic bounds of that country. Flag any customers where the coordinates are inconsistent with the declared country, and identify the country whose bounds the coordinates actually fall within."**

## Table Reference
**Customers** — `schemas/01_Customers.csv`

## Solution Query

```sql
-- Step 1: Define country bounding boxes
-- Bounding boxes are approximate; real implementations use polygon intersection
WITH CountryBounds AS (
    SELECT 'UK'      AS Country, 49.8 AS MinLat, 60.9 AS MaxLat, -8.2 AS MinLon, 1.8  AS MaxLon UNION ALL
    SELECT 'US',                 24.0,            71.5,           -125.0,         -66.0          UNION ALL
    SELECT 'Germany',            47.3,            55.1,           6.0,            15.0           UNION ALL
    SELECT 'France',             41.3,            51.1,           -5.2,           9.6            UNION ALL
    SELECT 'Spain',              36.0,            43.8,           -9.3,           4.3            UNION ALL
    SELECT 'Netherlands',        50.7,            53.6,           3.3,            7.2
),
-- Step 2: Match each customer's coordinates against their declared country
CustomerCoordCheck AS (
    SELECT
        c.CustomerID,
        c.Country        AS DeclaredCountry,
        c.Latitude,
        c.Longitude,
        -- Does the coordinate fall within the bounds of the declared country?
        CASE
            WHEN c.Latitude IS NULL OR c.Longitude IS NULL
                 THEN 'NULL: No coordinates to check'
            WHEN b.Country IS NULL
                 THEN 'UNKNOWN COUNTRY: "' + c.Country + '" has no bounding box defined'
            WHEN c.Latitude  BETWEEN b.MinLat AND b.MaxLat
             AND c.Longitude BETWEEN b.MinLon AND b.MaxLon
                 THEN 'CONSISTENT: Coordinates within declared country bounds'
            ELSE 'MISMATCH: Coordinates outside declared country '
                 + c.Country + ' bounds ('
                 + CAST(b.MinLat AS VARCHAR) + '–' + CAST(b.MaxLat AS VARCHAR) + '°N, '
                 + CAST(b.MinLon AS VARCHAR) + '–' + CAST(b.MaxLon AS VARCHAR) + '°E/W)'
        END AS ConsistencyFlag
    FROM Customers c
    LEFT JOIN CountryBounds b ON c.Country = b.Country
)
SELECT * FROM CustomerCoordCheck;

-- Step 3: Identify which country the coordinates actually point to
WITH CountryBounds AS (
    SELECT 'UK'      AS Country, 49.8 AS MinLat, 60.9 AS MaxLat, -8.2 AS MinLon, 1.8  AS MaxLon UNION ALL
    SELECT 'US',                 24.0,            71.5,           -125.0,         -66.0          UNION ALL
    SELECT 'Germany',            47.3,            55.1,           6.0,            15.0           UNION ALL
    SELECT 'France',             41.3,            51.1,           -5.2,           9.6            UNION ALL
    SELECT 'Spain',              36.0,            43.8,           -9.3,           4.3            UNION ALL
    SELECT 'Netherlands',        50.7,            53.6,           3.3,            7.2
)
SELECT
    c.CustomerID,
    c.Country     AS DeclaredCountry,
    c.Latitude,
    c.Longitude,
    ISNULL(
        (SELECT TOP 1 b.Country
         FROM CountryBounds b
         WHERE c.Latitude  BETWEEN b.MinLat AND b.MaxLat
           AND c.Longitude BETWEEN b.MinLon AND b.MaxLon),
        'No matching country in bounding box list'
    ) AS CoordinateCountry,
    CASE
        WHEN c.Country = ISNULL(
                (SELECT TOP 1 b.Country
                 FROM CountryBounds b
                 WHERE c.Latitude  BETWEEN b.MinLat AND b.MaxLat
                   AND c.Longitude BETWEEN b.MinLon AND b.MaxLon), '?')
             THEN 'CONSISTENT'
        ELSE 'MISMATCH: Declared=' + ISNULL(c.Country, 'NULL')
             + ' Coordinates point to='
             + ISNULL(
                 (SELECT TOP 1 b.Country FROM CountryBounds b
                  WHERE c.Latitude BETWEEN b.MinLat AND b.MaxLat
                    AND c.Longitude BETWEEN b.MinLon AND b.MaxLon),
                 'Unknown')
    END AS ConsistencyVerdict
FROM Customers c
WHERE c.Latitude IS NOT NULL AND c.Longitude IS NOT NULL;

-- Step 4: Mismatch summary by declared country
WITH CountryBounds AS (
    SELECT 'UK'      AS Country, 49.8 AS MinLat, 60.9 AS MaxLat, -8.2 AS MinLon, 1.8  AS MaxLon UNION ALL
    SELECT 'US',                 24.0,            71.5,           -125.0,         -66.0          UNION ALL
    SELECT 'Germany',            47.3,            55.1,           6.0,            15.0           UNION ALL
    SELECT 'France',             41.3,            51.1,           -5.2,           9.6            UNION ALL
    SELECT 'Spain',              36.0,            43.8,           -9.3,           4.3
)
SELECT
    c.Country AS DeclaredCountry,
    COUNT(*) AS TotalCustomers,
    SUM(CASE
        WHEN c.Latitude BETWEEN b.MinLat AND b.MaxLat
         AND c.Longitude BETWEEN b.MinLon AND b.MaxLon
        THEN 1 ELSE 0 END) AS ConsistentCoords,
    SUM(CASE
        WHEN NOT (c.Latitude BETWEEN b.MinLat AND b.MaxLat
              AND c.Longitude BETWEEN b.MinLon AND b.MaxLon)
         AND c.Latitude IS NOT NULL
        THEN 1 ELSE 0 END) AS MismatchedCoords,
    SUM(CASE WHEN c.Latitude IS NULL THEN 1 ELSE 0 END) AS NullCoords
FROM Customers c
LEFT JOIN CountryBounds b ON c.Country = b.Country
GROUP BY c.Country
ORDER BY MismatchedCoords DESC;

-- Step 5: Cross-validation with postal region
-- UK postcodes starting with known area codes imply specific regions
SELECT
    CustomerID,
    PostalCode,
    Latitude,
    Longitude,
    CASE
        WHEN PostalCode LIKE 'SW%' OR PostalCode LIKE 'WC%' OR PostalCode LIKE 'EC%'
          OR PostalCode LIKE 'W[0-9]%' OR PostalCode LIKE 'E[0-9]%'
          OR PostalCode LIKE 'N[0-9]%' OR PostalCode LIKE 'SE%'
             THEN 'London postcode area'
        WHEN PostalCode LIKE 'B[0-9]%' OR PostalCode LIKE 'CV%' OR PostalCode LIKE 'DY%'
             THEN 'Birmingham/Midlands postcode area'
        WHEN PostalCode LIKE 'M[0-9]%' OR PostalCode LIKE 'SK%' OR PostalCode LIKE 'OL%'
             THEN 'Manchester postcode area'
        WHEN PostalCode LIKE 'EH%' OR PostalCode LIKE 'G[0-9]%'
             THEN 'Scotland postcode area'
        ELSE 'Other UK region'
    END AS PostcodeRegion,
    CASE
        WHEN (PostalCode LIKE 'EH%' OR PostalCode LIKE 'G[0-9]%')
          AND Latitude IS NOT NULL
          AND Latitude < 54.0
             THEN 'MISMATCH: Scotland postcode but latitude below 54°N'
        WHEN (PostalCode LIKE 'SW%' OR PostalCode LIKE 'WC%')
          AND Latitude IS NOT NULL
          AND (Latitude < 51.0 OR Latitude > 52.0)
             THEN 'MISMATCH: London postcode but latitude outside 51°–52°N'
        ELSE 'Consistent or unchecked'
    END AS PostcodeCoordConsistency
FROM Customers
WHERE PostalCode IS NOT NULL AND Latitude IS NOT NULL;
```

## Explanation

**Bounding box as a first-pass consistency check**
Country bounding boxes are rectangular approximations of a country's geographic extent. They produce false negatives (some coordinates outside the bounding box are in the country — e.g., islands) and false positives (some coordinates inside the bounding box are in a neighbouring country — e.g., a German coordinate that falls within France's bounding box in the Alsace region). For a first-pass consistency check detecting major errors (UK customers with German coordinates), bounding boxes are accurate enough. Precise checks require polygon intersection with actual country boundary geometries.

**Subquery for coordinate-to-country reverse lookup**
Step 3's `SELECT TOP 1 b.Country FROM CountryBounds b WHERE Latitude BETWEEN...` is a correlated subquery that performs the reverse geocoding lookup in SQL — finding which country the coordinate falls within. `TOP 1` is required because bounding boxes overlap for some border regions. In production this would use a spatial index and a proper geometry table for accuracy.

**Postcode area prefix as a regional signal**
UK postcode area codes (the 1–2 letter prefix) are geographically meaningful: EH = Edinburgh, G = Glasgow, SW/WC/EC = London, M = Manchester, B = Birmingham. Cross-validating the postcode area prefix against the coordinate's latitude band catches transposition errors and geocoding pipeline mismatches without requiring a full postcode lookup table.

**Two-source validation principle**
Comparing two independently-sourced data items (declared country and geocoded coordinates) implements the two-source validation principle: neither source is assumed correct in isolation, but where they agree, confidence is high; where they disagree, one or both are wrong. The SQL identifies the disagreements without presupposing which source is incorrect — that determination requires business knowledge or a third source.

## Severity
**High** — Country-coordinate mismatches cause customers to receive incorrect regional treatment: wrong tax rates, wrong regulatory disclosures, wrong language content, wrong service offerings, and wrong geographic segmentation. A UK customer placed in Germany may receive German privacy notices (violating UK GDPR obligations) or be excluded from UK-only promotions — both are regulatory and commercial problems.
