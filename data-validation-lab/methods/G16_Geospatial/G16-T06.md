# G16-T06 — Geospatial | Spatial Join and Coverage Gap Analysis

## ID
G16-T06

## Group
16 — Geospatial

## Type
Spatial Join and Coverage Gap Analysis — Identifying Regions With No Customer Coverage and Validating Spatial Completeness

## Live Scenario
A broadband provider models its network coverage as a set of polygons — each exchange covers a geographic area. Customer addresses are geocoded and should each fall within exactly one coverage polygon. After a network expansion loads 12 new exchange polygons into the coverage table, an audit reveals 340 customer addresses whose coordinates don't fall within any exchange polygon — they are in the geographic gaps between polygons where coverage boundaries were not perfectly contiguous. These customers receive no service despite being within the theoretical coverage area. The coverage gap check, using bounding box approximations of coverage zones and detecting customers with no matching zone, identifies all 340 and routes them to the network team for manual polygon correction.

## The Question
> Spatial join validation in SQL (without a spatial index) approximates geographic containment using bounding boxes and distance thresholds. It identifies records that should have a spatial match but don't (coverage gaps — customers outside all service zones), records that match multiple zones (overlap — customers in ambiguous areas between service zones), and zones with no associated records (empty coverage areas — either genuine gaps or data not yet loaded).
> **"Analyse spatial coverage for the Customers dataset: define approximate service zone bounding boxes for UK regions, check that each customer coordinate falls within at least one service zone, identify customers that fall outside all defined zones (coverage gaps), detect customers matching multiple zones (zone overlaps), and flag service zones with no customers (empty zones)."**

## Table Reference
**Customers** — `schemas/01_Customers.csv`

## Solution Query

```sql
-- Step 1: Define service zone bounding boxes (approximating polygon coverage)
-- In production these would come from a geometry table with actual polygon coordinates
WITH ServiceZones AS (
    SELECT 'Zone-London'     AS ZoneID, 'London'      AS ZoneName,
           51.30 AS MinLat, 51.70 AS MaxLat, -0.50 AS MinLon, 0.30 AS MaxLon
    UNION ALL
    SELECT 'Zone-Manchester', 'Manchester',
           53.30, 53.70, -2.50, -2.00
    UNION ALL
    SELECT 'Zone-Birmingham', 'Birmingham',
           52.30, 52.65, -2.00, -1.60
    UNION ALL
    SELECT 'Zone-Leeds',      'Leeds',
           53.75, 54.00, -1.65, -1.35
    UNION ALL
    SELECT 'Zone-Edinburgh',  'Edinburgh',
           55.80, 56.10, -3.40, -3.00
    UNION ALL
    SELECT 'Zone-Bristol',    'Bristol',
           51.35, 51.60, -2.75, -2.40
),
-- Step 2: Spatial join — match each customer to service zones
CustomerZoneMatches AS (
    SELECT
        c.CustomerID,
        c.Latitude,
        c.Longitude,
        c.Country,
        z.ZoneID,
        z.ZoneName
    FROM Customers c
    LEFT JOIN ServiceZones z
        ON c.Latitude  BETWEEN z.MinLat AND z.MaxLat
        AND c.Longitude BETWEEN z.MinLon AND z.MaxLon
    WHERE c.Latitude IS NOT NULL AND c.Longitude IS NOT NULL
),
-- Step 3: Count zone matches per customer
CustomerZoneSummary AS (
    SELECT
        CustomerID,
        Latitude,
        Longitude,
        Country,
        COUNT(ZoneID)                    AS ZoneMatchCount,
        STRING_AGG(ZoneName, ', ')       AS MatchedZones,
        MAX(CASE WHEN ZoneID IS NULL THEN 1 ELSE 0 END) AS HasNoMatch
    FROM CustomerZoneMatches
    GROUP BY CustomerID, Latitude, Longitude, Country
)
SELECT
    CustomerID,
    Latitude,
    Longitude,
    Country,
    ZoneMatchCount,
    MatchedZones,
    CASE
        WHEN ZoneMatchCount = 0 OR HasNoMatch = 1
             THEN 'COVERAGE GAP: Customer coordinates do not fall within any service zone'
        WHEN ZoneMatchCount = 1
             THEN 'COVERED: Exactly one zone match — ' + MatchedZones
        WHEN ZoneMatchCount > 1
             THEN 'OVERLAP: Customer falls in ' + CAST(ZoneMatchCount AS VARCHAR)
                  + ' zones — ' + MatchedZones
    END AS CoverageFlag
FROM CustomerZoneSummary
ORDER BY ZoneMatchCount ASC;

-- Step 4: Zone coverage summary — any zones with no customers?
WITH ServiceZones AS (
    SELECT 'Zone-London'     AS ZoneID, 'London'      AS ZoneName,
           51.30 AS MinLat, 51.70 AS MaxLat, -0.50 AS MinLon, 0.30 AS MaxLon
    UNION ALL
    SELECT 'Zone-Manchester', 'Manchester', 53.30, 53.70, -2.50, -2.00
    UNION ALL
    SELECT 'Zone-Birmingham', 'Birmingham', 52.30, 52.65, -2.00, -1.60
    UNION ALL
    SELECT 'Zone-Leeds',      'Leeds',      53.75, 54.00, -1.65, -1.35
    UNION ALL
    SELECT 'Zone-Edinburgh',  'Edinburgh',  55.80, 56.10, -3.40, -3.00
    UNION ALL
    SELECT 'Zone-Bristol',    'Bristol',    51.35, 51.60, -2.75, -2.40
)
SELECT
    z.ZoneID,
    z.ZoneName,
    COUNT(c.CustomerID) AS CustomersInZone,
    CASE
        WHEN COUNT(c.CustomerID) = 0
             THEN 'EMPTY ZONE: No customers in this service zone — data gap or unserved area'
        ELSE 'Has customers: ' + CAST(COUNT(c.CustomerID) AS VARCHAR)
    END AS ZoneCoverageFlag
FROM ServiceZones z
LEFT JOIN Customers c
    ON c.Latitude  BETWEEN z.MinLat AND z.MaxLat
    AND c.Longitude BETWEEN z.MinLon AND z.MaxLon
    AND c.Latitude IS NOT NULL
GROUP BY z.ZoneID, z.ZoneName
ORDER BY CustomersInZone ASC;

-- Step 5: Coverage gap quantification
SELECT
    'Customers with coordinates'         AS Metric,
    COUNT(*) AS Value
FROM Customers WHERE Latitude IS NOT NULL AND Longitude IS NOT NULL
UNION ALL
SELECT
    'Customers matched to at least one zone',
    COUNT(DISTINCT c.CustomerID)
FROM Customers c
JOIN (
    SELECT 'Zone-London'     AS ZoneID, 51.30 AS MinLat, 51.70 AS MaxLat, -0.50 AS MinLon, 0.30 AS MaxLon
    UNION ALL SELECT 'Zone-Manchester', 53.30, 53.70, -2.50, -2.00
    UNION ALL SELECT 'Zone-Birmingham', 52.30, 52.65, -2.00, -1.60
    UNION ALL SELECT 'Zone-Leeds',      53.75, 54.00, -1.65, -1.35
    UNION ALL SELECT 'Zone-Edinburgh',  55.80, 56.10, -3.40, -3.00
    UNION ALL SELECT 'Zone-Bristol',    51.35, 51.60, -2.75, -2.40
) z ON c.Latitude BETWEEN z.MinLat AND z.MaxLat
    AND c.Longitude BETWEEN z.MinLon AND z.MaxLon
WHERE c.Latitude IS NOT NULL
UNION ALL
SELECT
    'Customers in coverage gap (no zone)',
    COUNT(DISTINCT c.CustomerID)
FROM Customers c
WHERE c.Latitude IS NOT NULL
  AND NOT EXISTS (
      SELECT 1 FROM (
          SELECT 51.30 AS MinLat, 51.70 AS MaxLat, -0.50 AS MinLon, 0.30 AS MaxLon
          UNION ALL SELECT 53.30, 53.70, -2.50, -2.00
          UNION ALL SELECT 52.30, 52.65, -2.00, -1.60
          UNION ALL SELECT 53.75, 54.00, -1.65, -1.35
          UNION ALL SELECT 55.80, 56.10, -3.40, -3.00
          UNION ALL SELECT 51.35, 51.60, -2.75, -2.40
      ) z
      WHERE c.Latitude  BETWEEN z.MinLat AND z.MaxLat
        AND c.Longitude BETWEEN z.MinLon AND z.MaxLon
  );
```

## Explanation

**LEFT JOIN for gap detection**
The spatial join uses LEFT JOIN from customers to zones: every customer appears in the result, joined to whichever zone(s) contain their coordinate. A customer with no matching zone appears with NULL zone fields — detected by `ZoneMatchCount = 0`. This mirrors the standard LEFT JOIN + IS NULL orphan pattern applied to geographic containment.

**NOT EXISTS for zone gap detection (Step 5)**
Step 5's NOT EXISTS subquery is more efficient than a GROUP BY + HAVING COUNT = 0 for coverage gap counting: it exits as soon as any matching zone is found, rather than counting all matches. For large customer tables with many service zones, this performance difference is significant.

**Bounding box vs polygon containment**
Bounding box containment is O(n×m) — each customer is compared to each zone — and introduces false positives at corners (a coordinate in the corner of a zone's bounding box may be outside the actual polygon). True polygon containment requires either a spatial geometry data type (geography/geometry in SQL Server) or an explicit point-in-polygon algorithm. For rectangular service areas (grids, administrative regions), bounding boxes are exact; for irregular polygons (watershed boundaries, franchise territories), they are an approximation that must be validated with the actual geometry.

**Empty zone as a data completeness signal**
A service zone with no customers is either a genuine unserved area or an indicator that customers in that area were not loaded, were assigned to a different zone, or had their coordinates stripped during ETL. Step 4's empty zone check distinguishes between these explanations by providing context — a brand-new zone (e.g., Zone-Bristol just added) legitimately has no customers; an existing zone that previously had customers and now shows zero indicates a load error.

## Severity
**Medium** — Coverage gap errors cause silent service failures: customers in coverage gaps receive no communications targeted by zone, are excluded from zone-specific pricing, and are omitted from capacity planning. Empty zone detection is operationally critical for service planning — an empty zone that should have customers indicates either a data load failure or a geographic area that needs to be investigated for service expansion.
