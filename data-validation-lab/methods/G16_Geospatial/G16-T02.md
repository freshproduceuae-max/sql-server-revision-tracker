# G16-T02 — Geospatial | Distance and Proximity Validation

## ID
G16-T02

## Group
16 — Geospatial

## Type
Distance and Proximity Validation — Computing Distances Between Points and Detecting Geographic Outliers

## Live Scenario
A logistics company's ETL loads driver GPS pings every 5 minutes. A data entry error causes a driver's home depot to be recorded at coordinates (51.51, -0.13) — central London — when the actual depot is in Birmingham (52.48, -1.90). The distance validation check, computing the great-circle distance between each driver's GPS pings and their assigned depot, flags that this driver's pings are consistently 163km from their recorded depot — an impossible commute for a 5-minute GPS interval. The check runs post-load and quarantines 847 pings attributed to the wrong depot before they distort the route efficiency calculations.

## The Question
> Distance validation uses the Haversine formula (approximated in SQL as an equirectangular projection for short distances) to compute distances between coordinate pairs, then checks whether those distances are within expected bounds. SQL implements this as a derived column on a JOIN between two tables sharing a geographic relationship — validating that a customer's coordinates are within a plausible distance of their postal region centroid, or that consecutive GPS pings imply a physically achievable speed.
> **"Validate geographic distances in the Customers table: compute the distance between each customer's coordinates and the London centroid (51.5074, -0.1278), identify customers whose coordinates place them at implausible distances from expected regions, and detect coordinate pairs that are suspiciously close together (possible duplicates) or impossibly far apart."**

## Table Reference
**Customers** — `schemas/01_Customers.csv`

## Solution Query

```sql
-- Step 1: Compute approximate distance from London centroid using equirectangular projection
-- Distance formula: sqrt((Δlat)² + (Δlon × cos(lat))²) × R
-- where R = 6371 km (Earth radius), angles in radians
-- Accurate to ~0.5% for distances up to ~500km
SELECT
    CustomerID,
    Latitude,
    Longitude,
    Country,
    -- Equirectangular distance approximation (km)
    ROUND(
        6371.0 * SQRT(
            POWER((Latitude  - 51.5074) * PI() / 180.0, 2)
            + POWER((Longitude - (-0.1278)) * PI() / 180.0
                    * COS(51.5074 * PI() / 180.0), 2)
        ), 1
    ) AS DistFromLondonKm,
    CASE
        WHEN Latitude IS NULL OR Longitude IS NULL
             THEN 'NULL: Cannot compute distance'
        WHEN 6371.0 * SQRT(
                POWER((Latitude  - 51.5074) * PI() / 180.0, 2)
                + POWER((Longitude - (-0.1278)) * PI() / 180.0
                        * COS(51.5074 * PI() / 180.0), 2)
             ) > 1000
             THEN 'DISTANT: More than 1000km from London — outside UK'
        WHEN 6371.0 * SQRT(
                POWER((Latitude  - 51.5074) * PI() / 180.0, 2)
                + POWER((Longitude - (-0.1278)) * PI() / 180.0
                        * COS(51.5074 * PI() / 180.0), 2)
             ) < 0.1
             THEN 'COINCIDENT: Customer coordinate is within 100m of London centroid — possible default'
        ELSE 'Within expected UK range'
    END AS DistanceFlag
FROM Customers
WHERE Latitude IS NOT NULL AND Longitude IS NOT NULL
ORDER BY DistFromLondonKm DESC;

-- Step 2: Detect suspiciously close coordinates — possible duplicate customers
-- Two customers within 10 metres (0.01 km) of each other
SELECT
    a.CustomerID  AS CustomerID_A,
    b.CustomerID  AS CustomerID_B,
    a.Latitude    AS Lat_A,
    a.Longitude   AS Lon_A,
    b.Latitude    AS Lat_B,
    b.Longitude   AS Lon_B,
    ROUND(
        6371.0 * SQRT(
            POWER((a.Latitude  - b.Latitude)  * PI() / 180.0, 2)
            + POWER((a.Longitude - b.Longitude) * PI() / 180.0
                    * COS(a.Latitude * PI() / 180.0), 2)
        ) * 1000, 1
    ) AS DistanceMetres,
    'NEAR-DUPLICATE LOCATION: Customers within 10m — possible duplicate registration' AS Flag
FROM Customers a
JOIN Customers b
    ON a.CustomerID < b.CustomerID  -- avoid self-join and symmetric pairs
    AND a.Latitude IS NOT NULL AND b.Latitude IS NOT NULL
WHERE 6371.0 * SQRT(
        POWER((a.Latitude  - b.Latitude)  * PI() / 180.0, 2)
        + POWER((a.Longitude - b.Longitude) * PI() / 180.0
                * COS(a.Latitude * PI() / 180.0), 2)
     ) < 0.01;  -- less than 10 metres

-- Step 3: Speed-implied distance check
-- For sequential orders from the same customer, the time between orders
-- implies a minimum travel time — used as a proxy for impossible-location detection
WITH OrderedCustomerOrders AS (
    SELECT
        o.CustomerID,
        o.OrderID,
        o.OrderDate,
        c.Latitude,
        c.Longitude,
        LAG(o.OrderDate)  OVER (PARTITION BY o.CustomerID ORDER BY o.OrderDate) AS PriorOrderDate,
        LAG(c.Latitude)   OVER (PARTITION BY o.CustomerID ORDER BY o.OrderDate) AS PriorLat,
        LAG(c.Longitude)  OVER (PARTITION BY o.CustomerID ORDER BY o.OrderDate) AS PriorLon
    FROM Orders o
    JOIN Customers c ON o.CustomerID = c.CustomerID
    WHERE c.Latitude IS NOT NULL AND c.Longitude IS NOT NULL
)
SELECT
    CustomerID,
    OrderID,
    CAST(OrderDate AS DATE) AS OrderDate,
    CAST(PriorOrderDate AS DATE) AS PriorOrderDate,
    DATEDIFF(DAY, PriorOrderDate, OrderDate) AS DaysBetweenOrders,
    ROUND(
        6371.0 * SQRT(
            POWER((Latitude  - PriorLat) * PI() / 180.0, 2)
            + POWER((Longitude - PriorLon) * PI() / 180.0
                    * COS(Latitude * PI() / 180.0), 2)
        ), 1
    ) AS DistKmFromPrior,
    'NOTE: Same customer coordinates across orders — customer location is static (expected)' AS Note
FROM OrderedCustomerOrders
WHERE PriorLat IS NOT NULL
  AND ABS(Latitude - PriorLat) < 0.0001   -- same coordinate = same customer address
  AND ABS(Longitude - PriorLon) < 0.0001;

-- Step 4: Bounding box summary — what area do the customer coordinates span?
SELECT
    'Latitude range'   AS Metric,
    CAST(ROUND(MIN(Latitude),  4) AS VARCHAR) + ' to ' +
    CAST(ROUND(MAX(Latitude),  4) AS VARCHAR) AS Value,
    ROUND(MAX(Latitude) - MIN(Latitude), 2) AS Span
FROM Customers WHERE Latitude IS NOT NULL
UNION ALL
SELECT
    'Longitude range',
    CAST(ROUND(MIN(Longitude), 4) AS VARCHAR) + ' to ' +
    CAST(ROUND(MAX(Longitude), 4) AS VARCHAR),
    ROUND(MAX(Longitude) - MIN(Longitude), 2)
FROM Customers WHERE Longitude IS NOT NULL
UNION ALL
SELECT
    'Approx N-S span (km)',
    CAST(ROUND(ABS(MAX(Latitude) - MIN(Latitude)) * 111.0, 0) AS VARCHAR) + ' km',
    ROUND(ABS(MAX(Latitude) - MIN(Latitude)) * 111.0, 0)
FROM Customers WHERE Latitude IS NOT NULL;
```

## Explanation

**Equirectangular projection vs Haversine**
The equirectangular projection (used in Step 1) approximates great-circle distance as if the Earth were flat in the local area. It introduces less than 0.5% error for distances up to 500km and avoids the trigonometric complexity of the full Haversine formula. For UK-scale distances (up to ~1000km), the error is acceptable for anomaly detection. For precise routing calculations, the full Haversine formula should be used.

**The 111km-per-degree rule**
One degree of latitude = approximately 111km anywhere on Earth (the Earth is nearly spherical). One degree of longitude varies by latitude: at 51°N (London), one degree of longitude ≈ 111 × cos(51°) ≈ 70km. These approximations enable quick mental calculations and sanity checks in Step 4 without trigonometry.

**Self-join for proximity detection (Step 2)**
Detecting pairs of customers that are suspiciously close requires comparing every customer to every other customer — a self-join. The `a.CustomerID < b.CustomerID` condition prevents self-matching (a customer to itself) and duplicate pairs (A-B and B-A). For large tables, this self-join can be expensive; a spatial index or a grid-based partitioning approach is needed at scale.

**Coincident coordinate as default signal**
A customer coordinate exactly matching the London centroid (51.5074, -0.1278) is more likely a geocoding failure default than a real address — the centroid is often used as a fallback when an address cannot be resolved. Step 1's coincident check uses a 100m radius (0.001 degrees ≈ 100m) rather than exact equality to catch coordinates that were rounded to fewer decimal places.

## Severity
**Medium** — Distance validation errors propagate into geographic segmentation, depot assignment, coverage analysis, and delivery routing. A customer placed 1000km from their actual location is excluded from regional promotions, assigned to the wrong service area, and generates anomalous delivery distance metrics. Unlike many data quality errors, coordinate errors are often individually indistinguishable from valid data — only distance-based validation reveals them.
