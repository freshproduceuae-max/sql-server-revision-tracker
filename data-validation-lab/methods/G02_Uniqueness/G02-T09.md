# G02-T09 — Uniqueness | Duplicate with Different Surrogate Key

## ID
G02-T09

## Group
2 — Uniqueness / Duplicates

## Type
Duplicate with Different Surrogate Key — Re-loaded Without Deduplication

## Live Scenario
An ETL pipeline loads product data from a supplier's API every night. The pipeline has a bug: instead of MERGE (update if exists, insert if new), it does a straight INSERT. After 3 nights, every product has 3 rows in the table — each with a different auto-generated ProductID (the surrogate key is unique!) but identical business content. The primary key constraint is satisfied. Every join fans out by 3×.

## The Question
> The surrogate key (auto-generated ID) is unique for every row. But the business content — the actual data — is a duplicate of one or more other rows. The PK constraint gives a false sense of data integrity.
> **"Find all Products where the business content (ProductName, Category, UnitCost, SellingPrice) is identical to another row, even though each row has a different ProductID. These are reload duplicates."**

## Table Reference
**Products** — `schemas/03_Products.csv`

## Solution Query

```sql
-- Step 1: Find business-content duplicates (surrogate key differs but data is the same)
SELECT
    ProductName,
    Category,
    SubCategory,
    UnitCost,
    SellingPrice,
    COUNT(*)                                            AS DuplicateCount,
    MIN(ProductID)                                      AS FirstLoadedID,
    MAX(ProductID)                                      AS LastLoadedID,
    STRING_AGG(CAST(ProductID AS VARCHAR(20)), ', ')    AS AllProductIDs
FROM Products
GROUP BY ProductName, Category, SubCategory, UnitCost, SellingPrice
HAVING COUNT(*) > 1
ORDER BY DuplicateCount DESC;

-- Step 2: Full row detail for each group of content duplicates
WITH ContentRanked AS (
    SELECT *,
        ROW_NUMBER() OVER (
            PARTITION BY ProductName, Category, UnitCost, SellingPrice
            ORDER BY ProductID ASC   -- lowest ID = first load = original
        ) AS LoadRank,
        COUNT(*) OVER (
            PARTITION BY ProductName, Category, UnitCost, SellingPrice
        ) AS LoadCount
    FROM Products
)
SELECT
    ProductID,
    ProductName,
    Category,
    UnitCost,
    SellingPrice,
    StockQty,
    LoadRank,
    LoadCount,
    CASE
        WHEN LoadRank = 1 THEN 'First load — KEEP'
        ELSE 'Reload duplicate #' + CAST(LoadRank AS VARCHAR) + ' — DELETE'
    END AS LoadStatus
FROM ContentRanked
WHERE LoadCount > 1
ORDER BY ProductName, LoadRank;

-- Step 3: CHECKSUM-based approach — fingerprint each row's content
SELECT
    ProductID,
    ProductName,
    CHECKSUM(ProductName, Category, SubCategory, UnitCost, SellingPrice) AS RowChecksum
FROM Products
ORDER BY RowChecksum, ProductID;

-- Rows with identical checksums (possible content duplicates)
SELECT
    RowChecksum,
    COUNT(*) AS RowCount,
    STRING_AGG(CAST(ProductID AS VARCHAR), ', ') AS ProductIDs
FROM (
    SELECT
        ProductID,
        CHECKSUM(ProductName, Category, SubCategory, UnitCost, SellingPrice) AS RowChecksum
    FROM Products
) checksums
GROUP BY RowChecksum
HAVING COUNT(*) > 1;
```

## Expected Output

**Step 1:**
| ProductName | DuplicateCount | FirstLoadedID | LastLoadedID | AllProductIDs |
|---|---|---|---|---|
| USB-C Hub 7-Port | 3 | P001 | P043 | P001, P022, P043 |

**Step 2:**
| ProductID | ProductName | LoadRank | LoadStatus |
|---|---|---|---|
| P001 | USB-C Hub 7-Port | 1 | First load — KEEP |
| P022 | USB-C Hub 7-Port | 2 | Reload duplicate #2 — DELETE |
| P043 | USB-C Hub 7-Port | 3 | Reload duplicate #3 — DELETE |

## Explanation

**Unique PK does NOT mean no duplicates**
An auto-increment surrogate key guarantees that every row has a unique identifier. It says nothing about the content of the row. A PK constraint on ProductID prevents two rows with ProductID = P001, but it cannot prevent two rows with identical ProductName, Category, and Price carrying different auto-generated IDs.

**CHECKSUM for fast content fingerprinting**
`CHECKSUM(col1, col2, col3)` generates an integer hash of the combined column values. Rows with identical content produce the same checksum. Rows with different checksums are definitely different content. CHECKSUM has a small collision risk (two different rows producing the same hash) — for critical deduplication use `HASHBYTES('SHA2_256', ...)` instead (see G02-T01 for a more collision-resistant approach).

**STRING_AGG to show all affected IDs**
`STRING_AGG(CAST(ProductID AS VARCHAR), ', ')` lists all ProductIDs that share the same content in a single readable cell. This is essential for understanding the scope — "this product was loaded 7 times" — without expanding every row.

**The fix: MERGE instead of INSERT**
The root cause of reload duplicates is usually an INSERT-only pipeline. The correct pattern is MERGE:
```sql
MERGE Products AS target
USING @NewProducts AS source ON target.ProductCode = source.ProductCode
WHEN MATCHED THEN UPDATE SET ...
WHEN NOT MATCHED THEN INSERT ...;
```

## Severity
**Critical** — Reload duplicates with different surrogate keys are invisible to PK constraints. They silently multiply every aggregation, JOIN fan-out, and report total by the number of duplicate loads.
