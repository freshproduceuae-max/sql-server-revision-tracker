# G02-T04 — Uniqueness | Near-Duplicate (Fuzzy Match)

## ID
G02-T04

## Group
2 — Uniqueness / Duplicates

## Type
Near-Duplicate — Same Person, Slightly Different Spelling

## Live Scenario
A legal firm's conflict-of-interest check must ensure no client appears twice under slightly different names. "Jonathan Smith" and "Jon Smith" share the same date of birth and postcode — almost certainly the same person, but exact matching misses them because the names differ. The firm risks breaching conflict rules because their duplicate check only catches exact matches.

## The Question
> Exact duplicate checks pass, but you suspect some records represent the same real-world entity with slightly different data entry.
> **"Find potential near-duplicate customers using phonetic matching and shared secondary attributes. Return pairs of records that appear to be the same person entered twice."**

## Table Reference
**Customers** — `schemas/01_Customers.csv`
**Employees** — `schemas/04_Employees.csv`

## Solution Query

```sql
-- Method A: Shared email — different name/ID (clearest signal)
SELECT
    A.CustomerID   AS ID_A,
    A.FirstName + ' ' + A.LastName AS Name_A,
    B.CustomerID   AS ID_B,
    B.FirstName + ' ' + B.LastName AS Name_B,
    A.Email,
    A.DOB,
    'Shared email — likely same person' AS MatchReason
FROM Customers A
JOIN Customers B
    ON  A.Email       = B.Email
    AND A.CustomerID <> B.CustomerID
    AND A.CustomerID  < B.CustomerID   -- avoid (A,B) and (B,A) pairs
WHERE A.Email IS NOT NULL;

-- Method B: SOUNDEX phonetic match on name + same DOB
SELECT
    A.CustomerID   AS ID_A,
    A.FirstName + ' ' + A.LastName AS Name_A,
    B.CustomerID   AS ID_B,
    B.FirstName + ' ' + B.LastName AS Name_B,
    A.DOB,
    A.Country,
    SOUNDEX(A.LastName)  AS SoundexLastName,
    'Phonetic last name match + same DOB' AS MatchReason
FROM Customers A
JOIN Customers B
    ON  SOUNDEX(A.LastName) = SOUNDEX(B.LastName)
    AND A.DOB               = B.DOB
    AND A.CustomerID       <> B.CustomerID
    AND A.CustomerID        < B.CustomerID
WHERE A.DOB IS NOT NULL;

-- Method C: DIFFERENCE() score — similar sounding full name, same country
SELECT
    A.CustomerID   AS ID_A,
    A.FirstName + ' ' + A.LastName AS Name_A,
    B.CustomerID   AS ID_B,
    B.FirstName + ' ' + B.LastName AS Name_B,
    A.Country,
    DIFFERENCE(
        A.FirstName + ' ' + A.LastName,
        B.FirstName + ' ' + B.LastName
    ) AS NameSimilarityScore,  -- 4 = very similar, 0 = very different
    'Phonetic name similarity >= 3 in same country' AS MatchReason
FROM Customers A
JOIN Customers B
    ON  A.Country       = B.Country
    AND A.CustomerID   <> B.CustomerID
    AND A.CustomerID    < B.CustomerID
WHERE DIFFERENCE(
        A.FirstName + ' ' + A.LastName,
        B.FirstName + ' ' + B.LastName
      ) >= 3
  AND A.Country IS NOT NULL;
```

## Expected Output

**Method B:**
| ID_A | Name_A | ID_B | Name_B | DOB | SoundexLastName | MatchReason |
|---|---|---|---|---|---|---|
| E001 | Sarah Thompson | E015 | Sara Thompson | 1985-06-20 | T512 | Phonetic last name match + same DOB |

## Explanation

**SOUNDEX — how it works**
SOUNDEX converts a string to a 4-character code: first letter + 3 digits encoding consonant groups. "Thompson" and "Tomson" both produce T512. "Smith" and "Smyth" both produce S530. The code ignores vowels and similar-sounding consonants, making it effective at catching name typos and phonetic variants.

**DIFFERENCE() — a similarity score**
`DIFFERENCE(str1, str2)` compares two SOUNDEX codes and returns 0 (no similarity) to 4 (sounds identical). A score of 3 or 4 is a strong near-duplicate signal. It works best on single words; for full names, applying it to the concatenated full name is a reasonable heuristic.

**Preventing duplicate pairs (A,B) and (B,A)**
Without `AND A.CustomerID < B.CustomerID`, every pair appears twice — once as (1,11) and once as (11,1). The less-than condition ensures each pair appears exactly once in the result.

**These are candidates, not confirmed duplicates**
SOUNDEX and DIFFERENCE are heuristics. They generate candidates for human review. The standard process is: (1) generate candidates via phonetic matching, (2) narrow by a second corroborating attribute (same DOB, same postcode), (3) human review or automated scoring to confirm, (4) MERGE to consolidate confirmed duplicates.

## Severity
**High** — Near-duplicates inflate customer counts, cause duplicate outreach, and in regulated industries (healthcare, legal, finance) can cause confidential data to be shown to the wrong person.
