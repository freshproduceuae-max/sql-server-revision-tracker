# G02-T06 — Uniqueness | Composite Key Duplicate

## ID
G02-T06

## Group
2 — Uniqueness / Duplicates

## Type
Composite Key Duplicate

## Live Scenario
A payroll system stores one salary record per employee per month. The key is (EmployeeID, PayrollMonth) — neither column alone is unique. A batch job runs twice due to a scheduling error. Now every employee has two salary records for March 2024. The payroll run doubles every payment. The error is not visible from checking EmployeeID alone or PayrollMonth alone — only the combination reveals the duplicate.

## The Question
> No single column is the key — uniqueness is defined by a combination of two or more columns.
> **"In the Transactions table, each combination of (CustomerID, TransactionDate, Amount) should appear at most once. Find all cases where this composite key is duplicated, indicating a possible double-transaction."**

## Table Reference
**Transactions** — `schemas/05_Transactions.csv`

## Solution Query

```sql
-- Step 1: Find duplicate composite keys
SELECT
    CustomerID,
    TransactionDate,
    Amount,
    COUNT(*) AS Occurrences
FROM Transactions
GROUP BY CustomerID, TransactionDate, Amount
HAVING COUNT(*) > 1
ORDER BY Occurrences DESC, CustomerID;

-- Step 2: Show full rows for each duplicate composite key group
WITH CompositeRanked AS (
    SELECT *,
        ROW_NUMBER() OVER (
            PARTITION BY CustomerID, TransactionDate, Amount
            ORDER BY TransactionID ASC
        ) AS RowRank,
        COUNT(*) OVER (
            PARTITION BY CustomerID, TransactionDate, Amount
        ) AS GroupSize
    FROM Transactions
)
SELECT
    TransactionID,
    CustomerID,
    TransactionDate,
    Amount,
    TransactionType,
    RowRank,
    GroupSize,
    CASE WHEN RowRank = 1 THEN 'Original' ELSE 'DUPLICATE' END AS Status
FROM CompositeRanked
WHERE GroupSize > 1
ORDER BY CustomerID, TransactionDate, Amount, RowRank;

-- Step 3: SalesTargets — unique per (SalespersonID, Year, Quarter)
SELECT
    SalespersonID,
    Year,
    Quarter,
    COUNT(*) AS DuplicateCount,
    SUM(TargetAmount) AS CombinedTarget,
    MIN(TargetAmount) AS MinTarget,
    MAX(TargetAmount) AS MaxTarget
FROM SalesTargets
GROUP BY SalespersonID, Year, Quarter
HAVING COUNT(*) > 1
ORDER BY DuplicateCount DESC;
```

## Expected Output

**Step 1:**
| CustomerID | TransactionDate | Amount | Occurrences |
|---|---|---|---|
| C005 | 2024-03-15 | 250.00 | 2 |
| C012 | 2024-03-15 | 89.99 | 2 |

**Step 2:**
| TransactionID | CustomerID | TransactionDate | Amount | RowRank | Status |
|---|---|---|---|---|---|
| T0044 | C005 | 2024-03-15 | 250.00 | 1 | Original |
| T0045 | C005 | 2024-03-15 | 250.00 | 2 | DUPLICATE |

## Explanation

**Why single-column uniqueness checks miss this**
CustomerID C005 appears many times — that is normal and expected. TransactionDate 2024-03-15 appears many times — also normal. The problem only becomes visible when you combine them: this specific customer should not have two transactions of the same amount on the same date. Composite key validation requires GROUP BY on all columns that together form the key.

**PARTITION BY multiple columns in ROW_NUMBER**
`PARTITION BY CustomerID, TransactionDate, Amount` means "restart the row numbering for each unique combination of these three values." Every combination that appears more than once will have a row with RowRank = 2, 3, etc. — those are the duplicates.

**COUNT(*) OVER for GroupSize**
Adding `COUNT(*) OVER (PARTITION BY CustomerID, TransactionDate, Amount)` as a window function computes the group size for every row in the result without a GROUP BY. This lets you filter (`WHERE GroupSize > 1`) and display the count on the same rows that show the detail.

**What constitutes a composite key is a business decision**
In this example, (CustomerID, TransactionDate, Amount) is the composite key. But maybe two charges of $250.00 on the same day are legitimate (morning and evening). The business must define what combination of columns should be unique — the SQL pattern is always the same, only the GROUP BY columns change.

## Severity
**Critical** — In payment and payroll systems, composite key duplicates cause double-charges or double-payments. In reporting, they inflate every metric that aggregates the affected rows.
