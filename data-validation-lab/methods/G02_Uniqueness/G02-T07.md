# G02-T07 — Uniqueness | Conditional Duplicate

## ID
G02-T07

## Group
2 — Uniqueness / Duplicates

## Type
Conditional Duplicate — Unique Within a Group or Partition

## Live Scenario
A telecoms company allows one active contract per customer per product type. A customer can have a Mobile contract AND a Broadband contract simultaneously — that is normal. But two active Mobile contracts for the same customer is a billing error. The uniqueness rule is conditional: unique on (CustomerID, ProductType) only when Status = 'Active'. Standard duplicate checks flag the two contracts as fine because CustomerID alone is not the key.

## The Question
> A record must be unique only within a specific subset — not across the whole table.
> **"Each employee can hold only one active role per department at a time. Find any employee who currently has more than one active record in the same department — a conditional uniqueness violation."**

## Table Reference
**Employees** — `schemas/04_Employees.csv`
**Orders** — `schemas/02_Orders.csv`

## Solution Query

```sql
-- Employees: only one active role per department
SELECT
    Department,
    EmployeeID,
    COUNT(*) AS ActiveRoleCount
FROM Employees
WHERE IsActive = 1       -- condition: only check among active records
GROUP BY Department, EmployeeID
HAVING COUNT(*) > 1      -- violation: more than one active record per (Dept, Employee)
ORDER BY Department, EmployeeID;

-- Full detail of violating employees
WITH ActiveRanked AS (
    SELECT *,
        ROW_NUMBER() OVER (
            PARTITION BY Department, EmployeeID
            ORDER BY HireDate DESC    -- most recent hire date = assumed current role
        ) AS RoleRank,
        COUNT(*) OVER (
            PARTITION BY Department, EmployeeID
        ) AS RoleCount
    FROM Employees
    WHERE IsActive = 1
)
SELECT
    EmployeeID,
    FullName,
    Department,
    HireDate,
    Salary,
    RoleRank,
    RoleCount,
    CASE WHEN RoleRank = 1 THEN 'Current role' ELSE 'DUPLICATE ACTIVE ROLE' END AS RoleStatus
FROM ActiveRanked
WHERE RoleCount > 1
ORDER BY Department, EmployeeID, RoleRank;

-- Orders: one pending order per customer per product (no duplicate pending orders)
SELECT
    CustomerID,
    ProductID,
    COUNT(*) AS PendingOrderCount,
    STRING_AGG(CAST(OrderID AS VARCHAR), ', ') AS OrderIDs
FROM Orders
WHERE Status = 'Pending'    -- condition: only among pending orders
GROUP BY CustomerID, ProductID
HAVING COUNT(*) > 1
ORDER BY PendingOrderCount DESC;
```

## Expected Output

**Active role violation:**
| EmployeeID | FullName | Department | RoleRank | RoleCount | RoleStatus |
|---|---|---|---|---|---|
| E008 | Marcus Lee | Sales | 1 | 2 | Current role |
| E008 | Marcus Lee | Sales | 2 | 2 | DUPLICATE ACTIVE ROLE |

## Explanation

**The WHERE clause defines the uniqueness scope**
Conditional uniqueness is uniqueness within a filtered subset of rows. The key step is adding `WHERE Status = 'Active'` (or `WHERE IsActive = 1`, or `WHERE EndDate IS NULL`) before the GROUP BY. This restricts the duplicate check to only the rows where the uniqueness rule applies. Rows outside the condition (historical records, cancelled contracts) are excluded from the check.

**Why this cannot be enforced with a simple UNIQUE constraint**
A database UNIQUE constraint applies across all rows unconditionally. To enforce conditional uniqueness at the database level, you need a filtered unique index:
```sql
CREATE UNIQUE INDEX UIX_Employee_ActiveDept
ON Employees (Department, EmployeeID)
WHERE IsActive = 1;
```
This index enforces the rule at insert/update time. The validation query is the equivalent check in plain SQL.

**PARTITION BY on the subset**
The CTE uses `PARTITION BY Department, EmployeeID` to rank within the conditional group. Only rows where `IsActive = 1` are in the CTE, so the partition only sees active records — the non-active history is invisible to the rank calculation.

## Severity
**High** — Conditional duplicates are business logic violations that look correct to schema-level checks. Two active contracts, two active roles, or two pending orders for the same item typically indicate a failed deduplication guard in the application layer.
