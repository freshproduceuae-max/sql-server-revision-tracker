# G02-T08 — Uniqueness | Cross-Table Duplicate

## ID
G02-T08

## Group
2 — Uniqueness / Duplicates

## Type
Cross-Table Duplicate — Same Record in Two Tables

## Live Scenario
A bank runs two systems: a legacy core banking platform and a new CRM. During a phased migration, some customers were created in both systems. The bank now has Customer ID 10042 in the legacy system and Customer ID 88201 in the CRM — both representing the same person with the same account number. Interest calculations, statement generation, and fraud alerts all run independently on both records. The customer receives duplicate statements and double fraud alerts.

## The Question
> The same real-world entity exists in two separate tables or two separate systems with different surrogate keys.
> **"We have a Customers table and an Employees table. Some people appear in both — they are customers who also work for us. Find everyone who appears in both tables using email as the match key, and flag whether their details are consistent between the two."**

## Table Reference
**Customers** — `schemas/01_Customers.csv`
**Employees** — `schemas/04_Employees.csv`

## Solution Query

```sql
-- Find entities present in both tables (using email as the natural key)
SELECT
    c.CustomerID,
    c.FirstName + ' ' + c.LastName      AS CustomerName,
    c.Email,
    e.EmployeeID,
    e.FullName                          AS EmployeeName,
    e.Email                             AS EmployeeEmail,
    -- Consistency check: does the name match across tables?
    CASE
        WHEN UPPER(LTRIM(RTRIM(c.FirstName + ' ' + c.LastName)))
           = UPPER(LTRIM(RTRIM(e.FullName)))
        THEN 'Names match'
        ELSE 'Name mismatch: Customer=[' + c.FirstName + ' ' + c.LastName
             + '] Employee=[' + e.FullName + ']'
    END AS NameConsistency
FROM Customers c
JOIN Employees e
    ON UPPER(LTRIM(RTRIM(c.Email))) = UPPER(LTRIM(RTRIM(e.Email)))
WHERE c.Email IS NOT NULL
  AND e.Email IS NOT NULL;

-- Count: how many cross-table matches exist?
SELECT
    COUNT(*) AS CrossTableDuplicates,
    SUM(CASE
        WHEN UPPER(LTRIM(RTRIM(c.FirstName + ' ' + c.LastName)))
           = UPPER(LTRIM(RTRIM(e.FullName)))
        THEN 1 ELSE 0
    END) AS ConsistentNames,
    SUM(CASE
        WHEN UPPER(LTRIM(RTRIM(c.FirstName + ' ' + c.LastName)))
          <> UPPER(LTRIM(RTRIM(e.FullName)))
        THEN 1 ELSE 0
    END) AS InconsistentNames
FROM Customers c
JOIN Employees e
    ON UPPER(LTRIM(RTRIM(c.Email))) = UPPER(LTRIM(RTRIM(e.Email)))
WHERE c.Email IS NOT NULL AND e.Email IS NOT NULL;

-- Also check DOB consistency for matched records
SELECT
    c.CustomerID,
    e.EmployeeID,
    c.Email,
    c.DOB       AS Customer_DOB,
    e.DOB       AS Employee_DOB,
    CASE WHEN c.DOB = e.DOB THEN 'DOB matches' ELSE 'DOB MISMATCH' END AS DOBConsistency
FROM Customers c
JOIN Employees e
    ON UPPER(LTRIM(RTRIM(c.Email))) = UPPER(LTRIM(RTRIM(e.Email)))
WHERE c.Email IS NOT NULL AND e.Email IS NOT NULL;
```

## Expected Output

| CustomerID | CustomerName | EmployeeID | EmployeeName | NameConsistency |
|---|---|---|---|---|
| 6 | Anjali Sharma | E003 | Anjali Sharma | Names match |
| 10 | Robert Blake | E010 | Robert J. Blake | Name mismatch: Customer=[Robert Blake] Employee=[Robert J. Blake] |

## Explanation

**UPPER + LTRIM + RTRIM before the JOIN**
Email comparison across systems is prone to case differences and leading/trailing spaces. Normalising both sides with `UPPER(LTRIM(RTRIM(...)))` before the JOIN prevents missed matches caused by purely cosmetic differences in how the two systems stored the same email.

**JOIN as a cross-table existence check**
An INNER JOIN between two tables on a natural key returns only rows that exist in BOTH tables — which is exactly the cross-table duplicate detection pattern. LEFT JOIN returns all from one side with NULLs where no match exists; INNER JOIN returns only the intersection.

**Consistency checks within the JOIN result**
Finding that a record exists in both tables is step one. Step two is checking whether the attributes are consistent. If the same person has a different date of birth in Customer vs Employee, one of the values is wrong — and it matters which system is the authoritative source.

**This is not always an error**
In the example above, an employee who is also a customer is a legitimate business case — it's expected. The cross-table check here answers "who appears in both, and are their attributes consistent?" In a migration context the same pattern answers "which records in the old system also exist in the new system?"

## Severity
**Medium to High** — Depends entirely on context. Cross-table duplicates in a migration represent work done correctly or incorrectly. In operational systems, they can cause duplicate billing, duplicate communications, or security boundary violations.
