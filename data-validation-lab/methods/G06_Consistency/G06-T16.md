# G06-T16 — Consistency | Encoding / Collation Mismatch

## ID
G06-T16

## Group
6 — Consistency

## Type
Encoding / Collation Mismatch — Same Value Stored in Inconsistent Case or Character Encoding

## Live Scenario
A global CRM system was migrated from Oracle (using AL32UTF8 encoding with case-sensitive collation) to SQL Server (using Latin1_General_CI_AS — case-insensitive, accent-sensitive). Email addresses stored as `'john.smith@example.com'` in Oracle were imported without normalisation. The SQL Server collation means `WHERE Email = 'John.Smith@Example.COM'` now returns these records — different from Oracle's behaviour. A deduplication process that relied on case-sensitive exact matching to detect duplicates now fails to find them: `'john.smith@example.com'` and `'John.Smith@EXAMPLE.COM'` are treated as the same record by SQL Server's CI collation but were separate in Oracle's CS collation, causing a merge of two different users' records.

## The Question
> Collation affects whether string comparisons are case-sensitive, accent-sensitive, or both. When data from multiple systems with different collations is combined, values that should be identical (email addresses, product codes) may be stored in inconsistent case — causing duplicates that are missed or matches that should not occur.
> **"Find all pairs of Customers who have the same Email address when compared case-insensitively but different case in the stored value — and find all Products where ProductCode exists in multiple case variants."**

## Table Reference
**Customers** — `schemas/01_Customers.csv`
**Products** — `schemas/03_Products.csv`
**Transactions** — `schemas/05_Transactions.csv`

## Solution Query

```sql
-- Step 1: Case-insensitive duplicate emails (same email, different case)
SELECT
    a.CustomerID AS Customer1ID,
    a.Email AS Email1,
    b.CustomerID AS Customer2ID,
    b.Email AS Email2,
    'DUPLICATE: Same email address, different case' AS Issue
FROM Customers a
JOIN Customers b
    ON  LOWER(a.Email) = LOWER(b.Email)  -- case-insensitive match
    AND a.CustomerID < b.CustomerID       -- avoid self-match and duplicate pairs
    AND a.Email <> b.Email COLLATE Latin1_General_CS_AS;  -- case-sensitive differs

-- Step 2: Normalise email case for audit — show stored value vs normalised form
SELECT
    CustomerID,
    Email AS StoredEmail,
    LOWER(Email) AS NormalisedEmail,
    CASE
        WHEN Email <> LOWER(Email) THEN 'Case normalisation needed'
        ELSE 'Already lowercase'
    END AS NormalisationStatus
FROM Customers
WHERE Email IS NOT NULL
  AND Email <> LOWER(Email);

-- Step 3: Product code case variants
SELECT
    UPPER(ProductCode) AS NormalisedCode,
    COUNT(*) AS VariantCount,
    STRING_AGG(ProductCode + ' (P' + CAST(ProductID AS VARCHAR) + ')', ', ')
        WITHIN GROUP (ORDER BY ProductCode) AS AllVariants,
    'Multiple case variants of same product code' AS Issue
FROM Products
WHERE ProductCode IS NOT NULL
GROUP BY UPPER(ProductCode)
HAVING COUNT(*) > 1;

-- Step 4: Detect accent/diacritic inconsistency (e.g., 'Müller' vs 'Muller')
-- SQL Server accent-sensitive (AS) collation treats these as different
SELECT
    a.CustomerID AS Customer1,
    a.LastName AS LastName1,
    b.CustomerID AS Customer2,
    b.LastName AS LastName2,
    'Potential accent variant — same name different encoding' AS Note
FROM Customers a
JOIN Customers b
    ON  a.LastName <> b.LastName                                    -- stored differently
    AND a.LastName COLLATE Latin1_General_CI_AI                     -- accent-insensitive match
        = b.LastName COLLATE Latin1_General_CI_AI
    AND a.CustomerID < b.CustomerID;

-- Step 5: Collation-aware comparison for IP addresses in Transactions
-- SourceIP should always be stored in lowercase for IPv6; uppercase for IPv4 is tolerable
-- but mixed case in the same table is a consistency issue
SELECT
    TransactionID,
    SourceIP,
    LOWER(SourceIP) AS NormalisedIP,
    CASE
        WHEN SourceIP <> LOWER(SourceIP) THEN 'Mixed case IP — normalise to lowercase'
        ELSE 'OK'
    END AS IPCaseCheck
FROM Transactions
WHERE SourceIP IS NOT NULL
  AND SourceIP <> LOWER(SourceIP);

-- Step 6: Summary of encoding/collation issues
SELECT 'Customers: emails needing case normalisation' AS Check, COUNT(*) AS Count
FROM Customers
WHERE Email IS NOT NULL AND Email <> LOWER(Email)

UNION ALL

SELECT 'Products: multi-case ProductCode variants', COUNT(*)
FROM (
    SELECT UPPER(ProductCode) AS NormCode
    FROM Products WHERE ProductCode IS NOT NULL
    GROUP BY UPPER(ProductCode)
    HAVING COUNT(*) > 1
) x

ORDER BY Count DESC;
```

## Expected Output

**Step 1 — Case-duplicate emails:**
| Customer1ID | Email1 | Customer2ID | Email2 | Issue |
|---|---|---|---|---|
| 3 | john.smith@example.com | 9 | John.Smith@EXAMPLE.com | DUPLICATE: Same email address, different case |

**Step 2 — Normalisation needed:**
| CustomerID | StoredEmail | NormalisedEmail | NormalisationStatus |
|---|---|---|---|
| 9 | John.Smith@EXAMPLE.com | john.smith@example.com | Case normalisation needed |
| 12 | ALICE@COMPANY.CO.UK | alice@company.co.uk | Case normalisation needed |

## Explanation

**Collation determines sort and compare behaviour**
SQL Server collation names encode their properties: `Latin1_General_CI_AS` means Case-Insensitive (CI), Accent-Sensitive (AS). `CS` = Case-Sensitive, `AI` = Accent-Insensitive. Joining two tables with different collations requires explicit `COLLATE` clauses, or SQL Server raises a collation conflict error.

**`LOWER()` for application-layer case normalisation**
Wrapping comparisons in `LOWER()` forces case-insensitive matching regardless of collation: `WHERE LOWER(a.Email) = LOWER(b.Email)`. This is reliable but bypasses index seeks (indexes are collation-aware; a LOWER() wrap typically forces a scan). For large tables, a persisted computed column `EmailLower AS LOWER(Email)` with its own index is more efficient.

**The `COLLATE` clause for explicit comparison**
`a.Email <> b.Email COLLATE Latin1_General_CS_AS` forces a case-sensitive comparison even on a CI database. This allows the query in Step 1 to confirm the stored values differ (case-sensitive) while LOWER() confirms they are the same logical value.

**Normalisation at ingest**
The correct fix is to normalise string values to a canonical form (e.g., lowercase emails, uppercase product codes) at data entry or ETL ingestion. Storing mixed-case versions that are meant to be the same value creates ongoing deduplication complexity.

## Severity
**Medium** — Collation mismatches cause false duplicates (CI collation misses records that CS considers distinct) or false negatives (CI collation incorrectly merges distinct records). In customer deduplication, this causes data loss — two distinct customers merged into one record. In product catalogues, case-variant codes create phantom items.
