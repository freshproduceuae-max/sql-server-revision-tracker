# G06-T05 — Consistency | Self-Referential / Circular Hierarchy

## ID
G06-T05

## Group
6 — Consistency

## Type
Self-Referential / Circular Hierarchy — An Entity References Itself or Creates a Cycle

## Live Scenario
An HR system stores the organisational hierarchy with a `ManagerID` self-referencing FK on the Employees table. During a reorg, an administrator incorrectly updates Manager E001 to report to E005, while E005 already reports to E001 — creating a cycle: E001 → E005 → E001. A recursive CTE that walks the org chart to generate a headcount report enters an infinite loop and times out after the `MAXRECURSION` limit. The report fails for three days before the cycle is detected. Additionally, an employee record is updated to set `ManagerID = EmployeeID` (an employee managing themselves), which a tree-walk also cannot handle.

## The Question
> Self-referential hierarchies (org charts, bill-of-materials, category trees) must be acyclic. A node that is its own ancestor creates an infinite loop in any recursive traversal. SQL can detect self-references (direct cycles of length 1) and indirect cycles using recursive CTEs with a cycle-break condition.
> **"Find all Employees where ManagerID equals EmployeeID (self-managing), and use a recursive CTE to detect cycles in the management hierarchy where an employee appears as their own ancestor."**

## Table Reference
**Employees** — `schemas/04_Employees.csv`

## Solution Query

```sql
-- Step 1: Direct self-reference (employee manages themselves)
SELECT
    EmployeeID,
    FullName,
    ManagerID,
    'SELF-REFERENCE: ManagerID = EmployeeID' AS Issue
FROM Employees
WHERE ManagerID = EmployeeID;

-- Step 2: Two-node cycle detection (A manages B, B manages A)
SELECT
    a.EmployeeID AS Employee_A,
    a.FullName AS Name_A,
    a.ManagerID AS A_ReportsTo,
    b.EmployeeID AS Employee_B,
    b.FullName AS Name_B,
    b.ManagerID AS B_ReportsTo,
    'CYCLE: A reports to B, B reports to A' AS Issue
FROM Employees a
JOIN Employees b
    ON  a.ManagerID = b.EmployeeID
    AND b.ManagerID = a.EmployeeID
    AND a.EmployeeID < b.EmployeeID;  -- avoid duplicate pair (A,B) and (B,A)

-- Step 3: General cycle detection using recursive CTE with ancestry tracking
WITH HierarchyCTE AS (
    -- Anchor: start from each employee
    SELECT
        EmployeeID AS RootID,
        EmployeeID AS CurrentID,
        ManagerID,
        CAST(EmployeeID AS VARCHAR(MAX)) AS AncestorPath,
        0 AS Depth,
        0 AS CycleDetected
    FROM Employees
    WHERE ManagerID IS NOT NULL

    UNION ALL

    -- Recursive: walk up the hierarchy
    SELECT
        h.RootID,
        e.EmployeeID,
        e.ManagerID,
        h.AncestorPath + ' -> ' + CAST(e.EmployeeID AS VARCHAR(10)),
        h.Depth + 1,
        CASE WHEN CHARINDEX(CAST(e.EmployeeID AS VARCHAR(10)), h.AncestorPath) > 0
             THEN 1 ELSE 0 END
    FROM HierarchyCTE h
    JOIN Employees e ON h.ManagerID = e.EmployeeID
    WHERE h.CycleDetected = 0
      AND h.Depth < 20  -- safety limit to prevent runaway recursion
)
SELECT DISTINCT
    RootID AS EmployeeWithCycle,
    AncestorPath AS CyclePath,
    Depth AS CycleDepth
FROM HierarchyCTE
WHERE CycleDetected = 1
ORDER BY RootID;

-- Step 4: Validate hierarchy root (should have exactly one root with ManagerID IS NULL)
SELECT
    COUNT(*) AS RootCount,
    STRING_AGG(CAST(EmployeeID AS VARCHAR), ', ') AS RootEmployeeIDs,
    CASE
        WHEN COUNT(*) = 0 THEN 'ERROR: No root found — all employees have a manager (cycle possible)'
        WHEN COUNT(*) = 1 THEN 'OK: Exactly one root'
        ELSE 'WARNING: Multiple roots — may indicate disconnected subtrees'
    END AS RootStatus
FROM Employees
WHERE ManagerID IS NULL;

-- Step 5: Maximum hierarchy depth and orphaned nodes
WITH HierarchyDepth AS (
    SELECT EmployeeID, ManagerID, 0 AS Depth
    FROM Employees WHERE ManagerID IS NULL
    UNION ALL
    SELECT e.EmployeeID, e.ManagerID, hd.Depth + 1
    FROM Employees e
    JOIN HierarchyDepth hd ON e.ManagerID = hd.EmployeeID
    WHERE hd.Depth < 20
)
SELECT
    MAX(Depth) AS MaxDepth,
    AVG(CAST(Depth AS FLOAT)) AS AvgDepth,
    COUNT(*) AS NodesReached,
    (SELECT COUNT(*) FROM Employees) AS TotalEmployees,
    (SELECT COUNT(*) FROM Employees) - COUNT(*) AS OrphanedNodes
FROM HierarchyDepth
OPTION (MAXRECURSION 100);
```

## Expected Output

**Step 1 — Self-reference:**
| EmployeeID | FullName | ManagerID | Issue |
|---|---|---|---|
| E009 | James Miller | E009 | SELF-REFERENCE: ManagerID = EmployeeID |

**Step 2 — Two-node cycle:**
| Employee_A | Name_A | Employee_B | Name_B | Issue |
|---|---|---|---|---|
| E001 | Sarah Johnson | E005 | Mark Davies | CYCLE: A reports to B, B reports to A |

**Step 4 — Root validation:**
| RootCount | RootEmployeeIDs | RootStatus |
|---|---|---|
| 1 | E001 | OK: Exactly one root |

## Explanation

**Self-reference is the simplest cycle**
`WHERE ManagerID = EmployeeID` catches depth-1 cycles in a single query. No recursion needed. This is the most common mistake (a data entry error where someone sets an employee as their own manager) and should be the first check run.

**Two-node cycles without recursion**
A self-join `ON a.ManagerID = b.EmployeeID AND b.ManagerID = a.EmployeeID` detects A→B→A cycles without recursion. The `AND a.EmployeeID < b.EmployeeID` condition eliminates duplicate pairs.

**CHARINDEX for path-based cycle detection**
The recursive CTE in Step 3 tracks the path walked (`AncestorPath`) as a string. If the current node's ID already appears in the path string, a cycle has been found. `CHARINDEX(id, path) > 0` performs the membership test. This is a breadth-first cycle detection and handles cycles of any length.

**MAXRECURSION safety limit**
Without the `Depth < 20` guard and `OPTION (MAXRECURSION n)`, a cycle causes infinite recursion until SQL Server hits its default limit (100). Always include a depth limit when writing recursive hierarchy CTEs, and set `MAXRECURSION` to a value appropriate for your hierarchy's maximum expected depth.

## Severity
**Critical** — Cycles in a self-referential hierarchy cause infinite loops in any recursive query. Org chart reports, bill-of-materials explosions, and category tree traversals all fail with a MAXRECURSION error. The failure is not graceful — the query times out and returns no data, which may be misinterpreted as "no results" rather than "query failed."
