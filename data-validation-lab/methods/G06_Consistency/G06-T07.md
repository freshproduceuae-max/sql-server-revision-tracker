# G06-T07 — Consistency | Aggregation Level Mismatch

## ID
G06-T07

## Group
6 — Consistency

## Type
Aggregation Level Mismatch — Row-Level Detail Mixed with Aggregate Values

## Live Scenario
A reporting database has two tables: `DailySales` (one row per store per day with aggregated totals) and `Transactions` (individual transaction records). A report joins them and sums `DailySales.DailyTotal + SUM(Transactions.Amount)` — mixing a pre-aggregated value with a row-level sum. On days where 50 transactions occurred, `DailySales.DailyTotal` already includes all 50, but `SUM(Transactions.Amount)` adds them again. The report double-counts every transaction, overstating revenue by 100%. The error goes undetected for a quarter because the numbers are large enough that the doubling is not immediately obvious, and the report has no independent total to reconcile against.

## The Question
> Mixing aggregated and non-aggregated data in the same calculation produces double-counting errors. SQL validation must verify that the grain (level of detail) is consistent across tables being joined and values being summed.
> **"Find all CustomerIDs where the sum of their individual Transactions does not match the TotalAmount on their Orders, and flag the discrepancy — demonstrating why aggregation level matters."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Transactions** — `schemas/05_Transactions.csv`
**Customers** — `schemas/01_Customers.csv`

## Solution Query

```sql
-- Step 1: Customer-level: Orders.TotalAmount vs aggregated Transactions
WITH CustomerOrderTotals AS (
    SELECT
        CustomerID,
        SUM(TotalAmount) AS SumOfOrderTotals,
        COUNT(*) AS OrderCount
    FROM Orders
    GROUP BY CustomerID
),
CustomerTxTotals AS (
    SELECT
        o.CustomerID,
        SUM(t.Amount) AS SumOfTransactions,
        COUNT(t.TransactionID) AS TxCount
    FROM Transactions t
    JOIN Orders o ON t.OrderID = o.OrderID
    GROUP BY o.CustomerID
)
SELECT
    cot.CustomerID,
    cot.SumOfOrderTotals,
    cot.OrderCount,
    ISNULL(ctt.SumOfTransactions, 0) AS SumOfTransactions,
    ISNULL(ctt.TxCount, 0) AS TxCount,
    ROUND(cot.SumOfOrderTotals - ISNULL(ctt.SumOfTransactions, 0), 2) AS Discrepancy,
    CASE
        WHEN ctt.CustomerID IS NULL
             THEN 'No transactions found for this customer'
        WHEN ABS(cot.SumOfOrderTotals - ctt.SumOfTransactions) < 0.01
             THEN 'Consistent'
        ELSE 'MISMATCH: Order totals ≠ Transaction totals'
    END AS AggregationConsistency
FROM CustomerOrderTotals cot
LEFT JOIN CustomerTxTotals ctt ON cot.CustomerID = ctt.CustomerID
WHERE ABS(cot.SumOfOrderTotals - ISNULL(ctt.SumOfTransactions, 0)) > 0.01
   OR ctt.CustomerID IS NULL
ORDER BY ABS(cot.SumOfOrderTotals - ISNULL(ctt.SumOfTransactions, 0)) DESC;

-- Step 2: Demonstrate the double-counting error pattern
-- WRONG: Summing Orders.TotalAmount after joining to Transactions (fan-out)
SELECT
    'WRONG — fan-out double-count' AS Method,
    o.OrderID,
    o.TotalAmount,
    COUNT(t.TransactionID) AS TxCount,
    SUM(o.TotalAmount) AS WrongSum  -- TotalAmount counted once per transaction row
FROM Orders o
LEFT JOIN Transactions t ON o.OrderID = t.OrderID
GROUP BY o.OrderID, o.TotalAmount
ORDER BY o.OrderID;

-- CORRECT: Aggregate transactions separately, then join
SELECT
    'CORRECT — aggregate first, then join' AS Method,
    o.OrderID,
    o.TotalAmount AS OrderTotal,
    ISNULL(tt.TxSum, 0) AS TxTotal
FROM Orders o
LEFT JOIN (
    SELECT OrderID, SUM(Amount) AS TxSum FROM Transactions GROUP BY OrderID
) tt ON o.OrderID = tt.OrderID
ORDER BY o.OrderID;

-- Step 3: Grain check — verify Transactions are at correct grain for joining
-- Each transaction should relate to exactly one order
SELECT
    TransactionID,
    COUNT(*) AS RowCount,
    'Duplicate TransactionID detected' AS Issue
FROM Transactions
GROUP BY TransactionID
HAVING COUNT(*) > 1;

-- Step 4: Year/month aggregation — Orders vs Transactions (monthly reconciliation)
SELECT
    YEAR(o.OrderDate) AS OrderYear,
    MONTH(o.OrderDate) AS OrderMonth,
    SUM(o.TotalAmount) AS OrderHeaderTotal,
    SUM(t.Amount) AS TransactionTotal,
    COUNT(DISTINCT o.OrderID) AS OrderCount,
    COUNT(t.TransactionID) AS TxCount,
    ROUND(SUM(o.TotalAmount) - SUM(t.Amount), 2) AS MonthlyGap,
    CASE
        WHEN ABS(SUM(o.TotalAmount) - SUM(t.Amount)) < 1
             THEN 'Reconciled'
        ELSE 'RECONCILIATION GAP'
    END AS ReconciliationStatus
FROM Orders o
LEFT JOIN Transactions t ON o.OrderID = t.OrderID
GROUP BY YEAR(o.OrderDate), MONTH(o.OrderDate)
ORDER BY OrderYear, OrderMonth;
```

## Explanation

**Fan-out: the double-counting trap**
When a parent table (Orders) is joined to a child table (Transactions), each Order row is repeated for every matching Transaction. If you then `SUM(Orders.TotalAmount)` in that joined result, you sum the same order total N times (once per transaction). This is a fan-out multiplication error — the single most common aggregation mistake in SQL.

**The fix: aggregate the child table first**
Resolve fan-out by aggregating the child table to the same grain as the parent before joining: `(SELECT OrderID, SUM(Amount) AS TxSum FROM Transactions GROUP BY OrderID) AS tt`. This produces one row per order and can be safely joined to Orders without fan-out.

**Grain consistency**
Every table in a query should be at the same grain (level of detail) or aggregated to that grain. Mixing grain levels — one table at order grain, another at transaction grain — requires explicit aggregation before the join, not after.

**Reconciliation as aggregation validation**
Step 4 performs a monthly financial reconciliation: Orders total vs Transactions total should match. Gaps indicate missing transactions, double-billed orders, or data import failures. This monthly check is the standard pattern used in financial close processes.

## Severity
**High** — Aggregation-level mismatches cause double-counting of revenue, costs, or transaction volumes. The error is particularly dangerous because the result looks numerically plausible — it's just the wrong number by a deterministic multiple. Double-counted revenue figures mislead financial decisions and can cause regulatory filing errors.
