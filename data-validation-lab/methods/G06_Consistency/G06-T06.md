# G06-T06 — Consistency | Temporal Sequence Violation

## ID
G06-T06

## Group
6 — Consistency

## Type
Temporal Sequence Violation — Events Out of Expected Chronological Order

## Live Scenario
An order fulfilment system records five lifecycle events per order: `OrderDate`, `PickDate` (when warehouse staff picked the items), `PackDate`, `DispatchDate`, and `DeliveryDate`. The required sequence is: OrderDate < PickDate < PackDate < DispatchDate < DeliveryDate. A warehouse management system integration uses batch uploads with timestamps rounded to midnight, causing `PickDate` and `PackDate` to be set to the same midnight timestamp — meaning `PickDate = PackDate`, which violates the "packed after picked" constraint. Additionally, a timezone conversion error causes 11 records to have `DispatchDate` after `DeliveryDate` — physically impossible for ground shipping.

## The Question
> When a process produces multiple timestamped events, those events must occur in the correct chronological order. Violations indicate either data entry errors, system clock issues, or timezone conversion bugs. SQL detects sequence violations by comparing adjacent event dates in the expected order.
> **"Find all Orders where the event sequence OrderDate → DeliveryDate is violated — where any later event precedes an earlier one."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Transactions** — `schemas/05_Transactions.csv`

## Solution Query

```sql
-- Step 1: Detect all out-of-sequence date pairs in Orders
SELECT
    OrderID,
    CustomerID,
    OrderDate,
    DeliveryDate,
    -- Check each adjacent pair in the expected sequence
    CASE
        WHEN DeliveryDate < OrderDate
             THEN 'VIOLATION: DeliveryDate before OrderDate'
        WHEN DeliveryDate = OrderDate
             THEN 'WARNING: Delivered same day as ordered — verify'
        ELSE 'Sequence OK'
    END AS SequenceCheck,
    DATEDIFF(DAY, OrderDate, DeliveryDate) AS DaysBetween
FROM Orders
WHERE DeliveryDate IS NOT NULL
  AND DeliveryDate < OrderDate
ORDER BY DATEDIFF(DAY, DeliveryDate, OrderDate) DESC;

-- Step 2: Transaction sequence vs Order date
-- A payment transaction should not precede its order
SELECT
    t.TransactionID,
    t.OrderID,
    o.OrderDate,
    t.TransactionDate,
    DATEDIFF(DAY, t.TransactionDate, o.OrderDate) AS DaysBeforeOrder,
    CASE
        WHEN t.TransactionDate < o.OrderDate
             THEN 'VIOLATION: Transaction predates its Order'
        WHEN t.TransactionDate > DATEADD(DAY, 90, o.OrderDate)
             THEN 'WARNING: Transaction > 90 days after Order'
        ELSE 'Sequence OK'
    END AS SequenceStatus
FROM Transactions t
JOIN Orders o ON t.OrderID = o.OrderID
WHERE t.TransactionDate < o.OrderDate
   OR t.TransactionDate > DATEADD(DAY, 90, o.OrderDate);

-- Step 3: Multi-event sequence using LEAD/LAG to check adjacent events
-- Simulated multi-stage event check using available date columns
WITH OrderSequence AS (
    SELECT
        OrderID,
        OrderDate AS Event1,
        DeliveryDate AS Event2,
        DATEDIFF(DAY, OrderDate, DeliveryDate) AS Lag_1_to_2
    FROM Orders
    WHERE OrderDate IS NOT NULL AND DeliveryDate IS NOT NULL
)
SELECT
    OrderID,
    Event1 AS OrderDate,
    Event2 AS DeliveryDate,
    Lag_1_to_2 AS DaysToDeliver,
    CASE
        WHEN Lag_1_to_2 < 0  THEN 'VIOLATION: Event2 before Event1'
        WHEN Lag_1_to_2 = 0  THEN 'WARNING: Events on same day'
        WHEN Lag_1_to_2 > 30 THEN 'WARNING: >30 days between events'
        ELSE 'Normal sequence'
    END AS SequenceFlag
FROM OrderSequence
WHERE Lag_1_to_2 < 0 OR Lag_1_to_2 = 0
ORDER BY Lag_1_to_2;

-- Step 4: Per-customer order sequence (orders should not have earlier OrderDate than a previous delivery)
WITH CustomerOrders AS (
    SELECT
        CustomerID,
        OrderID,
        OrderDate,
        DeliveryDate,
        LAG(DeliveryDate) OVER (PARTITION BY CustomerID ORDER BY OrderDate) AS PrevDeliveryDate
    FROM Orders
    WHERE OrderDate IS NOT NULL
)
SELECT
    CustomerID,
    OrderID,
    OrderDate,
    PrevDeliveryDate,
    CASE
        WHEN PrevDeliveryDate IS NULL THEN 'First order — no previous delivery'
        WHEN OrderDate < PrevDeliveryDate
             THEN 'OVERLAP: New order placed before previous order was delivered'
        ELSE 'Sequential — new order after previous delivery'
    END AS CustomerSequenceCheck
FROM CustomerOrders
WHERE PrevDeliveryDate IS NOT NULL
  AND OrderDate < PrevDeliveryDate;

-- Step 5: Summary of sequence violations
SELECT
    'DeliveryDate before OrderDate' AS ViolationType,
    COUNT(*) AS Count
FROM Orders
WHERE DeliveryDate IS NOT NULL AND DeliveryDate < OrderDate

UNION ALL

SELECT
    'Transaction before Order',
    COUNT(*)
FROM Transactions t
JOIN Orders o ON t.OrderID = o.OrderID
WHERE t.TransactionDate < o.OrderDate

ORDER BY Count DESC;
```

## Explanation

**The expected sequence as a chain of constraints**
Each stage must occur after the previous: `t1 < t2 < t3 < … < tn`. Each adjacent pair forms its own constraint: `t2 > t1`, `t3 > t2`, etc. Checking all pairs requires either multiple WHERE conditions or a CASE expression that evaluates each pair individually.

**DATEDIFF sign for direction**
`DATEDIFF(DAY, earlier, later)` returns a positive number if `later` is indeed after `earlier`. A negative result means the sequence is inverted. Using `DATEDIFF(DAY, OrderDate, DeliveryDate)` as the key metric makes violations visible as negative numbers.

**LAG for consecutive-record sequence validation**
`LAG(DeliveryDate) OVER (PARTITION BY CustomerID ORDER BY OrderDate)` retrieves the previous order's delivery date for the same customer. Comparing `OrderDate < PrevDeliveryDate` catches overlapping orders — a customer placing a new order before a previous order has been delivered (valid for backorders, suspicious for sequential shipping).

**Timezone errors as sequence violation root cause**
When timestamps from multiple systems are stored without timezone normalisation, a "later" event in local time can have an earlier UTC timestamp. Always convert to a single timezone (UTC) before storing timestamps that will be compared across tables or systems.

## Severity
**High** — Sequence violations break audit trails, SLA calculations, and process analytics. A `DeliveryDate` before `OrderDate` causes negative lead-time metrics, which corrupt performance dashboards. In regulated industries (financial trade lifecycle, clinical trials), out-of-sequence event records may cause regulatory reporting failures.
