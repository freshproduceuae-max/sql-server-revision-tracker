# G06-T13 — Consistency | Parent-Child Attribute Agreement

## ID
G06-T13

## Group
6 — Consistency

## Type
Parent-Child Attribute Agreement — Child Record Attributes Must Match Parent

## Live Scenario
An insurance policy system stores policies in a `Policies` table with a `PolicyType` column ('Auto', 'Home', 'Life'). Each policy has child records in a `PolicyClaims` table, which also has a `ClaimType` column that must match the parent's `PolicyType` — you cannot make an 'Auto' claim on a 'Home' policy. A data migration that merged two regional databases failed to remap `ClaimType` values, leaving 312 claims with mismatched types. The claims processing system uses `PolicyClaims.ClaimType` directly, routing auto-type claims to the auto-claims team even when the underlying policy is a Home policy. The wrong team receives and partially processes 47 claims before the mismatch is caught.

## The Question
> Child records that repeat an attribute from their parent must agree with the parent's value. When a child table stores a denormalised copy of a parent attribute, any discrepancy between the copy and the master value is a consistency violation.
> **"Find all Orders where the ProductID references a Product that is inactive (IsActive = 0) — the order's product must agree with the product's current status — and find employee records whose Department does not match their Manager's Department."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Products** — `schemas/03_Products.csv`
**Employees** — `schemas/04_Employees.csv`

## Solution Query

```sql
-- Step 1: Orders referencing inactive products
-- Business rule: an order can only be placed for an active product
SELECT
    o.OrderID,
    o.CustomerID,
    o.ProductID,
    o.OrderDate,
    o.TotalAmount,
    p.ProductName,
    p.IsActive,
    p.Price AS CurrentPrice,
    CASE
        WHEN p.ProductID IS NULL   THEN 'ORPHAN: Product not found'
        WHEN p.IsActive = 0        THEN 'VIOLATION: Order references inactive product'
        ELSE 'Product active — OK'
    END AS ProductConsistency
FROM Orders o
LEFT JOIN Products p ON o.ProductID = p.ProductID
WHERE p.ProductID IS NULL
   OR p.IsActive = 0;

-- Step 2: Employee department vs manager's department
-- Business rule: an employee's department should match their manager's department
-- (except for cross-department manager scenarios — flag for review)
SELECT
    e.EmployeeID,
    e.FullName AS EmployeeName,
    e.Department AS EmployeeDept,
    e.ManagerID,
    m.FullName AS ManagerName,
    m.Department AS ManagerDept,
    CASE
        WHEN e.ManagerID IS NULL         THEN 'No manager (root node)'
        WHEN m.EmployeeID IS NULL        THEN 'Manager not found'
        WHEN e.Department = m.Department THEN 'Department matches manager — OK'
        ELSE 'MISMATCH: Employee dept ≠ Manager dept'
    END AS DeptConsistency
FROM Employees e
LEFT JOIN Employees m ON e.ManagerID = m.EmployeeID
WHERE m.EmployeeID IS NOT NULL
  AND e.Department <> m.Department;

-- Step 3: Customer country consistency — active customers should have valid country
SELECT
    o.OrderID,
    o.CustomerID,
    c.Country AS CustomerCountry,
    c.IsActive AS CustomerIsActive,
    CASE
        WHEN c.CustomerID IS NULL  THEN 'Customer not found'
        WHEN c.IsActive = 0        THEN 'WARNING: Order placed by inactive customer'
        WHEN c.Country IS NULL     THEN 'WARNING: Customer has no country on file'
        ELSE 'OK'
    END AS CustomerConsistency
FROM Orders o
LEFT JOIN Customers c ON o.CustomerID = c.CustomerID
WHERE c.CustomerID IS NULL
   OR c.IsActive = 0
   OR c.Country IS NULL;

-- Step 4: Product VAT rate consistency — all products in same category should have same VAT rate
SELECT
    p1.ProductID AS Product1,
    p1.ProductName AS Name1,
    p1.VATRate AS VAT1,
    p2.ProductID AS Product2,
    p2.ProductName AS Name2,
    p2.VATRate AS VAT2,
    'Same product category but different VAT rates' AS Issue
FROM Products p1
JOIN Products p2
    ON  LEFT(p1.ProductCode, 3) = LEFT(p2.ProductCode, 3)  -- same category prefix
    AND p1.ProductID < p2.ProductID                          -- avoid self and duplicate pairs
    AND p1.VATRate <> p2.VATRate;

-- Step 5: Summary of parent-child attribute violations
SELECT 'Orders → inactive Products' AS Check, COUNT(*) AS ViolationCount
FROM Orders o
JOIN Products p ON o.ProductID = p.ProductID
WHERE p.IsActive = 0

UNION ALL

SELECT 'Orders → inactive Customers', COUNT(*)
FROM Orders o
JOIN Customers c ON o.CustomerID = c.CustomerID
WHERE c.IsActive = 0

UNION ALL

SELECT 'Employees: dept ≠ manager dept', COUNT(*)
FROM Employees e
JOIN Employees m ON e.ManagerID = m.EmployeeID
WHERE e.Department <> m.Department

ORDER BY ViolationCount DESC;
```

## Explanation

**Denormalised copies vs derived values**
When a child table repeats an attribute from its parent (e.g., `Orders.ProductCategory` copied from `Products.Category`), both must agree. The parent table is the master; the child's copy is the denormalised replica. Any difference indicates the replica was not updated when the master changed.

**Active status propagation**
If a product is marked inactive, its parent-child implication is that no new orders should reference it, and existing pending orders may need re-routing or cancellation. The validation in Step 1 surfaces orders placed while the product was already inactive — or placed correctly but the product was subsequently inactivated.

**Department hierarchy vs reporting line**
Step 2 checks whether an employee's department matches their manager's department. Cross-department reporting lines are sometimes legitimate (a finance business partner reporting to a department head outside Finance). The query flags all such cases for human review rather than declaring them all violations.

**JOIN vs LEFT JOIN for parent-child checks**
When checking attribute agreement (parent and child must both exist), an INNER JOIN is sufficient. When also checking for orphan records (child exists but parent does not), use LEFT JOIN with `WHERE parent.pk IS NULL`. Steps 1 and 3 use LEFT JOIN to catch both cases.

## Severity
**Medium** — Parent-child attribute mismatches cause records to be routed, classified, or processed incorrectly. Orders on inactive products may ship items that have been recalled or discontinued. In insurance, claims routed to the wrong team based on a mismatched type cause processing delays, customer complaints, and potential regulatory violations.
