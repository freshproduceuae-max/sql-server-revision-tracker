# G06-T09 — Consistency | Sign / Direction Inconsistency

## ID
G06-T09

## Group
6 — Consistency

## Type
Sign / Direction Inconsistency — Positive/Negative Sign Violates Business Meaning

## Live Scenario
A payments platform records both debits and credits in the same `Transactions` table. The business convention is: payments TO the customer (refunds, payouts) are stored as positive amounts; payments FROM the customer (purchases) are also stored as positive amounts with a `TransactionType = 'Debit'` flag. A developer builds a balance calculation as `SUM(Amount)` without considering TransactionType — summing all transactions as if they were all positive adds refunds and purchases together instead of netting them. A customer with £500 in purchases and a £200 refund shows a balance of £700 (500 + 200) instead of the correct £300 (500 - 200). The error goes undetected because all individual amounts are positive and no row looks wrong in isolation.

## The Question
> When a field can represent both positive and negative values, the sign must be consistent with the semantic meaning. Charges should always be positive (or always negative), credits the opposite. A mix of signs for the same transaction type, or incorrect sign application relative to business rules, corrupts any calculation using those values.
> **"Find all Transactions where Amount is negative (when the business rule requires positive amounts), and demonstrate how sign inconsistency corrupts balance calculations."**

## Table Reference
**Transactions** — `schemas/05_Transactions.csv`
**Orders** — `schemas/02_Orders.csv`
**Products** — `schemas/03_Products.csv`

## Solution Query

```sql
-- Step 1: Find negative amounts where positive is required
SELECT
    TransactionID,
    OrderID,
    Amount,
    Currency,
    TransactionDate,
    'VIOLATION: Amount is negative — business rule requires positive values' AS Issue
FROM Transactions
WHERE Amount < 0;

-- Step 2: Find zero amounts (debatable but usually incorrect)
SELECT
    TransactionID,
    OrderID,
    Amount,
    'WARNING: Zero-value transaction — likely a data entry or processing error' AS Note
FROM Transactions
WHERE Amount = 0;

-- Step 3: Product price sign check — prices must be positive
SELECT
    ProductID,
    ProductName,
    Price,
    DiscountPercent,
    CASE
        WHEN Price < 0        THEN 'VIOLATION: Negative price'
        WHEN Price = 0        THEN 'WARNING: Zero price — free item or error?'
        WHEN DiscountPercent < 0  THEN 'VIOLATION: Negative discount (surcharge?) — needs review'
        WHEN DiscountPercent > 100 THEN 'VIOLATION: Discount > 100% — impossible'
        ELSE 'OK'
    END AS SignCheck
FROM Products
WHERE Price < 0
   OR Price = 0
   OR DiscountPercent < 0
   OR DiscountPercent > 100;

-- Step 4: Demonstrate sign impact on balance calculations
-- Correct pattern: use signed amounts based on transaction type
-- The Amount column should already encode direction via sign
SELECT
    o.CustomerID,
    SUM(CASE WHEN t.Amount > 0 THEN t.Amount ELSE 0 END) AS TotalCharges,
    SUM(CASE WHEN t.Amount < 0 THEN ABS(t.Amount) ELSE 0 END) AS TotalRefunds,
    SUM(t.Amount) AS NetBalance,  -- correct only if negative = refund, positive = charge
    COUNT(*) AS TxCount
FROM Transactions t
JOIN Orders o ON t.OrderID = o.OrderID
GROUP BY o.CustomerID
ORDER BY NetBalance DESC;

-- Step 5: SalesTargets — commission rate must be between 0 and 100
SELECT
    TargetID,
    SalespersonID,
    TargetAmount,
    CommissionRate,
    CASE
        WHEN CommissionRate < 0   THEN 'VIOLATION: Negative commission rate'
        WHEN CommissionRate > 100 THEN 'VIOLATION: Commission rate > 100%'
        WHEN CommissionRate = 0   THEN 'WARNING: Zero commission rate — intentional?'
        ELSE 'Valid'
    END AS CommissionSignCheck
FROM SalesTargets
WHERE CommissionRate < 0
   OR CommissionRate > 100;

-- Step 6: Sign consistency audit summary
SELECT 'Transactions with negative Amount' AS Check, COUNT(*) AS Count
FROM Transactions WHERE Amount < 0
UNION ALL
SELECT 'Transactions with zero Amount', COUNT(*)
FROM Transactions WHERE Amount = 0
UNION ALL
SELECT 'Products with negative Price', COUNT(*)
FROM Products WHERE Price < 0
UNION ALL
SELECT 'Products with DiscountPercent out of 0-100', COUNT(*)
FROM Products WHERE DiscountPercent < 0 OR DiscountPercent > 100
ORDER BY Count DESC;
```

## Explanation

**Convention: sign-per-row vs type-per-column**
Two design patterns handle debits and credits. Pattern 1: all amounts are positive, and a `Type` column ('Debit'/'Credit') provides direction. Pattern 2: amounts carry sign — positive for credits, negative for debits (or vice versa). Both work, but they require different aggregation logic. Mixing conventions within the same table is the most dangerous scenario.

**The silent corruption of unsigned sums**
`SUM(Amount)` on a table where all amounts are positive produces a gross total (debits + credits). `SUM(Amount)` on a table where amounts are signed produces a net total (credits - debits). The query looks identical; the result is completely different. The business rule for what sign means must be documented and consistently applied.

**Zero-value transactions**
A transaction of £0.00 is usually an error (a void, a failed record, a test entry) but may be legitimate (a £0 free-tier subscription renewal). Zero amounts corrupt average calculations (`AVG(Amount)` is pulled toward zero) without contributing to totals.

**Compound rules**
Step 3 checks both sign (price < 0) and magnitude (discount > 100%). These are separate violations with different causes: a negative price is usually a sign error; a discount > 100% is usually a percentage/decimal error (110 entered instead of 10 for 10% discount).

## Severity
**High** — Sign inconsistencies silently corrupt balance calculations, P&L reports, and commission computations. The error is invisible at the row level — each individual amount may look plausible — but aggregations produce systematically wrong totals. Financial systems with incorrect sign handling can overstate or understate revenue, liabilities, and net positions.
