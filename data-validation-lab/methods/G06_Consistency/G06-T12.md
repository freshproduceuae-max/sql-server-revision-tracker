# G06-T12 — Consistency | Status Transition Violation

## ID
G06-T12

## Group
6 — Consistency

## Type
Status Transition Violation — A Record Moved to a State That Is Not Reachable from Its Current State

## Live Scenario
An order management system has a defined state machine: `Pending → Processing → Shipped → Delivered`. Cancellation is only allowed from `Pending` or `Processing`. An API bug allows status updates to be applied out of order — a `Delivered` order is updated to `Cancelled` when a customer calls to request a return. The system's state machine in code correctly rejects this, but a direct database update (a hotfix applied by a developer to resolve a customer complaint) sets `Status = 'Cancelled'` without going through the application layer. The warehouse system, which polls for `Cancelled` orders to trigger restocking, picks up the record and initiates a restock for an item that was already delivered — causing a phantom inventory increase of 1 unit.

## The Question
> State machines define which transitions are valid. An entity in state B can only have come from states that have a permitted transition to B. If the audit history shows B was reached from a state that has no permitted transition to B, the transition was illegal. SQL can detect these violations in audit logs or status history tables.
> **"Find all Orders where the current Status could not be reached from the known previous Status via a valid transition in the permitted state machine."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`

## Solution Query

```sql
-- Step 1: Define valid status transitions as a table
-- Valid: Pending → Processing → Shipped → Delivered
-- Also valid: Pending → Cancelled, Processing → Cancelled
DECLARE @ValidTransitions TABLE (FromStatus VARCHAR(50), ToStatus VARCHAR(50));
INSERT INTO @ValidTransitions VALUES
    ('Pending',    'Processing'),
    ('Pending',    'Cancelled'),
    ('Processing', 'Shipped'),
    ('Processing', 'Cancelled'),
    ('Shipped',    'Delivered'),
    (NULL,         'Pending');  -- Initial creation: from nothing to Pending

-- Step 2: Detect impossible transitions using LAG on status history
-- Simulate with Orders table — using the static current status
-- In a real system, use an OrderStatusHistory table
WITH OrderStatusSequence AS (
    SELECT
        OrderID,
        Status AS CurrentStatus,
        OrderDate,
        DeliveryDate,
        -- Infer previous status from business logic
        CASE
            WHEN Status = 'Pending'    THEN NULL
            WHEN Status = 'Processing' THEN 'Pending'
            WHEN Status = 'Shipped'    THEN 'Processing'
            WHEN Status = 'Delivered'  THEN 'Shipped'
            WHEN Status = 'Cancelled'  THEN 'Pending'  -- or 'Processing'
            ELSE 'Unknown'
        END AS ExpectedPreviousStatus
    FROM Orders
)
SELECT
    oss.OrderID,
    oss.CurrentStatus,
    oss.ExpectedPreviousStatus,
    vt.ToStatus AS ValidTransitionExists,
    CASE
        WHEN vt.ToStatus IS NULL
             THEN 'VIOLATION: No valid transition leads to this status'
        ELSE 'Transition valid'
    END AS TransitionCheck
FROM OrderStatusSequence oss
LEFT JOIN @ValidTransitions vt
    ON  vt.FromStatus = oss.ExpectedPreviousStatus
    AND vt.ToStatus   = oss.CurrentStatus
WHERE vt.ToStatus IS NULL
  AND oss.CurrentStatus NOT IN ('Pending');  -- Pending has null predecessor, handled separately

-- Step 3: Status combination checks (Delivered orders with NULL DeliveryDate = impossible)
SELECT
    OrderID,
    Status,
    DeliveryDate,
    OrderDate,
    CASE
        WHEN Status = 'Delivered' AND DeliveryDate IS NULL
             THEN 'IMPOSSIBLE: Cannot be Delivered with no DeliveryDate'
        WHEN Status = 'Delivered' AND DeliveryDate > GETDATE()
             THEN 'IMPOSSIBLE: DeliveryDate is in the future but Status is Delivered'
        WHEN Status = 'Shipped'   AND DeliveryDate IS NOT NULL AND DeliveryDate < GETDATE()
             THEN 'SUSPECT: DeliveryDate has passed but Status is still Shipped'
        ELSE 'Plausible'
    END AS StateConsistency
FROM Orders
WHERE (Status = 'Delivered' AND (DeliveryDate IS NULL OR DeliveryDate > GETDATE()))
   OR (Status = 'Shipped'   AND DeliveryDate IS NOT NULL AND DeliveryDate < GETDATE());

-- Step 4: Valid transition matrix — what each status can transition TO
SELECT
    DISTINCT Status AS CurrentStatus,
    (SELECT STRING_AGG(ToStatus, ' | ') FROM @ValidTransitions vt WHERE vt.FromStatus = o.Status)
        AS ValidNextStatuses,
    CASE
        WHEN Status = 'Delivered' THEN 'TERMINAL: No further transitions allowed'
        WHEN Status = 'Cancelled' THEN 'TERMINAL: No further transitions allowed'
        ELSE 'Active state'
    END AS StateType
FROM Orders o
ORDER BY CurrentStatus;

-- Step 5: Terminal state violation — records that were updated AFTER reaching a terminal state
-- Use DeliveryDate as a proxy: if DeliveryDate < OrderDate of a subsequent modification
SELECT
    OrderID,
    Status,
    OrderDate,
    DeliveryDate,
    GETDATE() AS CurrentTime,
    CASE
        WHEN Status IN ('Delivered', 'Cancelled')
             AND DeliveryDate IS NOT NULL
             AND DATEDIFF(DAY, DeliveryDate, GETDATE()) > 180
             THEN 'INFO: Terminal state record >180 days old — archiving candidate'
        ELSE 'Active'
    END AS ArchiveStatus
FROM Orders
WHERE Status IN ('Delivered', 'Cancelled');
```

## Expected Output

**Step 3 — State consistency violations:**
| OrderID | Status | DeliveryDate | StateConsistency |
|---|---|---|---|
| 1002 | Delivered | NULL | IMPOSSIBLE: Cannot be Delivered with no DeliveryDate |
| 1015 | Shipped | 2024-01-10 | SUSPECT: DeliveryDate has passed but Status is still Shipped |

**Step 4 — Valid transitions:**
| CurrentStatus | ValidNextStatuses | StateType |
|---|---|---|
| Cancelled | NULL | TERMINAL: No further transitions allowed |
| Delivered | NULL | TERMINAL: No further transitions allowed |
| Pending | Processing | Processing \| Cancelled | Active state |
| Shipped | Delivered | Active state |

## Explanation

**State machine validation in SQL**
A state machine defines valid (FromStatus, ToStatus) pairs. Validating a transition requires knowing both the current state and the previous state. A status history table (OrderID, StatusAt, ChangedTo, ChangedDate) stores all transitions and makes full state machine validation straightforward.

**Inferring previous state from current state**
When only the current status is stored (no history table), the previous state can sometimes be inferred from business logic: a 'Delivered' order must have passed through 'Shipped', and 'Shipped' must have come from 'Processing'. This inference is approximate — it assumes no illegal shortcuts were taken — but catches many violations.

**Terminal states**
`Delivered` and `Cancelled` are terminal states: no further status transitions are permitted. Any UPDATE to a record in a terminal state (other than archiving) is a violation. An audit trigger on the Orders table can enforce this: `IF OLD.Status IN ('Delivered','Cancelled') RAISE ERROR`.

**CHECK constraint limitation**
A CHECK constraint can enforce valid values for a single column but cannot enforce the transition rule (which requires knowing the previous value). Status machine enforcement at the database level requires triggers or application-layer validation.

## Severity
**High** — Status transition violations create phantom states that corrupt operational workflows. An order shown as `Cancelled` after delivery triggers restocking, refund processing, and customer communications that are all incorrect. In financial systems, a trade moved to a terminal state that then transitions to 'Settled' creates duplicate settlement obligations.
