# G06-T15 — Consistency | Cascade / Soft-Delete Orphan

## ID
G06-T15

## Group
6 — Consistency

## Type
Cascade / Soft-Delete Orphan — Child Records Active After Parent Is Deleted or Deactivated

## Live Scenario
A SaaS platform soft-deletes customers by setting `IsActive = 0` rather than physically deleting rows — preserving historical records. A compliance policy requires that when a customer is deactivated (e.g., GDPR right-to-erasure request), all their associated open orders must also be cancelled. The automated deactivation process has a bug: it sets `Customers.IsActive = 0` but fails to cancel orders in a `Pending` or `Processing` state. Three months later, the fulfilment system ships 14 orders to deactivated (and in several cases, GDPR-erased) customers — dispatching goods to addresses that may no longer exist and processing payments against accounts that should be closed.

## The Question
> When a parent record is soft-deleted (marked inactive/deleted without physical removal), child records that remain "active" become orphaned from a business perspective. They reference an inactive parent and may continue to be processed when they should have been deactivated or cancelled.
> **"Find all Orders in active statuses (Pending, Processing, Shipped) that belong to Customers where IsActive = 0, and find all SalesTargets that belong to Employees who have a TerminationDate in the past."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Customers** — `schemas/01_Customers.csv`
**SalesTargets** — `schemas/06_SalesTargets.csv`
**Employees** — `schemas/04_Employees.csv`

## Solution Query

```sql
-- Step 1: Active orders belonging to inactive (soft-deleted) customers
SELECT
    o.OrderID,
    o.CustomerID,
    o.OrderDate,
    o.Status,
    o.TotalAmount,
    c.FirstName,
    c.LastName,
    c.IsActive AS CustomerIsActive,
    'VIOLATION: Active order for inactive customer' AS Issue
FROM Orders o
JOIN Customers c ON o.CustomerID = c.CustomerID
WHERE o.Status IN ('Pending', 'Processing', 'Shipped')
  AND c.IsActive = 0
ORDER BY o.OrderDate;

-- Step 2: SalesTargets for terminated employees
SELECT
    st.TargetID,
    st.SalespersonID,
    st.Year,
    st.Quarter,
    st.TargetAmount,
    e.FullName,
    e.TerminationDate,
    DATEDIFF(DAY, e.TerminationDate, GETDATE()) AS DaysSinceTermination,
    'WARNING: Sales target exists for terminated employee' AS Issue
FROM SalesTargets st
JOIN Employees e ON st.SalespersonID = e.EmployeeID
WHERE e.TerminationDate IS NOT NULL
  AND e.TerminationDate < GETDATE()
ORDER BY e.TerminationDate;

-- Step 3: Transactions linked to cancelled/closed orders (soft-delete cascade check)
-- A cancelled order should have no new (post-cancellation) transactions
SELECT
    t.TransactionID,
    t.OrderID,
    t.TransactionDate,
    t.Amount,
    o.Status,
    o.OrderDate,
    DATEDIFF(DAY, o.OrderDate, t.TransactionDate) AS DaysAfterOrder,
    CASE
        WHEN o.Status = 'Cancelled' AND t.TransactionDate > o.OrderDate
             THEN 'VIOLATION: Transaction after order cancellation'
        WHEN o.Status = 'Cancelled'
             THEN 'INFO: Historical transaction on cancelled order'
        ELSE 'OK'
    END AS CancellationConsistency
FROM Transactions t
JOIN Orders o ON t.OrderID = o.OrderID
WHERE o.Status = 'Cancelled'
  AND t.TransactionDate > o.OrderDate;

-- Step 4: Customer account summary — soft-deleted customers with any outstanding items
SELECT
    c.CustomerID,
    c.FirstName + ' ' + c.LastName AS CustomerName,
    c.IsActive,
    COUNT(DISTINCT CASE WHEN o.Status IN ('Pending','Processing','Shipped') THEN o.OrderID END)
        AS ActiveOrders,
    SUM(CASE WHEN o.Status IN ('Pending','Processing','Shipped') THEN o.TotalAmount ELSE 0 END)
        AS OutstandingValue,
    MAX(o.OrderDate) AS LastOrderDate
FROM Customers c
LEFT JOIN Orders o ON c.CustomerID = o.CustomerID
WHERE c.IsActive = 0
GROUP BY c.CustomerID, c.FirstName, c.LastName, c.IsActive
HAVING COUNT(DISTINCT CASE WHEN o.Status IN ('Pending','Processing','Shipped') THEN o.OrderID END) > 0
ORDER BY OutstandingValue DESC;

-- Step 5: Summary of soft-delete cascade violations
SELECT 'Active orders → inactive customers' AS ViolationType, COUNT(*) AS ViolationCount
FROM Orders o
JOIN Customers c ON o.CustomerID = c.CustomerID
WHERE o.Status IN ('Pending','Processing','Shipped') AND c.IsActive = 0

UNION ALL

SELECT 'SalesTargets → terminated employees', COUNT(*)
FROM SalesTargets st
JOIN Employees e ON st.SalespersonID = e.EmployeeID
WHERE e.TerminationDate IS NOT NULL AND e.TerminationDate < GETDATE()

ORDER BY ViolationCount DESC;
```

## Explanation

**Soft-delete vs hard-delete cascade**
Hard-delete with `ON DELETE CASCADE` automatically removes child records when the parent is deleted. Soft-delete has no automatic cascade — the application must explicitly propagate the deactivation to child records. When this propagation logic fails, soft-deleted parents leave active children, creating logical orphans.

**Business-level orphans**
These records are not referential integrity violations — the FK still resolves. But they are business-logic violations: an order processing against a customer who has been deactivated. Standard FK constraints do not detect this; application-layer or validation-query checks are required.

**GDPR implications**
When soft-delete is the mechanism for GDPR right-to-erasure (with customer PII pseudonymised or nulled while the record ID is retained), active orders on pseudonymised customers may continue being processed — shipping to a blank address, emailing a null email address. The cascade must include all dependent records.

**Remediation: cascade deactivation**
The fix is a stored procedure that, when `IsActive` is set to 0, cancels all pending orders for that customer in the same transaction. This ensures atomicity: either the customer is deactivated AND all orders cancelled, or neither change is committed.

## Severity
**High** — Soft-delete cascade failures cause active processing of records that should be dormant. In GDPR contexts, this is a compliance violation (processing data for an erased subject). In financial contexts, it means billing customers whose accounts are closed. In fulfilment, it means shipping goods to cancelled accounts.
