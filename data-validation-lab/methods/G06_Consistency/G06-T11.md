# G06-T11 — Consistency | Multi-Row Constraint Violation

## ID
G06-T11

## Group
6 — Consistency

## Type
Multi-Row Constraint — A Business Rule Spanning Multiple Rows Is Violated

## Live Scenario
A sales commission system enforces that each salesperson can have at most one active target per quarter. The business rule is: one row per `(SalespersonID, Year, Quarter)` combination in `SalesTargets`. A batch import creates duplicate targets for three salespeople in Q2 2024 because the upsert logic failed silently — instead of updating the existing target, it inserted a new row. The commission calculation sums `TargetAmount` per salesperson per quarter and now shows inflated targets: one salesperson appears to have a Q2 target of £240,000 when the actual target is £120,000. Their commission is calculated on the wrong denominator, understating their performance against target by 50%.

## The Question
> Some business rules span multiple rows: "each salesperson may have at most one target per quarter," "each product SKU must appear exactly once in an order line," or "a customer must not have overlapping subscription periods." SQL detects multi-row violations using GROUP BY and HAVING to find groups that exceed their permitted count.
> **"Find all (SalespersonID, Year, Quarter) combinations in SalesTargets that have more than one row — violating the one-target-per-period business rule."**

## Table Reference
**SalesTargets** — `schemas/06_SalesTargets.csv`
**Orders** — `schemas/02_Orders.csv`

## Solution Query

```sql
-- Step 1: Detect duplicate (SalespersonID, Year, Quarter) combinations
SELECT
    SalespersonID,
    Year,
    Quarter,
    COUNT(*) AS RowCount,
    SUM(TargetAmount) AS SummedTarget,
    MIN(TargetAmount) AS MinTarget,
    MAX(TargetAmount) AS MaxTarget,
    STRING_AGG(CAST(TargetID AS VARCHAR), ', ') AS TargetIDs,
    'VIOLATION: Multiple targets for same salesperson-period' AS Issue
FROM SalesTargets
GROUP BY SalespersonID, Year, Quarter
HAVING COUNT(*) > 1
ORDER BY RowCount DESC, SalespersonID;

-- Step 2: Show the full rows for each violation
WITH DuplicatePeriods AS (
    SELECT SalespersonID, Year, Quarter
    FROM SalesTargets
    GROUP BY SalespersonID, Year, Quarter
    HAVING COUNT(*) > 1
)
SELECT
    st.TargetID,
    st.SalespersonID,
    st.Year,
    st.Quarter,
    st.TargetAmount,
    st.CommissionRate,
    ROW_NUMBER() OVER (PARTITION BY st.SalespersonID, st.Year, st.Quarter
                       ORDER BY st.TargetID) AS RowWithinGroup,
    'Duplicate: more than one row for this period' AS Flag
FROM SalesTargets st
JOIN DuplicatePeriods dp
    ON  st.SalespersonID = dp.SalespersonID
    AND st.Year = dp.Year
    AND st.Quarter = dp.Quarter
ORDER BY st.SalespersonID, st.Year, st.Quarter, st.TargetID;

-- Step 3: Multi-row constraint on Orders — same product must not appear twice in same order
SELECT
    OrderID,
    ProductID,
    COUNT(*) AS OrderLineCount,
    SUM(TotalAmount) AS TotalForProduct,
    'VIOLATION: Same product ordered twice in same order — should be combined' AS Issue
FROM Orders
GROUP BY OrderID, ProductID
HAVING COUNT(*) > 1
ORDER BY OrderLineCount DESC;

-- Step 4: Customer-level uniqueness rule — each customer must appear in Orders at most once per day
-- (business rule: one order per customer per day)
SELECT
    CustomerID,
    CAST(OrderDate AS DATE) AS OrderDay,
    COUNT(*) AS OrdersOnDay,
    STRING_AGG(CAST(OrderID AS VARCHAR), ', ') AS OrderIDs,
    'WARNING: Multiple orders from same customer on same day' AS Note
FROM Orders
GROUP BY CustomerID, CAST(OrderDate AS DATE)
HAVING COUNT(*) > 1
ORDER BY OrdersOnDay DESC;

-- Step 5: Impact of duplicate targets on commission calculation
WITH CorrectTargets AS (
    -- Use the latest (MAX TargetID) row per period as the canonical target
    SELECT
        SalespersonID,
        Year,
        Quarter,
        MAX(TargetAmount) AS MaxTarget,
        SUM(TargetAmount) AS NaiveSumIfDuplicated,
        COUNT(*) AS RowCount
    FROM SalesTargets
    GROUP BY SalespersonID, Year, Quarter
)
SELECT
    SalespersonID,
    Year,
    Quarter,
    MaxTarget AS CorrectTarget,
    NaiveSumIfDuplicated AS InflatedTarget,
    NaiveSumIfDuplicated - MaxTarget AS Overcount,
    RowCount AS DuplicateRows
FROM CorrectTargets
WHERE RowCount > 1;
```

## Explanation

**GROUP BY … HAVING COUNT(*) > 1**
This is the standard pattern for detecting multi-row violations. GROUP BY defines the unique key — the combination of columns that should be unique — and `HAVING COUNT(*) > 1` filters to only the groups where that uniqueness is violated.

**UNIQUE constraint vs application logic**
A UNIQUE constraint on `(SalespersonID, Year, Quarter)` in the `SalesTargets` table would prevent duplicates at the database level: `ALTER TABLE SalesTargets ADD CONSTRAINT uq_SalespersonPeriod UNIQUE (SalespersonID, Year, Quarter)`. The SQL validation query detects existing violations; the constraint prevents new ones.

**ROW_NUMBER for identifying which row to keep**
Once duplicates are identified, Step 2 uses `ROW_NUMBER() OVER (PARTITION BY ... ORDER BY TargetID)` to number rows within each group. Row 1 is the "canonical" record (by TargetID order); rows 2+ are the duplicates to be deleted or merged.

**STRING_AGG for surfacing all affected IDs**
`STRING_AGG(CAST(TargetID AS VARCHAR), ', ')` collects all TargetIDs in the duplicate group into a single string, making it easy to identify every row involved. This is especially useful when handing results to a data steward for manual review.

## Severity
**High** — Multi-row violations corrupt any aggregation that assumes the violated constraint holds. Commission targets summed across duplicated rows produce inflated denominators, making actual performance appear worse than it is. In financial systems, duplicate transaction records overstate revenue or expenses by the volume of duplicated amounts.
