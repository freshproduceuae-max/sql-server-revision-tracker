# G06-T04 — Consistency | Unit / Currency Mismatch

## ID
G06-T04

## Group
6 — Consistency

## Type
Unit / Currency Mismatch — Values in Different Units Combined Without Conversion

## Live Scenario
A multinational company processes transactions in GBP, EUR, and USD. A reporting query sums `Amount` across all Transactions without a currency filter, producing a figure of £2,341,892 — actually a mix of pounds, euros, and dollars added together as if they were the same unit. The CFO presents this figure to the board as "total revenue in GBP." The actual GBP revenue is £1,180,000; the remaining amounts are EUR 841,000 and USD 320,892 — which at prevailing exchange rates represent approximately £1,055,000 GBP equivalent, giving a true total closer to £2,235,000. The board approves a budget based on a £106,000 overstated revenue figure.

## The Question
> Numeric values that look identical but are in different units (currencies, kilograms vs pounds, miles vs kilometres) cannot be summed without first converting to a common unit. SQL can detect unit mismatches by checking whether values being aggregated share the same unit, and flag rows where the unit is missing or inconsistent.
> **"Find all Transactions where Currency is mixed within the same aggregation group, flag transactions with missing Currency, and demonstrate the correct pattern for currency-safe aggregation."**

## Table Reference
**Transactions** — `schemas/05_Transactions.csv`
**Orders** — `schemas/02_Orders.csv`

## Solution Query

```sql
-- Step 1: Flag missing currency on transactions
SELECT
    TransactionID,
    OrderID,
    Amount,
    Currency,
    'Missing Currency — amount cannot be safely aggregated' AS Issue
FROM Transactions
WHERE Currency IS NULL
   OR LTRIM(RTRIM(Currency)) = '';

-- Step 2: Detect mixed-currency orders (a single order with transactions in different currencies)
WITH OrderCurrencies AS (
    SELECT
        OrderID,
        COUNT(DISTINCT Currency) AS DistinctCurrencies,
        STRING_AGG(DISTINCT Currency, ', ') WITHIN GROUP (ORDER BY Currency) AS CurrencyList
    FROM Transactions
    WHERE Currency IS NOT NULL
    GROUP BY OrderID
)
SELECT
    oc.OrderID,
    oc.DistinctCurrencies,
    oc.CurrencyList,
    o.TotalAmount,
    'MIXED CURRENCIES: Cannot sum without conversion' AS Issue
FROM OrderCurrencies oc
JOIN Orders o ON oc.OrderID = o.OrderID
WHERE oc.DistinctCurrencies > 1;

-- Step 3: Currency-safe totals — segregated by currency (correct pattern)
SELECT
    Currency,
    COUNT(*) AS TxCount,
    SUM(Amount) AS TotalInCurrency,
    MIN(Amount) AS MinAmount,
    MAX(Amount) AS MaxAmount
FROM Transactions
WHERE Currency IS NOT NULL
GROUP BY Currency
ORDER BY TotalInCurrency DESC;

-- Step 4: Incorrect pattern — naive sum across all currencies (DO NOT USE for reporting)
-- Shown here to illustrate what the wrong query looks like
SELECT
    'UNSAFE: Mixed currency sum (illustrative only)' AS Warning,
    SUM(Amount) AS WrongTotal,  -- GBP + EUR + USD summed as-is
    COUNT(DISTINCT Currency) AS CurrenciesIncluded
FROM Transactions;

-- Step 5: Currency consistency between Orders and Transactions
-- If Orders has a currency and Transactions has a currency, they should match
SELECT
    t.TransactionID,
    t.OrderID,
    t.Currency AS TransactionCurrency,
    t.Amount,
    'Transactions table: verify currency matches order expectation' AS Note
FROM Transactions t
JOIN Orders o ON t.OrderID = o.OrderID
WHERE t.Currency NOT IN ('GBP', 'EUR', 'USD')  -- unexpected currencies
   OR t.Currency IS NULL;

-- Step 6: Identify implausible amounts given currency context
-- Very small amounts in GBP suggest possible unit error (pence vs pounds)
SELECT
    TransactionID,
    Amount,
    Currency,
    CASE
        WHEN Currency = 'GBP' AND Amount < 0.50 AND Amount > 0
             THEN 'WARNING: < £0.50 — possible pence/pounds unit error'
        WHEN Currency = 'USD' AND Amount > 1000000
             THEN 'WARNING: > $1M single transaction — verify'
        WHEN Currency = 'JPY' AND Amount < 100
             THEN 'WARNING: < ¥100 — likely unit error (JPY is a low-unit currency)'
        ELSE 'Amount plausible for currency'
    END AS AmountUnitCheck
FROM Transactions
WHERE (Currency = 'GBP' AND Amount < 0.50 AND Amount > 0)
   OR (Currency = 'USD' AND Amount > 1000000)
   OR (Currency = 'JPY' AND Amount < 100);
```

## Explanation

**The unit consistency rule**
Mathematical operations (SUM, AVG, subtraction) are only valid on values in the same unit. `100 GBP + 100 EUR ≠ 200` of anything meaningful. The correct approach: always GROUP BY the unit column (Currency, UnitOfMeasure) before summing, or convert all values to a common unit first using an exchange rate or conversion factor.

**STRING_AGG for detecting multiple values**
`STRING_AGG(DISTINCT Currency, ', ')` (SQL Server 2017+) concatenates all distinct currency values per order into a single string. This makes the multi-currency problem visible in a single column: `'GBP, EUR'` immediately signals a problem.

**Pence vs pounds, cents vs dollars**
Unit errors also occur within a single currency. An amount of `0.05` labelled GBP could be 5 pence (likely correct) or £0.05 entered as 5 when the field expected pence — making it really 500 pence = £5. Plausibility checks by amount range and currency (Step 6) catch these magnitude errors.

**Exchange rate tables for conversion**
The correct multi-currency aggregation pattern uses an exchange rate table: `SUM(Amount * ISNULL(er.RateToGBP, 1))` where `er` is a daily rates table. Without an exchange rate table, cross-currency aggregation is impossible — SQL can only segregate by currency or flag the problem.

## Severity
**High** — Currency aggregation errors silently produce meaningless totals that are then used in financial reporting, budget planning, and investment decisions. The error is invisible in the query result — a sum of 28,750 looks like a valid number. Detection requires knowing which currencies were included, which requires the underlying data.
