# G06-T02 — Consistency | Cross-Table Value Mismatch

## ID
G06-T02

## Group
6 — Consistency

## Type
Cross-Table Value Mismatch — The Same Fact Stored Differently in Two Tables

## Live Scenario
A retail system stores customer email addresses in two places: the `Customers` table (the master record) and the `Orders` table (captured at time of order placement). A self-service portal allows customers to update their email in the Customers table. The Orders table is never updated retroactively. After 18 months, an email marketing campaign queries Orders for customer emails and sends promotional messages to 3,400 old addresses. The bounce rate is 41%. The correct approach is to always join to Customers for the current email, but a developer unfamiliar with the schema used Orders.Email directly. Additionally, 89 customer records have a different email in Orders than in Customers, indicating the customer changed their email after placing orders.

## The Question
> When the same attribute (customer email, product price, employee name) is stored in multiple tables, the values must match — or there must be a documented reason they differ (e.g., point-in-time snapshot). Cross-table mismatches reveal denormalisation problems, stale copies, or update propagation failures.
> **"Find all Orders where the CustomerID exists in the Customers table but the order's recorded data differs from the master customer record — demonstrating the cross-table consistency check pattern."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Customers** — `schemas/01_Customers.csv`
**Products** — `schemas/03_Products.csv`

## Solution Query

```sql
-- Step 1: Identify CustomerIDs that appear in Orders but have no matching Customer record
-- (orphan FK — referenced in Customers check first)
SELECT
    o.OrderID,
    o.CustomerID,
    o.TotalAmount,
    o.OrderDate,
    c.FirstName,
    c.LastName,
    c.IsActive,
    CASE
        WHEN c.CustomerID IS NULL THEN 'ORPHAN: CustomerID not in Customers table'
        WHEN c.IsActive = 0       THEN 'WARNING: Order linked to inactive customer'
        ELSE 'Customer record found and active'
    END AS CustomerConsistency
FROM Orders o
LEFT JOIN Customers c ON o.CustomerID = c.CustomerID
WHERE c.CustomerID IS NULL
   OR c.IsActive = 0;

-- Step 2: Cross-table amount consistency — TotalAmount in Orders vs sum of Transactions
WITH TransactionTotals AS (
    SELECT
        OrderID,
        SUM(Amount) AS TransactionSum,
        COUNT(*) AS TxCount
    FROM Transactions
    GROUP BY OrderID
)
SELECT
    o.OrderID,
    o.TotalAmount AS OrderTotalAmount,
    tt.TransactionSum,
    tt.TxCount,
    o.TotalAmount - tt.TransactionSum AS Discrepancy,
    CASE
        WHEN tt.OrderID IS NULL
             THEN 'No transactions found for this order'
        WHEN ABS(o.TotalAmount - tt.TransactionSum) > 0.01
             THEN 'MISMATCH: Order total ≠ sum of transactions'
        ELSE 'Amounts consistent'
    END AS AmountConsistency
FROM Orders o
LEFT JOIN TransactionTotals tt ON o.OrderID = tt.OrderID
WHERE tt.OrderID IS NULL
   OR ABS(o.TotalAmount - tt.TransactionSum) > 0.01
ORDER BY ABS(o.TotalAmount - ISNULL(tt.TransactionSum, 0)) DESC;

-- Step 3: Product price consistency — Orders.TotalAmount vs Products.Price × implied quantity
-- A simple sanity check: if TotalAmount < Products.Price, at least 1 unit must be wrong
SELECT
    o.OrderID,
    o.ProductID,
    o.TotalAmount AS OrderTotal,
    p.Price AS CurrentUnitPrice,
    CASE
        WHEN p.ProductID IS NULL
             THEN 'Product not found — FK issue'
        WHEN o.TotalAmount < p.Price * 0.5
             THEN 'WARNING: Order total suspiciously low vs unit price'
        WHEN o.TotalAmount > p.Price * 100
             THEN 'WARNING: Order total unusually high vs unit price'
        ELSE 'Price/amount relationship plausible'
    END AS PriceConsistency
FROM Orders o
LEFT JOIN Products p ON o.ProductID = p.ProductID
WHERE p.ProductID IS NULL
   OR o.TotalAmount < p.Price * 0.5
   OR o.TotalAmount > p.Price * 100;

-- Step 4: Summary of cross-table inconsistencies
SELECT
    'Orders → Customers (orphan or inactive)' AS Check,
    COUNT(*) AS Issues
FROM Orders o
LEFT JOIN Customers c ON o.CustomerID = c.CustomerID
WHERE c.CustomerID IS NULL OR c.IsActive = 0

UNION ALL

SELECT
    'Orders → Transactions (amount mismatch)',
    COUNT(*)
FROM Orders o
LEFT JOIN (
    SELECT OrderID, SUM(Amount) AS TransactionSum FROM Transactions GROUP BY OrderID
) tt ON o.OrderID = tt.OrderID
WHERE tt.OrderID IS NULL OR ABS(o.TotalAmount - tt.TransactionSum) > 0.01

ORDER BY Issues DESC;
```

## Explanation

**Denormalisation creates consistency risk**
When data from a master table (Customers) is copied into a transactional table (Orders.Email), any subsequent update to the master is not automatically propagated. This is the fundamental trade-off of denormalisation: faster reads, but consistency maintenance responsibility falls to the application.

**Point-in-time vs current value**
Some cross-table differences are intentional. The price in an Order row may legitimately differ from the current Products.Price — the order captured the price at time of sale. Before flagging a mismatch, verify whether the cross-table copy is meant to be a current value or a historical snapshot.

**LEFT JOIN for mismatch detection**
`LEFT JOIN … WHERE right.col IS NULL` detects records in the left table with no match in the right table (orphan records). For value comparison, the JOIN finds the matching row and then the CASE expression compares the values, flagging differences.

**Financial reconciliation as consistency check**
Step 2 — comparing `Orders.TotalAmount` to `SUM(Transactions.Amount)` — is a reconciliation pattern. The two values should agree to within rounding tolerance (0.01 in this case). Discrepancies indicate either a missed transaction, a cancelled partial transaction, or a manual adjustment that was not reflected in the order header.

## Severity
**High** — Cross-table value mismatches cause downstream processes to use stale or incorrect data silently. In financial systems, order total vs transaction sum mismatches create unexplained cash discrepancies. In operational systems, an inactive customer being linked to active orders may bypass business rules that check customer status.
