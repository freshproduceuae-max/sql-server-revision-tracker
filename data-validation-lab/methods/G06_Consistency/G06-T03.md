# G06-T03 — Consistency | Derived Field Mismatch

## ID
G06-T03

## Group
6 — Consistency

## Type
Derived Field Mismatch — A Stored Computed Value Differs from the Recomputed Value

## Live Scenario
An e-commerce platform stores `TotalAmount` in the Orders table, computed as `UnitPrice × Quantity - Discount + VAT`. A pricing engine update six months ago changed the VAT rate from 20% to 0% for a specific product category (children's clothing). The recalculation logic in the application was updated, but 2,800 historic orders were not retroactively recalculated — their `TotalAmount` still reflects the old 20% VAT rate. A tax reconciliation report for the period overstates VAT collected by £38,000. The error is only discovered when HMRC's automated cross-reference flags the discrepancy between VAT returns and transaction records.

## The Question
> Stored computed values (totals, aggregates, hashes, checksums) become stale when their source components are updated without triggering a recalculation. SQL can detect mismatches by recomputing the value in the query and comparing it to the stored value.
> **"Find all Orders where TotalAmount does not match the sum of its component transactions, and find all SalesTargets where CommissionRate applied to TargetAmount produces a different result than any stored commission value."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Transactions** — `schemas/05_Transactions.csv`
**SalesTargets** — `schemas/06_SalesTargets.csv`

## Solution Query

```sql
-- Step 1: Compare stored TotalAmount to sum of linked transactions
WITH OrderTransactionTotals AS (
    SELECT
        OrderID,
        SUM(Amount) AS SumOfTransactions,
        COUNT(*) AS TransactionCount
    FROM Transactions
    GROUP BY OrderID
)
SELECT
    o.OrderID,
    o.CustomerID,
    o.TotalAmount AS StoredTotal,
    ott.SumOfTransactions AS RecomputedTotal,
    ott.TransactionCount,
    ROUND(o.TotalAmount - ott.SumOfTransactions, 2) AS Difference,
    CASE
        WHEN ott.OrderID IS NULL
             THEN 'No transactions — cannot validate'
        WHEN ABS(o.TotalAmount - ott.SumOfTransactions) < 0.01
             THEN 'Consistent (within £0.01 rounding)'
        WHEN ABS(o.TotalAmount - ott.SumOfTransactions) < 1.00
             THEN 'Minor discrepancy (< £1.00) — rounding likely'
        ELSE 'MISMATCH: Significant difference — investigate'
    END AS ConsistencyStatus
FROM Orders o
LEFT JOIN OrderTransactionTotals ott ON o.OrderID = ott.OrderID
WHERE ABS(o.TotalAmount - ISNULL(ott.SumOfTransactions, 0)) > 0.01
ORDER BY ABS(o.TotalAmount - ISNULL(ott.SumOfTransactions, 0)) DESC;

-- Step 2: Commission value consistency check
-- Expected commission = TargetAmount × CommissionRate / 100
-- If a StoredCommission column existed, this would compare stored vs recomputed
SELECT
    TargetID,
    SalespersonID,
    TargetAmount,
    CommissionRate,
    ROUND(TargetAmount * CommissionRate / 100.0, 2) AS RecomputedCommission,
    -- In a real scenario: StoredCommission AS StoredCommission,
    -- ABS(StoredCommission - RecomputedCommission) AS Discrepancy
    'Recomputed commission for validation' AS Note
FROM SalesTargets
WHERE TargetAmount IS NOT NULL
  AND CommissionRate IS NOT NULL
ORDER BY TargetID;

-- Step 3: Detect stale derived values using a hash/checksum approach
-- Row checksum: CHECKSUM(*) or BINARY_CHECKSUM(*) can detect any row change
SELECT
    OrderID,
    CustomerID,
    TotalAmount,
    CHECKSUM(CustomerID, ProductID, TotalAmount, Status) AS RowChecksum,
    -- In practice, compare stored_checksum (from an audit column) to recomputed
    'CHECKSUM value for change detection' AS ChecksumNote
FROM Orders
ORDER BY OrderID;

-- Step 4: Multi-component total validation
-- Validate that product prices × implicit quantities make sense
SELECT
    o.OrderID,
    o.TotalAmount,
    p.Price AS UnitPrice,
    CASE
        WHEN p.Price > 0 THEN ROUND(o.TotalAmount / p.Price, 0)
        ELSE NULL
    END AS ImpliedQuantity,
    CASE
        WHEN p.Price IS NULL THEN 'Product not found'
        WHEN o.TotalAmount <= 0 THEN 'Invalid total: zero or negative'
        WHEN o.TotalAmount / NULLIF(p.Price, 0) > 1000
             THEN 'WARNING: Implied quantity > 1000 — verify'
        WHEN o.TotalAmount / NULLIF(p.Price, 0) < 0.5
             THEN 'WARNING: Total less than one unit price — discount or error?'
        ELSE 'Plausible'
    END AS ComponentCheck
FROM Orders o
LEFT JOIN Products p ON o.ProductID = p.ProductID
ORDER BY o.TotalAmount DESC;

-- Step 5: Aggregate consistency — sum of order lines should match header total
SELECT
    YEAR(o.OrderDate) AS OrderYear,
    MONTH(o.OrderDate) AS OrderMonth,
    SUM(o.TotalAmount) AS OrderHeaderTotal,
    SUM(t.Amount) AS TransactionTotal,
    SUM(o.TotalAmount) - SUM(t.Amount) AS MonthlyDiscrepancy
FROM Orders o
LEFT JOIN Transactions t ON o.OrderID = t.OrderID
GROUP BY YEAR(o.OrderDate), MONTH(o.OrderDate)
HAVING ABS(SUM(o.TotalAmount) - SUM(t.Amount)) > 1.00
ORDER BY ABS(SUM(o.TotalAmount) - SUM(t.Amount)) DESC;
```

## Explanation

**Why stored computed values go stale**
A derived value (total, sum, hash) is consistent with its source at the time it is calculated. Any subsequent change to the source components (unit price, discount, quantity) requires a recalculation. If the application fails to trigger the recalculation — due to a code bug, a direct database update bypassing application logic, or a data migration — the stored value drifts from the correct recomputed value.

**Rounding tolerance in financial comparisons**
`ABS(stored - recomputed) < 0.01` allows a 1-penny tolerance. This accounts for floating-point rounding differences in different calculation paths. Without tolerance, valid records with rounding differences at the penny level generate false positives. The tolerance should be set to the smallest meaningful difference for the domain.

**CHECKSUM for change detection**
`CHECKSUM(col1, col2, ...)` produces a single integer that changes when any input column changes. It is not cryptographically secure (collisions are possible) but is fast for routine change detection. For audit trails, a full hash (`HASHBYTES('SHA2_256', ...)`) is more reliable.

**The architectural solution: computed columns or views**
The correct fix for a stale derived value is to remove the stored copy and replace it with a computed column (`AS UnitPrice * Quantity - Discount + VAT PERSISTED`) or a view that recalculates on read. Persisted computed columns are stored but automatically recalculated when any source column changes, eliminating the synchronisation problem.

## Severity
**High** — Stale derived values silently corrupt any report or calculation that reads them. Financial totals, tax amounts, and commission values that drift from their source components cause balance sheet errors, incorrect tax filings, and payroll discrepancies.
