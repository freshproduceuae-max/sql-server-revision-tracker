# G07-T09 — Business Rules | Segregation of Duties Violation

## ID
G07-T09

## Group
7 — Business Rules

## Type
Segregation of Duties Violation — Same Person Performed Conflicting Roles in a Transaction

## Live Scenario
An accounts payable system requires that no single employee can both create a supplier invoice and approve the same invoice for payment — this is a segregation of duties (SoD) control required by SOX (Sarbanes-Oxley Act) compliance. An employee discovers they can self-approve their own expense claims by using a colleague's login to create the initial claim and then approving it under their own login. A SOX audit finds 14 transactions where the CreatedBy and ApprovedBy employee IDs are the same — the employee had access to both functions and exploited it. The company's SOX opinion is qualified, requiring a remediation programme.

## The Question
> Segregation of duties controls require that high-risk transaction steps (create, approve, pay) are performed by different individuals. SQL validates SoD by comparing the actor IDs across consecutive steps within the same transaction.
> **"Find all Orders where the same employee is recorded as both the salesperson and the approver, and find all Transactions where the source and destination employee IDs overlap — demonstrating the SoD validation pattern."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Transactions** — `schemas/05_Transactions.csv`
**Employees** — `schemas/04_Employees.csv`
**SalesTargets** — `schemas/06_SalesTargets.csv`

## Solution Query

```sql
-- Step 1: Self-referential SoD check on SalesTargets
-- Business rule: SalespersonID should not be in a position to set their own targets
-- Proxy check: flag targets where Salesperson is also a Manager (ManagerID = SalespersonID)
SELECT
    st.TargetID,
    st.SalespersonID,
    st.Year,
    st.Quarter,
    st.TargetAmount,
    e.FullName AS SalespersonName,
    e.ManagerID,
    CASE
        WHEN e.ManagerID = st.SalespersonID
             THEN 'SoD VIOLATION: Salesperson is their own manager'
        ELSE 'Roles separated'
    END AS SoDStatus
FROM SalesTargets st
JOIN Employees e ON st.SalespersonID = e.EmployeeID
WHERE e.ManagerID = st.SalespersonID;

-- Step 2: Transaction SoD — detect if same bank account number appears as both source and destination
-- Proxy: same SourceIP placing multiple large transactions to the same BankAccountNumber
WITH IPTransactionSummary AS (
    SELECT
        SourceIP,
        BankAccountNumber,
        COUNT(*) AS TxCount,
        SUM(Amount) AS TotalAmount,
        MIN(TransactionDate) AS FirstTx,
        MAX(TransactionDate) AS LastTx
    FROM Transactions
    WHERE SourceIP IS NOT NULL
      AND BankAccountNumber IS NOT NULL
    GROUP BY SourceIP, BankAccountNumber
)
SELECT
    SourceIP,
    BankAccountNumber,
    TxCount,
    TotalAmount,
    FirstTx,
    LastTx,
    CASE
        WHEN TxCount > 10 AND TotalAmount > 5000
             THEN 'HIGH RISK: High volume/value from same IP to same account'
        WHEN TxCount > 3
             THEN 'REVIEW: Multiple transactions same IP/account combination'
        ELSE 'Normal'
    END AS SoDFlag
FROM IPTransactionSummary
WHERE TxCount > 3
ORDER BY TotalAmount DESC;

-- Step 3: Manager-employee target setting conflict
-- A manager (ManagerID) should not set targets for themselves
SELECT
    e.EmployeeID,
    e.FullName,
    e.ManagerID,
    m.FullName AS ManagerName,
    st.TargetID,
    st.TargetAmount,
    CASE
        WHEN st.SalespersonID = e.ManagerID
             THEN 'SoD WARNING: Manager appears as both target recipient and potential setter'
        ELSE 'No conflict'
    END AS ConflictNote
FROM Employees e
JOIN Employees m ON e.ManagerID = m.EmployeeID
JOIN SalesTargets st ON e.ManagerID = st.SalespersonID
WHERE e.EmployeeID = st.SalespersonID
   OR e.ManagerID = st.SalespersonID;

-- Step 4: Unusual concentration — one CorrelationID used across multiple orders
-- Idempotency keys should be unique per transaction; reuse may indicate abuse
SELECT
    CorrelationID,
    COUNT(DISTINCT OrderID) AS DistinctOrders,
    COUNT(*) AS TotalTransactions,
    SUM(Amount) AS TotalAmount,
    'REVIEW: CorrelationID used across multiple orders — potential SoD/fraud flag' AS Flag
FROM Transactions
WHERE CorrelationID IS NOT NULL
GROUP BY CorrelationID
HAVING COUNT(DISTINCT OrderID) > 1
ORDER BY TotalAmount DESC;

-- Step 5: Summary of SoD indicators
SELECT 'Self-managing employees' AS SoDCheck, COUNT(*) AS Count
FROM Employees WHERE ManagerID = EmployeeID

UNION ALL

SELECT 'CorrelationIDs used across multiple orders', COUNT(*)
FROM (
    SELECT CorrelationID
    FROM Transactions
    WHERE CorrelationID IS NOT NULL
    GROUP BY CorrelationID
    HAVING COUNT(DISTINCT OrderID) > 1
) x

UNION ALL

SELECT 'High-volume same-IP-to-account transactions (>3)', COUNT(*)
FROM (
    SELECT SourceIP, BankAccountNumber
    FROM Transactions
    WHERE SourceIP IS NOT NULL AND BankAccountNumber IS NOT NULL
    GROUP BY SourceIP, BankAccountNumber
    HAVING COUNT(*) > 3
) x

ORDER BY Count DESC;
```

## Explanation

**SoD in audit contexts**
Segregation of duties is a foundational internal control under SOX, ISO 27001, and GDPR. The core principle: no single person should control a complete high-risk transaction cycle from initiation to completion without independent oversight. SQL validation detects cases where the same actor appears in multiple roles within the same transaction.

**Proxy checks when direct SoD data is unavailable**
When a single table doesn't store both `CreatedBy` and `ApprovedBy`, SoD validation uses proxies: same ManagerID as EmployeeID (self-management), same SourceIP for multiple transactions to the same account (access concentration), or same CorrelationID across multiple orders (idempotency key reuse).

**Data vs process SoD**
SQL can only validate SoD from data stored in the database. If the application layer enforces SoD but doesn't log actor IDs, SQL cannot verify compliance. Effective SoD audit trails require storing the actor ID at each step: `CreatedByEmployeeID`, `ApprovedByEmployeeID`, `PaidByEmployeeID`.

**Access control vs data validation**
The root SoD control is access control — ensuring no single account has permissions for both steps. Data validation is the detective control that catches failures in the access control layer. Both are needed: preventive (access control) + detective (data validation).

## Severity
**Critical** — SoD violations in financial systems represent a failure of fundamental internal controls required by SOX, FCA regulations, and auditing standards. A qualified SOX audit opinion has direct legal and stock market consequences. Individual SoD violations may indicate fraud — the pattern that enables fraud exists even if no fraud has yet occurred.
