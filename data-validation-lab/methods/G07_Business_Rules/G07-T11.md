# G07-T11 — Business Rules | Frequency / Velocity Check

## ID
G07-T11

## Group
7 — Business Rules

## Type
Frequency / Velocity Check — Unusual Transaction Rate Indicates Error or Fraud

## Live Scenario
A card payment processor monitors for velocity-based fraud signals. The normal transaction pattern for a consumer account is 2–15 transactions per day. A compromised card is used in an automated fraud script that processes 847 transactions in 45 minutes — a rate of approximately 19 transactions per minute. The fraud detection system has a velocity rule: flag accounts with more than 20 transactions per hour. The rule fires correctly, but the fraud team's review queue is backed up and the flag isn't acted on for 2 hours — by which time the total fraudulent charge is £12,400. Post-incident review finds that a second rule ("flag if > 10 transactions within any 15-minute window") would have triggered 12 minutes into the attack.

## The Question
> Velocity rules detect anomalous frequency — too many events in too short a time window. SQL implements velocity checks by counting events per entity per time window and comparing to a threshold.
> **"Find all Customers who have more than 5 Orders in a single day, and find all bank accounts in Transactions with more than 10 transactions within any rolling 60-minute window."**

## Table Reference
**Transactions** — `schemas/05_Transactions.csv`
**Orders** — `schemas/02_Orders.csv`
**Customers** — `schemas/01_Customers.csv`

## Solution Query

```sql
-- Step 1: Daily order velocity — customers with more than 5 orders in one day
SELECT
    o.CustomerID,
    c.FirstName + ' ' + c.LastName AS CustomerName,
    CAST(o.OrderDate AS DATE) AS OrderDay,
    COUNT(*) AS OrdersOnDay,
    SUM(o.TotalAmount) AS DailyOrderValue,
    CASE
        WHEN COUNT(*) > 20 THEN 'CRITICAL: >20 orders in one day — bot/fraud indicator'
        WHEN COUNT(*) > 10 THEN 'HIGH: 11–20 orders — investigate'
        WHEN COUNT(*) > 5  THEN 'ALERT: 6–10 orders in one day — unusual'
        ELSE 'Normal'
    END AS VelocityFlag
FROM Orders o
JOIN Customers c ON o.CustomerID = c.CustomerID
GROUP BY o.CustomerID, c.FirstName, c.LastName, CAST(o.OrderDate AS DATE)
HAVING COUNT(*) > 5
ORDER BY OrdersOnDay DESC;

-- Step 2: Transaction velocity — transactions per hour per bank account
WITH HourlyVelocity AS (
    SELECT
        BankAccountNumber,
        DATEPART(YEAR, TransactionDate)  AS TxYear,
        DATEPART(MONTH, TransactionDate) AS TxMonth,
        DATEPART(DAY, TransactionDate)   AS TxDay,
        DATEPART(HOUR, TransactionDate)  AS TxHour,
        COUNT(*) AS TxCount,
        SUM(Amount) AS HourlyAmount,
        MIN(TransactionDate) AS FirstInHour,
        MAX(TransactionDate) AS LastInHour
    FROM Transactions
    WHERE BankAccountNumber IS NOT NULL
    GROUP BY
        BankAccountNumber,
        DATEPART(YEAR, TransactionDate),
        DATEPART(MONTH, TransactionDate),
        DATEPART(DAY, TransactionDate),
        DATEPART(HOUR, TransactionDate)
)
SELECT
    BankAccountNumber,
    TxYear,
    TxMonth,
    TxDay,
    TxHour,
    TxCount,
    HourlyAmount,
    FirstInHour,
    LastInHour,
    DATEDIFF(MINUTE, FirstInHour, LastInHour) AS SpanMinutes,
    CASE
        WHEN TxCount > 20 THEN 'CRITICAL: >20 tx in one hour'
        WHEN TxCount > 10 THEN 'HIGH: 11–20 tx per hour'
        WHEN TxCount > 5  THEN 'ALERT: 6–10 tx per hour'
        ELSE 'Normal'
    END AS HourlyVelocityFlag
FROM HourlyVelocity
WHERE TxCount > 5
ORDER BY TxCount DESC;

-- Step 3: Rolling window velocity using window functions
-- Count transactions within the preceding 60-minute window for each transaction
SELECT
    t.TransactionID,
    t.BankAccountNumber,
    t.TransactionDate,
    t.Amount,
    COUNT(t2.TransactionID) AS TxInPrior60Min,
    SUM(t2.Amount) AS AmountInPrior60Min,
    CASE
        WHEN COUNT(t2.TransactionID) > 10 THEN 'HIGH VELOCITY: >10 tx in 60 min'
        WHEN COUNT(t2.TransactionID) > 5  THEN 'ELEVATED: >5 tx in 60 min'
        ELSE 'Normal'
    END AS RollingVelocityFlag
FROM Transactions t
LEFT JOIN Transactions t2
    ON  t2.BankAccountNumber = t.BankAccountNumber
    AND t2.TransactionDate   > DATEADD(MINUTE, -60, t.TransactionDate)
    AND t2.TransactionDate   < t.TransactionDate
WHERE t.BankAccountNumber IS NOT NULL
GROUP BY t.TransactionID, t.BankAccountNumber, t.TransactionDate, t.Amount
HAVING COUNT(t2.TransactionID) > 5
ORDER BY TxInPrior60Min DESC;

-- Step 4: IP-level velocity — same source IP with many transactions
SELECT
    SourceIP,
    CAST(TransactionDate AS DATE) AS TxDate,
    COUNT(*) AS TxCount,
    COUNT(DISTINCT BankAccountNumber) AS DistinctAccounts,
    SUM(Amount) AS TotalAmount,
    CASE
        WHEN COUNT(DISTINCT BankAccountNumber) > 10
             THEN 'CRITICAL: One IP accessing >10 different accounts in one day'
        WHEN COUNT(*) > 50
             THEN 'HIGH: >50 transactions from one IP in one day'
        ELSE 'Review'
    END AS IPVelocityFlag
FROM Transactions
WHERE SourceIP IS NOT NULL
GROUP BY SourceIP, CAST(TransactionDate AS DATE)
HAVING COUNT(*) > 10 OR COUNT(DISTINCT BankAccountNumber) > 5
ORDER BY TxCount DESC;
```

## Explanation

**Two velocity check patterns**
1. **Tumbling window**: GROUP BY the time bucket (hour, day) and COUNT within each bucket. Simple and fast but misses bursts that span two adjacent buckets (e.g., 8 transactions 11:55–12:05 spans two hours but only 4 show in each).
2. **Rolling window**: For each transaction, count preceding transactions within N minutes using a self-join or window function. More accurate but more expensive to compute.

**Rolling window self-join**
`LEFT JOIN Transactions t2 ON t2.TransactionDate > DATEADD(MINUTE, -60, t.TransactionDate)` selects all transactions within the previous 60 minutes. This is a self-join correlated to each row — computationally expensive on large tables. In production, a date-partitioned index on `(BankAccountNumber, TransactionDate)` makes this efficient.

**Multi-dimensional velocity**
Step 4 combines two velocity signals: volume (count of transactions) and breadth (count of distinct accounts from the same IP). An IP accessing many different accounts is a more specific fraud indicator than just high volume from one IP.

**Velocity threshold calibration**
Thresholds (5, 10, 20 per hour) must be calibrated to the specific domain. A point-of-sale system for a busy restaurant might legitimately have 50 transactions per hour. The thresholds in these examples are illustrative — they should be derived from historical baseline distributions for the specific entity type.

## Severity
**High** — High transaction velocity from a single source is the primary real-time fraud indicator for card-not-present fraud and account takeover. The faster the detection and block, the lower the fraud loss. A 15-minute detection saves significantly more than a 2-hour detection for the same attack.
