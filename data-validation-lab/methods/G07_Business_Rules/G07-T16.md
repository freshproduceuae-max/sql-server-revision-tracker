# G07-T16 — Business Rules | Approval Threshold Bypass

## ID
G07-T16

## Group
7 — Business Rules

## Type
Approval Threshold Bypass — High-Value Activity Processed Without Required Authorisation

## Live Scenario
A procurement policy requires purchase orders above £10,000 to have Director-level approval and above £50,000 to have Board-level approval. An employee submits a £52,000 equipment purchase as two separate requisitions: one for £28,000 and one for £24,000. Each individual requisition is below the Director threshold and receives only manager-level approval. Together they represent a £52,000 commitment that should have required Board approval. An internal audit finds this pattern — "requisition splitting" — on 7 occasions totalling £287,000 of commitments that bypassed the correct approval tier. The company's procurement policy is deemed inadequate by its ISO 9001 auditor.

## The Question
> Approval threshold bypass occurs when a single commitment is split into multiple sub-threshold records to circumvent the authorisation requirement. Detection requires aggregating related records (same supplier, same category, same period) and comparing the total to the threshold.
> **"Find all Customers where the aggregate order value in a single month exceeds the threshold that would require Director approval (£10,000), even though no individual order reached that threshold."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Customers** — `schemas/01_Customers.csv`
**SalesTargets** — `schemas/06_SalesTargets.csv`

## Solution Query

```sql
-- Step 1: Monthly order aggregation — detect threshold bypass by splitting
DECLARE @ManagerThreshold  DECIMAL(10,2) = 1000.00;
DECLARE @DirectorThreshold DECIMAL(10,2) = 10000.00;
DECLARE @BoardThreshold    DECIMAL(10,2) = 50000.00;

WITH MonthlyOrderAgg AS (
    SELECT
        CustomerID,
        YEAR(OrderDate)  AS OrderYear,
        MONTH(OrderDate) AS OrderMonth,
        COUNT(*) AS OrderCount,
        MAX(TotalAmount) AS MaxSingleOrder,
        SUM(TotalAmount) AS MonthlyTotal
    FROM Orders
    WHERE Status NOT IN ('Cancelled', 'Refunded')
    GROUP BY CustomerID, YEAR(OrderDate), MONTH(OrderDate)
)
SELECT
    moa.CustomerID,
    c.FirstName + ' ' + c.LastName AS CustomerName,
    moa.OrderYear,
    moa.OrderMonth,
    moa.OrderCount,
    moa.MaxSingleOrder,
    moa.MonthlyTotal,
    CASE
        WHEN moa.MaxSingleOrder >= @DirectorThreshold
             THEN 'Individual order already meets Director threshold — correct approval path'
        WHEN moa.MonthlyTotal >= @DirectorThreshold
             AND moa.MaxSingleOrder < @DirectorThreshold
             THEN 'BYPASS RISK: Monthly total (' + CAST(moa.MonthlyTotal AS VARCHAR)
                  + ') exceeds Director threshold but no individual order does'
        WHEN moa.MonthlyTotal >= @ManagerThreshold
             AND moa.MaxSingleOrder < @ManagerThreshold
             THEN 'BYPASS RISK: Monthly total exceeds Manager threshold by splitting'
        ELSE 'Within thresholds'
    END AS ThresholdBypassFlag
FROM MonthlyOrderAgg moa
JOIN Customers c ON moa.CustomerID = c.CustomerID
WHERE moa.MonthlyTotal >= @ManagerThreshold
ORDER BY moa.MonthlyTotal DESC;

-- Step 2: Show the individual orders that together create the bypass
WITH HighAggCustomers AS (
    SELECT
        CustomerID,
        YEAR(OrderDate)  AS OrderYear,
        MONTH(OrderDate) AS OrderMonth,
        SUM(TotalAmount) AS MonthlyTotal
    FROM Orders
    WHERE Status NOT IN ('Cancelled','Refunded')
    GROUP BY CustomerID, YEAR(OrderDate), MONTH(OrderDate)
    HAVING SUM(TotalAmount) >= @DirectorThreshold
       AND MAX(TotalAmount) < @DirectorThreshold
)
SELECT
    o.OrderID,
    o.CustomerID,
    o.OrderDate,
    o.TotalAmount,
    hac.MonthlyTotal AS MonthlyAggregate,
    'Part of potential threshold bypass — aggregate exceeds Director level' AS Flag
FROM Orders o
JOIN HighAggCustomers hac
    ON  o.CustomerID = hac.CustomerID
    AND YEAR(o.OrderDate) = hac.OrderYear
    AND MONTH(o.OrderDate) = hac.OrderMonth
WHERE o.Status NOT IN ('Cancelled','Refunded')
ORDER BY o.CustomerID, o.OrderDate;

-- Step 3: Near-threshold orders — suspicious proximity to approval threshold
SELECT
    OrderID,
    CustomerID,
    TotalAmount,
    OrderDate,
    CASE
        WHEN TotalAmount BETWEEN @DirectorThreshold * 0.95 AND @DirectorThreshold - 0.01
             THEN 'SUSPICIOUS: Within 5% below Director threshold (£10,000)'
        WHEN TotalAmount BETWEEN @ManagerThreshold * 0.95 AND @ManagerThreshold - 0.01
             THEN 'SUSPICIOUS: Within 5% below Manager threshold (£1,000)'
        ELSE 'Not near threshold'
    END AS NearThresholdFlag
FROM Orders
WHERE (TotalAmount BETWEEN @DirectorThreshold * 0.95 AND @DirectorThreshold - 0.01)
   OR (TotalAmount BETWEEN @ManagerThreshold * 0.95 AND @ManagerThreshold - 0.01)
ORDER BY TotalAmount DESC;

-- Step 4: Recurring customer-month patterns — same customer splitting regularly
SELECT
    CustomerID,
    COUNT(DISTINCT CAST(YEAR(OrderDate) AS VARCHAR) + '-' + CAST(MONTH(OrderDate) AS VARCHAR))
        AS MonthsWithSplitting,
    SUM(TotalAmount) AS TotalSplitAmount
FROM Orders
WHERE Status NOT IN ('Cancelled','Refunded')
  AND CustomerID IN (
    SELECT CustomerID
    FROM Orders
    WHERE Status NOT IN ('Cancelled','Refunded')
    GROUP BY CustomerID, YEAR(OrderDate), MONTH(OrderDate)
    HAVING SUM(TotalAmount) >= @DirectorThreshold AND MAX(TotalAmount) < @DirectorThreshold
  )
GROUP BY CustomerID
HAVING COUNT(DISTINCT CAST(YEAR(OrderDate) AS VARCHAR) + '-' + CAST(MONTH(OrderDate) AS VARCHAR)) > 1
ORDER BY TotalSplitAmount DESC;

-- Step 5: Summary statistics
SELECT
    'Orders within 5% below Manager threshold' AS Pattern,
    COUNT(*) AS Count,
    SUM(TotalAmount) AS TotalValue
FROM Orders
WHERE TotalAmount BETWEEN @ManagerThreshold * 0.95 AND @ManagerThreshold - 0.01
UNION ALL
SELECT 'Orders within 5% below Director threshold', COUNT(*), SUM(TotalAmount)
FROM Orders
WHERE TotalAmount BETWEEN @DirectorThreshold * 0.95 AND @DirectorThreshold - 0.01
ORDER BY Count DESC;
```

## Explanation

**Aggregation-based bypass detection**
Single-order threshold checks are easily circumvented by splitting. The correct check aggregates related orders — same customer, same time period — and compares the total to the threshold. The key clause: `HAVING SUM(TotalAmount) >= threshold AND MAX(TotalAmount) < threshold` — the aggregate triggers the threshold but no individual record does.

**Near-threshold clustering**
The 5% proximity check in Step 3 catches individual orders that are deliberately priced just below a threshold. This is the single-transaction equivalent of structuring. A legitimate £9,800 order exists; a £9,800 order from a customer who has three similar ones in the same month is a pattern.

**Time window definition**
Using monthly aggregation (year + month) is a common simplification. A more robust check uses a rolling window (any 30-calendar-day period) to catch splits that span a month boundary: e.g., £5,000 on January 31 and £6,000 on February 1, which totals £11,000 but appears in different months.

**Defining "related" records**
What makes two orders "related" for bypass detection depends on the procurement policy: same supplier, same category, same project, same department. In this example, we use same customer per month. In a procurement system, grouping by supplier would be more appropriate.

## Severity
**High** — Approval threshold bypass circumvents financial controls, enabling commitments to be made without required governance oversight. In regulated industries (financial services, healthcare procurement, government contracting), bypassed approvals represent a control failure that must be disclosed in audit reports and may void the underlying contracts.
