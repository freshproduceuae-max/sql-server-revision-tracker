# G07-T06 — Business Rules | Product Stock Oversell

## ID
G07-T06

## Group
7 — Business Rules

## Type
Product Stock Oversell — Orders Accepted Exceeding Available Stock Quantity

## Live Scenario
A flash sale platform sells limited-edition items. The warehouse has 50 units of a product (`StockQuantity = 50`). The platform's checkout process reads StockQuantity, confirms availability, and then writes the order — but under high concurrency during the flash sale, 127 concurrent users pass the availability check simultaneously before any order reduces the stock count. All 127 users complete checkout. The platform now has 127 orders for 50 physical units. Customer service must contact 77 customers to apologise and offer refunds — creating reputational damage and £3,200 in processing costs.

## The Question
> Stock validation must compare confirmed orders against available quantity. A simple current-quantity check is insufficient under concurrent load — the correct pattern queries total units ordered (from the Orders table) and compares it to the stated StockQuantity. SQL can detect post-hoc oversells even when real-time concurrency control failed.
> **"Find all Products where the total quantity ordered (summed across active Orders) exceeds the available StockQuantity — detecting oversell after the fact."**

## Table Reference
**Products** — `schemas/03_Products.csv`
**Orders** — `schemas/02_Orders.csv`

## Solution Query

```sql
-- Step 1: Detect oversold products — orders exceed stock
-- Note: Orders table doesn't have Quantity column in our schema,
-- so we use COUNT(OrderID) per product as a proxy for units ordered
WITH ProductOrderCounts AS (
    SELECT
        ProductID,
        COUNT(*) AS TotalOrderedUnits,
        SUM(TotalAmount) AS TotalOrderValue,
        SUM(CASE WHEN Status NOT IN ('Cancelled','Refunded') THEN 1 ELSE 0 END)
            AS ActiveOrderedUnits
    FROM Orders
    WHERE ProductID IS NOT NULL
    GROUP BY ProductID
)
SELECT
    p.ProductID,
    p.ProductName,
    p.ProductCode,
    p.StockQuantity AS AvailableStock,
    ISNULL(poc.ActiveOrderedUnits, 0) AS ActiveOrders,
    ISNULL(poc.ActiveOrderedUnits, 0) - p.StockQuantity AS OversellAmount,
    CASE
        WHEN ISNULL(poc.ActiveOrderedUnits, 0) > p.StockQuantity
             THEN 'OVERSELL: Orders exceed available stock by '
                  + CAST(ISNULL(poc.ActiveOrderedUnits, 0) - p.StockQuantity AS VARCHAR) + ' units'
        WHEN ISNULL(poc.ActiveOrderedUnits, 0) = p.StockQuantity
             THEN 'AT LIMIT: Stock fully committed'
        WHEN p.StockQuantity = 0
             THEN 'OUT OF STOCK: No stock available'
        WHEN ISNULL(poc.ActiveOrderedUnits, 0) > p.StockQuantity * 0.80
             THEN 'WARNING: >80% of stock committed'
        ELSE 'Stock available'
    END AS StockStatus
FROM Products p
LEFT JOIN ProductOrderCounts poc ON p.ProductID = poc.ProductID
WHERE p.StockQuantity IS NOT NULL
ORDER BY OversellAmount DESC;

-- Step 2: Out-of-stock products with pending orders
SELECT
    p.ProductID,
    p.ProductName,
    p.StockQuantity,
    COUNT(o.OrderID) AS PendingOrders,
    SUM(o.TotalAmount) AS PendingOrderValue,
    'CRITICAL: Product out of stock with pending orders' AS Issue
FROM Products p
JOIN Orders o ON p.ProductID = o.ProductID
WHERE p.StockQuantity = 0
  AND o.Status IN ('Pending', 'Processing')
GROUP BY p.ProductID, p.ProductName, p.StockQuantity
ORDER BY PendingOrders DESC;

-- Step 3: Stock level categories
SELECT
    CASE
        WHEN StockQuantity = 0             THEN 'Out of stock'
        WHEN StockQuantity BETWEEN 1 AND 5 THEN 'Critical low (1–5)'
        WHEN StockQuantity BETWEEN 6 AND 20 THEN 'Low (6–20)'
        WHEN StockQuantity BETWEEN 21 AND 100 THEN 'Normal (21–100)'
        ELSE 'High (>100)'
    END AS StockBand,
    COUNT(*) AS ProductCount,
    SUM(StockQuantity) AS TotalUnits,
    SUM(Price * StockQuantity) AS StockValue
FROM Products
WHERE StockQuantity IS NOT NULL
  AND IsActive = 1
GROUP BY
    CASE
        WHEN StockQuantity = 0             THEN 'Out of stock'
        WHEN StockQuantity BETWEEN 1 AND 5 THEN 'Critical low (1–5)'
        WHEN StockQuantity BETWEEN 6 AND 20 THEN 'Low (6–20)'
        WHEN StockQuantity BETWEEN 21 AND 100 THEN 'Normal (21–100)'
        ELSE 'High (>100)'
    END
ORDER BY MIN(StockQuantity);

-- Step 4: Negative stock quantity (should never occur)
SELECT
    ProductID,
    ProductName,
    StockQuantity,
    'IMPOSSIBLE: Negative stock quantity — data integrity error' AS Issue
FROM Products
WHERE StockQuantity < 0;

-- Step 5: Products with orders but no stock record
SELECT
    o.ProductID,
    COUNT(DISTINCT o.OrderID) AS OrderCount,
    'WARNING: Orders reference ProductID with no stock record' AS Issue
FROM Orders o
LEFT JOIN Products p ON o.ProductID = p.ProductID
WHERE p.ProductID IS NULL
GROUP BY o.ProductID;
```

## Explanation

**Post-hoc vs real-time stock check**
SQL validation detects oversells that have already occurred — it cannot prevent concurrent oversells in real time. Real-time prevention requires database-level pessimistic locking (`SELECT ... WITH (UPDLOCK)`) or optimistic concurrency with a stock version counter. The SQL query is the detection tool; the architectural pattern is the prevention tool.

**Active orders only**
Cancelled and refunded orders should not count against stock — those units are returned to available inventory. `WHERE Status NOT IN ('Cancelled','Refunded')` ensures only active commitments are counted.

**COUNT(*) as unit proxy**
In the current schema, `Orders` does not have a Quantity column — each order row represents one order event. A real inventory system would sum `OrderLines.Quantity` to get total units. The COUNT-based approach here demonstrates the pattern; replace with `SUM(Quantity)` in a fully normalised schema.

**Negative StockQuantity**
A negative stock count is a data integrity error — physical stock cannot be negative. It indicates either an inventory system bug (adjustments applied out of order) or an oversell that has been reflected in the stock count but not resolved. Step 4 treats these as hard errors.

## Severity
**High** — Oversells create fulfilled orders that cannot be physically completed. Each oversold unit requires either a customer cancellation (reputational damage) or emergency stock procurement (cost overrun). High-demand products during peak events (flash sales, product launches) are the highest-risk scenario.
