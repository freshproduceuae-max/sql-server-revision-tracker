# G07-T10 — Business Rules | Refund Without Original Transaction

## ID
G07-T10

## Group
7 — Business Rules

## Type
Refund Without Original Transaction — A Refund Record Has No Matching Original Purchase

## Live Scenario
A refund processing system processes refunds from a customer service portal that queries refund eligibility from a separate CRM system. A data synchronisation lag causes the CRM to show a customer's purchase history from a now-deleted test order. A customer service agent issues a £240 refund for a transaction that never existed in the live payment system — only in the test environment's CRM data. The refund is processed to the customer's account. A weekly reconciliation between the payments system and the CRM identifies the orphan refund three days later, by which time the funds have been disbursed.

## The Question
> Refunds must reference a valid original transaction. A refund with no matching purchase is either a data entry error, a fraud attempt, or a system integration failure. SQL validates refunds by checking that each refund links to an existing, completed original transaction.
> **"Find all Transactions marked as refunds that do not have a corresponding original purchase transaction for the same OrderID, and find refund amounts that exceed the original purchase amount."**

## Table Reference
**Transactions** — `schemas/05_Transactions.csv`
**Orders** — `schemas/02_Orders.csv`

## Solution Query

```sql
-- Step 1: Identify refund transactions (negative amounts = refunds in this schema)
-- In systems with a TransactionType column, filter on Type = 'Refund'
SELECT
    TransactionID,
    OrderID,
    Amount,
    Currency,
    TransactionDate,
    'Identified as refund (negative amount)' AS TransactionType
FROM Transactions
WHERE Amount < 0
ORDER BY Amount;

-- Step 2: Refunds without a matching positive (original) transaction for the same Order
WITH Purchases AS (
    SELECT OrderID, SUM(Amount) AS TotalPurchased
    FROM Transactions WHERE Amount > 0
    GROUP BY OrderID
),
Refunds AS (
    SELECT OrderID, SUM(ABS(Amount)) AS TotalRefunded, COUNT(*) AS RefundCount
    FROM Transactions WHERE Amount < 0
    GROUP BY OrderID
)
SELECT
    r.OrderID,
    r.TotalRefunded,
    r.RefundCount,
    ISNULL(p.TotalPurchased, 0) AS TotalPurchased,
    CASE
        WHEN p.OrderID IS NULL
             THEN 'NO ORIGINAL: Refund with no purchase for this OrderID'
        WHEN r.TotalRefunded > p.TotalPurchased
             THEN 'EXCESS REFUND: Refunded more than original purchase amount'
        ELSE 'Refund within original purchase amount'
    END AS RefundValidation
FROM Refunds r
LEFT JOIN Purchases p ON r.OrderID = p.OrderID
WHERE p.OrderID IS NULL
   OR r.TotalRefunded > p.TotalPurchased
ORDER BY r.TotalRefunded DESC;

-- Step 3: Refunds where the Order itself has no record (orphan at order level)
SELECT
    t.TransactionID,
    t.OrderID,
    t.Amount AS RefundAmount,
    t.TransactionDate,
    o.OrderID AS OrderExists,
    CASE
        WHEN o.OrderID IS NULL THEN 'CRITICAL: Refund references non-existent OrderID'
        WHEN o.Status = 'Cancelled' THEN 'WARNING: Refund on cancelled order — verify'
        WHEN o.Status = 'Pending'   THEN 'WARNING: Refund on still-pending order'
        ELSE 'Order exists'
    END AS OrderConsistency
FROM Transactions t
LEFT JOIN Orders o ON t.OrderID = o.OrderID
WHERE t.Amount < 0
  AND (o.OrderID IS NULL OR o.Status IN ('Cancelled','Pending'));

-- Step 4: Refund timing validation — refund before purchase
WITH OrderedTx AS (
    SELECT
        OrderID,
        TransactionDate AS RefundDate,
        Amount AS RefundAmount,
        (SELECT MIN(TransactionDate) FROM Transactions t2
         WHERE t2.OrderID = t.OrderID AND t2.Amount > 0) AS OriginalPurchaseDate
    FROM Transactions t
    WHERE Amount < 0
)
SELECT
    OrderID,
    RefundDate,
    OriginalPurchaseDate,
    RefundAmount,
    DATEDIFF(DAY, OriginalPurchaseDate, RefundDate) AS DaysAfterPurchase,
    CASE
        WHEN OriginalPurchaseDate IS NULL
             THEN 'NO PURCHASE DATE: No original purchase found'
        WHEN RefundDate < OriginalPurchaseDate
             THEN 'IMPOSSIBLE: Refund before purchase date'
        WHEN DATEDIFF(DAY, OriginalPurchaseDate, RefundDate) > 365
             THEN 'WARNING: Refund > 1 year after purchase'
        ELSE 'Timing valid'
    END AS RefundTimingCheck
FROM OrderedTx
ORDER BY DaysAfterPurchase;

-- Step 5: Refund-to-purchase ratio by order
SELECT
    o.OrderID,
    o.TotalAmount AS OrderAmount,
    SUM(CASE WHEN t.Amount > 0 THEN t.Amount ELSE 0 END) AS TotalPaid,
    SUM(CASE WHEN t.Amount < 0 THEN ABS(t.Amount) ELSE 0 END) AS TotalRefunded,
    ROUND(
        100.0 * SUM(CASE WHEN t.Amount < 0 THEN ABS(t.Amount) ELSE 0 END)
        / NULLIF(SUM(CASE WHEN t.Amount > 0 THEN t.Amount ELSE 0 END), 0),
        1
    ) AS RefundPct,
    SUM(t.Amount) AS NetAmount
FROM Orders o
JOIN Transactions t ON o.OrderID = t.OrderID
GROUP BY o.OrderID, o.TotalAmount
HAVING SUM(CASE WHEN t.Amount < 0 THEN ABS(t.Amount) ELSE 0 END) > 0
ORDER BY RefundPct DESC;
```

## Explanation

**Negative amounts as refund indicator**
In a single-table transaction ledger, refunds are typically represented as negative amounts. Identifying refunds as `WHERE Amount < 0` is the standard pattern when no explicit TransactionType column exists. In systems with a TransactionType column, filter on `WHERE TransactionType = 'Refund'`.

**LEFT JOIN for orphan detection**
`LEFT JOIN Purchases ON r.OrderID = p.OrderID WHERE p.OrderID IS NULL` detects refund groups with no matching purchase group. This is the standard anti-join pattern for orphan detection across derived aggregations.

**Excess refund detection**
A refund greater than the original purchase is mathematically impossible in a valid system — the customer cannot receive back more than they paid. `r.TotalRefunded > p.TotalPurchased` catches these cases, which may indicate: a duplicate refund entry, a currency conversion error, or a fraud attempt.

**Refund timing**
A refund cannot precede its original purchase. Step 4 compares the refund date to the earliest purchase date for the same order using a correlated subquery. A refund before purchase is a temporal impossibility — clock drift, manual back-dating, or system error.

## Severity
**Critical** — Refunds without original transactions represent direct financial loss: funds disbursed with no corresponding revenue to offset. Excess refunds compound this by refunding more than was collected. Both patterns are also fraud indicators — the SoD check should follow any orphan refund discovery.
