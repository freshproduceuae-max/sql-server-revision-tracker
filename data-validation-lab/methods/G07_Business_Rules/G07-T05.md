# G07-T05 — Business Rules | Duplicate Transaction Detection

## ID
G07-T05

## Group
7 — Business Rules

## Type
Duplicate Transaction Detection — Same Payment Event Recorded More Than Once

## Live Scenario
A payment gateway integration retries failed API calls with exponential backoff. The gateway processes the payment successfully on the first attempt but the acknowledgment response is lost due to a network timeout. The application retries the payment, the gateway processes it again, and two payment transactions are created for the same order. The customer is charged twice. An automatic reconciliation script compares transaction count to order count but uses a date-level granularity that groups both transactions into the same day, masking the duplication. Three weeks pass before a customer notices the double charge on their bank statement and calls customer service.

## The Question
> Duplicate transactions are the same payment event recorded multiple times. They are identified by matching on the combination of keys that should uniquely identify a payment: OrderID + Amount + TransactionDate (or a correlation ID, idempotency key, or bank reference). SQL detects them by finding groups of rows that share all uniqueness-determining attributes.
> **"Find all pairs of Transactions where the same OrderID, Amount, and TransactionDate appear more than once — potential duplicate payment events."**

## Table Reference
**Transactions** — `schemas/05_Transactions.csv`

## Solution Query

```sql
-- Step 1: Exact duplicates — same OrderID, Amount, and TransactionDate
SELECT
    OrderID,
    Amount,
    Currency,
    CAST(TransactionDate AS DATE) AS TxDate,
    COUNT(*) AS OccurrenceCount,
    STRING_AGG(CAST(TransactionID AS VARCHAR), ', ') AS TransactionIDs,
    'DUPLICATE: Same order/amount/date combination' AS Issue
FROM Transactions
GROUP BY OrderID, Amount, Currency, CAST(TransactionDate AS DATE)
HAVING COUNT(*) > 1
ORDER BY OccurrenceCount DESC, OrderID;

-- Step 2: Near-duplicate detection — same order and amount within a short time window
WITH OrderedTransactions AS (
    SELECT
        TransactionID,
        OrderID,
        Amount,
        Currency,
        TransactionDate,
        LAG(TransactionDate) OVER (PARTITION BY OrderID, Amount ORDER BY TransactionDate)
            AS PrevTransactionDate,
        LAG(TransactionID) OVER (PARTITION BY OrderID, Amount ORDER BY TransactionDate)
            AS PrevTransactionID
    FROM Transactions
)
SELECT
    TransactionID,
    PrevTransactionID AS PossibleDuplicateOf,
    OrderID,
    Amount,
    TransactionDate,
    PrevTransactionDate,
    DATEDIFF(MINUTE, PrevTransactionDate, TransactionDate) AS MinutesBetween,
    CASE
        WHEN DATEDIFF(MINUTE, PrevTransactionDate, TransactionDate) < 5
             THEN 'HIGH RISK: Same amount/order within 5 minutes — likely retry duplicate'
        WHEN DATEDIFF(HOUR, PrevTransactionDate, TransactionDate) < 1
             THEN 'MEDIUM RISK: Same amount/order within 1 hour — review'
        ELSE 'Low risk — time gap > 1 hour'
    END AS DuplicateRisk
FROM OrderedTransactions
WHERE PrevTransactionDate IS NOT NULL
  AND DATEDIFF(MINUTE, PrevTransactionDate, TransactionDate) < 60
ORDER BY MinutesBetween;

-- Step 3: Correlation ID duplicate check (idempotency key)
-- If CorrelationID is present and meant to be unique, duplicate CorrelationIDs = duplicate transactions
SELECT
    CorrelationID,
    COUNT(*) AS TxCount,
    SUM(Amount) AS TotalAmount,
    MIN(TransactionDate) AS FirstOccurrence,
    MAX(TransactionDate) AS LastOccurrence,
    STRING_AGG(CAST(TransactionID AS VARCHAR), ', ') AS AllTransactionIDs,
    'DUPLICATE CorrelationID — idempotency violation' AS Issue
FROM Transactions
WHERE CorrelationID IS NOT NULL
GROUP BY CorrelationID
HAVING COUNT(*) > 1
ORDER BY TxCount DESC;

-- Step 4: Financial impact of detected duplicates
SELECT
    COUNT(*) AS DuplicateGroupCount,
    SUM(ExtraAmount) AS TotalOverchargeAmount,
    SUM(DuplicateTransactions) AS TotalDuplicateTransactions
FROM (
    SELECT
        OrderID,
        Amount,
        COUNT(*) - 1 AS DuplicateTransactions,
        Amount * (COUNT(*) - 1) AS ExtraAmount
    FROM Transactions
    GROUP BY OrderID, Amount, Currency, CAST(TransactionDate AS DATE)
    HAVING COUNT(*) > 1
) duplicates;

-- Step 5: Bank account number duplicate within a time window
-- Multiple transactions to the same bank account within 24 hours for same amount
SELECT
    BankAccountNumber,
    CAST(TransactionDate AS DATE) AS TxDate,
    Amount,
    COUNT(*) AS TxCount,
    SUM(Amount) AS TotalPaid,
    'WARNING: Multiple payments to same account/amount/day' AS Note
FROM Transactions
WHERE BankAccountNumber IS NOT NULL
GROUP BY BankAccountNumber, CAST(TransactionDate AS DATE), Amount
HAVING COUNT(*) > 1
ORDER BY TxCount DESC;
```

## Explanation

**Unique key definition for duplicates**
A transaction duplicate is defined by the combination of fields that should uniquely identify it. Common natural keys: `(OrderID, Amount, Currency, Date)` or an idempotency key (`CorrelationID`). The choice depends on what guarantees are available — if a CorrelationID is assigned by the payment initiator, it is the most reliable duplicate key.

**Exact vs near-duplicate**
Exact duplicates (same values in all key fields) are unambiguous. Near-duplicates (same order and amount, slightly different timestamp — due to retry timing) require a time window tolerance. The 5-minute window in Step 2 is appropriate for API retry patterns; adjust based on the retry backoff policy.

**Idempotency keys**
Modern payment APIs issue idempotency keys (correlation IDs) to prevent duplicate processing at the gateway level. Step 3 checks whether these keys are actually unique in the database — if the same CorrelationID appears twice, either the idempotency key was reused (a key generation bug) or the gateway processed the same idempotency key twice (a gateway bug).

**LAG for consecutive-record comparison**
`LAG(TransactionDate) OVER (PARTITION BY OrderID, Amount ORDER BY TransactionDate)` returns the timestamp of the previous transaction with the same order and amount. Comparing the current transaction's date to its predecessor's date reveals suspiciously short gaps that indicate retry duplicates.

## Severity
**Critical** — Duplicate transactions charge customers multiple times for a single purchase. Discovery typically requires customer complaint escalation (3–4 weeks post-transaction), during which the customer has been overcharged. Remediation requires refunds, customer service resources, and potentially regulatory reporting if the error affects a large number of customers.
