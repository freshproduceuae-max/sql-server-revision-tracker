# G07-T03 — Business Rules | Discount / Commission Rate Validity

## ID
G07-T03

## Group
7 — Business Rules

## Type
Discount / Commission Rate Validity — Rate Outside Approved Range or Requires Authorisation

## Live Scenario
A sales organisation allows salespeople to offer discounts of up to 10% without approval, up to 20% with manager approval, and up to 30% with director approval. An integration bug populates `DiscountPercent` with the raw decimal value from the API payload — a 10% discount sent as `0.10` is stored as `0.10` (interpreted as 0.10% instead of 10%). All 4,200 orders processed during a two-week integration window have DiscountPercent = 0.10 where the intended value was 10. Additionally, a salesperson manually entered `110` (typing 110 instead of 10) for one order, creating a discount that exceeds 100% and results in the customer being charged a negative amount.

## The Question
> Discount and commission rates must fall within defined bands. A rate of 0 is suspicious (is this intentional?), a rate above the approved maximum is a policy violation, and a rate above 100% is mathematically impossible. Each band may require different levels of authorisation.
> **"Find all Products where DiscountPercent is outside the valid range 0–30%, and find all SalesTargets where CommissionRate is outside the approved band, classifying violations by severity."**

## Table Reference
**Products** — `schemas/03_Products.csv`
**SalesTargets** — `schemas/06_SalesTargets.csv`

## Solution Query

```sql
-- Step 1: Product discount rate validation
SELECT
    ProductID,
    ProductName,
    Price,
    DiscountPercent,
    CASE
        WHEN DiscountPercent IS NULL         THEN 'NULL: No discount set'
        WHEN DiscountPercent < 0             THEN 'INVALID: Negative discount'
        WHEN DiscountPercent > 100           THEN 'IMPOSSIBLE: Discount > 100%'
        WHEN DiscountPercent > 30            THEN 'VIOLATION: Exceeds max 30% — director approval needed'
        WHEN DiscountPercent > 20            THEN 'REQUIRES APPROVAL: 21–30% needs manager sign-off'
        WHEN DiscountPercent > 10            THEN 'MANAGER TIER: 11–20% discount (check approval)'
        WHEN DiscountPercent = 0             THEN 'ZERO: No discount applied'
        WHEN DiscountPercent < 0.5           THEN 'WARNING: Discount < 0.5% — possible decimal entry error'
        ELSE 'STANDARD: Within 0–10% self-approval band'
    END AS DiscountValidation,
    -- Effective price after discount
    ROUND(Price * (1 - DiscountPercent / 100.0), 2) AS EffectivePrice
FROM Products
WHERE DiscountPercent < 0
   OR DiscountPercent > 30
   OR DiscountPercent IS NULL
ORDER BY DiscountPercent DESC;

-- Step 2: Commission rate validation for sales targets
SELECT
    TargetID,
    SalespersonID,
    Year,
    Quarter,
    TargetAmount,
    CommissionRate,
    CASE
        WHEN CommissionRate IS NULL          THEN 'NULL: No commission rate set'
        WHEN CommissionRate < 0              THEN 'INVALID: Negative commission rate'
        WHEN CommissionRate > 100            THEN 'IMPOSSIBLE: Rate > 100%'
        WHEN CommissionRate > 25             THEN 'VIOLATION: Above maximum 25% commission'
        WHEN CommissionRate > 15             THEN 'HIGH: 16–25% commission — verify authorisation'
        WHEN CommissionRate = 0              THEN 'ZERO: No commission — non-commissioned target?'
        ELSE 'VALID: Within standard commission range'
    END AS CommissionValidation,
    ROUND(TargetAmount * CommissionRate / 100.0, 2) AS ImpliedCommissionValue
FROM SalesTargets
WHERE CommissionRate IS NULL
   OR CommissionRate < 0
   OR CommissionRate > 25
ORDER BY CommissionRate DESC;

-- Step 3: Decimal entry error detection
-- A discount of 0.10 when 10 was intended — common integration error
SELECT
    ProductID,
    ProductName,
    DiscountPercent,
    DiscountPercent * 100 AS LikelyIntendedPercent,
    'POSSIBLE ENTRY ERROR: Very small percentage — was this meant to be ' +
        CAST(ROUND(DiscountPercent * 100, 0) AS VARCHAR) + '%?' AS Warning
FROM Products
WHERE DiscountPercent > 0 AND DiscountPercent < 1  -- likely a decimal fraction entered instead of percent
ORDER BY DiscountPercent;

-- Step 4: Commission summary by tier for reporting
SELECT
    CASE
        WHEN CommissionRate = 0       THEN 'Non-commissioned'
        WHEN CommissionRate <= 5      THEN '1–5% (base tier)'
        WHEN CommissionRate <= 10     THEN '6–10% (standard tier)'
        WHEN CommissionRate <= 15     THEN '11–15% (premium tier)'
        WHEN CommissionRate <= 25     THEN '16–25% (high performer)'
        ELSE 'Above policy maximum'
    END AS CommissionBand,
    COUNT(*) AS TargetCount,
    SUM(TargetAmount) AS TotalTargetValue,
    ROUND(AVG(CommissionRate), 2) AS AvgRate,
    SUM(ROUND(TargetAmount * CommissionRate / 100.0, 2)) AS TotalCommissionPool
FROM SalesTargets
WHERE CommissionRate IS NOT NULL
GROUP BY
    CASE
        WHEN CommissionRate = 0       THEN 'Non-commissioned'
        WHEN CommissionRate <= 5      THEN '1–5% (base tier)'
        WHEN CommissionRate <= 10     THEN '6–10% (standard tier)'
        WHEN CommissionRate <= 15     THEN '11–15% (premium tier)'
        WHEN CommissionRate <= 25     THEN '16–25% (high performer)'
        ELSE 'Above policy maximum'
    END
ORDER BY TotalCommissionPool DESC;
```

## Explanation

**Rate as percentage vs decimal fraction**
The most common discount/commission data entry error is mixing up percentage notation (10 = 10%) and decimal notation (0.10 = 10%). A value of 0.10 in a "DiscountPercent" column is ambiguous: it could mean 0.10% (correct for a micro-discount) or the developer meant to store 10% as 0.10 (decimal fraction, wrong column convention). Plausibility checks catch values in the range 0 to 1 where 0–100 is expected.

**Maximum rate enforcement by tier**
The tiered check (self-approval, manager, director) encodes an authorisation workflow in a validation query. Each rate band triggers a different severity, directing the validation output to the appropriate review team.

**Negative effective price**
A discount > 100% produces a negative effective price: `Price * (1 - 110/100) = Price * (-0.1) = -£X`. This means the business would owe the customer money on every unit sold — a catastrophic billing error if processed at scale.

**Commission pool visibility**
Step 4 computes the total commission liability (`TargetAmount × Rate`) by tier. This gives finance visibility into the total commission obligation before it is paid, and flags any tier with implausibly high payout rates.

## Severity
**High** — A discount > 100% results in negative revenue per transaction. A commission rate above the policy maximum creates an unauthorised financial liability. Decimal entry errors affecting thousands of transactions systematically underprice products or overcompensate salespeople.
