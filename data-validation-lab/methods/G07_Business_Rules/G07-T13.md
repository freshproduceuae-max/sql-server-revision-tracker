# G07-T13 — Business Rules | Geo-Restriction Violation

## ID
G07-T13

## Group
7 — Business Rules

## Type
Geo-Restriction Violation — Transaction or Access from Unauthorised Geography

## Live Scenario
A financial services company is licensed to operate in the UK and EU only. Its payment platform should reject transactions from IP addresses geolocated outside these regions. A VPN detection system is in place, but a configuration error disables it for API requests (only web browser requests are screened). Bot-driven API calls from IP addresses in sanctioned jurisdictions process 312 transactions totalling £89,000 before the configuration error is found. The FCA requires a report explaining the transactions, and the firm must conduct enhanced due diligence on each transaction to demonstrate they did not involve sanctioned entities.

## The Question
> Geographic restrictions control which regions can originate or receive transactions. Validation checks the source location (IP address, registered address, billing country) against the permitted region list and flags transactions from prohibited origins.
> **"Find all Transactions where SourceIP originates from a known restricted CIDR range or where the Customer's Country is not in the approved operating list."**

## Table Reference
**Transactions** — `schemas/05_Transactions.csv`
**Customers** — `schemas/01_Customers.csv`
**Orders** — `schemas/02_Orders.csv`

## Solution Query

```sql
-- Step 1: Customer country geo-restriction check
-- Operating licence: UK and EU countries only
DECLARE @ApprovedCountries TABLE (CountryCode CHAR(2), CountryName VARCHAR(60), Region VARCHAR(20));
INSERT INTO @ApprovedCountries VALUES
    ('GB', 'United Kingdom', 'UK'),
    ('DE', 'Germany', 'EU'),
    ('FR', 'France', 'EU'),
    ('NL', 'Netherlands', 'EU'),
    ('IE', 'Ireland', 'EU'),
    ('ES', 'Spain', 'EU'),
    ('IT', 'Italy', 'EU'),
    ('BE', 'Belgium', 'EU'),
    ('SE', 'Sweden', 'EU'),
    ('PL', 'Poland', 'EU');

SELECT
    c.CustomerID,
    c.FirstName + ' ' + c.LastName AS CustomerName,
    c.Country,
    ac.Region,
    CASE
        WHEN c.Country IS NULL          THEN 'RISK: No country on file — cannot verify geo-restriction'
        WHEN ac.CountryCode IS NULL     THEN 'VIOLATION: Country not in approved operating list'
        ELSE 'Country approved — ' + ac.Region
    END AS GeoComplianceStatus
FROM Customers c
LEFT JOIN @ApprovedCountries ac ON c.Country = ac.CountryCode
WHERE ac.CountryCode IS NULL OR c.Country IS NULL;

-- Step 2: IP-based geo flag (using known ranges as proxy)
-- In production: join to a GeoIP reference table with CIDR ranges
-- Here: use PARSENAME to extract the first octet and flag known restricted ranges
DECLARE @RestrictedIPPrefixes TABLE (FirstOctet INT, Description VARCHAR(100));
INSERT INTO @RestrictedIPPrefixes VALUES
    (10,  'RFC1918 Private range — should not appear as external SourceIP'),
    (127, 'Loopback — localhost traffic in production data'),
    (0,   'Reserved — invalid source');

SELECT
    t.TransactionID,
    t.OrderID,
    t.SourceIP,
    t.Amount,
    t.TransactionDate,
    CAST(PARSENAME(t.SourceIP, 4) AS INT) AS FirstOctet,
    r.Description AS RestrictionReason,
    CASE
        WHEN t.SourceIP IS NULL THEN 'RISK: No source IP recorded'
        WHEN r.FirstOctet IS NOT NULL THEN 'FLAG: IP from restricted range — ' + r.Description
        ELSE 'IP range not flagged'
    END AS IPGeoFlag
FROM Transactions t
LEFT JOIN @RestrictedIPPrefixes r
    ON TRY_CAST(PARSENAME(t.SourceIP, 4) AS INT) = r.FirstOctet
WHERE t.SourceIP IS NULL
   OR r.FirstOctet IS NOT NULL;

-- Step 3: Cross-check customer country vs transaction IP location
-- Flag customers whose registered country is approved but whose IP suggests a different region
SELECT
    t.TransactionID,
    t.SourceIP,
    o.CustomerID,
    c.Country AS RegisteredCountry,
    -- Simple heuristic: private IPs from external customers are suspicious
    CASE
        WHEN c.Country IN ('GB','DE','FR','NL','IE','ES','IT','BE','SE','PL')
         AND TRY_CAST(PARSENAME(t.SourceIP, 4) AS INT) IN (10, 172, 192)
             THEN 'ANOMALY: EU/UK customer using private IP range — VPN or NAT'
        ELSE 'No geo mismatch detected'
    END AS GeoMismatchFlag
FROM Transactions t
JOIN Orders o ON t.OrderID = o.OrderID
JOIN Customers c ON o.CustomerID = c.CustomerID
WHERE TRY_CAST(PARSENAME(t.SourceIP, 4) AS INT) IN (10, 172, 192)
  AND c.Country IN ('GB','DE','FR','NL','IE','ES','IT','BE','SE','PL');

-- Step 4: Orders from non-approved countries
SELECT
    o.OrderID,
    o.CustomerID,
    c.Country,
    o.TotalAmount,
    o.OrderDate,
    'VIOLATION: Order from customer in non-approved country' AS Issue
FROM Orders o
JOIN Customers c ON o.CustomerID = c.CustomerID
LEFT JOIN @ApprovedCountries ac ON c.Country = ac.CountryCode
WHERE ac.CountryCode IS NULL
  AND c.Country IS NOT NULL;

-- Step 5: Geo-compliance summary
SELECT
    'Customers in non-approved countries' AS Check,
    COUNT(*) AS Count,
    SUM(CASE WHEN o.OrderID IS NOT NULL THEN 1 ELSE 0 END) AS WithOrders
FROM Customers c
LEFT JOIN Orders o ON c.CustomerID = o.CustomerID
LEFT JOIN @ApprovedCountries ac ON c.Country = ac.CountryCode
WHERE ac.CountryCode IS NULL AND c.Country IS NOT NULL
GROUP BY 'Customers in non-approved countries';
```

## Explanation

**Two geo-validation layers**
1. **Country of registration** (`Customers.Country`): static, set at account creation, based on the customer's declared location.
2. **Transaction IP origin**: dynamic, reflects where the transaction was sent from. Both should be in approved regions; a mismatch between them is a fraud indicator.

**PARSENAME for IP parsing**
`PARSENAME('192.168.1.100', 4)` returns `'192'` — the first octet. PARSENAME was designed for SQL object names (`server.database.schema.table`) but works on any 4-part dot-delimited string. Always wrap in `TRY_CAST` in case the value is not a valid dotted-quad.

**Private IP ranges in production data**
RFC1918 private IPs (10.x.x.x, 172.16.x.x–172.31.x.x, 192.168.x.x) should not appear as source IPs for external customer transactions. Their presence indicates: NAT gateway not replacing source IP, test data in production, or internal fraud (transaction originated from within the corporate network).

**Sanctions screening is not SQL**
Full geo-restriction compliance also requires sanctions list screening (OFAC, UK Sanctions List), which matches individual entity names against government-maintained lists. This requires external data integration — SQL can check country codes against an approved list but cannot perform entity-level sanctions screening.

## Severity
**Critical** — Transactions from restricted or sanctioned jurisdictions expose the company to regulatory penalties, licence revocation, and criminal liability under sanctions laws (UK Sanctions and Anti-Money Laundering Act 2018, OFAC regulations). Each non-compliant transaction must be reported and assessed.
