# G18-T07 — Cross-System | Lookup Table Synchronisation Validation

## ID
G18-T07

## Group
18 — Cross-System

## Type
Lookup Table Synchronisation Validation — Verifying That Reference Tables Are Consistent Across Multiple Systems

## Live Scenario
A UK retailer uses three systems: a POS system, a CRM, and an e-commerce platform. All three reference a shared Product master (Products table) for product names and prices. When a new product is added to the POS system's product master, it should automatically synchronise to the CRM and e-commerce platform within 30 minutes. After a network configuration change, the synchronisation job fails silently for 11 days. During this period, 34 new products are added to the POS — these products are sold in stores but are invisible to the CRM (cannot be added to loyalty campaigns) and on the e-commerce platform (cannot be purchased online). The lookup synchronisation validation check, comparing the product count and product IDs across the three system representations, flags the 34 missing products on the first day.

## The Question
> Lookup table synchronisation validation compares the contents of a reference or lookup table across systems to verify that all systems share the same version of the reference data. SQL detects additions (new codes in one system not yet propagated to others), deletions (codes removed from one system but still present in others), updates (same code but different values — price, name, status), and orphaned references (transactions using codes that exist in one system's lookup but not another's).
> **"Validate lookup table synchronisation across the available tables: verify that all ProductIDs used in Orders exist in the Products master, check that CustomerIDs used in Orders exist in the Customers master, identify any lookup values referenced in Transactions that don't exist in their corresponding masters, and produce a synchronisation health report."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Customers** — `schemas/01_Customers.csv`
**Products** — `schemas/03_Products.csv`
**Transactions** — `schemas/05_Transactions.csv`

## Solution Query

```sql
-- Step 1: ProductID lookup synchronisation — Orders vs Products master
WITH OrderProductIDs AS (
    SELECT DISTINCT ProductID AS ProductID, 'Orders' AS SourceSystem
    FROM Orders WHERE ProductID IS NOT NULL
),
ProductMasterIDs AS (
    SELECT DISTINCT ProductID AS ProductID, 'Products' AS SourceSystem
    FROM Products WHERE ProductID IS NOT NULL
)
SELECT
    COALESCE(o.ProductID, p.ProductID) AS ProductID,
    o.SourceSystem AS InOrders,
    p.SourceSystem AS InProducts,
    CASE
        WHEN o.ProductID IS NOT NULL AND p.ProductID IS NULL
             THEN 'SYNC GAP: ProductID "' + o.ProductID
                  + '" referenced in Orders but not in Products master — lookup table out of sync'
        WHEN o.ProductID IS NULL AND p.ProductID IS NOT NULL
             THEN 'UNUSED: ProductID "' + p.ProductID
                  + '" in Products master but never ordered — acceptable'
        ELSE 'SYNCHRONISED: ProductID present in both'
    END AS SyncFlag
FROM OrderProductIDs o
FULL OUTER JOIN ProductMasterIDs p ON o.ProductID = p.ProductID;

-- Step 2: CustomerID lookup synchronisation — Orders vs Customers master
WITH OrderCustomerIDs AS (
    SELECT DISTINCT CustomerID, 'Orders' AS Src
    FROM Orders WHERE CustomerID IS NOT NULL
),
CustomerMasterIDs AS (
    SELECT DISTINCT CustomerID, 'Customers' AS Src
    FROM Customers WHERE CustomerID IS NOT NULL
)
SELECT
    COALESCE(o.CustomerID, c.CustomerID) AS CustomerID,
    CASE
        WHEN o.CustomerID IS NOT NULL AND c.CustomerID IS NULL
             THEN 'SYNC GAP: CustomerID "' + o.CustomerID
                  + '" referenced in Orders but missing from Customers master'
        WHEN o.CustomerID IS NULL AND c.CustomerID IS NOT NULL
             THEN 'INACTIVE: CustomerID "' + c.CustomerID
                  + '" in Customers but has no orders'
        ELSE 'SYNCHRONISED'
    END AS CustomerSyncFlag
FROM OrderCustomerIDs o
FULL OUTER JOIN CustomerMasterIDs c ON o.CustomerID = c.CustomerID;

-- Step 3: Status code synchronisation across tables
-- Orders and Transactions both reference Status/currency — should use the same code set
WITH OrderStatuses AS (
    SELECT DISTINCT Status, 'Orders' AS TableName
    FROM Orders WHERE Status IS NOT NULL
),
-- Simulate a second system with its own status codes (e.g., fulfilment system)
FulfilmentStatuses AS (
    SELECT 'Pending'    AS Status, 'Fulfilment' AS TableName UNION ALL
    SELECT 'Processing',           'Fulfilment'              UNION ALL
    SELECT 'Shipped',              'Fulfilment'              UNION ALL
    SELECT 'Delivered',            'Fulfilment'              UNION ALL
    SELECT 'Returned',             'Fulfilment'              UNION ALL
    SELECT 'Cancelled',            'Fulfilment'
)
SELECT
    COALESCE(o.Status, f.Status) AS Status,
    o.TableName AS InOrders,
    f.TableName AS InFulfilment,
    CASE
        WHEN o.Status IS NOT NULL AND f.Status IS NULL
             THEN 'ORDERS-ONLY STATUS: "' + o.Status
                  + '" exists in Orders but not in Fulfilment system — mapping mismatch'
        WHEN o.Status IS NULL AND f.Status IS NOT NULL
             THEN 'FULFILMENT-ONLY STATUS: "' + f.Status
                  + '" exists in Fulfilment system but not yet in Orders — data not propagated'
        ELSE 'SYNCHRONISED: Status code present in both systems'
    END AS StatusSyncFlag
FROM OrderStatuses o
FULL OUTER JOIN FulfilmentStatuses f ON o.Status = f.Status;

-- Step 4: Value drift in synchronised lookup
-- Same ProductID in both systems — but do the values match?
-- Simulate by checking self-consistency within Products table for price range
SELECT
    ProductID,
    ProductName,
    Price,
    IsActive,
    CASE
        WHEN Price <= 0
             THEN 'PRICE ZERO/NEGATIVE: Price not synchronised correctly'
        WHEN Price > 10000
             THEN 'PRICE VERY HIGH: Price of ' + CAST(Price AS VARCHAR)
                  + ' may reflect a unit error during sync (pence vs pounds?)'
        WHEN IsActive = 0 AND Price > 0
             THEN 'INACTIVE WITH PRICE: Product is inactive but has a positive price — '
                  + 'verify sync did not retain stale price from active period'
        ELSE 'Values consistent'
    END AS ValueSyncFlag
FROM Products;

-- Step 5: Synchronisation health summary
SELECT
    CheckName,
    TotalInSystem1,
    TotalInSystem2,
    MatchedCount,
    System1Only,
    System2Only,
    ROUND(100.0 * MatchedCount / NULLIF(TotalInSystem1, 0), 1) AS SyncPct,
    CASE
        WHEN System1Only + System2Only = 0
             THEN 'FULLY SYNCHRONISED'
        WHEN 100.0 * MatchedCount / NULLIF(TotalInSystem1, 0) >= 99
             THEN 'NEAR-SYNC: ' + CAST(System1Only + System2Only AS VARCHAR) + ' items out of sync'
        ELSE 'OUT OF SYNC: ' + CAST(System1Only AS VARCHAR) + ' missing from Products, '
             + CAST(System2Only AS VARCHAR) + ' unordered'
    END AS SyncStatus
FROM (
    SELECT
        'ProductID: Orders vs Products'    AS CheckName,
        (SELECT COUNT(DISTINCT ProductID) FROM Orders WHERE ProductID IS NOT NULL) AS TotalInSystem1,
        (SELECT COUNT(DISTINCT ProductID) FROM Products WHERE ProductID IS NOT NULL) AS TotalInSystem2,
        (SELECT COUNT(DISTINCT o.ProductID)
         FROM Orders o JOIN Products p ON o.ProductID = p.ProductID
         WHERE o.ProductID IS NOT NULL) AS MatchedCount,
        (SELECT COUNT(DISTINCT o.ProductID)
         FROM Orders o LEFT JOIN Products p ON o.ProductID = p.ProductID
         WHERE p.ProductID IS NULL AND o.ProductID IS NOT NULL) AS System1Only,
        (SELECT COUNT(DISTINCT p.ProductID)
         FROM Products p LEFT JOIN Orders o ON o.ProductID = p.ProductID
         WHERE o.ProductID IS NULL AND p.ProductID IS NOT NULL) AS System2Only
    UNION ALL
    SELECT
        'CustomerID: Orders vs Customers',
        (SELECT COUNT(DISTINCT CustomerID) FROM Orders WHERE CustomerID IS NOT NULL),
        (SELECT COUNT(DISTINCT CustomerID) FROM Customers WHERE CustomerID IS NOT NULL),
        (SELECT COUNT(DISTINCT o.CustomerID)
         FROM Orders o JOIN Customers c ON o.CustomerID = c.CustomerID
         WHERE o.CustomerID IS NOT NULL),
        (SELECT COUNT(DISTINCT o.CustomerID)
         FROM Orders o LEFT JOIN Customers c ON o.CustomerID = c.CustomerID
         WHERE c.CustomerID IS NULL AND o.CustomerID IS NOT NULL),
        (SELECT COUNT(DISTINCT c.CustomerID)
         FROM Customers c LEFT JOIN Orders o ON o.CustomerID = c.CustomerID
         WHERE o.CustomerID IS NULL AND c.CustomerID IS NOT NULL)
) SyncSummary;
```

## Explanation

**FULL OUTER JOIN for bidirectional sync validation**
Lookup synchronisation requires checking both directions: codes used in transactional data (Orders) that don't exist in the lookup (Products) are orphaned references indicating the lookup wasn't synchronised to include new codes; codes in the lookup that don't appear in any transactional data are unused entries that may be stale or simply not yet ordered. FULL OUTER JOIN detects both in a single query.

**Unused vs missing distinction**
A ProductID in the Products master that never appears in Orders is "unused" — not necessarily a sync problem. A ProductID in Orders that doesn't exist in Products is "orphaned" — definitely a sync problem because the lookup cannot be resolved. Step 5 counts these separately in `System1Only` (sync gap) and `System2Only` (unused), so the health report correctly classifies 100% sync for the transactional direction even when the lookup contains unused entries.

**Status code mapping as a common sync failure**
Step 3 identifies a common real-world synchronisation failure: two systems using overlapping but not identical code sets for the same concept. Orders uses "Delivered" while the Fulfilment system uses "Shipped" as an intermediate state before "Delivered". When these code sets diverge, status values from the Fulfilment system cannot be mapped to the Orders table without a translation layer. The FULL OUTER JOIN between the two status code sets immediately shows which codes exist in one system but not the other.

**Value drift after initial synchronisation**
Even after a lookup table is correctly synchronised, values can drift: a product price in the Products master is updated but the update doesn't propagate to the reporting warehouse. Step 4 detects within-table inconsistencies (negative prices, prices on inactive products) as a proxy for detecting values that may not have been correctly refreshed during the last sync.

## Severity
**High** — Lookup table synchronisation failures have multiplicative impact: every transaction that references an out-of-sync code produces a lookup failure, a NULL enrichment result, or a mapping error. For a system with millions of daily transactions referencing a dozen lookup tables, a single lookup table out of sync can degrade the quality of the entire transactional dataset.
