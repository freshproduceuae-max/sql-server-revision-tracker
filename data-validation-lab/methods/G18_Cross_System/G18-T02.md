# G18-T02 — Cross-System | Schema Drift and Version Mismatch Detection

## ID
G18-T02

## Group
18 — Cross-System

## Type
Schema Drift and Version Mismatch Detection — Identifying Differences Between Schema Versions Across Environments or Systems

## Live Scenario
A development team deploys a hotfix to production that adds a `DiscountPercent` column to the Products table and extends the `Status` column from VARCHAR(20) to VARCHAR(50). The deployment script runs successfully, but the ETL pipeline that reads from the production source and loads into the data warehouse was not updated to include `DiscountPercent`. Three days later, a business analyst notices that discount information is missing from all warehouse reports. Additionally, the Status column in the warehouse is still VARCHAR(20), so status values longer than 20 characters (a new status "Awaiting-Collection" added with the hotfix) are being silently truncated to "Awaiting-Collec". The schema drift check, comparing the warehouse schema against the expected production schema, would have flagged both differences immediately after the deployment.

## The Question
> Schema drift detection compares the current schema definition (column names, data types, lengths, nullability, ordinal position) against an expected baseline schema, identifying added columns (in source but not target), removed columns (in target but not source), and changed columns (same name but different type, length, or nullability). SQL queries INFORMATION_SCHEMA.COLUMNS to produce the current schema, which is then FULL OUTER JOINed against a hardcoded baseline to detect drift.
> **"Detect schema drift in the dataset: compare the current column definitions in the Customers, Products, and Orders tables against an expected baseline schema, identify any columns that have been added, removed, or have changed data type or length, and flag changes that could cause data truncation or type mismatch errors."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Customers** — `schemas/01_Customers.csv`
**Products** — `schemas/03_Products.csv`

## Solution Query

```sql
-- Step 1: Current schema snapshot
SELECT
    TABLE_NAME   AS TableName,
    COLUMN_NAME  AS ColumnName,
    ORDINAL_POSITION AS Position,
    DATA_TYPE    AS DataType,
    CHARACTER_MAXIMUM_LENGTH AS MaxLength,
    IS_NULLABLE  AS Nullable,
    COLUMN_DEFAULT AS DefaultValue
FROM INFORMATION_SCHEMA.COLUMNS
WHERE TABLE_NAME IN ('Customers', 'Products', 'Orders', 'Employees', 'Transactions')
ORDER BY TABLE_NAME, ORDINAL_POSITION;

-- Step 2: Schema drift detection — compare current schema to expected baseline
-- Expected baseline represents the "known good" schema version
WITH BaselineSchema AS (
    SELECT TableName, ColumnName, ExpDataType, ExpMaxLength, ExpNullable FROM (VALUES
        -- Customers baseline
        ('Customers', 'CustomerID',  'nvarchar', 50,   'NO'),
        ('Customers', 'FirstName',   'nvarchar', 100,  'YES'),
        ('Customers', 'LastName',    'nvarchar', 100,  'YES'),
        ('Customers', 'Email',       'nvarchar', 255,  'YES'),
        ('Customers', 'Phone',       'nvarchar', 50,   'YES'),
        ('Customers', 'PostalCode',  'nvarchar', 20,   'YES'),
        ('Customers', 'DateOfBirth', 'date',     NULL, 'YES'),
        ('Customers', 'Country',     'nvarchar', 100,  'YES'),
        ('Customers', 'IsActive',    'bit',      NULL, 'YES'),
        ('Customers', 'Latitude',    'float',    NULL, 'YES'),
        ('Customers', 'Longitude',   'float',    NULL, 'YES'),
        ('Customers', 'ContractEnd', 'date',     NULL, 'YES'),
        -- Products baseline
        ('Products', 'ProductID',       'nvarchar', 50,   'NO'),
        ('Products', 'ProductName',     'nvarchar', 200,  'NO'),
        ('Products', 'ProductCode',     'nvarchar', 50,   'YES'),
        ('Products', 'Price',           'decimal',  NULL, 'NO'),
        ('Products', 'StockQuantity',   'int',      NULL, 'YES'),
        ('Products', 'IsActive',        'bit',      NULL, 'YES'),
        ('Products', 'DiscountPercent', 'decimal',  NULL, 'YES'),
        ('Products', 'VATRate',         'decimal',  NULL, 'YES'),
        ('Products', 'ColourHex',       'nvarchar', 10,   'YES'),
        ('Products', 'Tags',            'nvarchar', 500,  'YES'),
        ('Products', 'Description',     'nvarchar', 1000, 'YES'),
        ('Products', 'Barcode',         'nvarchar', 50,   'YES'),
        -- Orders baseline
        ('Orders', 'OrderID',        'nvarchar', 50,   'NO'),
        ('Orders', 'CustomerID',     'nvarchar', 50,   'YES'),
        ('Orders', 'ProductID',      'nvarchar', 50,   'YES'),
        ('Orders', 'OrderDate',      'datetime2',NULL, 'YES'),
        ('Orders', 'DeliveryDate',   'datetime2',NULL, 'YES'),
        ('Orders', 'TotalAmount',    'decimal',  NULL, 'YES'),
        ('Orders', 'Status',         'nvarchar', 50,   'YES'),
        ('Orders', 'XMLData',        'nvarchar', -1,   'YES'),
        ('Orders', 'Metadata',       'nvarchar', -1,   'YES'),
        ('Orders', 'Notes',          'nvarchar', -1,   'YES'),
        ('Orders', 'AttachmentPath', 'nvarchar', 500,  'YES')
    ) B (TableName, ColumnName, ExpDataType, ExpMaxLength, ExpNullable)
),
CurrentSchema AS (
    SELECT
        TABLE_NAME       AS TableName,
        COLUMN_NAME      AS ColumnName,
        DATA_TYPE        AS CurDataType,
        CHARACTER_MAXIMUM_LENGTH AS CurMaxLength,
        IS_NULLABLE      AS CurNullable
    FROM INFORMATION_SCHEMA.COLUMNS
    WHERE TABLE_NAME IN ('Customers', 'Products', 'Orders')
)
SELECT
    COALESCE(b.TableName, c.TableName)   AS TableName,
    COALESCE(b.ColumnName, c.ColumnName) AS ColumnName,
    b.ExpDataType, c.CurDataType,
    b.ExpMaxLength, c.CurMaxLength,
    b.ExpNullable, c.CurNullable,
    CASE
        WHEN c.ColumnName IS NULL
             THEN 'COLUMN DROPPED: ' + b.ColumnName + ' present in baseline but missing in current schema'
        WHEN b.ColumnName IS NULL
             THEN 'NEW COLUMN: ' + c.ColumnName + ' not in baseline — ETL may need updating'
        WHEN b.ExpDataType <> c.CurDataType
             THEN 'TYPE CHANGE: ' + b.ColumnName + ' changed from ' + b.ExpDataType
                  + ' to ' + c.CurDataType + ' — possible data loss or conversion error'
        WHEN ISNULL(b.ExpMaxLength, -999) <> ISNULL(c.CurMaxLength, -999)
             THEN 'LENGTH CHANGE: ' + b.ColumnName
                  + ' length changed from '
                  + ISNULL(CAST(b.ExpMaxLength AS VARCHAR), 'MAX')
                  + ' to ' + ISNULL(CAST(c.CurMaxLength AS VARCHAR), 'MAX')
                  + CASE WHEN ISNULL(c.CurMaxLength,-1) < ISNULL(b.ExpMaxLength,-1)
                         THEN ' — TRUNCATION RISK: new length is shorter'
                         ELSE ' — Lengthened (safe)'
                    END
        WHEN b.ExpNullable <> c.CurNullable
             THEN 'NULLABILITY CHANGE: ' + b.ColumnName + ' changed from '
                  + b.ExpNullable + ' to ' + c.CurNullable
        ELSE 'MATCH'
    END AS DriftFlag
FROM BaselineSchema b
FULL OUTER JOIN CurrentSchema c
    ON b.TableName = c.TableName AND b.ColumnName = c.ColumnName
WHERE NOT (c.ColumnName IS NOT NULL AND b.ColumnName IS NOT NULL
           AND b.ExpDataType = c.CurDataType
           AND ISNULL(b.ExpMaxLength,-999) = ISNULL(c.CurMaxLength,-999)
           AND b.ExpNullable = c.CurNullable)
ORDER BY TableName, DriftFlag;

-- Step 3: Column count change detection
SELECT
    TABLE_NAME AS TableName,
    COUNT(*) AS CurrentColumnCount,
    CASE
        WHEN TABLE_NAME = 'Customers' AND COUNT(*) <> 12
             THEN 'DRIFT: Expected 12 columns, found ' + CAST(COUNT(*) AS VARCHAR)
        WHEN TABLE_NAME = 'Products'  AND COUNT(*) <> 12
             THEN 'DRIFT: Expected 12 columns, found ' + CAST(COUNT(*) AS VARCHAR)
        WHEN TABLE_NAME = 'Orders'    AND COUNT(*) <> 11
             THEN 'DRIFT: Expected 11 columns, found ' + CAST(COUNT(*) AS VARCHAR)
        ELSE 'Column count matches baseline'
    END AS ColumnCountFlag
FROM INFORMATION_SCHEMA.COLUMNS
WHERE TABLE_NAME IN ('Customers', 'Products', 'Orders')
GROUP BY TABLE_NAME;

-- Step 4: Data type compatibility matrix — which type changes cause silent data loss?
SELECT ChangeType, SourceType, TargetType, RiskLevel, Impact FROM (VALUES
    ('Narrowing', 'VARCHAR(500)', 'VARCHAR(20)',  'Critical', 'Truncation of values longer than 20 chars'),
    ('Narrowing', 'DECIMAL(18,4)', 'DECIMAL(18,2)', 'High', 'Rounding of 3rd and 4th decimal places'),
    ('Narrowing', 'BIGINT',       'INT',          'High',     'Overflow for values > 2,147,483,647'),
    ('Widening',  'VARCHAR(20)',  'VARCHAR(500)', 'None',     'Safe: all existing values fit in wider column'),
    ('Type change','DATE',        'DATETIME',     'Low',      'Adds time component — defaults to midnight'),
    ('Type change','NVARCHAR',    'VARCHAR',      'Medium',   'Possible encoding loss for non-ASCII characters'),
    ('Nullability','NOT NULL',    'NULL',         'Low',      'Allows NULLs where none previously existed'),
    ('Nullability','NULL',        'NOT NULL',     'High',     'Existing NULLs will fail if column reloaded')
) TypeMatrix (ChangeType, SourceType, TargetType, RiskLevel, Impact);
```

## Explanation

**FULL OUTER JOIN for schema comparison**
Schema drift detection uses the same FULL OUTER JOIN pattern as data reconciliation: the baseline represents the expected state, the current schema represents the actual state. A column present in the baseline but missing in current = dropped column; a column in current but missing from baseline = new column; a column in both with different properties = changed column. The WHERE clause filters out matching rows (no drift) so only differences appear.

**Truncation risk from length narrowing**
When a VARCHAR(500) column is changed to VARCHAR(20), the data type change itself does not fail — SQL Server allows the ALTER TABLE. But when the ETL loads data into the narrowed column, values longer than 20 characters are silently truncated (or the INSERT fails with an error, depending on SET ANSI_WARNINGS). Step 4's risk matrix documents this: narrowing changes are the most dangerous because they cause silent data loss.

**Baseline schema as a migration checkpoint**
The hardcoded baseline CTE in Step 2 represents the schema as of a known good release version. In practice, this baseline would be stored in a dedicated schema management table that is updated with each approved schema change. Running this comparison after every deployment verifies that the deployment did exactly what was planned — no more, no less.

**INFORMATION_SCHEMA vs sys.columns**
`INFORMATION_SCHEMA.COLUMNS` is the ANSI-standard view and works across SQL Server, PostgreSQL, MySQL, and Oracle. `sys.columns` is SQL Server-specific but provides more metadata (e.g., max_length in bytes rather than characters for NCHAR types). For cross-platform schema comparison, INFORMATION_SCHEMA is preferred; for SQL Server-specific deep schema auditing, sys.columns is more complete.

## Severity
**High** — Schema drift between systems causes ETL failures (column not found), silent data truncation (column shorter in target), and type conversion errors (type incompatibility). These failures are particularly hard to diagnose because the error often manifests far from its cause — a VARCHAR(20) column truncating a 35-character status value produces no error but causes incorrect status reporting weeks later.
