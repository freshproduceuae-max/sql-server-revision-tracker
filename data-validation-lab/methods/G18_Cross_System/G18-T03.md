# G18-T03 — Cross-System | Dual-Write Consistency Check

## ID
G18-T03

## Group
18 — Cross-System

## Type
Dual-Write Consistency Check — Verifying That Two Systems Written to in Parallel Contain Consistent Data

## Live Scenario
A financial institution is migrating from an on-premise Oracle database to a cloud-based SQL Server instance. During the transition period, both systems receive every transaction write simultaneously (dual-write). This ensures the cloud system is kept in sync and can take over immediately if the on-premise system fails. After three weeks of dual-write operation, the team runs a consistency check and discovers 94 transactions that exist in the on-premise system but not in the cloud (write failures due to a misconfigured cloud connection timeout), and 7 transactions that exist in the cloud but not on-premise (a brief period where the failover logic incorrectly wrote to the cloud before the on-premise write completed). The consistency check enables the team to identify the 101 discrepancies and resolve them before cutting over to the cloud system.

## The Question
> Dual-write consistency checks compare two tables that should be identical (or near-identical) mirrors of each other, detecting records in System A but not System B, records in System B but not System A, and records in both systems but with different field values (value drift). SQL implements this using LEFT JOIN + IS NULL for existence checks and FULL OUTER JOIN with field-level comparison for value drift detection.
> **"Simulate a dual-write consistency check between Orders (representing System A / on-premise) and Transactions (representing System B / cloud — with OrderID as the common key): identify Orders that have no matching Transaction, Transactions that have no matching Order, and detect any key values that appear to have been written to only one system."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Transactions** — `schemas/05_Transactions.csv`

## Solution Query

```sql
-- Step 1: Orders with no matching Transaction (System A records not in System B)
-- Using OrderID as the shared key between systems
SELECT
    o.OrderID,
    CAST(o.OrderDate AS DATE) AS OrderDate,
    o.TotalAmount,
    o.Status,
    o.CustomerID,
    'IN ORDERS ONLY: OrderID ' + o.OrderID
    + ' present in Orders (System A) but has no transaction record (System B)'
        AS ConsistencyFlag
FROM Orders o
LEFT JOIN Transactions t ON o.OrderID = t.OrderID
WHERE t.OrderID IS NULL
  AND o.OrderID IS NOT NULL
ORDER BY o.OrderDate DESC;

-- Step 2: Transactions with no matching Order (System B records not in System A)
SELECT
    t.TransactionID,
    t.OrderID,
    CAST(t.TransactionDate AS DATE) AS TransactionDate,
    t.Amount,
    t.Currency,
    'IN TRANSACTIONS ONLY: OrderID ' + CAST(t.OrderID AS VARCHAR)
    + ' referenced in Transactions (System B) but not found in Orders (System A)'
        AS ConsistencyFlag
FROM Transactions t
LEFT JOIN Orders o ON t.OrderID = o.OrderID
WHERE o.OrderID IS NULL
  AND t.OrderID IS NOT NULL
ORDER BY t.TransactionDate DESC;

-- Step 3: Matched records — compare key field values
-- For records existing in both systems, check for value drift
WITH MatchedPairs AS (
    SELECT
        o.OrderID,
        o.TotalAmount AS OrderAmount,
        t.Amount AS TxnAmount,
        CAST(o.OrderDate AS DATE) AS OrderDate,
        CAST(t.TransactionDate AS DATE) AS TxnDate,
        o.Status,
        t.Currency
    FROM Orders o
    JOIN Transactions t ON o.OrderID = t.OrderID
)
SELECT
    OrderID,
    OrderAmount,
    TxnAmount,
    ROUND(ABS(OrderAmount - TxnAmount), 2) AS AmountDiff,
    OrderDate,
    TxnDate,
    DATEDIFF(DAY, OrderDate, TxnDate) AS DateDiffDays,
    CASE
        WHEN ABS(ISNULL(OrderAmount, 0) - ISNULL(TxnAmount, 0)) > 0.01
             THEN 'AMOUNT MISMATCH: Order amount ' + CAST(OrderAmount AS VARCHAR)
                  + ' vs Transaction amount ' + CAST(TxnAmount AS VARCHAR)
                  + ' — delta ' + CAST(ROUND(ABS(OrderAmount - TxnAmount), 2) AS VARCHAR)
        WHEN ABS(DATEDIFF(DAY, OrderDate, TxnDate)) > 1
             THEN 'DATE MISMATCH: OrderDate ' + CAST(OrderDate AS VARCHAR)
                  + ' vs TransactionDate ' + CAST(TxnDate AS VARCHAR)
                  + ' — ' + CAST(ABS(DATEDIFF(DAY, OrderDate, TxnDate)) AS VARCHAR) + ' days apart'
        ELSE 'CONSISTENT: Key fields match between systems'
    END AS ValueDriftFlag
FROM MatchedPairs
ORDER BY AmountDiff DESC;

-- Step 4: Consistency summary metrics
SELECT
    'Orders (System A) total' AS Metric, COUNT(*) AS Value
FROM Orders
UNION ALL
SELECT 'Transactions (System B) total', COUNT(*)
FROM Transactions
UNION ALL
SELECT 'Matched (OrderID in both)', COUNT(DISTINCT o.OrderID)
FROM Orders o JOIN Transactions t ON o.OrderID = t.OrderID
UNION ALL
SELECT 'In Orders only (System A surplus)', COUNT(DISTINCT o.OrderID)
FROM Orders o LEFT JOIN Transactions t ON o.OrderID = t.OrderID
WHERE t.OrderID IS NULL AND o.OrderID IS NOT NULL
UNION ALL
SELECT 'In Transactions only (System B surplus)', COUNT(DISTINCT t.OrderID)
FROM Transactions t LEFT JOIN Orders o ON t.OrderID = o.OrderID
WHERE o.OrderID IS NULL AND t.OrderID IS NOT NULL
UNION ALL
SELECT 'Matched with amount mismatch',
    SUM(CASE WHEN ABS(ISNULL(o.TotalAmount,0) - ISNULL(t.Amount,0)) > 0.01 THEN 1 ELSE 0 END)
FROM Orders o JOIN Transactions t ON o.OrderID = t.OrderID;

-- Step 5: Consistency percentage — what fraction of records are perfectly consistent?
WITH ConsistencyCounts AS (
    SELECT
        COUNT(DISTINCT o.OrderID) AS TotalOrders,
        COUNT(DISTINCT CASE WHEN t.OrderID IS NOT NULL THEN o.OrderID END) AS MatchedOrders,
        COUNT(DISTINCT CASE
            WHEN t.OrderID IS NOT NULL
             AND ABS(ISNULL(o.TotalAmount,0) - ISNULL(t.Amount,0)) <= 0.01
            THEN o.OrderID END) AS FullyConsistentOrders
    FROM Orders o
    LEFT JOIN Transactions t ON o.OrderID = t.OrderID
)
SELECT
    TotalOrders,
    MatchedOrders,
    FullyConsistentOrders,
    ROUND(100.0 * MatchedOrders / NULLIF(TotalOrders, 0), 1) AS MatchPct,
    ROUND(100.0 * FullyConsistentOrders / NULLIF(TotalOrders, 0), 1) AS ConsistencyPct,
    CASE
        WHEN 100.0 * FullyConsistentOrders / NULLIF(TotalOrders, 0) >= 99.9
             THEN 'PASS: 99.9%+ consistency — acceptable for cutover'
        WHEN 100.0 * FullyConsistentOrders / NULLIF(TotalOrders, 0) >= 99.0
             THEN 'REVIEW: 99-99.9% consistency — resolve discrepancies before cutover'
        ELSE 'FAIL: <99% consistency — dual-write has significant gaps, do not cut over'
    END AS CutoverReadiness
FROM ConsistencyCounts;
```

## Explanation

**LEFT JOIN vs FULL OUTER JOIN for dual-write checks**
Steps 1 and 2 use separate LEFT JOINs (System A → System B, then System B → System A) rather than a single FULL OUTER JOIN. This is intentional: two separate queries produce clearer output, isolating "records only in A" from "records only in B" in separate result sets that the operations team can action independently. FULL OUTER JOIN combines both, which is more efficient for a summary but harder to operationalise.

**Threshold-based value drift detection**
Step 3's amount comparison uses `ABS(OrderAmount - TxnAmount) > 0.01` rather than exact equality. This tolerates floating-point rounding differences between systems that use different numeric precision internally, while still catching genuine value mismatches. The threshold should be set based on the business's materiality threshold — for financial transactions, 0.01 (1 penny) is appropriate.

**Cutover readiness threshold**
Step 5 provides a cutover readiness assessment tied to specific consistency thresholds. 99.9% consistency (1 discrepancy per 1,000 records) is a common industry threshold for system migrations before cutover — with a remediation plan for the remaining 0.1%. The decision to cut over at a given consistency level depends on the nature of the discrepancies (all in one data type? all from a specific time window?) and the business risk tolerance.

**N:M relationship causing apparent discrepancies**
The sample data shows 20 Orders vs 25 Transactions with only 12 matched OrderIDs. This reflects the legitimate N:M nature of the relationship (multiple transactions per order, and transactions that reference orders differently). In a true dual-write scenario, the key being compared should be the primary key of the entity being mirrored — here, that would require the same entity across both tables, which Orders/Transactions don't perfectly represent (they're related but different entities).

## Severity
**Critical** — Dual-write consistency failures directly cause data integrity problems at cutover: if the cloud system is missing 0.1% of records and is promoted to primary, those records are permanently lost with no recovery path (since the on-premise system is decommissioned). The consistency check must achieve near-100% before any migration cutover can be safely executed.
