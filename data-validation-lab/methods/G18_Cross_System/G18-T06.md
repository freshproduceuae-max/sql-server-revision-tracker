# G18-T06 — Cross-System | Timezone and Timestamp Alignment Check

## ID
G18-T06

## Group
18 — Cross-System

## Type
Timezone and Timestamp Alignment Check — Detecting Timezone Inconsistencies When Combining Timestamps from Multiple Systems

## Live Scenario
A UK e-commerce company's order system runs in UTC. Their US partner's fulfilment system runs in US Eastern Time (UTC-5). When orders are shipped from the US warehouse, the shipment timestamp is recorded in Eastern Time and loaded into the UK warehouse's Orders table without conversion. The result: an order placed at 23:45 UTC on March 15th shows a shipment timestamp of 18:45 EST on March 15th — but when this is treated as UTC in the UK system, it appears to have been shipped 5 hours before it was placed. The timezone alignment check, looking for DeliveryDate values that precede OrderDate after accounting for expected timezone differences, flags 847 records where the time sequence is violated, all traceable to shipments from the US warehouse.

## The Question
> Timezone alignment validation detects when timestamps from different source systems have been combined without consistent timezone conversion: delivery dates that precede order dates, transaction timestamps that are offset by a fixed number of hours (suggesting one system's UTC offset was applied incorrectly), and timestamp distributions that show a suspicious bimodal pattern (half the records offset by N hours from the other half, indicating two systems with different timezone settings). SQL detects these patterns using DATEDIFF, time-of-day analysis, and outlier detection on timestamp differences.
> **"Validate timestamp consistency in the Orders and Transactions tables: detect any records where DeliveryDate precedes OrderDate (a temporal impossibility), identify whether OrderDate and TransactionDate distributions show timezone offset patterns, flag records where the time difference between related timestamps is implausible, and check for the characteristic N-hour offset that indicates a missing timezone conversion."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Transactions** — `schemas/05_Transactions.csv`

## Solution Query

```sql
-- Step 1: Delivery before order — temporal impossibility
SELECT
    OrderID,
    CAST(OrderDate   AS DATE) AS OrderDate,
    CAST(DeliveryDate AS DATE) AS DeliveryDate,
    DATEDIFF(DAY, OrderDate, DeliveryDate) AS DeliveryLeadDays,
    CASE
        WHEN DeliveryDate IS NULL
             THEN 'NULL DELIVERY: Delivery date not recorded'
        WHEN CAST(DeliveryDate AS DATE) < CAST(OrderDate AS DATE)
             THEN 'TEMPORAL VIOLATION: DeliveryDate ('
                  + CAST(CAST(DeliveryDate AS DATE) AS VARCHAR)
                  + ') is before OrderDate ('
                  + CAST(CAST(OrderDate AS DATE) AS VARCHAR)
                  + ') — possible timezone offset error or data entry mistake'
        WHEN CAST(DeliveryDate AS DATE) = CAST(OrderDate AS DATE)
             THEN 'SAME-DAY: Ordered and delivered same day — verify if correct'
        WHEN DATEDIFF(DAY, OrderDate, DeliveryDate) > 365
             THEN 'EXCESSIVE LEAD TIME: ' + CAST(DATEDIFF(DAY, OrderDate, DeliveryDate) AS VARCHAR)
                  + ' days between order and delivery — likely data error'
        ELSE 'Valid: ' + CAST(DATEDIFF(DAY, OrderDate, DeliveryDate) AS VARCHAR)
             + '-day lead time'
    END AS TemporalFlag
FROM Orders
WHERE OrderDate IS NOT NULL
ORDER BY DeliveryLeadDays ASC;

-- Step 2: Order-to-transaction time gap analysis
-- For matched orders and transactions, the transaction should follow the order
-- An offset pattern (all transactions N hours before order) indicates timezone error
WITH OrderTxnTimeDiff AS (
    SELECT
        o.OrderID,
        o.OrderDate,
        t.TransactionDate,
        DATEDIFF(HOUR, o.OrderDate, t.TransactionDate) AS HourDiff,
        DATEDIFF(DAY,  o.OrderDate, t.TransactionDate) AS DayDiff
    FROM Orders o
    JOIN Transactions t ON o.OrderID = t.OrderID
    WHERE o.OrderDate IS NOT NULL AND t.TransactionDate IS NOT NULL
)
SELECT
    OrderID,
    CAST(OrderDate AS DATE) AS OrderDate,
    CAST(TransactionDate AS DATE) AS TransactionDate,
    HourDiff,
    DayDiff,
    CASE
        WHEN HourDiff < 0
             THEN 'TIMEZONE SUSPECT: Transaction appears '
                  + CAST(ABS(HourDiff) AS VARCHAR)
                  + ' hours BEFORE the order — possible timezone offset of '
                  + CAST(ABS(HourDiff) AS VARCHAR) + 'h'
        WHEN HourDiff > 168
             THEN 'LATE TRANSACTION: Transaction is ' + CAST(HourDiff / 24 AS VARCHAR)
                  + ' days after order — possible delayed processing'
        WHEN HourDiff BETWEEN 0 AND 24
             THEN 'Normal: Transaction within 24h of order'
        ELSE 'REVIEW: Transaction is ' + CAST(DayDiff AS VARCHAR) + ' days after order'
    END AS TimezoneFlag
FROM OrderTxnTimeDiff
ORDER BY HourDiff ASC;

-- Step 3: Timezone offset pattern detection
-- A fixed offset of -5, -8, etc. hours across many records indicates a timezone error
WITH HourDiffs AS (
    SELECT
        DATEDIFF(HOUR, o.OrderDate, t.TransactionDate) AS HourDiff
    FROM Orders o
    JOIN Transactions t ON o.OrderID = t.OrderID
    WHERE o.OrderDate IS NOT NULL AND t.TransactionDate IS NOT NULL
)
SELECT
    HourDiff,
    COUNT(*) AS Frequency,
    ROUND(100.0 * COUNT(*) / NULLIF(SUM(COUNT(*)) OVER (), 0), 1) AS FrequencyPct,
    CASE
        WHEN HourDiff IN (-8, -7, -6, -5, -4) AND COUNT(*) > 2
             THEN 'US TIMEZONE OFFSET: ' + CAST(HourDiff AS VARCHAR)
                  + ' hour offset matches US timezone (UTC-8 to UTC-4)'
        WHEN HourDiff IN (1, 2, 3, 4) AND COUNT(*) > 2
             THEN 'EU TIMEZONE OFFSET: ' + CAST(HourDiff AS VARCHAR)
                  + ' hour offset matches European timezone (UTC+1 to UTC+4)'
        WHEN HourDiff IN (8, 9, 10, 11) AND COUNT(*) > 2
             THEN 'APAC TIMEZONE OFFSET: ' + CAST(HourDiff AS VARCHAR)
                  + ' hour offset matches Asia-Pacific timezone'
        ELSE 'Normal or low frequency'
    END AS TimezoneOffsetFlag
FROM HourDiffs
GROUP BY HourDiff
ORDER BY COUNT(*) DESC;

-- Step 4: Time-of-day distribution — bimodal pattern as a timezone signal
-- If two systems contribute records in different timezones, the hour distribution
-- may show two peaks (e.g., business hours in UK and business hours in US)
SELECT
    DATEPART(HOUR, OrderDate) AS HourOfDay,
    COUNT(*) AS OrderCount,
    REPLICATE('█', COUNT(*)) AS FrequencyBar,
    CASE
        WHEN DATEPART(HOUR, OrderDate) BETWEEN 9 AND 17
             THEN 'UK business hours (9am-5pm UTC)'
        WHEN DATEPART(HOUR, OrderDate) BETWEEN 14 AND 22
             THEN 'US EST business hours (9am-5pm EST = 14:00-22:00 UTC)'
        ELSE 'Off-hours'
    END AS HourBand
FROM Orders
WHERE OrderDate IS NOT NULL
GROUP BY DATEPART(HOUR, OrderDate)
ORDER BY HourOfDay;

-- Step 5: Timestamp quality summary
SELECT
    'Orders with OrderDate'            AS Metric, COUNT(*) AS Value
FROM Orders WHERE OrderDate IS NOT NULL
UNION ALL
SELECT 'Orders with DeliveryDate', COUNT(*)
FROM Orders WHERE DeliveryDate IS NOT NULL
UNION ALL
SELECT 'Orders where Delivery < Order (impossible)', COUNT(*)
FROM Orders
WHERE DeliveryDate IS NOT NULL AND OrderDate IS NOT NULL
  AND CAST(DeliveryDate AS DATE) < CAST(OrderDate AS DATE)
UNION ALL
SELECT 'Orders with same-day delivery', COUNT(*)
FROM Orders
WHERE DeliveryDate IS NOT NULL AND OrderDate IS NOT NULL
  AND CAST(DeliveryDate AS DATE) = CAST(OrderDate AS DATE)
UNION ALL
SELECT 'Orders with lead time > 30 days', COUNT(*)
FROM Orders
WHERE DeliveryDate IS NOT NULL AND OrderDate IS NOT NULL
  AND DATEDIFF(DAY, OrderDate, DeliveryDate) > 30
UNION ALL
SELECT 'Transactions before their Order date', COUNT(*)
FROM Transactions t JOIN Orders o ON t.OrderID = o.OrderID
WHERE CAST(t.TransactionDate AS DATE) < CAST(o.OrderDate AS DATE);
```

## Explanation

**Fixed N-hour offset as timezone fingerprint**
When one system stores timestamps in UTC and another stores them in local time, every timestamp from the second system is offset by a fixed number of hours. If 85% of the hour differences between Order and Transaction timestamps cluster at -5 (or -8 for Pacific time), this is a strong signal that the Transaction timestamps were stored in US Eastern (or Pacific) time without converting to UTC. Step 3's frequency distribution of hour differences detects this pattern.

**Bimodal hour distribution**
A legitimate single-timezone system should show a unimodal distribution of order times centred on business hours for that timezone. If orders from two timezones are merged without conversion, the hour distribution becomes bimodal — a peak around 10am and another peak around 15:00 UTC (which is 10am US Eastern). Step 4's hour-of-day distribution visualises this signal.

**Delivery before order as a definitive error**
`DeliveryDate < OrderDate` is an absolute temporal impossibility — an item cannot be delivered before it is ordered. In the real world, this always indicates a data quality error: either the delivery date was entered in the wrong timezone, the two dates are from different source systems with timezone mismatches, or the data was corrupted during ETL. Unlike many validation checks that identify probable errors, this one identifies certain errors.

**DATEDIFF in hours vs days**
Step 2 uses `DATEDIFF(HOUR, ...)` rather than `DATEDIFF(DAY, ...)` to catch timezone offsets that span midnight. A transaction at 23:00 UTC on March 15th and an order at 01:00 UTC on March 16th have a `DATEDIFF(DAY)` of -1 (apparently wrong) but a `DATEDIFF(HOUR)` of -2 (small offset, possibly timezone). Hour-level analysis is necessary for timezone validation.

## Severity
**Medium to High** — Timezone errors range from minor cosmetic issues (timestamps displaying in the wrong timezone in reports) to business-critical failures (orders appearing to be delivered before being placed, causing automated fraud alerts; SLA breach calculations being wrong by hours; commission calculations using wrong trade timestamps). The severity depends on how the timestamps are used downstream.
