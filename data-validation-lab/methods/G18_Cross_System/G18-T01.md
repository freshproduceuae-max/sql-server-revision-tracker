# G18-T01 — Cross-System | Row Count Reconciliation Across Systems

## ID
G18-T01

## Group
18 — Cross-System

## Type
Row Count Reconciliation Across Systems — Verifying That Record Counts Match Between Source and Target Systems After Data Transfer

## Live Scenario
A retailer's nightly ETL copies sales orders from the OLTP system (SQL Server) to the data warehouse (a different SQL Server instance). After the ETL, the operations team checks a dashboard that shows "Today's orders: 4,812." The source OLTP system's order management screen shows "New orders today: 4,819." Seven orders are missing from the warehouse — they were rolled back in the OLTP system after the ETL extraction window closed (returns processed after midnight) but the ETL re-ran for those IDs without picking up the rollback. The cross-system row count reconciliation, comparing the count by date from both systems, flags the 7-record discrepancy within minutes of the ETL completing.

## The Question
> Cross-system row count reconciliation compares record counts for the same logical dataset across two or more systems — source OLTP vs target warehouse, warehouse vs reporting mart, system A vs system B in a dual-write architecture. SQL implements this using a simulated source count (via a control table or hardcoded expected value) compared against the actual count in the available table, producing a delta with a pass/fail verdict. Where both systems are accessible via linked servers or a federated query, the comparison runs directly.
> **"Reconcile record counts between the Orders table (representing the target/warehouse) and expected source counts (simulated via monthly totals): verify that the total count, count by month, and count by status all match expected values, and flag any discrepancies with the direction of the variance (warehouse has more or fewer than expected)."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Transactions** — `schemas/05_Transactions.csv`

## Solution Query

```sql
-- Step 1: Simulate source vs target count comparison
-- In production, SourceCount would come from a linked server or control table
-- Here we use the actual table vs expected monthly minimums as a proxy
WITH ActualMonthlyCounts AS (
    SELECT
        YEAR(OrderDate)  AS Yr,
        MONTH(OrderDate) AS Mo,
        COUNT(*)         AS ActualCount,
        ROUND(SUM(TotalAmount), 2) AS ActualRevenue
    FROM Orders
    WHERE OrderDate IS NOT NULL
    GROUP BY YEAR(OrderDate), MONTH(OrderDate)
),
-- Simulated source system expected counts (would come from source in production)
ExpectedMonthlyCounts AS (
    SELECT 2024 AS Yr, 1 AS Mo, 7 AS ExpectedCount, 9200.00 AS ExpectedRevenue UNION ALL
    SELECT 2024, 2, 9, 14300.00 UNION ALL
    SELECT 2024, 3, 4, 6200.00
)
SELECT
    COALESCE(a.Yr, e.Yr)                AS Year_,
    COALESCE(a.Mo, e.Mo)                AS Month_,
    e.ExpectedCount,
    a.ActualCount,
    a.ActualCount - e.ExpectedCount     AS CountDelta,
    e.ExpectedRevenue,
    a.ActualRevenue,
    ROUND(a.ActualRevenue - e.ExpectedRevenue, 2) AS RevenueDelta,
    CASE
        WHEN a.ActualCount IS NULL
             THEN 'MISSING MONTH: No records in target for this period — possible ETL failure'
        WHEN e.ExpectedCount IS NULL
             THEN 'UNEXPECTED PERIOD: Target has records for a period not in source control'
        WHEN a.ActualCount > e.ExpectedCount
             THEN 'OVER-LOAD: Target has ' + CAST(a.ActualCount - e.ExpectedCount AS VARCHAR)
                  + ' more records than source — possible duplicate load'
        WHEN a.ActualCount < e.ExpectedCount
             THEN 'UNDER-LOAD: Target is missing ' + CAST(e.ExpectedCount - a.ActualCount AS VARCHAR)
                  + ' records — ETL load shortfall'
        ELSE 'MATCH: Count reconciles'
    END AS ReconciliationFlag
FROM ExpectedMonthlyCounts e
FULL OUTER JOIN ActualMonthlyCounts a ON e.Yr = a.Yr AND e.Mo = a.Mo
ORDER BY Year_, Month_;

-- Step 2: Status distribution reconciliation
-- Verify that the distribution of statuses is consistent with the source system's distribution
WITH StatusDist AS (
    SELECT
        Status,
        COUNT(*) AS ActualCount,
        ROUND(100.0 * COUNT(*) / NULLIF(SUM(COUNT(*)) OVER (), 0), 1) AS ActualPct
    FROM Orders
    WHERE Status IS NOT NULL
    GROUP BY Status
),
ExpectedStatusDist AS (
    SELECT 'Pending'    AS Status, 2 AS ExpCount, 10.0 AS ExpPct UNION ALL
    SELECT 'Processing',           3,             15.0           UNION ALL
    SELECT 'Delivered',            12,            60.0           UNION ALL
    SELECT 'Cancelled',            2,             10.0           UNION ALL
    SELECT 'Returned',             1,              5.0
)
SELECT
    COALESCE(s.Status, e.Status) AS Status,
    e.ExpCount,
    s.ActualCount,
    ROUND(e.ExpPct, 1) AS ExpPct,
    ROUND(s.ActualPct, 1) AS ActualPct,
    s.ActualCount - e.ExpCount AS CountDelta,
    CASE
        WHEN s.ActualCount IS NULL
             THEN 'MISSING STATUS: Status expected in target but absent'
        WHEN e.ExpCount IS NULL
             THEN 'UNEXPECTED STATUS: Status in target not in source distribution'
        WHEN ABS(s.ActualCount - e.ExpCount) > 2
             THEN 'DISTRIBUTION MISMATCH: Count delta of ' + CAST(ABS(s.ActualCount - e.ExpCount) AS VARCHAR)
        ELSE 'Within tolerance'
    END AS StatusReconcFlag
FROM ExpectedStatusDist e
FULL OUTER JOIN StatusDist s ON e.Status = s.Status;

-- Step 3: Grand total reconciliation
SELECT
    'Orders total rows'              AS Metric,
    COUNT(*)                         AS Value,
    20                               AS Expected,
    COUNT(*) - 20                    AS Delta,
    CASE WHEN COUNT(*) = 20 THEN 'PASS' ELSE 'FAIL' END AS Result
FROM Orders
UNION ALL
SELECT
    'Orders total revenue',
    ROUND(SUM(TotalAmount), 0),
    29700,
    ROUND(SUM(TotalAmount), 0) - 29700,
    CASE WHEN ABS(SUM(TotalAmount) - 29700) < 100 THEN 'PASS' ELSE 'FAIL' END
FROM Orders WHERE TotalAmount IS NOT NULL
UNION ALL
SELECT
    'Transactions total rows',
    COUNT(*),
    25,
    COUNT(*) - 25,
    CASE WHEN COUNT(*) = 25 THEN 'PASS' ELSE 'FAIL' END
FROM Transactions
UNION ALL
SELECT
    'Transactions total amount',
    ROUND(SUM(Amount), 0),
    27000,
    ROUND(SUM(Amount), 0) - 27000,
    CASE WHEN ABS(SUM(Amount) - 27000) < 500 THEN 'PASS' ELSE 'FAIL' END
FROM Transactions WHERE Amount IS NOT NULL;

-- Step 4: Cross-table internal reconciliation
-- Orders and Transactions should be aligned — same customers, overlapping dates
SELECT
    'Orders: distinct customers'   AS Metric, COUNT(DISTINCT CustomerID) AS Value
FROM Orders WHERE CustomerID IS NOT NULL
UNION ALL
SELECT 'Transactions: distinct order references', COUNT(DISTINCT OrderID)
FROM Transactions WHERE OrderID IS NOT NULL
UNION ALL
SELECT 'Orders with at least one Transaction',
    COUNT(DISTINCT o.OrderID)
FROM Orders o
JOIN Transactions t ON o.OrderID = t.OrderID
UNION ALL
SELECT 'Orders with no Transaction',
    COUNT(DISTINCT o.OrderID)
FROM Orders o
LEFT JOIN Transactions t ON o.OrderID = t.OrderID
WHERE t.OrderID IS NULL;
```

## Expected Output

**Step 1 — Monthly reconciliation:**
| Year_ | Month_ | ExpectedCount | ActualCount | CountDelta | ReconciliationFlag |
|---|---|---|---|---|---|
| 2024 | 1 | 7 | 7 | 0 | MATCH: Count reconciles |
| 2024 | 2 | 9 | 9 | 0 | MATCH: Count reconciles |
| 2024 | 3 | 4 | 4 | 0 | MATCH: Count reconciles |

**Step 3 — Grand total reconciliation:**
| Metric | Value | Expected | Delta | Result |
|---|---|---|---|---|
| Orders total rows | 20 | 20 | 0 | PASS |
| Transactions total rows | 25 | 25 | 0 | PASS |

## Explanation

**FULL OUTER JOIN for two-direction reconciliation**
`FULL OUTER JOIN` between the expected (source) and actual (target) counts catches both directions of mismatch: target records that have no expected counterpart (over-load — the target received more than the source sent) and expected records with no actual counterpart (under-load — the target is missing records). A simple join misses the direction where the unmatched side has no rows.

**Delta with direction**
`ActualCount - ExpectedCount` produces a signed delta: positive = over-load (target has more), negative = under-load (target has fewer). The sign is important for diagnosis: a consistent positive delta across months suggests a systematic duplicate load; a consistent negative delta suggests a systematic data loss; an alternating pattern suggests a timing/watermark issue.

**Revenue reconciliation alongside count**
Count reconciliation is necessary but not sufficient: 20 orders with a total of £29,700 may be correct in count but wrong in value (e.g., one order was loaded with a 10× amount error). Step 3 reconciles both count and revenue independently, so a count match with a revenue mismatch is detected.

**Cross-table reconciliation as consistency check**
Step 4's count of orders with no transaction and orders with a transaction provides an internal consistency check between the two tables. If the source system guarantees that every order has at least one payment transaction, then orders with no transaction represent either an ETL failure (the transaction table didn't load completely) or a data quality issue in the source (orders taken without payment processing).

## Severity
**High** — Record count discrepancies between systems are the most common and most impactful data quality failure in ETL environments. A missing 0.1% of records may represent 0.1% of revenue, which at scale is material. Duplicate records inflate all revenue and volume metrics. Count reconciliation is the first check that should run after any data transfer.
