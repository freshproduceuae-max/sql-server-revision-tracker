# G18-T08 — Cross-System | End-to-End Data Flow Validation

## ID
G18-T08

## Group
18 — Cross-System

## Type
End-to-End Data Flow Validation — Tracing a Record from Source to Final Destination and Verifying It Survived Each Stage Intact

## Live Scenario
A retailer's data platform has four stages: (1) Orders captured in the OLTP system; (2) Orders loaded into a staging table; (3) staging transformed and loaded into the data warehouse; (4) warehouse aggregated into a reporting mart. The finance team notices that the Q1 revenue figure in the reporting mart (£4.2M) is £180K less than the Q1 revenue in the warehouse (£4.38M). Investigation reveals that the mart aggregation query inadvertently excluded orders with Status = 'Returned' from its revenue calculation, but the warehouse includes them as negative amounts. The end-to-end flow validation, checking that every order ID present at stage 1 is traceable to stage 4 with consistent amounts at each stage, identifies the divergence exactly at the mart aggregation step.

## The Question
> End-to-end data flow validation traces a record (or an aggregate of records) through each stage of a multi-step data pipeline, verifying that the count, key field values, and financial totals are consistent at every stage. SQL implements this by computing stage-by-stage snapshots from the available tables (treated as pipeline stages) and comparing adjacent stages using LAG() or FULL OUTER JOIN to identify the specific stage where a discrepancy first appears.
> **"Validate the end-to-end data flow across the available tables treating them as pipeline stages: Stage 1 = Orders (OLTP source), Stage 2 = Transactions (staging/enrichment), Stage 3 = a monthly aggregate (reporting mart). Trace record counts and revenue totals through each stage, identify where counts or amounts diverge, and produce a pipeline health report showing which stage introduced each discrepancy."**

## Table Reference
**Orders** — `schemas/02_Orders.csv`
**Customers** — `schemas/01_Customers.csv`
**Products** — `schemas/03_Products.csv`
**Transactions** — `schemas/05_Transactions.csv`

## Solution Query

```sql
-- Step 1: Stage 1 → Stage 2 flow: Orders to Transactions
-- Every order should ideally produce at least one transaction
WITH Stage1 AS (
    SELECT
        YEAR(OrderDate)  AS Yr,
        MONTH(OrderDate) AS Mo,
        COUNT(*) AS OrderCount,
        ROUND(SUM(TotalAmount), 2) AS OrderRevenue,
        COUNT(DISTINCT CustomerID) AS UniqueCustomers,
        COUNT(DISTINCT ProductID)  AS UniqueProducts
    FROM Orders
    WHERE OrderDate IS NOT NULL
    GROUP BY YEAR(OrderDate), MONTH(OrderDate)
),
Stage2 AS (
    SELECT
        YEAR(TransactionDate)  AS Yr,
        MONTH(TransactionDate) AS Mo,
        COUNT(*) AS TxnCount,
        ROUND(SUM(Amount), 2) AS TxnRevenue,
        COUNT(DISTINCT OrderID) AS UniqueOrders
    FROM Transactions
    WHERE TransactionDate IS NOT NULL
    GROUP BY YEAR(TransactionDate), MONTH(TransactionDate)
)
SELECT
    COALESCE(s1.Yr, s2.Yr) AS Year_,
    COALESCE(s1.Mo, s2.Mo) AS Month_,
    -- Stage 1 metrics
    s1.OrderCount,
    s1.OrderRevenue,
    -- Stage 2 metrics
    s2.TxnCount,
    s2.TxnRevenue,
    s2.UniqueOrders,
    -- Divergence detection
    s2.TxnCount - s1.OrderCount AS CountDelta_S1_to_S2,
    ROUND(s2.TxnRevenue - s1.OrderRevenue, 2) AS RevenueDelta_S1_to_S2,
    CASE
        WHEN s1.Yr IS NULL
             THEN 'Stage 2 has period not in Stage 1'
        WHEN s2.Yr IS NULL
             THEN 'Stage 1 period not loaded to Stage 2'
        WHEN ABS(s2.TxnRevenue - s1.OrderRevenue) / NULLIF(s1.OrderRevenue, 0) > 0.05
             THEN 'REVENUE DIVERGENCE S1→S2: '
                  + CAST(ROUND(ABS(s2.TxnRevenue - s1.OrderRevenue) / NULLIF(s1.OrderRevenue, 0) * 100, 1) AS VARCHAR)
                  + '% difference between Orders and Transactions revenue'
        ELSE 'Within 5% tolerance'
    END AS S1toS2Flag
FROM Stage1 s1
FULL OUTER JOIN Stage2 s2 ON s1.Yr = s2.Yr AND s1.Mo = s2.Mo
ORDER BY Year_, Month_;

-- Step 2: Stage 3 simulation — reporting mart (monthly summary with business rules)
-- Mart rule: include only Delivered and Processing orders (exclude Returned/Cancelled)
WITH ReportingMart AS (
    SELECT
        YEAR(OrderDate)  AS Yr,
        MONTH(OrderDate) AS Mo,
        COUNT(*) AS MartOrderCount,
        ROUND(SUM(TotalAmount), 2) AS MartRevenue
    FROM Orders
    WHERE Status IN ('Delivered', 'Processing')
      AND OrderDate IS NOT NULL
    GROUP BY YEAR(OrderDate), MONTH(OrderDate)
),
Warehouse AS (
    SELECT
        YEAR(OrderDate) AS Yr,
        MONTH(OrderDate) AS Mo,
        COUNT(*) AS WHCount,
        ROUND(SUM(TotalAmount), 2) AS WHRevenue
    FROM Orders
    WHERE OrderDate IS NOT NULL
    GROUP BY YEAR(OrderDate), MONTH(OrderDate)
)
SELECT
    COALESCE(m.Yr, w.Yr) AS Year_,
    COALESCE(m.Mo, w.Mo) AS Month_,
    w.WHCount    AS WarehouseCount,
    w.WHRevenue  AS WarehouseRevenue,
    m.MartOrderCount AS MartCount,
    m.MartRevenue    AS MartRevenue,
    w.WHCount - m.MartOrderCount AS ExcludedCount,
    ROUND(w.WHRevenue - m.MartRevenue, 2) AS ExcludedRevenue,
    CASE
        WHEN w.WHRevenue > m.MartRevenue
             THEN 'MART EXCLUSION: Mart excludes '
                  + CAST(w.WHCount - m.MartOrderCount AS VARCHAR) + ' orders ('
                  + CAST(ROUND(w.WHRevenue - m.MartRevenue, 2) AS VARCHAR)
                  + ' revenue) — verify exclusion rules are intentional'
        WHEN m.MartRevenue > w.WHRevenue
             THEN 'MART INFLATION: Mart shows more revenue than warehouse — aggregation error'
        ELSE 'Mart and warehouse reconcile'
    END AS MartReconcFlag
FROM Warehouse w
FULL OUTER JOIN ReportingMart m ON w.Yr = m.Yr AND w.Mo = m.Mo
ORDER BY Year_, Month_;

-- Step 3: Individual record traceability
-- For each Order, trace whether it has a corresponding Transaction
SELECT
    o.OrderID,
    o.CustomerID,
    CAST(o.OrderDate AS DATE) AS OrderDate,
    o.TotalAmount,
    o.Status,
    COUNT(t.TransactionID) AS TransactionCount,
    ROUND(SUM(t.Amount), 2) AS TotalTransactionAmount,
    CASE
        WHEN COUNT(t.TransactionID) = 0
             THEN 'NOT IN STAGE 2: Order has no transaction — lost at Stage 1→2 transition'
        WHEN ROUND(SUM(t.Amount), 2) <> o.TotalAmount
             THEN 'AMOUNT MISMATCH: Order total ' + CAST(o.TotalAmount AS VARCHAR)
                  + ' vs transaction total ' + CAST(ROUND(SUM(t.Amount), 2) AS VARCHAR)
        ELSE 'TRACEABLE: Order present in both stages with consistent amounts'
    END AS TraceabilityFlag
FROM Orders o
LEFT JOIN Transactions t ON o.OrderID = t.OrderID
GROUP BY o.OrderID, o.CustomerID, o.OrderDate, o.TotalAmount, o.Status
ORDER BY TransactionCount ASC, o.OrderDate;

-- Step 4: Pipeline health summary
SELECT
    'Stage 1 (Orders) total records'           AS Stage, COUNT(*) AS RecordCount,
    ROUND(SUM(TotalAmount), 2) AS Revenue
FROM Orders WHERE OrderDate IS NOT NULL
UNION ALL
SELECT 'Stage 2 (Transactions) total records', COUNT(*), ROUND(SUM(Amount), 2)
FROM Transactions WHERE TransactionDate IS NOT NULL
UNION ALL
SELECT 'Stage 3 (Mart: Delivered+Processing only)', COUNT(*), ROUND(SUM(TotalAmount), 2)
FROM Orders WHERE Status IN ('Delivered','Processing') AND OrderDate IS NOT NULL
UNION ALL
SELECT 'Orders with no Transaction (lost S1→S2)', COUNT(*), ROUND(SUM(TotalAmount), 2)
FROM Orders o
LEFT JOIN Transactions t ON o.OrderID = t.OrderID
WHERE t.OrderID IS NULL AND o.TotalAmount IS NOT NULL;

-- Step 5: Data lineage completeness check
SELECT
    'Orders traceable to Transactions (via OrderID)' AS Check_,
    COUNT(DISTINCT o.OrderID) AS Traceable,
    (SELECT COUNT(DISTINCT OrderID) FROM Orders WHERE OrderID IS NOT NULL) AS Total,
    ROUND(100.0 * COUNT(DISTINCT o.OrderID) /
          NULLIF((SELECT COUNT(DISTINCT OrderID) FROM Orders WHERE OrderID IS NOT NULL), 0), 1)
          AS TraceabilityPct
FROM Orders o
JOIN Transactions t ON o.OrderID = t.OrderID
UNION ALL
SELECT
    'Customers with at least one Order',
    COUNT(DISTINCT o.CustomerID),
    (SELECT COUNT(DISTINCT CustomerID) FROM Customers WHERE CustomerID IS NOT NULL),
    ROUND(100.0 * COUNT(DISTINCT o.CustomerID) /
          NULLIF((SELECT COUNT(DISTINCT CustomerID) FROM Customers WHERE CustomerID IS NOT NULL), 0), 1)
FROM Orders o
JOIN Customers c ON o.CustomerID = c.CustomerID;
```

**Step 4 — Pipeline health summary:**

|---|---|---|
| Stage 1 (Orders) total records | 20 | 25475.00 |
| Stage 2 (Transactions) total records | 25 | 27150.00 |
| Stage 3 (Mart: Delivered+Processing only) | 15 | 19175.00 |
| Orders with no Transaction (lost S1→S2) | 8 | 10025.00 |

**Step 5 — Lineage completeness:**
| Check_ | Traceable | Total | TraceabilityPct |
|---|---|---|---|

## Explanation

**Stage-by-stage comparison isolates the failure point**
The key technique in end-to-end validation is computing the same metric (count, revenue) at each pipeline stage and comparing adjacent stages. When Stage 1 and Stage 2 match but Stage 2 and Stage 3 diverge, the failure was introduced in the Stage 2→3 transition — not somewhere earlier. This pinpoints which ETL step, transformation rule, or aggregation logic needs investigation, dramatically reducing the diagnostic time.

**Mart exclusion rules as intentional divergence**
Step 2 explicitly shows that the reporting mart excludes Cancelled and Returned orders from revenue — this is an intentional business rule, not a data quality error. But the £6,300 difference between warehouse and mart revenue must be documented and understood by finance analysts, because if they compare the two figures without this context, they will escalate what appears to be a discrepancy as an error. The mart reconciliation comment explicitly describes the exclusion, preventing false escalations.

**Record-level traceability vs aggregate traceability**
Step 4's aggregate comparison shows 20 orders at Stage 1 and 25 transactions at Stage 2 — the aggregate appears to expand at Stage 2. But Step 3's record-level trace reveals that 8 specific orders have no transaction (lost), while 5 transactions reference orders not in the current window (e.g., transactions for prior-month orders). Aggregate-level reconciliation masks this: the total counts are similar, so no alarm fires. Record-level traceability catches the actual loss.

**CorrelationID as a pipeline stage marker**
In production pipelines, each stage stamps the record with a stage identifier (CorrelationID, BatchID, or a stage-specific timestamp) when it processes it. The presence or absence of these stamps provides an exact trace of which stage last processed each record. The `CorrelationID` in the Transactions table serves this role — a transaction with a CorrelationID has been processed by the load stage; one without has not.

## Severity
**High** — End-to-end flow validation is the final quality gate that ensures data enters the reporting layer with full fidelity. Pipeline failures at any intermediate stage that go undetected produce incorrect reports that are presented to stakeholders as accurate. The finance team making budget decisions based on mart revenue that is £180K lower than warehouse revenue will make incorrect budget allocations — a direct business impact traceable to the pipeline validation gap.
