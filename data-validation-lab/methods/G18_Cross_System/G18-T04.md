# G18-T04 — Cross-System | API Response Validation

## ID
G18-T04

## Group
18 — Cross-System

## Type
API Response Validation — Verifying That Data Returned by an External API Matches Expected Formats, Ranges, and Business Rules

## Live Scenario
A logistics company's ETL pipeline calls a third-party geocoding API to resolve delivery addresses to coordinates, then loads the results into the Customers table. After a 2-day API outage, the geocoding provider restores service with a degraded fallback mode: the API returns HTTP 200 (success) but returns country centroid coordinates for any address it cannot resolve, rather than an error code. The ETL loads all coordinates without validation. 3,400 customers receive coordinates pointing to the UK centroid (51.5°N, -0.1°W) — indistinguishable from correct London addresses. The API response validation check, examining the coordinate values returned by the API and detecting the centroid clustering pattern, would have flagged the degraded API responses before they were loaded.

## The Question
> API response validation treats the loaded data as the materialised form of an API response and validates it against the expected API contract: field presence (required fields must be populated), value ranges (coordinates must be within valid bounds), format conformance (dates in ISO 8601, currencies in ISO 4217), and business rule compliance (geocoded coordinates must not be centroid defaults). SQL validates API response quality by checking loaded values against these contract constraints.
> **"Validate the quality of API-sourced data in the dataset: identify records where API-sourced fields (Latitude/Longitude from geocoding, Status from order management API, Currency from FX API) appear to contain API error states or default fallback values, and quantify the proportion of API responses that appear valid vs degraded."**

## Table Reference
**Customers** — `schemas/01_Customers.csv`
**Orders** — `schemas/02_Orders.csv`
**Transactions** — `schemas/05_Transactions.csv`

## Solution Query

```sql
-- Step 1: Geocoding API response validation — Latitude/Longitude quality
-- API contract: coordinates must be populated, within UK bounds, not centroid defaults
SELECT
    CustomerID,
    Latitude,
    Longitude,
    Country,
    CASE
        WHEN Latitude IS NULL OR Longitude IS NULL
             THEN 'API_NULL: Geocoding API returned no coordinates — API may have errored'
        WHEN ABS(Latitude - 51.5074) < 0.001 AND ABS(Longitude - (-0.1278)) < 0.001
             THEN 'API_CENTROID: Coordinates match London centroid — degraded API fallback suspected'
        WHEN ABS(Latitude - 54.0) < 0.5 AND ABS(Longitude - (-2.0)) < 0.5
             THEN 'API_UK_CENTROID: Coordinates near UK geographic centre — national centroid fallback'
        WHEN Latitude  NOT BETWEEN 49.8 AND 60.9 AND Country = 'UK'
             THEN 'API_OUT_OF_REGION: UK address geocoded outside UK bounds — API region error'
        WHEN Latitude = FLOOR(Latitude) AND Longitude = FLOOR(Longitude)
             THEN 'API_LOW_PRECISION: Whole-number coordinates — API returned centroid-level precision'
        ELSE 'API_VALID: Coordinate appears geocoded correctly'
    END AS GeocodingAPIFlag,
    CASE
        WHEN Latitude IS NULL                                        THEN 1
        WHEN ABS(Latitude - 51.5074) < 0.001                       THEN 2
        WHEN Latitude = FLOOR(Latitude)                             THEN 3
        ELSE 4
    END AS APIQualityScore  -- 1=error, 2=centroid fallback, 3=low precision, 4=valid
FROM Customers
WHERE Latitude IS NOT NULL OR Country IS NOT NULL;

-- Step 2: Order status API response validation
-- Status field is populated by an order management API — validate against expected status codes
SELECT
    OrderID,
    Status,
    CAST(OrderDate AS DATE) AS OrderDate,
    CASE
        WHEN Status IS NULL
             THEN 'API_NULL: Order management API did not return a status'
        WHEN Status IN ('Pending', 'Processing', 'Delivered', 'Cancelled', 'Returned')
             THEN 'API_VALID: Known status code'
        WHEN Status IN ('ERROR', 'UNKNOWN', 'N/A', 'null', 'undefined', 'TIMEOUT')
             THEN 'API_ERROR_STATE: Status is an API error response, not a business value'
        WHEN LEN(Status) > 50
             THEN 'API_OVERFLOW: Status value is unexpectedly long — possible API response corruption'
        ELSE 'API_UNKNOWN_CODE: Unrecognised status "' + Status + '" — possible new status from API'
    END AS StatusAPIFlag
FROM Orders;

-- Step 3: Currency API response validation
-- Currency field sourced from FX rate API — must be ISO 4217 3-letter code
SELECT
    TransactionID,
    Currency,
    Amount,
    CASE
        WHEN Currency IS NULL
             THEN 'API_NULL: FX API did not return a currency code'
        WHEN LEN(Currency) <> 3
             THEN 'API_INVALID_LENGTH: Currency code "' + CAST(Currency AS VARCHAR)
                  + '" is not 3 characters — API response malformed'
        WHEN Currency NOT LIKE '[A-Z][A-Z][A-Z]'
             THEN 'API_NON_ALPHA: Currency code contains non-alphabetic characters'
        WHEN Currency IN ('GBP', 'USD', 'EUR', 'JPY', 'CHF', 'CAD', 'AUD')
             THEN 'API_VALID: Known major currency code'
        WHEN Currency IN ('ERR', 'N/A', 'UNK', 'XXX')
             THEN 'API_ERROR_STATE: Currency is an error/unknown placeholder'
        ELSE 'API_UNCOMMON: Currency "' + Currency + '" is valid format but uncommon — verify'
    END AS CurrencyAPIFlag
FROM Transactions
WHERE Currency IS NOT NULL;

-- Step 4: API response freshness check
-- If the API updates data in real-time, records should reflect current state
-- Proxy: look for records where dates suggest stale API data
SELECT
    OrderID,
    Status,
    CAST(OrderDate AS DATE) AS OrderDate,
    CAST(DeliveryDate AS DATE) AS DeliveryDate,
    CASE
        WHEN Status = 'Pending'
         AND DeliveryDate IS NOT NULL
         AND CAST(DeliveryDate AS DATE) < CAST(GETDATE() AS DATE)
             THEN 'API_STALE: Order is "Pending" but DeliveryDate is in the past — '
                  + 'API has not updated status since delivery date passed'
        WHEN Status = 'Processing'
         AND CAST(OrderDate AS DATE) < DATEADD(DAY, -30, CAST(GETDATE() AS DATE))
             THEN 'API_STALE: Order has been "Processing" for over 30 days — '
                  + 'API may have lost connection to fulfilment system'
        ELSE 'Status appears current'
    END AS APIFreshnessFlag
FROM Orders
WHERE Status IN ('Pending', 'Processing')
  AND OrderDate IS NOT NULL;

-- Step 5: API quality scorecard
SELECT
    APISource,
    TotalRecords,
    ValidResponses,
    ErrorOrFallback,
    NullResponses,
    ROUND(100.0 * ValidResponses / NULLIF(TotalRecords, 0), 1) AS ValidPct,
    CASE
        WHEN 100.0 * ValidResponses / NULLIF(TotalRecords, 0) >= 99
             THEN 'PASS: API quality ≥99%'
        WHEN 100.0 * ValidResponses / NULLIF(TotalRecords, 0) >= 95
             THEN 'WARN: API quality 95-99% — monitor'
        ELSE 'FAIL: API quality <95% — investigate API degradation'
    END AS APIHealthStatus
FROM (
    SELECT
        'Geocoding API (Lat/Lon)'   AS APISource,
        COUNT(*)                     AS TotalRecords,
        SUM(CASE WHEN Latitude IS NOT NULL
                  AND NOT (ABS(Latitude - 51.5074) < 0.001 AND ABS(Longitude - (-0.1278)) < 0.001)
                  AND NOT (Latitude = FLOOR(Latitude))
                  AND Latitude BETWEEN 49.8 AND 60.9
                 THEN 1 ELSE 0 END) AS ValidResponses,
        SUM(CASE WHEN Latitude IS NOT NULL
                  AND (ABS(Latitude - 51.5074) < 0.001 OR Latitude = FLOOR(Latitude))
                 THEN 1 ELSE 0 END) AS ErrorOrFallback,
        SUM(CASE WHEN Latitude IS NULL THEN 1 ELSE 0 END) AS NullResponses
    FROM Customers
    WHERE Country = 'UK'
    UNION ALL
    SELECT
        'Status API',
        COUNT(*),
        SUM(CASE WHEN Status IN ('Pending','Processing','Delivered','Cancelled','Returned')
                 THEN 1 ELSE 0 END),
        SUM(CASE WHEN Status IN ('ERROR','UNKNOWN','N/A','null','undefined') THEN 1 ELSE 0 END),
        SUM(CASE WHEN Status IS NULL THEN 1 ELSE 0 END)
    FROM Orders
    UNION ALL
    SELECT
        'Currency API',
        COUNT(*),
        SUM(CASE WHEN Currency IN ('GBP','USD','EUR','JPY','CHF','CAD','AUD') THEN 1 ELSE 0 END),
        SUM(CASE WHEN Currency IN ('ERR','N/A','UNK','XXX') THEN 1 ELSE 0 END),
        SUM(CASE WHEN Currency IS NULL THEN 1 ELSE 0 END)
    FROM Transactions
) APIQuality;
```

## Explanation

**API error states masquerading as valid data**
A common API failure mode is returning a semantic error value rather than an HTTP error code — the API returns 200 OK with `{"status": "ERROR"}` or `{"currency": "N/A"}`. The ETL pipeline receives a successful HTTP response and loads the value without realising it represents an error state. Step 2 and Step 3 detect these by checking for known API error sentinel values in the loaded field.

**Centroid clustering as API degradation fingerprint**
When a geocoding API operates in degraded mode, it often falls back to centroid coordinates (postcode centroid, city centroid, country centroid) rather than returning an error. These fallback coordinates are geographically plausible — they pass range checks — but produce artificial clustering. Step 1 detects this by checking for values that exactly match known centroid coordinates within a small tolerance radius.

**Freshness as API contract property**
An API that provides real-time order status has an implied freshness contract: the status value returned should reflect the current state of the order. Step 4 identifies violations of this contract: an order in "Pending" status with a delivery date in the past indicates the status API has not been called (or the response was not stored) since the delivery was completed. This represents both a data quality failure and a potential API integration issue.

**API quality threshold vs operational tolerance**
Step 5's thresholds (99% = pass, 95-99% = warn, <95% = fail) are illustrative. The appropriate threshold depends on the API's SLA and the business impact of degraded responses. A geocoding API at 95% quality means 5% of customer addresses are wrong — which may be acceptable for a delivery distance estimate but unacceptable for regulatory address verification.

## Severity
**High** — API response quality failures are invisible to the ETL pipeline if only HTTP status codes are checked. Degraded API responses (centroid coordinates, error sentinels, stale status values) are stored as if they were correct, then used as input to downstream analysis, routing, and reporting. The downstream impact is proportional to the API's role in the data pipeline — a geocoding API affecting delivery routing can directly cause operational failures.
