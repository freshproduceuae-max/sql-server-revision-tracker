# G18-T05 — Cross-System | Currency and Unit Conversion Validation

## ID
G18-T05

## Group
18 — Cross-System

## Type
Currency and Unit Conversion Validation — Verifying That Values Have Been Correctly Converted Between Units or Currencies Across Systems

## Live Scenario
A multinational company consolidates financial data from regional systems into a central reporting database. The US system reports revenue in USD, the UK system in GBP, and the German system in EUR. The ETL applies conversion rates and loads all values as GBP. A quarterly review reveals that the USD amounts have been converted using the previous quarter's exchange rate (the rate table was not updated after the quarter-end refresh). The EUR amounts appear correct, but 12 transactions from the German system had their amounts doubled — the German system stores amounts in Euro cents, but the conversion was applied assuming Euro whole units. The currency conversion validation check compares the converted GBP amounts against independently computed expected GBP values and flags both anomalies.

## The Question
> Currency and unit conversion validation verifies that cross-currency or cross-unit amounts have been correctly converted by checking: (1) whether amounts from known source currencies are within the expected range for that currency after conversion; (2) whether the ratio between original and converted amounts is consistent with an expected exchange rate; and (3) whether amounts that should be identical in all systems actually agree within rounding tolerance. SQL implements this by computing expected converted amounts and comparing them to actual values.
> **"Validate currency and amount consistency in the Transactions table: verify that amounts are positive and within reasonable bounds for each currency, check that the distribution of amounts by currency is internally consistent (no currency has amounts that are systematically 100× higher or lower than others, suggesting a cents/units conversion error), and flag any transactions where the amount appears implausible for the stated currency."**

## Table Reference
**Transactions** — `schemas/05_Transactions.csv`
**Orders** — `schemas/02_Orders.csv`

## Solution Query

```sql
-- Step 1: Amount plausibility check by currency
-- Typical order amounts: GBP 10–5000, USD 10–5000, EUR 10–5000
-- Amounts 100x typical suggest a cents/pence conversion error
SELECT
    TransactionID,
    Amount,
    Currency,
    CAST(TransactionDate AS DATE) AS TransactionDate,
    CASE
        -- GBP plausibility
        WHEN Currency = 'GBP' AND Amount > 100000
             THEN 'GBP VERY HIGH: Amount ' + CAST(Amount AS VARCHAR)
                  + ' is > £100,000 — verify not in pence (divide by 100?)'
        WHEN Currency = 'GBP' AND Amount < 0.01 AND Amount > 0
             THEN 'GBP VERY LOW: Amount is sub-penny — possible unit conversion error'
        -- USD plausibility
        WHEN Currency = 'USD' AND Amount > 100000
             THEN 'USD VERY HIGH: Amount > $100,000 — possible cents conversion error'
        WHEN Currency = 'USD' AND Amount < 0.01 AND Amount > 0
             THEN 'USD VERY LOW: Sub-cent amount — possible unit error'
        -- EUR plausibility
        WHEN Currency = 'EUR' AND Amount > 100000
             THEN 'EUR VERY HIGH: Amount > €100,000 — verify not in eurocents'
        -- Negative amounts
        WHEN Amount < 0
             THEN 'NEGATIVE AMOUNT: ' + CAST(Amount AS VARCHAR)
                  + ' — verify if refund or conversion error'
        -- Zero amount
        WHEN Amount = 0
             THEN 'ZERO AMOUNT: Transaction recorded with £0 value'
        -- NULL
        WHEN Amount IS NULL
             THEN 'NULL AMOUNT: Amount not recorded'
        ELSE 'Amount plausible for currency'
    END AS AmountPlausibilityFlag
FROM Transactions
WHERE Amount IS NULL OR Amount <= 0 OR Amount > 100000;

-- Step 2: Cross-currency amount comparison
-- If the same OrderID has transactions in multiple currencies, amounts should reconcile
WITH MultiCurrencyOrders AS (
    SELECT
        OrderID,
        COUNT(DISTINCT Currency) AS CurrencyCount,
        STRING_AGG(Currency, ', ') AS Currencies,
        SUM(Amount) AS TotalAllCurrencies,
        MIN(Amount) AS MinAmount,
        MAX(Amount) AS MaxAmount
    FROM Transactions
    WHERE OrderID IS NOT NULL AND Currency IS NOT NULL AND Amount IS NOT NULL
    GROUP BY OrderID
    HAVING COUNT(DISTINCT Currency) > 1
)
SELECT
    m.OrderID,
    m.CurrencyCount,
    m.Currencies,
    m.TotalAllCurrencies,
    m.MinAmount,
    m.MaxAmount,
    ROUND(m.MaxAmount / NULLIF(m.MinAmount, 0), 2) AS MaxToMinRatio,
    CASE
        WHEN m.MaxAmount / NULLIF(m.MinAmount, 0) > 150
             THEN 'CONVERSION ANOMALY: Max/min ratio of '
                  + CAST(ROUND(m.MaxAmount / NULLIF(m.MinAmount, 0), 0) AS VARCHAR)
                  + 'x — possible pence/cents error (factor of 100) in one currency'
        WHEN m.MaxAmount / NULLIF(m.MinAmount, 0) > 3
             THEN 'EXCHANGE RATE RANGE: Amounts vary by '
                  + CAST(ROUND(m.MaxAmount / NULLIF(m.MinAmount, 0), 1) AS VARCHAR)
                  + 'x across currencies — verify exchange rates applied'
        ELSE 'Multi-currency amounts within expected range'
    END AS ConversionFlag
FROM MultiCurrencyOrders m;

-- Step 3: Currency distribution and amount statistics
SELECT
    Currency,
    COUNT(*) AS TxnCount,
    ROUND(MIN(Amount), 2) AS MinAmount,
    ROUND(MAX(Amount), 2) AS MaxAmount,
    ROUND(AVG(Amount), 2) AS AvgAmount,
    ROUND(STDEV(Amount), 2) AS StdDevAmount,
    ROUND(SUM(Amount), 2) AS TotalAmount,
    -- Flag currencies where average is 100x different from others (suggests unit error)
    CASE
        WHEN AVG(Amount) > (SELECT AVG(Amount) * 100 FROM Transactions WHERE Currency <> t.Currency AND Currency IS NOT NULL AND Amount IS NOT NULL)
             THEN 'UNIT ERROR SUSPECTED: Average ' + Currency + ' amount is 100x other currencies'
        WHEN AVG(Amount) < (SELECT AVG(Amount) / 100 FROM Transactions WHERE Currency <> t.Currency AND Currency IS NOT NULL AND Amount IS NOT NULL)
             THEN 'UNIT ERROR SUSPECTED: Average ' + Currency + ' amount is 1/100 of other currencies'
        ELSE 'Amount distribution consistent with other currencies'
    END AS UnitConsistencyFlag
FROM Transactions t
WHERE Currency IS NOT NULL AND Amount IS NOT NULL
GROUP BY Currency;

-- Step 4: Orders vs Transactions amount reconciliation
-- For matched Order-Transaction pairs, TotalAmount and Amount should be close
-- (allowing for partial payments, fees, or FX conversion)
WITH OrderTxnPairs AS (
    SELECT
        o.OrderID,
        o.TotalAmount AS OrderAmount,
        t.Amount AS TxnAmount,
        t.Currency,
        ROUND(ABS(o.TotalAmount - t.Amount), 2) AS AmountDiff,
        ROUND(ABS(o.TotalAmount - t.Amount) / NULLIF(o.TotalAmount, 0) * 100, 1) AS DiffPct
    FROM Orders o
    JOIN Transactions t ON o.OrderID = t.OrderID
    WHERE o.TotalAmount IS NOT NULL AND t.Amount IS NOT NULL
)
SELECT
    OrderID,
    OrderAmount,
    TxnAmount,
    Currency,
    AmountDiff,
    DiffPct,
    CASE
        WHEN DiffPct > 50
             THEN 'LARGE DISCREPANCY: ' + CAST(DiffPct AS VARCHAR)
                  + '% difference — possible currency conversion error or partial payment'
        WHEN DiffPct > 10
             THEN 'MODERATE DISCREPANCY: ' + CAST(DiffPct AS VARCHAR)
                  + '% difference — investigate exchange rate or fee adjustment'
        WHEN DiffPct > 1
             THEN 'MINOR DISCREPANCY: ' + CAST(DiffPct AS VARCHAR) + '% — likely FX rounding'
        ELSE 'RECONCILED: Amounts match within 1%'
    END AS ReconciliationFlag
FROM OrderTxnPairs
ORDER BY DiffPct DESC;

-- Step 5: Conversion validation summary
SELECT
    'Transactions with valid currency code' AS Metric, COUNT(*) AS Value
FROM Transactions WHERE Currency IN ('GBP','USD','EUR','JPY','CHF','CAD','AUD')
UNION ALL
SELECT 'Transactions with amount > 0', COUNT(*)
FROM Transactions WHERE Amount > 0
UNION ALL
SELECT 'GBP transactions', COUNT(*)
FROM Transactions WHERE Currency = 'GBP'
UNION ALL
SELECT 'Non-GBP transactions (may require FX validation)', COUNT(*)
FROM Transactions WHERE Currency <> 'GBP' AND Currency IS NOT NULL
UNION ALL
SELECT 'Orders with matching Transaction amounts (within 1%)',
    COUNT(*)
FROM Orders o JOIN Transactions t ON o.OrderID = t.OrderID
WHERE ABS(ISNULL(o.TotalAmount,0) - ISNULL(t.Amount,0)) / NULLIF(o.TotalAmount,0) <= 0.01;
```

## Explanation

**Cents vs units as a 100× systematic error**
The most common currency conversion error is loading amounts in the smallest monetary unit (pence, cents, eurocents) when the target expects amounts in the major unit (pounds, dollars, euros). A transaction of £12.50 stored as 1250 (pence) appears in reports as £1,250 — a 100× overstatement. Step 3's ratio comparison detects when one currency's average is 100× different from others, which is the statistical fingerprint of this error.

**FX rate validation by ratio**
If the source system provides original-currency amounts and the target expects converted GBP amounts, the conversion factor (Amount_GBP / Amount_original) should equal the exchange rate on the transaction date ± rounding. A transaction converted at a ratio of 1.27 on a date when USD/GBP was 0.79 is either wrong or uses a different rate basis. Step 2's max/min ratio detection provides a proxy check without requiring the actual rate table.

**Multi-currency order detection**
Step 2 identifies orders where multiple transactions were recorded in different currencies — which may be legitimate (split payments across currencies) or may indicate that the ETL applied different conversion rules to transactions from the same order. The max/min ratio within a multi-currency order provides a conversion plausibility check.

**1% reconciliation tolerance for FX rounding**
Step 4's 1% tolerance for Order vs Transaction amount reconciliation accommodates FX rounding (a USD→GBP conversion may introduce rounding differences), transaction fees (payment processors charge 0.3–3% per transaction), and timing differences (the exchange rate at transaction time differs from the order rate). Differences above 10% warrant investigation; differences above 50% suggest a systematic conversion error.

## Severity
**High** — Currency conversion errors directly misstate financial figures. A cents-vs-units error produces a 100× overstatement of revenue in reports, which can mislead management decisions and, in regulated environments, constitutes a material financial reporting error. Exchange rate errors produce smaller but systematic misstatements that accumulate over time.
