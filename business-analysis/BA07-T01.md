# BA07-T01 — Requirements Analysis and Design Definition | Specifying and Modelling Requirements

## ID
BA07-T01

## Chapter
7 — Requirements Analysis and Design Definition

## Live Scenario
A requirement reads: 'The system should handle overdue invoices appropriately.' Three developers implement three different behaviours, all defensible against that sentence.

## The Question
> How do you specify this so that only one implementation is possible?

## Approach
1. Replace ambiguous verbs with defined behaviour and explicit conditions.
2. Model rather than describe where structure matters — a decision table beats a paragraph for branching rules.
3. State the boundaries: what happens at exactly 30 days, at zero balance, on a weekend.
4. Define acceptance criteria alongside the requirement so 'done' is testable.

## Deliverables
- A specified requirement with acceptance criteria
- A decision table or process model for branching logic

## Tools
- Visio or Lucidchart for models
- Confluence for specifications
- Jira for acceptance criteria

## Common Pitfall
Words like appropriately, properly, and as required. Each one is a decision deferred to whoever writes the code, usually without them realising it.

## Interview Angle
You may be handed a vague requirement and asked to improve it. Boundary conditions are what separate a strong answer from a generic one.
