## Live Scenario
The nightly settlement job (from the previous lesson's SLA-monitoring scenario) is now correctly paging on-call when it is at risk of a late finish -- but the on-call engineer who gets paged at 3 AM has never actually used the Spark UI to diagnose a real problem before, and defaults to restarting the job 'to see if it goes faster the second time' whenever they get paged, without looking at anything. Tonight's page fires because a single stage -- a groupBy aggregation over 800 million settlement records -- has been running for 35 minutes while every other stage that night finished in under 4 minutes. The on-call engineer's habitual restart makes it worse: the restarted job hits the exact same slow stage again, now with less time left before the SLA deadline than before.

## The Question
> Using the Spark UI's actual Stages and Tasks views (not guesswork or a blind restart), walk through how to diagnose whether this specific stage's slowness is caused by data skew, insufficient parallelism, or a genuinely larger data volume than usual -- and explain, using real Spark UI evidence, why a blind restart was the wrong first move regardless of which of the three turns out to be the actual cause.

## Solution Code
```python
from pyspark.sql import SparkSession

spark = SparkSession.builder.appName("nightly-settlement").getOrCreate()

# --- Step 1: the Spark UI's Stages tab, BEFORE touching anything ---
# Navigate to the Spark UI's Stages tab for the currently-running job and
# find the groupBy stage that has been running 35 minutes. The Stages tab
# shows, per stage: total tasks, tasks completed, and -- critically --
# task DURATION DISTRIBUTION (min / 25th percentile / median / 75th
# percentile / max), not just an average. This distribution is the single
# most important piece of evidence for distinguishing skew from the other
# two candidate causes, and it is available WHILE the stage is still
# running -- exactly the evidence a blind restart throws away and has to
# re-accumulate from zero.

# --- Step 2: reading the task duration distribution to distinguish the
# three candidate causes ---
#
# SKEW signature: max duration is dramatically higher than the 75th
# percentile (e.g. 75th percentile = 40 seconds, max = 34 minutes) while
# MOST tasks (the 25th/50th/75th percentiles) completed quickly. This
# means the DATA is unevenly distributed across partitions -- one or a
# few partitions/keys have far more rows than the rest -- not that the
# whole stage is short on resources.
#
# INSUFFICIENT PARALLELISM signature: task count itself is suspiciously
# low relative to the cluster's available cores (e.g. 8 tasks total on a
# 200-core cluster), and durations are fairly EVEN across tasks -- the
# work is spread across too few partitions to use the available
# executors, not concentrated on one skewed key.
#
# GENUINELY LARGER VOLUME signature: task count and duration distribution
# both look NORMAL/even relative to typical nights (no skew, adequate
# parallelism), but total row count for this stage's input is measurably
# higher than the historical baseline -- the stage is just doing
# proportionally more real work, correctly, not failing.

spark.sql("SELECT COUNT(*) FROM iceberg_catalog.banking.settlements WHERE settlement_date = current_date()").show()
# Compare this count against the same query's typical historical result --
# this is the concrete check for "genuinely larger volume" as a candidate
# cause, rather than assuming it without evidence.

# --- Step 3: if skew is the diagnosis (the actual cause here, per the
# Spark UI's task-duration distribution showing one 34-minute outlier
# against a 40-second 75th percentile) -- confirm the skewed key(s) ---
from pyspark.sql import functions as F
skew_check = (
    spark.table("iceberg_catalog.banking.settlements")
    .filter(F.col("settlement_date") == F.current_date())
    .groupBy("settlement_batch_id")
    .count()
    .orderBy(F.col("count").desc())
    .limit(5)
)
skew_check.show()
# If one settlement_batch_id has an order-of-magnitude more rows than the
# rest, this confirms skew as the root cause, driven by a specific,
# identifiable key -- not a vague "the job is slow" -- and the fix (salting
# that key, or enabling/confirming AQE's skew-join handling if this were a
# join rather than a groupBy) targets that specific key, not the whole job.
```

## Explanation
**The on-call engineer's habitual "restart to see if it goes faster" was the wrong first move regardless of which of the three candidate causes turned out to be real, because a restart changes nothing about any of them -- it discards the one thing the still-running job actually had: a partially-completed stage's real, in-progress evidence.**

**Why a restart cannot fix skew:** if the slowdown is caused by one partition/key holding a disproportionate share of the data (as it is here -- one settlement_batch_id with 340 million rows against a next-largest of 1.2 million), that data distribution is a property of the DATA itself for this run, not of the specific execution attempt. Restarting the job re-reads the exact same skewed data and re-assigns the exact same oversized partition to some task, which will take just as long the second time -- this is exactly what happened in the scenario, and it is why the restart made things strictly worse: the same delay recurred, but now with less time left before the SLA deadline.

**Why a restart cannot fix insufficient parallelism either:** if the real cause were too few partitions relative to available cluster cores, restarting the identical job with the identical partitioning configuration produces the identical parallelism problem -- nothing about a fresh process changes how many partitions the data was split into.

**Why a restart cannot fix genuinely larger data volume:** if the stage is simply processing more real rows than a typical night (correctly, not erroneously), restarting does not reduce the amount of data that needs processing -- the job will take roughly the same, appropriately longer time on its second attempt as its first.

**Why the Spark UI's task-duration distribution -- not a single average -- is the actual diagnostic evidence, and why it had to be read WHILE the stage was still running rather than after a restart destroyed it:** the Stages tab's breakdown into minimum/25th-percentile/median/75th-percentile/maximum task duration is what distinguishes the three candidate causes concretely. Skew shows as a small number of dramatic outliers against an otherwise fast, even distribution (199 tasks under a minute, one task at 35+ minutes) -- this is a data-distribution signature, not a resource signature. Insufficient parallelism shows as a suspiciously low total task count relative to available cores, with fairly even (if uniformly slow) durations -- a partitioning-configuration signature. Genuinely larger volume shows as a normal, even distribution with a normal task count, but a higher total row count against the historical baseline for that query -- a real-workload-growth signature, not a bug at all. Each of these is directly checkable from the Spark UI and a simple count query while the job is still healthy and running -- exactly the evidence a blind restart throws away, forcing a second, identical wait before any of it can be reconstructed.

**The general debugging discipline this generalizes to:** a slow-but-not-crashed Spark stage is diagnosable, in real time, from the Spark UI's task-level evidence -- and the correct first move is always to read that evidence before taking any action that changes the job's state, because restarting (or any other reactive action) is only ever justified once the actual cause is known, since different causes have entirely different fixes (salting a skewed key; increasing partition count; simply accepting a longer runtime for genuinely more data) and none of them is "start over and hope."
