## Live Scenario
A transaction-banking team inherits a nightly reconciliation script written as one 300-line function with no type hints, global variables for file paths, and a bare `except:` around the whole thing. It has failed silently twice this quarter -- once because a source file was late, once because a currency field arrived as a string instead of a float -- and both times the team only found out when Finance asked why yesterday's numbers looked wrong. You are asked to rewrite the core of it as maintainable, typed, testable Python before it is trusted with a third data source.

## The Question
> Refactor a single monolithic reconciliation function into typed, single-responsibility functions with explicit error handling, so a malformed input fails loudly at the point of failure instead of producing a silently wrong number three steps later.

## Solution Code
```python
from dataclasses import dataclass
from decimal import Decimal, InvalidOperation
from pathlib import Path
import csv


@dataclass(frozen=True)
class TransactionRow:
    transaction_id: str
    account_id: str
    amount: Decimal
    currency: str


class RowParseError(Exception):
    """Raised when a single CSV row cannot be parsed into a TransactionRow.
    Carries the row number so the caller can report exactly which line failed,
    not just that 'something' in the file was wrong."""
    def __init__(self, row_number: int, reason: str):
        self.row_number = row_number
        self.reason = reason
        super().__init__(f"row {row_number}: {reason}")


def parse_row(row_number: int, raw: dict[str, str]) -> TransactionRow:
    """Parse one CSV row into a typed TransactionRow, or raise RowParseError
    naming exactly which row and which field failed -- the opposite of a bare
    `except:` that swallows the row number and the reason together."""
    try:
        amount = Decimal(raw["amount"])
    except (InvalidOperation, KeyError) as e:
        raise RowParseError(row_number, f"invalid amount {raw.get('amount')!r}") from e
    currency = raw.get("currency", "").strip().upper()
    if len(currency) != 3:
        raise RowParseError(row_number, f"invalid currency code {currency!r}")
    if not raw.get("transaction_id"):
        raise RowParseError(row_number, "missing transaction_id")
    return TransactionRow(
        transaction_id=raw["transaction_id"],
        account_id=raw.get("account_id", ""),
        amount=amount,
        currency=currency,
    )


def load_transactions(path: Path) -> tuple[list[TransactionRow], list[RowParseError]]:
    """Load every parseable row and collect every parse failure -- rather than
    stopping at the first bad row, which would hide how many other rows are
    also broken and force a fix-one-rerun-fix-one-rerun cycle to find out."""
    good: list[TransactionRow] = []
    bad: list[RowParseError] = []
    with path.open(newline="", encoding="utf-8") as f:
        reader = csv.DictReader(f)
        for i, raw in enumerate(reader, start=2):  # header is row 1
            try:
                good.append(parse_row(i, raw))
            except RowParseError as e:
                bad.append(e)
    return good, bad


def reconcile_totals(rows: list[TransactionRow]) -> dict[str, Decimal]:
    """Sum amounts per currency using Decimal throughout -- never float for
    money, since binary floating point cannot represent most decimal
    fractions exactly and the rounding error compounds across thousands of
    rows into a genuinely wrong total, not just a display artifact."""
    totals: dict[str, Decimal] = {}
    for row in rows:
        totals[row.currency] = totals.get(row.currency, Decimal("0")) + row.amount
    return totals
```

## Expected Output
Running `load_transactions(Path('transactions.csv'))` against a file with 3 malformed rows out of 1,000 returns `(997 good rows, [RowParseError(row 2: invalid amount ''), RowParseError(row 451: invalid currency code 'GB'), RowParseError(row 812: missing transaction_id)])` -- every failure is named and located, and the 997 good rows still reconcile correctly instead of the whole run aborting or silently including three corrupted rows.

## Explanation
**Type hints and `@dataclass(frozen=True)` turn a stringly-typed dict-of-dicts into a real, checkable shape.** A static type checker (mypy) or even just an IDE can now catch `row.ammount` (typo) or passing a `str` where a `TransactionRow` is expected, before the code ever runs against real data.

**A specific exception class beats a bare `except:`.** The original script's blanket `except:` catches genuine bugs (a typo in a variable name) the same way it catches a genuinely malformed input row -- both disappear silently. `RowParseError` carries the row number and reason, so a failure is diagnosable from the exception alone, not from re-reading the whole file.

**Collecting all failures instead of stopping at the first one** is a deliberate design choice for a reconciliation job specifically: the operator needs to know the *scope* of the data-quality problem (3 bad rows out of 1,000 is very different from 300) before deciding whether to fix-and-rerun or escalate.

**`Decimal`, never `float`, for money.** `0.1 + 0.2 == 0.30000000000000004` in IEEE 754 floating point -- a real, reproducible bug, not a theoretical one. Summing thousands of transaction amounts as `float` produces a total that is *close* to correct but not exactly correct, which is exactly the kind of discrepancy that triggers a false reconciliation break and wastes an afternoon chasing a bug that was never in the data.
