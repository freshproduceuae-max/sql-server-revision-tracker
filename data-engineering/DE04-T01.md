# DE04-T01 — Hadoop Ecosystem and Cloudera Data Platform | HDFS and Apache Ozone

## ID
DE04-T01

## Chapter
4 — Hadoop Ecosystem and Cloudera Data Platform

## Live Scenario
A bank's fraud-detection platform stores two very different things on the same on-prem Hadoop cluster: a handful of enormous nightly transaction-ledger extracts (each 200-500GB, written once, read many times by Spark batch jobs) and millions of small per-customer risk-model artifacts (each 50-200KB, one file per customer per day, produced by an ML scoring job). Six months in, the NameNode's memory usage has grown alarmingly and cluster admins are getting warnings about approaching the practical file-count ceiling -- almost entirely driven by the small risk-model files, even though they are a tiny fraction of total bytes stored. A junior engineer proposes 'just add more NameNode memory,' but the platform team instead migrates only the small-file workload to Apache Ozone, leaving the large ledger extracts on HDFS untouched.

## The Question
> Explain, in terms of how HDFS and Ozone are actually architected -- not just 'Ozone is newer' -- why the small-file workload was the one causing the NameNode pressure, why migrating only that workload (not the whole cluster) was the correct fix, and what would have gone wrong if the team had migrated the large ledger extracts to Ozone instead.

## Solution Code
```bash
# --- Why HDFS strains under many small files ---
# HDFS's NameNode holds the ENTIRE filesystem namespace -- every file,
# directory and block's metadata -- in memory, on a single active node.
# Each file, regardless of its size, costs roughly the same fixed amount
# of NameNode memory (an inode-like metadata record, plus one block record
# per block the file occupies). A 500GB ledger extract stored as a handful
# of large blocks costs the NameNode about the same metadata overhead as
# a single 100KB risk-model file -- so a million small files cost roughly
# a million times more NameNode memory than one big file, for a tiny
# fraction of the actual bytes stored. This is HDFS's well-known "small
# files problem": it was designed around a POSIX-like model optimized for
# a moderate number of very large files, not a high count of small ones.

hdfs dfsadmin -report | grep -A2 "Configured Capacity"
hdfs fsck /risk-model-artifacts -files -blocks | tail -5
# ^ this is where the team would have seen the actual small-file count
# driving the NameNode pressure, not the ledger extracts.

# --- Why Ozone fixes the small-file case specifically ---
# Ozone is architected as a distributed KEY-VALUE / OBJECT store, not a
# single-NameNode-namespace filesystem. Its metadata is split across
# multiple Ozone Managers backed by RocksDB, and objects (keys) map
# directly to storage containers without funneling every single file's
# metadata through one node's heap the way HDFS's NameNode does. This is
# specifically what makes Ozone suited to a very high count of small
# objects: metadata scaling is distributed, not bottlenecked on one
# process's memory.

ozone sh volume create /risk-models
ozone sh bucket create /risk-models/daily-scores
ozone sh key put /risk-models/daily-scores/customer-12345-2026-08-21.json ./scored_output.json
# Migrating ONLY this workload -- not the ledger extracts -- moves exactly
# the files that were causing NameNode pressure, onto the architecture
# built to hold many small objects cheaply.

# --- Why migrating the LARGE ledger extracts to Ozone would have been wrong ---
# HDFS remains genuinely well suited to large, sequentially-written,
# sequentially-read files -- this is not "HDFS is legacy, replace it
# everywhere." Ozone's S3-compatible object semantics and Hadoop-compatible
# file-system interface (o3fs/ofs) make it a drop-in replacement in many
# cases, but the platform team's choice to leave the large files on HDFS
# was deliberate: it correctly diagnosed which SPECIFIC workload was
# hitting a SPECIFIC architectural limit, rather than treating "move to
# the newer object store" as a universal upgrade.
hdfs dfs -ls -h /ledger-extracts/ | head -3
```

## Expected Output
hdfs fsck small-file directory: ~4,200,000 files, most under 200KB --
  this count, not total bytes, is what NameNode memory pressure scales with.

After migrating only risk-model-artifacts to Ozone:
  NameNode memory pressure drops sharply (file count it tracks falls by
  ~4.2M); ledger-extracts/ (still on HDFS, ~180 large files totalling
  40TB) is completely unaffected -- because it was never the source of
  the pressure in the first place.

If the ledger extracts HAD been moved to Ozone instead: no NameNode
  relief (the small files, still the actual cause, would remain on HDFS
  untouched), while adding migration risk and operational complexity to
  a workload that was never broken.

## Explanation
**The mistake the junior engineer's "add more NameNode memory" proposal made was treating the symptom (memory pressure) as the problem, rather than diagnosing which specific workload characteristic was driving it -- and the platform team's fix worked because it correctly separated "HDFS has a small-file problem" from "HDFS is broadly inadequate for this cluster."**

**Why file count, not byte volume, is what stresses a NameNode:** HDFS keeps its entire namespace -- every file's metadata, every directory, every block-to-datanode mapping -- resident in the active NameNode's memory, because every metadata operation (a file open, a listing, a block lookup) has to be served from RAM to meet HDFS's latency expectations. This means the NameNode's memory footprint scales with the *number* of files and blocks, almost independent of their size. A single 500GB file split into a handful of 128MB-or-larger blocks costs the NameNode a small, roughly constant amount of metadata. A million 100KB files cost the NameNode a million times that overhead, while occupying a small fraction of the actual disk space the 500GB file does. This is exactly the mismatch in the scenario: millions of small risk-model files were the entire source of the NameNode pressure, while the enormous but few-in-number ledger extracts were essentially free from the NameNode's point of view.

**Why Ozone fixes specifically this problem, architecturally, not just "because it's newer":** Ozone does not use a single NameNode-style namespace holder at all. It is built as a distributed key-value/object store: Ozone Managers (which can themselves be scaled/replicated) track key-to-container metadata in RocksDB, and actual data lives in Storage Container Manager-managed containers, addressed directly rather than through one process's in-memory namespace tree. This is the concrete mechanism behind Ozone's suitability for very high object counts -- it was designed, from the ground up, around the assumption that metadata volume needs to scale independently of any single node's memory, which is precisely the axis HDFS's architecture does not scale well on.

**Why migrating only the small-file workload -- not the whole cluster -- was the right scope, and why moving the large files instead would have been a real mistake:** HDFS's block-oriented, POSIX-like design is still a good fit for large, sequentially-accessed files; nothing about the ledger extracts' access pattern (nightly batch write, repeated large sequential reads by Spark) benefits from Ozone's object-store semantics, and migrating them would have added real operational risk (a data-migration project, new access-pattern validation, retraining any tooling that assumed classic HDFS paths) for a workload that was never contributing to the actual problem. Meanwhile, if the team had "fixed" the NameNode pressure by moving the large files instead of the small ones, the true cause -- millions of small-file inodes still resident in NameNode memory -- would have remained completely untouched, and the pressure would have continued exactly as before.

**The general diagnostic principle this generalizes to:** before choosing a storage-layer migration, identify the specific resource being exhausted (here: NameNode metadata memory, which scales with file count) and the specific workload driving it (here: the small-file writer, not the large-file writer) -- then move only that workload to the architecture that actually addresses that specific bottleneck, rather than treating a platform-level migration as a blanket upgrade applied uniformly.
