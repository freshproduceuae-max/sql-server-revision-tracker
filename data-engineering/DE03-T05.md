## Live Scenario
A platform architecture review is choosing where the bank's newly ingested transaction-banking data should land. One team argues for a traditional data warehouse (structured, schema-on-write, strong ACID guarantees, but expensive to scale and rigid about schema changes -- directly relevant given T03's schema-evolution scenario). Another argues for a raw data lake (cheap object storage, schema-on-read, handles any file format, but historically has no transactional guarantees -- a batch job that fails halfway through a write can leave the lake in a partially-written, inconsistent state with no rollback). A third proposes Apache Iceberg specifically, describing it as getting 'the best of both,' but cannot explain concretely what problem Iceberg actually solves versus a raw lake, beyond the marketing phrase.

## The Question
> Explain concretely -- not as a marketing claim -- what specific problem Iceberg's table format solves that a raw data lake does not, using Iceberg's actual mechanisms (not vague 'ACID for lakes' language), and state when a straightforward data warehouse is still the better choice despite Iceberg being available.

## Solution Code
```python
from pyspark.sql import SparkSession

spark = SparkSession.builder.appName("lakehouse-format-comparison").getOrCreate()

# --- Raw data lake write: no transactional guarantee ---
# If this job fails after writing 60% of its output files, the lake now
# contains a partial write with no built-in way to know which files belong
# to a "complete" logical write versus a failed one -- a reader querying
# mid-failure sees inconsistent, partial data with no signal that anything
# is wrong.
raw_df = spark.read.parquet("s3://bank-data/transactions/staging/")
raw_df.write.mode("overwrite").parquet("s3://raw-lake/transactions/2026-08-20/")
# ^ if this crashes partway, the target prefix now has SOME of the new
# files and possibly some of the old files, and nothing recorded which
# set is "the current, valid version of this data."

# --- Iceberg: the same write, but through a table format with atomic commits ---
spark.sql("""
  CREATE TABLE IF NOT EXISTS lakehouse.transactions.settled (
    transaction_id STRING, amount DOUBLE, currency STRING, settled_ts TIMESTAMP
  ) USING iceberg
""")

raw_df.writeTo("lakehouse.transactions.settled").append()
# Iceberg tracks table state as a sequence of immutable METADATA SNAPSHOTS --
# each write produces a new snapshot that atomically becomes "current" only
# once every one of its data files has been written successfully. A crash
# partway through leaves the previous snapshot as the only "current" one;
# readers never see a half-written state, because the atomic pointer swap
# to the new snapshot never happens until the write fully succeeds.

# This is also what enables TIME TRAVEL -- a capability a raw lake has no
# mechanism for at all, because a raw lake has no concept of "prior state"
# beyond whatever files happen to still exist:
spark.sql("SELECT * FROM lakehouse.transactions.settled VERSION AS OF 4").show(5)
spark.sql("SELECT * FROM lakehouse.transactions.settled TIMESTAMP AS OF '2026-08-19 00:00:00'").show(5)

# And it is what makes the SCHEMA EVOLUTION from T03 safe without rewriting
# data: because Iceberg tracks columns by stable ID (not by file layout),
# a metadata-only schema change and a metadata-only snapshot commit are the
# same underlying mechanism applied to two different kinds of table change.
spark.sql("ALTER TABLE lakehouse.transactions.settled ADD COLUMN risk_score DOUBLE")
```

## Explanation
**The third team's claim ("best of both") was true but unhelpful as stated, because it didn't identify a mechanism -- and the concrete mechanism is Iceberg's snapshot-based commit model, not a vague notion of "ACID."**

**What a raw data lake actually lacks, mechanically:** object storage (S3, Ozone) has no concept of a multi-file transaction. A Spark job writing 200 output files to a lake prefix is really performing 200 independent object-storage writes; if the job fails after 120 of them, those 120 files simply exist in the same prefix as whatever was there before, with nothing in the storage layer itself recording "these 120 files are part of an incomplete write, do not read them as valid." A concurrent reader querying that prefix mid-failure has no way to know it is seeing a partial result -- this is the literal absence of a transaction boundary, not an abstract "lacks ACID" claim.

**What Iceberg's table format adds, mechanically:** every write operation (append, MERGE, overwrite) produces a new **snapshot** -- an immutable metadata record listing exactly which data files constitute the table's state as of that write. The catalog's "current snapshot" pointer only advances to the new snapshot after every file in it has been written successfully; if the job crashes partway, the new snapshot's file list was never fully written, so the pointer never advances, and every reader continues seeing the last snapshot that *did* complete. This is what "atomic commit" concretely means here: not a database-style row lock, but an all-or-nothing swap of which snapshot is authoritative.

**This same snapshot history is what enables time travel** (`VERSION AS OF`, `TIMESTAMP AS OF`) essentially for free -- old snapshots are not deleted immediately, so querying "the table as it looked yesterday" is just pointing a read at an older, still-intact snapshot rather than a bespoke feature bolted on separately. A raw lake has no equivalent: once files are overwritten, whatever they represented is gone unless a team manually built their own versioning scheme on top.

**And it connects directly back to T03's schema-evolution lesson:** Iceberg's column-ID tracking (why renames and additions are safe metadata-only operations) and its snapshot-based writes (why partial failures don't corrupt reader-visible state) are the same underlying design choice -- table state, in both the schema dimension and the data dimension, is tracked as versioned metadata pointing at immutable files, rather than being inferred from whatever happens to be in a directory.

**When a straightforward data warehouse still wins despite Iceberg being available:** Iceberg (and lakehouse formats generally) solve the "transactional guarantees over cheap object storage, at large and varied-format scale" problem -- they do not make a data warehouse's sub-second interactive query performance obsolete, nor do they eliminate the operational simplicity of a warehouse's mature query optimizer for highly structured, moderately sized, well-understood schemas. A team with a few hundred GB of clean, strictly-tabular data, needing interactive dashboard-speed queries, and with no requirement to retain raw or semi-structured source formats for future reprocessing, is often still better served by a traditional warehouse -- the lakehouse pattern earns its complexity specifically at the scale and format-diversity this bank's transaction-banking platform actually has (large volume, multiple raw ingestion formats from T01's three sources, a genuine need to reprocess historical raw data as schemas evolve), not universally.
