## Live Scenario
A data science team building a fraud-scoring model asks the data engineering team for 'a customer's transaction history for the last 30 days' as a training feature. The DE team computes it straightforwardly: for every row in the training dataset, join against the transactions table and count transactions where the timestamp is within 30 days of TODAY (the day the training job happens to run). Six months after the model ships, its live fraud-catch rate is measurably worse than its offline-evaluated accuracy suggested it should be -- and investigation traces the gap to this exact feature: at TRAINING time, 'last 30 days' was computed relative to the day the training job ran (long after the labeled fraud events actually occurred), silently including transactions that happened AFTER the labeled event the model was supposed to be predicting -- data the model would never have had access to at real prediction time.

## The Question
> Explain the specific mechanism by which this feature computation caused training-serving skew and a leakage problem (not model-building technique -- the feature ENGINEERING error), and redesign the feature computation to be point-in-time correct, so the model only ever sees data it would genuinely have had access to at real prediction time. This lesson is about reproducible, leakage-free data preparation for ML, not about choosing or tuning a model.

## Solution Code
```python
from pyspark.sql import SparkSession
from pyspark.sql import functions as F
from pyspark.sql.window import Window

spark = SparkSession.builder.appName("fraud-feature-preparation").getOrCreate()

# --- The LEAKY version: "last 30 days" computed relative to TODAY
# (the training job's run date), not relative to each labeled event's
# actual timestamp ---
labeled_events = spark.table("banking.fraud_labels")  # customer_id, event_ts, is_fraud
transactions = spark.table("banking.transactions")     # customer_id, txn_ts, amount

leaky_feature = (
    labeled_events
    .join(transactions, "customer_id")
    .filter(F.col("txn_ts") >= F.date_sub(F.current_date(), 30))  # <- BUG:
    # "current_date()" is TODAY (whenever the training job happens to
    # run), not the labeled event's own timestamp. For a fraud event that
    # occurred 8 months ago, this filter includes every transaction from
    # the last 30 days relative to TODAY -- which includes transactions
    # that happened AFTER that 8-month-old event, data the model would
    # never have had access to when actually scoring that customer at
    # the real, historical prediction time.
    .groupBy("customer_id", "event_ts", "is_fraud")
    .agg(F.count("*").alias("txn_count_last_30d"))
)

# --- The POINT-IN-TIME CORRECT version: "last 30 days" computed
# relative to EACH ROW'S OWN event_ts, not to today ---
correct_feature = (
    labeled_events.alias("lbl")
    .join(
        transactions.alias("txn"),
        (F.col("lbl.customer_id") == F.col("txn.customer_id"))
        # THE FIX: the window is anchored to event_ts (the labeled
        # event's own historical timestamp), and -- critically --
        # ALSO excludes the event_ts itself, so a transaction cannot
        # "see itself" or anything after it:
        & (F.col("txn.txn_ts") >= F.date_sub(F.col("lbl.event_ts"), 30))
        & (F.col("txn.txn_ts") < F.col("lbl.event_ts"))  # strictly BEFORE
        # the labeled event -- this is what makes the feature genuinely
        # reconstructable at real prediction time: at the moment a real
        # fraud-scoring call would have happened (right before or at
        # event_ts), only transactions strictly before that moment could
        # possibly have existed yet.
    )
    .groupBy("lbl.customer_id", "lbl.event_ts", "lbl.is_fraud")
    .agg(F.count("*").alias("txn_count_last_30d"))
)

# --- Verifying reproducibility and lineage: this feature computation is
# captured as a named, versioned transformation, not an ad-hoc notebook
# cell -- so "how was txn_count_last_30d computed for THIS training run"
# is an answerable, auditable fact, the same discipline Chapter 5's Atlas
# lineage lesson established for pipeline lineage generally, applied here
# to a FEATURE's specific lineage. ---
correct_feature.write.mode("overwrite") \
    .option("feature_version", "txn_count_last_30d_v2_point_in_time_fix") \
    .saveAsTable("feature_store.fraud_features")

# --- Checking for skew AFTER the fix: comparing the feature's
# distribution in this training set against its distribution when
# computed the SAME way against live scoring traffic -- this is a
# MEASURED check, not an assumption that fixing the join solved everything ---
training_distribution = correct_feature.select(
    F.mean("txn_count_last_30d").alias("mean"),
    F.stddev("txn_count_last_30d").alias("stddev")
)
training_distribution.show()
# Compare against the equivalent statistic computed from the live serving
# path's feature computation -- a persistent gap between the two, even
# after this point-in-time fix, would indicate a DIFFERENT training-
# serving skew source (e.g. the serving path using a different window
# definition or a different data source than training) still needing
# investigation -- this fix addresses the LEAKAGE mechanism specifically,
# not every possible source of training-serving skew.
```

## Expected Output
Leaky version: for a fraud event labeled 8 months ago, txn_count_last_30d
  includes transactions from the 30 days relative to WHENEVER the training
  job ran -- which for an 8-month-old event, includes transactions from
  roughly 7-8 months AFTER the event, none of which could have existed at
  real prediction time. The model trained on a feature value it will
  NEVER see at real inference time, because real inference always happens
  at or near event_ts, when those future transactions don't exist yet.

Point-in-time corrected version: for the same 8-month-old event,
  txn_count_last_30d includes only transactions strictly between
  (event_ts - 30 days) and event_ts -- exactly the data window that
  would have existed at the real moment a fraud-scoring call happened.

Distribution check: training_distribution's mean/stddev for
  txn_count_last_30d, computed the point-in-time-correct way, is now
  directly comparable to the same statistic computed via the live
  serving path -- a persistent gap here (not observed in this case)
  would flag a remaining, different skew source still needing
  investigation.

## Explanation
**This is a feature ENGINEERING defect -- specifically, a point-in-time correctness failure -- not a model-quality or model-choice problem, and the six-months-later symptom (live catch rate worse than offline accuracy suggested) is the textbook signature of training-serving skew caused by leakage, not of an under-tuned model.**

**Why "last 30 days relative to today" is a leakage bug, mechanically:** the training job runs on some date long after most labeled historical fraud events occurred -- computing "last 30 days" relative to that RUN date, rather than relative to each labeled event's own historical timestamp, means the feature silently includes transactions that happened AFTER the event the model is being trained to predict. A fraud-scoring model, at real prediction time, is always evaluating a customer at or near the actual moment of a transaction -- it can never see transactions that have not happened yet, by definition. Training the model on a feature value that includes future-relative-to-the-label data teaches it to rely on information it will structurally never have access to during real inference, which is precisely what "leakage" means: information present at training time that will not be present at serving time.

**Why this specific mistake produces exactly the symptom described (good offline accuracy, worse live catch rate) rather than an obviously broken model:** the leaked feature is not random noise -- it is often correlated with the label in a way that looks like genuine predictive signal during offline evaluation (a fraud event is often followed by patterns of related fraudulent activity, so "transaction count in a window that happens to include some post-event activity" can genuinely correlate with is_fraud in the training data). This is what makes the defect dangerous rather than obviously wrong: the model's offline evaluation metrics look good, because the leaked information really does help predict the label WITHIN THE TRAINING SET. The gap only appears in production, where the equivalent feature computed on live traffic can never include that same future-relative-to-the-label information, because at real serving time there IS no "future" data yet.

**Why the fix is anchoring the window to each row's own event_ts, not to current_date(), and why the strict-inequality boundary matters specifically:** the corrected join filters transactions to those with txn_ts in [event_ts - 30 days, event_ts) -- a window defined relative to each individual labeled event, not to whenever the training job happens to run. The strict < (rather than <=) on the upper boundary is deliberate: it ensures the event's own transaction (if event_ts corresponds to a transaction record itself) cannot be counted as its own feature input, which would be a second, subtler leakage path even after fixing the primary "today vs. event_ts" bug. This is what makes the feature point-in-time correct: at the reconstructed moment corresponding to a real prediction call (at or immediately before event_ts), only data with that exact boundary condition could genuinely have existed.

**Why this generalizes as feature-lineage and reproducibility discipline, not just a one-off join fix:** recording the feature computation as a named, versioned transformation (rather than an ad-hoc notebook cell) is what makes "how was this specific feature computed for this training run" an auditable, answerable fact later -- the same lineage discipline Chapter 5 established for pipeline provenance generally, applied here specifically to a feature's own computation history. And explicitly comparing the feature's statistical distribution between the training computation and the live serving computation (rather than assuming the point-in-time fix alone resolved every possible skew source) is the measured-evidence discipline this whole chapter has required throughout -- a persistent distributional gap after this fix would be real evidence of a DIFFERENT skew source (e.g., the serving path computing the same nominal feature differently) still needing investigation, not something to assume away.

**What this lesson is deliberately not about:** none of this is model-selection, hyperparameter tuning, or model-architecture guidance -- the defect, the diagnosis, and the fix are all entirely at the level of how the input DATA to any model is prepared, which is the scope this lesson stays within.
