## Live Scenario
A bank's Spark ingestion pipeline loads daily transaction files into the lakehouse. A recent source-system bug caused 4,200 transactions (out of 2.1 million that day) to arrive with a null customer_id -- a completeness defect Data Validation G01 already teaches how to DETECT with a SQL Server null-count query. The pipeline, however, has no equivalent check at Spark scale: it currently loads every row regardless, and the 4,200 bad rows silently propagate into three downstream tables before anyone notices, three days later, when a reconciliation report breaks. The engineer who built the pipeline argues for making the whole job fail immediately on any null customer_id. A second engineer argues the opposite: never fail the job, just log a warning and load everything anyway, since 4,200 out of 2.1 million is 'basically nothing.'

## The Question
> Using the completeness-check LOGIC Data Validation G01 already teaches (not re-deriving it from scratch), design where in the Spark pipeline that check should run, and explain why neither 'always hard-fail' nor 'always load and warn' is the right uniform policy for every quality defect a pipeline might encounter.

## Solution Code
```python
from pyspark.sql import SparkSession
from pyspark.sql import functions as F

spark = SparkSession.builder.appName("dq-gate-transactions").getOrCreate()

raw = spark.read.parquet("s3://bank-data/transactions/date=2026-08-21/")

# The COMPLETENESS CHECK ITSELF is exactly what Data Validation G01 already
# teaches -- "is this required column null" -- just expressed against a
# DataFrame instead of a SQL Server table. This lesson does not re-derive
# that logic; it answers a question G01 does not need to answer at
# SQL-Server-table scale: WHERE in a distributed pipeline does the check
# run, and what happens to the 2.1 million rows while 4,200 of them are
# being evaluated.
completeness_check = raw.withColumn(
    "customer_id_null",  # same check as G01's null-count query, applied per-row
    F.col("customer_id").isNull()
)

good_rows = completeness_check.filter(~F.col("customer_id_null")).drop("customer_id_null")
bad_rows  = completeness_check.filter(F.col("customer_id_null")).drop("customer_id_null")

bad_count = bad_rows.count()
total_count = raw.count()
bad_fraction = bad_count / total_count

# QUARANTINE, not silent pass-through and not a blanket hard-fail: the bad
# rows are written to their own table/location -- measurable, inspectable,
# and specifically NOT allowed into the tables the reconciliation report
# reads from -- while the good rows continue through the pipeline.
bad_rows.write.mode("append").parquet(
    f"s3://lakehouse/quarantine/transactions/reason=null_customer_id/date=2026-08-21/"
)
good_rows.write.mode("append").parquet(
    "s3://lakehouse/raw/transactions/date=2026-08-21/"
)

# The DECISION of fail-vs-quarantine-and-continue is itself data-driven,
# against an explicit, agreed THRESHOLD -- not a blanket policy applied to
# every defect regardless of its actual severity or blast radius.
NULL_CUSTOMER_ID_HARD_FAIL_THRESHOLD = 0.01  # 1% of the day's volume

if bad_fraction > NULL_CUSTOMER_ID_HARD_FAIL_THRESHOLD:
    raise RuntimeError(
        f"HARD FAIL: {bad_count}/{total_count} ({bad_fraction:.2%}) rows failed "
        f"the customer_id completeness check -- exceeds the {NULL_CUSTOMER_ID_HARD_FAIL_THRESHOLD:.0%} "
        f"threshold, indicating a likely upstream systemic failure rather than "
        f"isolated bad records. Pipeline halted; nothing written downstream of quarantine."
    )
else:
    print(
        f"QUARANTINED, PIPELINE CONTINUES: {bad_count}/{total_count} ({bad_fraction:.4%}) rows "
        f"quarantined for null customer_id -- below the {NULL_CUSTOMER_ID_HARD_FAIL_THRESHOLD:.0%} "
        f"threshold. {total_count - bad_count} good rows proceeded to raw/transactions/."
    )
# This run: 4,200 / 2,100,000 = 0.2% -- well under the 1% threshold, so the
# pipeline quarantines and continues rather than halting 2.096 million
# genuinely good rows over an isolated 0.2% defect.
```

## Expected Output
Completeness check result (2026-08-21 run):
  4,200 / 2,100,000 rows (0.2000%) failed the customer_id null check.
  0.2% < the agreed 1% hard-fail threshold -> QUARANTINED, PIPELINE CONTINUES.
  2,095,800 good rows loaded into raw/transactions/.
  4,200 bad rows written to quarantine/transactions/reason=null_customer_id/
    -- inspectable, NOT present in any table the reconciliation report reads.

Contrast: if the SAME upstream bug had instead corrupted 35,700 rows (1.7%
  of that day's volume) -- above the 1% threshold -- the pipeline would
  raise RuntimeError and halt, writing nothing to raw/transactions/ for
  that date, because a defect at that scale is evidence of a likely
  systemic upstream failure, not isolated bad records safe to set aside.

## Explanation
**Both engineers' proposed policies were each half-right and half-wrong, because both were arguing for a single UNIFORM policy applied to every quality defect regardless of its actual scale and blast radius -- and the fix is not "compromise between the two," it is to make the fail-vs-continue decision an explicit, measured, threshold-driven one rather than a blanket rule either way.**

**Why "always hard-fail" is wrong as a universal policy:** halting the entire 2.1-million-row pipeline over 4,200 isolated bad rows (0.2% of volume) destroys the value of the 99.8% of the data that was perfectly good, delays every downstream consumer of that data by a full day for a defect that quarantining could have handled cleanly, and treats an isolated data-quality issue as if it were a systemic outage -- which it demonstrably was not, since the vast majority of the same source feed loaded correctly the same day.

**Why "always load and warn" is wrong as a universal policy, and why it was the actual root cause of the three-days-later reconciliation break:** logging a warning and loading the bad rows anyway means the defect propagates into every downstream table with no measured limit and no separation from good data -- which is precisely what happened here. "4,200 out of 2.1 million is basically nothing" is true as a *fraction*, but it is not true as a *consequence*: those 4,200 rows corrupted three downstream tables and broke a reconciliation report three days later, specifically because nothing separated them from the good data or made their existence visible until a much later, harder-to-diagnose failure surfaced.

**Why quarantine-with-a-threshold is the actual fix, and how it uses G01's check without re-deriving it:** the completeness check itself -- "is this required column null" -- is exactly the logic Data Validation G01 already establishes; nothing about running it against a Spark DataFrame instead of a SQL Server table changes what the check *is*. What Spark-scale pipelines need beyond G01's detection logic is a DECISION POLICY for what happens once the check finds violations, applied at the volume and velocity a distributed pipeline actually runs at: quarantining bad rows to their own inspectable location keeps them out of the tables downstream consumers (like the reconciliation report) actually read, while measuring the defect rate against an explicit, agreed threshold (here, 1% of daily volume) is what decides whether this specific run's defect rate is "isolated bad records, quarantine and continue" or "evidence of a systemic upstream failure large enough that continuing would compound the damage, halt instead." The same mechanism -- quarantine plus a measured threshold -- produces the hard-fail behavior the first engineer wanted when the defect rate is actually large (the 1.7% counter-example), and the continue-with-quarantine behavior the second engineer wanted when it is actually small (the real 0.2% case), without either engineer's proposed policy being applied blindly regardless of the actual numbers.

**The general principle that generalizes past this one scenario:** a data-quality gate at pipeline scale needs three things a simple detection query does not: an enforcement point (where in the pipeline the check runs, before data reaches downstream consumers), a quarantine mechanism (an inspectable, separate destination for violations, rather than either silent pass-through or complete loss), and a measured, threshold-based decision (fail vs. continue, driven by the actual defect rate for this run, not a blanket policy chosen once and applied regardless of scale). None of these three replace or duplicate G01's completeness-check logic -- they are what a distributed pipeline needs in addition to it.
