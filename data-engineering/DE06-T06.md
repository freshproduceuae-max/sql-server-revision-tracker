## Live Scenario
It is 3 AM. The nightly settlement pipeline (orchestrated per T01, deployed via the CI/CD from T02, running as Spark-on-Kubernetes per T04) has failed at the summarize stage, three hours after a successful extract stage. The on-call engineer, woken by a page, has no runbook to follow -- the team has never written one -- and has to reconstruct, from scratch, at 3 AM: whether it is safe to just re-run the failed stage, whether the extract stage's output might now be stale if this drags into the next business day, whether the last successful run's output is still intact if a rollback becomes necessary, and who else needs to know. They guess wrong on the first question, re-run the WHOLE pipeline from scratch (not just the failed stage), which duplicates the extract stage's already-correct output because that stage's write was never designed to be safely re-run.

## The Question
> Design the specific pieces this pipeline needs -- a real runbook, a retry/backfill policy consistent with T01's idempotent orchestration, a rollback plan referencing a specific recoverable prior state, and an incident-communication plan -- so a 3 AM on-call engineer has concrete, pre-decided answers rather than having to improvise every one of these decisions live, under pressure, for the first time.

## Solution Code
```markdown
# Runbook: Nightly Settlement Pipeline -- Stage Failure

## 1. Retry policy (decided in ADVANCE, not improvised at 3 AM)

| Failed stage | Safe to re-run ALONE? | Why |
|---|---|---|
| extract_transactions | YES | Idempotent per T02's MERGE-on-natural-key
  pattern -- re-running it for the same business_date produces the
  identical result, not duplicate rows. |
| summarize_settlements | YES | Reads extract's output (already correct,
  unchanged by a re-run of THIS stage) and overwrites its own output
  table for the business_date -- safe to re-run alone. |
| generate_regulatory_report | YES | Reads summarize's output and
  overwrites the report for the business_date -- safe to re-run alone. |

**Action for THIS incident:** summarize_settlements failed. Per the table
above, re-run ONLY summarize_settlements (`airflow tasks clear -t
summarize_settlements -s <business_date> -e <business_date>
daily_settlement`) -- extract_transactions already succeeded and does
NOT need to be touched. Re-running the WHOLE pipeline (what actually
happened this incident) was the wrong move BECAUSE it re-ran an already-
successful, already-idempotent extract stage unnecessarily -- not
incorrect in the sense of corrupting data (idempotent writes prevented
that), but incorrect in the sense of wasted time and cluster cost during
an active incident, when every minute matters against the SLA.

## 2. Backfill decision tree (if this drags past the business-day
boundary)

- If resolved before 06:00 UTC (the stated SLA): no backfill needed,
  proceed as a same-day re-run.
- If NOT resolved before 06:00 UTC: this becomes a BACKFILL for a
  business_date that is now "yesterday" relative to wall-clock time --
  explicitly set --conf spark.sql.session.timeZone and the pipeline's
  usiness_date parameter to the ORIGINAL date being processed, not
  today's date, and confirm with airflow dags backfill using
  --start-date and --end-date both set to that original date. This
  is exactly the "catchup=True is an explicit decision, not a default"
  caution from T01 -- a backfill run must be deliberately scoped to the
  specific missed date(s), never to a wider range that could
  accidentally re-trigger already-correct historical runs.

## 3. Rollback plan (referencing a SPECIFIC recoverable state, not a
vague "roll back if needed")

- The report table (iceberg_catalog.banking.regulatory_report) is an
  Iceberg table -- if a bad report is somehow generated and DISTRIBUTED
  before this is caught, the specific recoverable state is: `SELECT
  snapshot_id, committed_at FROM
  iceberg_catalog.banking.regulatory_report.snapshots ORDER BY
  committed_at DESC, then roll back via CALL
  iceberg_catalog.system.rollback_to_snapshot('banking.regulatory_report',
  <last_known_good_snapshot_id>)`. This is the SAME snapshot-based
  recovery mechanism Chapter 3's lakehouse lesson established, applied
  here specifically as this pipeline's rollback plan, not a
  from-scratch design.
- **What rollback does NOT cover:** if the bad report has already been
  consumed downstream (e.g. sent to a regulator), a snapshot rollback
  fixes the TABLE's state but does not itself un-send anything already
  distributed -- that is a separate incident-communication action (see
  section 4), not something the rollback mechanism can address.

## 4. Incident communication (decided in advance: WHO, at WHAT trigger)

| Trigger | Notify |
|---|---|
| Any stage failure detected by paging (T04's alerting) | On-call
  engineer (already paged) |
| Not resolved within 30 min of page | Platform lead (escalation) |
| SLA (06:00 UTC) at risk per T04's projected-completion alert | Downstream
  consumer team (reconciliation) -- proactively, BEFORE they notice
  stale data themselves, which is the exact gap Chapter 5's observability
  lesson identified |
| Any rollback executed | Compliance/audit contact -- a rollback of a
  regulatory-adjacent table is itself an auditable event per Chapter 5's
  lineage discipline |

## 5. Post-incident: update THIS runbook

Any gap discovered during a real incident (a stage whose retry safety
was assumed but not verified, a rollback path that didn't exist for a
table that needed one) gets added here before the incident is closed --
a runbook that is not updated after every real incident becomes exactly
as unreliable as having no runbook at all.
```

## Expected Output
Before (no runbook): on-call engineer, at 3 AM, guesses wrong on
  "re-run just the failed stage vs. the whole pipeline," re-runs
  everything, unnecessarily re-executes an already-successful,
  already-idempotent extract stage -- wasted time and cluster cost
  during an active SLA-risk incident, though no data corruption occurred
  because T02's idempotent write pattern happened to prevent that
  specific consequence.

After (runbook in place): the SAME incident (summarize_settlements
  failure) has a pre-decided answer -- re-run ONLY summarize_settlements,
  per the retry-policy table -- available to ANY on-call engineer, not
  just whoever happened to reason it out correctly at 3 AM this time.

Rollback path: a specific, testable command
  (rollback_to_snapshot with an actual snapshot_id lookup query) exists
  BEFORE it is ever needed, rather than being improvised during a real
  rollback scenario.

Communication: a stated escalation trigger (30 minutes unresolved) and a
  stated proactive-notification trigger (SLA-at-risk, per Chapter 5's
  observability alert) exist in advance, rather than being a judgment
  call made under pressure about whether and when to tell anyone.

## Explanation
**The core failure this incident exposes is not a technical defect in the pipeline -- T02's idempotent writes actually did their job, preventing data corruption from the unnecessary full re-run -- it is the ABSENCE of a pre-decided runbook, which forced an on-call engineer to improvise, under time pressure, at 3 AM, decisions that should have been made calmly in advance and made identically available to whoever is on call.**

**Why the retry-policy table is the direct payoff of T01's orchestration design and T02's idempotency work, not a new mechanism:** T01 established that Airflow tracks each stage as an independently re-runnable task; T02 (and Chapter 3's MERGE/replaceWhere patterns) established which specific write patterns make a stage SAFE to re-run alone. The runbook's retry table does not invent new resilience mechanisms -- it simply writes down, in advance, the answer that was already implied by those two lessons' design choices, so a 3 AM on-call engineer does not have to re-derive "is extract_transactions safe to leave alone" from first principles under pressure. The actual incident-time mistake (re-running the whole pipeline) did not corrupt data, specifically because T02's idempotent MERGE pattern made even the unnecessary re-run of extract_transactions harmless -- but it still cost real time and cluster resources during an active SLA-risk window, which a pre-written retry table would have prevented by giving a fast, correct, unambiguous answer.

**Why the backfill decision tree explicitly reuses T01's "catchup=True is a deliberate choice" caution:** an incident that drags past the business-day boundary turns "re-run this stage" into "backfill a specific historical date," and the danger T01 flagged generalizes directly here -- a backfill must be scoped to exactly the missed date(s), because a broader or vaguer backfill range risks re-triggering already-correct historical runs unnecessarily, exactly the kind of accidental-recompute risk T01's catchup=False default was designed to guard against by requiring backfills to be explicit, deliberate actions rather than an accidental default behavior.

**Why the rollback plan references a specific, already-existing mechanism (Iceberg snapshot rollback from Chapter 3) rather than proposing something new:** resilience planning does not require inventing new recovery mechanisms from scratch -- it requires identifying which ALREADY-EXISTING mechanism (here, Iceberg's snapshot history, established for an entirely different purpose in Chapter 3's lakehouse lesson) applies to THIS pipeline's specific recovery need, and writing down the exact, testable command that would use it. The explicit caveat that rollback does not un-send anything already distributed downstream is equally important: it is what prevents a runbook from overstating what its own recovery mechanism actually covers, the same "do not imply one control provides a guarantee belonging to another" discipline this whole chapter's guardrails required for CI/CD, containers, and Kubernetes.

**Why the incident-communication table connects directly to Chapter 5's observability lesson rather than being a separate, unrelated concern:** the "notify the reconciliation team proactively if the SLA is at risk" trigger is not a new idea invented for this lesson -- it is the exact fix Chapter 5's observability lesson designed (an SLA-risk alert that fires while the job is still running, specifically so someone can act before the deadline is actually missed) now extended one step further into an explicit communication plan: not just "alert on-call," but "at this specific trigger, also proactively tell this specific downstream team," closing the loop Chapter 5 opened.

**The general principle this chapter -- and this whole 36-lesson track -- closes on:** production resilience is not a single technical mechanism to add; it is the discipline of writing down, in advance and while calm, the retry policy, backfill scoping, rollback path, and communication triggers that a pipeline's own already-built properties (idempotency, orchestration tracking, snapshot history, SLA alerting) already make POSSIBLE -- so that a real incident, at 3 AM, under pressure, is a matter of following a pre-decided runbook rather than re-deriving every one of these decisions from first principles for the first time while the SLA clock is running.
