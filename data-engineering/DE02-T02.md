## Live Scenario
A transaction-banking ingestion job reads a daily CSV export with `inferSchema=True` because it was faster to write during development. It has worked correctly for three months. Then one day, a source-system change causes an `AccountID` column that was always numeric to start containing a handful of alphanumeric branch-prefixed values (e.g. `"BR04-88213"` alongside `882130`). The job doesn't fail -- it silently infers the whole `AccountID` column as `StringType` that day instead of `LongType`, and a downstream join against a dimension table keyed on `LongType` AccountID silently returns zero matches for every row, with no error anywhere in the pipeline.

## The Question
> Explain why schema inference is the actual root cause of a silent, zero-match join failure with no error message, and rewrite the ingestion to use an explicit schema that would have made this same source-data change fail loudly and immediately at read time instead.

## Solution Code
```python
from pyspark.sql.types import StructType, StructField, LongType, StringType, DoubleType, DateType
from pyspark.sql import SparkSession

spark = SparkSession.builder.appName("transaction-ingestion").getOrCreate()

# FRAGILE: inferSchema=True re-derives the schema from a SAMPLE of the file
# every single run. A schema-changing source anomaly (like the scenario's
# mixed-type AccountID column) doesn't raise an error -- it just silently
# produces a DIFFERENT schema than yesterday's run, and every downstream
# join/filter that assumed the old schema keeps running without complaint.
# transactions_fragile = spark.read.csv(
#     "s3://bank-data/daily-export/", header=True, inferSchema=True
# )

# ROBUST: an explicit schema is a contract. A file that violates it either
# fails the read outright (mode="FAILFAST") or routes the offending rows to
# a quarantine column (mode="PERMISSIVE" with columnNameOfCorruptRecord) --
# either way, the anomaly becomes visible at ingestion time, not three
# pipeline stages later as an unexplained zero-row join result.
transaction_schema = StructType([
    StructField("TransactionID", StringType(), nullable=False),
    StructField("AccountID", LongType(), nullable=False),  # states the contract explicitly
    StructField("Amount", DoubleType(), nullable=False),
    StructField("Currency", StringType(), nullable=False),
    StructField("TransactionDate", DateType(), nullable=False),
])

transactions = spark.read.csv(
    "s3://bank-data/daily-export/",
    header=True,
    schema=transaction_schema,
    mode="FAILFAST",  # any row that cannot conform to the schema aborts the read immediately
)

# Spark SQL, not just the DataFrame API, sees the exact same enforced schema --
# both are the same underlying Catalyst-optimized query, just two syntaxes.
transactions.createOrReplaceTempView("transactions")
high_value = spark.sql("""
    SELECT TransactionID, AccountID, Amount
    FROM transactions
    WHERE Amount > 10000 AND Currency = 'GBP'
""")
```

## Expected Output
Against a source file where `AccountID` contains the mixed numeric/alphanumeric values from the scenario, `mode="FAILFAST"` raises `org.apache.spark.SparkException: Malformed records are detected... Parse Mode: FAILFAST` immediately at read time, naming the offending value -- surfacing the exact source-data problem on the day it happened, instead of a silent zero-row join result discovered (or not discovered) downstream. Against a well-formed file, both the DataFrame chain and the equivalent `spark.sql(...)` query above produce identical results -- confirming the two APIs are genuinely interchangeable syntaxes over the same execution engine.

## Explanation
**`inferSchema=True` is a real, well-documented Spark feature, not a bug -- but it re-infers from a data sample on every run, which makes the inferred schema a moving target rather than a fixed contract.** The scenario's failure isn't that inference is wrong; it's that a schema silently *changing* between runs is far more dangerous in a production pipeline than a schema being wrong once and staying consistently wrong (which at least fails the same way every time and gets noticed).

**A zero-match join is one of the quietest failure modes in Spark specifically because it isn't an error.** `LongType(882130).equals(StringType("882130"))` is simply `false` under Spark's type semantics -- the join executes successfully, just against no matching rows on either side that share both a value and a type. Nothing in the pipeline raises an exception; the job reports success with an empty or drastically smaller-than-expected result, which is exactly the kind of failure that only gets caught by someone independently checking row counts, if anyone does.

**Explicit schemas plus a `FAILFAST`/quarantine mode turn a silent contract violation into a loud one, at the earliest possible point.** This is the same principle DE01-T01's typed Python and DE01-T04's REST API validation both apply -- fail at the boundary where bad data enters the system, not several transformations later where the failure has become disconnected from its actual cause.

**The DataFrame API and Spark SQL are not two different systems -- they compile to the identical Catalyst-optimized query plan.** `transactions.filter(...).select(...)` and the equivalent `SELECT ... WHERE ...` produce the same physical plan and the same performance; the choice between them is a readability preference for a given transformation, not a performance trade-off. This directly builds on DE01-T02's SQL-tuning lesson: the same sargability and predicate-pushdown reasoning that applies to a SQL Server query applies to a Spark SQL query's WHERE clause, because Catalyst applies analogous optimizations (predicate pushdown to the file format, in this case).

## Job-Readiness Note
Schema-contract discipline here is the Spark-scale application of DE01-T01's typed-Python and DE01-T04's ingestion-validation principles -- the underlying discipline transfers, the mechanism (an explicit StructType, not a Python dataclass) is what's new.
