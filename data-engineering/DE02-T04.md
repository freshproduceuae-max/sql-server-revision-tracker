## Live Scenario
A transaction-enrichment job joins 800 million transaction rows against a 40,000-row branch-reference table (branch name, region, opening hours) to attach branch details to every transaction. The join runs, but takes 25 minutes -- roughly the same time as joining two genuinely large tables would take, even though one side of this join is tiny. A colleague suggests the join strategy Spark chose is the problem, not the join logic itself.

## The Question
> Explain the two main join strategies Spark can choose (broadcast hash join and sort-merge join), why Spark chose sort-merge for this join even though one side is small, and how to force the correct strategy.

## Solution Code
```python
from pyspark.sql import functions as F

# Spark's Catalyst optimizer chooses a join strategy based on the estimated
# size of each side -- but that estimate comes from table/file METADATA
# (e.g. Parquet footer statistics), which can be missing or stale if the
# branch-reference table was loaded via a path Spark can't size-estimate
# cheaply (a wide CSV, a JDBC source, a table with no ANALYZE TABLE stats).
# Result: Spark falls back to sort-merge (its default, safe-for-any-size
# strategy) even though the branch table is genuinely tiny.

branches = spark.read.csv("s3://bank-data/branches.csv", header=True, inferSchema=True)
transactions = spark.read.parquet("s3://bank-data/transactions/")

# SLOW (if Spark's size estimate for `branches` is wrong or missing): a
# SORT-MERGE JOIN shuffles BOTH sides across the network and sorts them --
# real, unavoidable work even though one side has only 40,000 rows.
# enriched_slow = transactions.join(branches, on="BranchID", how="left")

# FAST: explicitly force a BROADCAST HASH JOIN -- the entire small table is
# sent ("broadcast") to every executor's memory once; each executor then
# joins its local partition of the large table against that in-memory copy
# with NO shuffle of the 800-million-row side at all. This is exactly what
# Spark's default autoBroadcastJoinThreshold (10 MiB) is meant to trigger
# automatically -- the hint below removes the dependency on Spark's size
# estimate being correct.
enriched = transactions.join(F.broadcast(branches), on="BranchID", how="left")

# Confirm which strategy actually ran -- never assume the hint took effect,
# read the physical plan. A correct broadcast join's plan shows
# "BroadcastHashJoin" and a "BroadcastExchange" node, not "SortMergeJoin".
enriched.explain(mode="formatted")
```

## Expected Output
Without the hint, `enriched.explain()` on the scenario's slow run shows `SortMergeJoin` with a full `Exchange` (shuffle) on both the transactions and branches sides. With `F.broadcast(branches)`, the plan shows `BroadcastHashJoin` with a single `BroadcastExchange` on the branches side only -- the 800-million-row transactions side is read and joined locally per-partition with no shuffle at all, and the job's runtime drops from ~25 minutes to a small fraction of that, dominated now by simply reading the 800 million rows once rather than reading-plus-shuffling them.

## Explanation
**A broadcast hash join and a sort-merge join solve the same join correctness problem with fundamentally different cost profiles, and the choice matters enormously at scale.** Sort-merge join shuffles and sorts *both* sides of the join on the join key -- correct for any size combination, including two genuinely huge tables, but it pays a real network/disk cost proportional to the total data moved on both sides. Broadcast hash join sends one full copy of the *smaller* side to every executor once, then joins locally with zero shuffle of the larger side -- dramatically cheaper, but only viable when the smaller side is small enough to fit comfortably in every executor's memory (Spark's default threshold for auto-selecting this strategy, `spark.sql.autoBroadcastJoinThreshold`, is 10 MiB).

**Why Spark chose sort-merge here despite the branch table's genuinely small row count is the actual diagnostic lesson, not just "broadcast is faster."** Spark's cost-based optimizer decides based on an *estimated size in bytes*, derived from table statistics -- not row count directly, and not always accurately available. A CSV read via `inferSchema=True` (as in this scenario) often has no reliable size statistics the way a Parquet file's footer metadata does, so Spark can't confidently know the branch table is small enough to broadcast safely, and defaults to the always-safe sort-merge strategy instead.

**Adaptive Query Execution changes this story at runtime, and connects directly to DE02-T01's execution-order lesson.** Because AQE re-optimizes at shuffle stage boundaries using *actual* runtime statistics (not just pre-execution estimates), a modern Spark version can sometimes detect after an initial exchange that one side turned out to be small and switch a sort-merge join to a broadcast join mid-query -- but this is not guaranteed for every plan shape, and explicitly hinting with `F.broadcast()` removes the dependency on that runtime detection working correctly for a specific, known-small reference table like this one.

**Always verify with `.explain()`, never assume a hint "worked" from the code alone** -- CLAUDE.md's own standing rule for this app ("a passing guard may have checked nothing") applies exactly here: a broadcast hint on a table that turns out to exceed Spark's broadcast size limit is silently ignored, falling back to sort-merge with no error and no obvious symptom except the join staying just as slow as before.

## Job-Readiness Note
Choosing and verifying join strategy is one of the highest-leverage Spark performance skills -- a single unnecessary sort-merge join against a genuinely small reference table is a very common, very fixable source of a job running far slower than its data volume alone would explain.
