## Live Scenario
A bank's compliance team is asked, during an audit, two specific questions about a `customer_risk_score` column that appears in a downstream fraud-analytics table: (1) which source systems and transformation steps did this column's data pass through to get here, and (2) who is currently allowed to query it, and why. The data platform team can answer neither question quickly -- the lineage is 'in people's heads and some old wiki pages,' and access is granted through a mix of ad-hoc S3 bucket policies and a spreadsheet nobody has updated in eight months. A new hire, having read about CDP's governance capabilities, assumes 'turning on SDX' is a single action that will retroactively answer both questions. The senior platform engineer corrects them: SDX is not a single feature to turn on, and lineage tracking specifically has to be wired into the pipeline's transformations to produce anything to query.

## The Question
> Explain what Apache Atlas and Apache Ranger each actually do within CDP's SDX layer -- as two distinct components solving two distinct problems, not one governance feature -- and design what the pipeline needs to add so both audit questions become answerable going forward (not retroactively, since that requires lineage that was never captured).

## Solution Code
```python
from pyspark.sql import SparkSession
from pyspark.sql import functions as F

spark = SparkSession.builder \
    .appName("customer-risk-score-pipeline") \
    .config("spark.extraListeners", "com.hortonworks.spark.atlas.SparkAtlasEventTracker") \
    .config("spark.sql.queryExecutionListeners", "com.hortonworks.spark.atlas.SparkAtlasEventTracker") \
    .getOrCreate()
# Atlas's Spark hook (a Spark listener registered via spark.extraListeners
# / spark.sql.queryExecutionListeners) is what turns this job's actual
# transformations into lineage EDGES in Atlas's metadata graph -- lineage
# is not inferred after the fact from table names; it is captured at
# execution time from the real read/write/transform operations this job
# performs. The exact listener class and required Atlas application
# properties vary by CDP/Atlas version -- verify the current cluster's
# own Atlas integration documentation for the exact class name and
# config rather than assuming this one is current on every deployment.
# Without SOME such listener configured, running the job produces no
# lineage record at all, regardless of whether SDX/Atlas exists on the
# cluster -- this is the concrete answer to "lineage has to be wired in,"
# not a passive platform capability.

source_transactions = spark.table("iceberg_catalog.banking.transactions")
source_credit_bureau = spark.table("iceberg_catalog.banking.credit_bureau_feed")

risk_score = (
    source_transactions.join(source_credit_bureau, "customer_id")
    .withColumn(
        "customer_risk_score",
        F.col("txn_velocity_30d") * 0.4 + F.col("bureau_score_normalized") * 0.6
    )
    .select("customer_id", "customer_risk_score")
)
risk_score.write.mode("overwrite").saveAsTable("iceberg_catalog.fraud_analytics.customer_risk_score")
# Because Atlas's Spark hook is attached to this SparkSession, THIS specific
# read-transactions + read-credit_bureau + compute + write-customer_risk_score
# sequence is what gets recorded as a lineage graph -- answering audit
# question (1) going forward, because the actual transformation, not a
# guess from table names, is what was captured.

# --- Answering audit question (2): access control, via Ranger, SEPARATELY ---
# Atlas recording lineage does not itself grant or restrict who can query
# the resulting table -- that is Apache Ranger's job, a distinct component
# solving a distinct problem (authorization policy enforcement), not a side
# effect of Atlas tracking where the data came from.

# Ranger policy (illustrative -- real policies are managed via Ranger's
# admin UI/REST API, not hand-written Spark code, but this shows the
# CONCEPT: a tag-based policy driven by an Atlas classification, so that
# adding a classification to a column is what drives access -- rather than
# a hand-maintained spreadsheet of who currently has access, which is
# exactly the stale-tracking problem the audit surfaced).
RANGER_TAG_POLICY_EXAMPLE = {
    "policyName": "PII-classified-columns-fraud-analyst-only",
    "resource": {"database": "fraud_analytics", "table": "customer_risk_score"},
    "atlas_tag": "PII",  # this column is TAGGED in Atlas as PII
    "allow": ["role:fraud_analyst", "role:compliance_auditor"],
    "deny_others": True,
}
# Tagging customer_risk_score as PII in Atlas is what makes this Ranger
# policy apply to it automatically -- if the column is later propagated
# into a new derived table, Atlas's lineage-aware tag propagation carries
# the PII classification forward, and Ranger's policy follows the tag,
# without a human having to remember to update an access list for every
# new table the data flows into.
```

## Explanation
**The new hire's "turn on SDX" framing collapsed two genuinely distinct components -- Atlas (lineage/metadata/classification) and Ranger (access-control policy enforcement) -- into one imagined feature, which is exactly the kind of guarantee-conflation the platform must not make: lineage tracking and access control solve different problems and neither one substitutes for the other.**

**What Apache Atlas actually does, and why it did not already have an answer for the lineage question:** Atlas is CDP's metadata and lineage-tracking component -- it records what data exists, how it is classified (tags like "PII"), and, critically, the actual lineage graph of which source tables and transformation jobs produced a given table's data. That lineage graph is built from real captured events, typically via hooks (like the Spark listener shown here) attached to the jobs that actually read and write the data -- it is not a retroactive inference the platform can derive after the fact from table names or documentation. This is precisely why "just turn on SDX" could not retroactively answer the audit's first question: if no prior job writing customer_risk_score had Atlas's Spark hook configured, no lineage was ever captured for it to query now, no matter how governance-capable the platform is in principle. This is also why the fix has to be forward-looking (instrument the pipeline going forward) rather than a magic retroactive query.

**What Apache Ranger actually does, and why it is a genuinely separate concern from Atlas:** Ranger is CDP's centralized authorization-policy engine -- it defines and enforces who can access what, evaluated at query time against defined policies. Critically, Ranger's policies can be driven by Atlas's classifications (a "tag-based policy"): tagging a column as PII in Atlas, and defining a Ranger policy keyed on that tag rather than the specific table name, means the access rule automatically follows the data if the same classified content is later propagated into a new derived table -- Atlas's lineage-aware tag propagation carries the classification forward, and Ranger's tag-based policy applies to wherever that classification now lives. This is architecturally why Atlas and Ranger are described as two components within SDX rather than one: Atlas answers "what is this data and where did it come from," Ranger answers "who is allowed to touch it" -- and a tag-based Ranger policy is one place where the two connect, but connecting them is a specific design choice (tagging plus a policy keyed to that tag), not something that happens automatically merely because both components exist on the same platform.

**Why the spreadsheet-and-ad-hoc-bucket-policy approach was the real root cause of the audit's second failure:** without Ranger as the actual enforcement point, "who currently has access" has no single, authoritative, currently-correct source of truth -- a spreadsheet drifts out of date the moment access changes happen anywhere except through updating that spreadsheet, which is exactly what an 8-month-stale document demonstrates happened. Moving enforcement to Ranger, with policy driven by Atlas tags rather than a hand-maintained list, is what makes "who has access and why" a live, queryable fact rather than a document someone has to remember to keep current.

**The general principle this generalizes to:** CDP's governance capability is not a single switch -- it is Atlas (lineage and classification, captured from real pipeline execution) and Ranger (policy enforcement, ideally driven by those classifications) as two distinct mechanisms that jointly answer two distinct kinds of audit question, neither of which retroactively covers data or access decisions made before the mechanism was actually wired into the relevant pipelines and policies.
