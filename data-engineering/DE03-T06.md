## Live Scenario
After building working, one-off pipelines for the ledger, card-authorization, and FX-rate sources from T01, the platform team is asked to onboard 15 more source systems over the next two quarters -- each with its own schema, its own batch-or-streaming pattern, its own target table, and its own SCD/append/replace write semantics. The team's first instinct is to copy the FX-rate batch job's Python file, rename it, and hand-edit the source path, schema, and table name for each new source -- after four sources, this has produced four near-duplicate scripts that already disagree subtly on how they handle a missing source file (two log and skip, one raises, one silently writes an empty DataFrame), making the team realize hand-copying does not scale to 15 more sources without both duplicated effort and inconsistent failure behavior across sources.

## The Question
> Design a metadata-driven ingestion framework -- one codebase, driven by a per-source configuration -- that can onboard a new source by adding a config entry rather than writing new pipeline code, and explain what must stay uniform across all sources for this to actually reduce inconsistency rather than just relocate it into config.

## Solution Code
```python
from pyspark.sql import SparkSession
from pyspark.sql import functions as F
from dataclasses import dataclass
from typing import Optional
import json

spark = SparkSession.builder.appName("metadata-driven-ingestion").getOrCreate()

@dataclass
class SourceConfig:
    source_id: str
    ingestion_pattern: str        # "batch" | "scheduled_batch" | "streaming"  (per T01's decision framework)
    source_path: str
    source_format: str            # "csv" | "parquet" | "json" | "kafka"
    target_table: str
    write_mode: str               # "append_merge" | "replace_partition" | "scd2_merge"  (per T02/T04)
    natural_key: list             # columns identifying a unique source record
    partition_col: str
    on_missing_source: str        # "fail" | "skip_and_alert"  -- explicit per source, not implicit per script

# The 15 onboarding sources live as DATA, not code -- this is the entire
# point: onboarding source #16 next quarter means adding one entry here,
# not writing and testing a new Python script.
SOURCE_REGISTRY = [
    SourceConfig("ledger_nightly", "batch", "s3://bank-data/ledger/", "csv",
                 "lakehouse.raw.ledger", "replace_partition",
                 ["ledger_entry_id"], "extract_date", "fail"),
    SourceConfig("fx_rates", "scheduled_batch", "https://fx-provider.example.com/rates", "json",
                 "lakehouse.raw.fx_rates", "replace_partition",
                 ["currency_pair"], "fetch_date", "skip_and_alert"),
    SourceConfig("card_authorizations", "streaming", "card-authorizations", "kafka",
                 "lakehouse.raw.card_authorizations", "append_merge",
                 ["card_id", "ts"], "event_date", "fail"),
    # ... 15 more sources added here as data, not as new .py files, once
    # onboarded -- each new source is one dataclass instance, reviewed the
    # way a config change is reviewed, not a new pipeline PR each time.
]

def run_ingestion(spark: SparkSession, cfg: SourceConfig, run_date: str):
    """One function, driven entirely by cfg -- this IS the framework: the
    logic path a source takes depends only on its config values, never on
    a source-specific branch of hand-written code. run_date is the one
    per-run value every source needs (T01's scheduled_batch sources use it
    as their fetch/extract date; batch sources use it as their partition
    predicate), passed in rather than hardcoded so the same function is
    correct whether it runs for today or is backfilled for an earlier date."""
    # cfg.ingestion_pattern selects HOW the source is read, per T01's
    # decision framework -- "streaming" sources need readStream, not
    # read; treating every source as a one-shot batch read (as an earlier
    # draft of this framework did) silently breaks any source registered
    # as streaming, exactly the kind of drift a shared framework exists to
    # prevent.
    if cfg.ingestion_pattern == "streaming":
        if cfg.source_format != "kafka":
            raise ValueError(f"{cfg.source_id}: streaming pattern requires a kafka source, got {cfg.source_format}")
        stream_df = (
            spark.readStream.format("kafka")
            .option("kafka.bootstrap.servers", "broker1:9092,broker2:9092")
            .option("subscribe", cfg.source_path)
            .load()
        )
        # Streaming sources write continuously via their own query, keyed
        # by natural_key through the same append_merge MERGE logic below --
        # applied per micro-batch via foreachBatch rather than once per run.
        def _write_batch(batch_df, _batch_id):
            _merge_write(spark, batch_df, cfg)
        return (
            stream_df.writeStream
            .foreachBatch(_write_batch)
            .option("checkpointLocation", f"s3://lakehouse/checkpoints/{cfg.source_id}/")
            .trigger(processingTime="5 seconds")
            .start()
        )

    # batch / scheduled_batch: a one-shot read for this run_date.
    try:
        if cfg.source_format == "csv":
            df = spark.read.option("header", True).csv(cfg.source_path)
        elif cfg.source_format == "parquet":
            df = spark.read.parquet(cfg.source_path)
        elif cfg.source_format == "json":
            df = spark.read.json(cfg.source_path)
        else:
            raise ValueError(f"Unsupported format for {cfg.source_id}: {cfg.source_format}")
    except Exception as e:
        # UNIFORM missing/failed-read handling, driven by cfg.on_missing_source
        # -- this is exactly the inconsistency (log-and-skip vs. raise vs.
        # silently-empty) that hand-copied scripts had already drifted on
        # after only four sources.
        if cfg.on_missing_source == "skip_and_alert":
            print(f"ALERT: source {cfg.source_id} unavailable this run: {e}")
            return
        raise RuntimeError(f"Source {cfg.source_id} failed and on_missing_source=fail") from e

    df = df.withColumn(cfg.partition_col, F.lit(run_date))

    # Write path selected by cfg.write_mode, using the SAME idempotent
    # patterns from T02/T04 for every source -- not a per-source reinvention.
    if cfg.write_mode == "replace_partition":
        (df.write.format("iceberg").mode("overwrite")
           # run_date, not a hardcoded current_date() -- the same function
           # must be correct for a scheduled today-run AND a manual backfill
           # of an earlier date; a hardcoded current_date() would silently
           # overwrite TODAY's partition even when backfilling yesterday's.
           .option("replaceWhere", f"{cfg.partition_col} = '{run_date}'")
           .save(cfg.target_table))
    elif cfg.write_mode == "append_merge":
        _merge_write(spark, df, cfg)
    elif cfg.write_mode == "scd2_merge":
        raise NotImplementedError("SCD2 merge path follows T04's bucketed-MERGE pattern per source")

def _merge_write(spark: SparkSession, df, cfg: SourceConfig):
    """Shared MERGE logic for both one-shot append_merge batches and
    streaming foreachBatch micro-batches -- one implementation, used by
    both call sites above, so a fix or a rule change here applies to every
    source using this write_mode regardless of how it is triggered."""
    df.createOrReplaceTempView("src")
    key_match = " AND ".join(f"t.{k} = s.{k}" for k in cfg.natural_key)
    spark.sql(f"""
        MERGE INTO {cfg.target_table} t USING src s
        ON {key_match}
        WHEN MATCHED THEN UPDATE SET *
        WHEN NOT MATCHED THEN INSERT *
    """)

RUN_DATE = "2026-08-20"  # supplied by the orchestrator per run; a manual
                          # backfill passes an earlier date to the same function.
for cfg in SOURCE_REGISTRY:
    run_ingestion(spark, cfg, RUN_DATE)
```

## Expected Output
Before (4 hand-copied scripts): 4 different failure behaviors for a
  missing source file (log-skip / log-skip / raise / silent-empty-write),
  discovered only by reading each script individually.

After (1 framework, 3+ config entries): on_missing_source is an explicit,
  reviewed field in every source's config -- "fail" or "skip_and_alert" --
  chosen deliberately per source rather than accidentally varying by
  whichever engineer copied the script last.

Onboarding source #16: add one SourceConfig entry (~10 lines of config),
  not a new .py file -- the ingestion logic path, write semantics, and
  error handling are already implemented once, in run_ingestion().

## Explanation
**The core design idea is moving what varies between sources (path, format, target table, write semantics, failure policy) into declarative configuration, while what should NOT vary between sources (how a given write mode is actually executed, how a missing source is actually handled once the policy is chosen) stays in one shared code path.** This is the fix for the specific failure the scenario describes: the four hand-copied scripts had already drifted on missing-source handling not because anyone decided sources should be handled inconsistently, but because copy-paste-and-edit has no mechanism to keep behavior in sync across copies as each one gets small, well-intentioned edits over time.

**Why this is a real reduction in inconsistency, not just a relocation of it into config:** the risk with "metadata-driven" as a phrase is that a team can build a framework so generic that any behavior can be expressed in config, which just moves the same inconsistency risk from Python files into config files -- four config entries could still specify four different missing-source behaviors just as easily as four scripts could. The discipline that actually prevents this is: **config fields must be a closed, reviewed set of choices** (here, `on_missing_source` is one of exactly two named policies, not a free-text field), and **the code path each choice maps to must be implemented once and shared** (`run_ingestion`'s `if cfg.on_missing_source == "skip_and_alert"`/`raise` branch is the only place that logic exists, for every source). A new source's config has to pick from real, understood options -- it cannot invent a fifth undocumented failure behavior the way copy-paste drift silently did.

**What stays uniform across every source, and why each is load-bearing:**
- **The write-mode implementations** (replace_partition via T02's `replaceWhere`, append_merge via T02's MERGE pattern) are each implemented exactly once. A source picks which pattern fits its data (per T01/T02's reasoning), but does not get to reimplement how that pattern executes -- this is what stops "16 sources" from becoming "16 subtly different MERGE statements."
- **The ingestion-pattern classification** (batch / scheduled_batch / streaming) is recorded per source using the same decision criteria T01 established (does the source emit events or expose a snapshot; how often does it actually change; what latency does the consumer need) -- config makes that decision an explicit, reviewable field instead of an implicit choice buried in which script template someone started from.
- **Schema-evolution handling** (not shown in this excerpt, but the natural next config field once T03's rename/addition distinction is applied per source) would need the same treatment: a source's config should declare which schema changes it can auto-apply versus which must halt for review, using T03's Avro-alias/Iceberg-ID-based compatibility rules uniformly, not per-source judgment calls re-derived from scratch each time.

**The limit of this pattern, honestly stated:** a metadata-driven framework only reduces inconsistency for the dimensions it has actually parameterized. A source with a genuinely novel requirement the config schema has no field for (say, a source needing a bespoke deduplication rule beyond a natural key) either needs the config schema extended (in a reviewed, shared way) or a real, separate pipeline -- forcing every future novel requirement into an ill-fitting existing config field just reintroduces inconsistency in a new place, so the framework's config schema itself has to be maintained deliberately as new source types are onboarded, not treated as a one-time design.
