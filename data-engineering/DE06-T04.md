# DE06-T04 — Production Engineering: Orchestration, CI/CD, Containers, ML Data, Operations | Kubernetes for Data Platforms

## ID
DE06-T04

## Chapter
6 — Production Engineering: Orchestration, CI/CD, Containers, ML Data, Operations

## Live Scenario
A platform engineer, having just containerized the fraud-scoring Spark job (Docker image built, pushed, scanned, non-root, secrets externalized), announces the job is 'ready for Kubernetes' and submits it via a bare kubectl run command pointing at the image, expecting Spark's driver/executor model to somehow 'just work' the way it did on YARN. It fails immediately -- there is no Spark driver, no executor pods, nothing resembling a Spark application at all, just one container that starts, tries to run spark-submit inside itself with no cluster to submit to, and exits.

## The Question
> Explain what Docker packaging, Kubernetes scheduling, and Spark's own driver/executor execution model each actually provide -- as three separate, necessary layers -- and design the correct way to run this job on Kubernetes, distinguishing what changes from the YARN model this bank's other Chapter 4 clusters use and what does not.

## Solution Code
```yaml
# ===== Layer 1: Docker -- PACKAGING, not execution or scheduling =====
# The image built in T03 packages the Spark job's code and its pinned
# dependencies into a runnable filesystem + entrypoint. Docker's job ends
# there -- it has no concept of "cluster," "driver," "executor," or
# "where should this run relative to other workloads." A bare
# 'kubectl run' pointing at this image starts exactly one container
# running exactly one process -- it does not know this image is meant to
# become a Spark APPLICATION with a driver and multiple executors,
# because that concept does not exist at the Docker-image layer at all.

# ===== Layer 2: Kubernetes -- SCHEDULING pods onto nodes, not Spark
# execution semantics =====
# Kubernetes' job is deciding which node a pod runs on, restarting failed
# pods per a declared policy, and managing pod lifecycle -- it has no
# built-in understanding of "this pod is a Spark driver and needs to
# create N more pods as executors and coordinate with them." That
# coordination is Spark's own job, layer 3 below -- Kubernetes provides
# the pod-scheduling substrate Spark's own cluster manager mode USES, it
# does not replace Spark's execution model.

# ===== Layer 3: Spark's own driver/executor model -- unchanged in
# CONCEPT from YARN, different in MECHANISM =====
# Spark-on-Kubernetes uses Kubernetes as Spark's cluster manager (the
# same role YARN's ResourceManager plays in Chapter 4's clusters) --
# the driver/executor relationship, the DAG scheduling, the shuffle
# behavior are Spark concepts that do not change. What changes is HOW the
# driver requests and manages its executors: instead of YARN allocating
# containers, the Spark driver itself creates executor PODS directly via
# the Kubernetes API.

# The CORRECT way to submit this job -- spark-submit, not a bare
# 'kubectl run', with Kubernetes specified as the cluster manager:
# spark-submit \
#   --master k8s://https://<k8s-api-server>:6443 \
#   --deploy-mode cluster \
#   --name fraud-scoring \
#   --conf spark.kubernetes.container.image=fraud-etl:pinned-sha \
#   --conf spark.kubernetes.namespace=data-engineering \
#   --conf spark.executor.instances=8 \
#   --conf spark.kubernetes.driver.pod.name=fraud-scoring-driver \
#   --conf spark.kubernetes.executor.deleteOnTermination=true \
#   local:///app/fraud_scoring_job.py
# This is spark-submit -- the SAME command family used against YARN in
# Chapter 4, just with --master pointed at the Kubernetes API server
# instead of yarn. Spark itself creates a driver pod, which then creates
# executor pods via the Kubernetes API and coordinates with them exactly
# as it would coordinate with YARN-allocated containers -- the DAG
# scheduling, task distribution, and shuffle mechanics are unchanged.

# --- A distinct, K8s-specific control T03 did not cover: SERVICE IDENTITY
# for pod-to-cloud-resource authentication ---
apiVersion: v1
kind: ServiceAccount
metadata:
  name: fraud-scoring-spark-sa
  namespace: data-engineering
---
# Bound to a cloud IAM role (illustrative) so executor pods can
# authenticate to S3/object storage WITHOUT a baked-in credential --
# this is a DIFFERENT control from T03's secrets-externalization fix:
# T03 solved "don't bake a static secret into the image"; this solves
# "how does a pod prove ITS identity to external cloud resources,"
# typically via a workload-identity mechanism binding the Kubernetes
# ServiceAccount to a cloud IAM role, distinct from any application-level
# secret at all.
```

## Expected Output
Bare 'kubectl run' against the fraud-scoring image: fails immediately --
  Docker packaged the code, but nothing told Kubernetes this pod needed
  to become a Spark driver creating executor pods; nothing told Spark
  what cluster manager to coordinate through. One container starts, has
  no cluster to submit to, exits.

spark-submit --master k8s://... --deploy-mode cluster: Spark creates a
  driver pod, the driver pod creates 8 executor pods via the Kubernetes
  API, task scheduling and shuffle behavior proceed exactly as they would
  under YARN -- because Spark's own execution model did not change,
  only the mechanism by which the driver obtains its executors did.

What is genuinely new relative to Chapter 4's YARN clusters: pod-level
  resource requests/limits (Kubernetes' own isolation granularity,
  distinct from YARN's queue-based capacity model covered in Chapter 4),
  and workload identity via a Kubernetes ServiceAccount bound to a cloud
  IAM role for pod-to-cloud-resource authentication -- a control T03's
  Docker-level secrets-externalization fix does not itself provide.

## Explanation
**The platform engineer's mistake was assuming that having correctly finished layer 1 (a well-built Docker image) meant layers 2 and 3 (Kubernetes scheduling, and Spark's own cluster-manager coordination) would happen automatically -- when in fact each of these three layers does a genuinely different job, and none of them substitutes for either of the other two.**

**What Docker actually provides, and why it stops there:** Docker packaging answers "what code and dependencies are inside this container, and what happens when it starts" -- it has no concept of a multi-process, coordinated application spanning several containers with defined roles (a driver coordinating multiple executors). A kubectl run pointing at a correctly-built Spark image starts exactly one container running whatever its entrypoint says -- if that entrypoint tries to run spark-submit with no --master pointing at an actual cluster manager, it has nothing to submit to and fails exactly as the scenario describes, regardless of how well T03's packaging concerns were addressed.

**What Kubernetes actually provides, and why it is not itself a Spark execution model:** Kubernetes schedules pods onto nodes, restarts failed pods per policy, and manages pod lifecycle and networking -- this is genuinely useful infrastructure, but Kubernetes itself has no built-in notion of "this pod is a Spark driver that needs to create N more pods as executors and coordinate distributed task execution with them." That coordination logic lives entirely in Spark's own code, which is why Spark has to be explicitly told to use Kubernetes as its CLUSTER MANAGER (via --master k8s://...) -- Kubernetes provides the scheduling substrate; Spark's own driver process is what actually calls the Kubernetes API to create executor pods and then talks to those executors directly to distribute tasks and shuffle data, exactly the same conceptual relationship YARN's ResourceManager and Spark's YARN-mode executors have in this bank's Chapter 4 clusters.

**Why the driver/executor model, the DAG scheduling, and shuffle mechanics genuinely do NOT change between YARN and Kubernetes as cluster managers:** this is the concrete reassurance to give a team moving Spark jobs from YARN (Chapter 4) to Kubernetes -- the actual Spark execution semantics this bank already understands (lazy evaluation, transformations vs. actions, partitioning, shuffle behavior, AQE) are entirely cluster-manager-agnostic; they are Spark's own concepts, unaffected by whether the driver obtained its executors from YARN's ResourceManager or from the Kubernetes API. What changes is purely the MECHANISM of executor acquisition and pod lifecycle -- spark-submit's --master value and a handful of spark.kubernetes.* configuration options, not a different Spark programming model.

**Why service identity is a genuinely new, fifth control beyond T03's four, not a restatement of the secrets-externalization fix:** T03 established "do not bake a static credential into the image" as its own distinct control. Kubernetes workloads add a different question entirely: how does a running pod prove its own identity to external cloud resources (object storage, a managed database) without EITHER a baked-in secret OR a runtime-injected static credential that itself needs rotating and protecting? Binding a Kubernetes ServiceAccount to a cloud IAM role (a workload-identity mechanism) answers this by letting the cloud platform itself vouch for the pod's identity based on its ServiceAccount, rather than any credential value at all -- a genuinely distinct mechanism from T03's "inject the secret at runtime instead of baking it in," solving a problem T03's fix does not address (T03's fix still requires SOME secret to exist and be distributed to the runtime; service identity can eliminate the need for that secret to exist as a distributable value in the first place).

**The general principle this generalizes to, and the correction to "ready for Kubernetes" as a phrase:** "containerized" (Docker), "schedulable" (Kubernetes), and "able to execute as a distributed Spark application" (Spark's own cluster-manager integration) are three separate readiness properties, each satisfied by a different mechanism -- a job can be perfectly containerized and still fail immediately on Kubernetes if Spark itself is never told to treat Kubernetes as its cluster manager and coordinate driver/executor pods through it, exactly as this scenario demonstrates.

## Job-Readiness Note
This lesson's driver/executor-model-unchanged-across-cluster-managers claim is deliberately qualified ("as of the CDP/Spark versions this bank runs") because Spark-on-Kubernetes tooling has moved quickly -- newer official Spark Kubernetes Operators and batch schedulers exist and may change some of the manual spark-submit flags shown here; a learner applying this lesson to a real cluster should verify current behavior against that cluster's actual Spark and Kubernetes versions rather than assuming this example's exact flags are current on every deployment.
