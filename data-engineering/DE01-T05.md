## Live Scenario
Two engineers on a transaction-banking data team both edit the same nightly-reconciliation pipeline script directly on a shared server, taking turns and communicating changes over chat. Last week, one engineer's fix to a currency-rounding bug was silently overwritten when the other engineer pasted in an older version of the file to make an unrelated change -- the rounding bug shipped to production again, and nobody could say for certain when or how it came back.

## The Question
> Design a branching and pull-request workflow for a small data engineering team's pipeline code that would have caught the overwritten fix before it reached production, and explain specifically which part of the workflow catches it.

## Solution Code
```text
Proposed workflow for the reconciliation pipeline repo:

1. No direct commits to the default branch. Every change -- a bug fix, a
   new source integration, a refactor -- happens on its own feature branch,
   named for what it does: `fix/currency-rounding`, `feat/fx-rate-ingestion`.

2. A pull request is required to merge into the default branch. The PR
   diff is the single source of truth for "what changed" -- reviewable
   line-by-line, unlike a pasted file overwriting another file on a shared
   server with no record of what was lost.

3. At least one other engineer reviews the diff before merge. This is the
   step that directly catches the scenario's failure: a reviewer looking
   at the actual diff for the second engineer's "unrelated change" PR
   would see the currency-rounding fix disappearing from the file, which
   is a visible, reviewable line in a diff -- not an invisible loss inside
   a full-file paste.

4. The default branch is protected: it cannot be force-pushed to, and a
   PR cannot merge until required checks pass (see CI note below). This
   is what actually enforces steps 2-3 rather than leaving them as a
   convention someone can skip under time pressure.

5. Commit messages state what changed and why, not just what: "fix:
   round FX amounts to 2dp before summing (was truncating, not rounding,
   causing a systematic 0.3% understatement)" is diagnosable six months
   later; "fix bug" is not.

What this workflow adds beyond version control alone: a required-approval
gate specifically prevents the class of failure in the scenario, because
the fix's removal becomes a visible, reviewable diff line instead of a
silent side effect of a full-file overwrite.
```

## Expected Output
Applying this workflow retroactively to the scenario: the second engineer's "unrelated change" PR diff would show `-round(amount, 4)` (the buggy old truncation-adjacent line) replacing `+round(amount, 2)` (the fix) as an explicit, highlighted removal -- exactly the kind of change a reviewer is looking for, and something no reviewer could reasonably miss in a standard code review, unlike a silent overwrite with no diff to review at all.

## Explanation
**The core mechanism that fixes the scenario is the *diff*, not version control in the abstract.** Git alone (without required PRs and reviews) would still let someone push a full-file overwrite directly to the default branch with no review -- the same failure could still happen. It's specifically the combination of "changes must go through a reviewable diff" plus "a human must approve that diff" that catches a regression like this.

**Branch protection is what makes the process actually enforced, not just recommended.** A team that *intends* to always use PRs but has no protection on the default branch will eventually skip it under a deadline -- exactly the pressure that caused the original direct-server-editing habit in the scenario.

**"CI-aware" in this lesson's title matters even without full CI/CD implementation yet** (that's Chapter 6's scope): a PR-required workflow is what CI/CD *hooks into* later — automated tests, linting, and build checks all run as required status checks on the PR, gating the merge the same way human review does. Establishing the branch/PR discipline now is what makes adding automated checks later a small addition, not a process overhaul.

## Job-Readiness Note
