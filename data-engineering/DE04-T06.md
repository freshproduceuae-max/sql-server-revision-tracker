## Live Scenario
A bank's card-authorization event pipeline publishes every swipe to a Kafka topic with 12 partitions, keyed by `card_id`, consumed by a fraud-scoring Spark Structured Streaming job running with a consumer group of 4 instances for parallelism. During a Black Friday-style volume spike, the platform team notices something specific: 3 of the 4 consumer instances are running near-idle while the 4th is falling further and further behind, its consumer lag climbing into the millions of events, even though the topic overall has plenty of partitions and the consumer group has capacity. A separate concern surfaces the same week: a different team wants to replay the last 24 hours of card-authorization events into a newly-deployed version of the fraud model for backtesting, without disrupting the live fraud-scoring consumer group at all.

## The Question
> Diagnose why keying by `card_id` produced this specific lopsided-consumer-lag pattern rather than an even spread across the 4 consumer instances, and explain the Kafka mechanism (not a vague 'add more partitions') that lets the replay team read the last 24 hours without touching the live consumer group's state at all.

## Solution Code
```python
from kafka import KafkaConsumer, TopicPartition
from kafka.admin import KafkaAdminClient

# --- Diagnosing the lopsided consumer lag ---
# Kafka guarantees ORDERING per partition, not per topic -- and a topic's
# partition assignment for a keyed message is a deterministic function of
# the key (by default, a hash of the key modulo partition count). Every
# event for the SAME card_id always lands on the SAME partition, which is
# what preserves per-card event ordering -- but it also means partition
# load is only as balanced as the KEY distribution actually is, not
# guaranteed even just because there are 12 partitions and 4 consumers.

admin = KafkaAdminClient(bootstrap_servers="broker1:9092,broker2:9092")
consumer = KafkaConsumer(bootstrap_servers="broker1:9092,broker2:9092",
                          group_id="fraud-scoring-group")

partitions = [TopicPartition("card-authorizations", p) for p in range(12)]
consumer.assign(partitions)
end_offsets = consumer.end_offsets(partitions)
committed = {p: consumer.committed(p) for p in partitions}
for p in partitions:
    lag = end_offsets[p] - (committed[p] or 0)
    print(f"partition {p.partition}: lag={lag}")
# If this shows lag concentrated on a small number of partitions (not
# spread evenly across all 12), the root cause is almost certainly key
# skew: a small number of high-volume card_ids (e.g. a small set of
# corporate/high-frequency merchant-facing cards during a Black-Friday-
# style spike) hashing onto the same one or two partitions, and those
# specific partitions' assigned consumer instance falling behind while
# the other partitions -- and the consumer instances handling them --
# stay comfortably caught up. Adding partitions alone would not fix this:
# the same skewed keys would still hash onto a proportionally smaller
# but still-skewed subset of a larger partition count, unless the
# partitioning key itself changes.

# A real fix needs to address the SKEW, not just the partition count --
# e.g. a composite key (card_id + a time-bucket salt) for very
# high-volume cards specifically, while preserving per-card ordering
# within each time bucket, which is enough for fraud-scoring's actual
# ordering requirement (recent-window pattern detection, not
# all-time-ever ordering per card).

# --- The replay-without-disrupting-the-live-consumer-group requirement ---
# Kafka retains events in a topic for its configured retention period
# (independent of whether any consumer group has read them), and
# consumer OFFSETS are tracked per consumer GROUP -- this is the
# mechanism that makes replay-without-disruption possible: a second,
# independent consumer group reading the same topic has its own,
# completely separate offset tracking from the live fraud-scoring group's.
replay_consumer = KafkaConsumer(
    bootstrap_servers="broker1:9092,broker2:9092",
    group_id="fraud-backtest-replay-group",   # a DIFFERENT consumer group
    auto_offset_reset="earliest",
)
replay_partitions = [TopicPartition("card-authorizations", p) for p in range(12)]
replay_consumer.assign(replay_partitions)

import time
target_ts = int((time.time() - 24 * 3600) * 1000)  # 24 hours ago, in ms
offsets_for_times = replay_consumer.offsets_for_times(
    {p: target_ts for p in replay_partitions}
)
for p, offset_and_ts in offsets_for_times.items():
    if offset_and_ts is not None:
        replay_consumer.seek(p, offset_and_ts.offset)
# The replay group now reads from 24 hours ago, at its own pace, against
# its own offsets -- the live fraud-scoring group's partition assignment,
# committed offsets, and processing rate are completely untouched by
# this, because Kafka tracks progress per (topic, partition, consumer
# GROUP), not once per topic globally.
```

## Explanation
**Both halves of this scenario turn on the same underlying Kafka mechanism -- partition assignment and offset tracking are both scoped more narrowly than "the topic," and understanding exactly what they're scoped to (the partition, and the consumer group, respectively) is what explains both the skew problem and the replay solution.**

**Why keying by card_id produced lopsided lag rather than an even 4-way split:** Kafka's ordering guarantee is per-partition, not per-topic -- to preserve the order of events for a given key (here, all of one card's authorization events, which fraud-scoring genuinely needs in order to detect patterns like rapid repeated swipes), every event with the same key must be routed to the same partition, deterministically, typically via a hash of the key modulo the partition count. This is a real, necessary property for the fraud-scoring use case, not an implementation detail that could simply be turned off -- but it has a direct consequence: partition load balance is only as good as the actual distribution of key values feeding it. If a small number of card_ids generate a disproportionate share of events during a volume spike (a plausible real pattern -- certain corporate or merchant-facing cards see much higher authorization frequency than typical retail cards, and a Black-Friday-style spike would concentrate exactly this kind of activity), those specific card_ids' events all land on the same one or two partitions regardless of how many total partitions or consumer instances exist. The consumer instance assigned to that specific partition falls behind while the other three, whose assigned partitions never saw the same concentration, stay comfortably caught up -- which is exactly the lopsided pattern observed, and precisely why "add more partitions" would not fix it: a larger partition count changes the modulus in the hash, but the same skewed keys still concentrate onto whichever subset of the larger partition count they now hash to, unless the actual partitioning key changes to something with less skew (e.g. a composite key that distributes high-volume cards' events across multiple partitions using a bounded time-bucket salt, while still preserving the ordering fraud-scoring actually needs within each bucket).

**Why the replay team can read the last 24 hours without touching the live consumer group at all:** Kafka's two independent scoping mechanisms are what make this possible. First, a topic retains its events for its configured retention period regardless of whether any particular consumer group has read them yet -- reading is non-destructive, so the live fraud-scoring group consuming the topic does not remove or consume the data away from any other reader. Second, and more directly relevant here, consumer *offsets* -- the bookkeeping of "how far has this reader gotten" -- are tracked per (topic, partition, consumer **group**), not once globally per topic. A second consumer group, with its own group id, has entirely separate offset state from the live group's; seeking that second group's offsets back to a timestamp 24 hours in the past (via offsets_for_times, which maps a timestamp to the earliest offset at or after it) only affects that new group's own bookkeeping. The live fraud-scoring group's committed offsets, partition assignment, and processing rate are untouched, because nothing about the replay group's operations writes to or reads from the live group's own tracked state.

**The general principle both halves illustrate:** Kafka's core guarantees (ordering, offset tracking) are deliberately scoped narrower than "the topic as a whole" -- ordering is per-partition, offsets are per-group-per-partition -- and treating either as if it applied topic-wide (assuming "12 partitions means load spreads evenly" or worrying "another reader might disrupt the live consumers") is the specific misunderstanding this lesson's two problems are each built to correct.
