## Live Scenario
The Data Validation lab already taught you how to *write* correct SQL to catch bad data -- NULL checks, duplicate detection, referential integrity, the full G01-G19 toolkit. A data engineer needs one more skill on top of that: knowing when a technically-correct query is going to be too slow to run in production, and why. A daily batch job that reconciles 40 million transaction-banking rows against a lookup table has started missing its SLA window, and the query itself has no obvious bug -- it returns the right answer, just too slowly.

## The Question
> Given a correct but slow query joining a 40-million-row transaction table against a small lookup table, diagnose why an index isn't being used and rewrite the query so the execution plan changes from a table scan to an index seek -- without changing what the query returns.

## Solution Code
```sql
-- SLOW: a function wrapped around the indexed column defeats the index.
-- SQL Server cannot seek an index on TransactionDate when the predicate is
-- YEAR(TransactionDate) = 2026 -- it must evaluate YEAR() for every row
-- first, which forces a full scan regardless of any index that exists.
SELECT t.TransactionID, t.Amount, l.CategoryName
FROM Transactions t
JOIN CategoryLookup l ON t.CategoryCode = l.CategoryCode
WHERE YEAR(t.TransactionDate) = 2026;

-- FAST: rewrite the predicate as a sargable range on the raw column, so
-- the optimizer can seek the index instead of scanning every row to
-- compute YEAR() before it can even evaluate the WHERE clause.
SELECT t.TransactionID, t.Amount, l.CategoryName
FROM Transactions t
JOIN CategoryLookup l ON t.CategoryCode = l.CategoryCode
WHERE t.TransactionDate >= '2026-01-01'
  AND t.TransactionDate <  '2027-01-01';

-- Confirm the plan actually changed, don't just assume the rewrite worked --
-- SET STATISTICS IO ON reports logical reads per table, which is the
-- concrete, checkable evidence a table scan became a seek.
SET STATISTICS IO ON;
SELECT t.TransactionID, t.Amount, l.CategoryName
FROM Transactions t
JOIN CategoryLookup l ON t.CategoryCode = l.CategoryCode
WHERE t.TransactionDate >= '2026-01-01'
  AND t.TransactionDate <  '2027-01-01';
```

## Expected Output
Before the rewrite, `SET STATISTICS IO` reports `Table 'Transactions'. Scan count 1, logical reads 612000` (a full scan of every page in the table). After the rewrite, against an index on `TransactionDate`, it reports `Table 'Transactions'. Scan count 1, logical reads 8400` -- roughly a 70x reduction in logical reads for the identical result set, because the engine can now seek directly to the 2026 rows instead of evaluating `YEAR()` against all 40 million.

## Explanation
**This lesson deliberately does not re-teach what a NULL check or a duplicate-detection query is -- Data Validation G01-G19 already covers that in depth.** What it adds is query-plan awareness: the difference between a query that is *correct* (returns the right rows) and one that is *sargable* (can actually use an index to find them). A data engineer writes the same kind of validation and transformation SQL as Data Validation already teaches, but now has to make it perform at production data volumes.

**"Sargable" (Search ARGument ABLE) means the predicate can be evaluated using an index seek.** Wrapping the indexed column in a function -- `YEAR(col)`, `LEFT(col, 4)`, `ISNULL(col, x)` -- forces the engine to compute that function for every single row before it can check the condition, which defeats the index entirely and falls back to a full scan.

**`SET STATISTICS IO ON` is the evidence, not the assumption.** A query "looking" faster or a developer's intuition that a rewrite should help is not proof; logical reads before and after is a concrete, comparable number. This is the same discipline this app's own CLAUDE.md insists on for any performance claim: verify, don't assert.

**This exact pattern recurs at Spark scale in Chapter 2** (predicate pushdown, partition pruning) -- the underlying principle, "help the engine avoid reading data it doesn't need," is the same one, just with a different execution engine underneath it.
