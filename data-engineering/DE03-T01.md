## Live Scenario
A transaction-banking platform ingests data from three source systems into the lakehouse: (1) a core banking ledger that exports a full nightly extract, (2) a card-authorization service that emits an event per swipe with sub-second latency requirements for fraud scoring, and (3) a third-party FX rate provider that publishes a rate table update every few minutes with no event stream at all, only a REST endpoint. A newly hired engineer proposes building one generic Structured Streaming job that polls all three sources every 10 seconds, reasoning that "streaming everywhere is simpler than maintaining two ingestion patterns." On review, this creates three problems: the nightly ledger extract is 40GB and re-reading it every 10 seconds wastes cluster capacity for no benefit (the data does not change intra-day), the FX endpoint returns HTTP 429 (rate limited) after the third rapid poll, and the fraud-scoring path's true requirement -- sub-second latency -- is not actually improved by using Structured Streaming over the FX/ledger sources, only over the card events.

## The Question
> For each of the three sources, decide whether batch or streaming ingestion fits, and explain the cost of applying the wrong pattern to each -- not just which pattern is 'better' in the abstract.

## Solution Code
```python
from pyspark.sql import SparkSession
from pyspark.sql import functions as F

spark = SparkSession.builder.appName("ingestion-pattern-selection").getOrCreate()

# --- Source 1: core banking ledger -- full nightly extract, no intra-day change ---
# BATCH is correct here. The data has a natural batch cadence (once nightly);
# a scheduled job, not a continuously polling stream, matches that cadence.
ledger = (
    spark.read
    .option("header", True)
    .csv("s3://bank-data/ledger/extract_date=2026-08-20/")
)
ledger.write.mode("overwrite").partitionBy("extract_date").parquet(
    "s3://lakehouse/raw/ledger/"
)

# --- Source 2: card-authorization events -- sub-second latency requirement ---
# STREAMING is correct here. Structured Streaming's micro-batch engine
# (or Continuous Processing mode, for the sources that support it) is what
# actually meets a sub-second, per-event latency requirement; a nightly or
# even 10-second poll cannot.
card_events = (
    spark.readStream
    .format("kafka")
    .option("kafka.bootstrap.servers", "broker1:9092,broker2:9092")
    .option("subscribe", "card-authorizations")
    .load()
)
parsed = card_events.select(
    F.from_json(F.col("value").cast("string"), "card_id STRING, amount DOUBLE, merchant STRING, ts TIMESTAMP").alias("data")
).select("data.*")

query = (
    parsed.writeStream
    .format("parquet")
    .option("path", "s3://lakehouse/raw/card_authorizations/")
    .option("checkpointLocation", "s3://lakehouse/checkpoints/card_authorizations/")
    .trigger(processingTime="5 seconds")
    .start()
)

# --- Source 3: FX rate provider -- REST endpoint, updates every few minutes, no event stream ---
# NEITHER "always batch" nor "always streaming" fits blindly. There is no event
# stream to subscribe to, so Structured Streaming's readStream sources do not
# apply directly -- but polling every 10 seconds (as the rejected proposal did)
# hits the provider's rate limit for no benefit, since rates only change every
# few minutes. The right pattern is a SCHEDULED micro-batch (e.g. a job run
# every 5 minutes, matched to the provider's actual update cadence), which is
# architecturally "batch" even though it runs frequently.
def fetch_fx_rates_batch(spark):
    import requests
    resp = requests.get("https://fx-provider.example.com/rates", timeout=10)
    resp.raise_for_status()
    rates_df = spark.createDataFrame(resp.json()["rates"])
    rates_df.write.mode("overwrite").parquet("s3://lakehouse/raw/fx_rates/")
# Scheduled externally (e.g. every 5 minutes via an orchestrator), not polled
# in a tight streaming loop -- this respects the provider's real cadence and
# avoids the 429s the naive "stream everything" design hit.
```

## Explanation
**The mistake in the rejected design was treating "streaming" as a technology choice made once for the whole platform, rather than a per-source decision driven by two questions: how often does the data actually change, and what latency does the downstream consumer genuinely require?**

**Batch fits the ledger** because a nightly extract has a natural once-a-day cadence baked into the source system itself -- no ingestion pattern on the consuming side can make data "fresher" than the producer's own update frequency. Streaming against a source that only changes once a day just re-reads the same bytes repeatedly, at a real infrastructure cost (cluster time, S3 GET requests) with no correctness or freshness benefit.

**Streaming fits card authorizations** because the requirement -- sub-second fraud-scoring latency -- is real and cannot be met any other way. This is the one source in the scenario where Structured Streaming's continuous or short-trigger micro-batch processing is solving an actual problem, not adding complexity for its own sake.

**The FX provider is the case that breaks the false batch-vs-streaming binary.** It has no event stream to subscribe to (no Kafka topic, no webhook), so Structured Streaming's `readStream` sources do not apply structurally -- but that does not make aggressive polling correct either. The 10-second poll interval in the rejected design was chosen without reference to how often the source actually changes (every few minutes) or what it can tolerate (the 429 after three rapid polls). The fix is a scheduled batch job at a cadence matched to the source's real update frequency -- architecturally still "batch," even though it runs frequently, because it is triggered on a schedule rather than reacting to a continuous event stream.

**The general rule for choosing an ingestion pattern:** ask (1) does the source emit discrete events or expose a queryable snapshot, (2) how often does the underlying data actually change, and (3) what latency does the specific downstream consumer require -- then match the pattern to the answer for that source, not to a platform-wide preference. Applying streaming where batch fits wastes capacity and can violate a provider's rate limits; applying batch where streaming is required silently fails to meet a real latency SLA.
