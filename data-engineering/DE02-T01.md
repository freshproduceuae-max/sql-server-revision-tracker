## Live Scenario
A data engineer new to Spark writes a transaction-cleansing script that chains ten `.filter()` and `.withColumn()` calls on a 200-million-row transaction DataFrame, then adds a `print("cleaning step complete")` after the chain, expecting it to print once the cleaning has actually run. In testing against a small sample, the print statement appears instantly, before any visible cluster activity -- and the engineer concludes, wrongly, that the transformations must be running near-instantly on the full dataset too. In production against the real 200-million-row table, the job then appears to hang for several minutes at the point where the DataFrame is finally written out, with no warning beforehand.

## The Question
> Explain why the print statement appeared instantly regardless of data size, why the real work becomes visible only at the write, and what this means for where a data engineer should actually look when diagnosing which step in a chain is slow.

## Solution Code
```python
from pyspark.sql import SparkSession
from pyspark.sql import functions as F

spark = SparkSession.builder.appName("transaction-cleansing").getOrCreate()

transactions = spark.read.parquet("s3://bank-data/transactions/")

# Every line below is a TRANSFORMATION -- it builds a logical plan (a DAG of
# operations) but does not read a single row or touch the cluster. This is
# why the scenario's print statement returns instantly: nothing has run yet,
# regardless of whether the source table has 10 rows or 200 million.
cleaned = (
    transactions
    .filter(F.col("amount").isNotNull())
    .filter(F.col("currency").isin("GBP", "USD", "EUR"))
    .withColumn("amount_gbp", F.when(F.col("currency") == "GBP", F.col("amount"))
                               .otherwise(F.col("amount") * F.col("fx_rate")))
    .withColumn("is_high_value", F.col("amount_gbp") > 10000)
)

print("cleaning step complete")  # prints instantly -- only the PLAN was built

# .count() is an ACTION -- this is the line that actually triggers execution.
# Spark now optimizes the full chain (via Catalyst) and executes it as one
# job, reading and processing every row for the first time.
row_count = cleaned.count()
print(f"rows after cleaning: {row_count}")

# Inspect the logical AND physical plan Spark actually built, to see exactly
# what will run when an action finally triggers it -- the direct answer to
# "where do I look to diagnose a slow step":
cleaned.explain(mode="formatted")
```

## Expected Output
`cleaned = (...)` and the `print("cleaning step complete")` line both return in milliseconds regardless of table size -- no cluster work has happened yet. `cleaned.count()` is where execution actually starts, and its duration scales with the real data volume (seconds on a sample, minutes on 200 million rows). `cleaned.explain(mode="formatted")` prints the physical plan showing all four transformations (two filters, two withColumn projections) fused into a single stage -- proving Spark did not run each `.filter()`/`.withColumn()` as a separate pass over the data, but planned them together and will execute them as one.

## Explanation
**Lazy evaluation is the single most important mental model shift moving from single-machine Python/SQL to Spark.** A pandas `.filter()` or a SQL Server `UPDATE` executes immediately, row by row or set by set, as the statement runs. A Spark **transformation** (`.filter()`, `.select()`, `.withColumn()`, `.join()`, `.groupBy()`) does not touch data at all -- it only adds a node to a logical plan. Only an **action** (`.count()`, `.collect()`, `.write()`, `.show()`) triggers Spark to optimize that whole accumulated plan (via the Catalyst optimizer) and actually execute it across the cluster.

**This directly explains the scenario's production surprise.** The engineer's mental model was "each line does work as it runs" -- so the instant `print()` seemed to confirm the cleaning had finished cheaply. In reality, all ten transformations were still just an unexecuted plan; the write step at the end was the first action, so it was the first point where all the accumulated work -- reading 200 million rows and applying every transformation -- actually happened at once. The job wasn't "hanging at the write" so much as "finally doing all the work the whole chain had deferred."

**Diagnosing a slow step means reading the physical plan, not timing individual transformation lines.** Because transformations don't execute individually, putting a timer around each `.filter()` call measures almost nothing (each returns instantly) and tells you nothing about which part of the plan is actually expensive. `.explain(mode="formatted")` (or the Spark UI's SQL tab once a job has run) shows the real physical plan -- which stages exist, which operations got fused together, and where a shuffle boundary (a genuinely expensive operation, covered in DE02-T03) sits.

**The driver/executor split is the other half of this architecture.** The `SparkSession` and the code building the logical plan run on the **driver** -- a single JVM process, not distributed. Once an action triggers execution, the driver's optimized plan is broken into tasks distributed across **executors** (JVM processes on cluster worker nodes), which do the actual parallel reading, transforming and writing of data partitions. A `.collect()` action pulls all resulting data back to the driver -- calling it on a 200-million-row DataFrame, rather than `.count()` or `.write()`, is a separate, common way this same architecture surprises a new Spark engineer by exhausting the driver's memory.
