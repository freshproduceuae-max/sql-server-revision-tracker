## Live Scenario
A data platform team is proud of their CI/CD pipeline for the fraud-detection Spark job: every merge to main triggers unit tests, a container build, and an automated deploy to production within eight minutes. A engineering lead reports to a stakeholder that 'the fraud-detection pipeline is production-ready -- we have full CI/CD.' Two weeks later, a deploy that passed every CI/CD check (unit tests green, build succeeded, deploy completed without error) ships a subtly wrong join condition that silently drops 8% of transactions from the fraud-scoring input -- the deploy succeeded perfectly, and the data has been wrong for eleven days before anyone notices.

## The Question
> Explain specifically what the CI/CD pipeline's passing checks did and did not verify, and why 'CI/CD is green' is not the same claim as 'the pipeline produces correct data' or 'this pipeline is production-ready' -- then design what would need to be added to this CI/CD pipeline to have a chance of catching this specific class of defect before it reached production.

## Solution Code
```yaml
# --- What this team's existing CI/CD pipeline actually verified ---
# unit_tests: PASS   -- tests exercised individual functions/transformations
#                        in isolation, likely with small, hand-crafted
#                        sample data -- these tests can pass perfectly
#                        while a JOIN CONDITION between two real tables is
#                        subtly wrong, because the sample data used in the
#                        unit test may not have exercised the specific
#                        join-key mismatch that drops 8% of real production
#                        transactions.
# container_build: PASS -- confirms the code compiles/packages into a
#                        working container image -- says NOTHING about
#                        whether the logic inside that container produces
#                        correct output against real data.
# deploy: PASS          -- confirms the new container was successfully
#                        rolled out to the production environment and is
#                        running -- says NOTHING about whether what it is
#                        now doing to production data is correct.
#
# NONE of these three checks -- individually or together -- verify data
# CORRECTNESS against real production-shaped data. This is the specific,
# concrete gap: "CI/CD is green" means "the code we intended to ship,
# shipped, without crashing" -- it is a claim about DEPLOYMENT MECHANICS,
# not a claim about DATA CORRECTNESS, and conflating the two is exactly
# what let a silently-wrong join reach production for eleven days.

# --- What needs to be ADDED to have a chance of catching this specific
# class of defect -- a data-level validation stage, not more unit tests ---
name: fraud-detection-pipeline-ci-cd
on: [push]
jobs:
  unit_tests:
    steps:
      - run: pytest tests/unit/

  # NEW: a data-contract / row-count / referential-integrity check against
  # a REALISTIC staging dataset (not hand-crafted unit-test fixtures) --
  # this is what could have caught an 8% silent row-drop, because it
  # measures the ACTUAL OUTPUT ROW COUNT against an expected range, not
  # just whether individual functions behave correctly on small samples.
  data_contract_validation:
    needs: unit_tests
    steps:
      - name: Run pipeline against staging with real-shaped data
        run: spark-submit staging_validation_job.py --date 2026-08-10
      - name: Verify output row count against expected range
        run: |
          python verify_row_count.py \
            --table staging.fraud_scoring_input \
            --expected-min-pct 98 \
            --expected-max-pct 102 \
            --baseline-source staging.transactions_raw
          # This check FAILS the pipeline if fraud_scoring_input's row
          # count is outside 98-102% of transactions_raw's row count for
          # the same date -- an 8% silent drop (92% of expected) would
          # have failed this gate, BEFORE deploy, rather than surfacing
          # eleven days later in production.

  container_build:
    needs: data_contract_validation  # only build/deploy AFTER data
                                       # validation passes, not in parallel
    steps:
      - run: docker build -t fraud-detection:${{ github.sha }} .

  deploy_to_production:
    needs: container_build
    steps:
      - run: kubectl apply -f k8s/fraud-detection-deployment.yaml
      - name: Post-deploy smoke check -- row count in PRODUCTION, not just staging
        run: |
          python verify_row_count.py \
            --table prod.fraud_scoring_input \
            --expected-min-pct 98 --expected-max-pct 102 \
            --baseline-source prod.transactions_raw
          # A staging-only check is not sufficient by itself -- production
          # data volume, skew and edge cases can differ from staging's.
          # This is a genuinely separate, second check, not a duplicate.
```

## Expected Output
Before (unit tests + build + deploy only): the wrong join condition
  passed all three checks -- unit tests never exercised the specific
  join-key mismatch, build succeeded because the code compiles fine, and
  deploy succeeded because the container ran without crashing. The 8%
  silent data drop was invisible to every existing gate.

After (data-contract row-count validation added, gating build/deploy):
  the same faulty join, run against a realistic staging dataset, produces
  fraud_scoring_input at ~92% of transactions_raw's row count -- outside
  the declared 98-102% expected range -- FAILING the pipeline before
  container_build or deploy_to_production ever run, and again as a
  post-deploy production smoke check as a second, independent catch.

## Explanation
**The engineering lead's "full CI/CD" claim and the stakeholder's implicit takeaway ("production-ready") both collapsed two genuinely different properties into one -- whether the deployment MECHANISM works (code compiles, ships, runs without crashing) and whether the DATA the pipeline produces is actually correct -- and this team's CI/CD pipeline, as built, only ever verified the first one.**

**Why each of the three original checks verified deployment mechanics, not data correctness, specifically:** unit tests verify that individual functions behave as expected against the specific inputs the test author thought to construct -- they are only as good as the test author's imagination about what could go wrong, and a subtly wrong join condition between two real production tables is exactly the kind of defect that a hand-crafted small sample often fails to exercise, because the sample was built to test the function's intended behavior, not to reproduce a real-world join-key mismatch. A container build succeeding verifies the code compiles and packages correctly -- it has no access to real data at all, and cannot verify anything about output correctness by construction. A deploy succeeding verifies the new container started running in production without an infrastructure-level failure (crash, missing dependency, resource exhaustion) -- it verifies the process is alive, not that what the process is now doing to production data is right. Stacking all three together produces "the code we intended to ship, shipped, and is running" -- a real and useful claim, but not the claim "this pipeline now produces correct data," which is a distinct property none of the three checks were designed to verify.

**Why this specific defect (an 8% silent row drop from a subtly wrong join) is exactly the failure mode this gap allows through:** a wrong join condition does not crash anything -- Spark executes the join, returns fewer rows than it should, and the job completes successfully with a plausible-looking, non-empty, non-error result. Every one of the three original CI/CD checks is satisfied by exactly this outcome: the code compiled, built, deployed, and ran without an exception. Nothing in that chain was ever positioned to notice that the actual row count silently dropped by 8% relative to the correct join's expected output -- which is precisely why it took eleven days and presumably a downstream symptom (a fraud-detection metric or reconciliation discrepancy) to surface at all.

**Why the fix is a data-level validation stage, not more or better unit tests:** unit tests operate on small, deliberately constructed inputs and can never be exhaustive against every real-world data shape a production join might encounter -- a data-contract check that runs the actual pipeline logic against a realistic staging dataset and measures the ACTUAL output row count (or other measurable data-shape properties) against an expected range is a fundamentally different kind of check: it does not ask "does this function behave as I expect on this sample," it asks "did this run, against real-shaped data, produce output consistent with what correct behavior should look like." An 8% drop against a declared 98-102% expected range is exactly the kind of measurable signal that would have failed this gate before the container was ever built or deployed -- catching the defect at the point in the pipeline (staging validation) specifically designed to catch data-shape regressions, rather than relying on unit tests never designed to catch this class of defect at all.

**The general principle this generalizes to, and the specific correction to the "CI/CD means production-ready" framing:** CI/CD, as commonly implemented (unit tests, build, deploy), is a genuine and valuable set of checks for deployment mechanics -- it answers "did the intended code ship successfully" -- but it is a category error to treat that as equivalent to "the pipeline produces correct data" or "this pipeline is production-ready" without an explicit, separate data-correctness validation stage measuring real output against real expectations. A CI/CD pipeline can be entirely green, every single time, while silently shipping wrong data indefinitely, because deployment success and data correctness are two different claims that happen to often be conflated under one reassuring "CI/CD passed" status.
