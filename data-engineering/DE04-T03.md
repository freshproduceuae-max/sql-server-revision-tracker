# DE04-T03 — Hadoop Ecosystem and Cloudera Data Platform | YARN and Cluster Resource Management

## ID
DE04-T03

## Chapter
4 — Hadoop Ecosystem and Cloudera Data Platform

## Live Scenario
A shared CDP cluster runs three tenants: a nightly Spark ETL pipeline (large, bursty, tolerant of queueing), an always-on Spark Structured Streaming fraud-detection job (needs guaranteed, continuous resources, cannot tolerate being starved), and an ad-hoc data-science team running exploratory notebooks (unpredictable, low-priority, should never block the other two). All three currently submit to YARN's `default` queue with no further configuration. During a month-end batch spike, the fraud-detection streaming job is repeatedly starved of executors for several minutes at a time -- exactly the workload that was supposed to be guaranteed continuous resources -- while data-science notebook jobs continue running unaffected in the background.

## The Question
> Diagnose why submitting all three tenants to one undifferentiated queue caused the guaranteed-resource workload to be the one that got starved, and redesign the YARN capacity scheduler configuration so each tenant's actual resource requirement (guaranteed continuous, bursty-tolerant, low-priority-preemptible) is what YARN actually enforces.

## Solution Code
```xml
<!-- capacity-scheduler.xml -- BEFORE: everything in one undifferentiated
     queue means YARN has no basis to distinguish "this job must never be
     starved" from "this job can wait." Within a single queue, YARN's
     scheduler allocates by submission order and configured per-queue
     policy, not by any notion of one specific application's business
     criticality -- so a burst of ETL applications can legitimately consume
     available containers before the streaming job's executors can be
     replaced or scaled, because nothing in the configuration told YARN
     the streaming job's resources were not to be touched. -->
<property>
  <name>yarn.scheduler.capacity.root.queues</name>
  <value>default</value>
</property>
<property>
  <name>yarn.scheduler.capacity.root.default.capacity</name>
  <value>100</value>
</property>

<!-- ===== AFTER: three queues, each matched to its tenant's real requirement ===== -->
<property>
  <name>yarn.scheduler.capacity.root.queues</name>
  <value>fraud_streaming,nightly_etl,data_science</value>
</property>

<!-- fraud_streaming: guaranteed capacity, minimal preemption risk --
     capacity + maximum-capacity pinned equal so it can never be squeezed
     below what it needs even under cluster-wide contention. -->
<property>
  <name>yarn.scheduler.capacity.root.fraud_streaming.capacity</name>
  <value>30</value>
</property>
<property>
  <name>yarn.scheduler.capacity.root.fraud_streaming.maximum-capacity</name>
  <value>30</value>
</property>
<!-- default-application-priority (NOT a bare "priority" property, which
     is not a real leaf-queue setting) sets the priority newly submitted
     applications in this queue get by default when they don't specify
     their own -- this affects ordering among applications already
     admitted to the queue, it is not what enforces the guaranteed
     capacity floor above. The floor is enforced by capacity ==
     maximum-capacity plus preemption, not by this property. -->
<property>
  <name>yarn.scheduler.capacity.root.fraud_streaming.default-application-priority</name>
  <value>10</value>
</property>

<!-- nightly_etl: a real guaranteed floor, but allowed to BURST above it
     into idle cluster capacity when other queues aren't using their share
     -- this is what "bursty-tolerant" means in capacity-scheduler terms:
     a generous maximum-capacity, but a modest guaranteed capacity so it
     cannot itself starve the other two queues when it bursts. -->
<property>
  <name>yarn.scheduler.capacity.root.nightly_etl.capacity</name>
  <value>50</value>
</property>
<property>
  <name>yarn.scheduler.capacity.root.nightly_etl.maximum-capacity</name>
  <value>80</value>
</property>

<!-- data_science: a small guaranteed floor, explicitly marked preemptible
     so YARN can reclaim its containers first when fraud_streaming or
     nightly_etl need capacity they are entitled to and are not getting. -->
<property>
  <name>yarn.scheduler.capacity.root.data_science.capacity</name>
  <value>20</value>
</property>
<property>
  <name>yarn.scheduler.capacity.root.data_science.maximum-capacity</name>
  <value>40</value>
</property>
<property>
  <name>yarn.scheduler.capacity.root.data_science.disable_preemption</name>
  <value>false</value>
</property>

<!-- Cluster-wide preemption must be ON for the above per-queue intent to
     actually be enforced -- without it, a queue below its guaranteed
     capacity has no mechanism to reclaim containers already granted to
     another queue, and the "guarantee" is only a target, not an
     enforced floor. -->
<property>
  <name>yarn.resourcemanager.scheduler.monitor.enable</name>
  <value>true</value>
</property>
```

## Expected Output
Before (one 'default' queue, no ACLs/preemption distinctions):
  Month-end ETL burst starves fraud_streaming's executors for several
  minutes at a time -- YARN has no configured basis to treat that job's
  resources as protected.

After (three capacity-scheduler queues + preemption enabled):
  fraud_streaming: guaranteed 30% capacity, capacity == maximum-capacity,
    so it can never be squeezed below its floor even during the ETL burst.
  nightly_etl: guaranteed 50%, can burst to 80% of cluster capacity when
    the other queues are idle -- but never at fraud_streaming's expense.
  data_science: guaranteed 20%, explicitly preemptible -- its containers
    are the first reclaimed if fraud_streaming or nightly_etl are below
    their guaranteed share and need capacity back.

## Explanation
**The root cause was not "the cluster is too small" or "the fraud job needs more resources" -- it was that a single undifferentiated queue gives YARN no configuration-level information about which tenant's resource needs are actually non-negotiable, so YARN had nothing to enforce beyond first-come-first-served scheduling within that one queue.**

**Why one shared queue produced exactly this failure mode:** YARN's capacity scheduler allocates resources at the granularity of queues, using each queue's configured capacity and maximum-capacity to decide how contention is resolved. With all three tenants submitting to the single "default" queue, YARN has no per-tenant signal at all -- from its point of view, a burst of ETL applications and the fraud-detection streaming job's executor requests are indistinguishable competing demands on the same undifferentiated pool. During the month-end ETL burst, YARN simply granted containers to whichever applications requested them within that one queue's available capacity, with no configured basis to protect the streaming job's resources specifically -- which is exactly why the "supposedly guaranteed" workload was the one that got starved, while the genuinely low-priority data-science notebooks were unaffected (they were never competing hard for capacity in the first place, so the lack of differentiation happened not to hurt them this time).

**Why separate queues fix this, mechanically:** creating three queues with distinct capacity and maximum-capacity values gives YARN an actual configuration to enforce rather than relying on submission-order luck. Setting the fraud_streaming queue's capacity and maximum-capacity to the same value (30/30) is what makes its guarantee a hard floor rather than a soft target -- the queue can never be allocated less than its capacity when it has pending demand, and it is also capped there, which prevents it from ever needing to compete unpredictably for more. The nightly_etl queue's wider gap between capacity (50) and maximum-capacity (80) is what "bursty-tolerant" concretely means in capacity-scheduler terms: it can absorb a burst by using idle capacity beyond its guaranteed share, but only capacity the other queues are not currently using.

**Why preemption has to be explicitly enabled for any of this to matter under real contention:** capacity and maximum-capacity values are enforced going forward for new container requests, but if a queue is already below its guaranteed capacity because another queue's containers are occupying that capacity, YARN needs the scheduler's preemption monitor (yarn.resourcemanager.scheduler.monitor.enable) actively running to reclaim those containers back -- without it, a queue's "guarantee" is really only a target the scheduler tries to honor for new allocations, not an enforced floor it will actively restore once violated. This is precisely the mechanism that lets the data_science queue's containers be reclaimed first when fraud_streaming needs its guaranteed share back and is not getting it.

**The general resource-isolation principle this generalizes to:** shared-cluster resource contention needs to be modeled explicitly, per tenant, as a queue configuration with a real floor (capacity), a real ceiling (maximum-capacity), and an explicit preemption policy -- "everyone shares one pool and it works itself out" is not a resource-isolation strategy, it is the absence of one, and the specific tenant that suffers when contention actually happens is whichever one's requirement was never encoded into the scheduler's configuration in the first place.
