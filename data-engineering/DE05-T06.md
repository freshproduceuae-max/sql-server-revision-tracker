## Live Scenario
A platform team is asked to 'optimize' the bank's daily fraud-scoring Spark job to reduce cloud cost. The engineer assigned the task doubles the cluster's executor count, reasoning that 'more resources means faster, and faster means cheaper.' The job does finish 20% faster -- but the monthly cloud bill for this job rises by 60%, because the doubled executor count runs for most of that (shorter) duration at low utilization: the job's actual bottleneck was never insufficient compute, it was an unnecessarily large shuffle caused by a join with no partition pruning, and a full table scan where a predicate could have eliminated 90% of the source data before it was ever read.

## The Question
> Using measurable evidence (not the vague claim 'it's optimized now'), diagnose the job's real cost driver and design the actual fix -- explaining specifically why adding executors was the wrong lever for a bottleneck that was never about available compute.

## Solution Code
```python
from pyspark.sql import SparkSession
from pyspark.sql import functions as F

spark = SparkSession.builder.appName("fraud-scoring-cost-optimization").getOrCreate()

# --- Measuring the ACTUAL bottleneck, not assuming it's compute ---
# Before touching executor count, the Spark UI's SQL tab and the job's
# physical plan are the measurable evidence for where cost/time is
# actually going -- "add more executors" without this evidence is a guess,
# not a diagnosis.

transactions = spark.table("iceberg_catalog.banking.transactions")
customer_dim = spark.table("iceberg_catalog.banking.customer_dim")

# BEFORE: a full scan of customer_dim (40M rows) joined against a full
# scan of transactions for the WHOLE table, then filtered to today AFTER
# the join and shuffle have already happened.
before_plan = (
    transactions.join(customer_dim, "customer_id")
    .filter(F.col("transaction_date") == F.current_date())
)
before_plan.explain(mode="formatted")
# The physical plan shows a full scan of transactions (no partition
# pruning applied, because the filter runs AFTER the join in this query's
# logical shape) -- this is measurable, checkable evidence: the plan
# itself shows Spark reading and shuffling far more data than the
# 'transaction_date == today' predicate would actually require, IF that
# predicate were applied at scan time instead of after the join.

# AFTER: apply the date predicate BEFORE the join, on a table partitioned
# by transaction_date -- this is PREDICATE PUSHDOWN taking effect: Spark's
# Catalyst optimizer (and, for Iceberg tables, Iceberg's own partition
# pruning) can now eliminate ~90% of transactions' data at SCAN time,
# before any shuffle or join work happens on it at all.
todays_transactions = transactions.filter(F.col("transaction_date") == F.current_date())
after_plan = todays_transactions.join(customer_dim, "customer_id")
after_plan.explain(mode="formatted")
# The physical plan for this version shows a PartitionFilters entry
# reflecting the date predicate applied at the scan node itself -- this is
# the measurable difference: fewer files/partitions read, not a claim of
# "it's optimized," but a specific, checkable line in the plan.

# --- Measuring the shuffle-size reduction, not just asserting it ---
spark.conf.set("spark.sql.adaptive.enabled", "true")  # AQE, default-enabled
                                                        # since Spark 3.2,
                                                        # confirmed here
                                                        # explicitly rather
                                                        # than assumed
after_plan.write.mode("overwrite").parquet("s3://scratch/fraud-scoring-test/")
# Compare Spark UI's SQL tab "shuffle write" metric for this query against
# the BEFORE version's shuffle write metric -- this measured byte count,
# not a subjective "feels faster," is the actual evidence the fix worked.

# --- Why "add executors" was the wrong lever, made concrete ---
# Executors add PARALLEL COMPUTE CAPACITY -- more executors help when a
# job is bottlenecked on not having enough parallel workers for the WORK
# THE JOB ACTUALLY NEEDS TO DO. Here, the job was doing far MORE work than
# it needed to (reading 100% of transactions and shuffling the full join
# result, when the date predicate could have eliminated 90% of the data
# before either happened) -- doubling executors makes that unnecessary
# work complete faster, but does not reduce the AMOUNT of unnecessary
# work, which is what was actually driving both the runtime and the cost.
# Fixing the predicate-pushdown gap reduces the actual data volume
# processed; doubling executors just processes the same excess volume
# with double the paid-for compute.
```

## Expected Output
BEFORE (doubled executors, no predicate pushdown fix):
  Runtime: 20% faster than the original single-executor-count baseline.
  Monthly cost: +60% -- more executors running for most of a (shorter)
  duration at LOW utilization, because the job's actual data volume
  (a full scan + full shuffle) never shrank; it was just processed by
  more, mostly-idle-per-task compute.

AFTER (predicate pushdown fix, executor count reverted to baseline):
  Spark UI SQL tab, shuffle write: ~90% reduction in bytes shuffled
  (measured, not asserted) -- because the date filter now eliminates most
  of transactions' data at scan time via partition pruning, before the
  join's shuffle ever touches it.
  Physical plan: PartitionFilters entry present on the scan node (BEFORE
  version had none) -- direct, checkable evidence of predicate pushdown
  actually taking effect, not an inferred claim.
  Runtime: comparable to or better than the doubled-executor version.
  Monthly cost: back near the ORIGINAL baseline (single executor count),
  because the job is now processing ~10x less data, not paying for 2x
  the compute to process the same excess.

## Explanation
**The engineer's "more resources means faster, faster means cheaper" reasoning conflated two genuinely different levers -- adding compute capacity, and reducing the actual amount of data the job needs to process -- and the job's real bottleneck was the second one, which the first lever cannot fix.**

**Why doubling executors made runtime better but cost worse, and why that is not a contradiction:** executors are parallel compute capacity, paid for by the hour (or equivalent billing unit) regardless of how efficiently each one is used. Doubling executor count for a job whose actual data volume never shrank means twice as much paid compute processes the same excess amount of work -- the job finishes somewhat faster (more parallelism does help *somewhat*, which is why the 20% runtime improvement is real and not fake), but the cost math is dominated by "double the executors, running most of that shorter duration at low utilization," because the job was never short on parallel workers relative to the WORK IT ACTUALLY NEEDED TO DO -- it was doing more work than it needed to, full stop, and no amount of added parallelism changes the volume of that unnecessary work.

**Why the real bottleneck was predicate pushdown never happening, and what that means concretely:** the job's logical query applied the transaction_date == today filter *after* joining the full transactions table against customer_dim, rather than before. This ordering means Spark's optimizer has no predicate to push down to the scan itself -- it has no choice but to read and shuffle the ENTIRE transactions table (all historical dates, not just today's), then filter down to today's rows only after the expensive join and shuffle have already processed all of it. Restructuring the query so the date filter is applied to transactions before the join lets Spark's Catalyst optimizer (and, for a partitioned Iceberg table, Iceberg's own partition-pruning mechanism) eliminate roughly 90% of the source data AT SCAN TIME -- before any shuffle or join work touches it. This is measurable and checkable directly in the physical plan (a PartitionFilters entry appearing on the scan node, absent in the original plan) and in the Spark UI's SQL tab shuffle-write metric (a real, large reduction in bytes shuffled), not something to take on faith from a query rewrite alone.

**Why "it's optimized now" is not an acceptable claim on its own, and what replaces it here:** every improvement claimed in this lesson is backed by a specific, checkable number -- the physical plan's PartitionFilters entry, the Spark UI's measured shuffle-write byte count before and after, the actual monthly cost figure before and after. "Optimized" as a bare adjective asserts an outcome without evidence; the discipline this lesson is built around is that a cost or performance claim needs the measurement that would let someone else verify it independently, exactly the same way DV's data-quality checks and this chapter's own quarantine-threshold and SLA-monitoring lessons require measured evidence rather than a vague "it's fine now."

**The general principle for choosing between "add more compute" and "reduce the actual work":** more executors is the correct fix when a job is genuinely compute-bound -- adequate parallelism for the real, necessary data volume, but not enough workers to use it. When a job is instead doing more work than it needs to (an unpruned scan, an unnecessary full shuffle, a missing filter pushed to the wrong place in the query), adding compute capacity makes the unnecessary work complete faster without reducing its cost, because cost scales with (data volume processed) × (compute paid for), and adding executors only ever addresses the second factor -- diagnosing which factor is actually the bottleneck, from real plan and Spark UI evidence, is what has to happen before either lever is chosen.
