## Live Scenario
The bank's nightly settlement pipeline has an internal SLA: complete by 6:00 AM so the morning reconciliation team has current data. Twice in the past month, the pipeline finished at 6:40 AM and 7:15 AM respectively -- both times, nobody noticed until the reconciliation team asked why their dashboard looked stale, well after their workday had started. When the platform team investigates after the fact, Spark's own history server shows exactly which stage took unusually long each time, but that information only exists AFTER the fact, in a UI nobody was watching in real time. The team's current 'monitoring' is a single generic alert that fires only if the job's Spark process crashes outright -- both slow-but-completed runs never crashed, so the existing alert never fired for either incident.

## The Question
> Design what this pipeline actually needs to detect an SLA breach while it is happening (not discover it after the fact from history-server data), and explain why 'alert if the job crashes' is a fundamentally different -- and here, insufficient -- signal from 'alert if the job is going to miss its SLA.'

## Solution Code
```python
from pyspark.sql import SparkSession
import time

spark = SparkSession.builder.appName("nightly-settlement").getOrCreate()

SLA_DEADLINE_HOUR_UTC = 6  # 6:00 AM -- the actual, stated business SLA
PIPELINE_START_TIME = time.time()

def check_sla_risk(stage_name: str, elapsed_seconds: float, expected_seconds: float):
    """Called after each major stage completes -- compares REAL elapsed
    time against that stage's own historical baseline, not a single
    end-of-job check. This is the concrete difference from 'alert if the
    job crashes': a crash detector has nothing to say about a job that is
    still running, just running slowly -- it can only ever fire after the
    process has already died. An SLA-risk check evaluates progress WHILE
    the job is still healthy and running, which is exactly the two real
    incidents' actual failure mode (finished, just too late)."""
    overrun_ratio = elapsed_seconds / expected_seconds
    if overrun_ratio > 1.5:  # this stage alone is running 50%+ over its
                              # own historical baseline
        send_alert(
            severity="WARNING",
            message=(
                f"Stage '{stage_name}' took {elapsed_seconds:.0f}s, "
                f"{overrun_ratio:.1f}x its {expected_seconds:.0f}s baseline. "
                f"Projected completion may miss the 06:00 UTC SLA -- "
                f"on-call should check NOW, not after the job finishes."
            ),
        )
    # Separately, an explicit PROJECTED-COMPLETION check against the
    # actual deadline -- not just "this one stage is slow" but "given
    # current progress, will the WHOLE pipeline make the 06:00 deadline":
    remaining_stages_avg_seconds = 1800  # from historical baseline
    projected_finish = time.time() + remaining_stages_avg_seconds
    projected_finish_hour_utc = time.gmtime(projected_finish).tm_hour
    if projected_finish_hour_utc >= SLA_DEADLINE_HOUR_UTC:
        send_alert(
            severity="CRITICAL",
            message=(
                f"Projected pipeline completion is at or after "
                f"{SLA_DEADLINE_HOUR_UTC}:00 UTC -- SLA breach likely. "
                f"Reconciliation team should be warned NOW, before their "
                f"workday starts, not after they notice stale data."
            ),
        )

def send_alert(severity: str, message: str):
    # Routed to the on-call paging system, NOT a log line nobody is
    # watching -- the point of this lesson's fix is that the signal
    # reaches a human before the deadline passes, not that it merely
    # exists somewhere in a UI.
    print(f"[{severity}] {message}")  # illustrative -- real implementation
                                        # pages via the on-call tool

# --- Contrast: the existing 'alert if crash' logic, kept for what IT
# actually IS good at (detecting genuine process failure), but explicitly
# NOT relied on for SLA-breach detection -- these are two different
# signals for two different failure modes, not one alert covering both. ---
def job_crash_alert(exit_code: int):
    if exit_code != 0:
        send_alert(severity="CRITICAL", message=f"Pipeline process crashed, exit code {exit_code}.")
    # This alert correctly fires for an actual crash -- but BOTH real
    # incidents in the scenario had exit_code == 0 (the job finished,
    # just late), which is exactly why this alert alone was insufficient
    # and never fired for either one.
```

## Explanation
**The existing monitoring's blind spot was not a bug in the crash-detection alert -- that alert works exactly as designed, for the specific condition it was built to detect. The actual gap was that "did the process crash" and "will this job miss its SLA" are two fundamentally different signals, and the pipeline had monitoring for only the first one while its two real incidents were both instances of the second.**

**Why a crash alert structurally cannot catch a late-but-successful run:** a crash detector's entire signal is the process's exit code -- it fires when a job dies unexpectedly, and by construction has nothing to say about a job that is still running, or that finished with exit code 0. Both real incidents in this scenario are exactly that case: the pipeline did not crash, it simply took longer than its 6:00 AM SLA allowed, finishing at 6:40 AM and 7:15 AM respectively. No refinement of a crash-detection alert -- more sensitive thresholds, faster polling, anything -- can ever catch this failure mode, because the failure mode it is looking for (an unexpected process death) genuinely did not occur either time. This is the core reason "alert if the job crashes" and "alert if the job is going to miss its SLA" have to be understood as two separate signals rather than one alert covering both conditions -- they are answering different questions about the pipeline's health.

**Why the fix has to detect SLA risk WHILE the job is running, not after it finishes:** Spark's history server already shows, after the fact, exactly which stage ran long each time -- that information genuinely exists, but only becomes visible in a UI someone has to be actively watching, well after the fact. The actual fix compares each stage's real elapsed time against its own historical baseline as the job progresses (not waiting for the whole job to finish), and separately projects the pipeline's likely completion time against the actual 6:00 AM deadline using current progress -- both checks evaluated DURING execution, specifically so a human can be paged before the deadline passes rather than discovering the miss only when someone downstream notices stale data. This is the concrete mechanism that turns "the information exists somewhere, in a UI nobody is watching" into "an alert reaches on-call before the SLA is actually breached."

**Why this doesn't replace the crash alert, and why both need to coexist rather than one subsuming the other:** the crash alert remains the correct, sufficient signal for its own failure mode (an actual process death) -- nothing about adding SLA-risk monitoring should remove or weaken it, since a genuine crash is a real, different failure this pipeline can still experience, and the new SLA-risk checks would not catch a crash any better than the old crash alert catches a slow-but-successful run. The lesson here is not "replace a bad alert with a good one," it is "recognize that this pipeline has two genuinely distinct failure modes, and monitoring built for one of them provides zero coverage for the other, no matter how well-tuned it is."

**The general observability principle this generalizes to:** effective pipeline monitoring requires identifying each DISTINCT failure mode a pipeline can actually experience (crash, SLA miss, silent data-quality degradation, resource exhaustion, and others) and building a specific, measurable signal for each one -- a single generic "is something wrong" alert, however well-intentioned, will structurally miss any failure mode that doesn't happen to match the one condition it was actually built to detect.
