# DE04-T02 — Hadoop Ecosystem and Cloudera Data Platform | Hive and Impala

## ID
DE04-T02

## Chapter
4 — Hadoop Ecosystem and Cloudera Data Platform

## Live Scenario
A transaction-monitoring team runs two kinds of queries against the same Iceberg tables on CDP: a nightly batch job that joins five years of transaction history against a slowly-changing customer dimension to rebuild a compliance report (runs for 40 minutes, touches nearly the whole table, tolerant of that latency), and an ad-hoc compliance-analyst workload where analysts run dozens of small, filtered lookups per day ('show me this one customer's transactions from last week') and expect sub-5-second responses. A new engineer, seeing both workloads hit the same tables, configures both to run through Hive, reasoning that 'one engine, one configuration, is simpler to operate.' The analysts' ad-hoc queries become the team's top complaint within a week -- each one taking 20-40 seconds even for a single customer's single week of data.

## The Question
> Explain why running both workloads through the same engine was the wrong simplification here, using what Hive and Impala are each actually architected to do well, and redesign which engine each workload should use.

## Solution Code
```sql
-- ===== Workload 1: the nightly 5-year compliance rebuild -- HIVE fits =====
-- Hive's execution model (historically MapReduce, now commonly Tez or Spark
-- as the execution engine underneath HiveQL) is built around throughput over
-- large-scale, long-running batch jobs -- it tolerates and amortizes startup
-- and coordination overhead well because that overhead is small relative to
-- a 40-minute job touching years of data. Hive's cost-based optimizer and
-- its tolerance for very large, complex, multi-stage query plans (with
-- intermediate stages spilling to disk if needed) are exactly the properties
-- this batch job needs -- and Hive is *not* being used here because it is
-- "the safe default," but because a 40-minute, near-full-table batch job is
-- genuinely the workload Hive's execution model is built for.
CREATE TABLE compliance_report_2026 AS
SELECT
    c.customer_id, c.segment, c.risk_tier,
    COUNT(t.transaction_id)                     AS txn_count,
    SUM(t.amount)                                AS txn_total,
    MIN(t.transaction_date)                      AS earliest_txn,
    MAX(t.transaction_date)                      AS latest_txn
FROM iceberg_catalog.banking.transactions t
JOIN iceberg_catalog.banking.customer_dim c
    ON t.customer_id = c.customer_id
    AND t.transaction_date BETWEEN c.effective_from AND c.effective_to  -- point-in-time SCD2 join
WHERE t.transaction_date >= DATE '2021-08-21'
GROUP BY c.customer_id, c.segment, c.risk_tier;

-- ===== Workload 2: ad-hoc, sub-5-second analyst lookups -- IMPALA fits =====
-- Impala uses its own MPP (massively parallel processing) execution engine,
-- with long-lived daemon processes on every node that skip the per-query
-- job-startup/coordination overhead a Hive-on-Tez/Spark job pays -- this is
-- the specific architectural reason Impala is built for low-latency,
-- interactive queries rather than Hive's throughput-oriented batch model.
-- Impala talks to the SAME Hive metastore and reads the SAME Iceberg
-- tables -- this is not a data duplication or a second copy of the data,
-- only a different, already-running execution engine pointed at it.
SELECT transaction_id, transaction_date, amount, merchant, status
FROM iceberg_catalog.banking.transactions
WHERE customer_id = 'CUST-2004471'
  AND transaction_date >= DATE_SUB(CURRENT_DATE(), INTERVAL 7 DAYS)
ORDER BY transaction_date DESC;
-- A filtered, partition-pruned lookup against one customer, one week --
-- exactly the shape of query Impala's daemon-based MPP engine answers in
-- low single-digit seconds, versus Hive's per-query job-startup overhead
-- dominating a query this small.
```

## Expected Output
Before (both workloads on Hive):
  Nightly compliance rebuild: ~40 min -- acceptable, matches Hive's design.
  Ad-hoc single-customer lookup: 20-40 sec -- almost entirely per-query
    job coordination/startup overhead, not actual data-scan time, because
    the query itself only touches a tiny, partition-pruned slice of data.

After (nightly rebuild on Hive, ad-hoc lookups on Impala):
  Nightly compliance rebuild: unchanged, ~40 min on Hive.
  Ad-hoc single-customer lookup: ~1-3 sec on Impala's always-running
    daemons -- same underlying Iceberg table, same Hive metastore,
    different execution engine matched to the query's actual latency need.

## Explanation
**The junior engineer's "one engine is simpler" reasoning conflated operational simplicity with query-shape fitness -- and the two workloads in this scenario have genuinely different latency requirements that map onto genuinely different execution architectures, not just different tuning of the same engine.**

**Why Hive fits the nightly compliance rebuild:** Hive's execution model -- historically MapReduce, and in current Cloudera deployments typically Tez or Spark as the underlying execution engine for HiveQL -- is built around orchestrating large, multi-stage, often long-running jobs, with a cost-based optimizer suited to complex query plans over very large data volumes. The per-query overhead of planning and launching a job's execution stages is real, but it is small relative to a 40-minute job scanning years of transaction history -- this overhead is exactly what a throughput-oriented batch engine is designed to amortize, not eliminate.

**Why that same per-query overhead is what breaks the ad-hoc workload:** a query asking for one customer's transactions from the last week touches a tiny amount of actual data -- with correct partitioning, this is a fast scan. But when routed through Hive, the query still pays the same job-startup and coordination overhead a Hive job always pays, and for a query this small, that fixed overhead dominates the total response time. This is the concrete reason the analysts saw 20-40 second responses for a query that should complete in a couple of seconds: the bottleneck was never the amount of data scanned, it was the execution model's fixed per-query cost being applied to a workload shaped for a different execution model entirely.

**Why Impala is architected specifically to avoid that overhead:** Impala runs its own long-lived MPP (massively parallel processing) daemon on every relevant node in the cluster, continuously ready to execute queries without the job-submission and coordination steps a Hive-on-Tez/Spark job goes through for every single query. This is the specific mechanism behind Impala's interactive-latency positioning -- not a marketing claim, but a direct consequence of trading Hive's job-per-query model for always-running daemons that can start executing a query's fragments immediately.

**Why this required no data duplication or table redesign:** both engines, in a CDP deployment, read the same underlying Iceberg tables through the same Hive metastore (or Iceberg's own catalog layer built on top of it) -- routing the ad-hoc workload to Impala was purely a change in which execution engine a query goes through, not a data-copying or table-restructuring exercise. This is what makes "the right engine per workload shape" a genuinely low-cost fix once diagnosed correctly, versus the real cost of having initially misdiagnosed it as a configuration-tuning problem on a single engine.

**The general rule this generalizes to:** choosing between Hive and Impala (or, more broadly, between a throughput-oriented batch engine and an interactive MPP engine) should be driven by the query's actual latency requirement and data-touch pattern -- large-scan, latency-tolerant batch work fits Hive's job-oriented model; small, latency-sensitive, high-frequency lookups fit Impala's always-on daemon model -- not by a preference for operating fewer moving parts, which optimizes the wrong thing when the two workloads' actual requirements diverge this sharply.
