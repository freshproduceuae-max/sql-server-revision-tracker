## Live Scenario
The bank's customer dimension is being migrated from a single SQL Server table (where Data Validation G14 already validates SCD2 gap/overlap integrity with LAG/LEAD window queries) to a distributed Spark pipeline that loads the same customer dimension into Iceberg, at a scale of 40 million customers with several million daily change-events. A first implementation writes a straightforward `MERGE INTO` that closes the current row and inserts a new one whenever any tracked attribute changes -- functionally the same SCD2 idea G14 validates for. Under load testing with concurrent daily batches, two problems appear that never showed up on the single-node SQL Server version: (1) two change-events for the same customer arriving in the same micro-batch, processed in an non-deterministic order within a partition, sometimes produce two new 'current' rows instead of one, and (2) the MERGE's `whenMatchedUpdate` step, run at 40-million-row scale, becomes the single most expensive stage in the whole pipeline because it is not partition-pruned and scans far more data than the day's actual change volume.

## The Question
> Diagnose why both problems are specific to distributed, at-scale SCD2 (not concerns the single-node SQL Server version has), referencing the same gap/overlap/current-row invariants G14 validates for, and fix both without changing what a correct SCD2 history is defined to look like.

## Solution Code
```python
from pyspark.sql import SparkSession
from pyspark.sql import functions as F
from pyspark.sql.window import Window
from delta.tables import DeltaTable

spark = SparkSession.builder.appName("scd2-at-scale").getOrCreate()

# --- Problem 1: multiple same-customer changes in one micro-batch, processed
# out of order -- fix by collapsing to ONE net change per customer per batch
# BEFORE the MERGE ever runs, using event time to pick the true latest state.
raw_changes = spark.read.parquet("s3://bank-data/customer-changes/batch=2026-08-19/")

# Rank each customer's events by event time within this batch; keep only the
# latest. This enforces the same "exactly one current row per entity" invariant
# G14 validates for -- but it has to be enforced explicitly here, because
# distributed processing offers no guarantee about the order same-key events
# are handled in across partitions/tasks the way a single-threaded SQL Server
# session naturally processes rows in one order.
w = Window.partitionBy("customer_id").orderBy(F.col("event_ts").desc())
latest_change_per_customer = (
    raw_changes
    .withColumn("rn", F.row_number().over(w))
    .filter(F.col("rn") == 1)
    .drop("rn")
)

# --- Problem 2: unpruned MERGE scanning the full 40M-row dimension ---
# Fix: partition the Iceberg table by a low-cardinality, mergeable key
# (e.g. a hash bucket of customer_id) and give the MERGE's join condition
# something to prune on, instead of matching purely on customer_id against
# the whole table. This is the distributed-scale analogue of an index seek
# a single-node database gets for free.
spark.sql("""
  CREATE TABLE IF NOT EXISTS lakehouse.dim.customer_scd2 (
    customer_id STRING, segment STRING, address STRING,
    effective_from TIMESTAMP, effective_to TIMESTAMP, is_current BOOLEAN,
    cust_bucket INT
  )
  USING iceberg
  PARTITIONED BY (cust_bucket)
""")

changes_bucketed = latest_change_per_customer.withColumn(
    "cust_bucket", F.pmod(F.hash("customer_id"), F.lit(64))
)

target = DeltaTable.forName(spark, "lakehouse.dim.customer_scd2") if False else None
# Iceberg MERGE via Spark SQL, with the bucket predicate included in the ON
# clause so the planner can prune to only the partitions this batch touches
# instead of scanning all 40M rows on every run:
changes_bucketed.createOrReplaceTempView("changes")
spark.sql("""
  MERGE INTO lakehouse.dim.customer_scd2 t
  USING changes s
  ON t.customer_id = s.customer_id
     AND t.cust_bucket = s.cust_bucket   -- partition-pruning predicate
     AND t.is_current = true
  WHEN MATCHED AND (t.segment <> s.segment OR t.address <> s.address) THEN
    UPDATE SET t.effective_to = s.event_ts, t.is_current = false
  WHEN NOT MATCHED THEN
    INSERT (customer_id, segment, address, effective_from, effective_to, is_current, cust_bucket)
    VALUES (s.customer_id, s.segment, s.address, s.event_ts, NULL, true, s.cust_bucket)
""")
# A second pass inserts the new current row for every customer whose old
# current row was just closed -- kept as an explicit second MERGE (rather
# than one MERGE trying to both close and open in a single matched clause)
# because Iceberg's MERGE INTO permits at most one action per match branch,
# and correctness here depends on this running only after the close commits.
```

## Expected Output
Before fix (100 concurrent same-customer changes in one batch):
  ~3-5% of affected customers ended with 2 rows flagged is_current = true
  -- the exact "ALERT: More current rows than customers" case G14-T01's
  Step 3 query is built to catch.

After collapsing to one net change per customer via row_number()+event_ts:
  0 customers with multiple current rows; G14-style current-row-count check
  passes at 40M-row scale the same way it does on the SQL Server table.

MERGE stage duration, unpruned (scans all 40M rows every run): ~38 min.
MERGE stage duration, bucket-partitioned + pruned to touched buckets: ~90 sec.

## Explanation
**Both problems are genuinely new at distributed scale, not scaled-up versions of anything the single-node SQL Server pipeline has to worry about -- and it's worth being explicit about why, since the SCD2 invariants themselves (from G14: non-overlapping, gapless, exactly-one-current-row) do not change.**

**Problem 1 -- multiple current rows from same-batch, same-customer changes -- is a consequence of distributed execution having no implicit ordering guarantee.** A single-node SQL Server session processing a batch of change rows does so one row at a time, in whatever order a cursor or set-based statement happens to touch them, but critically that is *one* process making *one* pass. A Spark job processing the same batch splits it across partitions and executor tasks that run concurrently and independently; if two change events for the same `customer_id` land in different tasks (or even the same task but are not explicitly ordered), a naive `MERGE` has no guarantee about which one "wins" the current-row slot, and in the worst case both get treated as distinct changes against a target row that was only current for a moment -- producing exactly the multiple-current-row violation G14-T01's Step 3 summary query is designed to catch (`SUM(IsCurrent) > COUNT(DISTINCT CustomerID)`). The fix does not change the *definition* of correct SCD2 history at all -- it enforces the same "exactly one current row" invariant, just doing so explicitly (via `row_number()` ordered by event time, collapsing to one net change per customer before the MERGE runs) because distributed processing does not give that ordering for free the way single-threaded execution incidentally does.

**Problem 2 -- the MERGE becoming the single most expensive stage -- is a partition-pruning problem that has no equivalent on a single-node system with a b-tree index.** SQL Server can seek directly to the rows matching `customer_id` via an index, touching a tiny fraction of the table regardless of its total size. Spark's MERGE, run against an Iceberg table with no partition structure aligned to the join key, has to plan a scan that in the worst case reads every data file to find rows matching each incoming customer_id -- there is no index-seek equivalent unless the table's physical layout (partitioning) gives the query planner something to prune on. Bucketing the table by a hash of `customer_id` and including that bucket as an explicit predicate in the `MERGE`'s `ON` clause lets Iceberg's planner skip entire partitions that contain no customers present in this batch's (typically much smaller) change set -- turning an O(table size) scan into something closer to O(batch size), which is what actually explains the ~38min-to-~90sec difference.

**The invariant that must not move, regardless of either fix:** a correct SCD2 history at 40M rows and distributed scale still has to satisfy the same three properties G14-T01 validates for a few thousand rows on SQL Server -- non-overlapping, gapless, exactly-one-current-row. Neither fix changes what "correct" means; both fixes exist purely to make the distributed implementation actually deliver that same correctness under conditions (out-of-order concurrent processing, no free index seek) the single-node implementation never had to contend with.
