## Live Scenario
A data scientist's exploratory notebook computes three different summary statistics from the same cleansed 300-million-row transaction DataFrame -- but the cleansing logic (a chain of joins and filters) re-runs from the raw source data from scratch for each of the three summaries, because lazy evaluation means nothing was actually kept in memory after the first computation finished. The notebook takes 45 minutes to run all three summaries, and the data scientist assumes Spark itself is just slow.

## The Question
> Identify why the same cleansing work is being repeated three times, apply caching correctly to fix it, and explain the serialization trade-off that determines how much memory the cached result actually consumes.

## Solution Code
```python
from pyspark import StorageLevel
from pyspark.sql import functions as F

raw = spark.read.parquet("s3://bank-data/transactions/")

cleaned = (
    raw
    .join(customers, on="CustomerID", how="inner")
    .filter(F.col("Amount") > 0)
    .withColumn("amount_gbp", F.col("Amount") * F.col("fx_rate"))
)

# WITHOUT caching: each action below is a SEPARATE trigger of the ENTIRE
# lazy plan above -- the join, the filter and the withColumn all re-run
# from the raw Parquet source three separate times, because Spark has no
# memory that this exact plan was already computed once.
# total = cleaned.agg(F.sum("amount_gbp")).collect()          # run 1: full recompute
# by_currency = cleaned.groupBy("Currency").count().collect() # run 2: full recompute
# top10 = cleaned.orderBy(F.desc("amount_gbp")).limit(10)      # run 3: full recompute

# WITH caching: .cache() marks the DataFrame's plan to be materialized and
# kept (in memory and/or disk) after its FIRST action runs, so every
# SUBSEQUENT action reuses that stored result instead of recomputing the
# join/filter/withColumn chain from raw data again.
cleaned.cache()  # DataFrame .cache() defaults to StorageLevel.MEMORY_AND_DISK
cleaned.count()  # forces the first, materializing action -- caching has no effect until something actually runs the plan once

total = cleaned.agg(F.sum("amount_gbp")).collect()           # reuses the cached result
by_currency = cleaned.groupBy("Currency").count().collect()  # reuses the cached result
top10 = cleaned.orderBy(F.desc("amount_gbp")).limit(10).collect()  # reuses the cached result

# Explicit StorageLevel control, when the default doesn't fit the situation:
# MEMORY_AND_DISK_SER trades some CPU (deserializing on read) for
# significantly less memory footprint -- worth it when the cached DataFrame
# is large relative to available executor memory.
cleaned.unpersist()  # release the default-level cache before re-caching differently
cleaned.persist(StorageLevel.MEMORY_AND_DISK_SER)

# Always release a cache once it's no longer needed -- an un-unpersisted
# cache holds executor memory for the rest of the job/session, which can
# starve later, unrelated work of the memory it needs.
# cleaned.unpersist()
```

## Expected Output
Without caching, the Spark UI's Jobs tab shows three separate jobs, each reading and processing the full 300 million rows from the raw Parquet source -- roughly equal, additive time for each of the three summaries. With `.cache()` plus the forcing `.count()`, the UI shows one job materializing the cleaned DataFrame, then three much shorter jobs that read from the cached result (visible in the UI as a `InMemoryTableScan` node in each subsequent job's plan, rather than a re-read of the raw Parquet source) -- the total notebook runtime drops from roughly three full passes to roughly one full pass plus three cheap reads of the cached result.

## Explanation
**The root cause is a direct consequence of lazy evaluation (DE02-T01): Spark has no memory of a plan it has already executed unless explicitly told to keep the result.** Three actions against the same unmaterialized `cleaned` DataFrame are, to Spark, three independent requests to run the full plan from scratch -- there is no automatic memoization the way a spreadsheet or a pandas DataFrame would implicitly hold in memory. This is precisely why the notebook's "Spark is just slow" diagnosis was wrong: the actual work being done was three full passes over 300 million rows, not one Spark being three times slower than expected.

**`.cache()` and `.persist()` are the same underlying mechanism** -- `.cache()` is shorthand for `.persist(StorageLevel.MEMORY_AND_DISK)`, the default storage level for a **DataFrame** specifically (an RDD's `.cache()` default is `MEMORY_ONLY` -- a real, documented difference between the two APIs worth knowing rather than assuming they always match). Neither call does anything by itself -- caching only takes effect once the *first* action after the `.cache()`/`.persist()` call actually executes the plan and materializes the result; calling `.cache()` and then immediately inspecting `.storageLevel` shows the intent, not yet the reality, until that first action runs.

**Serialization is the trade-off that determines how much memory a cached result actually costs.** `MEMORY_AND_DISK` (the DataFrame default) stores rows in a partially-serialized, Spark-internal format that's reasonably compact already. `MEMORY_AND_DISK_SER` explicitly serializes the cached data more aggressively before storing it -- meaningfully smaller memory footprint, at the cost of CPU time to deserialize on every subsequent read. Kryo serialization (`spark.serializer=org.apache.spark.serializer.KryoSerializer`) is faster and more compact than Spark's default Java serialization for custom objects, but is *not* Spark's default configuration -- it requires opting in, because Kryo needs classes registered for full safety and doesn't serialize every Java type out of the box the way Java's built-in serialization does.

**Executor sizing is the resource-allocation half of this same performance picture**, not covered in code above but essential context: too few, oversized executors reduce parallelism and increase the blast radius of a single executor failure; too many, undersized executors waste overhead on per-task scheduling and risk out-of-memory errors on any partition larger than expected (exactly the skew scenario from DE02-T03). Sizing executors correctly for a given cluster and workload is itself informed by the same partition-count and data-volume reasoning DE02-T03 and this lesson both build.
