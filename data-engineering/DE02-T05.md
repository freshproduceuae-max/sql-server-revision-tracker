## Live Scenario
A fraud-monitoring team wants near-real-time alerts when a customer's card is used in two different countries within an implausibly short time window. They ask for a Spark Structured Streaming job reading a Kafka topic of live card-transaction events, but are unclear on how "real-time" this can actually be, and what happens to an event that arrives severely delayed (a transaction that reaches the platform 20 minutes late due to a mobile network outage at the point of sale).

## The Question
> Explain Structured Streaming's micro-batch execution model (what "near-real-time" actually means in practice), and design a watermarked windowed aggregation that correctly handles late-arriving events without holding unbounded state in memory forever.

## Solution Code
```python
from pyspark.sql import functions as F
from pyspark.sql.types import StructType, StructField, StringType, DoubleType, TimestampType

event_schema = StructType([
    StructField("CardID", StringType(), False),
    StructField("CountryCode", StringType(), False),
    StructField("Amount", DoubleType(), False),
    StructField("EventTime", TimestampType(), False),  # when the transaction actually happened
])

# Structured Streaming reads Kafka as an unbounded, continuously-appending
# DataFrame -- the SAME DataFrame API as batch (DE02-T02), not a separate
# streaming-specific API. This is a deliberate Spark design choice: the
# same transformations, joins and aggregations apply to both.
raw_events = (
    spark.readStream
    .format("kafka")
    .option("kafka.bootstrap.servers", "kafka-broker:9092")
    .option("subscribe", "card-transactions")
    .load()
)

events = (
    raw_events
    .select(F.from_json(F.col("value").cast("string"), event_schema).alias("data"))
    .select("data.*")
)

# WATERMARKING: tells Spark "I will accept an event as late as 15 minutes
# after its EventTime, but no later" -- this is what bounds the streaming
# state Spark must keep in memory. Without a watermark, Spark would have to
# retain state for every open window FOREVER, since an arbitrarily old
# event could theoretically still arrive -- an unbounded, eventually-fatal
# memory growth in a long-running streaming job.
country_windows = (
    events
    .withWatermark("EventTime", "15 minutes")
    .groupBy(
        F.col("CardID"),
        F.window("EventTime", "10 minutes"),  # tumbling 10-minute windows, keyed by event time
    )
    .agg(
        F.collect_set("CountryCode").alias("countries_seen"),
        F.count("*").alias("txn_count"),
    )
)

# outputMode="update" emits a row every time a window's aggregate changes --
# appropriate for a fraud-alerting use case that wants to react as new
# matching events arrive, not wait for a window to fully close.
query = (
    country_windows.writeStream
    .outputMode("update")
    .format("console")
    .trigger(processingTime="30 seconds")  # the micro-batch interval
    .start()
)
```

## Expected Output
With the 15-minute watermark set, an event whose `EventTime` is more than 15 minutes older than the maximum `EventTime` Spark has seen so far is dropped from the aggregation (not held forever) -- so the scenario's 20-minute-late transaction, if it exceeds the watermark threshold by the time it arrives, is excluded from its original window's count rather than causing that window's state to stay open indefinitely. `trigger(processingTime="30 seconds")` means the job checks Kafka for new events and processes a micro-batch every 30 seconds -- "near-real-time" in this design means "results update roughly every 30 seconds," not sub-second true real-time processing.

## Explanation
**Structured Streaming's core execution model is micro-batch, not continuous per-event processing** (a separate, more limited experimental Continuous Processing mode exists in Spark but is not the default and has significant operational restrictions) -- Spark repeatedly runs the *same* batch query (built from the identical DataFrame/Spark SQL API covered in DE02-T02) against whatever new data has arrived in the source since the last micro-batch, on a fixed trigger interval. This is exactly why the answer to "how real-time is this" is "as real-time as your trigger interval," not an unqualified "instant."

**A watermark is the mechanism that makes late data a *design decision* instead of an unbounded resource leak.** Without one, Spark cannot know when it is safe to stop waiting for more events belonging to an already-computed window, so it would have to retain state for every window that has ever been opened, forever -- in a job meant to run continuously for weeks or months, this state grows without bound and eventually exhausts memory. `withWatermark("EventTime", "15 minutes")` is an explicit business decision ("we accept up to 15 minutes of lateness") that lets Spark safely discard state for windows older than the watermark threshold.

**Event time vs. processing time is the distinction the scenario's late-arriving transaction turns on.** `EventTime` is when the transaction actually happened at the point of sale; the time Spark actually receives and processes the Kafka message is separate and, in the scenario's network-outage case, 20 minutes later. Windowing and watermarking in the code above are both keyed on `EventTime`, specifically so that a late-arriving event is still correctly attributed to the window it *actually* belongs to (if within the watermark tolerance) rather than the window Spark happened to be processing when the event finally arrived.

**Exactly-once semantics is a separate guarantee from watermarking, worth naming so the two aren't conflated**: Structured Streaming's checkpointing mechanism (a `checkpointLocation` option, omitted above for brevity but required in production) is what provides exactly-once processing guarantees for the streaming query's own state and output -- surviving a job restart without either dropping or double-processing already-handled data. Watermarking bounds *state size for late data*; checkpointing provides *fault-tolerant, exactly-once execution*. A production fraud-alerting job needs both, for different reasons.
