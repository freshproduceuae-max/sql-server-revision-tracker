## Live Scenario
During the same audit, the compliance team asks the platform team to confirm that customer PII in the banking data platform is 'secure.' The platform lead responds with a single sentence: 'yes, the cluster uses Kerberos, so it's secure.' The auditor pushes back with three specific follow-up questions the platform lead cannot answer cleanly: (1) Kerberos authenticates that a user is who they claim to be -- what actually decides whether that authenticated user is ALLOWED to query the specific PII columns in question? (2) is the data encrypted only in transit, only at rest, or both -- and does Kerberos have anything to do with either? (3) if a fraud analyst is allowed to query the customer table for their job, do they see the customer's raw national ID number, or something else?

## The Question
> Answer the auditor's three questions precisely, distinguishing which specific security control (not 'security' as one undifferentiated property) each one is actually asking about, and explain why the platform lead's single-sentence answer was a category error -- naming one real control while implying it covered guarantees that control does not provide.

## Solution Code
```sql
-- Q1: Kerberos authenticates identity. It does NOT decide authorization
-- (what an authenticated user is allowed to do). Authorization here is
-- Apache Ranger's job -- a distinct control, enforced after Kerberos has
-- already confirmed who the user is.

-- Ranger policy (illustrative -- real policies are managed via Ranger's
-- admin UI/API): this is what actually decides whether the fraud analyst
-- can query the PII columns, NOT Kerberos.
-- policy: table=customers, columns=[national_id, date_of_birth],
--         allow=[role:fraud_analyst, role:compliance_auditor],
--         deny=[role:general_analyst]

-- Q2: encryption at rest and encryption in transit are TWO SEPARATE
-- controls, and Kerberos provides NEITHER of them -- Kerberos is purely
-- an authentication protocol.

-- Encryption AT REST: data on disk/object storage is encrypted --
-- typically HDFS Transparent Data Encryption (TDE) with encryption zones,
-- or server-side encryption on Ozone/S3-compatible object storage.
-- Confirming this requires checking the actual storage configuration,
-- not the authentication mechanism:
-- hdfs crypto -listZones
-- (shows which HDFS paths are inside an encryption zone -- this is the
-- actual, checkable evidence for "is this data encrypted at rest",
-- not an inference from "Kerberos is enabled")

-- Encryption IN TRANSIT: data moving between cluster nodes, or between
-- a client and the cluster, is encrypted via TLS -- a separate
-- configuration from both Kerberos and at-rest encryption. Confirming
-- this requires checking TLS is actually configured for the relevant
-- service (e.g. Spark's internal shuffle traffic, JDBC/Hive/Impala
-- client connections), not assuming it from Kerberos being enabled.

-- Q3: what the fraud analyst SEES when authorized -- raw value vs. a
-- masked/obfuscated value -- is a DIFFERENT control again: DATA MASKING,
-- typically enforced via Ranger's column-masking policies. This is
-- distinct from authorization (Q1): a masking policy can let a user
-- query a column (authorized) while showing them a transformed value
-- rather than the raw one.

-- Ranger column-masking policy (illustrative): fraud_analyst role sees
-- national_id partially masked, NOT the raw value -- even though they
-- ARE authorized to query the column at all:
SELECT
  customer_id,
  -- Without a Ranger mask: raw value would be returned to any authorized query.
  -- With a Ranger MASK policy applied for role:fraud_analyst:
  CONCAT(REPEAT('*', 5), RIGHT(national_id, 4)) AS national_id_masked,
  date_of_birth
FROM customers
WHERE customer_id = 'CUST-2004471';
-- The masking transformation happens at query-evaluation time, driven by
-- the querying user's role -- a compliance_auditor role, under a
-- DIFFERENT Ranger masking policy, might be granted the raw, unmasked
-- national_id for a legitimate audit purpose, while fraud_analyst never
-- sees it unmasked -- same authorization (both roles CAN query the
-- column), different masking outcome.
```

## Expected Output
Q1 -- Authentication vs. authorization:
  Kerberos: confirms the user really is who they claim to be.
  Ranger (separate control): decides whether THAT authenticated user is
    allowed to query national_id/date_of_birth at all.
  Kerberos alone answers neither "who can see this" nor "should this
    specific user see this" -- only "is this really that user."

Q2 -- Encryption at rest vs. in transit:
  hdfs crypto -listZones -> confirms which paths are actually inside an
    HDFS encryption zone (at-rest evidence).
  TLS configuration on Spark shuffle / JDBC-Hive-Impala connections ->
    confirms in-transit encryption is actually configured.
  Neither is implied or provided by Kerberos being enabled.

Q3 -- Authorization vs. masking:
  fraud_analyst: authorized to query national_id (passes Ranger
    authorization) but sees "*****4471" under a Ranger masking policy.
  compliance_auditor: same authorization outcome (can query the column)
    but a different masking policy could show the unmasked raw value for
    a legitimate audit purpose.
  Authorization ("can they query it") and masking ("what do they see")
    are two independently configured Ranger policy types.

## Explanation
**The platform lead's "Kerberos, so it's secure" answer was a category error: naming one real, specific control (authentication) and letting it stand in for "security" as an undifferentiated whole, when the auditor's three questions each target a DIFFERENT control that Kerberos does not provide.**

**Q1 -- why Kerberos cannot answer "is this user allowed to see this":** Kerberos is an authentication protocol -- its entire job is verifying that a user really is who they claim to be (via ticket-granting and mutual verification), which happens *before* any question of what that verified identity is permitted to do. Authorization -- deciding whether an authenticated identity may query specific tables, columns, or rows -- is a separate control, and in CDP that is Apache Ranger's job, evaluated against explicit policies after Kerberos has already done its part. A cluster can have Kerberos correctly enabled and still have zero meaningful access control, if no Ranger (or equivalent) policy actually restricts who can query PII columns -- which is exactly the auditor's implicit concern, and exactly what the platform lead's answer failed to address.

**Q2 -- why encryption at rest and in transit are two separate, Kerberos-unrelated controls:** encryption at rest (protecting data as stored on disk or object storage, via mechanisms like HDFS Transparent Data Encryption with encryption zones, or server-side encryption on an object store) and encryption in transit (protecting data moving over the network, via TLS between nodes or between clients and cluster services) are independently configured mechanisms addressing different threat models -- at-rest protects against someone accessing the physical/storage layer directly; in-transit protects against network interception. Kerberos provides neither: it is purely about identity verification, and a cluster can have strong Kerberos authentication while having no encryption at rest, no TLS in transit, or both, entirely independently of Kerberos's configuration. Confirming either requires checking the actual storage/network configuration (e.g. hdfs crypto -listZones for at-rest zones, TLS configuration for the relevant service) -- not inferring it from an unrelated control being enabled.

**Q3 -- why "authorized to query" and "sees the raw value" are two different outcomes, not one:** even once Ranger has authorized a user to query a PII column at all, what value they actually see is governed by a separate mechanism -- data masking, typically enforced via Ranger's own column-masking policies, evaluated at query time based on the querying user's role. This is what allows two users with the *same* authorization outcome (both can query national_id) to see genuinely different results: a fraud analyst role masked to the last four digits, a compliance-auditor role potentially granted the unmasked raw value for a legitimate audit purpose. Masking is not a side effect of authorization succeeding -- it is its own policy type, answering "what transformation, if any, applies to the value this authorized user receives," distinct from "is this user allowed to query this column at all."

**The general security-review discipline this scenario is built to teach:** "is it secure" is not a single yes/no property -- a real security review has to name the SPECIFIC control being asked about (authentication, authorization, encryption at rest, encryption in transit, masking) and verify each one independently, because a system can genuinely have one of these controls correctly configured while entirely lacking another, and naming only the one that happens to be true (as the platform lead did with Kerberos) while implying it covers the others is precisely the kind of guarantee-conflation that leaves real gaps unexamined in an audit.
