## Live Scenario
A platform team containerizes their Spark ETL jobs so 'every environment runs the exact same image.' Their Dockerfile installs dependencies via pip install at build time from a public PyPI mirror with no version pinning, embeds a database password directly as an environment variable baked into the image (ENV DB_PASSWORD=prod_secret_123), runs the container process as root, and has never been scanned for known vulnerabilities in its base OS or Python packages -- the team's only stated concern was 'does the container run our Spark job correctly,' which it does. A security review six months later flags all four of these as separate, serious findings, and the team is initially confused why 'four different reviewers found four different problems' when they thought they had 'one container that works.'

## The Question
> Explain why each of the four findings (unpinned dependencies, a baked-in secret, running as root, no vulnerability scanning) is a genuinely distinct control -- not four symptoms of one 'container security' problem -- and design the fix for each, being explicit about why fixing one does not address the others.

## Solution Code
```dockerfile
# ===== BEFORE: all four findings present in one Dockerfile =====
# FROM python:3.11
# RUN pip install pyspark pandas boto3        # <- unpinned: no version pins
# ENV DB_PASSWORD=prod_secret_123               # <- secret baked into the image layer
# COPY etl_job.py /app/etl_job.py
# CMD ["python", "/app/etl_job.py"]             # <- runs as root (the default
#                                                #    USER in this base image)
# (no vulnerability scan step anywhere in the build process)

# ===== AFTER: each finding fixed by its OWN distinct mechanism =====

# --- Finding 1: unpinned dependencies (a REPRODUCIBILITY / provenance
# problem -- "what exact code is actually running" is not knowable and
# can silently change between builds) ---
FROM python:3.11.9-slim@sha256:8f3a4b2c1e...  # base image pinned by DIGEST,
                                                # not just a mutable tag --
                                                # a tag like "3.11-slim" can
                                                # point to different actual
                                                # bytes over time; a digest
                                                # cannot.
COPY requirements.lock.txt /app/requirements.lock.txt
RUN pip install --require-hashes -r /app/requirements.lock.txt
# requirements.lock.txt pins EXACT versions and cryptographic hashes for
# every dependency (e.g. via pip-compile --generate-hashes) -- this fixes
# "what code is running" as a reproducibility property. It does NOT, by
# itself, fix anything about secrets, root, or known vulnerabilities in
# whatever exact versions get pinned.

# --- Finding 2: secret baked into the image (a DISTRIBUTION problem --
# anyone who can pull this image, from any registry it is ever pushed to,
# can extract the plaintext password from any layer, forever, even if
# the password is later rotated) ---
# NO ENV DB_PASSWORD line at all -- secrets are never baked into an image.
# Instead, the credential is injected at RUNTIME, from a secrets manager,
# never present in any image layer:
# kubectl create secret generic db-credentials --from-literal=password=<rotated-value>
# ---
# In the Kubernetes pod spec (NOT the Dockerfile):
#   env:
#     - name: DB_PASSWORD
#       valueFrom:
#         secretKeyRef: {name: db-credentials, key: password}
# This fixes "the secret is permanently embedded in a distributable
# artifact." It does NOT fix unpinned dependencies, root execution, or
# vulnerability scanning -- those remain entirely separate concerns.

# --- Finding 3: running as root (a LEAST-PRIVILEGE / blast-radius
# problem -- if the process is ever compromised via ANY vulnerability,
# root-in-container is a materially larger blast radius than a
# non-privileged user, independent of what that vulnerability actually is) ---
RUN groupadd -r sparkuser && useradd -r -g sparkuser sparkuser
USER sparkuser
# This fixes "what privilege level a compromised process would have." It
# does NOT fix unpinned dependencies, the secret-baking problem, or
# whether known-vulnerable packages are present -- a non-root process
# running a package with a known critical CVE is still running a
# known-vulnerable package, just with a smaller blast radius if exploited.

# --- Finding 4: no vulnerability scanning (a KNOWN-CVE VISIBILITY
# problem -- neither pinning versions nor running as non-root tells you
# whether the SPECIFIC pinned versions have known, disclosed
# vulnerabilities) ---
# Added as a CI pipeline STEP, not a Dockerfile instruction:
#   - name: Scan image for known vulnerabilities
#     run: trivy image --severity HIGH,CRITICAL --exit-code 1 fraud-etl:${{ github.sha }}
# This fixes "are there disclosed CVEs in this exact image's OS packages
# and Python dependencies." It does NOT fix reproducibility, secrets
# handling, or privilege level -- a perfectly pinned, secret-free,
# non-root image can still contain a package with a critical, disclosed
# vulnerability that a scan is specifically what surfaces.
```

## Explanation
**The team's confusion ("four different reviewers found four different problems" when they thought they had "one container that works") is exactly the outcome of treating "container security" as one undifferentiated property, when it is actually at least four independent controls, each addressing a genuinely different failure mode -- and "the container runs our Spark job correctly" says nothing about any of the four, because functional correctness and each of these security properties are entirely orthogonal.**

**Why unpinned dependencies is a reproducibility/provenance problem, distinct from the other three:** pip install pyspark pandas boto3 with no version constraints resolves to whatever the latest compatible versions happen to be AT BUILD TIME -- which can silently differ between builds, even from the identical Dockerfile, as upstream packages release new versions. This means "what exact code is running in production" is not a knowable, fixed fact -- it can change without any change to the team's own code. Pinning to exact versions with cryptographic hashes (via a lockfile) fixes this specific property: the same Dockerfile now always installs the identical bytes. This has no bearing on whether a secret is exposed, what user the process runs as, or whether the pinned versions themselves have known vulnerabilities -- it only fixes "is the build reproducible and its contents knowable."

**Why baking a secret into an image is a distribution problem, distinct from the other three:** a plaintext password set via ENV becomes part of an image layer -- and image layers are exactly the artifact that gets pushed to registries, pulled by any host with access, and potentially cached or archived indefinitely. Anyone with pull access to that image, at any point in its existence, can extract the plaintext value from any layer, even after the real password has been rotated in the actual database, because old images with the old secret baked in do not automatically stop existing. Injecting the credential at runtime from a secrets manager (never present in any image layer at all) fixes specifically this distribution exposure -- it has nothing to do with whether dependencies are pinned, what user the process runs as, or whether vulnerabilities have been scanned for.

**Why running as root is a least-privilege/blast-radius problem, distinct from the other three:** running the containerized process as root does not, by itself, cause a vulnerability -- but IF the process is ever compromised via any vulnerability (in the application code, a dependency, or the base OS), root privilege inside the container gives that compromise a materially larger blast radius (broader filesystem access, more capability to affect the host or other containers, depending on the container runtime's isolation) than a non-privileged user would. Declaring an explicit non-root USER fixes this specific dimension -- the privilege level available IF something goes wrong -- and has no bearing on whether something goes wrong in the first place, which is precisely why a non-root container can still be running unpinned, unscanned, known-vulnerable code; least privilege limits damage, it does not prevent the underlying issue.

**Why the absence of vulnerability scanning is a distinct, fourth problem -- known-CVE visibility -- that neither pinning, secret handling, nor non-root execution can substitute for:** pinning dependencies to exact versions tells you WHAT is running, but says nothing about whether those exact, pinned versions have disclosed security vulnerabilities. A perfectly reproducible, secret-free, non-root image can still contain a base OS package or Python library with a publicly known, critical CVE -- and none of the other three fixes would surface that fact. A dedicated scanning step (e.g. Trivy, run in CI against the built image) is what specifically answers "does this exact image contain known-vulnerable software," gating the build/deploy pipeline on that answer rather than assuming it because the other three controls happen to be in place.

**The general principle this generalizes to:** "container security" is not one property to fix with one action -- it decomposes into distinct controls (reproducibility/provenance, secrets handling, least privilege, vulnerability visibility, and others depending on the threat model) that must each be verified and fixed independently, because a container can be fully correct on any three of these dimensions while still failing the fourth, and no single fix -- however thorough -- substitutes for the others.
