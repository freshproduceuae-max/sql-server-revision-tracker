## Live Scenario
A bank's daily settlement process runs as three dependent Spark jobs: extract-and-cleanse raw transactions, compute per-customer settlement summaries, and generate a regulatory report from those summaries. A junior engineer wires all three together as one giant Spark job -- one SparkSession, one script, sequential Spark actions -- reasoning that 'Airflow is just extra infrastructure for what one script already does in order.' The very next month, the extract stage needs to be re-run alone after a late-arriving source file, and there is no way to do that without re-running the summary and report stages too, because none of the three stages' completion, inputs, or outputs are tracked independently -- everything lives inside one Python process's control flow.

## The Question
> Explain what an orchestrator (like Airflow) actually adds beyond 'run these steps in order' -- specifically per-task tracked state, independent re-runnability, and dependency management -- and why folding three logically separate jobs into one script's sequential Spark calls loses exactly the properties this bank's re-run requirement needed. Be explicit that this is a claim about ORCHESTRATION, not about Spark's own execution engine, which neither Airflow nor any orchestrator replaces.

## Solution Code
```python
# --- What the junior engineer actually built: one script, no orchestrator ---
# extract() writes cleansed transactions, then summarize() reads that
# output and writes summaries, then report() reads THAT and writes the
# regulatory report -- all three run inside ONE Python process, as
# ordinary sequential function calls with no independent state.
def run_settlement_pipeline_NAIVE(business_date):
    extract(business_date)     # Spark job 1 -- a real, independent unit of work
    summarize(business_date)   # Spark job 2 -- depends on job 1's OUTPUT DATA,
                                # not on Python control flow per se
    report(business_date)      # Spark job 3 -- depends on job 2's output
# Nothing here tracks "did extract() for 2026-08-21 actually complete
# successfully" as a fact independent of whether the WHOLE script ran to
# completion -- if summarize() or report() fails, or if extract() alone
# needs a re-run after a late file, there is no unit smaller than "the
# entire script" to re-trigger.

# --- What Airflow adds: each stage becomes a TRACKED TASK with its own
# state, independently re-runnable, with explicit dependencies ---
from airflow import DAG
from airflow.operators.python import PythonOperator
from datetime import datetime

with DAG(
    dag_id="daily_settlement",
    schedule="0 2 * * *",
    start_date=datetime(2026, 1, 1),
    catchup=False,  # deliberately False -- see T06 for why catchup=True
                     # (backfill) is a DIFFERENT, explicit decision, not a
                     # default to enable casually
) as dag:

    extract_task = PythonOperator(
        task_id="extract_transactions",
        python_callable=extract,
        op_kwargs={"business_date": "{{ ds }}"},
        retries=3,  # Airflow tracks retry attempts PER TASK, not per script
    )
    summarize_task = PythonOperator(
        task_id="summarize_settlements",
        python_callable=summarize,
        op_kwargs={"business_date": "{{ ds }}"},
        retries=2,
    )
    report_task = PythonOperator(
        task_id="generate_regulatory_report",
        python_callable=report,
        op_kwargs={"business_date": "{{ ds }}"},
        retries=1,
    )

    # EXPLICIT dependency declaration -- Airflow tracks that summarize_task
    # depends on extract_task's completion, and can independently know
    # "extract_task succeeded for 2026-08-21, summarize_task has not run
    # yet" as a fact, without re-running or even touching extract_task.
    extract_task >> summarize_task >> report_task

# --- The re-run this bank actually needed, now genuinely possible ---
# airflow tasks clear -t extract_transactions -s 2026-08-21 -e 2026-08-21 daily_settlement
# This re-runs ONLY extract_task for that one date -- Airflow's metadata
# database already recorded that summarize_task and report_task exist as
# separate tracked units; clearing just the upstream task and letting its
# downstream dependencies re-trigger (or not, depending on trigger rules)
# is the exact capability the single-script version had no mechanism for.
```

## Expected Output
Naive single-script version: re-running "just the extract stage" after
  a late-arriving file requires re-running summarize() and report() too,
  because nothing tracked extract()'s completion as a fact independent of
  the whole script's execution.

Airflow-orchestrated version: 'airflow tasks clear -t extract_transactions
  -s 2026-08-21 -e 2026-08-21' clears exactly the one task, for exactly
  one date, and lets its own downstream dependencies decide whether to
  re-trigger per their configured trigger rules -- because Airflow's
  metadata database tracks each task's completion, retries and
  dependencies as independent, queryable state, not as an artifact of
  one Python process's control flow.

What did NOT change between the two versions: extract(), summarize() and
  report() are still the same Spark jobs, doing the same Spark work, on
  the same Spark execution engine -- Airflow orchestrates WHEN and IN
  WHAT ORDER they run and tracks whether they succeeded; it does not
  replace, re-implement, or speed up Spark's own DataFrame/SQL execution.

## Explanation
**The junior engineer's "Airflow is just extra infrastructure for what one script already does in order" reasoning conflated two genuinely different things: the ORDER work happens in (which a plain script can express just fine) and the TRACKED, INDEPENDENTLY RE-RUNNABLE STATE of each unit of work (which a plain script's control flow cannot provide at all) -- and this bank's actual re-run requirement needed the second thing specifically.**

**Why "one script, sequential calls" genuinely does express the right ORDER:** there is nothing wrong with the naive version's sequencing -- extract before summarize before report is exactly the right dependency order, and a plain script expresses that correctly. The junior engineer was not wrong that the ORDER was already right; the mistake was concluding that getting the order right meant nothing else was missing.

**Why the missing piece was tracked, independent state per stage:** an orchestrator like Airflow maintains, for every task in a DAG, persistent metadata -- has this task run for this business date, did it succeed or fail, how many times has it been retried, what does it depend on -- as data in its own metadata store, entirely separate from whether any particular Python process is currently running. This is what makes "re-run just the extract stage for one date" a real, safe operation: Airflow already knows, independent of re-running anything else, that summarize_task and report_task are separate tracked units whose own state is unaffected by clearing and re-running extract_task alone. The naive single-script version has no equivalent concept -- extract(), summarize(), and report() are just three function calls inside one process's execution; nothing persists the fact that extract() completed successfully for a specific date as a fact independent of the process's overall exit status.

**Why explicit dependency declaration (extract_task >> summarize_task >> report_task) is more than syntax for expressing order:** this declaration is what lets Airflow reason about the DAG's structure -- which tasks can safely be cleared and re-run without necessarily re-running their downstream dependents, which tasks are blocked waiting on an upstream failure, which tasks could in principle run in parallel because they share no dependency edge. A sequence of Python function calls carries none of this as queryable structure; it is simply the order the interpreter executes statements in, with no separate representation an operator can inspect or act on independently.

**Why this is a claim about orchestration, not about Spark's execution engine, and why that distinction matters:** nothing about adding Airflow changes what extract(), summarize(), or report() actually do as Spark jobs -- they still run on the same Spark execution engine, with the same DataFrame operations, the same physical plans, the same cluster resources. Airflow's job is entirely about WHEN each of those jobs runs, in what order, with what retry policy, and whether its prior completion is tracked -- it orchestrates the scheduling and dependency layer, and does not replace, wrap, or reimplement Spark's own execution. A common and costly misunderstanding is expecting an orchestrator to somehow make the underlying jobs themselves faster or more correct -- it does neither; it only makes the SEQUENCING and RE-RUN behavior of already-correct, already-performant jobs manageable at the task level instead of the whole-script level.

**The general principle this generalizes to:** the moment a pipeline's stages have genuinely independent lifecycles -- different retry needs, different re-run scenarios, different failure-recovery requirements, as this bank's late-file-driven partial re-run demonstrates -- collapsing them into one script's control flow discards exactly the tracked, independently-actionable state that scenario needed, even though the sequencing itself was never the problem.
