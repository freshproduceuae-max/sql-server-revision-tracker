## Live Scenario
The card-authorization event schema (Avro, in the message registry) has been stable for a year: `{card_id, amount, merchant, ts}`. The payments team needs to add a `risk_score` field for a new fraud model, and separately wants to rename `merchant` to `merchant_name` for clarity. They push both changes in one deploy, directly editing the Avro schema file with no compatibility check. The very next Spark Structured Streaming micro-batch that consumes the new events throws a deserialization error and the job stops -- not on the new field, but on the rename: consumers still on the old schema definition are looking for a `merchant` field that no longer exists in the wire format, and Iceberg's downstream table (which reads by the old column name) breaks the same way.

## The Question
> Explain which of the two changes was actually safe and which one broke consumers, using Avro's forward/backward-compatibility rules and Iceberg's column-ID-based schema tracking, and redesign the rollout so both changes can ship without breaking any running consumer.

## Solution Code
```python
from pyspark.sql import SparkSession
from pyspark.sql.avro.functions import from_avro

spark = SparkSession.builder.appName("schema-evolution-safe-rollout").getOrCreate()

# --- Change 1: adding risk_score -- SAFE, if given a default ---
# Avro schema evolution rule: adding a field is backward-compatible (old
# readers can still read new-schema data) ONLY if the new field has a default
# value. Without a default, an old reader's schema has no slot for the field
# and Avro's schema-resolution rules cannot fill it in.
new_schema_with_default = """
{
  "type": "record", "name": "CardAuth",
  "fields": [
    {"name": "card_id", "type": "string"},
    {"name": "amount", "type": "double"},
    {"name": "merchant", "type": "string"},
    {"name": "ts", "type": "long"},
    {"name": "risk_score", "type": ["null", "double"], "default": null}
  ]
}
"""
# This alone -- shipped by itself, with a default -- would NOT have broken
# any consumer. It was safe. The break came from the second change.

# --- Change 2: renaming merchant -> merchant_name -- UNSAFE as a raw rename ---
# Avro has no "rename" primitive that preserves compatibility for readers
# still on the old schema; a straight field-name change is read by
# schema-resolution rules as "the old field was dropped and a new,
# unrelated field was added" -- which breaks any reader still expecting
# "merchant" by name, exactly as the deserialization error showed.
#
# The safe way to rename is Avro's own mechanism for this: an `aliases`
# entry, which lets a NEW schema still be matched by readers looking for
# the OLD field name during the transition window.
safe_rename_schema = """
{
  "type": "record", "name": "CardAuth",
  "fields": [
    {"name": "card_id", "type": "string"},
    {"name": "amount", "type": "double"},
    {"name": "merchant_name", "type": "string", "aliases": ["merchant"]},
    {"name": "ts", "type": "long"},
    {"name": "risk_score", "type": ["null", "double"], "default": null}
  ]
}
"""
# With the alias in place, data written under the NEW schema (writer uses
# "merchant_name") can still be resolved by a reader whose OWN schema still
# asks for "merchant" -- Avro's schema-resolution step consults the writer
# schema's aliases and maps the old reader field to it. This is what makes
# the rollout safe for readers who have not yet migrated; it is the writer
# schema's alias, resolved per read, not an unconditional guarantee that
# any two schema versions can read each other's data -- readers should
# still migrate to the new field name before the alias is eventually
# dropped, rather than treating the alias as a permanent equivalence.

# --- The Iceberg table side: column-ID tracking makes the SAME rename safe ---
# Iceberg does not match columns by name at read time -- it matches by a
# stable internal column ID assigned when the column was created. A rename
# in Iceberg (ALTER TABLE ... RENAME COLUMN) only changes the ID-to-name
# mapping in the metadata; existing data files, and any query already
# compiled against the old name via that ID, are unaffected.
spark.sql("ALTER TABLE lakehouse.payments.card_authorizations RENAME COLUMN merchant TO merchant_name")
spark.sql("ALTER TABLE lakehouse.payments.card_authorizations ADD COLUMN risk_score DOUBLE")
# Both are pure metadata operations in Iceberg -- no data files are rewritten,
# and old data files simply return NULL for risk_score on rows written before
# the column existed, per Iceberg's evolution guarantees.
```

## Explanation
**The failure was mis-diagnosed at first glance as "schema evolution is risky," when the actual cause was narrower: one specific kind of change (an unaliased rename) was unsafe, and it was shipped in the same deploy as a genuinely safe change (an additive field with a default), making it easy to blame "the schema change" generically instead of the specific operation.**

**Why the addition was safe:** Avro's schema resolution model compares a writer's schema (what produced the bytes) against a reader's schema (what the consumer expects) field by field. Adding a field with an explicit `default` value is backward-compatible because an old reader, encountering data written with the new schema, simply never asks for the new field -- and a new reader, encountering data written with the old schema (which has no `risk_score` at all), falls back to the declared default. Neither side errors. This is why the rejected deploy's failure was NOT on the new field -- if `risk_score` had shipped alone, the job would have kept running.

**Why the rename broke everything:** Avro resolves fields by name, not position. A schema with `merchant_name` instead of `merchant` is not "the same field, differently spelled" to Avro's resolution algorithm -- it looks like two independent changes: the `merchant` field was removed (any reader still asking for `merchant` gets nothing, and if the reader's schema marks that field as required with no default, deserialization fails outright, which is exactly the error observed) and an unrelated new field `merchant_name` was added. The fix is Avro's `aliases` mechanism, which explicitly tells the schema-resolution process "a reader asking for this old name should be satisfied by this field" -- this is the supported, compatible way to rename a field during a migration window, as opposed to a bare field-name edit.

**Iceberg's column-ID model solves the same class of problem differently, and this matters because the scenario has both an Avro wire-format layer and an Iceberg table layer that both needed to survive the rename.** Iceberg does not use field names as the durable identity of a column at all -- every column gets a permanent integer ID at creation time, and all reads resolve by ID internally, with the name being only a display-layer mapping in the current metadata. `ALTER TABLE ... RENAME COLUMN` in Iceberg is therefore a pure metadata edit: it changes which name maps to which ID, but every existing data file (written under the old name) and every column-ID-based read path continues to resolve correctly, because the ID never changed. This is also why adding `risk_score` as an Iceberg column is safe without needing an explicit default the way Avro requires one: Iceberg's own guarantee is that older data files simply return NULL for a column ID that did not exist when they were written, which is a property of Iceberg's read-time reconciliation, not something the schema author has to declare.

**The general contract-management rule:** every schema change needs to be classified against the compatibility rules of *each* layer it touches (the wire-format schema registry and the table format can have different rules for the same logical change), and "additive with a default" is close to universally safe while "rename" and "type-narrowing" changes need their layer's specific compatible mechanism (Avro aliases; Iceberg's ID-based rename) rather than being shipped as a raw edit.
