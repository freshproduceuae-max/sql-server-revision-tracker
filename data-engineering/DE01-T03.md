## Live Scenario
A transaction-banking analytics team currently queries the live operational database directly for their monthly reporting -- a normalized OLTP schema with transactions, accounts, customers, and branches spread across a dozen linked tables. Every report is a five-way join, reports are slow, and worse, a schema change made for the operational system (adding a new account-status column) silently broke three downstream reports nobody remembered existed. You are asked to design a reporting-friendly model that decouples analytics from the operational schema.

## The Question
> Design a star schema for monthly transaction-banking reporting from a normalized operational schema, and explain what specifically improves (and what specifically gets harder) compared to querying the operational tables directly.

## Solution Code
```sql
-- Operational (OLTP) schema: normalized, optimized for single-row writes
-- and referential integrity, not for scanning millions of rows at once.
-- Transactions, Accounts, Customers, Branches, CategoryLookup all live as
-- separate linked tables -- a monthly report joins all five.

-- Star schema: one fact table (grain = one row per transaction), and
-- denormalized dimension tables the fact table references directly.
CREATE TABLE DimAccount (
    AccountKey       INT IDENTITY PRIMARY KEY,   -- surrogate key, stable even if the source system's AccountID is reused
    AccountID        VARCHAR(20) NOT NULL,        -- natural/business key from the source system
    AccountType      VARCHAR(30) NOT NULL,
    BranchName       VARCHAR(100) NOT NULL,       -- denormalized from a separate Branches table -- one join fewer at query time
    CustomerSegment  VARCHAR(30) NOT NULL         -- denormalized from Customers
);

CREATE TABLE DimDate (
    DateKey     INT PRIMARY KEY,                  -- YYYYMMDD as an integer, not a DATE type -- see explanation
    FullDate    DATE NOT NULL,
    MonthName   VARCHAR(20) NOT NULL,
    Quarter     TINYINT NOT NULL,
    Year        SMALLINT NOT NULL
);

CREATE TABLE FactTransaction (
    TransactionID   VARCHAR(30) PRIMARY KEY,      -- grain: one row per transaction, stated explicitly
    AccountKey      INT NOT NULL REFERENCES DimAccount(AccountKey),
    DateKey         INT NOT NULL REFERENCES DimDate(DateKey),
    Amount          DECIMAL(18,2) NOT NULL,
    CategoryName    VARCHAR(50) NOT NULL           -- denormalized from CategoryLookup
);

-- The monthly report is now a single join against one small dimension,
-- not a five-way join across the operational schema:
SELECT d.MonthName, d.Year, a.CustomerSegment, SUM(f.Amount) AS TotalAmount
FROM FactTransaction f
JOIN DimDate d    ON f.DateKey = d.DateKey
JOIN DimAccount a ON f.AccountKey = a.AccountKey
WHERE d.Year = 2026
GROUP BY d.MonthName, d.Year, a.CustomerSegment;
```

## Expected Output
The reporting query above touches 2 tables instead of 5, and because `DimAccount`/`DimDate` are small and denormalized, the join is far cheaper than the operational five-way join it replaces. A schema change to the operational `Accounts` table (e.g. adding a new status column) no longer affects this report at all, because `DimAccount` is populated by a controlled load process, not queried live -- the report's schema only changes when the load process is deliberately updated.

## Explanation
**Denormalization here is a deliberate trade, not an oversight.** `DimAccount.BranchName` duplicates data that also lives in a separate `Branches` table in the operational schema -- normalized design would call that redundant. In a star schema it's correct: it removes a join from every single report query, at the cost of needing an explicit reload if a branch is renamed (an acceptable trade, since branch renames are rare and reports run constantly).

**`DateKey` as an integer (`YYYYMMDD`), not a `DATE` type, is a real and common star-schema convention** -- it joins faster than a `DATE` column in some engines, sorts correctly as a number, and lets `DimDate` carry pre-computed attributes (`MonthName`, `Quarter`, fiscal-year fields) that would otherwise need to be recalculated in every single query.

**What gets harder, stated honestly:** the star schema is now a second copy of the data that must be kept in sync with the operational system via an explicit load process (this is exactly what Chapter 3's ETL/ELT and SCD lessons build) -- and it will always lag the operational system by however long that load process takes to run. A report needing truly live, to-the-second data is the wrong use case for a star schema; that's what querying the operational system directly (accepting its performance cost) is actually for.

**This builds directly on Data Validation G14** (Data Warehouse & SCD-Specific techniques), which already covers dimensional-model validation mechanics -- surrogate keys, grain violations, fact-to-dimension resolution. That lesson assumes you already know what those checks are for; this lesson is where the *design* comes from that G14 later validates.
