## Live Scenario
A transaction-banking data platform needs to ingest daily FX rate data from a third-party provider's REST API. The API returns paginated results (500 rates per page), rate-limits at 60 requests per minute, and occasionally returns a transient 503 while the provider's own systems are under load. A first attempt at the ingestion script works in testing against a handful of pages, then fails in production on page 40 of 60 with no useful error message, and the team has no way to tell whether it needs to restart from page 1 or can resume from where it stopped.

## The Question
> Write a resilient REST API ingestion function that handles pagination, respects a rate limit, retries a transient failure with backoff, and can resume from the last successfully-fetched page rather than restarting from scratch.

## Solution Code
```python
import time
import requests
from dataclasses import dataclass


@dataclass
class FetchState:
    """Persisted after every successful page, so a restart resumes from
    here instead of page 1 -- the exact gap in the original script that
    made a page-40 failure indistinguishable from a page-1 failure."""
    next_page: int
    pages_fetched: int


def fetch_fx_rates(base_url: str, api_key: str, state: FetchState) -> list[dict]:
    all_rates: list[dict] = []
    session = requests.Session()
    session.headers["Authorization"] = f"Bearer {api_key}"

    while True:
        response = _get_with_retry(
            session, f"{base_url}/rates", params={"page": state.next_page, "page_size": 500}
        )
        payload = response.json()
        all_rates.extend(payload["rates"])

        state.pages_fetched += 1
        state.next_page += 1
        _persist_state(state)  # so a crash here resumes from state.next_page, not page 1

        if not payload.get("has_more", False):
            break
        time.sleep(1.05)  # 60 req/min limit -> stay just under one request per second

    return all_rates


def _get_with_retry(session: requests.Session, url: str, params: dict, max_attempts: int = 4) -> requests.Response:
    """Retries only on transient failures (429 rate-limited, 503 unavailable),
    with exponential backoff -- retrying a 404 or 401 would just repeat a
    failure that backoff cannot fix, and would burn through the retry budget
    hiding a real, permanent problem (a bad API key, a wrong URL)."""
    for attempt in range(1, max_attempts + 1):
        response = session.get(url, params=params, timeout=10)
        if response.status_code in (429, 503) and attempt < max_attempts:
            wait = 2 ** attempt  # 2s, 4s, 8s
            time.sleep(wait)
            continue
        response.raise_for_status()  # raises for any other 4xx/5xx immediately, no retry
        return response
    raise RuntimeError(f"exhausted {max_attempts} retry attempts against {url}")


def _persist_state(state: FetchState) -> None:
    """In production this writes to a small durable store (a database row,
    a checkpoint file) -- the specific mechanism matters less than the
    principle: state that survives a crash is what makes resume possible."""
```

## Expected Output
On a simulated run where the provider's API returns a 503 on page 23, the retry logic waits 2s, then 4s, then succeeds on the third attempt and continues from page 23 -- the job completes without operator intervention. On a simulated hard failure (the process is killed) after page 40, restarting the job with the persisted `FetchState(next_page=41, ...)` resumes from page 41 instead of re-fetching (and double-counting) pages 1-40.

## Explanation
**Retrying only specific status codes (429, 503) is deliberate, not an oversight.** A 401 (bad credentials) or 404 (wrong URL) will never succeed no matter how many times it's retried -- retrying those anyway just delays the failure and makes the eventual error message harder to find in the logs. `response.raise_for_status()` for anything else fails immediately and loudly.

**Exponential backoff (`2 ** attempt`) exists specifically for rate limits and transient overload**: a fixed short retry delay against a rate-limited API just gets rate-limited again immediately; backing off gives the provider's system time to recover, and is the polite, expected pattern most API providers explicitly document.

**Persisting `FetchState` after every page, not just at the end, is what makes the job resumable rather than merely retriable.** A job that only checkpoints at completion still restarts from zero on any mid-run failure -- exactly the page-40 problem in the scenario. This is the same idempotent, re-runnable design principle Chapter 3 covers for full ETL/ELT pipelines; here it's applied at the scale of a single ingestion function.

**Rate-limit compliance (`time.sleep(1.05)` for a 60/min limit) is a real operational requirement, not a nicety** -- exceeding a documented rate limit commonly gets a service account temporarily blocked entirely, turning a slow-but-working job into a fully broken one.
