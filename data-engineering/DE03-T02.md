## Live Scenario
A nightly Spark job appends the day's settled transactions from the payments platform into a Delta/Iceberg table using `df.write.mode("append")`. On 2026-08-19, the job runs, writes 1.2 million rows, and then fails during a downstream step (an unrelated notification service times out) after the write has already committed. The on-call engineer, following the standard runbook of "if last night's job failed, re-run it," re-triggers the full pipeline the next morning without checking whether the write step had already completed. The re-run reads the same day's 1.2 million source rows and appends them again -- the table now has 2.4 million rows for that day, and every downstream balance reconciliation report for 2026-08-19 is silently double-counted.

## The Question
> Explain why 'append' plus 'just re-run it on failure' is unsafe here, and design the pipeline so that re-running it after a partial failure -- for any reason, at any point -- produces the same final table state as running it exactly once.

## Solution Code
```python
from pyspark.sql import SparkSession
from pyspark.sql import functions as F
from delta.tables import DeltaTable

spark = SparkSession.builder.appName("idempotent-transaction-load").getOrCreate()

BUSINESS_DATE = "2026-08-19"
target_table = "lakehouse.payments.settled_transactions"

# Read this run's source data, tagged with the business date it represents --
# this tag is what makes the write idempotent, not a property of "append" itself.
source_df = (
    spark.read.parquet(f"s3://payments-platform/settled/date={BUSINESS_DATE}/")
    .withColumn("business_date", F.lit(BUSINESS_DATE))
)

if spark.catalog.tableExists(target_table):
    target = DeltaTable.forName(spark, target_table)

    # MERGE, not append: match on the natural key (transaction_id) plus the
    # business_date partition. Re-running this exact job for the exact same
    # business_date, any number of times, produces the same final rows --
    # matched rows are overwritten with identical values, not duplicated.
    (
        target.alias("t")
        .merge(
            source_df.alias("s"),
            "t.transaction_id = s.transaction_id AND t.business_date = s.business_date"
        )
        .whenMatchedUpdateAll()
        .whenNotMatchedInsertAll()
        .execute()
    )
else:
    source_df.write.format("delta").partitionBy("business_date").saveAsTable(target_table)

# A second, independent idempotency guard: an explicit re-runnable "replace
# this partition" pattern for jobs where MERGE's per-row semantics aren't
# needed and a whole business_date can simply be replaced atomically.
def replace_partition_idempotent(spark, source_df, target_table, business_date):
    (
        source_df.write
        .format("delta")
        .mode("overwrite")
        .option("replaceWhere", f"business_date = '{business_date}'")
        .partitionBy("business_date")
        .saveAsTable(target_table)
    )
    # replaceWhere makes this safe to re-run: every re-run for the same
    # business_date atomically replaces exactly that partition's rows,
    # regardless of how many times it has already run or where a prior
    # run failed -- there is no "append on top of a partial write" case.
```

## Expected Output
First run,  business_date=2026-08-19: table has 1,200,000 rows for that date.
Job fails downstream (notification timeout) AFTER the write already committed.
Re-run,     business_date=2026-08-19: MERGE matches all 1,200,000 existing rows
            on (transaction_id, business_date) and updates them in place --
            table STILL has 1,200,000 rows for that date, not 2,400,000.
Re-run again (e.g. a third manual retry): same result -- 1,200,000 rows.

## Explanation
**The root cause was not "the job failed" -- failures are normal and expected in any production pipeline. The root cause was that the write step's semantics (blind append) were not safe to repeat.** `append` mode has no concept of "have I already written this data" -- it has no natural key, no dedup, and no memory of prior runs. Every execution, successful or partially failed, adds its rows on top of whatever is already there. Re-running an append-mode job after a partial failure is therefore not "retrying the job," it is "running a second, independent job that happens to write the same table" -- and nothing prevents both runs' output from coexisting.

**MERGE fixes this by making the write's outcome a function of the data, not a function of how many times the job has run.** Matching on `(transaction_id, business_date)` means: if a row for that transaction and date already exists, update it (to the same values, since the source data for a settled historical date does not change) rather than inserting a duplicate. Run the job once, five times, or fail-and-retry ten times for the same business date, and the final table state is identical -- this is the definition of idempotent.

**The `replaceWhere` partition-overwrite pattern is a second valid idempotent design**, better suited when a job's natural unit of work is "the whole of business_date X," not "row-by-row reconciliation." Instead of matching individual rows, it atomically replaces the entire partition for that date on every run. This is simpler than MERGE when the source data for a given business date is itself a complete, self-consistent extract (as in this scenario), and it sidesteps a subtlety MERGE has: MERGE assumes the source is complete for the matched keys, but if a re-run's source extract is itself incomplete (e.g. a partial re-export), MERGE's `whenNotMatchedInsertAll` would still add rows without removing anything -- `replaceWhere` avoids that ambiguity by making "replace this partition, in full, every time" the explicit contract.

**Checkpointing matters for a different reason on the streaming side of the same problem**: a streaming job that crashes mid-micro-batch relies on its checkpoint (the committed offset range from the last completed batch) to know exactly which records it has already processed, so a restart resumes from the correct offset rather than reprocessing or skipping data. Idempotent sinks plus checkpointed offsets are what jointly give Structured Streaming its exactly-once guarantee end-to-end -- the checkpoint alone is not sufficient without an idempotent write, and an idempotent write alone (as in this batch example) does not need a streaming checkpoint at all, because the "which business date am I responsible for" bookkeeping is external to Spark, not tracked in a Spark-managed checkpoint.

The rule that generalizes past this one scenario: **before choosing a write mode, ask what happens if this exact job runs twice for the exact same input.** If the answer is "duplicate data," the write is not safe to retry, and a production runbook that says "just re-run it on failure" is silently building an assumption the write mode does not actually guarantee.
