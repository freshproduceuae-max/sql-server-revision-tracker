## Live Scenario
A nightly job aggregates total transaction volume per customer across 500 million transaction-banking rows, partitioned by `CustomerID`. The job runs in 40 minutes most nights. Once a month, after a major corporate payroll batch runs through one specific high-volume merchant-services account, the same job takes over 4 hours -- and the Spark UI shows 199 of 200 tasks in the final aggregation stage finish within seconds of each other, while exactly 1 task runs for the full 4 hours alone.

## The Question
> Diagnose why one task can dominate the runtime of an otherwise-parallel job, and apply the two standard mitigations -- salting the skewed key, and enabling Spark's built-in skew-join handling -- explaining what each one actually does differently.

## Solution Code
```python
from pyspark.sql import functions as F
from pyspark.sql.window import Window

# DIAGNOSIS: a groupBy/aggregation shuffles rows so all rows sharing the same
# key land on the same partition/task. If one CustomerID (the merchant-
# services account) has vastly more transactions than any other single
# customer that month, ALL of those rows funnel into ONE task -- while the
# other 199 tasks each handle a normal, roughly-equal share. Total cluster
# parallelism collapses to "1 task's worth of work" for that single skewed
# partition, which is exactly the 199-fast-1-slow pattern in the Spark UI.

# MITIGATION 1: salting -- artificially split the skewed key into several
# sub-keys so its rows spread across multiple tasks, then combine the partial
# results. This changes the actual partitioning, not just a config setting.
SALT_BUCKETS = 20

salted = transactions.withColumn(
    "salt", (F.rand() * SALT_BUCKETS).cast("int")
).withColumn(
    "salted_customer_id", F.concat(F.col("CustomerID"), F.lit("_"), F.col("salt"))
)

partial_totals = (
    salted.groupBy("salted_customer_id", "CustomerID")
    .agg(F.sum("Amount").alias("partial_total"))
)

# Combine the salted partial sums back to one row per real CustomerID -- this
# second, much smaller aggregation is cheap because the skewed customer's
# rows are now spread across 20 partial totals instead of 1 giant one.
final_totals = (
    partial_totals.groupBy("CustomerID")
    .agg(F.sum("partial_total").alias("total_amount"))
)

# MITIGATION 2: Spark's own Adaptive Query Execution (AQE) skew-join handling
# -- enabled by default since Spark 3.2. It detects skew AT RUNTIME from
# actual shuffle-file statistics (not a guess made before execution) and
# automatically splits an oversized partition into smaller sub-partitions
# for a SORT-MERGE JOIN specifically -- a narrower, automatic version of the
# manual salting technique above, but it does not apply to a plain groupBy
# aggregation the way manual salting does.
spark.conf.set("spark.sql.adaptive.enabled", "true")             # default true since 3.2
spark.conf.set("spark.sql.adaptive.skewJoin.enabled", "true")    # default true since 3.2
```

## Expected Output
Salting spreads the skewed `CustomerID`'s rows across 20 salted sub-keys, so the first aggregation stage's task-time distribution flattens from "199 fast + 1 four-hour task" to roughly even task durations across all 200+20 partitions -- the second, combining aggregation is cheap since it operates on already-pre-aggregated partial sums, not the original 500 million raw rows. AQE's skew-join handling, checked via the Spark UI's SQL tab after a run with a join present, shows the physical plan annotated with split skewed-partition sub-tasks -- confirming the runtime detection and automatic splitting actually took effect for that join, without any manual salting code.

## Explanation
**A shuffle is Spark physically moving data across the network so that rows sharing a key land on the same executor/partition** -- required for any wide transformation: `groupBy`, `join`, `distinct`, `repartition`. It is one of the most expensive operations in Spark specifically because it involves disk I/O, network I/O and serialization, unlike a narrow transformation (`filter`, `select`) that Spark can execute within each partition independently with no data movement at all.

**Skew is a distribution problem a shuffle cannot avoid by design**: the shuffle's whole mechanism is "same key, same destination partition," so if one key genuinely has 100x the rows of any other key, that destination partition inherits 100x the work, and Spark's parallelism (many tasks running concurrently) cannot help a single task that is itself enormous -- there's nothing left to parallelize once all of one key's rows have already landed together.

**Salting and AQE skew-join handling solve the same problem via genuinely different mechanisms, which is why the lesson teaches both rather than treating them as interchangeable.** Salting is a *data transformation* the engineer writes explicitly, and it works for any wide operation including a plain `groupBy` aggregation (as in this scenario). AQE's skew-join handling is *automatic, runtime, join-specific* behavior built into Spark's own Adaptive Query Execution framework (default-on since Spark 3.2) -- it detects skew from actual shuffle-file statistics after the initial shuffle has already happened, then re-splits the oversized partition for a sort-merge join specifically. Knowing which one actually applies to a given operation (aggregation vs. join) is the difference between a fix that works and a config flag that quietly does nothing for this particular job shape.

**`repartition()` vs `coalesce()` matter here too, though this scenario doesn't need them directly**: `repartition(n)` always triggers a full shuffle to redistribute data into exactly `n` partitions (useful to fix skew or increase parallelism); `coalesce(n)` avoids a full shuffle by only merging existing partitions together, which is cheaper but can only reduce partition count, never increase it or fix an uneven distribution the way `repartition()` can.
